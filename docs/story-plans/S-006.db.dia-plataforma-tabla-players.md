# Story Plan: S-006 (db) - Día de la plataforma y tabla players

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-006](../stories/S-006.dia-plataforma-tabla-players.md)
- **Servicio:** db
- **Resumen:** Agrega a `@nerdose/db` la primera tabla de negocio: los enums de PostgreSQL `locale` y `code_language`, la tabla `players` (jugador anónimo, sin PII) con el índice `idx_players_created_at`, y la migración versionada `0001_players` (generada con drizzle-kit + `GRANT SELECT, INSERT, UPDATE ON players TO nerdose_api` manual, forward-only). Es la base de persistencia de la que dependen `POST /api/session` y `PATCH /api/me/preferences` (S-007) y el estado del día (S-008).

> **Alcance de este plan:** solo el servicio `db` (`packages/db`). CA-5 (migración de `players`) y CA-6 (permisos por rol) son de `db`. CA-1 a CA-4 (`platform-day` y enums de `@nerdose/core`) ya están implementados en `S-006.core` (Completed) y acá solo se **consumen** (`LOCALES`, `CODE_LANGUAGES`).
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a la raíz del paquete, `packages/db/`, salvo que se indique lo contrario.
>
> **Nota sobre CA-5:** la story dice "la base con la migración `0000`". Se interpreta como: la base ya tiene aplicada `0000_roles_and_grants` (S-002) y esta story agrega `0001_players`; la migración `0000` **no se edita** (las migraciones aplicadas son inmutables, convención `orm`). CA-6 confirma el nombre `0001_players`.
>
> **Fuera de alcance:** repositorios (`IdentityRepository` vive en `apps/api`, S-007), cualquier otra tabla del DBML (`plays`, `challenges`, etc.), `seed:dev`, el enum `game_id` de PostgreSQL (lo crea la story que agregue `challenges`/`plays`), y el parseo de `LAUNCH_DATE`.

### ADRs Relevantes

#### ADR-004: PostgreSQL como única base, con propiedad por roles

- **Decisión:** PostgreSQL 16 como única base (`nerdose-db`); la frontera entre servicios se hace cumplir en la base con tres roles: dueño del schema (DDL, solo migraciones), `nerdose_api` (lectura y escritura de `players`, `plays`, `player_game_stats`, `player_stats`, `challenge_reports`, `rejected_guesses`; `INSERT`/`SELECT` en `generation_requests`; `SELECT` y `UPDATE` por columna en `challenges`; `SELECT` y `UPDATE (status, rejection_reason)` en `terms`/`timeline_facts`; `SELECT` de `job_runs` y vistas `metrics_*`) y `nerdose_generator` (lectura y escritura de `challenges`, `terms`, `timeline_facts`, `generation_requests`, `generation_failures`, `job_runs`).
- **Reglas de Implementación (verbatim):**
  - La única base MUST ser PostgreSQL ≥ 16. MUST NOT agregarse otra base (Redis, MongoDB, SQLite) en v1.
  - Los campos que varían por juego (`challenges.payload`, `challenges.verification`, `plays.state`, `plays.result`, `player_game_stats.extra`, `challenge_reports.context`, `job_runs.summary`) MUST ser `jsonb`.
  - Los textos de contenido bilingües MUST guardarse como `jsonb` con la forma `{ "es": string, "en": string }`.
  - Las fechas de día MUST ser `date` (día UTC). Los instantes MUST ser `timestamptz`.
  - Los ids MUST ser `uuid` (`gen_random_uuid()`), salvo las PK compuestas o naturales que define `docs/db-schemas/nerdose-db.md`.
  - La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
  - Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db`, con permisos por columna sobre `challenges`, `terms` y `timeline_facts` exactamente como en la tabla de arriba.
  - La unicidad de un Challenge vigente MUST implementarse como índice único parcial sobre `(game_id, date)` con `WHERE status IN ('approved','published','voided')`.
  - `plays` MUST tener `UNIQUE (player_id, challenge_id)` y `challenge_reports` MUST tener `UNIQUE (player_id, challenge_id)`.
  - Los enums del dominio (`game_id`, `challenge_status`, `play_status`, `code_language`, `locale`, etc.) MUST ser enums de PostgreSQL con los valores exactos del análisis de dominio.
- **Riesgo explícito y mitigación:** "una migración olvida los `GRANT` de una tabla nueva y un servicio falla en producción" → "test de integración que corre con cada rol las operaciones esperadas sobre una base migrada" (Tarea 3).

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables)

- `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
- `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa) y `./notify` (solo Node). (`@nerdose/db` importa solo `.`.)
- MUST NOT haber dependencias entre apps. Lo compartido va en `packages/`.

#### ADR-009: Identidad del jugador anónimo (reglas aplicables a la tabla)

- El nombre de la cookie MUST ser `nd_pid` y su valor MUST ser el `players.id` (UUID v4) tal cual.
- Al crear un Player, `locale` MUST salir de `Accept-Language` si es `es` o `en`, y si no, `es`. `preferred_code_language` MUST ser `js`. (La lógica es de la `api`; la tabla aporta los defaults `es`/`js`.)
- MUST NOT guardarse PII del jugador (ni IP, ni email, ni fingerprint) en `players`. El `user_agent` solo se guarda en el `context` de un reporte.
- `players.user_id` (nullable) queda reservado para enlazar un `User` en el futuro.

### Convenciones activas (extracto aplicable)

#### `orm` (Drizzle)

- Estructura: `packages/db/src/schema/` "Drizzle schema, one file per table group"; `migrations/` "drizzle-kit SQL + manual SQL (partial indexes, triggers, views, GRANT)".
- Migraciones:
  ```bash
  pnpm --filter @nerdose/db db:generate --name add_challenge_reports   # generate SQL
  pnpm --filter @nerdose/db db:migrate                                  # apply, with DATABASE_URL_OWNER
  ```
- "A migration that creates a table MUST include the `GRANT`s for `nerdose_api` and `nerdose_generator` (column-level on `challenges`, `terms`, `timeline_facts`, per ADR-004)." Para `players` el `generator` **no** recibe permisos (ADR-004 / `nerdose-db.md`).
- Reglas (verbatim, las aplicables):
  - The Drizzle schema and the migrations live only in `@nerdose/db`. Services MUST NOT declare tables.
  - Use types inferred from the schema (`typeof table.$inferSelect`) or from `@nerdose/db`. No hand-written types that duplicate the schema.
  - Day columns are `date` (UTC day) and instants are `timestamptz`. Do not convert them with local timezones.
  - Raw SQL only for what Drizzle cannot express (see How to use). Document why in a one-line comment.
  - Migrations are forward-only, reviewed by hand, and committed together with the schema change. Never edit an applied migration.
  - Migrations run before starting `api` and `generator`, with the owner role. Services do not run migrations at startup.
  - Each service MUST only write the tables and columns its role allows (ADR-004). A test runs the expected operations with each role.
- Ejemplo de consumo futuro (S-007, `apps/api`), que fija los nombres exportados:
  ```ts
  import { eq } from 'drizzle-orm';
  import { players } from '@nerdose/db';
  import type { Db, Tx } from '@nerdose/db';

  export class IdentityRepository {
    constructor(private readonly db: Db | Tx) {}
    async findById(id: string) {
      const [row] = await this.db.select().from(players).where(eq(players.id, id));
      return row ?? null;
    }
  }
  ```

### Contexto de Base de Datos

**Enums nuevos (DBML de `nerdose-db.md`, verbatim):**

```dbml
Enum locale {
  es
  en
}

Enum code_language {
  js
  go
  java
}
```

**Tabla `players` (DBML verbatim, `nerdose-db.md` l. 140):**

```dbml
Table players {
  id uuid [pk, default: `gen_random_uuid()`, note: 'Valor de la cookie nd_pid (UUID v4)']
  locale locale [not null, default: 'es']
  preferred_code_language code_language [not null, default: 'js']
  user_id uuid [null, note: 'Reservado para enlazar un User (fuera de v1). Sin FK hasta que exista la tabla users']
  created_at timestamptz [not null, default: `now()`]
  last_seen_at timestamptz [not null, default: `now()`]

  indexes {
    created_at [name: 'idx_players_created_at']
  }

  Note: 'Jugador anónimo. Sin PII. Se crea en POST /api/session'
}
```

- **Relaciones:** ninguna saliente. `players.user_id` **no** tiene FK en v1. Tablas futuras (`plays`, `player_game_stats`, `player_stats`, `challenge_reports`, `rejected_guesses`) referenciarán `players.id` con `ON DELETE RESTRICT` (fuera de alcance).
- **Índice:** `idx_players_created_at (created_at)`, BTREE (métricas futuras).
- **Permisos (`nerdose-db.md` l. 490, filtrado a `players`):**
  ```sql
  GRANT SELECT, INSERT, UPDATE ON players TO nerdose_api;
  ```
  - `nerdose_generator`: **sin acceso** a `players` ("El `generator` no puede tocar jugadores, partidas ni reportes").
  - "Ningún rol de servicio tiene `DELETE`, DDL ni `TRUNCATE`."
- **Sin PII:** `players` no tiene IP, email ni fingerprint.
- **Estrategia de migraciones (`nerdose-db.md`):**
  1. Se modifica el schema en `packages/db/src/schema/`, o se agrega un archivo SQL manual para vistas, triggers o grants.
  2. `pnpm --filter @nerdose/db db:generate --name <cambio>` genera la migración SQL.
  3. Se revisa el SQL generado. Si la migración crea una tabla, MUST incluir sus `GRANT` para `nerdose_api` y `nerdose_generator`.
  4. Se commitea la migración junto con el schema.
  5. Antes de levantar `api` y `generator`, se aplica con `pnpm --filter @nerdose/db db:migrate` usando el rol `nerdose_owner` (`DATABASE_URL_OWNER`).
- **Rollback:** forward-only; para revertir se escribe una migración nueva.
- **Registro de migraciones:** `drizzle.__drizzle_migrations` (columnas `id`, `hash`, `created_at`). Hoy tiene **1** fila (`0000_roles_and_grants`); tras esta story, **2**.
- **Estado de `migrations/meta/`:** `_journal.json` con una entrada (`idx: 0`, `tag: "0000_roles_and_grants"`, `breakpoints: true`); `0000_snapshot.json` con `tables: {}` y `enums: {}`. `drizzle-kit generate` comparará el schema nuevo contra ese snapshot y producirá `0001_players.sql` + `0001_snapshot.json` + entrada `idx: 1` en el journal.

**SQL esperado de `0001_players.sql`** (forma que genera drizzle-kit 0.31 + `GRANT` manual al final; el implementador verifica el generado contra esto):

```sql
CREATE TYPE "public"."code_language" AS ENUM('js', 'go', 'java');--> statement-breakpoint
CREATE TYPE "public"."locale" AS ENUM('es', 'en');--> statement-breakpoint
CREATE TABLE "players" (
	"id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
	"locale" "locale" DEFAULT 'es' NOT NULL,
	"preferred_code_language" "code_language" DEFAULT 'js' NOT NULL,
	"user_id" uuid,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL,
	"last_seen_at" timestamp with time zone DEFAULT now() NOT NULL
);
--> statement-breakpoint
CREATE INDEX "idx_players_created_at" ON "players" USING btree ("created_at");--> statement-breakpoint
GRANT SELECT, INSERT, UPDATE ON players TO nerdose_api;
```

### Contexto de Flujos

**primera-visita-y-sesion** (`docs/flows/primera-visita-y-sesion.md`) — pasos que tocan `nerdose-db`:

- Participante `nerdose-db`: "Guarda `players` y lee `plays`, `player_game_stats` y `player_stats`" (Procesador).
- `POST /api/session` con cookie válida y Player existente: `A->>DB: UPDATE players SET last_seen_at`.
- Sin cookie válida: `A->>DB: INSERT players` con `INSERT INTO players (locale, preferred_code_language) VALUES (pickLocale(Accept-Language), 'js')`.
- Evento de dominio `PlayerCreated` (`player_id`, `locale`): solo logs.
- `Set-Cookie: nd_pid=<players.id>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=34560000`.
- Estado final: "Player: fila en `players` con `locale` y `preferred_code_language`, y `last_seen_at` actualizado."
- `number` del día puede ser `null` (lo resuelve `core`, no `db`).

**preferencias-y-share** (vía REQ-002): `UPDATE players SET locale = $1 WHERE id = $2` con el rol `nerdose_api`.

**cambio-de-dia-y-publicacion:** no toca `players` (usa `nextResetAt`/`secondsToReset` de `core`). Sin impacto en `db`.

**Lo que esta story agrega a los flujos:** la tabla y los permisos que hacen posibles los `INSERT`/`UPDATE`/`SELECT` de arriba con `nerdose_api`. No implementa los pasos de la `api`.
