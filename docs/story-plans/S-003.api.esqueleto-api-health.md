## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript con `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`, `module: ESNext`, `moduleResolution: bundler`, `verbatimModuleSyntax: true`, `skipLibCheck: true`, `noEmit: true` (heredado de `tsconfig.base.json` de la raíz).
- **Runtime:** Node.js 24 LTS (`engines.node` `">=24 <25"` en la raíz), pnpm `11.6.0`, Turborepo (`turbo run dev|lint|typecheck|test`). Los paquetes internos se consumen como fuente TS (`exports` → `./src/index.ts`, sin build).
- **HTTP:** `hono` (incluye `hono/secure-headers`, `hono/request-id`, `hono/factory`) + `@hono/node-server`. Prohibidos Express, Fastify y NestJS (ADR-002).
- **Base de datos:** PostgreSQL 16 a través de `@nerdose/db` (`createDb(url)` → `{ db, sql }`, Drizzle sobre postgres.js). La `api` se conecta como `nerdose_api`.
- **Entorno:** `@t3-oss/env-core` (`^0.13.11`, la misma versión que `@nerdose/db`) + `zod` (`^4.6.7`, la misma que `@nerdose/core`); `dotenv` solo para cargar `.env.local` en desarrollo.
- **Logs:** `pino` (runtime) y `pino-pretty` (solo `NODE_ENV=development`).
- **Scripts:** `tsx` (`tsx watch src/index.ts` para `dev`; `node --import tsx` en los tests de proceso).
- **Tests:** Vitest `^5.1.0` + `@testcontainers/postgresql` (`^12.2.1`, la misma que `@nerdose/db`). Integración contra PostgreSQL 16 real; nunca se mockea la base.
- **Errores:** `AppError` / `ERROR_CATALOG` / `ErrorCode` de `@nerdose/core`.
- **Versiones de dependencias nuevas** (`hono`, `@hono/node-server`, `pino`, `pino-pretty`): las vigentes al instalar con `pnpm --filter api add ...`, con rango `^`. La documentación no fija versiones.

### Arquitectura del Servicio

- **Tipo:** api (node). Vive en `apps/api`. Nombre del paquete: `api` (los filtros de pnpm de la documentación usan `pnpm --filter api ...`).
- **Propósito (overview):** única interfaz HTTP del backend. Sirve a `web` (`/api/*`) y a `admin` (`/api/admin/*`). **Nunca ejecuta código** ni llama a APIs externas, salvo el SMTP de alertas (que no entra en esta story).
- **Módulos de dominio (manifest):** `identity`, `gameplay`, `progress`, `quality`, `publishing`, `admin`. Ninguno se implementa en esta story: el health no tiene lógica de dominio y vive en `http/` + `infra/database/`.
- **Convenciones activas usadas en esta story:** `_base`, `http-server`, `error-handling`, `env-config`, `logging`, `orm`, `testing`, `game-registry`. `security` se aplica solo en `secureHeaders()` y "sin CORS"; los middlewares de `Origin`/`Content-Type`, `bodyLimit` y el rate limit llegan con la primera mutación (Feature Group 2), por decisión de REQ-001.

**Estructura objetivo de esta story** (subconjunto de `http-server` + `_base` + `game-registry`):

**Patrones:**
- `buildApp(deps)` construye la app con sus dependencias inyectadas, para que los tests la instancien con las suyas (`http-server`).
- Los handlers no acceden a la base: el ping vive en `infra/database` y el handler llama a `deps.health.check(...)` (`orm`, `http-server`).
- Fábricas en lugar de singletons con efectos al importar (`createLogger`, `createDatabase`, `loadEnv`), para poder testear con entornos y destinos propios.

**Manejo de errores (`error-handling`):** catálogo cerrado en `@nerdose/core`; forma `{ "error": { "code", "message" } }` sin campos extra; `AppError` → status del catálogo + log `warn` sin stack; cualquier otro error → log `error` con stack y `500 internal_error` con mensaje genérico; nunca stack, SQL ni detalles internos en la respuesta.

**Logging (`logging`):** un único logger Pino por servicio; child logger por request con `requestId`; primer argumento objeto de contexto, segundo argumento mensaje corto y **estático** (sin interpolar); nunca se loguean secretos (la `DATABASE_URL` incluye contraseña: no se loguea); en tests `LOG_LEVEL=silent` o un destino de captura.

### ADRs Relevantes

#### ADR-001: Mapa de servicios
- **Decisión:** 4 servicios (`web`, `admin`, `api`, `generator`) y un PostgreSQL compartido, sin bus ni Redis. `api` es la única interfaz HTTP.
- **Reglas de Implementación (verbatim):**
  - Los servicios MUST ser exactamente `web`, `admin`, `api` y `generator`, en `apps/web`, `apps/admin`, `apps/api` y `apps/generator`.
  - `api` MUST ser la única interfaz HTTP del backend. `generator` MUST NOT abrir ningún puerto ni exponer endpoints.
  - `api` MUST NOT ejecutar código (no `child_process`, `vm`, `eval` ni equivalentes) y MUST NOT llamar a APIs externas, salvo el envío de mail de alertas (ADR-013).
  - `generator` MUST ser el único proceso que hace `INSERT` en `challenges`, `terms` y `timeline_facts`.
  - `web` y `admin` MUST hablar solo con `api` (más Plausible en `web`, si está activo). MUST NOT acceder a la base.
  - MUST NOT agregarse Redis, RabbitMQ, Kafka, BullMQ ni ningún broker en v1.
  - Debe haber una sola instancia de `api` en v1. Las caches y el rate limit en memoria dependen de eso (ADR-012).
- **Nota:** el código de **producción** de `apps/api/src` no usa `child_process`. Los tests de proceso (`test/`) sí usan `node:child_process` para lanzar la `api` y verificar el arranque; eso no es código de la `api`.

#### ADR-002: Stack tecnológico
- **Decisión (back `api`):** Node.js 24 LTS + Hono + `@hono/node-server`; Zod + `@hono/zod-validator`; Drizzle ORM + drizzle-kit con postgres.js; `hono/jwt`; `hono-rate-limiter`; nodemailer; pino. Testing con Vitest.
- **Reglas de Implementación (verbatim):**
  - Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
  - `api` y `generator` MUST correr en Node.js 24 LTS. `engines.node` MUST ser `">=24 <25"`.
  - El framework HTTP de la `api` MUST ser Hono. MUST NOT usarse Express, Fastify ni NestJS.
  - Todo acceso a la base MUST pasar por Drizzle ORM con el driver postgres.js. SQL crudo solo en migraciones, en las vistas `metrics_*` y donde Drizzle no lo soporte (`LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`).
  - Toda entrada HTTP (body, query, params) MUST validarse con Zod vía `@hono/zod-validator`. Los schemas de jugada MUST importarse del paquete del juego, nunca redefinirse.
  - `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
  - Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
  - Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
  - Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
  - El PRNG del `generator` MUST ser `pure-rand` (xoroshiro128+). MUST NOT usarse `Math.random()` en la generación de desafíos.
  - Los tests MUST usar Vitest; los e2e, Playwright.
- **Aplicación en esta story:** los health no reciben entrada (sin body, query ni params), por eso no se instala todavía `@hono/zod-validator`. El `SELECT 1` y el `SELECT current_user` son SQL crudo con el driver postgres.js de `createDb`: ver la nota en "Contexto de Base de Datos".

#### ADR-003: Monorepo y paquetes compartidos
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.
- **Ya aplicado en la raíz:** `pnpm-workspace.yaml` incluye `apps/*`; `eslint.config.js` ya tiene el bloque `files: ['apps/api/**']` que prohíbe `@nerdose/game-*/client`, `@nerdose/game-*/generator`, `@nerdose/polyglot` e imports desde otras apps.

#### ADR-004: PostgreSQL como única base, con propiedad por roles (reglas aplicables)
- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
- Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db` (ya hecho en S-002: `0000_roles_and_grants`).

#### ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores (reglas aplicables, verbatim)
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
- Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.
- **Simplificación acordada en REQ-001 para esta story:** el `errorHandler` responde el `message` en **español fijo** (todavía no hay resolución de locale; llega con `player-identity`). `es` es además el último recurso del orden de resolución, así que el comportamiento es consistente con ADR-015 para una request sin `lang`, sin jugador y sin `Accept-Language`.

### Convenciones activas (extracto aplicable)

#### `http-server` (Hono) — configuración de referencia

```ts
// apps/api/src/http/app.ts
import { Hono } from 'hono';
import { secureHeaders } from 'hono/secure-headers';
import { requestId } from 'hono/request-id';
import { requestContext } from './middleware/request-context';
import { errorHandler } from './middleware/error-handler';
import { registerRoutes } from './routes';
import type { AppDeps, AppEnv } from './types';

export function buildApp(deps: AppDeps) {
  const app = new Hono<AppEnv>();

  app.use(requestId());
  app.use(requestContext(deps.logger));
  app.use(secureHeaders());
  // No CORS middleware: same origin only (ADR-009). See security for Origin / Content-Type checks.

  app.onError(errorHandler);
  app.notFound((c) => c.json({ error: { code: 'not_found', message: 'Not found' } }, 404));

  registerRoutes(app, deps);
  return app;
}
```

```ts
// apps/api/src/index.ts
import { serve } from '@hono/node-server';
import { env } from '@/config/env';
import { buildApp } from '@/http/app';

const app = buildApp(await buildDeps(env));
const server = serve({ fetch: app.fetch, port: env.PORT });
process.on('SIGTERM', () => server.close());
```

```ts
// apps/api/src/http/middleware/request-context.ts
import { createMiddleware } from 'hono/factory';
import type { Logger } from 'pino';

export const requestContext = (logger: Logger) =>
  createMiddleware<AppEnv>(async (c, next) => {
    c.set('logger', logger.child({ requestId: c.get('requestId') }));
    await next();
  });
```

```ts
// apps/api/src/http/middleware/error-handler.ts
import type { ErrorHandler } from 'hono';
import { AppError } from '@nerdose/core';

export const errorHandler: ErrorHandler<AppEnv> = (err, c) => {
  const log = c.var.logger;
  if (err instanceof AppError) {
    log.warn({ code: err.code }, 'Application error');
    return c.json({ error: { code: err.code, message: c.var.i18n.error(err.code) } }, err.status);
  }
  log.error({ err }, 'Unexpected error');
  return c.json({ error: { code: 'internal_error', message: c.var.i18n.error('internal_error') } }, 500);
};
```

```ts
// apps/api/src/http/routes/index.ts (forma)
export function registerRoutes(app: Hono<AppEnv>, deps: AppDeps) {
  app.get('/api/health', healthHandler(deps));
  // ... módulos de dominio en stories posteriores
}
```

**Health check (verbatim de `http-server`):** "`GET /api/health` (players) and `GET /api/admin/health` (owner) require no authentication. They answer `200 { status: 'ok', db: 'ok' }` after a cheap `SELECT 1`, or `503 { status: 'degraded', db: 'error' }` when the database is unreachable (see `docs/apis/api.yaml`)."

**Reglas de `http-server` que aplican:**
- One route = one controller handler. No nested logic.
- Controllers **do not access the DB** or external systems.
- Status codes per `docs/apis/api.yaml`. Never answer `200` with an error inside.
- Responses have **no generic envelope**: the resource is returned directly. Errors use `{ "error": { "code", "message" } }`.
- No CORS headers are emitted. Security headers come from `hono/secure-headers`.
- No handler may take longer than `30s`.
- Handlers never run code (`child_process`, `vm`, `eval`) nor call external services other than the alert mail.
- The `app` is built by `buildApp(deps)` so tests can instantiate it with their own dependencies.
- Any log inside a handler uses `c.var.logger` (not the global logger) to keep the `requestId`.

**Adaptaciones de esta story respecto del ejemplo de la convención** (sin contradecir sus reglas):
- `c.var.i18n` todavía no existe: el mensaje sale de `errorMessage(code)` en español fijo (REQ-001).
- El `errorHandler` se construye con `createErrorHandler(deps.logger)` y usa `c.var.logger ?? baseLogger`, porque un error lanzado antes de `requestContext` no tendría child logger.
- `notFound` usa `errorMessage('not_found')` (español) en lugar de `'Not found'`.
- El ejemplo de `index.ts` se completa con la verificación del rol, el log de arranque y el cierre de la conexión al apagar.

#### `env-config` (@t3-oss/env-core) — reglas aplicables

- Todas las variables se cargan y validan en **un solo lugar** (`src/config/env.ts`). Nunca `process.env` en otro archivo.
- Validación al arrancar; el servicio no arranca con un entorno inválido.
- Variables numéricas con `z.coerce`.
- Secretos nunca se loguean.
- `.env.example` versionado con **todas** las variables del servicio, **sin valor** y con un comentario de una línea; se mantiene sincronizado con `env.ts`. `.env.local` y `.env.test` están en `.gitignore` (ya verificado por `test/repo-hygiene.test.ts` de la raíz para `apps/api/.env.local`).
- `dotenv` solo en desarrollo, para cargar `.env.local`.
- **Variables de esta story (decisión 4 de REQ-001, incrementales):** `NODE_ENV`, `PORT` (default 3000), `LOG_LEVEL`, `SERVICE_NAME`, `DATABASE_URL` (rol `nerdose_api`). Las demás de la convención (`LAUNCH_DATE`, `ADMIN_*`, `WEB_ORIGIN`, `ADMIN_ORIGIN`, `SMTP_*`, …) **no se declaran todavía**: las suma cada feature group que las usa.

Schemas exactos (de la convención):

```ts
NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
PORT: z.coerce.number().int().min(1).max(65535).default(3000),
LOG_LEVEL: z.enum(['trace', 'debug', 'info', 'warn', 'error', 'fatal', 'silent']).default('info'),
SERVICE_NAME: z.string().default('api'),
DATABASE_URL: z.string().url(),                       // role nerdose_api
```

> Con zod 4 (`^4.6.7`) usar `z.url()` como en `packages/db/src/config/env.ts` (`z.string().url()` está deprecado en v4).

Patrón ya implementado en el repo por `@nerdose/db` (reutilizar la misma forma):

```ts
// packages/db/src/config/env.ts
export function loadMigrateEnv(runtimeEnv: Record<string, string | undefined>) {
  return createEnv({
    server: { DATABASE_URL_OWNER: z.url(), /* ... */ },
    runtimeEnv,
    emptyStringAsUndefined: true,
    onValidationError: (issues) => {
      const names = [...new Set(issues.map((issue) => issue.path?.join('.')).filter(Boolean))];
      throw new AppError('validation_error', `Variables de entorno inválidas: ${names.join(', ')}`);
    },
  });
}
```

`emptyStringAsUndefined: true` es necesario: el `.env.example` se copia con valores vacíos (`PORT=`) y deben aplicar los defaults.

#### `logging` (Pino) — configuración de referencia

```ts
// src/shared/logger.ts
import pino from 'pino';
import { env } from '@/config/env';

export const logger = pino({
  level: env.LOG_LEVEL ?? 'info',
  base: {
    service: env.SERVICE_NAME,
    env: env.NODE_ENV,
  },
  timestamp: pino.stdTimeFunctions.isoTime,
  formatters: {
    level: (label) => ({ level: label }),
  },
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      '*.password',
      '*.token',
      '*.refreshToken',
      '*.apiKey',
    ],
    censor: '[REDACTED]',
  },
  transport: env.NODE_ENV === 'development'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
});
```

| Level | When |
|---|---|
| `trace` | Very fine-grained, off by default. |
| `debug` | Debug information, off in prod. |
| `info` | Normal system events (request received, job processed, etc.). |
| `warn` | Something unexpected but recoverable (retry, fallback). |
| `error` | Error that broke an operation. |
| `fatal` | The service cannot continue. |

- Estructura: `logger.info({ context }, 'message')` — objeto de contexto + mensaje **estático**.
- Errores esperados (`AppError`): `warn`/`info` sin stack. Inesperados: `error` con stack (`{ err }`).
- Adaptación: en lugar del singleton que importa `env`, `createLogger(env, destination?)`; `destination` permite a los tests capturar las líneas JSON (con `destination` presente, no se usa `transport`).

#### `orm` — reglas aplicables

```ts
// apps/api/src/infra/database/db.ts  (forma de la convención)
import { createDb } from '@nerdose/db';
import { env } from '@/config/env';

// DATABASE_URL is the URL of the service role: nerdose_api or nerdose_generator.
export const { db, sql } = createDb(env.DATABASE_URL);
```

- Services connect with their own role: `api` as `nerdose_api`. No DDL, no owner role. `DATABASE_URL_OWNER` is used only by `db:migrate`.
- No direct `db` calls from HTTP handlers.
- Raw SQL only for what Drizzle cannot express. Document why in a one-line comment.
- Migrations run before starting `api`; **services do not run migrations at startup**.
- Adaptación: `createDatabase(url)` como fábrica (sin efectos al importar), para que `index.ts` y los tests construyan su conexión.

#### `error-handling` — reglas aplicables

- Throw `AppError` with a catalog code for every expected failure. Never `throw new Error(...)` in domain code.
- Error responses have exactly the shape `{ "error": { "code", "message" } }`. No `details`, no stack, no SQL.
- 5xx errors are never remapped to 4xx. They are logged with stack and answered `500 internal_error`.
- Never answer `200` with an error body.
- `AppError`: log at `warn` without stack.

#### `game-registry` — reglas aplicables

```ts
// apps/api/src/games/registry.ts (forma en esta story: registro vacío, decisión 7 de REQ-001)
import { createGameRegistry } from '@nerdose/core';

export const games = createGameRegistry([]);
```

- The `api` imports only `@nerdose/game-<game_id>/definition`.
- A registry entry is validated at startup: unknown or duplicated ids make the process fail to start (ya lo hace `createGameRegistry`).
- Routes resolve the game through the registry. No `if (game_id === ...)`.

#### `testing` (Vitest + Testcontainers) — configuración de referencia

- **Un solo contenedor** `postgres:16-alpine` por suite, iniciado en `globalSetup`; los archivos leen las URLs con `inject()`; `fileParallelism: false`.
- Fixtures con el rol owner; el código bajo test usa `nerdose_api`.
