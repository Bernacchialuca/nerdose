## Status

## Referencia de la Story

- **Story:** [S-001](../stories/S-001.monorepo-base-core-ui.md)
- **Servicio:** core
- **Resumen:** Crea el paquete compartido `@nerdose/core` (`packages/core`) con su entrada isomorfa `.`: los tipos `GameId` y `Locale`, el contrato `GameDefinition` exacto a ADR-006, `MoveError`, el catálogo cerrado de errores (`ERROR_CATALOG`, `ErrorCode`, `AppError`) y `createGameRegistry()`. ### Arquitectura del Servicio

Del `overview.md` y `manifest.yaml` de `core`:

- **Propósito:** paquete `@nerdose/core` (`packages/core`): la lógica y los contratos que comparten `api`, `generator`, `web` y `admin`. La entrada `.` es **isomorfa** (corre en Node y en el navegador, sin `node:*`) y expone el contrato `GameDefinition` y sus tipos, el registry de juegos, el día UTC de la plataforma, el número de desafío, las rachas con días neutros, el seed/PRNG y el `ERROR_CATALOG` con `AppError`. La entrada `./notify` es **solo Node** (nodemailer) y expone `notify()` para las alertas por mail.
- **Tipo:** library en node. Vive en `packages/core` y la consumen todas las apps. ADR-003, 006, 008, 011, 013 y 015.
- **Módulos del dominio** (en negrita los de este plan):
  - **game-contract**: `GameId`, `Locale`, `GameDefinition`, `MoveError` y `createGameRegistry()` (ADR-006).
  - **errors**: `ERROR_CATALOG`, `AppError` y `ErrorCode` (ADR-015).
  - platform-day, seed-prng, notify: fuera de alcance.
- **Reglas de entrada:** `.` no importa `./notify` ni `node:*`; `web` y `admin` no importan `./notify`.
- **Convenciones activas:** `_base` (catálogo node), `validation`, `testing`, `game-registry`, `platform-day`, `alerts-mail` y `error-handling` (auto-incluida por `validation`). Aplican a este plan: `_base`, `error-handling`, `game-registry`, `testing` y `validation` (solo en lo que toca a Zod).

**Paquetes internos sin build (JIT) — decisión 1 del REQ-001:** `core` exporta su TypeScript fuente por `exports` (`"."` → `./src/index.ts`). Vite y `tsx` lo consumen directamente, y `typecheck` es `tsc --noEmit` en el paquete. El build de producción queda diferido con el hosting.

Decisiones de estructura (no fijadas por la documentación, se dejan indicadas):

| Decisión | Por qué |
|---|---|
| Archivos planos en `src/` en lugar de `src/domain/{module}/` de `_base` | La convención `error-handling` fija `packages/core/src/errors.ts`, `alerts-mail` fija `packages/core/src/notify.ts`, y el `eslint.config.js` raíz excluye exactamente `packages/core/src/notify.ts`. Un paquete library chico con módulos de un archivo sigue ese layout. |
| Imports relativos (`./errors`) dentro de `core`, no el alias `@/` de `_base` | `core` se consume JIT desde otros paquetes: cuando Vite o `tsc` de `apps/web` resuelven un `@/…` dentro de `packages/core/src`, lo resuelven contra el `tsconfig`/alias del consumidor, no del paquete. El alias rompería a los consumidores. |
| Tests en `test/` y no co-locados en `src/` | La regla de ESLint de la raíz prohíbe `node:*` en `packages/core/src/**`. El test del manifiesto necesita `node:fs`; con los tests fuera de `src/`, `src/` queda 100 % isomorfo y lint lo prueba. La convención `testing` permite ambas ubicaciones. |

### Convención `error-handling` (copiada, partes aplicables)

```ts
// packages/core/src/errors.ts
export const ERROR_CATALOG = {
  no_session:               { status: 401 },
  unauthorized:             { status: 401 },
  invalid_credentials:      { status: 401 },
  forbidden_origin:         { status: 403 },
  no_challenge_today:       { status: 404 },
  not_found:                { status: 404 },
  challenge_expired:        { status: 409 },
  challenge_voided:         { status: 409 },
  game_finished:            { status: 409 },
  already_reported:         { status: 409 },
  not_voidable:             { status: 409 },
  not_regenerable:          { status: 409 },
  not_voided:               { status: 409 },
  report_not_open:          { status: 409 },
  unsupported_media_type:   { status: 415 },
  invalid_move:             { status: 422 },
  not_in_word_list:         { status: 422 },
  invalid_report:           { status: 422 },
  validation_error:         { status: 422 },
  rate_limited:             { status: 429 },
  internal_error:           { status: 500 },
} as const;

export type ErrorCode = keyof typeof ERROR_CATALOG;

export class AppError extends Error {
  readonly status: number;
  constructor(readonly code: ErrorCode, message?: string) {
    super(message ?? code);
    this.name = 'AppError';
    this.status = ERROR_CATALOG[code].status;
  }
}
```

Reglas de la convención (verbatim):

- Throw `AppError` with a catalog code for every expected failure. Never `throw new Error(...)` in domain code.
- The error codes are part of the public contract. Changing or removing one is a breaking change; the catalog is closed.
- Error responses have exactly the shape `{ "error": { "code", "message" } }`. No `details`, no stack, no SQL.
- `message` is localized to the request locale and never contains sensitive data (cookies, tokens, other players' data, internals).
- 5xx errors are never remapped to 4xx. They are logged with stack and answered `500 internal_error`.
- Never answer `200` with an error body.
- Each failure has one canonical place where it is thrown. If the same error can arise in N places, extract a helper.
- Unique-constraint violations are translated by the service layer into the right code (`already_reported`); repositories do not throw `AppError`.
- A failed alert delivery (`notify()`) is logged and never changes the HTTP response or fails a job run.

"Adding a code is a change to `@nerdose/core` **and** to ADR-015 and `docs/apis/api.yaml`."

> **Nota sobre "enum":** ADR-015 dice que el catálogo se "exporta como enum desde `@nerdose/core`". La convención `error-handling` lo concreta como el objeto `ERROR_CATALOG` (`as const`) más el tipo `ErrorCode = keyof typeof ERROR_CATALOG`. Se implementa la forma de la convención, que es la que el resto de la documentación (api, generator) ya usa. No se crea un `enum` de TypeScript.

### Convención `game-registry` (copiada, partes aplicables)

Forma de referencia del registry (la convención lo muestra dentro de `apps/api`; el REQ-001, decisión 7, lo mueve a `@nerdose/core` como `createGameRegistry(definitions)` y `apps/api/src/games/registry.ts` lo instancia con `[]` en S-003):

```ts
const definitions = [devdle, grepGrid, timeline, bigO, bugHunt] as const;
const byId = new Map<GameId, GameDefinition<any, any, any, any, any, any, any>>(definitions.map((d) => [d.id, d]));

export const games = {
  ids: () => [...byId.keys()],
  get(id: string) {
    const game = byId.get(id as GameId);
    if (!game) throw new AppError('not_found');
    return game;
  },
};
```

Reglas aplicables (verbatim):

- Adding a game requires only the package and one line in the registry (the `web`/`admin` and `generator` have their own registries).
- A registry entry is validated at startup: unknown or duplicated ids make the process fail to start.
- Routes resolve the game through the registry. No `if (game_id === ...)` or `switch` by game in `apps/api` (ADR-006).

### Decisiones de diseño del REQ-001 que aplican (copiadas)

- **7. Registry de juegos compartido en `@nerdose/core`.** `createGameRegistry(definitions)` devuelve `{ ids(), get(id) }`:
  - `get` lanza `AppError('not_found')` si el `game_id` no está registrado (forma de `game-registry`, AC 12);
  - si hay ids repetidos, falla al construirse ("unknown or duplicated ids make the process fail to start", `game-registry`);
  - `apps/api/src/games/registry.ts` lo instancia con `[]`;
  - los registries de `client` (`web`/`admin`) y de `GameGenerator` (`generator`) se crean con el primer juego, porque su forma (`Record<GameId, …>`) no admite un registro vacío útil.
- **8. Alcance de `@nerdose/core` en este grupo.** Entrada `.` isomorfa con `GameId`, `Locale`, `GameDefinition` (exacta a ADR-006), `MoveError`, `ERROR_CATALOG`, `AppError`, `ErrorCode` y `createGameRegistry`.
  - La entrada `./notify` (nodemailer) se crea con el primer feature group que envía alertas: el SMTP está fuera de alcance y un stub sería código muerto. Se mantiene la regla de ADR-003: `.` no importa `node:*`.
  - `GameGenerator`, `VerificationLog`, `HistoryItem` y `VerifyContext` se agregan con el primer generador, porque ADR-006 no fija la forma completa de `HistoryItem` ni de `VerifyContext`.
- **Escenario 6 del REQ (AC 12):** `games.get('devdle')` sobre el registro vacío (`createGameRegistry([])`) → `@nerdose/core` lanza `AppError('not_found')` con `status` 404 del `ERROR_CATALOG`. Outcome: error controlado del catálogo, no una excepción genérica.
- **Pruebas mínimas de `@nerdose/core` (REQ):** `createGameRegistry([]).get('devdle')` lanza `AppError` con `code: 'not_found'`; un id duplicado falla al construir el registro; `AppError` toma el `status` del catálogo.

Decisiones de implementación de este plan (no fijadas por la documentación):

| Tema | Decisión | Por qué |
|---|---|---|
| Error al construir con id duplicado o desconocido | `throw new Error('Duplicate game id in registry: <id>')` / `throw new Error('Unknown game id in registry: <id>')` (`Error` plano, no `AppError`) | No es una falla esperada de dominio que llegue a un cliente: es un error de programación que tiene que tirar el arranque del proceso. El catálogo es cerrado (ADR-015) y ningún código describe "registro mal armado"; usar `internal_error` mezclaría un bug de arranque con errores de request. |
| Validación de id desconocido | Se agrega `GAME_IDS` (constante `as const` con los 5 ids de ADR-006) y `GameId` se deriva de ella; `createGameRegistry` rechaza ids fuera de `GAME_IDS` | La regla de `game-registry` pide "unknown **or** duplicated ids make the process fail to start". Sin una lista en runtime solo se podría validar el duplicado. Los 5 ids están fijados por ADR-006 y ADR-015. |
| Búsqueda por `Map` | `get` busca en un `Map`, nunca en un objeto plano | `get('__proto__')` o `get('constructor')` no pueden devolver nada distinto de `not_found`. |
| `ids()` | Devuelve un array nuevo en cada llamada, en orden de registro | Modificar el array devuelto no altera el registro. |
| `any` en el tipo del registry | `type AnyGameDefinition = GameDefinition<any, any, any, any, any, any, any>` con un comentario del motivo | Un registro heterogéneo de juegos con genéricos distintos; `_base` permite `any` en bordes con comentario, y la convención `game-registry` usa la misma forma. |

### Convenciones de Código (`_base` de node, catálogo)

- TypeScript obligatorio, `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022` o mayor (ya en `tsconfig.base.json`: además `module: ESNext`, `moduleResolution: bundler`, `verbatimModuleSyntax: true`, `skipLibCheck: true`, `noEmit: true`).
- Sin `any` salvo en bordes con librerías sin tipos; si se usa, comentar el motivo.
- Nombres: archivos y carpetas `kebab-case`; clases `PascalCase` (`AppError`); funciones y variables `camelCase` (`createGameRegistry`); constantes globales `SCREAMING_SNAKE_CASE` (`ERROR_CATALOG`, `GAME_IDS`); tipos `PascalCase` sin prefijo `I` (`GameDefinition`).
- Orden de imports: externos (`node:*`, npm) → absolutos del proyecto → relativos; grupos separados por una línea en blanco. En `core` no hay absolutos (ver decisión de estructura).
- Con `verbatimModuleSyntax: true`, los imports solo de tipos MUST ser `import type { … }` (por ejemplo, `import type { z } from 'zod'`).
- Errores esperados: clases específicas lanzadas con `throw` (acá, `AppError`). Sin `Result<T, E>`.
- Comentarios: por defecto ninguno; solo el porqué cuando no es obvio. Sin `// TODO` sin issue.

### Convención `testing` (aplicable a `core`)

- **Unit tests** para lógica pura: sin I/O, sin contenedores. Todo `core` en este plan es unit: **no** usa `globalSetup` ni Testcontainers (esa parte de la convención es para `api`/`generator`).
- Archivos co-locados o bajo `test/`, con sufijo `.test.ts`; `describe` nombra la unidad e `it` el escenario.
- Reset de mocks y timers entre tests (`vi.clearAllMocks()`, `vi.useRealTimers()`) si se usan (este plan no los necesita).
- Tests sin red.

Tests de tipos: se escriben con `expectTypeOf` de Vitest y `// @ts-expect-error`. En runtime `expectTypeOf` no verifica nada; la verificación real la hace `pnpm typecheck` (`tsc --noEmit` incluye `test/`). Un `@ts-expect-error` que deja de ser error hace fallar el typecheck.

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables

- **Decisión:** cada juego es un paquete `packages/games/<game_id>` que implementa el contrato `GameDefinition` de `@nerdose/core`. Hay un registry en `api`, en `web`/`admin` y en `generator` que mapea `game_id` → la entrada correspondiente.
- **Contrato (verbatim, la parte de servidor es lo que implementa este plan):**

```ts
// @nerdose/core — contrato de servidor (entrada ./definition de cada juego)
export interface GameDefinition<Payload, PublicView, State, Move, Feedback, Result, Stats> {
  id: GameId;                       // 'devdle' | 'grep-grid' | 'timeline' | 'big-o' | 'bug-hunt'
  version: number;                  // versión del schema de Payload
  moveSchema: z.ZodType<Move>;

  toPublic(p: Payload, locale: Locale): PublicView;          // sin solución
  initState(p: Payload, now: Date): State;
  applyMove(p: Payload, s: State, m: Move, now: Date):
    { state: State; feedback: Feedback } | { error: MoveError };   // 'invalid_move' | 'not_in_word_list'
  isFinished(s: State): boolean;
  result(p: Payload, s: State, locale: Locale): Result;      // incluye solución y explicación
  isWin(r: Result): boolean;
  score(r: Result): number;

  initialStats(): Stats;
  reduceStats(prev: Stats, r: Result): Stats;
  historyLabel(r: Result): string;  // "✓ 4/6", "8/8", "3/5", "✓ O(n log n)", "✗ L7"
}
```

  (`GameGenerator` y la entrada `./client` del mismo bloque quedan fuera de alcance, decisión 8.)

- **Reglas de Implementación (verbatim):**
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload)`; después, `result(payload, state)`.
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo con pnpm workspaces y Turborepo; `packages/core` contiene `GameDefinition`, día UTC, número de desafío, rachas, PRNG, códigos de error y `notify()` en la entrada aparte `./notify` (solo Node).
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

> La regla "`@nerdose/core` MUST exponer dos entradas" se cumple en forma incremental: en esta story solo existe `.`; `./notify` se agrega con el primer feature group que envía alertas (decisión 8 del REQ-001, ya aceptada).

#### ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores

- **Decisión:** errores `{ "error": { "code": "<code>", "message": "<texto en el locale>" } }` con un catálogo cerrado de códigos en `@nerdose/core`.
- **Catálogo (verbatim):**

| HTTP | `code` | Cuándo |
|---|---|---|
| 401 | `no_session` | Ruta de jugador sin cookie `nd_pid` válida |
| 401 | `unauthorized` | Ruta de admin sin JWT válido |
| 401 | `invalid_credentials` | Login de admin con contraseña incorrecta |
| 403 | `forbidden_origin` | Mutación con `Origin` no permitido |
| 404 | `no_challenge_today` | No hay desafío de hoy publicado ni anulado para ese juego |
| 404 | `not_found` | Recurso inexistente (`game_id`, `challenge_id`, `report_id`) |
| 409 | `challenge_expired` | `challenge_number` distinto del de hoy |
| 409 | `challenge_voided` | Jugada sobre un desafío anulado |
| 409 | `game_finished` | Jugada sobre una Play que no está `in_progress` |
| 409 | `already_reported` | Segundo reporte del mismo jugador al mismo desafío |
| 409 | `not_voidable` | Anular un desafío que no está `published` |
| 409 | `not_regenerable` | Regenerar un desafío que no está `approved` o con `date <= today` |
| 409 | `not_voided` | `acknowledge-void` sobre un desafío que no está anulado |
| 409 | `report_not_open` | Resolver o descartar un reporte que ya no está `open` |
| 415 | `unsupported_media_type` | Mutación sin `Content-Type: application/json` |
| 422 | `invalid_move` | La jugada no pasa `moveSchema` o es inválida para el estado |

  import { GAME_IDS, type GameDefinition, type GameId } from './game-definition';

  // Heterogeneous registry: each game has its own generic parameters.
  // eslint-disable-next-line @typescript-eslint/no-explicit-any
  export type AnyGameDefinition = GameDefinition<any, any, any, any, any, any, any>;

  export function createGameRegistry(definitions: readonly AnyGameDefinition[]) {
    const byId = new Map<string, AnyGameDefinition>();
    for (const definition of definitions) {
      if (!(GAME_IDS as readonly string[]).includes(definition.id)) {
        throw new Error(`Unknown game id in registry: ${definition.id}`);
      }
      if (byId.has(definition.id)) {
        throw new Error(`Duplicate game id in registry: ${definition.id}`);
      }
      byId.set(definition.id, definition);
    }
    return {
      ids: (): GameId[] => [...byId.keys()] as GameId[],
      get(id: string): AnyGameDefinition {
        const game = byId.get(id);
        if (!game) throw new AppError('not_found');
        return game;
      },
    };
  }
