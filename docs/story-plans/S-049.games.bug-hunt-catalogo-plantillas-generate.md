### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **Qué exporta `./generator` en esta story.** Igual que S-044 (decisión 1): `GameGenerator` exige `verify`, que es de S-050, así que **no** se exporta el objeto `generator` ni un `verify` stub. `src/generator/index.ts` exporta con nombre:
   - `generate`, `createGenerate`, `historySpec`, `usedBankItems`, `MAX_COMBOS` y `EVAL_STEP_LIMIT`;
   - el catálogo: `TEMPLATES`, `templateById` y los tipos `Template`, `TemplateId`, `TemplateParams`, `TestInput`, `MutationSite`, `BuiltTemplate`;
   - la mutación: `OPERATORS`, `OPERATOR_IDS`, `OperatorId`, `mutationsOf`, `neutralExpr`, `neutralStmt`;
   - los tests: `TEST_COUNT`, `MAX_TEST_DRAWS`, `testSize`, `buildTests`, `selectTests`, `formatCall`, `formatValue`;
   - la variedad: `VARIETY_DAYS`, `canonicalJson`, `varietyKey`, `keysUsedNear`;
   - la forma: `MIN_LINES`, `MAX_LINES`, `MAX_NESTING`, `measureCode`;
   - `addDays`.

   S-050 compone `export const generator: GameGenerator<BugHuntPayload> = { historySpec, usedBankItems, generate, verify }`. `package.json` suma `"./generator": "./src/generator/index.ts"` (precedente de S-043/S-044/S-048: cada story agrega su entrada y actualiza el test del manifest). `./client` sigue sin existir hasta S-051.
2. **Dependencia nueva:** `"@nerdose/polyglot": "workspace:*"` en `dependencies`. Solo se importa desde `src/generator/**`, y `test/boundaries.test.ts` lo fija.
3. **`binary_search` es "primer mayor o igual" y "primer mayor" (no "exacto").** El REQ (decisión 4) dice "exacto o primer mayor o igual". Sin `else` ni `break`, la búsqueda exacta emitida mide 17 líneas y se pasa del tope de 15. Las variantes `lower` (`lowerBound`, primera posición con valor ≥ `target`) y `upper` (`upperBound`, primera con valor > `target`) miden 14. Además, `relax_comparison` / `tighten_comparison` convierten una en la otra, que es un bug natural de búsqueda binaria.
4. **`is_palindrome` "con o sin el elemento del medio" = dos estilos de recorrido.** Ese elemento nunca cambia el resultado, así que el parámetro es `style: 'two_pointers' | 'mirror'`: dos punteros con `while` o un `for` hasta `half(len)` que compara contra el espejo. Ambos se llaman `isPalindrome`.
5. **Catálogo de 12 plantillas y 48 combinaciones** (tabla en "Catálogo de plantillas" del Contexto Arquitectónico). El REQ da los ids y ejemplos de parámetros, no los dominios ni el código exacto; esta lista los fija.
   - Los `id` de plantilla, los nombres de parámetros y valores, y los `id` de operador son **estables**: forman parte de la clave de variedad y del payload guardado.
   - El implementador puede ajustar casos borde, roles o sitios si un test de invariantes del catálogo (TS-10, TS-11) lo exige, siempre que se sigan cumpliendo los mínimos (≥ 12 plantillas, cada `bug_type` en ≥ 4 plantillas).
6. **Operadores de mutación con `id` estable** (tabla en "Operadores de mutación"). Se respetan los dos que ya usan los fixtures de la definición: `relax_comparison` y `flip_bool_init`. Un operador produce 0..n **variantes** (`to`) para un nodo. Cada variante reemplaza un único nodo con `replaceNode` sin cambiar la estructura de líneas.
7. **Tokens `from` / `to` en notación neutra del árbol** (`neutralExpr`, `neutralStmt`):
   - operadores como en el árbol (`==`, `!=`, no `===`);
   - `len(nums)`, `half(x)`, `nums[i]`, literales y nombres tal cual;
   - sentencias `best = i`, `count += 1`, `count++`, `return best`.

   Son para el admin (`Preview`, S-051) y para la clave de variedad. La explicación del jugador **nunca cita** un token que se imprime distinto entre lenguajes (`==`/`!=`, `len`, `half`): para esos operadores el texto lo describe con palabras (TS-24).
8. **Explicación de 3 pasos fijos** (dentro de 2–4): (1) qué hace la línea con el bug (texto del operador con `{Role}`, `{from}`, `{to}`), (2) la traza sobre el test oculto armada con sus valores (`Con maxIndex([5, 1, 5]) devuelve 2 en lugar de 0.`), (3) por qué pasan los visibles y el fix. No se reconstruye la traza paso a paso del intérprete (decisión 6.7 del REQ: "se arma con los valores del test, no con la traza paso a paso del intérprete").
9. **Sitios declarados por la plantilla, no inferidos.** `build(params, b)` devuelve el árbol correcto y sus sitios `{ node, operators, role, swaps?, returns? }`. `swaps` (nombres para `swap_variable`) y `returns` (variables para `early_return`) los decide el autor de la plantilla. `checkPortable` descarta igual lo que no tipa o no está en alcance.
10. **Tests generados: `TEST_COUNT = 10` distintos.** Primero los casos borde de la plantilla en el orden declarado y después entradas al azar hasta 10 distintas, con un tope de `MAX_TEST_DRAWS = 200` sorteos (una plantilla de prueba con pocas entradas posibles termina con menos). La decisión 3 del REQ habla de 8–12 casos y la 6 de "hasta 10": 10 cumple las dos. Un test del catálogo exige que toda combinación real llegue a 10 (TS-19).
11. **Rango de valores:** arrays de 0 a 7 elementos con valores en `[-9, 20]` (decisión 4 del REQ). Para provocar empates y vecinos iguales, `randomArray` sortea primero si el array es "angosto" (valores en `[0, 6]`) o "ancho" (`[-9, 20]`), mitad y mitad. Los escalares los define cada plantilla (umbral `k` en `[-9, 20]`, posición en `[-1, 8]`, `target` en `[-10, 21]`).
12. **Paso de evaluación acotado:** `EVAL_STEP_LIMIT = 5_000` para `evaluate` en `generate`. Las funciones correctas usan < 200 pasos con arrays de ≤ 7. Un mutante con loop infinito se corta rápido con `step_limit` y se descarta, sin gastar los 100 000 pasos por defecto en cada test.
13. **Orden de consumo del `rng`** (determinismo verificable):
    1. `bug_type`: `rng.pick` sobre `BUG_TYPES` filtrado a los tipos que el catálogo admite (con el catálogo real son los 7).
    2. Por cada intento de combinación (hasta `MAX_COMBOS = 30`):
       1. `rng.pick` de la plantilla, entre las que admiten el tipo, ordenadas por `id`;
       2. `rng.pick` de los parámetros, entre las combinaciones de esa plantilla que admiten el tipo, en el orden declarado;
       3. las entradas al azar de `buildTests`;
       4. el barajado Fisher–Yates de los candidatos de mutación (`shuffle`, con `rng.int(0, i)` desde el final).

    El `bug_type` **no cambia** entre intentos, así la distribución se mantiene uniforme (CA-6).
14. **Respaldo cuando ningún candidato sirve:** tras 30 combinaciones sin un candidato válido, `generate` devuelve igual el mejor candidato evaluable. Así `verify` (S-050) lo rechaza con su motivo, tras 20 intentos queda la falla registrada (ADR-017) y ninguna regla se relaja. La prioridad del respaldo es:
    1. falla solo por variedad;
    2. falla por `not_enough_passing`;
    3. mutante equivalente.

    Dentro de cada grupo gana el último que se encontró. Un candidato que no pasa `checkPortable` o no se evalúa sin error nunca se emite: no tiene `actual`. Si en 30 combinaciones no hubo **ningún** candidato evaluable, es un error de catálogo: `throw new Error('bug-hunt: no evaluable candidate')`. TS-10 y TS-11 lo hacen imposible con el catálogo real.
15. **`bug_line` sale del árbol correcto:** `bug_line = emit(correcto, 'js').lineOf[site.node]`. La mutación no cambia la estructura de líneas, así que es la misma línea en el mutante y en los 3 lenguajes. TS-16 lo comprueba: el código mutado y el correcto difieren **solo** en esa línea, en los 3 lenguajes.
16. **Clave de variedad:** `varietyKey(p) = \`${p.template}:${canonicalJson(p.params)}:${p.mutation.operator}@${p.mutation.node}:${p.mutation.to}\``.
    - `canonicalJson` es `JSON.stringify` con las claves ordenadas.
    - La ventana es `[D − 59, D + 59]` sin la fila de `D` (CA-5: "últimos 60 días o próximos 60"; mismo criterio que Big O con 30 → ±29).
    - Cuentan todas las filas que llegan en `history.recentChallenges`: el `generator` ya filtra `approved`, `published` y `voided`.
17. **Plantillas de prueba inyectables:** `generate = createGenerate(TEMPLATES)`. `createGenerate(templates)` existe para probar CA-2, CA-3 y CA-5 con plantillas chicas y deterministas (`test-fixtures.ts`). Sus entradas al azar salen solo de los casos borde, así los tests quedan fijos.
18. **Especificaciones escritas por separado en ES y EN** (D13 del REQ), con la tabla de frases de condición de "Especificaciones". La de `extreme_index` `{ extreme: 'max', tie: 'first' }` es exactamente `SPEC_MAX_INDEX` del fixture de la definición, para que TS-25 compare contra él.
19. **Ajustes hechos al implementar (verificados con TS-10 / TS-11):**
    - `bad_initialization` sin `shift_init` en `count_where`, `sum_range`, `max_window_sum` y `count_equal_neighbors`: un acumulador con valor inicial corrido falla todos los tests (ninguno pasa). El tipo sigue en 7 plantillas.
    - `binary_search`: el sitio de la condición solo ofrece `relax_comparison` y solo en `lower`; negarla o endurecerla en `upper` deja un caso donde ninguna rama corre y el loop no termina. `inverted_condition` queda en 10 plantillas.
    - `last_index_where`: sin `negate_condition` (la negación solo deja pasar el array vacío).
    - `max_window_sum`: `bound_minus_one` sobre el `k` de la primera ventana en lugar de `loop_cond_relax` (que lee fuera de rango con `k = len`).
    - Casos borde extra en varias plantillas (primer o último elemento como única coincidencia, empates por mitades) para cumplir TS-11.
    - `boundaries.test.ts` prohíbe `'node:`, `"node:` y `` `node:`` (comillas incluidas) porque `node: z.string()` de `schemas.ts` contiene la cadena `node:`.
20. **Hallazgos de documentación (no bloquean, este plan no edita docs de producto):**
    - `docs/flows/generacion-diaria.md`, paso 3 (bug-hunt): sigue con la línea vieja ("`polyglot.run` de la correcta y la mutada…"). La story dice que se edita en S-050.
    - Decisión 4 del REQ: dice "binary_search (exacto o primer mayor o igual)" y "is_palindrome (con o sin el elemento del medio)". Este plan los cambia por `lower`/`upper` y `two_pointers`/`mirror` (decisiones 3 y 4). Conviene alinear el REQ o `code-tree` ("Pieces built on the tree") con `/product-change-technical-definition` si se quiere dejar registro.
    - `docs/architectures/games/conventions/game-package.md`, tabla "What each entry exports": sigue con `share(result, number)` (el `locale` es de S-051) y no menciona entradas parciales por story.

Reglas aplicables (verbatim):
- `generate` is deterministic: same `{ date, seed, history }` gives the same payload. It never uses `Math.random()` or the current time; randomness comes from the PRNG built from the seed.
- Every player-facing text of a `Payload` is `{ es, en }`; `verify` fails if a language is missing.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint, see `monorepo-tooling`).
- Game-specific dependencies stay inside the game package (Shiki for `big-o` and `bug-hunt`, dnd-kit for `timeline`, `@nerdose/polyglot` for the generators of `big-o` and `bug-hunt`).
- `verify` may be `async` (games that execute code through `@nerdose/polyglot`); the `generator` always `await`s it. It receives no date: a game whose variety checks need `D` carries it in the payload (`date`), as every game does (`big-o` declares it optional and fails `variety_*` without it).

Tabla de miembros neutros (verbatim): `bankUsage: BankUsage | null` → `null` (`big-o`, `bug-hunt`).

#### Convención `game-registry` (extracto aplicable, verbatim)

- `GameGenerator.verify` may return a `Promise` (the `generator` awaits it) and `historySpec` accepts an optional `aheadDays` (default 0): history is read over `[D - recentDays, D + aheadDays]` excluding the row of `D`.
- `GameGenerator` declares `historySpec = { bank, lastUsedField, recentDays, aheadDays? }` and `usedBankItems(payload)`; the `generator` builds a generic history `{ bankItems, recentChallenges }`, with no per-game logic.
- `GameDefinition.bankUsage` (REQ-008) is `{ bank: 'terms' | 'timeline_facts'; lastUsedField: string; windowDays: number; itemsPerChallenge: number } | null` (… Big O and Bug Hunt `null`). The `api` builds the content stock from it without per-game constants; a package test asserts it matches `historySpec`.

#### Convención `testing` (extracto aplicable, verbatim)

- **Unit tests** for pure logic (streaks, seeds, day calculation, move reducers): no I/O, no containers.
- Unit tests are for pure functions. If it does I/O, write an integration test.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Tests do not touch the network or Wikimedia.
- Reset mocks and timers between tests (`vi.clearAllMocks()`, `vi.useRealTimers()`).

#### Convención `_base` (Node), extracto

- Archivos y carpetas `kebab-case`; funciones y variables `camelCase`; constantes globales `SCREAMING_SNAKE_CASE`; tipos `PascalCase` sin prefijo `I`.
- Sin `any` salvo en bordes con librerías sin tipos, con un comentario que diga por qué.
- Errores esperados con clases específicas; los inesperados se propagan. En `./generator`, una violación de invariante del catálogo es un `throw new Error('bug-hunt: …')` (mismo criterio que Big O).
- Sin comentarios salvo el porqué no obvio. Sin `// TODO` sin issue.
- Orden de imports: externos, absolutos del proyecto y relativos, separados por línea en blanco. Dentro del paquete se usan imports relativos (molde: `packages/games/big-o/src/generator/generate.ts`).

#### Payload que `generate` tiene que producir (verbatim, `src/definition/schemas.ts`)

```ts
export const MIN_STEPS = 2;
export const MAX_STEPS = 4;
export const MIN_VISIBLE_TESTS = 2;
export const MAX_VISIBLE_TESTS = 3;

const localized = z.object({ es: z.string(), en: z.string() });
const int32 = z.number().int().min(-2147483648).max(2147483647);
const arg = z.union([int32, z.array(int32)]);
const value = z.union([int32, z.boolean()]);

// Structural shape only: content rules (counts, ordering, equivalence) belong to `verify`.
export const payloadSchema = z.object({
  date: day.optional(),
  template: z.string().min(1),
  params: z.record(z.string(), z.union([z.string(), int32, z.boolean()])),
  function_name: z.string().regex(/^[a-z][A-Za-z0-9]*$/),
  bug_type: bugType,
  mutation: z.object({
    operator: z.string().min(1),
    node: z.string().min(1),
    from: z.string(),
    to: z.string(),
  }),
  spec: localized,
  code: codeByLanguageSchema,          // { js, go, java } non-empty strings
  bug_line: posInt,
  fix: codeByLanguageSchema,
  pickable_lines: z.array(posInt).min(1),
  tests: z.array(testCaseSchema).min(1),
  visible_tests: z.array(visibleTestSchema),
  failing_test: testCaseSchema,
  explanation: z.object({ steps: z.array(localized).min(MIN_STEPS).max(MAX_STEPS) }),
});
```

Reglas de contenido del REQ (decisión 3, verbatim):
- `code` es la versión **con el bug**. `fix[lang]` es el texto correcto de la línea `bug_line` en ese lenguaje (con su indentación): la versión correcta es `code[lang]` con esa línea reemplazada. Todas las mutaciones afectan una sola sentencia de una sola línea (decisión 5), así que el fix es siempre una línea.
- `tests` es el conjunto generado completo con `expected` (versión correcta) y `actual` (versión con bug); `visible_tests` y `failing_test` salen de ahí (decisión 6). `input` es la lista de argumentos (`[[5, 1, 5]]` para `maxIndex(nums)`; `[[3, 7, 2], 4]` para una función de dos parámetros); `expected`/`actual` son entero o booleano.
- `mutation.operator` es el operador del catálogo (p. ej. `relax_comparison`), `node` el id del nodo mutado en el árbol de la plantilla (determinista para la misma plantilla y parámetros) y `from`/`to` los tokens neutros del árbol (`>` → `>=`, `0` → `1`, `i` → `best`). Con `template` y `params` arman la clave de variedad (decisión 6).
- `date` como en Big O: opcional en el schema, `generate` siempre la pone; `verify` la necesita para la variedad y sin ella rechaza.

Orden de claves que produce `generate` (el del schema): `date`, `template`, `params`, `function_name`, `bug_type`, `mutation`, `spec`, `code`, `bug_line`, `fix`, `pickable_lines`, `tests`, `visible_tests`, `failing_test`, `explanation`.

#### `@nerdose/polyglot`: lo que usa este plan (extracto verbatim de `code-tree`)

- Statements: `func(name, params, body, returns?)`, `let(name, expr, type?)`, `assign(name, expr)`, `inc(name)`, `compound(name, op, expr)` (`+=`, `-=`, `*=`), `for(init, cond, step, body)` (`init` is a `let`; `step` is `inc`, `compound` or `assign`), `while(cond, body)`, `if(cond, then)`, `return(expr)`.
- Expressions: `num`, `bool`, `var`, `bin` (`+ - * % < <= > >= == != && ||`), `half(expr)` (integer division by 2, truncating toward zero), `call(name, args)`, `index(array, index)` and `len(array)`.
- Subset: integers, read-only arrays of integers and booleans. No strings, maps, `else`, `break` or assignment to array elements.
- `func(name, params, body, returns?)` takes `params` as `string[]` (every parameter is an `int` and the function returns `int`) or as `Param[]`. … A typed one adds `paramTypes: Type[]` and `returns` (default `'int'`).
- Identifiers match `^[a-z][a-zA-Z0-9]*$` and are not in `RESERVED_IDENTIFIERS`.
- `bin('%', left, right)` requires `right` to be a `num` with `value > 0`, otherwise `RangeError('invalid_modulo_divisor')`.
- `emit(func, lang) -> { code, lineOf, statementLines }` … **One statement per line**, closing braces on their own line. Indentation: 2 spaces (JS), tab (Go), 4 spaces (Java).
- `statementLines` lists, ascending and without repeats, the lines where a statement starts (simple statements and `for`/`while`/`if` headers); never line 1 nor a closing `}`. It is identical in the three languages.
- JS emits `==` as `===` and `!=` as `!==`. `half` is `Math.trunc(x / 2)` in JS and `x / 2` in Go and Java. `len(a)` is `a.length` (JS, Java) and `len(a)` (Go).
- A negative `num` that is the right operand of a `bin` is wrapped (`a - (-1)`, `x < (-1)`), elsewhere it is printed as is (`-1 + a`, `return -1`).
- `evaluate(func, args, { maxSteps = EVAL_MAX_STEPS }) -> EvalOutcome` … `EvalOutcome = { ok: true; value: number | boolean } | { ok: false; error: EvalError }`, `EvalError = 'int_overflow' | 'index_out_of_range' | 'step_limit'`. … Arguments are validated against `signatureOf(func)`: `RangeError('arity_mismatch: …')` and `RangeError('invalid_argument: <JSON>')`. A malformed tree … throws `Error('evaluate: <detail>')`.
- `replaceNode(func, nodeId, build) -> FuncNode` returns a new tree (the original is untouched) where the node is replaced by `build(node, b)`. `b` numbers from the highest id of the tree plus one; untouched nodes, and the children `build` reuses, keep their ids. Errors: `node_not_found: <id>`; `replace_kind_mismatch: <id>` …; `RangeError('invalid_modulo_divisor')`; `duplicate_node_id: <id>`.
- `checkPortable(func) -> PortabilityIssue[]` (`{ kind, nodeId }`, in emission order, `[]` when portable, never throws): `type_mismatch`, `unused_local` (only a read through a `var` counts as use), `unreachable_statement`, `missing_return`.
- Rule: "the generator discards whatever `checkPortable` or `evaluate` rejects".

### Decisiones de diseño de REQ-010 aplicables (verbatim)

**Decisión 4. Catálogo de plantillas (C-31; RF 11; CA 11).** Vive en `packages/games/bug-hunt/src/generator/catalog/` (solo la entrada `./generator`). Cada **plantilla** declara:
- `id`, dominio de `params` (combinaciones finitas: extremo mayor/menor, empate primero/último, condición y umbral `k`, inclusión de extremos, valor por defecto `-1` o la longitud, tamaño de ventana…), nombre de la función por combinación (`maxIndex`, `countAbove`, `firstNegative`…: identificadores en inglés, neutros respecto del idioma del jugador);

- `spec(params)` → `{ es, en }` (escritas por separado en cada idioma, D13; deben resolver empates y casos borde, p. ej. "si el máximo se repite, devuelve el primero");
- `inputs(rng, params)` → casos borde propios (array de un elemento, vacío si la especificación lo define, todos iguales, empates, negativos, el valor buscado en la primera o la última posición) y casos al azar; arrays de 0 a 7 elementos con valores en `[-9, 20]` para que entren en pantalla;
- `reference(params, args)` → implementación en TypeScript escrita aparte, que encarna la especificación.
- **Plantillas iniciales (≥ 12):** `extreme_index` (máx/mín · primero/último), `count_where` (`> k`, `< k`, par, impar, múltiplo de `k`), `sum_range` (desde/hasta · inclusivo o no), `first_index_where` (condición · `-1` o la longitud), `last_index_where`, `all_where`, `any_where`, `binary_search` (exacto o primer mayor o igual, array ordenado), `is_palindrome` (array · con o sin el elemento del medio), `max_window_sum` (`k`), `is_sorted` (estricto o no), `count_equal_neighbors`. Paridad con `% 2 == 0` / `% 2 != 0` (nunca `== 1`, que falla con negativos).
- **Tests del catálogo (obligatorios):** (a) para cada plantilla y cada combinación de parámetros, `evaluate(build(params))` coincide con `reference(params)` en ≥ 500 entradas al azar más los casos borde (la especificación, la referencia y el árbol dicen lo mismo); (b) el código emitido mide 8–15 líneas y ≤ 3 niveles de anidamiento en los 3 lenguajes; (c) `checkPortable` sin problemas; (d) cada uno de los 7 `bug_type` es aplicable en ≥ 4 plantillas; (e) textos `es`/`en` no vacíos.

**Decisión 5. Operadores de mutación por `bug_type` (C-31; CA 11).** Todos reemplazan **un nodo dentro de una sola sentencia** con `replaceNode`, sin cambiar la cantidad de líneas; el nodo pertenece a un sitio declarado por la plantilla (no se muta cualquier cosa):

| `bug_type` | Operadores | Ejemplo |
|---|---|---|
| `off_by_one` | límite de loop `<` ↔ `<=`; inicio de loop `0` ↔ `1`; límite `x` → `x - 1` / `x + 1` | `i < nums.length` → `i <= nums.length - 1`… |
| `comparison` | `>` ↔ `>=`, `<` ↔ `<=` en condiciones de `if` | `nums[i] > nums[best]` → `>=` |
| `wrong_operator` | `+` ↔ `-`, `+=` ↔ `-=`, `&&` ↔ `\|\|` | `sum += nums[i]` → `sum -= nums[i]` |
| `wrong_variable` | una variable o índice por otra del mismo tipo y en alcance | `nums[i]` → `nums[best]` |
| `bad_initialization` | literal inicial de un `let` (`0` ↔ `1`, `-1` → `0`, `true` ↔ `false`) | `let best = 0` → `let best = 1` |
| `misplaced_return` | la última sentencia de un bloque dentro de un loop pasa a ser `return <variable de resultado>` (o del índice): la función sale antes de terminar de recorrer | `best = i;` → `return i;` |
| `inverted_condition` | se niega la comparación de un `if` (`<` → `>=`, `==` → `!=`, `>` → `<=`) | `nums[i] < 0` → `nums[i] >= 0` |

`misplaced_return` se define así (y no moviendo el `return` final dentro del loop) porque mover sentencias cambia la estructura de líneas y Go y Java no compilan una función sin `return` final; reemplazar la última sentencia del bloque mantiene una sola línea afectada y no deja código inalcanzable para Java. Cada operador declara sus textos de explicación `{ es, en }` con marcadores (`{role}`, `{from}`, `{to}`, `{input}`, `{expected}`, `{actual}`).

**Decisión 6. `generate` determinista con tests, test oculto y variedad (C-31; RF 11–13; CA 11, 12, 14–16).** Con un único `rng = rngFrom(seed)` (ADR-007):
1. **Ventana:** de `history.recentChallenges` (`historySpec = { bank: null, lastUsedField: '', recentDays: 60, aheadDays: 60 }`, sin la fila de `D`) salen las claves usadas en `[D − 59, D + 59]`. **Clave de variedad** = `template` + `params` en JSON canónico (claves ordenadas) + `mutation.operator@mutation.node:mutation.to`. Cuentan `approved`, `published` y `voided` (`ACTIVE_STATUSES`); un regenerado queda `rejected` y no cuenta. …
2. **Tipo de bug:** `rng.pick` uniforme entre los 7 `bug_type`, para que el jugador vea variedad sin agregar una regla nueva; luego una plantilla que lo admita y una combinación de parámetros (orden estable por `id`).
3. **Tests:** casos borde de la plantilla más casos al azar hasta 10 distintos; `expected = evaluate(correcta, input)`.
4. **Mutación:** se recorren los sitios de ese `bug_type` en orden barajado por el `rng`; se acepta el primero cuyo árbol mutado pasa `checkPortable`, se evalúa sin error en todos los tests (un índice fuera de rango o un loop infinito descartan la mutación: JS no fallaría igual que Go y Java), tiene ≥ 1 test con `actual ≠ expected` (no es equivalente, CA 12), ≥ 2 con `actual = expected` (CA 14) y cuya clave no está en la ventana (CA 16). Si ningún sitio sirve, se prueba otra plantilla o parámetros (hasta 30 combinaciones); si tampoco, se devuelve igual el último candidato y `verify` lo rechaza con su motivo, de modo que tras 20 intentos queda la falla registrada (ADR-017, CA 17) sin relajar ninguna regla.
5. **Tests visibles y oculto:** tamaño de un test = cantidad total de elementos de sus arrays + cantidad de argumentos escalares; empates por orden de generación. `failing_test` = el más chico de los que fallan (CA 15); `visible_tests` = hasta 3 de los que pasan, los más chicos (mínimo 2).
6. **Código y líneas:** `code[lang] = emit(mutado, lang).code`; `bug_line = lineOf[nodo mutado]`; `pickable_lines = statementLines` del mutado; `fix[lang]` = línea `bug_line` de `emit(correcto, lang)`.
7. **Explicación** (2–4 pasos `{ es, en }`): qué hace la línea con el bug (texto del operador con el `role` del sitio y los tokens `from`/`to`); la traza sobre el test oculto ("Con `[5, 1, 5]`, al llegar a `i = 2` se cumple `5 >= 5` y devuelve 2 en lugar de 0" se arma con los valores del test, no con la traza paso a paso del intérprete); por qué pasaban los visibles y el fix. Texto por operador y por idioma, no traducciones (D13).
- Tests: mismo `{ date, seed, history }` → mismo payload; sobre ≥ 2000 seeds cada `bug_type` sale entre 8 % y 22 % de las veces y todos los payloads pasan el schema; simulación de 180 días seguidos con historia real sin fallas por variedad; el caso de una mutación equivalente se descarta en `generate` (unitario con una plantilla de prueba).

#### T1 `extreme_index` — params `{ extreme: 'max' | 'min', tie: 'first' | 'last' }` (4)

```js
function maxIndex(nums) {
  let best = 0;
  for (let i = 1; i < nums.length; i++) {
    if (nums[i] > nums[best]) {
      best = i;
    }
  }
  return best;
}
```

#### T3 `sum_range` — params `{ side: 'until' | 'from', inclusive: boolean }` (4)

Nombres y condición: until/false `sumBefore(nums, end)` `i < end`; until/true `sumUpTo(nums, end)` `i <= end`; from/true `sumFrom(nums, start)` `i >= start`; from/false `sumAfter(nums, start)` `i > start`.

```js
function sumUpTo(nums, end) {
  let sum = 0;
  for (let i = 0; i < nums.length; i++) {
    if (i <= end) {
      sum += nums[i];
    }
  }
  return sum;
}
```

| Sitio | Operadores | Rol es / en | extra |
|---|---|---|---|
| `0` de `let sum` | `shift_init` | el valor inicial de sum / the initial value of sum | |
| `0` del init del `for` | `loop_start_shift` | el inicio del recorrido / the start of the loop | |
| `nums.length` | `bound_minus_one` | el límite del recorrido / the loop bound | |
| cond del `if` | `relax_comparison`/`tighten_comparison`, `negate_condition` | la condición que decide qué posiciones se suman / the condition that decides which positions are added | |
| `sum += nums[i]` | `swap_compound`, `early_return` | la actualización de sum / the update of sum | returns `[sum]` |
| `i` de la cond | `swap_variable` | la posición que se compara con end (start) / the position compared with end (start) | swaps `[sum]` |

Especificación: es "Devuelve la suma de los elementos de nums en las posiciones {menores que end | menores o iguales que end | mayores o iguales que start | mayores que start}; la primera posición es 0.
