### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **Las tasas de `metrics_challenge_quality` son `double precision` (`float8`).** El schema doc define `completion_rate = finished / NULLIF(started, 0)` y `win_rate = count(won) / NULLIF(finished, 0)`, pero no fija el tipo. Con dos `int`, PostgreSQL hace división entera y daría `0`. Además, postgres.js devuelve `numeric` como `string`. `Metrics.challenge_quality[].completion_rate` y `win_rate` son `type: number, nullable: true` en `api.yaml`. Por eso el numerador se castea a `float8`, y postgres.js lo entrega como `number` de JS.
2. **Todos los conteos se castean a `::int`.** `count(...)` es `bigint`, y postgres.js lo devuelve como `string`. El SQL de REQ-011 ya castea (`count(DISTINCT player_id)::int`, `count(*)::int`). Se aplica igual a `metrics_challenge_quality` (`started`, `finished`, `reports`), que el REQ no escribe. Todas las columnas de conteo quedan `int4`.
3. **SQL de `metrics_challenge_quality`.** REQ-011 dice "sin cambios de definición", pero solo la describe en el schema doc. Se escribe con dos subconsultas preagregadas (`plays` por `challenge_id`, `challenge_reports` por `challenge_id`) unidas con `LEFT JOIN` a `challenges`. Así se evita multiplicar filas: con un `JOIN` directo, 6 plays × 2 reportes darían `started = 12`. El SQL exacto está en la Tarea 1.
4. **Las vistas no se declaran en el schema Drizzle (`pgView`).** La convención `orm` dice que el SQL crudo se permite para "los `metrics_*` views". El flujo de S-053 las lee con `SELECT * FROM metrics_… WHERE …`. Ningún documento pide tipos TS exportados para las vistas. Como no se declaran, `drizzle-kit generate` no las ve: compara contra el snapshot, no contra la base, y no propone borrarlas. Si S-053 necesita tipos, se agregan ahí o con `/product-change-technical-definition`.
5. **La migración se crea con `drizzle-kit generate --custom`.** Esto mantiene consistentes `_journal.json` y el snapshot `0008`, que es copia del `0007` porque el schema TS no cambia. Mismo criterio que `0000_roles_and_grants`, que es SQL manual registrado en el journal.
6. **Observación (sin cambio, para revisión de producto):** el flujo `anulacion-de-desafio` (paso de `acknowledge-void`) inserta una Play `status = 'voided'` con `state = '{}'` para el jugador que no había jugado ese desafío. Con las definiciones documentadas, esa Play:
   - cuenta en `metrics_daily_players` (no filtra por estado);
   - cuenta en `metrics_retention` como completada;
   - cuenta en `started` de `metrics_challenge_quality`.

   Se implementa tal cual está documentado. Si se quiere excluirla, hay que cambiar la definición con `/product-change-technical-definition`.

### ADRs Relevantes

#### ADR-014: Métricas en la base y analítica web opcional

- **Decisión:** las métricas de producto salen de PostgreSQL, con cuatro vistas en `@nerdose/db` que se leen con `GET /api/admin/metrics?from&to`:

  | Vista | Definición |
  |---|---|
  | `metrics_daily_players` | Jugadores distintos con alguna Play iniciada, por fecha (total con `game_id = null` y por juego) |
  | `metrics_retention` | Cohorte por fecha de la primera Play completada; `d1`/`d7` = % con una Play completada en cohorte+1 / cohorte+7 |
  | `metrics_streak_distribution` | Jugadores por tramo de `global_streak` vivo: `0`, `1`, `2-6`, `7-29`, `30+` |
  | `metrics_challenge_quality` | Por challenge: `started` (Play creadas), `finished` (won + lost), `completion_rate`, `win_rate`, `reports`, `status` |

- **Reglas de Implementación (verbatim):**
  - Las vistas MUST llamarse exactamente `metrics_daily_players`, `metrics_retention`, `metrics_streak_distribution` y `metrics_challenge_quality`, y MUST definirse en migraciones de `@nerdose/db`.
  - El rol `nerdose_api` MUST tener solo `SELECT` sobre las vistas `metrics_*`.
  - En `metrics_challenge_quality`, `completion_rate = finished / started` y `win_rate = won / finished`. Ambas MUST ser `null` si el divisor es 0.
  - Las Play `voided` MUST NOT contar en `finished` ni en `win_rate`.
  - El admin MUST mostrar las métricas como tablas HTML. MUST NOT agregarse librería de gráficos en v1.
  - `web` MUST llamar solo a `track(event)` de `@nerdose/ui`. MUST NOT referenciar `window.plausible` fuera de ese helper.
  - Si `VITE_PLAUSIBLE_DOMAIN` está vacío, el build MUST NOT inyectar el script de Plausible y `track()` MUST ser un no-op.
  - Si `VITE_PLAUSIBLE_DOMAIN` tiene valor, `VITE_PLAUSIBLE_SCRIPT_URL` MUST ser obligatoria (el build falla si falta), y el script MUST inyectarse con `defer` y `data-domain`.
  - El evento de share MUST llamarse exactamente `share:<game_id>` (por ejemplo `share:devdle`) y MUST NOT llevar propiedades personalizadas.
  - `admin` MUST NOT cargar analítica.
  - **Nota de implementación (REQ-011):** las vistas no dependen de "hoy". `metrics_retention` expone conteos (`d1_players`, `d7_players`) y `metrics_streak_distribution` el tramo de la racha guardada con `last_active_date`; la `api` completa `d1`/`d7` y la racha viva con su reloj y con `isStreakAlive` de core (ADR-011), para no duplicar la regla en SQL y poder probarla con relojes falsos.
- **Riesgo:** las vistas se vuelven lentas a medida que crece `plays`. **Mitigación:** índices por `date` y `challenge_id` (ya existen: `idx_plays_date`, `idx_plays_challenge_status`), y pasar a vistas materializadas si hace falta.

#### ADR-004: PostgreSQL como única base, con propiedad por roles

- **Decisión:** PostgreSQL 16 como única base, con la frontera entre servicios aplicada en la base por roles. `nerdose_api` tiene, entre otros, "`SELECT` de `job_runs`, `generation_failures` y las vistas `metrics_*`". `nerdose_generator` no tiene acceso a las vistas.
- **Reglas de Implementación (verbatim):**
  - La única base MUST ser PostgreSQL ≥ 16. MUST NOT agregarse otra base (Redis, MongoDB, SQLite) en v1.
  - Los campos que varían por juego (`challenges.payload`, `challenges.verification`, `plays.state`, `plays.result`, `player_game_stats.extra`, `challenge_reports.context`, `job_runs.summary`) MUST ser `jsonb`.
  - Los textos de contenido bilingües MUST guardarse como `jsonb` con la forma `{ "es": string, "en": string }`.
  - Las fechas de día MUST ser `date` (día UTC). Los instantes MUST ser `timestamptz`.
  - Los ids MUST ser `uuid` (`gen_random_uuid()`), salvo las PK compuestas o naturales que define `docs/db-schemas/nerdose-db.md`.
  - La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
  - Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db`, con permisos por columna sobre `challenges`, `terms` y `timeline_facts` exactamente como en la tabla de arriba.
  - La unicidad de un Challenge vigente MUST implementarse como índice único parcial sobre `(game_id, date)` con `WHERE status IN ('approved','published','voided')`.
  - `plays` MUST tener `UNIQUE (player_id, challenge_id)` y `challenge_reports` MUST tener `UNIQUE (player_id, challenge_id)`.
  - Los enums del dominio (`game_id`, `challenge_status`, `play_status`, `code_language`, `locale`, etc.) MUST ser enums de PostgreSQL con los valores exactos del análisis de dominio.
- **Riesgo relevante:** "una migración olvida los `GRANT` de una tabla nueva y un servicio falla en producción". **Mitigación:** test de integración que corre con cada rol las operaciones esperadas sobre una base migrada. Acá se aplica a las vistas (TS-7..TS-10).

#### ADR-011: Rachas con días neutros y agregados recalculables

Este ADR es el motivo por el que las vistas no calculan la racha viva.
- **Reglas de Implementación aplicables (verbatim):**
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.
- **Consecuencia para `db`:** `metrics_streak_distribution` agrupa por la racha **guardada** (`player_stats.global_streak`) y expone `last_active_date`. La `api` (S-053) decide si está viva con `isStreakAlive`. La vista MUST NOT usar `now()`, `CURRENT_DATE` ni equivalentes (prerequisito de la story: "Las vistas no usan `now()`").

#### Vistas de Métricas (schema doc, sección "Vistas de Métricas", ya actualizado por REQ-011)

Las cuatro vistas viven en migraciones de `@nerdose/db` (ADR-014). El rol `nerdose_api` solo tiene `SELECT` sobre ellas, y la API las filtra por `[from, to]`.

| Vista | Columnas | Definición |
|---|---|---|
| `metrics_daily_players` | `date`, `game_id` (null = total), `players` | `count(DISTINCT player_id)` de `plays` por `date`, agrupado por `game_id` y con `GROUPING SETS ((date, game_id), (date))` |
| `metrics_retention` | `cohort_date`, `cohort_size`, `d1_players`, `d7_players` | Cohorte = fecha de la primera Play con `status IN ('won','lost','voided')` de cada jugador. `d1_players`/`d7_players` = conteo de la cohorte con una Play completada en `cohort_date + 1` / `+ 7`. La vista no conoce "hoy": la api calcula `d1 = d1_players / cohort_size` y devuelve `null` si ese día todavía no terminó (REQ-011) |
| `metrics_streak_distribution` | `bucket`, `last_active_date`, `players` | Tramo de la racha **guardada** (`players LEFT JOIN player_stats`: sin `player_stats` cuenta en `'0'` con `last_active_date` null), agrupado en `'0'`, `'1'`, `'2-6'`, `'7-29'`, `'30+'`. La api mueve al `'0'` las filas cuya racha no está viva con `isStreakAlive` de core (ADR-011) |
| `metrics_challenge_quality` | `challenge_id`, `game_id`, `date`, `number`, `started`, `finished`, `completion_rate`, `win_rate`, `reports`, `status` | Por challenge `published` o `voided`: `started = count(plays)`, `finished = count(plays WHERE status IN ('won','lost'))`, `completion_rate = finished / NULLIF(started, 0)`, `win_rate = count(won) / NULLIF(finished, 0)`, `reports = count(challenge_reports)` |

Las vistas se crean en la migración `0008_metrics_views` (solo `CREATE VIEW` + `GRANT`, forward-only). `metrics_challenge_quality` lista desafíos `published` o `voided`.

#### SQL de REQ-011 ("Nuevas Vistas", migración `0008_metrics_views`, SQL manual)

```sql
-- metrics_daily_players (date, game_id, players) - sin cambios de definición
SELECT date, game_id, count(DISTINCT player_id)::int AS players
FROM plays GROUP BY GROUPING SETS ((date, game_id), (date));

-- metrics_retention (cohort_date, cohort_size, d1_players, d7_players)
WITH completed AS (SELECT DISTINCT player_id, date FROM plays WHERE status IN ('won','lost','voided')),
     cohort AS (SELECT player_id, min(date) AS cohort_date FROM completed GROUP BY player_id)
SELECT c.cohort_date, count(*)::int AS cohort_size,
       count(d1.player_id)::int AS d1_players, count(d7.player_id)::int AS d7_players
FROM cohort c
LEFT JOIN completed d1 ON d1.player_id = c.player_id AND d1.date = c.cohort_date + 1
LEFT JOIN completed d7 ON d7.player_id = c.player_id AND d7.date = c.cohort_date + 7
GROUP BY c.cohort_date;

-- metrics_streak_distribution (bucket, last_active_date, players)
SELECT CASE WHEN coalesce(s.global_streak, 0) = 0 THEN '0'
            WHEN s.global_streak = 1 THEN '1'
            WHEN s.global_streak <= 6 THEN '2-6'
            WHEN s.global_streak <= 29 THEN '7-29' ELSE '30+' END AS bucket,
       s.last_active_date, count(*)::int AS players
FROM players p LEFT JOIN player_stats s ON s.player_id = p.id
GROUP BY 1, 2;

-- metrics_challenge_quality - sin cambios de definición (challenges published/voided; completion_rate y win_rate
-- con NULLIF, voided fuera de finished y win_rate; reports = count(challenge_reports)).
```

- **Grants:** `GRANT SELECT ON metrics_daily_players, metrics_retention, metrics_streak_distribution, metrics_challenge_quality TO nerdose_api;` en la misma migración. `nerdose_generator` sin acceso.
- **Índices:** no se agregan (ADR-014: con ~1.000 jugadores diarios, cálculo al consultar). Ya existen `idx_plays_date`, `idx_plays_challenge_status` e `idx_player_stats_global_streak`.
- **Migración:** solo `CREATE VIEW` + `GRANT`, sin downtime. Rollback forward-only (`DROP VIEW` en una migración nueva).
- **Tests (`packages/db`):** el test de schema verifica las 4 vistas y que `nerdose_api` solo tiene `SELECT` sobre ellas; la migración `0000` sigue sin mencionar `metrics_`.

#### Control de acceso (schema doc, "Consideraciones de Seguridad")

```sql
-- nerdose_api (extracto)
GRANT SELECT ON job_runs, generation_failures TO nerdose_api;
GRANT SELECT ON metrics_daily_players, metrics_retention,
  metrics_streak_distribution, metrics_challenge_quality TO nerdose_api;
```
- Ningún rol de servicio tiene `DELETE`, DDL ni `TRUNCATE`.
- Las métricas son agregadas: ninguna columna expone `player_id` (REQ-011, Seguridad).

#### Estrategia de migraciones (schema doc)

1. Se modifica el schema en `packages/db/src/schema/`, o se agrega un archivo SQL manual para vistas, triggers o grants.
2. `pnpm --filter @nerdose/db db:generate --name <cambio>` genera la migración SQL.
3. Se revisa el SQL generado.
4. Se commitea la migración junto con el schema.
5. Antes de levantar `api` y `generator`, se aplica con `pnpm --filter @nerdose/db db:migrate` usando el rol `nerdose_owner` (`DATABASE_URL_OWNER`).

**Rollback:** forward-only.

**Nota técnica (PostgreSQL):** las vistas se ejecutan con los privilegios de su dueño (`nerdose_owner`, que corre la migración). `nerdose_api` solo necesita `SELECT` sobre la vista. Un cambio futuro de tipo o nombre en una columna de `plays`, `challenges`, `players`, `player_stats` o `challenge_reports` que use una vista va a requerir `DROP VIEW`/`CREATE VIEW` en la misma migración (PostgreSQL lo exige). Agregar un valor a un enum no lo requiere.

### Contexto de Flujos

**admin-login-y-consultas, Paso 5: Métricas** (verbatim, `docs/flows/admin-login-y-consultas.md`):

>
> **Response (éxito):** 200
> ```json

**Qué aporta esta story al flujo:** las vistas que el paso 5 lee. Las consultas que va a hacer la `api` (S-053), según REQ-011, son:
```sql
SELECT * FROM metrics_daily_players WHERE date BETWEEN $from AND $to ORDER BY date, game_id NULLS FIRST
SELECT * FROM metrics_retention WHERE cohort_date BETWEEN $from AND $to ORDER BY cohort_date
SELECT * FROM metrics_streak_distribution
SELECT * FROM metrics_challenge_quality WHERE date BETWEEN $from AND $to ORDER BY date DESC, game_id
```
Las columnas de las vistas deben llamarse exactamente como en esas consultas (`date`, `game_id`, `cohort_date`, …).

**anulacion-de-desafio (dato que afecta las vistas):** `acknowledge-void` inserta en `plays` (`player_id`, `challenge_id`, `game_id`, `date`, `state = '{}'`, `status = 'voided'`, `started_at`, `finished_at = now()`) ON CONFLICT DO NOTHING. Al anular, las `plays` del desafío pasan a `voided` conservando `result`. Ver la decisión 6.
