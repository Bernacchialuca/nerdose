**Rules (verbatim):**
- One package per game, with `game_id` in `devdle | grep-grid | timeline | big-o | bug-hunt` and package name `@nerdose/game-<game_id>`.
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry. A package may add a data resource (e.g. `./wordlist` in `devdle`, read only by the `api` with `node:fs`; `web` and `admin` never import it).
- `./definition` implements every method of `GameDefinition`; `toPublic` never includes the solution (per-game list in ADR-006).
- Every game has an anti-spoiler contract test: serialize `toPublic(payload)` and every pre-result response and verify none contains a solution value.
- `moveSchema` is the single schema used by `web` (before sending) and by `api` (validation); a parse failure is `422 invalid_move`.
- `share(result, number)` never includes the solution and ends with `nerdose.dev`.
- `generate` is deterministic: same `{ date, seed, history }` gives the same payload. It never uses `Math.random()` or the current time; randomness comes from the PRNG built from the seed.
- Every player-facing text of a `Payload` is `{ es, en }`; `verify` fails if a language is missing.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint, see `monorepo-tooling`).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk.
- Changing the `GameDefinition` interface touches all five packages in the same commit.

#### Convención `game-registry` (extracto aplicable)

- The `api` imports only `@nerdose/game-<game_id>/definition`. Never `./client` or `./generator`.
- The `api` never serializes `challenges.payload` in a player response. Before the Play ends it answers `toPublic(payload, locale)`; after, `result(payload, state, locale)`.
- `moveSchema` of the game validates the move; a failed parse answers `422 invalid_move`. A move invalid for the state also answers `invalid_move`.
- Win, score, stats and history label come only from the game definition (`isWin`, `score`, `reduceStats`, `historyLabel`).
- `Feedback` returned for a move never contains a solution value that the game has not already revealed by design.
- Update (REQ-004): `GameGenerator` declares `historySpec = { bank, lastUsedField, recentDays }` and `usedBankItems(payload)`; the `generator` builds a generic history `{ bankItems, recentChallenges }`, with no per-game logic.
- Update (REQ-005): `MoveContext = { isValidWord(word): boolean; locale: Locale }`; `toPublic(p, locale, state?)`: the `api` passes `play.state` only when the Play is `in_progress`. Both changes are additive: games that do not need them ignore them.

#### Convención `validation` (extracto)

- `moveSchema`, payload, state, result and stats schemas MUST be imported from the game package. Never redefined in `apps/`.
- Types are inferred from schemas (`z.infer`). No hand-written types that duplicate a schema.
- JSON property names in schemas are `snake_case` and match `docs/apis/api.yaml` (ADR-015). No `camelCase` aliases or transforms.
- Use composition (`.partial()`, `.omit()`, `.pick()`, `.extend()`) instead of duplicating schemas.
- Day dates are validated as `YYYY-MM-DD` strings.

#### Convención `error-handling` (extracto)

`invalid_move` (422) es el código para "Move fails `moveSchema` or the game state". En el paquete de juego no se lanza `AppError`: `applyMove` **devuelve** `{ error: 'invalid_move' }` (`MoveError`) y la `api` lo traduce y hace `ROLLBACK`.

#### Convención `testing` (extracto aplicable)

- **Unit tests** for pure logic (seeds, move reducers): no I/O, no containers.
- **Contract tests** for each game: anti-spoiler (ADR-006).
- Every game has an anti-spoiler contract test: `toPublic(payload)` and every pre-result response must not contain any solution value.
- Tests do not touch the network or Wikimedia.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Code under test never calls `new Date()` in domain logic.

#### Convención `_base` (Node) — extracto

TypeScript `strict`, `noUncheckedIndexedAccess`; archivos `kebab-case`, funciones `camelCase`, constantes globales `SCREAMING_SNAKE_CASE`, tipos `PascalCase` sin prefijo `I`; fechas de día como `YYYY-MM-DD` UTC, nunca asumir la zona horaria del servidor; por defecto sin comentarios, solo el "por qué" no obvio; sin `// TODO` sin issue.

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables

- **Decisión:** cada juego es un paquete `packages/games/<game_id>` que implementa `GameDefinition` de `@nerdose/core` con tres entradas; registries en `api`, `web`/`admin` y `generator`.

```ts
export interface GameDefinition<Payload, PublicView, State, Move, Feedback, Result, Stats> {
  id: GameId;                       // 'devdle' | 'grep-grid' | 'timeline' | 'big-o' | 'bug-hunt'
  version: number;                  // versión del schema de Payload
  moveSchema: z.ZodType<Move>;

  toPublic(p: Payload, locale: Locale, state?: State): PublicView;   // sin solución; state solo con la Play in_progress (REQ-005)
  initState(p: Payload, now: Date): State;
  applyMove(p: Payload, s: State, m: Move, now: Date, ctx: MoveContext):
    { state: State; feedback: Feedback } | { error: MoveError };   // 'invalid_move' | 'not_in_word_list'
  isFinished(s: State): boolean;
  result(p: Payload, s: State, locale: Locale): Result;      // incluye solución y explicación
  isWin(r: Result): boolean;
  score(r: Result): number;

  initialStats(): Stats;
  reduceStats(prev: Stats, r: Result): Stats;
  historyLabel(r: Result): string;  // "✓ 4/6", "8/8", "3/5", "✓ O(n log n)", "✗ L7"
}

export interface MoveContext { isValidWord(word: string): boolean; locale: Locale }

export interface GameGenerator<Payload> {
  historySpec: { bank: 'terms' | 'timeline_facts' | null; lastUsedField: string; recentDays: number };
  usedBankItems(p: Payload): string[];                       // ids del banco que consume el payload
  generate(input: { date: string; seed: Uint8Array; history: GeneratorHistory }): Payload;
  verify(p: Payload, history: GeneratorHistory): VerificationLog;   // { ok, checks[], reason? }
}
// GeneratorHistory = { bankItems (ítems approved con su last_used_*), recentChallenges (no rejected, [D - recentDays, D - 1]) }
```

- **Reglas de Implementación (verbatim):**
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
  - La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`). Con `state`, `toPublic` MAY revelar únicamente lo que el jugador ya descubrió en esa Play (Grep Grid: `words[].definition` de los `term_id` presentes en `found_words`); MUST NOT revelar nada de lo no descubierto (REQ-005).
  - `Feedback` MUST ir en el locale del jugador (`ctx.locale`), nunca como `{ es, en }` (ADR-015).
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` (sin estado y con estados intermedios, si el juego usa `state`) y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015 (extracto aplicable, verbatim)

- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
- Los enums MUST serializarse con sus valores exactos del dominio.

#### ADR-016 / ADR-007 (extracto aplicable)

- Timeline no repite un hecho en 90 días.
- Categorías v1: `programming_languages`, `frameworks`, `companies`, `operating_systems`, `video_games`; `hardware` quedó diferida en la primera corrida (S-026). El enum `TIMELINE_CATEGORIES` conserva las 6; una categoría diferida simplemente no tiene hechos `approved` en el banco, así que el generador no necesita conocer la lista v1.
- El pipeline del `generator` hace hasta 20 intentos por fecha (`attempt` 0–19), cada uno con `seed = HMAC-SHA256(GENERATOR_SECRET, "timeline:D:attempt")`; un candidato que falla `verify` queda `rejected` y se prueba el siguiente `attempt` (eso es S-028; aquí solo `generate` y `verify`).

### Decisiones de diseño de REQ-006 aplicables (verbatim)

**6. Payload, vista pública, estado y jugada (C-23, C-24; RF 2, 5; CA 1, 6, 7).**
- Payload: `{ date, category, prompt: { es, en }, items: [{ fact_id, opaque_id, label, event_date, date_precision, note: { es, en } }] ×5, correct_order: [opaque_id] ×5 }`. `items` está **en el orden mezclado que ve el jugador**; `correct_order` es cronológico. `prompt` sale de una plantilla fija por categoría en `shared/prompts.ts` (supuesto "consigna fija").
- `toPublic(p, locale)` → `{ category, prompt: p.prompt[locale], items: p.items.map(({ opaque_id, label }) => ({ opaque_id, label })) }`, idéntico a `TimelinePublicView` (l. 1264). Ignora `state`.
- **`State` con el orden confirmado (hallazgo del contrato).** La `api` calcula `result(payload, state, locale)` desde el `state` de la Play, así que el estado final tiene que guardar el orden enviado: `TimelineState = { order?: string[] }`. `initState → {}`; `isFinished(s) = s.order !== undefined`. Mientras la Play está `in_progress` el estado sigue vacío (el orden en construcción vive en el cliente).
- `moveSchema = z.strictObject({ order: z.array(z.string()).length(5) })` con refinamiento de unicidad (como `TimelineMove`, `uniqueItems`); la `api` responde `422 invalid_move` si el parse falla (menos o más de 5, repetidos, tipos distintos). `applyMove`: (a) `s.order` ya definido → `invalid_move` (defensivo; la `api` responde `409 game_finished` antes); (b) algún id que no está en `p.items` → `invalid_move` (desconocido o de otro desafío); (c) si no → `{ state: { order: m.order }, feedback: null }`. La Play no cambia en (a) y (b) porque la `api` hace `ROLLBACK` (CA 6, 7).

**7. Resultado, puntaje, stats y etiqueta (C-25; RF 6, 8; CA 3–5, 9).** `result(p, s, locale) = { win: score === 5, score, category, correct_order, submitted_order: s.order, items }`, con `score` = posiciones `i` donde `s.order[i] === correct_order[i]` e `items` en orden cronológico con `{ opaque_id, label, event_date, date_precision, note: note[locale] }` (forma de `TimelineResult`, l. 1529). `isWin = r.win`; `score(r) = r.score` (0–5; 0/5 es `lost` y cuenta para la racha). `historyLabel = "N/5"`. `extra = { by_category: { [category]: { played, correct } } }`: `reduceStats` suma 1 a `played` y `r.score` a `correct` de `r.category`; el promedio por categoría es `correct / played` y lo muestra FG-10. Las Play `voided` no pasan por `reduceStats` (`ProgressService.applyResult`).

**8. Generación (C-24; RF 14, 15; CA 25–30).** `historySpec = { bank: 'timeline_facts', lastUsedField: 'last_used', recentDays: 90 }`; `usedBankItems(p) = p.items.map(i => i.fact_id)`. Banco: `{ id, label, category, event_date, date_precision, note, last_used }` de los `approved`. Con un único `rng = rngFrom(seed)`:
- Elegibles: `last_used IS NULL OR last_used <= D − 90` y `id` ausente de `recentChallenges` (la ventana incluye los aprobados futuros, porque `approve` escribe `last_used = GREATEST(last_used, D)`, mismo patrón que Devdle y Grep Grid; CA 28).
- Categoría: entre las categorías con ≥ 5 elegibles, ordenadas por nombre, `rng.pick` (supuesto "sin garantía de rotación").
- Hechos: elegibles de esa categoría en orden estable (por `id` del banco), barajados con el `rng` (Fisher–Yates); se agregan en ese orden los que sean distinguibles de todos los ya elegidos, hasta 5. Si no se llega a 5 se entrega igual lo que haya y `verify` lo rechaza (patrón "sin elegibles se elige igual").
- **Distinguibilidad** (`shared/dates.ts`, la usan generador, `verify` y tests): `a` y `b` se distinguen si sus años difieren; si comparten año, solo si ambos tienen precisión `month` o `day` y sus meses difieren, o ambos tienen precisión `day` y sus fechas difieren. Una fecha idéntica nunca. (Go 2009/`year` + Node.js 2009-05 → no; 2009-05 + 2009-09 → sí; CA 26, 27.)
- `opaque_id`: 6 caracteres `[a-z0-9]` sorteados con el `rng` (nunca derivados de `fact_id` ni del orden), únicos dentro del desafío; si el orden alfabético de los 5 coincide con `correct_order`, se vuelven a sortear (hasta 10 veces). Mismo hecho en dos desafíos → ids distintos por construcción (CA 30).
- Mezcla inicial: permutación con el `rng`; si coincide con `correct_order` se vuelve a mezclar (hasta 10 veces) (RF 15). Nunca `Math.random()` ni la hora (ADR-006).

**9. `verify` (RF 16; CA 26, 29).** Checks con `name` estable para `challenges.verification`, en este orden: `items_count` (5 `fact_id` distintos), `facts_in_bank` (cada `fact_id` está en `bankItems` con el mismo `label`, `category`, `event_date` y `date_precision`), `same_category` (los 5 y `payload.category` iguales y ∈ `TIMELINE_CATEGORIES`), `texts_bilingual` (`prompt.es/en` y cada `note.es/en` no vacíos), `distinguishable` (todos los pares), `correct_order_consistent` (`correct_order` es una permutación de los 5 `opaque_id` y respeta `event_date` ascendente), `opaque_ids` (5 únicos, `^[a-z0-9]{6}$`, su orden alfabético ≠ `correct_order`), `shuffled` (orden de `items` ≠ `correct_order`), `not_used_90` (`last_used IS NULL OR <= D − 90` y fuera de `recentChallenges`). El primer check fallido va en `reason`.

**13 (extracto). Formato de fecha.** Fechas con `Intl.DateTimeFormat(locale, { timeZone: 'UTC', … })` según precisión: `year` → solo el año; `month` → mes y año; `day` → fecha completa (`shared/format-date.ts`; nunca inventa mes ni día).

**Supuestos del REQ aplicables:** la consigna es un texto fijo por categoría ("Ordená estos lenguajes del más antiguo al más reciente" / "Order these languages from oldest to newest"), sin variantes aleatorias; el `label` es el nombre en inglés de Wikidata, igual en ES y EN; `event_date` se guarda normalizado según la precisión (`year` → `YYYY-01-01`, `month` → `YYYY-MM-01`, `day` → fecha completa).

### Decisiones de este plan (no documentadas en la arquitectura) — `NOT DOCUMENTED - needs verification`

Detalles que la documentación no fija y que este plan resuelve para que la implementación sea determinista y testeable. Si alguno no convence, se cambia en el REQ/story.

1. **Inconsistencia en CA-3 (story) / CA 5 (REQ): "el orden exactamente inverso → 0/5" es imposible con la fórmula documentada.** Con 5 posiciones, invertir el orden deja fijo el elemento del medio: con correcto `[Python, Java, Go, Docker, Kubernetes]`, el inverso `[Kubernetes, Docker, Go, Java, Python]` tiene `Go` en la posición 3 → `score = 1`. La decisión 7 define el puntaje de forma explícita (posiciones `i` con `s.order[i] === correct_order[i]`), así que **el plan implementa la fórmula** y: (a) el test del inverso espera `score: 1`, `win: false`; (b) el 0/5 se cubre con un desarreglo completo, la rotación `[Java, Go, Docker, Kubernetes, Python]` → `score: 0`, `win: false`. Hay que corregir el texto de CA-3 de S-027 y CA 5 de REQ-006 (y el escenario equivalente de S-028/S-029) a "un orden sin ninguna posición correcta (p. ej. una rotación)".
2. **`./client` como stub.** La story lo pide ("queda como stub hasta S-029"). `src/client/index.ts` contiene solo `export {};` y `package.json` declara las tres entradas (cumple la regla de `exports` de `game-package`). Sin `react`, `@nerdose/ui` ni dnd-kit hasta S-029. Ningún registry lo importa todavía.
3. **`initialStats = { by_category: {} }`** y `statsSchema` con `z.partialRecord(z.enum(TIMELINE_CATEGORIES), z.object({ played: int ≥ 0, correct: int ≥ 0 }))`. La documentación fija la forma de `extra` pero no el valor inicial; las categorías aparecen a medida que se juegan.
4. **Consignas (`shared/prompts.ts`).** Documentadas: `programming_languages` (ES y EN, supuesto "Consigna" del REQ) y el inicio ES de `frameworks` ("Ordená estos frameworks…") y `companies` ("Ordená estas empresas…") en `timeline-partida.md`. El resto se completa con el mismo patrón:

   |---|---|---|

   | `frameworks` | `Ordená estos frameworks del más antiguo al más reciente` | `Order these frameworks from oldest to newest` |

   | `video_games` | `Ordená estos videojuegos del más antiguo al más reciente` | `Order these video games from oldest to newest` |
5. **`moveSchema` acepta cualquier string** (`z.string()`, como `TimelineMove`), no el patrón `^[a-z0-9]{6}$`: un id con otro formato llega a `applyMove` y es `invalid_move` por desconocido. El patrón `OPAQUE_ID_PATTERN = /^[a-z0-9]{6}$/` sí se exige en `payloadSchema` y en el check `opaque_ids`.
6. **`applyMove` revalida la permutación** aunque `moveSchema` ya la cubra (CA-2 pide que `applyMove` también rechace 4 ids o repetidos): `invalid_move` si `s.order !== undefined`, si `m.order.length !== 5`, si hay repetidos o si algún id no está en `p.items`. Con éxito, `state = { order: [...m.order] }` (copia, no la referencia del move).
7. **`result` con un estado no terminado** (`s.order === undefined`, no debería ocurrir): `submitted_order: []`, `score: 0`, `win: false`. Nunca lanza.
8. **Forma estricta de `toPublic`, `stateSchema` y `moveSchema`:** `z.strictObject` en `moveSchema` (decisión 6) y `stateSchema` (`additionalProperties: false`); `publicViewSchema` y `resultSchema` con `z.strictObject` también, para que el test anti-spoiler falle si se cuela un campo.
9. **`facts_in_bank` y `same_category`.** Los ítems del payload no llevan `category`: `facts_in_bank` compara `label`, `event_date` y `date_precision` contra el banco; `same_category` compara la `category` del banco de cada `fact_id` presente con `payload.category` y exige `payload.category ∈ TIMELINE_CATEGORIES`. Así un payload con `category` alterada falla en `same_category` y no antes.
10. **Orden cronológico y desempate:** `compareChronological(a, b)` = por `event_date` (string `YYYY-MM-DD`) y, si empatan, por `id`/`fact_id` ordinal. El empate solo ocurre en candidatos que `verify` va a rechazar (`distinguishable`), pero garantiza determinismo.
11. **Selección cuando faltan hechos (patrón "sin elegibles se elige igual"):**
    - Categorías candidatas = las de `TIMELINE_CATEGORIES` ordenadas por nombre (`companies`, `frameworks`, `hardware`, `operating_systems`, `programming_languages`, `video_games`) con ≥ 5 elegibles. Si no hay ninguna, se usan las que tengan ≥ 5 ítems en el banco (sin mirar la ventana); si tampoco, `generate` lanza `RangeError('timeline generate: no category has 5 facts')` (como Grep Grid con banco insuficiente: no hay payload que pase `payloadSchema`).
    - Si la selección voraz sobre los elegibles no llega a 5, se sigue con la **misma selección voraz** (solo distinguibles) sobre los no elegibles de la categoría (ordenados por `id` y barajados con el `rng`); si aún faltan, se completa con los sobrantes no distinguibles, primero los elegibles (en su orden barajado) y después los no elegibles. Así un candidato con hechos de la ventana falla por `not_used_90` y no por `distinguishable` cuando hay alternativas distinguibles, y uno sin alternativas (`BANK_TIGHT`) falla por `distinguishable`.
12. **Consumo del `rng`** (una sola instancia `rngFrom(seed)`, en este orden): `pick` de categoría → Fisher–Yates del pool elegible → (solo si hace falta completar) Fisher–Yates de los no elegibles → sorteo de los 5 `opaque_id` (y re-sorteos) → mezcla inicial (y re-mezclas). Fisher–Yates: `for i = n−1 … 1: j = rng.int(0, i); swap(i, j)` sobre una copia.
13. **Sorteo de `opaque_id`:** alfabeto `OPAQUE_ID_ALPHABET = 'abcdefghijklmnopqrstuvwxyz0123456789'`; cada id = 6 × `ALPHABET[rng.int(0, 35)]`; si repite uno ya sorteado en la ronda, se sortea otro. El id `i` corresponde al hecho `i` en orden cronológico (`correct_order = ids`). Si `[...ids].sort()` es igual a `ids`, se repite la ronda completa (hasta `MAX_REDRAWS = 10` rondas en total; si las 10 coinciden se entrega igual y `verify` rechaza por `opaque_ids`).
14. **Mezcla inicial:** permutación Fisher–Yates de los 5 hechos cronológicos; si el orden resultante de `opaque_id` es igual a `correct_order`, se re-mezcla (hasta `MAX_REDRAWS = 10` en total; si no, `verify` rechaza por `shuffled`).
15. **`addDays`/`isValidDate` se copian** a `timeline/src/generator/days.ts` (las fronteras prohíben importar entre paquetes de juego). El nombre `days.ts` evita confundirlo con `shared/dates.ts` (distinguibilidad).
16. **Ítem de banco `TimelineFact`** (exportado por `./generator`): `{ id: string; label: string; category: TimelineCategory; event_date: string; date_precision: DatePrecision; note: { es: string; en: string }; last_used: string | null }`. Es el contrato que S-028 debe producir en `bankItems` para `timeline_facts`.
17. **Test de tasa de rechazo sobre el dataset real** en `test/dataset-rejection-rate.test.ts` con `loadDataset()` (`id = wikidata_id`, `last_used: null`), 200 seeds, `MIN_RATE = 0.95`, y además ≥ 3 categorías distintas entre los 200 candidatos. El umbral no está en el REQ; es el mismo margen usado por Grep Grid sobre los 20 intentos del pipeline.
18. **`formatEventDate(event_date, date_precision, locale)`** usa `Intl.DateTimeFormat(locale, { timeZone: 'UTC', year: 'numeric' })` para `year`, `+ month: 'long'` para `month` y `+ month: 'long', day: 'numeric'` para `day`, sobre `new Date(`${event_date}T00:00:00.000Z`)`. Salidas verificadas en Node 24: `es` → `2009`, `junio de 2014`, `8 de junio de 1995`; `en` → `2009`, `June 2014`, `June 8, 1995`.
