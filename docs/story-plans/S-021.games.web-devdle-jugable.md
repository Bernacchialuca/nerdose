### Arquitectura del Servicio (`docs/architectures/games/overview.md`, copiado)

- **Propósito:** Los cinco paquetes de juego `packages/games/<game_id>`. Cada uno implementa el contrato `GameDefinition` de `@nerdose/core` y expone tres entradas separadas: `./definition` (servidor: la usa la `api`), `./client` (React: `Instructions`, `Game`, `Result` y `share()`; la usan `web` y `admin`) y `./generator` (`generate` y `verify`; lo usa el `generator`). ADR-003 y ADR-006.
- **Convenciones por entrada:** `client` sigue `styling`, `accessibility`, `testing-unit` y `game-clients` (copias de `web`). `game-package` es propia (estructura, las tres entradas y qué puede importar cada una). `game-clients` describe el lado de la app que consume cada entrada; aquí aplica como contrato que el paquete debe cumplir.

### Convención `game-package` (partes aplicables, copiadas)

**Estructura:**
```
packages/games/<game_id>/
├── src/
│   ├── definition/   # server contract
│   ├── client/       # React UI: Instructions, Game, Result, share()
│   │   ├── index.ts
│   │   └── *.test.tsx
│   ├── generator/
│   └── shared/       # pure types and helpers used by more than one entry
```

| Entry | Exports | Consumer |
|---|---|---|
| `./client` | React components `Instructions`, `Game`, `Result` and `share(result, number)` | `apps/web`, `apps/admin` |

| Entry | May import | Must not import |
|---|---|---|
| `./client` | `@nerdose/core` (`.`), `zod`, `react`, `@nerdose/ui`, `shared/`, types from `./definition` | `@nerdose/polyglot`, `node:*`, `@nerdose/core/notify`, `./generator`, runtime code of `./definition` that carries solutions |

**Rules (aplicables, verbatim):**
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry. A package may add a data resource (e.g. `./wordlist` in `devdle`, read only by the `api` with `node:fs`; `web` and `admin` never import it).
- `moveSchema` is the single schema used by `web` (before sending) and by `api` (validation); a parse failure is `422 invalid_move`.
- `share(result, number)` never includes the solution and ends with `nerdose.dev`.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint, see `monorepo-tooling`).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk.

**Interpretación para este plan:** `src/definition/schemas.ts` no lleva solución (son schemas Zod y constantes `WORD_PATTERN` / `MAX_GUESSES`), así que el client **puede** importarlo en runtime. El client **no** importa `src/definition/index.ts` (el objeto `devdle` con `result()`) ni `feedback.ts`.

### Convención `game-clients` (copiada)

- Every game provides its own UI in `packages/games/<game_id>/client` (ADR-006). The app keeps a **registry** that maps `game_id` to that entry, and the shell talks to every game through the same contract. The shell has no game-specific logic: adding a game means adding a package and a registry line.
- `GameClient` is the shape of the `./client` entry defined by the game contract: React components `Instructions`, `Game`, `Result` and `share(result, number): string`. The exact props of those components are owned by the game packages and `@nerdose/core`; the app passes them through and does not reinterpret them.
- The host fetches the public view and the play state with TanStack Query (`/api/games/{game_id}/today`), then hands them to the client components. Moves go through the game's `moveSchema` (Zod) before `POST .../move`.
- `share(result, number)` produces the text. The shell calls `navigator.share({ text })` when available and falls back to `navigator.clipboard.writeText`, with a visible confirmation message. After sharing it calls `track('share:<game_id>')`.
- **Rules:** Import only `@nerdose/game-<game_id>/client`. The registry is the only place that lists games. Each game is loaded with a dynamic `import()` so it is its own chunk. The shell renders games only through `Instructions`, `Game`, `Result` and `share`; it does not read game-specific fields. The `client` never receives the solution before the round ends in `web`. Share text is never built by the shell; it always comes from the game's `share()`. Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`. Adding a game must require only a new package, a registry line and its translations.

### Convención `i18n` de `web` (partes que fijan el contrato del client, copiadas)

- **i18next + react-i18next** translate only the **UI texts**. Challenge content (statements, definitions, explanations) and error messages arrive **already resolved in the player's locale** from the `api`, so the client never picks a language inside `{ es, en }` objects.
- "Game packages ship their own UI strings through the same i18n instance (a namespace per game, e.g. `devdle`)."
- **Rules:** Every UI string goes through `t()`; no hardcoded user-facing literals in components. Every key exists in both `es` and `en`; a missing key fails the unit test that compares both resource trees. Never translate or choose a language for content that comes from the `api`; render it as received. Never build sentences by concatenating translated fragments; use interpolation. Locale is only `es` or `en`. Do not translate error codes; branch on codes and show the `api`'s message or a UI key.

### Convención `styling` (partes aplicables, copiadas)

- Tailwind CSS v4 con tokens en `@theme` de `@nerdose/ui` (`tokens.css`). **Tokens live only in `packages/ui`**; los paquetes de juego no declaran tokens.
- **Rules:** Use only the tokens (Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components. Merge conditional classes with `cn()`; never concatenate class strings by hand. Contrast meets WCAG 2.1 AA (4.5:1 text, 3:1 large text and UI components). Focus is always visible: `focus-visible:` rings with `--color-accent`; never `outline-none` without a replacement. State is never conveyed by color alone. Respect `prefers-reduced-motion`. No CSS-in-JS and no component CSS files.
- **Values from data or timers** (progress width, countdown): set a CSS variable with `style={{ '--w': pct + '%' }}` and consume it in a class.
- **Updates from REQ-003:** no global media queries; layout uses `flex-wrap` and `repeat(auto-fit, minmax(min(300px, 100%), 1fr))`. **Static check:** `.tsx` files must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).
- Per-game accent is applied by the game's own `client` via its token, never with a literal hex.

### Convención `accessibility` (copiada, partes aplicables)

- One `<h1>` per screen, headings in order. Native elements first (`<button>`, `<ul>`). ARIA only when no native element fits.
- Everything operable with the mouse is operable with the keyboard; visible focus ring on every focusable element.
- Feedback that uses color (Devdle marks, win/loss) is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
- Result, errors and notices appear in `role="status"` (polite) or `role="alert"` regions.
- Touch targets ≥ 44 × 44 px. Layout reflows at 320 px without horizontal scroll and supports 200% text zoom.
- **Rules:** contrast ≥ 4.5:1; no interactive element built from `<div>`/`<span>` with a click handler; every icon decorative (`aria-hidden`) or named; color is never the only carrier of meaning; **each of the 5 games can be completed with the keyboard alone (NFR-U03)**; dynamic updates announced via live regions, focus not moved unexpectedly; axe-core reports zero violations.

### Convención `testing-unit` (copiada, partes aplicables)

- Vitest + React Testing Library en jsdom; queries por rol, label o texto visible (`data-testid` solo si no hay query accesible); `userEvent`, no `fireEvent`.
- Cada componente interactivo tiene un check axe (`expect(await axe(container)).toHaveNoViolations()`); se corrigen violaciones, no se desactivan reglas.
- Fixtures con los nombres `snake_case` de la API. Sin snapshots de árboles grandes. Sin reloj real. Nombres de test que dicen el comportamiento.

### Convención `_base` (Node, partes aplicables)

- TypeScript obligatorio, `strict`, sin `any`. Archivos y carpetas `kebab-case`; funciones/variables `camelCase`; tipos `PascalCase` sin `I`; constantes globales `SCREAMING_SNAKE_CASE`.
- Imports: (1) externos y `@nerdose/*`, (2) absolutos del proyecto, (3) relativos del mismo módulo; grupos separados por línea en blanco. `import type` para tipos (`verbatimModuleSyntax`).
- Comentarios: solo el porqué no obvio. Sin `// TODO` sin issue.

### Manejo de errores (aplicable al client)

- El client **no hace requests**: no recibe `ApiError` sino un `moveError: { code, message } | null` que le pasa `web`. Rama solo por `code` (catálogo cerrado de `@nerdose/core`): `not_in_word_list` y `rate_limited` se muestran en el hint `aviso-jugada` con claves propias de UI; cualquier otro `code` que `web` decida mostrar ahí se muestra con el `message` tal como llegó (ya localizado por la `api`).
- Datos de la `api` con forma inválida (`publicView`, `state`, `result`, `gameStats.extra`) → el parse Zod lanza `ZodError` y lo captura el error boundary de la ruta en `web` (`route-error.tsx`). Es un error de programación/contrato, no un estado de pantalla.

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables

- **Decisión:** cada juego es un paquete `packages/games/<game_id>` con tres entradas; la entrada `./client` expone `Instructions`, `Game`, `Result` (componentes React) y `share(result, number): string`. Hay un registry en `api`, en `web`/`admin` y en `generator`.
- **Reglas de Implementación (verbatim):**
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload)`; después, `result(payload, state)`.
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.
- **Consecuencia:** el admin reutiliza los componentes `client` para la preview con la solución (FG-7).

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (… `@nerdose/game-<game_id>`).
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
- Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.

#### ADR-014: Métricas y analítica (regla que acota al client)

- `web` MUST llamar solo a `track(event)` de `@nerdose/ui`; el evento de share MUST llamarse exactamente `share:<game_id>`. → El client **no** llama a `track()`: `share()` solo devuelve el texto; el evento lo emite `web` tras compartir.

### API Context

El client no llama a la `api`. Recibe por props los datos que `web` obtiene de `docs/apis/api.yaml` (copiado):

**`GET /api/games/{game_id}/today` → `200 GameToday`**
```yaml
GameToday:
  required: [game_id, date, number, challenge_status, public_view, play, result, game_stats]
  game_id: GameId
  date: string (date)
  number: integer >= 1, nullable   # null antes de LAUNCH_DATE (challenge_status none)
  challenge_status: PublicChallengeStatus
  public_view: PublicView, nullable  # null si challenge_status es none o voided
```

- Ejemplo: `{ game_id: devdle, date: '2026-11-03', number: 128, challenge_status: published, public_view: { length: 5, possible_categories: [programming_languages, git, databases, networking, linux, apis, security, software_engineering] }, play: { status: in_progress, state: { guesses: [ { guess: REACT, marks: [absent, present, absent, absent, absent] } ] }, score: null, code_language: null }, result: null, game_stats: null }`

**Schemas Zod del paquete (`src/definition/schemas.ts`, copiados — los usa el client):**
```ts
export const WORD_PATTERN = /^[A-Z]{4,12}$/;
export const MAX_GUESSES = 6;
export const moveSchema = z.object({ guess: z.string().regex(WORD_PATTERN) });
export const letterMarkSchema = z.enum(['correct', 'present', 'absent']);
export const guessSchema = z.object({ guess: z.string().regex(WORD_PATTERN), marks: z.array(letterMarkSchema) });
export const stateSchema = z.object({ guesses: z.array(guessSchema).max(MAX_GUESSES) });
export const publicViewSchema = z.object({ length: z.number().int().min(4).max(12), possible_categories: z.array(z.enum(TERM_CATEGORIES)) });
export const resultSchema = z.object({ win: z.boolean(), score: z.number().int().min(1).max(6), word: z.string(), category: z.enum(TERM_CATEGORIES), definition: z.string(), summary: z.string(), guesses: z.array(guessSchema) });
export const statsSchema = z.object({ guesses: z.object({ '1': count, '2': count, '3': count, '4': count, '5': count, '6': count }), losses: count });
// Tipos: DevdleMove, DevdleGuess, DevdleState, DevdlePublicView, DevdleResult, DevdleStats, LetterMark
```
- En una derrota `result.score` es `6` y `win` es `false` (`definition.result`): el client decide `k/6` vs `X/6` por `win`, nunca por `score`.

**Errores que `web` traduce a `moveError` para el client (`POST …/move`, catálogo ADR-015):**
- `422 not_in_word_list` — `{ error: { code: not_in_word_list, message: 'La palabra no está en la lista' } }`; no consume intento.
- `429 rate_limited` — con `Retry-After`; la jugada no se procesa.
- `422 invalid_move` — no debería ocurrir si el client valida; si `web` lo pasa, se muestra su `message`.
- `401 no_session`, `409 game_finished`, `409 challenge_expired`, `409 challenge_voided` → **los resuelve `web`** (banner cookies, refetch → resultado, vuelta a instrucciones con «día nuevo», `locked` + `alerta-anulado`).

### Flow Context

**`abrir-y-retomar-juego` / `jugada-y-cierre-de-partida` (pasos que tocan al client, resumidos de la story):**
1. **[web - game-host]** `/devdle` → client lazy → `GET /api/games/devdle/today?lang` → pantalla según el estado.
2. **[web - devdle client]** Salir de Instrucciones → `onStart()` → `web` hace `POST …/start { challenge_number }`.
3. **[web - devdle client]** El jugador escribe con el teclado físico o en pantalla. Solo se aceptan A–Z (se pasa a mayúsculas, el resto se ignora con aviso). Con `guess.length !== public_view.length` no se envía (aviso, CA 7). `moveSchema.parse` → `onMove({ guess })` → `web` hace `POST .../move { challenge_number, move: { guess } }`.
4. **[web]** Si cerró la partida: Resultado con rachas y distribución, invalida `today`; Compartir con Web Share API o portapapeles.

**`preferencias-y-share` — Paso 2 (recargar contenido en el locale nuevo) y Paso 3 (Compartir, solo cliente), copiado:**
- Paso 2: `GET /api/games/{game_id}/today` devuelve `public_view` (y `result`, si terminó) en el idioma nuevo. La partida (`plays.state`) no cambia. → El client re-renderiza con el nuevo `t`/`locale` y el `result` nuevo: palabra, tablero y distribución no cambian; definición y resumen sí.
- Paso 3: (1) `text = share(result, number)` del `client` del juego. Nunca incluye la solución y termina en `nerdose.dev`. (2) `navigator.share({ text })` o `navigator.clipboard.writeText(text)` y el aviso "copiado". (3) `track('share:<game_id>')`. Errores: `AbortError` al cancelar → se ignora; compartir no hace ningún request.
- **Formato vigente (REQ-004 decisión 11, story CA-7, `user-flows.md` flujo 5):** `🟩 Devdle #N · k/6` (o `X/6`), una línea de 🟩🟨⬛ por intento y `nerdose.dev`; nunca la palabra ni la categoría. **Nota:** el ejemplo del flujo (`🟩 Devdle #128` / filas / `2/6` / `nerdose.dev`) es anterior a REQ-004 y quedó desactualizado; manda el formato de la story.

- **Por qué los datos del juego son `unknown`:** el shell "does not read game-specific fields" y su registry es genérico (`Partial<Record<GameId, () => Promise<GameClient>>>`). Si las props fueran `DevdlePublicView`, un `GameClient` genérico no podría tipar los cinco juegos sin casts. El client parsea con sus schemas y obtiene tipos fuertes adentro. El tipo `GameClient` lo define `web` estructuralmente a partir de estas props (**NOT DOCUMENTED** dónde vive un `GameClient` compartido: `@nerdose/core` no está en los servicios afectados de la story; si más adelante se mueve a `core`, estas props ya tienen la forma genérica).
- **i18n:** el client no depende de `react-i18next` (no está en "May import" de `game-package`). Exporta sus recursos (`i18n.resources.es` / `.en`, namespace `devdle`); `web` los registra en su instancia (`i18n.addResourceBundle(lng, 'devdle', resources[lng])`) y pasa `t = useTranslation('devdle').t`. Cumple a la vez `game-package` (imports permitidos) e `i18n` ("Game packages ship their own UI strings through the same i18n instance (a namespace per game, e.g. `devdle`)").
- **`HELP_TARGET_ID = 'game-help'`:** id que llevan la sección «cómo se juega» de `Instructions` y la leyenda de `Game`. El botón «Cómo se juega» del `GameHeader` de `web` apunta a `#game-help` sin conocer al juego (en `Result` no hay botón de ayuda).

- **faltan letras:** «Faltan letras: el término tiene 6.» — «el front no envía una palabra de otro largo (CA 7)».

- **sin sesión:** banner y reintento (web); el client mantiene la fila escrita.

**Interacciones (verbatim):**
- teclado (en pantalla o físico) · letra → la suma a la fila actual (en mayúsculas); Borrar/Backspace → borra la última.
- Enviar/Enter con el largo exacto → envía la jugada; el servidor la valida y se pinta el feedback de la fila.
- Validaciones: caracteres que no son A–Z → se ignoran con el aviso «Solo letras de la A a la Z.»; largo distinto del término → el front no lo envía y avisa «Faltan letras: el término tiene N.»; palabra fuera de la lista → «No está en la lista. Probá con otro término.» (no consume intento).

**Accesibilidad (verbatim):** Orden de foco: header → titulo → consigna → tablero → teclado → pistas → link-reportar. `h1` con el nombre del juego; las cabeceras `//` de pistas son `h2`. La partida se completa solo con teclado físico (NFR-U03); las teclas en pantalla son botones con nombre («Enviar», «Borrar»). El feedback de cada jugada se anuncia en una región `aria-live=polite` («C correcta, A en otra posición, …»); cada celda tiene etiqueta accesible y el estado nunca depende solo del color (NFR-U04).

**Decisiones (verbatim, aplicables):** el tablero tiene de 4 a 12 columnas según el término; las celdas escalan al ancho en lugar de cambiar de layout. La pista de categorías lista las 8 categorías fijas del banco como chips `neutral`. Un solo bloque `aviso-jugada` cubre los rechazos que no consumen intento (fuera de la lista, faltan letras, caracteres no válidos, 429), como hint del juego del DS. #### Pattern `game-boards` v1.0.0 — sección Devdle (copiada)

- **Reglas comunes:** (1) El juego se apropia de su pantalla (acento `game.devdle.*`). (2) **Borde estable:** las piezas con borde de 2px lo mantienen en todos los estados (mismo color que el fondo cuando no se ve) para que el cambio de estado no mueva el layout. (3) Correcto = verde; racha = ámbar. (4) **Sin animación:** no hay flip, shake ni transición. (5) Accesibilidad del PRD manda: todo se juega con teclado (NFR-U03) y el feedback suma ícono o patrón (NFR-U04).

#### Guidelines — Accesibilidad (`guidelines/accessibility.md` v0.1.0 placeholder, aplicable)

WCAG 2.2 AA mínimo. Texto ≥ 4.5:1; componentes interactivos (bordes, íconos) ≥ 3:1; NO comunicar estado solo con color. Todo interactivo accesible por teclado, foco visible (≥ 3:1), orden lógico, Enter/Space activan controles, sin keyboard traps. Íconos decorativos `aria-hidden`; live regions para feedback dinámico (`aria-live="polite"`). `prefers-reduced-motion`. Targets táctiles ≥ 44×44 con spacing ≥ 8px.
