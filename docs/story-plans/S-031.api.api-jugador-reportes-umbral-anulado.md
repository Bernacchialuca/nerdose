### Decisiones de planificación

1. **El reporte busca el desafío dentro de la transacción y con el lock en la misma sentencia.** `SELECT id, status, alerted_at FROM challenges WHERE game_id = $1 AND number = $2 AND status IN ('published','voided') AND date <= $hoy FOR SHARE`. Sin fila → `404 not_found` (CA-7). No usa la `TodayCache` (que solo tiene hoy) ni compara contra el número de hoy: un desafío pasado `published`/`voided` es reportable y no existe `challenge_expired` en este endpoint (story, Diseño Técnico y `api.yaml`).
2. **Un body inválido del reporte responde `422 invalid_report`, no `validation_error`.** Se usa un hook propio (`reportValidationHook`) solo en la ruta de reporte; cualquier falla de `ReportRequest` (`reason` fuera del enum, `message` > 1000 después del `trim`, `challenge_number` ausente/no entero/< 1, `code_language` fuera del enum) da `invalid_report` (contrato de `api.yaml`, CA-6). El `game_id` del path sigue con `validationHook`; un juego no registrado da `404 not_found` por `games.get`.
3. **`message`:** se aplica `trim`; un `message` vacío después del `trim` o ausente se guarda como `null` (la columna es nullable y el check solo limita el largo). Es una decisión de este plan: la story y el REQ solo dicen "con `trim`".
4. **`user_agent`:** header `User-Agent` truncado a 512 caracteres (`slice(0, 512)`); sin header → `null`.
5. **`code_language` del body — NOT DOCUMENTED (ver abajo).** Los tres juegos registrados (`devdle`, `grep-grid`, `timeline`) no usan lenguaje de código y ADR-006 prohíbe ramificar por `game_id`. Este plan arma `context.code_language = play?.codeLanguage ?? null` y valida (enum) pero ignora `body.code_language`. Cuando existan Big O / Bug Hunt habrá que sumar un mecanismo genérico (p. ej. un miembro del `GameDefinition`) para aceptarlo.
6. **Deadlock en la marca del umbral: se reintenta la transacción una vez.** Dos reportes concurrentes del mismo desafío tienen `FOR SHARE` sobre la misma fila; si ambos alcanzan el umbral, los dos `UPDATE challenges SET alerted_at …` se bloquean entre sí y PostgreSQL aborta uno con `40P01` (deadlock_detected). La story fija `FOR SHARE` (compatible con el `FOR UPDATE` de la anulación de S-032), así que el servicio reintenta **toda** la transacción del reporte una sola vez ante `40P01`; en el reintento el otro ya confirmó (`alerted_at` no nulo → no hay `UPDATE`). El código se lee de `err.code ?? err.cause?.code` (Drizzle envuelve el error de postgres.js en `cause`). Cubierto por TS-24.
7. **`umbral` como función pura** `shouldAlert({ n, f }, thresholds)` en `quality.threshold.ts`: `n >= count || (n >= ratioMinCount && f > 0 && n / f > ratio)`. Testeable sin base (TS-47).
8. **`start` pasa a usar transacción.** Hoy `start` hace `insertPlayIfAbsent` sin transacción. Para el `FOR SHARE` (decisión 6 del REQ) se ejecuta con `runInTx`: `lockChallenge` → `voided` ⇒ `409 challenge_voided` → `insertPlayIfAbsent` → `findPlay`. El chequeo rápido contra la cache se mantiene antes de abrir la transacción.
9. **Orden de locks (consistente con S-032):** `challenges` (FOR SHARE) → `plays` → `player_game_stats` → `player_stats`. La anulación de S-032 toma `challenges` FOR UPDATE → `plays` → stats; así no hay ciclos con `move`, `start` ni `acknowledge-void`.
10. **`acknowledge-void` con Play existente devuelve las rachas vivas** leyendo después del COMMIT: `game` = `{ current: gameStatsView.current_streak, max: gameStatsView.max_streak }` y `global` = `todayStreaks(...).global`. No escribe nada.
11. **`reported` en `GameToday`:** la consulta `EXISTS` sobre `challenge_reports` la expone `QualityRepository.hasReported(playerId, challengeId)` y se inyecta en `GameplayService` como dependencia (`reports`), respetando "un repositorio por módulo".
12. **Thresholds por constructor.** `QualityService` recibe `{ alertCount, alertRatio, alertRatioMinCount }` desde `env` en `src/index.ts`; los tests lo construyen con los defaults (3, 0.05, 2). No se agregan a `AppDeps.config`.
13. **Validación de env más estricta que el ejemplo de `env-config`:** `REPORT_ALERT_COUNT` entero ≥ 1 (default 3), `REPORT_ALERT_RATIO` número `> 0` y `< 1` (default 0.05), `REPORT_ALERT_RATIO_MIN_COUNT` entero ≥ 1 (default 2), tal como fija el REQ-007 (decisión 8).
14. **Tests existentes que cambian de forma:** todos los `toEqual` de `GameToday` suman `reported` (`game-today`, `grep-grid`, `grep-grid-rules`, `timeline`, `timeline-rules`, `move`, `publication` según corresponda), y el TS-14 de `test/http/game-today.test.ts` ("anulado aunque haya Play") pasa a esperar la Play del jugador (CA-8).

No existe en `GameDefinition`. Mientras solo estén registrados Devdle, Grep Grid y Timeline, se ignora el valor del body (decisión 5).

```
├── http/
│   ├── app.ts                    # buildApp(deps): requestId, logger, locale, secureHeaders, bodyLimit, Origin/CT, GET limit, onError, rutas

│   └── routes/index.ts           # registerRoutes: monta módulos; ensureToday sobre /api/today y /api/games/*
└── domain/{module}/{module}.{routes,controller,schema,service,repository,types}.ts
```

Módulos del manifest: `identity`, `gameplay`, `progress`, **`quality`** (reportes, umbral, anulación y recálculo), `publishing`, `admin`. Este plan crea `domain/quality/` (solo reportes y umbral; la anulación la suma S-032).

Reglas de `http-server` aplicables:
- Una ruta = un handler; los controllers no acceden a la DB, llaman al service.
- Toda entrada externa se valida con `@hono/zod-validator`.
- Sin envelope genérico; errores `{ "error": { "code", "message" } }`.
- Rutas de juego genéricas sobre el registry; prohibido `if (game_id === …)` (ADR-006).
- `today` se lee de `@nerdose/core` vía el reloj inyectado (`Clock`), nunca `new Date()` en dominio.
- La app se construye con `buildApp(deps)` para que los tests inyecten dependencias.

Manejo de errores (`error-handling`): `AppError(code)` del catálogo cerrado de `@nerdose/core`; el handler global responde `status` del catálogo y `message` localizado; cualquier otro error → `500 internal_error` con log `error` y stack. Los repositorios no lanzan `AppError`; el service traduce (p. ej. `ON CONFLICT DO NOTHING` sin fila → `already_reported`). Códigos usados en esta story: `no_session` 401, `forbidden_origin` 403, `not_found` 404, `no_challenge_today` 404, `challenge_expired` 409, `challenge_voided` 409, `game_finished` 409, `already_reported` 409, `not_voided` 409, `unsupported_media_type` 415, `invalid_report` 422, `validation_error` 422, `rate_limited` 429, `internal_error` 500. Mensajes ES ya existentes (`src/http/error-messages.ts`): `not_found` "Recurso no encontrado.", `already_reported` "Ya reportaste este desafío.", `invalid_report` "Reporte inválido.", `not_voided` "El desafío no está anulado.", `challenge_voided` "El desafío fue anulado.", `challenge_expired` "El desafío ya venció.", `no_challenge_today` "No hay desafío para hoy.", `rate_limited` "Demasiadas solicitudes.", `no_session` "No hay una sesión activa.".

Logging: `c.var.logger` (child con `requestId` y `playerId`); eventos de dominio con campo `event` y solo después del COMMIT (patrón de `GameplayService.move`: se acumulan en `events: Array<() => void>` y se emiten al final).

Testing (`testing`): integración contra PostgreSQL 16 real; fixtures con el rol owner y código bajo test con `nerdose_api`; `truncateAll` por archivo/test; relojes falsos (`vi.useFakeTimers({ toFake: ['Date'] })`); sin sleeps; rutas con `app.request()`; mutaciones con `Origin` y `Content-Type: application/json`.

### ADRs Relevantes

**ADR-017: Alertas registradas en la base y visibles en el admin**
- Decisión: una alerta es un registro en la base (`challenges.alerted_at`), no un mensaje. No hay mail ni webhook.
- Reglas de Implementación:
  - Las alertas MUST NOT salir del sistema en v1: ningún servicio MUST enviar mails, webhooks ni notificaciones push.
  - La marca del umbral MUST hacerse con `UPDATE challenges SET alerted_at = now() WHERE id = $1 AND alerted_at IS NULL` en la **misma transacción** que inserta el reporte. MUST NOT volver a `NULL`.
  - El umbral MUST leerse de `REPORT_ALERT_COUNT` (default 3), `REPORT_ALERT_RATIO` (default 0.05) y `REPORT_ALERT_RATIO_MIN_COUNT` (default 2). Solo cuentan los reportes con `reason IN ('wrong_answer','ambiguous')`, de jugadores distintos.
  - La falla de generación MUST registrarse con `INSERT … ON CONFLICT (game_id, date) DO UPDATE SET attempts, last_reason, updated_at`. Una corrida posterior para la misma fecha MUST actualizar esa fila, no crear otra.
  - `GET /api/admin/reports` MUST incluir `alerted_at` por grupo y ordenar primero los grupos con `alerted_at` no nulo.
  - `GET /api/admin/challenges/upcoming` MUST incluir, por día y juego, la falla registrada (`attempts`, `last_reason`) cuando no hay desafío.
  - Las alertas MUST NOT anular ni despublicar nada.

**ADR-011: Rachas con días neutros y agregados recalculables**
- Decisión: una sola implementación de rachas en `@nerdose/core`; días sin challenge `published`/`voided` son neutros.
- Reglas de Implementación:
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
  - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
  - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.

**ADR-008: Día de la plataforma, publicación perezosa y jugada tardía**
- Reglas de Implementación:
  - `today` MUST calcularse siempre en el servidor con la función de `@nerdose/core` (día UTC). MUST NOT aceptarse una fecha del cliente en ninguna ruta de jugador.
  - `number` MUST ser `today − LAUNCH_DATE + 1`, con `LAUNCH_DATE` (`YYYY-MM-DD`) como variable de entorno compartida por `api` y `generator`.
  - La publicación MUST ejecutarse con el primer request del día y al arrancar, protegida con single-flight en memoria: un solo request ejecuta y los concurrentes esperan esa misma promesa.
  - La sentencia de publicación MUST ser exactamente `UPDATE challenges SET status='published' WHERE status='approved' AND date = :today`. MUST NOT publicar fechas pasadas ni futuras.
  - Un `approved` de un día en el que la `api` nunca corrió MUST quedarse `approved`, y ese día es neutro para las rachas.
  - Los bodies de `POST /api/games/{game_id}/today/start`, `/move`, `/report` y `/acknowledge-void` MUST incluir `challenge_number` (entero ≥ 1).
  - Si `challenge_number ≠ number` de hoy, la `api` MUST responder `409` con `{ "error": { "code": "challenge_expired", … } }`.
  - Una Play `in_progress` de un día pasado MUST quedar `in_progress` para siempre y no contar como completada.
  - `GET /api/today` MUST devolver `next_reset_at` (próxima 00:00 UTC, ISO 8601) y `seconds_to_reset`. Al llegar a 0, el front MUST esperar 0–3 s al azar antes de volver a pedir.
- Nota: en `/report` el `challenge_number` identifica el desafío (hoy o pasado) y no se compara contra hoy (story y `api.yaml` actualizados por REQ-007); `acknowledge-void`, `start` y `move` sí responden `challenge_expired`.

**ADR-012: Caches y rate limit en memoria de la api**
- Reglas de Implementación:
  - La cache de desafíos MUST invalidarse al cambiar el día (ADR-008), al arrancar y al terminar `POST /api/admin/challenges/{challenge_id}/void`.
  - La lista válida de Devdle MUST cargarse al arrancar y recargarse al cambiar el día. MUST contener la unión del archivo base del paquete `devdle` y los `terms` `approved`. Sumar `terms` garantiza que toda respuesta posible sea un intento válido.
  - La lista válida MUST NOT enviarse al cliente ni exponerse en ninguna ruta.
  - Los límites MUST ser exactamente los de la tabla, configurados con `hono-rate-limiter` y store en memoria.
  - La IP del cliente MUST tomarse del header del proxy de confianza configurado (`TRUST_PROXY_HEADER`, por ejemplo `X-Forwarded-For`), nunca de un header arbitrario sin configurar.
  - Un `429` MUST incluir `Retry-After` en segundos y el body `{ "error": { "code": "rate_limited", "message": … } }`. MUST NOT haber captcha.
  - El límite por `player_id` MUST aplicarse después de resolver la cookie `nd_pid`. Si no hay cookie, aplica solo el límite por IP.

**ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores**
- Reglas de Implementación:
  - Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
  - Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
  - `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
  - El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
  - Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
  - Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
  - Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
  - Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; `code_language`: `js | go | java`; `locale`: `es | en`).
  - Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.

**ADR-006: Contrato `GameDefinition` (extracto aplicable)**
- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
- La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`).

**ADR-004: PostgreSQL con roles (extracto aplicable)**
- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
- `plays` MUST tener `UNIQUE (player_id, challenge_id)` y `challenge_reports` MUST tener `UNIQUE (player_id, challenge_id)`.
- `challenge_reports.context` es `jsonb`.

**ADR-009: Identidad del jugador anónimo (extracto aplicable)**
- Las rutas de jugador que lo exigen MUST responder `401` con `{ "error": { "code": "no_session", … } }` si falta la cookie o no es válida.
- Toda mutación MUST rechazar con `415` un `Content-Type` distinto de `application/json`, y con `403 forbidden_origin` un `Origin` ausente o distinto de `WEB_ORIGIN` (rutas de jugador).
- MUST NOT guardarse PII del jugador en `players`. El `user_agent` solo se guarda en el `context` de un reporte.

### Contexto de API

Ref: `docs/apis/api.yaml`.

**`POST /api/games/{game_id}/today/report`** (`operationId: reportChallenge`, tag Reports, `security: playerCookie`)
- Descripción: solo sobre un desafío `published` o `voided` de ese juego, de hoy o de un día pasado, identificado por `challenge_number`. `context` lo arma el servidor (`code_language`, `play_status`, `play_state`, `user_agent`) y `locale`. Uno por jugador y desafío. Umbral (`REPORT_ALERT_COUNT` = 3, o `REPORT_ALERT_RATIO_MIN_COUNT` = 2 y > `REPORT_ALERT_RATIO` = 5% de las Play terminadas, contando solo `wrong_answer`/`ambiguous`) y `challenges.alerted_at IS NULL` → `alerted_at = now()` en la misma transacción, una vez. Rate limit: 10 / hora por IP.
- Request `ReportRequest`:
  ```yaml
  ReportRequest:
    type: object
    required: [challenge_number, reason]
    properties:
      challenge_number: { type: integer, minimum: 1 }
      reason: { $ref: '#/components/schemas/ReportReason' }   # wrong_answer | ambiguous | wrong_explanation | translation | display_bug | other
      message: { type: string, maxLength: 1000 }
      code_language:
        allOf: [ { $ref: '#/components/schemas/CodeLanguage' } ]   # js | go | java
        description: Solo big-o y bug-hunt; si la Play tiene `code_language`, manda la Play
  ```
  Ejemplo: `{ challenge_number: 128, reason: wrong_answer, message: 'La línea 7 no tiene el bug', code_language: go }`
- Responses: `201 { report_id: uuid }` (ej. `{ report_id: 3f6c1d2e-8a4b-4c1f-9e2a-7b5d0c9e1a23 }`); `401 NoSession`; `403 ForbiddenOrigin`; `404 NotFound` (`not_found`); `409` `already_reported`; `415`; `422` `invalid_report` (`reason` inválido o `message` > 1000); `429 RateLimited`.

**`POST /api/games/{game_id}/today/acknowledge-void`** (`operationId: acknowledgeVoid`, `security: playerCookie`)
- Para un jugador sin Play en el desafío anulado de hoy: crea una Play `voided` (`finished_at = now()`), `ON CONFLICT DO NOTHING`, y actualiza rachas y `total_completed`. ### Contexto de Flujos

**reporte-de-problema** (según la story; el doc de flujo está desactualizado):
1. `[web]` `POST /api/games/grep-grid/today/report` con `{ challenge_number, reason, message }`.
2. `[api - quality]` `limit` (10/h IP) → sesión → body (`422 invalid_report`) → transacción: `SELECT … FROM challenges WHERE game_id AND number AND status IN ('published','voided') AND date <= hoy FOR SHARE` (sin fila → `404 not_found`) → Play del jugador → `INSERT challenge_reports … ON CONFLICT (player_id, challenge_id) DO NOTHING RETURNING id` (sin fila → `409 already_reported`) → si `reason ∈ {wrong_answer, ambiguous}`, `status = published` y `alerted_at IS NULL`: `n = count(*)` de reportes `wrong_answer`/`ambiguous` del desafío, `f = count(*)` de Play `won`/`lost`; si `n >= COUNT` o (`n >= MIN_COUNT` y `f > 0` y `n/f > RATIO`) → `UPDATE challenges SET alerted_at = now() WHERE id = $1 AND alerted_at IS NULL` → COMMIT.
3. `[api]` `201 { report_id }`. Eventos: `ChallengeReported` (`report_id`, `challenge_id`, `reason`, `locale`; sin `message`), `ReportThresholdReached` (`challenge_id`, `report_count`, `ratio`) solo si el UPDATE afectó una fila.

**anulacion-de-desafio, pasos 4 y 5** (según la story):
4. `[web]` `GET …/today` → `challenge_status: voided`; sin Play → `{ public_view: null, play: null, result: null, game_stats: null, reported }`; con Play `voided` → `play: { status: voided, state, score, code_language }` + `game_stats`.
5. `[api - gameplay]` `POST …/acknowledge-void { challenge_number }`: `challenge_number == hoy` (si no `409 challenge_expired`) → cache con desafío de hoy (si no `404 no_challenge_today`) → transacción: `SELECT … FOR SHARE`; `status <> 'voided'` → `409 not_voided` → `INSERT plays (state = '{}', status = 'voided', finished_at = now()) ON CONFLICT DO NOTHING RETURNING` → si insertó `applyResult(outcome voided)` (racha del juego, global y `total_completed`; no `played`/`wins`/`extra`) → COMMIT → `200`; si no insertó → rachas vivas sin escribir. Eventos `PlayVoidAcknowledged`, `StreaksUpdated`.

**jugada-y-cierre-de-partida / abrir-y-retomar-juego** (cambios de esta story):
- `start`/`move`: validaciones previas (cache, `challenge_number`, `voided` en cache) + dentro de la transacción `SELECT status FROM challenges WHERE id = $1 FOR SHARE` antes de tocar `plays`; `voided` → `409 challenge_voided`. Una Play `voided` → `challenge_voided` (no `game_finished`).
- `GET …/today`: `reported` y Play `voided` como arriba.
