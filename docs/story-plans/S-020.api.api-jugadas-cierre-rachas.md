# Story Plan: S-020 (api) - API: jugadas, cierre transaccional y rachas

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-020](../stories/S-020.api-jugadas-cierre-rachas.md)
- **Servicio:** api
- **Resumen:** Implementa `POST /api/games/{game_id}/today/move`. El endpoint valida la jugada en el servidor y la aplica con `applyMove` dentro de una transacción serializada (`INSERT … ON CONFLICT DO NOTHING` + `SELECT … FOR UPDATE`). Si la jugada termina la partida, en la misma transacción cierra la Play y aplica `progress.applyResult` (rachas con días neutros usando `nextStreak` de `core`, contadores y `extra`), y responde `result`, `streaks` y `game_stats`. También registra `rejected_guesses` como mejor esfuerzo y aplica los rate limits 60/min por jugador y 300/min por IP.

> **Alcance de este plan:** solo el servicio `api` (`apps/api`). No hay cambios de base de datos: las tablas `plays`, `player_game_stats`, `player_stats` y `rejected_guesses`, y sus `GRANT` al rol `nerdose_api`, son de S-015.
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a `apps/api/` salvo que se indique `(raíz)`.
>
> **Dependencias:** S-019 (registry con Devdle, `TodayCache`, `WordList`, módulo `gameplay` con `getToday`/`start`, módulo `progress` de lectura) está `Completed` y mergeada en `dev` (commit `4f4d7df`). S-014 (`nextStreak`, `MoveContext`) y S-017 (`@nerdose/game-devdle/definition`) también están mergeadas.
>
> **UX / Design System:** la story tiene `affects_ui: false`, así que no se carga contexto de UX ni de Design System.
>
> **Fuera de alcance:**
> - `acknowledge-void` y `recomputeStats` (FG-6). `applyResult` igual acepta `status: 'voided'` para que FG-6 lo reuse (decisión 6).
> - `report` (FG-7) y `GET /api/me/stats` (FG-10).
> - El texto de share: lo arma el `client` en S-021 (decisión 11 del REQ).
> - `players.preferred_code_language` al cerrar Big O o Bug Hunt (no hay paquete registrado; ver decisión 12).

### Decisiones de planificación

1. **Orden real de las validaciones de `move`.**
   - Antes del handler corren los middlewares globales `originAndContentType` (`403 forbidden_origin` / `415 unsupported_media_type`) y `ensureToday`.
   - **Middlewares de la ruta**, en el orden del ejemplo de la convención `security`:
     1. `limit` 300/min por IP (`clientIp(TRUST_PROXY_HEADER)`), que también cubre requests sin cookie.
     2. `playerSession('required')` → `401 no_session`.
     3. `limit` 60/min por `player_id`.
     4. `zValidator('param', gameParamSchema)`.
     5. `zValidator('json', moveBodySchema)` → `422 validation_error` si `challenge_number` falta o no es entero ≥ 1.
   - **Servicio**, en el orden de la decisión 7 del REQ:
     1. `games.get` → `404 not_found`.
     2. Número de hoy → `409 challenge_expired` (incluye `number === null` antes de `LAUNCH_DATE`). Va **antes** de la cache.
     3. `cache.get` → `404 no_challenge_today`.
     4. `voided` → `409 challenge_voided`.
     5. `game.moveSchema.safeParse(move)` → `422 invalid_move`. Si falta `move`, el parse falla y la respuesta también es `invalid_move`.
     6. Transacción.
   - Toda request que llega a la ruta cuenta para los dos límites, incluidas las `422 not_in_word_list` (supuesto del REQ: evita usar el endpoint como oráculo de la lista).
2. **Transacción inyectable (`MoveTx`).** `GameplayService` no recibe `db`. Recibe una función `runInTx: MoveTx`:
   ```ts
   type MoveTxRepos = {
     plays: Pick<GameplayRepository, 'insertPlayIfAbsent' | 'lockPlay' | 'updateState' | 'closePlay'>;
     progress: ProgressWriteRepo;
   };
   type MoveTx = <T>(fn: (r: MoveTxRepos) => Promise<T>) => Promise<T>;
   ```
   - La implementación real es `moveTransaction(db)`: `(fn) => db.transaction((tx) => fn({ plays: new GameplayRepository(tx), progress: new ProgressRepository(tx) }))`. Si `fn` lanza, Drizzle hace ROLLBACK y relanza.
   - Así los unit tests usan un fake y los de integración usan PG real.
   - Cumple `orm` ("repositorio por módulo que recibe `Db | Tx`") y `platform-day` ("the closing transaction uses `Tx` repositories").
3. **Cómo se hace el ROLLBACK de los errores de la jugada.** Dentro de `runInTx`, `game_finished`, `invalid_move` y `not_in_word_list` se lanzan como `AppError`, así que Drizzle revierte todo, incluida la Play que el `INSERT … ON CONFLICT DO NOTHING` acaba de crear. El servicio captura el error **fuera** de la transacción para registrar el rechazo (decisión 4) y lo relanza. El handler global responde el `422`/`409`.
4. **La palabra rechazada se obtiene de forma genérica a través de `ctx`.**
   - **Restricción:** la `api` no puede leer `move.guess`, porque sería conocimiento específico de Devdle (ADR-006 / `game-registry`: no hay `if (game_id === …)`).
   - **Cómo se resuelve:** el servicio arma el `MoveContext` envolviendo `WordList.has` y guarda la última palabra que devolvió `false`:
     ```ts
     let rejectedWord: string | null = null;
     const ctx: MoveContext = {
       isValidWord: (w) => {
         const ok = wordList.has(w);
         if (!ok) rejectedWord = w.toUpperCase();
         return ok;
       },
     };
     ```
   - **Qué pasa con `not_in_word_list`:** después del ROLLBACK, si `rejectedWord !== null`, se ejecuta `rejected.insertRejectedGuess(rejectedWord, player.id)` (`INSERT INTO rejected_guesses (word, player_id) … ON CONFLICT DO NOTHING`) con el `Db` (no `Tx`).
   - **Si el `INSERT` falla:** `log.warn({ err, event: 'GuessRejectedNotRecorded' }, 'Rejected guess not recorded')` y la respuesta sigue siendo `422 not_in_word_list` (decisión 9 del REQ).
   - **Log `GuessRejected`:** se emite en `info` con `player_id` y `challenge_id`, sin la palabra.
5. **Locks de stats: "asegurar fila + `SELECT … FOR UPDATE`".**
   - **El riesgo:** la Play bloqueada serializa las jugadas sobre **el mismo** desafío, pero no protege `player_stats`, que comparten todos los juegos. Si se lee y se hace un UPSERT sin lock, dos cierres concurrentes de juegos distintos pueden perder una actualización.
   - **Cómo se resuelve:** `ProgressRepository` agrega dos métodos que siguen el mismo patrón que `plays`:
     - `lockGameStats(playerId, gameId, initialExtra)`: `INSERT INTO player_game_stats (player_id, game_id, extra) VALUES (…, initialExtra) ON CONFLICT DO NOTHING` y después `SELECT … FOR UPDATE`.
     - `lockPlayerStats(playerId)`: igual, sobre `player_stats`.
   - **`extra` de una fila nueva:** se inicializa con `game.initialStats()`, no con el default `'{}'` de la columna, para que `reduceStats` reciba un `Stats` válido.
   - **Escritura:** se hace con `saveGameStats` / `savePlayerStats` (`UPDATE … WHERE pk`).
   - Es el mismo patrón que la decisión 8 del REQ, sin SQL crudo: Drizzle soporta `.for('update')` y `.onConflictDoNothing()`.
6. **`ProgressService.applyResult` acepta `won | lost | voided`.**
   - **Firma:** `applyResult(repo: ProgressWriteRepo, input: { playerId; game: AnyGameDefinition; date: string; outcome: { status: 'won' | 'lost'; result: unknown } | { status: 'voided' } })`.
   - **Con `voided`:** suma a rachas y `total_completed`, pero no a `played`, `wins` ni `extra` (ADR-011, CA-4).
   - **Quién lo usa hoy:** en esta story `move` solo lo llama con `won`/`lost`. La rama `voided` se cubre con unit tests para que `acknowledge-void` (FG-6) la reuse sin reimplementarla.
   - **Cálculo de las rachas:**
     - `prev = await repo.prevActiveDays(date)`: la consulta de S-019 devuelve el `max(date)` de cada juego y el global, con `date < D` y `status IN ('published','voided')`.
     - **Racha del juego:**
       - `current_streak = nextStreak({ current: gs.currentStreak, lastCompleted: gs.lastCompletedDate, prevActiveDay: prev.byGame[game.id] ?? null }, date)`.
       - `max_streak = Math.max(gs.maxStreak, current_streak)`.
       - `last_completed_date = date`.
     - **Racha global:**
       - `global_streak = nextStreak({ current: ps.globalStreak, lastCompleted: ps.lastActiveDate, prevActiveDay: prev.global }, date)`.
       - `max_global_streak = Math.max(…)`.
       - `last_active_date = date`.
       - `total_completed + 1`.
     - **Contadores, solo con `won`/`lost`:** `played + 1`, `wins + (status === 'won' ? 1 : 0)` y `extra = game.reduceStats(gs.extra, result)`.
   - **Devuelve** `{ streaks: { game: { current, max }, global: { current, max } }, gameStats: GameStatsView }`.
     - `GameStatsView` sale de la fila ya actualizada.
     - `current_streak` es el valor nuevo, que está vivo por definición porque `last_completed_date = hoy`, igual que con `liveStreak`.
     - `win_rate = played === 0 ? null : wins / played`.
7. **Cierre de la Play.** Si `game.isFinished(state)`:
   - **Cálculo:**
     - `result = game.result(payload, state, locale)`.
     - `win = game.isWin(result)`.
     - `score = game.score(result)`.
   - **Escritura:** `plays.closePlay(play.id, { state, status: win ? 'won' : 'lost', result, score, finishedAt: clock.now() })` es un solo `UPDATE` con `state`, `status`, `result`, `score` y `finished_at`. Así se cumplen los checks `ck_plays_result_when_finished` y `ck_plays_finished_at` en una sentencia.
   - **`code_language`:** queda en `null`, porque Devdle no lo usa (ver decisión 12).
   - **`plays.result`:** se guarda en el **locale resuelto de la request**. Es solo el registro histórico: las respuestas al jugador siempre lo recalculan (decisión 12 del REQ). El locale en que se guarda no está documentado; ver la sección "NOT DOCUMENTED".
8. **Los logs de dominio se emiten después del COMMIT.**
   - El servicio junta los eventos dentro de `runInTx` y los loguea solo si la transacción confirmó. Así un ROLLBACK nunca deja un `PlayFinished` falso en los logs.
   - **Eventos:**
     - `PlayStarted` (`info`; si `move` creó la Play): `play_id`, `player_id`, `challenge_id`. Es el mismo evento que emite `start`.
     - `MoveApplied` (`debug`): `play_id`, `attempt` (= número de intentos válidos).
     - `PlayFinished` (`info`): `play_id`, `player_id`, `challenge_id`, `game_id`, `status`, `score`.
     - `StreaksUpdated` (`info`): `player_id`, `game_id`, `current_streak`, `max_streak`, `global_streak`, `max_global_streak`.
     - `GuessRejected` (`info`): `player_id`, `challenge_id`.
   - Ningún log incluye la palabra, la categoría ni el `payload`.
9. **Forma de `MoveResponse`.**
   - **Campos:** `{ feedback, play: { status, state, score }, result, streaks, game_stats }`.
     - `MoveResponse.play` **no** lleva `code_language`: así lo define el schema de `api.yaml`, que es distinto de `PlayView`.
     - `result`, `streaks` y `game_stats` son `null` mientras la partida sigue.
   - **`feedback`:** es el que devuelve `applyMove`. En Devdle es `{ guess, marks }`, y no revela la palabra (anti-spoiler, CA-9).
10. **`payload` y `state` sin parse Zod.** Se mantiene la decisión 8 de S-019: el contrato `GameDefinition` de `core` no expone `payloadSchema` ni `stateSchema`, así que la `api` pasa `challenge.payload` y `play.state` como `unknown` a la definición. Sigue pendiente la recomendación de `/product-change-technical-definition`.
11. **Unicidad y día de la Play.**
    - La Play se identifica por `(player_id, challenge_id)` del desafío de **hoy** que está en la cache.
    - Una Play `in_progress` de un día anterior nunca se toca: `challenge_expired` corta antes (CA-6). Queda `in_progress` para siempre (ADR-008).
    - `date` de la Play = `challenge.date`, que es el `D` que usan las rachas.
12. **`preferred_code_language` fuera de alcance.** El flujo `jugada-y-cierre-de-partida` actualiza `players.preferred_code_language` al cerrar Big O o Bug Hunt. No se implementa porque:
    - Solo hay que hacerlo en esos dos juegos, que no tienen paquete registrado, y no hay forma genérica de hacerlo sin código por juego.
    - El contrato `GameDefinition` no expone el lenguaje de la jugada.
    - Queda para FG-8/FG-9 junto con un método del contrato. `closePlay` deja `code_language` en `null`.
13. **Desviaciones de la implementación.** `moveBodySchema.move` es `z.unknown().optional()` (así un body sin `move` responde `422 invalid_move`, como exige TS-8). El log `MoveApplied` no incluye `attempt`, porque derivarlo requeriría conocer la forma del `state` de cada juego (ADR-006).
14. **Documentación de `api.yaml` (alineación menor).** La respuesta `404` de `/move` hoy referencia solo `NoChallengeToday`. La story y el REQ (decisión 13) piden también `not_found` para un juego sin paquete, igual que `start`. Task 7 reemplaza `'404' de `/move` por una descripción en línea idéntica a la de `start` (`'\`no_challenge_today\` (sin desafío hoy) o \`not_found\` (juego sin paquete registrado)'`), y agrega `game_stats: null` al ejemplo `devdle_en_curso`. Son cambios de documentación que no tocan el contrato del schema (`MoveResponse.game_stats` ya existe).

### NOT DOCUMENTED - needs verification

- **Locale con el que se guarda `plays.result`.** Ni ADR-011, ni el flujo, ni la decisión 12 del REQ lo fijan. Se usa el locale resuelto de la request (decisión de planificación 7). No tiene efecto visible, porque las respuestas siempre lo recalculan. Si FG-10 (historial) llegara a leer `plays.result`, solo usa `historyLabel(result)`, que no depende del idioma.

### ADRs Relevantes

**ADR-006: Contrato `GameDefinition` y registry**
- Decisión: cada juego es un paquete `@nerdose/game-<id>`, la `api` importa solo `./definition` y las rutas son genéricas sobre el registry.
- Reglas de Implementación:
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload)`; después, `result(payload, state)`.
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.
- Actualización REQ-004: `applyMove(p, s, m, now, ctx: MoveContext)`, con `ctx = { isValidWord(word) }` armado por la `api` desde `WordList.has`. Los juegos que no lo usan lo ignoran.
- Nota sobre `moveSchema`: la regla dice "`@hono/zod-validator`", pero el schema depende del `game_id` del path, que se conoce recién al resolver el registry. Por eso el body se valida en dos pasos: `zValidator('json', moveBodySchema)` valida `challenge_number` y deja `move: unknown`, y el servicio ejecuta `game.moveSchema.safeParse(move)`. Así lo muestra el ejemplo de la convención `game-registry` (`game.moveSchema.safeParse(input.move)` → `AppError('invalid_move')`).

**ADR-008: Día de la plataforma y publicación** (extracto aplicable)
- `today` MUST calcularse siempre en el servidor con la función de `@nerdose/core` (día UTC). MUST NOT aceptarse una fecha del cliente en ninguna ruta de jugador.
- `number` MUST ser `today − LAUNCH_DATE + 1`, con `LAUNCH_DATE` (`YYYY-MM-DD`) como variable de entorno compartida por `api` y `generator`.
- Los bodies de `POST /api/games/{game_id}/today/start`, `/move`, `/report` y `/acknowledge-void` MUST incluir `challenge_number` (entero ≥ 1).
- Si `challenge_number ≠ number` de hoy, la `api` MUST responder `409` con `{ "error": { "code": "challenge_expired", … } }`.
- Una Play `in_progress` de un día pasado MUST quedar `in_progress` para siempre y no contar como completada.

**ADR-011: Rachas con días neutros y agregados recalculables**
- Decisión:
  ```
  prev_active_day(game_id, D) = max(date) FROM challenges
                                WHERE game_id = :game_id AND date < D
                                  AND status IN ('published','voided')
  prev_active_day_global(D)   = el mismo max(date), sin filtrar game_id

  Al completar una Play del día D:
    game:   current_streak = (last_completed_date >= prev_active_day(game_id, D)) ? current_streak + 1 : 1
            (si last_completed_date == D, no cambia)
    global: global_streak  = (last_active_date >= prev_active_day_global(D)) ? global_streak + 1 : 1
            (si last_active_date == D, no cambia)
    max_* = max(max_*, current)

  Al leer: muestra current_streak si last_completed_date == today
           o last_completed_date >= prev_active_day(game_id, today); si no, 0
  ```
- Reglas de Implementación:
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
  - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
  - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.
- Aplica en esta story: la aplicación incremental en el cierre, con `nextStreak()`. `recomputeStats` es de FG-6 (decisión 18 del REQ).

**ADR-012: Caches y rate limit en memoria** (extracto aplicable)
- Límites de `POST /api/games/{game_id}/today/move`: 60 / min por `player_id` y 300 / min por IP.
- Reglas de Implementación:
  - La lista válida de Devdle MUST cargarse al arrancar y recargarse al cambiar el día. MUST contener la unión del archivo base del paquete `devdle` y los `terms` `approved`.
  - La lista válida MUST NOT enviarse al cliente ni exponerse en ninguna ruta.
  - Los límites MUST ser exactamente los de la tabla, configurados con `hono-rate-limiter` y store en memoria.
  - La IP del cliente MUST tomarse del header del proxy de confianza configurado (`TRUST_PROXY_HEADER`, por ejemplo `X-Forwarded-For`), nunca de un header arbitrario sin configurar.
  - Un `429` MUST incluir `Retry-After` en segundos y el body `{ "error": { "code": "rate_limited", "message": … } }`. MUST NOT haber captcha.
  - El límite por `player_id` MUST aplicarse después de resolver la cookie `nd_pid`. Si no hay cookie, aplica solo el límite por IP.

**ADR-015: Contratos JSON y errores** (extracto aplicable)
- Todas las propiedades JSON MUST estar en `snake_case` y coincidir con `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`.
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.

### Convenciones activas (extracto aplicable)

**`game-registry`**
- Las rutas resuelven el juego por el registry. No hay `if (game_id === ...)` ni `switch` por juego en `apps/api`.
- La `api` nunca serializa `challenges.payload` en una respuesta de jugador. Antes de que la Play termine responde `toPublic(payload, locale)`; después, `result(payload, state, locale)`.
- `moveSchema` del juego valida la jugada. Si el parse falla, la respuesta es `422 invalid_move`. Una jugada inválida para el estado también responde `invalid_move`. Una palabra de Devdle fuera de la lista válida responde `422 not_in_word_list` y no consume intento.
- Victoria, score, stats e `historyLabel` salen solo de la definición del juego (`isWin`, `score`, `reduceStats`, `historyLabel`).
- El `Feedback` de una jugada nunca contiene un valor de la solución que el juego no haya revelado por diseño.
- Ejemplo de la convención:

### Contexto de API

**`POST /api/games/{game_id}/today/move`** (operationId `makeMove`)
- Security: `playerCookie`. Parámetros: `game_id` (path), `lang` (query, opcional).
- Request body `MoveRequest` (requerido): `required: [challenge_number, move]`, con `challenge_number: { type: integer, minimum: 1 }` y `move: Move`.
  - Ejemplo Devdle: `{ challenge_number: 128, move: { guess: REACT } }`.
- Descripción del endpoint:
  - Valida `move` con `moveSchema` del juego y la aplica con `applyMove` en una transacción con `SELECT plays … FOR UPDATE`. Si no existe la Play, la crea `in_progress` como `/start`.
  - Si la jugada cierra la partida: guarda `plays.status = won|lost`, `result`, `score`, `code_language` y `finished_at`, y actualiza `player_game_stats` y `player_stats` en la misma transacción (rachas con días neutros, ADR-011).
  - Devdle: un intento fuera de la lista válida responde `422 not_in_word_list`, se registra en `rejected_guesses` y **no** consume intento.
  - Rate limit: 60 / min por `player_id` y 300 / min por IP.
- Respuestas:
  - `200 MoveResponse`:
    ```yaml
    MoveResponse:
      required: [feedback, play, result, streaks, game_stats]
      properties:
        feedback: Feedback            # nullable; Devdle: DevdleGuess { guess: '^[A-Z]{4,12}$', marks: LetterMark[] }
        play:
          required: [status, state, score]
          properties:
            status: PlayStatus        # in_progress | won | lost | voided
            state: PlayState          # Devdle: { guesses: DevdleGuess[] (máx. 6) }
            score: { type: integer, nullable: true }
        result: Result | null         # Solo si la jugada cerró la partida
        streaks: Streaks | null       # Solo si la jugada cerró la partida
        game_stats: GameStatsView | null   # Solo si la jugada cerró la partida
    Streaks: { required: [game, global], game: Streak, global: Streak }
    Streak:  { required: [current, max], current: integer ≥ 0, max: integer ≥ 0 }
    ```
  - Ejemplo `devdle_en_curso`: `{ feedback: { guess: REDIS, marks: [correct, correct, absent, absent, absent] }, play: { status: in_progress, state: { guesses: [ { guess: REDIS, marks: [...] } ] }, score: null }, result: null, streaks: null }`. Task 7 le agrega `game_stats: null`.
  - `401 NoSession`, `403 ForbiddenOrigin`.
  - `404`: `NoChallengeToday`. Task 7 documenta también `not_found` (decisión 13).
  - `409 PlayConflict`: `challenge_expired` (`challenge_number` ≠ número de hoy), `challenge_voided` (desafío anulado) o `game_finished` (la Play no está `in_progress`).
  - `415 UnsupportedMediaType`.
  - `422`: `invalid_move` (no pasa `moveSchema` o es inválida para el estado) o `not_in_word_list` (Devdle; no consume intento).
  - `429 RateLimited` (header `Retry-After`).
- **`DevdleResult`:** `required: [win, score, word, category, definition, summary, guesses]`. `score` va de 1 a 6; `definition` y `summary` son strings resueltos en el locale.
- **`GameStatsView`:** `required: [game_id, current_streak, max_streak, played, wins, win_rate, extra]`.
  - `current_streak` = racha viva.
  - `played` y `wins` excluyen `voided`.
  - `win_rate` = `wins / played`, o `null` si `played = 0`.
  - `extra` en Devdle: `{ "guesses": { "1": n, …, "6": n }, "losses": n }`.

### Contexto de Flujos

**`jugada-y-cierre-de-partida`** (con los ajustes de REQ-004, decisiones 7, 8, 9 y 10)

1. **Enviar la jugada.**
   - Request: `POST /api/games/{game_id}/today/move`, query `lang` opcional, body `{ "challenge_number": integer, "move": Move }`. Devdle: `{ "guess": "REACT" }` (A–Z, largo = `public_view.length`).
   - **Validaciones previas (sin transacción, orden ajustado por la decisión 7):** `nd_pid` → `challenge_number == number` → desafío de hoy en la cache → `status != 'voided'` → `moveSchema.parse(move)`.
2. **Aplicar la jugada** (decisión 8).
   - **Bloquear la Play:** `BEGIN` → `INSERT plays (player_id, challenge_id, game_id, date, state = initState(payload), status = 'in_progress') ON CONFLICT (player_id, challenge_id) DO NOTHING` → `SELECT … FOR UPDATE WHERE player_id AND challenge_id`. Si `status != 'in_progress'` → `409 game_finished`.
   - **Aplicar:** `applyMove(payload, state, move, now, ctx)` puede devolver:
     - `{ error: 'not_in_word_list' }` (solo Devdle) → **ROLLBACK** (decisión 9, reemplaza el "COMMIT" del diagrama original) → **fuera de la transacción**, `INSERT rejected_guesses (word, player_id) ON CONFLICT DO NOTHING`, de mejor esfuerzo → `422 not_in_word_list`. El `state` no cambia y no se consume intento.
     - `{ error: 'invalid_move' }` → ROLLBACK → `422 invalid_move`.
     - `{ state, feedback }` → `UPDATE plays SET state`.
   - **Eventos:** `GuessRejected` o `MoveApplied`, solo en los logs.
3. **Cerrar la partida** (si `isFinished(state)`, misma transacción).
   - **Calcular el resultado:** `result = result(payload, state, locale)`, `win = isWin(result)`, `score = score(result)`.
   - **Cerrar la Play:** `UPDATE plays SET status = win ? 'won' : 'lost', result, score, code_language (null en Devdle), finished_at = now()`.
   - **Leer los días activos anteriores:** `SELECT max(date) FROM challenges WHERE game_id AND date < D AND status IN ('published','voided')` (`prev_active_day`) y lo mismo sin `game_id` (`prev_active_day_global`).
   - **Actualizar `player_game_stats`:** `current_streak`, `max_streak`, `played + 1`, `wins + (win ? 1 : 0)`, `last_completed_date = D`, `extra = reduceStats(extra, result)`.
   - **Actualizar `player_stats`:** `global_streak`, `max_global_streak`, `last_active_date = D`, `total_completed + 1`.
   - `COMMIT`. Eventos `PlayFinished` y `StreaksUpdated`, solo en los logs.
4. **Respuesta.** `200 { feedback, play: { status, state, score }, result | null, streaks | null, game_stats | null }`. `game_stats` es nuevo (decisión 10).

**Manejo de errores del flujo:**

| Paso | Error | Código |
|---|---|---|
| 1 | Sin sesión | `401 no_session` |
| 1 | Sin desafío de hoy | `404 no_challenge_today` |
| 1 | Jugada tardía | `409 challenge_expired` |
| 1 | Desafío anulado | `409 challenge_voided` |
| 1 | `move` no pasa `moveSchema` | `422 invalid_move` |
| 2 | Play terminada | `409 game_finished` |
| 2 | Palabra fuera de la lista (Devdle) | `422 not_in_word_list` |
| 2 | Inválida para el estado | `422 invalid_move` |
| 1 | Rate limit (60/min por player, 300/min por IP) | `429 rate_limited` |
| 2–3 | Error de BD | `500 internal_error`, con ROLLBACK completo: ni la Play ni las rachas quedan a medias |

- **Notas del flujo:**
  - Si `last_completed_date == D` (no debería pasar por la unicidad de Play), la racha no cambia.
  - La lista válida de Devdle está en memoria (ADR-012). `rejected_guesses` solo se usa para el ranking del admin.

**`estadisticas-del-jugador`** (lo que toca el cierre)
- Las Play `voided` cuentan en las rachas y `total_completed`, pero no en `played`, `wins` ni `extra` (invariante 23).
- Las Play `in_progress` (incluidas las de días pasados) no cuentan.
- `win_rate = wins / played` (`null` si `played = 0`).

**`cambio-de-dia-y-publicacion`, paso 5 (jugada tardía)**
- `POST /api/games/{game_id}/today/move` con `{ "challenge_number": 127, "move": { … } }` enviado a las 00:00:05 UTC, cuando hoy es el #128 → `409 challenge_expired`.
- La Play vieja queda `in_progress`.

### Puntos de Integración

- **Servicios externos:** ninguno.
- **`@nerdose/game-devdle/definition`** (vía registry; el código de la `api` no la importa directamente):
  - `devdle.applyMove(p, s, m, now, ctx)`. Valida en este orden:
    1. Partida ya ganada o con 6 intentos → `{ error: 'invalid_move' }`.
    2. `guess` que no cumple `^[A-Z]{4,12}$` o con largo ≠ `p.word.length` → `invalid_move`.
    3. `guess !== p.word && !ctx.isValidWord(guess)` → `not_in_word_list`. La respuesta del día siempre se acepta.
    4. Si pasa todo → `{ state: { guesses: [...s.guesses, feedback] }, feedback: { guess, marks: scoreGuess(p.word, guess) } }`.
  - `devdle.moveSchema` = `z.object({ guess: z.string().regex(/^[A-Z]{4,12}$/) })`.
  - `devdle.isFinished(s)`: ganada o con 6 intentos.
  - `devdle.result(p, s, locale)` → `{ win, score: win ? s.guesses.length : 6, word, category, definition: p.definition[locale], summary: p.summary[locale], guesses }`.
  - `devdle.isWin(r)` = `r.win`; `devdle.score(r)` = `r.score`.
  - `devdle.initialStats()` → `{ guesses: { '1': 0, …, '6': 0 }, losses: 0 }`.
  - `devdle.reduceStats(prev, r)`: si es derrota, `losses + 1`; si es victoria, `guesses[String(score)] + 1`.
  - `devdle.historyLabel(r)` → `✓ {score}/6` o `✗ X/6`.
- **`@nerdose/core`:**
  - `nextStreak(input: { current; lastCompleted; prevActiveDay }, day)`: devuelve `current` si `lastCompleted === day`; `current + 1` si `lastCompleted !== null && (prevActiveDay === null || lastCompleted >= prevActiveDay)`; si no, `1`.
  - `MoveContext = { isValidWord(word: string): boolean }`.
  - `MoveError = 'invalid_move' | 'not_in_word_list'`.
