# Story Plan: S-053 (api) - API: métricas del admin

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-053](../stories/S-053.api-metricas-del-admin.md)
- **Servicio:** api
- **Resumen:** la `api` implementa `GET /api/admin/metrics?from&to`, protegido con el JWT del admin. Valida el rango con `validateMetricsRange` de core usando su propio reloj (`422 validation_error` si falla). Lee las 4 vistas `metrics_*` de S-052 filtradas por rango (salvo la distribución de rachas, que es una foto a hoy) y completa con su reloj y con core lo que las vistas no calculan:
  - `d1`/`d7` por cohorte (`null` si el día +1/+7 todavía no terminó);
  - los 5 tramos de racha viva con `isStreakAlive` y `prevActiveDays(today).global`;
  - el `summary` (únicos y completadas sobre `plays`, `d1`/`d7` ponderados por `cohort_size`).

  Ninguna columna de la respuesta expone `player_id`.

> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a `apps/api/`, salvo las que dicen `(raíz)`.
>
> **Estado actual del código (verificado al planificar, rama `dev` en `2166105`, después del merge de S-052):**
> - `packages/db/migrations/0008_metrics_views.sql` (raíz) crea las 4 vistas y el `GRANT SELECT ... TO nerdose_api`. Las vistas **no** están declaradas en el schema Drizzle de `@nerdose/db` (`packages/db/src/schema/` no menciona `metrics`).
> - `@nerdose/core` exporta `isStreakAlive(lastCompleted, prevActiveDay, today): boolean` y `validateMetricsRange(from, to, today): 'ok' | 'from_after_to' | 'future' | 'too_long'` (`packages/core/src/streaks.ts`, `packages/core/src/platform-day.ts`).
> - `apps/api/src/domain/progress/progress.repository.ts` tiene `prevActiveDays(day): Promise<{ byGame: Partial<Record<GameId, string>>; global: string | null }>` (último día `< day` con challenge `published`/`voided`). Lo usa `ProgressService` para la racha viva.
> - Las rutas de admin (`src/domain/admin/admin.routes.ts`) son: `/login`, `/reports`, `/reports/:report_id`, `/challenges/upcoming`, `/generation-failures` y `/content/stock`. **No existe** `/metrics`; hoy `GET /api/admin/metrics` con JWT responde `404 not_found`.
> - `src/http/routes/index.ts` monta `adminAuthExcept` sobre `/api/admin/*` antes de cualquier ruta de admin. `GET` no pasa por el chequeo de `Origin`/`Content-Type` (solo mutaciones) ni por el rate limit (las rutas de admin están excluidas del balde de lecturas).
> - El driver de Drizzle para postgres.js deja los tipos `date` (OID 1082) y `timestamptz` como **strings sin parsear** también en `db.execute(sql\`...\`)` (`drizzle-orm/postgres-js/driver.js`, `transparentParser`). Los `date` de las vistas llegan como `'YYYY-MM-DD'`.
> - `zod` 4.6.7: `z.iso.date()` acepta `2024-02-29` y rechaza `2026-02-30` y `2026-12-1` (verificado).

### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **Servicio nuevo `AdminMetricsService` en `src/domain/admin/admin-metrics.service.ts`.** Es el nombre que da la story. Va en un archivo propio, como `AdminContentService`, para no mezclarlo con el login y los reportes de `AdminService`.
2. **Lecturas de las vistas en `AdminRepository`**, el único repositorio del módulo `admin` (convención `orm`: un repositorio por módulo). Métodos nuevos: `metricsDailyPlayers(from, to)`, `metricsRetention(from, to)`, `metricsStreakDistribution()`, `metricsChallengeQuality(from, to)` y `playsSummary(from, to)`.
3. **SQL crudo para las vistas.** Las vistas no tienen schema Drizzle, y los servicios no pueden declarar tablas (`orm`). La convención `orm` permite SQL crudo para "the `metrics_*` views". Se usa `this.db.execute<Row>(sql\`...\`)` con un comentario de una línea con el porqué. Los parámetros de fecha van con cast explícito `${from}::date` para no depender de la inferencia de tipos del driver. Los tipos de fila de las vistas se escriben a mano (no hay schema del cual inferirlos) y se aliasan a camelCase en el `SELECT` (`game_id AS "gameId"`), igual que las filas del resto del repositorio. `playsSummary` sí usa el query builder de Drizzle sobre `plays`.
4. **`prevActiveDays` se reutiliza de `ProgressRepository`**, inyectado en `AdminMetricsService` como dependencia `activeDays: Pick<ProgressRepository, 'prevActiveDays'>`. La story y el flujo del REQ lo nombran (`prevActiveDays(today).global`). El overview define `admin` como orquestador de módulos de lectura, y ADR-011 exige una sola definición de `prev_active_day`. Copiar la consulta en `AdminRepository` duplicaría la regla.
5. **Día de la plataforma en un solo lugar.** `AdminMetricsService.currentDay()` devuelve `today(clock.now())` de core. El schema Zod de la query es una fábrica `metricsQuerySchema(currentDay: () => string)` que valida formato (`z.iso.date()`) y aplica `.refine((q) => validateMetricsRange(q.from, q.to, currentDay()) === 'ok')`. El handler llama `deps.adminMetrics.metrics(from, to, deps.adminMetrics.currentDay())`. El método se llama `currentDay` y no `today` para no chocar con la función `today` de core, que el mismo archivo importa. `metrics(from, to, today)` recibe el día por parámetro (firma de la story), así los tests unitarios lo fijan sin reloj.
6. **"El día +N terminó" = `shiftDay(cohort_date, N) < today`** (REQ-011, decisión 1: `null` si `cohort_date + 1 >= today`). Con `today = 2026-12-02`, la cohorte del `2026-12-01` tiene `d1: null`. Con `today = 2026-12-03`, `d1` ya se calcula.
7. **`summary.d1`/`d7` = `Σ dN_players / Σ cohort_size`** sobre las cohortes del rango cuyo día +N terminó. Es el promedio ponderado por `cohort_size` de las `dN` no nulas (REQ-011, decisión 4) sin acumular errores de redondeo. Si no hay ninguna cohorte que cumpla, es `null`.
8. **Sin redondeo en la `api`.** `completion_rate`, `win_rate`, `d1` y `d7` salen como `float8`/`number` sin redondear (`api.yaml`: `type: number`). El formato con un decimal (`96,7 %`) lo hace el `admin` (S-054). Los tests de CA-3 usan `toBeCloseTo(…, 3)`.
9. **Orden de las listas** (flujo del REQ-011, escenario Métricas):
   - `daily_players`: `ORDER BY date, game_id NULLS FIRST`. El total va primero y después los juegos en el orden del pgEnum, que es el de `GAME_IDS`.
   - `retention`: `ORDER BY cohort_date`.
   - `challenge_quality`: `ORDER BY date DESC, game_id`.
   - `streak_distribution`: siempre `['0', '1', '2-6', '7-29', '30+']`.
10. **Rango vacío:** `daily_players`, `retention` y `challenge_quality` vuelven `[]`. `summary` vuelve `{ unique_players: 0, completed: 0, d1: null, d7: null }`. `streak_distribution` sigue trayendo los 5 tramos porque no depende del rango (es una foto a hoy).
11. **Orden de chequeo:** JWT antes que validación. Un request sin token y con rango inválido responde `401 unauthorized`, porque `adminAuthExcept` corre antes que la ruta.
12. **Fixtures masivos.** Los CA usan 150, 100 y 300 jugadores/partidas. Se agregan a `test/helpers/db.ts` `insertPlayers(n)` e `insertPlays(values[])`, que hacen **un** `INSERT` multi-fila como owner, para que los tests no hagan cientos de round-trips.
13. **Ids de test.** Los `it` nuevos llevan el sufijo `(S-053 TS-n)`.

## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`), Node.js 24 LTS.
- **HTTP:** Hono ^4.13 + `@hono/node-server` (ADR-002). `@hono/zod-validator` para validar inputs.
- **Validación:** Zod ^4.6.7.
- **Base de datos:** PostgreSQL 16, Drizzle ORM ^0.45.4 sobre postgres.js ^4.0.0, a través de `@nerdose/db`. La `api` se conecta con el rol `nerdose_api`.
- **Lógica compartida:** `@nerdose/core` (`today`, `isStreakAlive`, `validateMetricsRange`, `AppError`, `GameId`).
- **Logs:** Pino (child logger por request en `c.var.logger`).
- **Tests:** Vitest con fake timers (`vi.useFakeTimers({ toFake: ['Date'] })`) y Testcontainers con PostgreSQL 16 compartido (`globalSetup`), archivos secuenciales y reset por archivo.

**Reglas de `http-server` que aplican (verbatim):**
- **One route = one controller handler**. No nested logic.
- Controllers **do not access the DB** or external systems. They call the module's `service`.
- Every endpoint that receives external input validates it with `@hono/zod-validator` (see `validation`). No route is open without validation.
- Status codes per the table above and `docs/apis/api.yaml`. Never answer `200` with an error inside.
- Responses have **no generic envelope**: the resource is returned directly. Errors use `{ "error": { "code", "message" } }` per `error-handling`.
- Path segments are kebab-case; query parameters and JSON properties are `snake_case` (`?from=2026-12-01&to=2026-12-07`).
- Route handlers read `today` from `@nerdose/core` through the platform-day service, never `new Date()` directly.
- The `app` is built by `buildApp(deps)` so tests can instantiate it with their own dependencies.

**Reglas de `orm` que aplican (verbatim):**
- No direct `db` calls from HTTP handlers, jobs or use-case functions. Always go through a module repository.
- One repository per domain module. Never share a repository across unrelated modules.
- Use types inferred from the schema (`typeof table.$inferSelect`) or from `@nerdose/db`. No hand-written types that duplicate the schema.
- Day columns are `date` (UTC day) and instants are `timestamptz`. Do not convert them with local timezones.
- Raw SQL only for what Drizzle cannot express (see How to use). Document why in a one-line comment.
- "Raw SQL is allowed only where Drizzle cannot express it: `LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`, the `metrics_*` views and migrations."

**Reglas de `validation` que aplican (verbatim):**
- Every route that receives external input validates it with `@hono/zod-validator`. No route is "open" without validation.
- Types are inferred from schemas (`z.infer`). No hand-written types that duplicate a schema.
- Validation failures reach the client as the closed error catalog: `422 validation_error`, or `422 invalid_move` for game moves. The raw Zod error is never returned.
- JSON property names in schemas are `snake_case` and match `docs/apis/api.yaml` (ADR-015). No `camelCase` aliases or transforms.
- Day dates are validated as `YYYY-MM-DD` strings and instants as ISO 8601 UTC; the server never accepts a date from the client on player routes (ADR-008).
- Response validation is done only in tests and anti-spoiler contract tests, not on every response.

Hook compartido (existente, `src/http/validation-hook.ts`):

**Manejo de errores (`error-handling`):** `AppError(code)` con un código del catálogo cerrado de `@nerdose/core`. El handler global responde `{ "error": { "code", "message" } }`, con `message` localizado (`es` por defecto). Los mensajes que importan acá (`src/http/error-messages.ts`):
- `validation_error` → `'Datos inválidos.'` (es) / `'Invalid data.'` (en)
- `unauthorized` → `'No autorizado.'` (es) / `'Unauthorized.'` (en)

**Logs:** esta ruta no emite eventos de dominio. Cualquier log usa `c.var.logger` (lleva el `requestId`). Las rutas de admin nunca leen ni emiten la cookie `nd_pid`.

**Testing (`testing`, verbatim de las reglas):**
- One shared container per suite, started in `globalSetup`. Never start a container in `beforeAll` per file or inside an `it`.
- Do not mock the database or `postgres.js` in integration tests. Real PostgreSQL 16 only.
- Unit tests are for pure functions. If it does I/O, write an integration test.
- Every file resets the database in `beforeAll` and owns its fixtures. No test depends on data left by another file.
- Fixtures use the owner role; the code under test uses `nerdose_api` or `nerdose_generator`.
- Streak and day logic is tested with fake clocks, including neutral days, voids and the day change.
- Reset mocks and timers between tests (`vi.clearAllMocks()`, `vi.useRealTimers()`).
- Keep log output quiet with `LOG_LEVEL=silent`.

### ADRs Relevantes

**ADR-014: Métricas en la base (sin analítica web)**
- Decisión: las métricas de producto salen de cuatro vistas en `@nerdose/db` que se leen con `GET /api/admin/metrics?from&to`. Sin analítica web.
- Reglas de Implementación (verbatim):
  - Las vistas MUST llamarse exactamente `metrics_daily_players`, `metrics_retention`, `metrics_streak_distribution` y `metrics_challenge_quality`, y MUST definirse en migraciones de `@nerdose/db`.
  - El rol `nerdose_api` MUST tener solo `SELECT` sobre las vistas `metrics_*`.
  - En `metrics_challenge_quality`, `completion_rate = finished / started` y `win_rate = won / finished`. Ambas MUST ser `null` si el divisor es 0.
  - Las Play `voided` MUST NOT contar en `finished` ni en `win_rate`.
  - El admin MUST mostrar las métricas como tablas HTML. MUST NOT agregarse librería de gráficos en v1.
  - `web` y `admin` MUST NOT cargar scripts de analítica ni de tracking de terceros, ni enviar eventos de uso. Sumar analítica requiere un ADR nuevo.
  - **Nota de implementación (REQ-011):** las vistas no dependen de "hoy". `metrics_retention` expone conteos (`d1_players`, `d7_players`) y `metrics_streak_distribution` el tramo de la racha guardada con `last_active_date`; la `api` completa `d1`/`d7` y la racha viva con su reloj y con `isStreakAlive` de core (ADR-011), para no duplicar la regla en SQL y poder probarla con relojes falsos.

**ADR-011: Rachas con días neutros y agregados recalculables**
- Decisión (verbatim):
  ```
  prev_active_day(game_id, D) = max(date) FROM challenges
                                WHERE game_id = :game_id AND date < D
                                  AND status IN ('published','voided')
  prev_active_day_global(D)   = el mismo max(date), sin filtrar game_id

  Al leer: muestra current_streak si last_completed_date == today
           o last_completed_date >= prev_active_day(game_id, today); si no, 0
  ```
- Reglas de Implementación (verbatim):
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
  - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
  - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.

**ADR-010: Autenticación del admin** — Reglas de Implementación aplicables (verbatim):
- Todas las rutas `/api/admin/*`, salvo `POST /api/admin/login` y `GET /api/admin/health`, MUST exigir `Authorization: Bearer <jwt>` válido. Si falta, es inválido o venció, MUST responder `401` con `{ "error": { "code": "unauthorized", … } }`.
- Las rutas `/api/admin/*` MUST NOT leer ni emitir la cookie `nd_pid`.
- MUST NOT haber refresh tokens ni usuarios múltiples.

**ADR-004: PostgreSQL como única base, con propiedad por roles** — Reglas aplicables (verbatim):
- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
- Fila del rol `nerdose_api`: "… `SELECT` de `job_runs`, `generation_failures` y las vistas `metrics_*`".

**ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores** — Reglas aplicables (verbatim):
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
- Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; …).
- Catálogo: `401 unauthorized` (ruta de admin sin JWT válido), `422 validation_error` (cualquier otro body, query o param inválido).

**Validación del rango (core, ya implementada en S-052):**

```ts
export type MetricsRangeReason = 'from_after_to' | 'future' | 'too_long';
export type MetricsRangeResult = 'ok' | MetricsRangeReason;

/** Admin metrics range: `from <= to`, `to <= today`, at most 366 days inclusive. Inputs must be valid `YYYY-MM-DD`. */
export function validateMetricsRange(from: string, to: string, today: string): MetricsRangeResult {
  if (from > to) return 'from_after_to';
  if (to > today) return 'future';
  const days =
    (Date.parse(`${to}T00:00:00.000Z`) - Date.parse(`${from}T00:00:00.000Z`)) / MS_PER_DAY;
  return days > 365 ? 'too_long' : 'ok';
}
```

Precondición: las tres fechas son `YYYY-MM-DD` válidas. Por eso la `api` valida el formato con Zod (`z.iso.date()`) antes de llamarla.

**Racha viva (core, ya implementada en S-052):**

```ts
/** ADR-011: alive if completed today or on/after the previous active day. Never writes. */
export function isStreakAlive(
  lastCompleted: string | null,
  prevActiveDay: string | null,
  today: string,
): boolean {
  if (lastCompleted === null) return false;
  return lastCompleted === today || prevActiveDay === null || lastCompleted >= prevActiveDay;
}
```

CREATE VIEW metrics_daily_players AS
SELECT date, game_id, count(DISTINCT player_id)::int AS players
FROM plays
GROUP BY GROUPING SETS ((date, game_id), (date));

CREATE VIEW metrics_retention AS
WITH completed AS (
  SELECT DISTINCT player_id, date FROM plays WHERE status IN ('won','lost','voided')
),
cohort AS (
  SELECT player_id, min(date) AS cohort_date FROM completed GROUP BY player_id
)
SELECT c.cohort_date,
       count(*)::int AS cohort_size,
       count(d1.player_id)::int AS d1_players,
       count(d7.player_id)::int AS d7_players
FROM cohort c
LEFT JOIN completed d1 ON d1.player_id = c.player_id AND d1.date = c.cohort_date + 1
LEFT JOIN completed d7 ON d7.player_id = c.player_id AND d7.date = c.cohort_date + 7
GROUP BY c.cohort_date;

CREATE VIEW metrics_streak_distribution AS
SELECT CASE WHEN coalesce(s.global_streak, 0) = 0 THEN '0'
            WHEN s.global_streak = 1 THEN '1'
            WHEN s.global_streak <= 6 THEN '2-6'
            WHEN s.global_streak <= 29 THEN '7-29'
            ELSE '30+' END AS bucket,
       s.last_active_date,
       count(*)::int AS players
FROM players p
LEFT JOIN player_stats s ON s.player_id = p.id
GROUP BY 1, 2;

-- Plays y reportes se preagregan por separado: un JOIN directo multiplicaría started por reports.
CREATE VIEW metrics_challenge_quality AS
SELECT c.id AS challenge_id,
       c.game_id,
       c.date,
       c.number,
       coalesce(p.started, 0) AS started,
       coalesce(p.finished, 0) AS finished,
       p.finished::float8 / NULLIF(p.started, 0) AS completion_rate,
       p.won::float8 / NULLIF(p.finished, 0) AS win_rate,
       coalesce(r.reports, 0) AS reports,
       c.status
FROM challenges c
LEFT JOIN (
  SELECT challenge_id,
         count(*)::int AS started,
         count(*) FILTER (WHERE status IN ('won','lost'))::int AS finished,
         count(*) FILTER (WHERE status = 'won')::int AS won
  FROM plays
  GROUP BY challenge_id
) p ON p.challenge_id = c.id
LEFT JOIN (
  SELECT challenge_id, count(*)::int AS reports
  FROM challenge_reports
  GROUP BY challenge_id
) r ON r.challenge_id = c.id
WHERE c.status IN ('published','voided');

GRANT SELECT ON metrics_daily_players, metrics_retention, metrics_streak_distribution, metrics_challenge_quality TO nerdose_api;

#### Descripción

async playsSummary(from: string, to: string): Promise<{ uniquePlayers: number; completed: number }> {
  const [row] = await this.db

      uniquePlayers: sql<number>`count(DISTINCT ${plays.playerId})::int`,
      completed: sql<number>`(count(*) FILTER (WHERE ${plays.status} IN ('won','lost','voided')))::int`,

### Tarea 2: `AdminMetricsService`: retención con el día de la plataforma, tramos vivos y `summary`

**Status:** Completed

#### Descripción

Crear `AdminMetricsService`, que arma la respuesta `Metrics` a partir de las filas de la Tarea 1 y de `prevActiveDays(today).global`. Calcula con el día de la plataforma lo que las vistas no saben (REQ-011, decisión 1; ADR-014, nota de implementación):

- el tramo de racha viva con `isStreakAlive` de core;

Expone `currentDay()` para que la ruta valide el rango con el mismo reloj.

#### Criterios de Aceptación

6. `daily_players` y `challenge_quality` se mapean a snake_case sin cambiar valores ni orden.
7. La racha viva no reimplementa la regla de ADR-011: usa `isStreakAlive`.

```ts
import { isStreakAlive, today } from '@nerdose/core';

import type { AdminRepository, RetentionRow } from '@/domain/admin/admin.repository';
import type { ProgressRepository } from '@/domain/progress/progress.repository';
import type { Clock } from '@/shared/clock';
import { shiftDay } from '@/shared/day';

import type { Metrics, StreakBucket } from './admin.types';

export const STREAK_BUCKETS = ['0', '1', '2-6', '7-29', '30+'] as const;

type Repo = Pick<
  AdminRepository,
  'metricsDailyPlayers' | 'metricsRetention' | 'metricsStreakDistribution' | 'metricsChallengeQuality' | 'playsSummary'
>;

/** El día cohort+N terminó si es anterior a hoy (REQ-011, decisión 1). */
const dayEnded = (cohortDate: string, offset: number, day: string) => shiftDay(cohortDate, offset) < day;

export class AdminMetricsService {
  constructor(
    private readonly deps: {
      repo: Repo;
      activeDays: Pick<ProgressRepository, 'prevActiveDays'>;
      clock: Clock;
    },
  ) {}

  currentDay(): string {
    return today(this.deps.clock.now());
  }

  async metrics(from: string, to: string, day: string): Promise<Metrics> {
    const { repo, activeDays } = this.deps;
    const [daily, cohorts, streaks, quality, totals, prev] = await Promise.all([
      repo.metricsDailyPlayers(from, to),
      repo.metricsRetention(from, to),
      repo.metricsStreakDistribution(),
      repo.metricsChallengeQuality(from, to),
      repo.playsSummary(from, to),
      activeDays.prevActiveDays(day),
    ]);

    const rate = (c: RetentionRow, offset: 1 | 7, players: number) =>
      c.cohortSize > 0 && dayEnded(c.cohortDate, offset, day) ? players / c.cohortSize : null;

    const weighted = (offset: 1 | 7, pick: (c: RetentionRow) => number) => {
      let num = 0;
      let den = 0;
      for (const c of cohorts) {
        if (!dayEnded(c.cohortDate, offset, day)) continue;
        num += pick(c);
        den += c.cohortSize;
      }
      return den === 0 ? null : num / den;
    };

    const counts = new Map<StreakBucket, number>(STREAK_BUCKETS.map((b) => [b, 0]));
    for (const r of streaks) {
      const bucket = isStreakAlive(r.lastActiveDate, prev.global, day) ? r.bucket : '0';
      counts.set(bucket, (counts.get(bucket) ?? 0) + r.players);
    }

    return {
      summary: {
        unique_players: totals.uniquePlayers,
        completed: totals.completed,
        d1: weighted(1, (c) => c.d1Players),
        d7: weighted(7, (c) => c.d7Players),
      },
      daily_players: daily.map((r) => ({ date: r.date, game_id: r.gameId, players: r.players })),
      retention: cohorts.map((c) => ({
        cohort_date: c.cohortDate,
        cohort_size: c.cohortSize,
        d1: rate(c, 1, c.d1Players),
        d7: rate(c, 7, c.d7Players),
      })),
      streak_distribution: STREAK_BUCKETS.map((bucket) => ({ bucket, players: counts.get(bucket) ?? 0 })),
      challenge_quality: quality.map((q) => ({
        challenge_id: q.challengeId,
        game_id: q.gameId,
        date: q.date,
        number: q.number,
        started: q.started,
        finished: q.finished,
        completion_rate: q.completionRate,
        win_rate: q.winRate,
        reports: q.reports,
        status: q.status,
      })),
    };
  }
}
```

- `summary.dN` es equivalente al promedio de las `dN` no nulas ponderado por `cohort_size`: `Σ (dN · size) / Σ size = Σ dN_players / Σ size`. Si `cohortSize` fuera 0 (no puede pasar: la vista solo crea cohortes con al menos un jugador), el término suma 0 al numerador y 0 al denominador.
- Una fila de `'0'` con `lastActiveDate` no nulo y viva se queda en `'0'`. Una fila con `lastActiveDate: null` nunca está viva (`isStreakAlive` devuelve `false`) y va a `'0'`.

**Dependencias:**
- `@nerdose/core` (`isStreakAlive`, `today`), `@/shared/day` (`shiftDay`), `@/shared/clock` (`Clock`).

import { REPORT_STATUSES, validateMetricsRange } from '@nerdose/core';
