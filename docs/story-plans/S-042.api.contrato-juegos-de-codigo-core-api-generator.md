# Story Plan: S-042 (api) - Contrato de juegos de código en core, api y generator

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-042](../stories/S-042.contrato-juegos-de-codigo-core-api-generator.md)
- **Servicio:** api
- **Resumen:** Al cerrar una Play, la `api` guarda `plays.code_language = game.codeLanguage(state)` y, cuando ese valor no es `null`, actualiza `players.preferred_code_language` en la misma transacción que cierra la Play y actualiza las rachas. Además, `MoveResponse.play` suma `code_language`. Todo es genérico sobre el registry, sin ramificar por `game_id` (ADR-006). Con esto, Big O (S-043) y Bug Hunt funcionan en la `api` sin tocar el shell.

> **Alcance de este plan:** solo el servicio `api` (`apps/api`). La story también afecta a `core` (`Completed`: `GameDefinition.codeLanguage`, `verify` asíncrono, `HistorySpec.aheadDays`, `BIG_O_OPTIONS`, `RECIPE_CATEGORIES`), a `games` (`Completed`: Devdle, Grep Grid y Timeline implementan `codeLanguage: () => null`) y a `generator` (plan propio: `await generator.verify(...)` y la ventana `[D - recentDays, D + aheadDays]` sin `D`). Este plan cubre:
> - **CA-1** (parte `api`): la `api` consume `codeLanguage` de los tres juegos registrados (`null`) y **sus tests siguen en verde**. El único cambio en las aserciones existentes es el campo nuevo `play.code_language: null` en las respuestas de `move`.
> - **CA-2** completo.
> - **CA-3** completo.
> - **CA-4, CA-5 y CA-6:** no aplican a la `api`.
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a `apps/api/`, salvo las que dicen `(raíz)`.
>
> **Estado actual del código (verificado al planificar, rama `feature/S-042_*` en `ab3f9ec`):**
> - `@nerdose/core` ya exporta `GameDefinition.codeLanguage(s): CodeLanguage | null`, `CODE_LANGUAGES`, `CodeLanguage` y `BIG_O_OPTIONS`/`BigOOption` (plan `core`, completado).
> - `@nerdose/game-devdle`, `@nerdose/game-grep-grid` y `@nerdose/game-timeline` (`./definition`) implementan `codeLanguage: () => null` (plan `games`, completado).
> - `src/games/registry.ts`: `createGameRegistry([devdle, grepGrid, timeline])`. Big O y Bug Hunt **no** están registrados (llegan con S-043 y siguientes).
> - `src/domain/gameplay/gameplay.service.ts` → `move()`: al cerrar llama a `plays.closePlay(play.id, { state, status, result, score, finishedAt })` **sin** `codeLanguage`. Después llama a `progress.applyResult(pRepo, ...)` y responde `play: { status, state, score }` **sin** `code_language` (tanto en la rama `in_progress` como en la de cierre).
> - `src/domain/gameplay/gameplay.repository.ts` → `closePlay` hace `UPDATE plays SET state, status, result, score, finished_at`. No escribe `code_language`. `moveTransaction(db)` arma `{ plays: new GameplayRepository(tx), progress: new ProgressRepository(tx) }`.
> - `src/domain/gameplay/gameplay.types.ts`: `MoveResponse.play = { status: PlayStatus; state: unknown; score: number | null }`. `PlayView` ya tiene `code_language: CodeLanguage | null` y `toPlayView(p)` lo mapea desde `p.codeLanguage` (por eso `GET .../today` y `POST .../start` ya lo devuelven).
> - `src/domain/identity/identity.repository.ts` → `updatePreferences(id, { locale?, preferredCodeLanguage? })` ya existe (lo usa `PATCH /api/me/preferences`). Hace `UPDATE players SET ... WHERE id` y devuelve el `Player` o `null`.
> - `docs/apis/api.yaml` (raíz) ya tiene `MoveResponse.play.code_language` (requerido, nullable) y la descripción precisa de `POST .../move`. `docs/flows/jugada-y-cierre-de-partida.md` ya describe el paso nuevo. **No hay cambios de documentación de producto en este plan.**
> - El rol `nerdose_api` ya tiene `GRANT SELECT, INSERT, UPDATE ON players, plays`. No hay migraciones.

### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **La preferencia se escribe con `IdentityRepository.updatePreferences` dentro de la transacción de la jugada.** `MoveTxRepos` suma `identity: Pick<IdentityRepository, 'updatePreferences'>` y `moveTransaction(db)` construye `new IdentityRepository(tx)`. Es el mismo patrón que `progress: ProgressRepository` dentro de la transacción de la jugada, y reutiliza el único `UPDATE players SET preferred_code_language` que ya existe en lugar de duplicarlo en `GameplayRepository` (regla de `orm`: "One repository per domain module"; `players` es de `identity`). La llamada es `identity.updatePreferences(player.id, { preferredCodeLanguage: codeLanguage })`.
2. **Orden dentro de la transacción de cierre** (copiado del flujo `jugada-y-cierre-de-partida`, paso 3): `closePlay` (con `codeLanguage`) → `progress.applyResult` (rachas y stats) → `identity.updatePreferences` (solo si `codeLanguage !== null`) → COMMIT. Si cualquiera de los tres falla, ROLLBACK completo: ni la Play, ni las rachas, ni la preferencia quedan a medias.
3. **`codeLanguage` se calcula una sola vez, sobre el `state` resultante de `applyMove`** (`game.codeLanguage(r.state)`), solo en la rama de cierre. La rama `in_progress` no llama a `codeLanguage` y responde el valor persistido de la Play (`updated.codeLanguage`, que vale `null` porque `code_language` solo se escribe al cerrar). Así `MoveResponse.play` y `PlayView` salen del mismo mapeo.
4. **`MoveResponse.play` pasa a ser `PlayView`** (`{ status, state, score, code_language }`). Las dos ramas usan `toPlayView(row)` sobre la fila que devuelve `updateState` / `closePlay` (`.returning()`), en vez de armar el objeto a mano. El JSON es idéntico a `PlayView` del OpenAPI.
5. **El "juego de prueba" de CA-2 es un `GameDefinition` mínimo con `id: 'big-o'`, que vive en `test/helpers/code-game.ts`.** Tiene que ser `big-o` (o `bug-hunt`) porque la base tiene el check `ck_plays_code_language_game`: `code_language IS NULL OR game_id IN ('big-o','bug-hunt')`. Tiene la forma de una jugada única al estilo Big O (REQ-009 decisión 6): `move = { language, option }`, `codeLanguage(s) = s.language ?? null`. **No** es el Big O real (S-043) ni se registra en `src/games/registry.ts`. Se usa con un registry de test (`createGameRegistry([devdle, grepGrid, timeline, codeGame])`) inyectado por una opción nueva `games` en `buildDbServices` / `buildDbApp`.
6. **`code_language` en los logs.** El flujo y la convención `logging` no piden el campo en `PlayFinished`. No se agrega, para no inventar contrato de logs.
7. **Ids de test.** Los `it` nuevos o modificados llevan el sufijo `(S-042 TS-n)`, como en los planes `core` y `games` de esta story, para no chocar con los `TS-n` de stories anteriores que ya usan los archivos de test de la `api`.
8. **Hallazgo de documentación (no bloquea).** `docs/flows/jugada-y-cierre-de-partida.md`, paso 3, campo `code_language`, dice "`= move.language` en big-o / bug-hunt; si no, null". El diagrama, el paso de "preferencia", la descripción de `api.yaml` y ADR-006 dicen `codeLanguage(state)`. Se implementa `codeLanguage(state)` (ADR-006 y REQ-009 decisión 1: la `api` no lee campos propios del `move`). Queda anotado para corregir con `/product-change-technical-definition`.

**Patrones:**
- **Repositorio por módulo** que recibe `Db | Tx` por constructor. El mismo repositorio sirve dentro y fuera de una transacción.
- **Transacción de la jugada:** `runInTx: MoveTx` (`<T>(fn: (r: MoveTxRepos) => Promise<T>) => Promise<T>`). Si `fn` lanza, ROLLBACK y relanza. `moveTransaction(db)` es la implementación real. Los tests la envuelven con `wrapTxRepos` para forzar fallas.
- **Eventos de dominio en logs**, emitidos solo después del COMMIT (`events.push(() => log.info(...))` y `for (const emit of events) emit()`).
- **Servicio genérico sobre el registry:** `games.get(gameId)` devuelve `AnyGameDefinition`. No hay `if (game_id === …)`.

**Manejo de errores** (convención `error-handling`, extracto): `AppError(code)` con catálogo cerrado de `@nerdose/core`. Shape `{ "error": { "code", "message" } }`. Los repositorios dejan propagar los errores del driver. Todo error no `AppError` se responde `500 internal_error` y se loguea con stack. Esta story **no agrega códigos de error**.

**Testing** (convención `testing`, reglas que aplican):
- Un solo contenedor compartido, levantado en `globalSetup`. Nunca levantar contenedores por archivo.
- No mockear la base en tests de integración. Solo PostgreSQL 16 real.
- Los tests unitarios son para funciones puras o servicios con fakes. Si hay I/O, test de integración.
- Cada archivo resetea la base en `beforeAll`/`beforeEach` y arma sus fixtures. Las fixtures se insertan con el rol **owner**; el código bajo test usa el rol **`nerdose_api`** (así aparecen los errores de permisos).
- Fechas con reloj falso (`vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime(...)`), nunca el reloj real.
- Se afirma sobre contenido (una fila concreta), no sobre conteos globales.
- `describe` nombra la unidad e `it` el escenario. Archivos `*.test.ts` bajo `test/`.
- `LOG_LEVEL=silent` / logger capturado.

### ADRs Relevantes

**ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables**
- **Decisión:** cada juego es un paquete `packages/games/<game_id>` que implementa `GameDefinition` de `@nerdose/core`. Hay un registry en `api`, `web`/`admin` y `generator`. Las rutas de la `api` (`/api/games/{game_id}/today/*`) son genéricas sobre el registry. Miembro nuevo (REQ-009): `codeLanguage(s: State): CodeLanguage | null; // lenguaje con el que se confirmó (Big O, Bug Hunt); null en los demás`.
- **Reglas de Implementación (copia literal):**
  - La `api` MUST guardar `plays.code_language = codeLanguage(state)` al cerrar la Play y, si no es `null`, actualizar `players.preferred_code_language` en la misma transacción, sin ramificar por `game_id` (REQ-009).
  - `generateForDate` MUST hacer `await` de `verify`; los generadores síncronos siguen siendo válidos.
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
  - La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`). Con `state`, `toPublic` MAY revelar únicamente lo que el jugador ya descubrió en esa Play (Grep Grid: `words[].definition` de los `term_id` presentes en `found_words`); MUST NOT revelar nada de lo no descubierto (REQ-005).
  - `Feedback` MUST ir en el locale del jugador (`ctx.locale`), nunca como `{ es, en }` (ADR-015).
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` (sin estado y con estados intermedios, si el juego usa `state`) y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `bankUsage` MUST coincidir con `historySpec` del generator del mismo juego (banco y campo `last_used_*`); un test del paquete lo verifica. Los juegos sin banco declaran `null` (REQ-008).
  - `culprits(p)` MUST devolver solo ítems de banco presentes en el payload; un juego sin banco devuelve `[]` (REQ-007).
  - `Preview` MUST ser de solo lectura: valida `payload` con el schema del juego, traduce con los recursos del propio paquete según `language`, y no hace `fetch`, no usa storage ni estado de partida. `web` MUST NOT montarla (necesita el `payload` completo, que solo devuelve `/api/admin/*`). El admin la monta en ES y EN lado a lado; un juego sin `Preview` cae a la vista genérica del payload (REQ-008).
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

**ADR-011: Rachas con días neutros** (vía convención `platform-day`, reglas que aplican)
- Cerrar una Play y actualizar `player_game_stats` y `player_stats` ocurre en la misma transacción. Si una falla, todo vuelve atrás. **Esta story agrega `UPDATE players SET preferred_code_language` a esa misma transacción.**

**ADR-004: PostgreSQL única base con roles**
- La `api` se conecta como `nerdose_api`. Solo escribe las tablas y columnas que su rol permite. `GRANT SELECT, INSERT, UPDATE ON players, plays, player_game_stats, player_stats, challenge_reports, rejected_guesses TO nerdose_api;`. Ningún rol de servicio tiene `DELETE`, DDL ni `TRUNCATE`.

**ADR-015: Contratos JSON y errores**
- Campos JSON en `snake_case`. El `code` de error es del catálogo cerrado. Esta story no agrega códigos.

### Contexto de API

**`POST /api/games/{game_id}/today/move`** (`docs/apis/api.yaml`, `operationId: makeMove`, `security: playerCookie`, parámetros `GameIdPath` y `Lang`). Descripción vigente (extracto):

> Si la jugada cierra la partida: `plays.status = won|lost`, `result`, `score`, `code_language`, `finished_at`; se actualizan `player_game_stats` y `player_stats` en la misma transacción (rachas con días neutros, ADR-011). `code_language = codeLanguage(state)` del juego (Big O y Bug Hunt; `null` en los demás) y, cuando no es null, se actualiza `players.preferred_code_language` en la misma transacción.
>
> Rate limit: 60 / min por `player_id` y 300 / min por IP.

Request (`MoveRequest`): `{ "challenge_number": integer (>= 1), "move": Move del juego }`. Ejemplo de Big O en el spec: `{ challenge_number: 128, move: { language: go, option: o_n_log_n } }`.

Response `200` — schema `MoveResponse` (copia literal):


### Contexto de Flujos

**Flujo `jugada-y-cierre-de-partida`** (`docs/flows/jugada-y-cierre-de-partida.md`). Esta story implementa los **pasos 3 y 4**. Extracto relevante, copia literal:

```mermaid
    else jugada cierra la partida
        A->>DB: UPDATE plays SET status, result, score, code_language, finished_at
        A->>DB: SELECT max(date) FROM challenges (prev_active_day)
        A->>DB: UPSERT player_game_stats; UPSERT player_stats
        A->>DB: UPDATE players SET preferred_code_language (cuando `codeLanguage(state)` no es null: big-o / bug-hunt)
        A->>DB: COMMIT
        A-->>W: 200 { feedback, play, result, streaks }
    end
```

**Paso 3: Cerrar la partida (si `isFinished(state)`)** — Interno, misma transacción que el paso 2.
- **Acción:** `result = result(payload, state, locale)`, `win = isWin(result)`, `score = score(result)`.
- **Tabla `plays`, UPDATE:** `status = win ? 'won' : 'lost'`, `result`, `score`, `code_language` (= `codeLanguage(state)`; ver decisión 8), `finished_at = now()`.
- **Rachas (F3.1 / ADR-011):** `challenges` SELECT `max(date)` (`prev_active_day`, `prev_active_day_global`); `player_game_stats` INSERT … ON CONFLICT DO UPDATE; `player_stats` INSERT … ON CONFLICT DO UPDATE.
- **Tabla `players` (preferencia):** UPDATE `preferred_code_language = codeLanguage(state)` (solo cuando no es null: big-o y bug-hunt).
- **Eventos de dominio:** `PlayFinished`, `StreaksUpdated`, solo en los logs.

**Paso 4: Respuesta** — `200`:
