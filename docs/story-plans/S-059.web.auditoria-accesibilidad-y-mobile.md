# Story Plan: S-059 (web) - Auditoría de accesibilidad y mobile de la plataforma

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-059](../stories/S-059.auditoria-accesibilidad-y-mobile.md)
- **Servicio:** web
- **Resumen:** auditoría **puntual** de todas las pantallas del jugador (`apps/web`) con Playwright + `@axe-core/playwright` y la red simulada con `page.route` y los fixtures tipados que ya usan los tests de MSW. Se audita cada pantalla en sus estados principales en `mobile` (320 px) y `desktop`, con una spec de teclado por juego. Se corrige en `apps/web` lo que es propio de `web` y se dejan registradas, con todos sus datos, las violaciones cuyo origen está en `@nerdose/ui` o en los `client` de los juegos. Se crea el informe `docs/audits/accesibilidad-REQ-011.md` y al final se desinstalan Playwright y axe-playwright de `web` y se borran specs, configuración y scripts.

> **Alcance de este plan:** solo el servicio `web`: `apps/web/**`, el informe `docs/audits/accesibilidad-REQ-011.md` (lo **crea** este plan, que es el primero de la story) y, si una corrección de `web` cambia una apariencia documentada, `docs/design-system/web/**`. Queda **fuera**:
> - **`ui`** (plan `S-059.ui.*`): correcciones en `packages/ui` (contraste, foco, tamaños de toque, `Heatmap`).
> - **`games`** (plan `S-059.games.*`): correcciones en `packages/games/*/src/client` (`Instructions`, `Game`, `Result`, `StatsSummary`).
> - **`admin`** (plan `S-059.admin.*`): su propio arnés temporal (solo `desktop`), sus correcciones y su sección del informe.
>
> **Orden de ejecución de la story (CRÍTICO):** los planes se implementan en el orden de la tabla de servicios: **web → admin → games → ui**. Este plan es el primero, así que **no puede esperar** a las correcciones de `ui` y `games`. Por eso:
> 1. Toda violación con origen en `packages/ui` o `packages/games/*` se registra en el informe, en la sección «Hallazgos derivados», con la regla de axe, el impacto, la pantalla, el estado, el proyecto, el selector, los colores y el ratio que da axe, y el archivo del paquete donde está el origen. **No se corrige acá**.
> 2. El informe incluye la receta completa para repetir la auditoría (sección «Cómo repetir»), para que los planes `games` y `ui` verifiquen sus correcciones sobre páginas reales con el mismo método puntual. Es lo que pide `testing-e2e`: «A future audit follows the same one-off approach unless D3 is closed».
> 3. Al terminar este plan, `apps/web` queda **sin** Playwright (CA-7 para `web`).
>
> **Rutas:** las de «Archivos a crear/modificar» son relativas a `apps/web/`, salvo las que empiezan con `docs/`, `packages/` o `pnpm-lock.yaml` (raíz del repo).

### Convenciones activas (partes aplicables, verbatim)

#### `accessibility` (completa en lo normativo)

> ### Structure and semantics
> - One `<main>` per page, landmarks for header/nav/footer, one `<h1>` per screen, headings in order.
> - Use native elements first: `<button>`, `<a>`, `<input>`, `<label>`, `<table>`. Use ARIA only when no native element fits.
> - Every input has a visible `<label>` or an `aria-label`; errors are tied with `aria-describedby`.
>
> ### Keyboard
> - Everything operable with the mouse is operable with the keyboard, in a logical tab order, with no keyboard traps.
> - Timeline's drag and drop uses dnd-kit with **both** `TouchSensor` and `KeyboardSensor`, and announces moves through live regions.
> - Provide a visible focus ring on every focusable element (`focus-visible`).
>
> ### Not only color
> - Feedback that uses color (Devdle marks, Timeline correct/wrong, win/loss) is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
>
> ### Dynamic messages
> - Result, errors and notices appear in `role="status"` (polite) or `role="alert"` (errors) regions.
> - On navigation, move focus to the new page heading and update `document.title`.
>
> ### Motion and sizes
> - Honor `prefers-reduced-motion`.
> - Touch targets are at least 44 x 44 px. Layout reflows at 320 px without horizontal scroll and supports 200% text zoom.
>
> ## Rules
> - Contrast is at least 4.5:1 for text (3:1 for large text and UI boundaries) against its actual background.
> - No interactive element is built from a `<div>` or `<span>` with a click handler; use a native control.
> - Every image or icon is either decorative (`aria-hidden`) or has an accessible name.
> - Color is never the only carrier of meaning.
> - Each of the 5 games can be completed with the keyboard alone (NFR-U03).
> - Focus is never removed (`outline: none`) without a visible replacement.
> - Modal and overlay UI traps focus while open, closes with `Escape` and returns focus to the trigger.
> - Dynamic updates are announced via live regions; do not move focus unexpectedly.
> - axe-core reports zero violations in unit checks and in page audits (one-off while e2e is not adopted, see testing-e2e).
> - Language is declared (`<html lang>`) and updated when the locale changes.

Paquetes declarados: `axe-core / vitest-axe` (component checks), «`@axe-core/playwright`: not installed; only for one-off page audits (see testing-e2e, debt D3)», `eslint-plugin-jsx-a11y`.

#### `testing-e2e` (estado vigente y diseño de referencia, verbatim)

> ## Current status
> - **There is no e2e suite in the repo.** Playwright, `@axe-core/playwright`, `e2e/` and `playwright.config.ts` are **not** installed and MUST NOT be assumed by stories or plans. Critical flows are covered by route tests in jsdom (`testing-unit`), `vitest-axe` on components and manual verification.
> - **Debt D3 stays open:** adopting e2e requires a running `api` with seeded challenges of every game (there is no `seed:dev`).
> - **REQ-011 accessibility and mobile audit (S-059) was one-off:** Playwright + `@axe-core/playwright` were installed temporarily (mocking `/api/*` with `page.route` and fixtures typed with `api.yaml`), the violations were fixed, and then the dependencies, specs and configuration were removed. The result (violations found, fixes, accepted exceptions with justification) lives in `docs/audits/accesibilidad-REQ-011.md`. A future audit follows the same one-off approach unless D3 is closed.
>
> ### Accessibility on full pages
> ```ts
> // e2e/helpers/a11y.ts
> import AxeBuilder from '@axe-core/playwright';
> export async function expectNoA11yViolations(page: Page) {
>   const { violations } = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag21aa']).analyze();
>   expect(violations).toEqual([]);
> }
> ```
>
> ### Keyboard-only play
> - At least one spec per game completes a round using only `keyboard` actions (NFR-U03), including Timeline reordering with the keyboard sensor.
>
> ## Rules (reference design)
> - Select with roles, labels and text (`getByRole`, `getByLabel`); avoid CSS selectors.
> - Each critical flow has a spec, and every page-level spec ends with `expectNoA11yViolations`.
> - Every game has a keyboard-only spec (no mouse) that reaches its result.
> - Run at 320 px (`mobile`) and desktop; assert no horizontal scroll at 320 px.
> - Specs are independent: each starts from a known state and does not rely on another spec's data.
> - No fixed `waitForTimeout`; rely on auto-waiting assertions.
> - No spec reads or asserts the solution before the round ends.
>
> ## Update (REQ-011)
> - The accessibility and mobile audit of REQ-011 (S-059) is one-off: Playwright + `@axe-core/playwright` are installed only while it runs, with `/api/*` mocked through `page.route` and fixtures typed with the `api.yaml` contracts (tags `wcag2a`, `wcag2aa`, `wcag21aa`; `mobile` 320 px and `desktop`, `admin` only `desktop`). When it ends, the dependencies, specs and Playwright configuration are removed and the report stays in `docs/audits/accesibilidad-REQ-011.md`. Playwright is not a current tool of the repo; flows against a real `api` remain open debt (D3).

#### `testing-unit` (reglas aplicables a los tests de regresión de las correcciones, verbatim)

> - Query by role, label or visible text. `data-testid` only when no accessible query exists.
> - Use `userEvent`, not `fireEvent`, for interactions.
> - Each interactive component has an axe check; fix violations instead of disabling rules.
> - Fixtures use the API's `snake_case` names; do not write camelCase fixtures.
> - Mock the network with MSW, never the app's own modules (api client, hooks) except to isolate a single unit.
> - No snapshot tests of large DOM trees.
> - Tests do not rely on the real date or timers; use fake timers.
> - Test names state the behavior ("shows ... when ..."), not the implementation.
> - Tests never hit a real `api`.

#### `styling` (reglas aplicables a las correcciones, verbatim)

> - Use only the tokens above (or later, the Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components.
> - Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them.
> - Merge conditional classes with `cn()`; never concatenate class strings by hand.
> - Text and interactive-element contrast meets WCAG 2.1 AA against the surface it sits on (4.5:1 text, 3:1 large text and UI components). Verify any new color pair.
> - Focus is always visible: use `focus-visible:` rings with `--color-accent`; never `outline-none` without a replacement.
> - State is never conveyed by color alone: pair it with an icon, text or pattern (see `accessibility`).
> - Respect `prefers-reduced-motion`: animations are disabled or reduced under it.
> - **Responsive design:** no global media queries. Layout uses `flex-wrap` and `repeat(auto-fit, minmax(min(300px, 100%), 1fr))`; only the 320 px adaptations documented in the Design System are allowed. Page container is `max-w-page` (1240 px) with a 32 px gutter.
> - **Static check:** component and web `.tsx` files must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).

#### `_base` (aplicable)

> - **`app/`**: wiring only (providers, router, layout). No business logic.
> - **`modules/{module}/`**: everything that belongs to one module. A module never imports from another module's internals.
> - Shared UI goes to `packages/ui`; if a component is needed in both apps, move it there instead of duplicating it.
> - The shell contains **no per-game logic** (see `game-clients`).
> - Order within a file: (1) external libraries and `@nerdose/*`, (2) `@/` imports, (3) relative imports from the same folder. Separate groups with a blank line.
> - Type-only imports use `import type`.
> - Default: no comments. Comment only the why when it is not obvious.
> - Project structure lists `e2e/ # e2e specs (not adopted yet, debt D3; see testing-e2e)`.

#### `routing` y `game-clients` (aplicable)

> - On route change, move focus to the page `<h1>` (or the `main` landmark) and update `document.title`.
> - Each route sets a meaningful `document.title` and moves focus on navigation.
> - The registry is the only place that lists games. No `if (gameId === ...)` or `switch` by game anywhere in `apps/*`.
> - The shell renders games only through `Instructions`, `Game`, `Result` and `share`; it does not read game-specific fields.
> - **accessibility**: every game must be fully playable with keyboard and its feedback must not rely only on color.

Consecuencia para las correcciones: **`web` no puede corregir un problema de un juego con una rama por `game_id`** ni leyendo campos propios del juego. Si el problema está en el `client`, es un hallazgo derivado a `games`.

### Decisiones de REQ-011 aplicables (verbatim)

> **13. Auditoría de accesibilidad puntual con Playwright y red simulada.** axe en jsdom (`vitest-axe`) no evalúa contraste ni layout, y los CA 27-29 piden páginas reales a 320 px. Durante S-059 se instala Playwright + `@axe-core/playwright` en `web` y `admin` con proyectos `mobile` (320 px) y `desktop`, y las specs **simulan `/api/*` con `page.route`** y fixtures tipados con los contratos de `api.yaml` (reusando los de MSW de los tests unitarios). Motivo: no existe `seed:dev` ni un dataset con desafíos de los 5 juegos (los de Big O y Bug Hunt requieren el toolchain de `polyglot`), y la auditoría evalúa render, teclado y layout, no integración. **Por decisión del usuario, Playwright no queda en el repo:** al terminar se escribe el informe `docs/audits/accesibilidad-REQ-011.md` (violaciones encontradas, correcciones hechas, `incomplete` revisados a mano y excepciones aceptadas con justificación) y luego se desinstalan `@playwright/test` y `@axe-core/playwright` y se borran las specs, los fixtures de Playwright, la configuración y los scripts `e2e`. La convención `testing-e2e` (web y admin) indica que Playwright no es una herramienta vigente; la deuda D3 (flujos e2e con `api` real) sigue abierta.

> Riesgo: la auditoría encuentra violaciones en componentes del DS (contraste de niveles 0-1 del heatmap, focos, tamaños de toque) que cambian la apariencia. Mitigación: los ajustes se derivan del DS y se registran con `/product-design-system-update`; las excepciones aceptadas se documentan con su justificación.

> Riesgo: al desinstalar Playwright no queda una verificación automática de accesibilidad de páginas completas; una regresión futura no se detecta sola. Mitigación: decisión aceptada por el usuario. Quedan `vitest-axe` en los tests de componentes y de ruta, el informe con lo auditado y la deuda D3 abierta; una próxima auditoría puede repetirse con el mismo método puntual.

Supuestos del REQ que definen el alcance (verbatim):

> - **[Pulido / color]:** se verifica en los 5 juegos, el heatmap, las tablas de métricas y los estados de la home (resuelto, en curso, anulado): ningún estado depende solo del color; se suma ícono, texto o patrón.
> - **[Pulido / movimiento y contraste]:** se verifican contraste AA en tema oscuro (único tema), foco visible, tamaños de toque razonables en mobile y respeto de la preferencia de movimiento reducido en las animaciones que existan. No se agrega tema claro.
> - **[Pulido / admin]:** el requisito de 320 px aplica a la superficie del jugador; el admin se audita en accesibilidad (WCAG, teclado) y en desktop únicamente.

**grep-grid-resultado** — Orden: header → veredicto → grilla final (lectura) → lista de palabras (lectura) → rachas → link-reportar → salidas (Compartir va en el header). Encontradas vs. reveladas con texto y glifo además del color.

**timeline-partida**
- **Orden de foco:** header → titulo → lista-hitos (por fila: asa → ↑ → ↓) → ayuda-mover (lectura) → btn-confirmar → link-reportar.
- **Foco y teclado:** `KeyboardSensor` de dnd-kit sobre el asa (Espacio/Enter toma y suelta, flechas mueven, Escape cancela) y, como alternativa sin modo «tomado», los botones ↑ ↓ con Tab. El foco visible se mantiene sobre el hito movido.
- **Propio:** cada fila expone su posición («3 de 5»); los movimientos se anuncian en una región `aria-live="polite"` `sr-only`. La fila tomada se distingue por borde y anuncio, no solo por color. Con `prefers-reduced-motion` no hay transición de reacomodo. Áreas táctiles: asa y ↑ ↓ de al menos 40 px de lado incluso a 320 px; si el ancho no alcanza, el nombre envuelve antes que achicar los controles.

**timeline-resultado** — Cada fila de «tu orden» dice acierto o error con ícono y texto («✓ bien», «✗ va en 3°») y con borde sólido o punteado, nunca solo con color. La confirmación «Copiado» se anuncia con `role=status`.

**big-o-partida**
- **Orden de foco:** header → titulo → pestañas de lenguaje → cuerpo del código (si desborda) → grupo de opciones → btn-confirmar → card-reglas (lectura) → link-reportar.
- **Foco y teclado:** pestañas `tablist`/`tab`/`tabpanel` (flechas ← →, `aria-selected`). Opciones como `radiogroup`: Tab entra y sale del grupo, las flechas mueven la elección (roving tabindex). Enter o Espacio en «Confirmar respuesta» envía. Toda la partida se completa sin mouse.
- **Propio:** la opción elegida se distingue con borde, peso y `●`, no solo con color. Los números de línea son `aria-hidden`.

**big-o-resultado** — la correcta y la elegida se distinguen con ✓/✗ y las etiquetas «correcta» / «tu respuesta». El confeti es `aria-hidden` y respeta `prefers-reduced-motion`.

**bug-hunt-partida**
- **Orden de foco:** header → titulo → especificación y tests (lectura) → pestañas de lenguaje → grupo de líneas (una sola parada de Tab; roving tabindex entre elegibles) → btn-confirmar → card-reglas (lectura) → link-reportar.
- **Foco y teclado:** Líneas como `radiogroup`: Tab entra y sale del grupo, ↑ ↓ recorren solo las elegibles, Espacio elige. Enter o Espacio en «Confirmar línea» envía.
- **Propio:** la línea elegida se distingue con barra lateral, tag «◀ tu elección» y el número en el botón, no solo con color.

**bug-hunt-resultado** — la línea del bug y la elegida se distinguen con barra, glifo (✓ / 🐛 / ✗) y texto («acá estaba el bug», «tu elección»). El confeti es `aria-hidden` y respeta `prefers-reduced-motion`.

**O-01 reportar** — Rol `dialog` con `aria-modal="true"` y título «Reportar un problema»; el aviso de spoilers por `aria-describedby`. Foco inicial en el motivo; atrapa el foco; Esc cierra salvo en `loading`; al cerrar devuelve el foco a `link-reportar`. El contenido de la pantalla de origen queda `inert`.

**O-02 anulado** — Rol `alertdialog`. Orden: texto → btn-marcar → btn-cerrar. Atrapa el foco; Esc cierra; devuelve el foco al disparador.

**O-03 cookies** — `role=status`, se anuncia una sola vez; no entra en el orden de foco; no tapa el header ni los CTA.

**O-04 rendirse** — Rol `alertdialog` con `aria-labelledby`/`aria-describedby`. Foco inicial en «Seguir jugando»; Escape equivale a «Seguir jugando»; al cerrarse devuelve el foco a `btn-rendirse`. El fondo queda inerte.

#### Guideline de accesibilidad (`guidelines/accessibility.md` v0.1.0, placeholder; extracto verbatim)

> - Texto body: contraste ≥4.5:1. Texto grande: ≥3:1. Componentes interactivos (bordes, iconos): ≥3:1. NO comunicar estado solo con color.
> - Todo elemento interactivo es accesible vía teclado. Foco visible (outline o equivalente, contraste ≥3:1). Orden de tab lógico. ESC cierra modales / popovers. Enter / Space activan controles. Sin keyboard traps.
> - Iconos puramente decorativos: `aria-hidden="true"`. Iconos funcionales: `aria-label` descriptivo. Live regions para feedback dinámico.
> - Respetar `prefers-reduced-motion: reduce`. No flashing >3 veces/segundo. Animaciones >5s deben ser pausables.
> - Targets táctiles: mínimo 44×44px. Spacing entre targets ≥8px.

(El README aclara que las guidelines son placeholders y que «las reglas de accesibilidad vigentes están en cada foundation y spec». Manda la convención `accessibility`, que pide WCAG **2.1** AA.)

`e2e/api-mock.ts` (forma):

```ts
import type { Page, Request } from '@playwright/test';

export type MockResponse = { status?: number; json: unknown; headers?: Record<string, string> };
export type RouteHandler = MockResponse | ((request: Request, url: URL) => MockResponse);
/** Clave: `${METHOD} ${pathname}`, p. ej. `GET /api/today`. */
export type Routes = Record<string, RouteHandler>;

export const apiError = (code: string, message: string) => ({ error: { code, message } });

export async function mockApi(page: Page, routes: Routes) {
  const unhandled: string[] = [];
  const calls: { method: string; path: string; body: unknown }[] = [];
  await page.route('**/api/**', async (route) => {
    const request = route.request();
    const url = new URL(request.url());
    const key = `${request.method()} ${url.pathname}`;
    calls.push({ method: request.method(), path: url.pathname + url.search, body: request.postDataJSON() });
    const handler = routes[key];
    if (!handler) { unhandled.push(key); return route.abort('failed'); }
    const res = typeof handler === 'function' ? handler(request, url) : handler;
    return route.fulfill({ status: res.status ?? 200, json: res.json, headers: res.headers });
  });
  return { unhandled, calls };
}
```

```ts
function statefulGame(gameId: GameId, notStarted: GameToday, started: { play: GameToday['play'] }, finalMove: MoveResponse) {
```
