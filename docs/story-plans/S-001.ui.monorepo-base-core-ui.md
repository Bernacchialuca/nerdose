La Revisión UX de REQ-001 registra "Design System: sin gaps" y que `docs/design-system/{web,admin}` es `placeholder` (v0.1.1) con la paleta oscura del prototipo ya alineada (`#0A0C0F`, acento `#3DDC84`). ## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript con `strict: true` y `noUncheckedIndexedAccess: true` (ADR-002, `_base` de `ui`). Node.js 24 LTS (`engines.node` `">=24 <25"` en la raíz).
- **Librería:** React 19 (`manifest.yaml` de `ui`: `type: library`, `language: react`). **En este plan no hay componentes**, así que el paquete no declara `react` todavía: se agrega con el primer componente compartido.
- **Estilos:** Tailwind CSS v4 con configuración CSS-first (`@theme`) (ADR-002: "Tailwind CSS v4, con los tokens del prototipo en `@theme`"). `tailwindcss` lo procesan las apps consumidoras con `@tailwindcss/vite` (S-005); `@nerdose/ui` solo publica el CSS.
- **Helper de clases:** `clsx` + `tailwind-merge` (convención `styling`, sección Package).
  - **NO DOCUMENTADO — versiones de `clsx` y `tailwind-merge`:** ningún documento las fija. Usar la estable vigente al implementar y dejarlas fijadas por `pnpm-lock.yaml`. Restricción: la major de `tailwind-merge` MUST ser compatible con Tailwind CSS v4 (la serie 3.x lo es; la 2.x apunta a Tailwind v3). Verificar en el changelog del paquete al instalar.
- **Pkg manager / tareas:** pnpm (único permitido, ADR-003) y Turborepo.
- **Tests:** Vitest (proyecto propio del paquete `ui`, descubierto por el `vitest.config.ts` raíz con el glob `packages/*/vitest.config.ts`).
- **Lint:** ESLint flat config de la raíz (`eslint.config.js`) + typescript-eslint; a `packages/ui/**/*.{ts,tsx}` ya se le aplican los presets recomendados de `eslint-plugin-jsx-a11y` y `eslint-plugin-react-hooks` (`REACT_FILES`).

Versiones ya instaladas en la raíz (`package.json` raíz, devDependencies): `typescript ^6.0.3`, `eslint ^9.39.5`, `typescript-eslint ^8.72.1`, `eslint-plugin-jsx-a11y ^6.10.2`, `eslint-plugin-react-hooks ^7.1.1`, `vitest ^5.1.0`, `@types/node ^24.19.2`, `turbo ^2.11.10`. **No** se redeclaran en `packages/ui` (contrato del plan de `workspace`, abajo). `packageManager` raíz: `pnpm@11.6.0`.

> **Precondición del entorno:** en la máquina actual `node --version` da `v22.14.0`. La story requiere Node 24; el plan de `workspace` verificó la raíz con Node 24.22.2. Usar Node 24 para validar CA-1.

### Arquitectura del Servicio

Del `overview.md` y `manifest.yaml` de `ui`:

- **Propósito:** paquete `@nerdose/ui` (`packages/ui`): lo visual compartido entre `web` y `admin`. Contiene los tokens (`tokens.css` con el bloque `@theme` de Tailwind v4: fondo `#0A0C0F`, acento `#3DDC84`, `--font-mono`, acentos por juego), los componentes compartidos (header, banners, share, stat cards), el helper `cn()` y `track()` (analítica opcional de ADR-014).
- **Tipo:** library en React 19 (TypeScript estricto), sin build propio: exporta su fuente. Vive en `packages/ui`. **No importa `@nerdose/db` ni `@nerdose/core/notify`.**
- **Módulos del dominio** (en negrita los de este plan):
  - **tokens**: `tokens.css` con `@theme`; fuente única de los tokens visuales.
  - components: componentes compartidos de `web` y `admin` (fuera de alcance).
  - **utils**: `cn()` (en este plan) y `track()` (fuera de alcance).
- **Convenciones activas** (todas custom, copias de las de `web`): `_base`, `styling`, `accessibility`, `testing-unit`. Aplican a este plan: `_base`, `styling` y `testing-unit` (sin componentes no hay nada que chequear con axe).
- **Design System:** cuando `docs/design-system/` defina los tokens, mandan sobre los de `styling` y `tokens.css` debe actualizarse para coincidir.

**Paquetes internos sin build (JIT) — decisión 1 del REQ-001:** `core`, `db` y `ui` exportan su TypeScript fuente por `exports` (`"."` → `./src/index.ts`). Vite y `tsx` lo consumen directamente, y `typecheck` es `tsc --noEmit` en cada paquete. El build para producción queda diferido con el hosting.

**Estructura objetivo del paquete:**

```
packages/ui/
├── package.json              # @nerdose/ui; exports "." -> ./src/index.ts, "./tokens.css" -> ./src/tokens.css
├── tsconfig.json             # extends ../../tsconfig.base.json
├── vitest.config.ts          # proyecto "ui"
├── src/
│   ├── index.ts              # entrada ".": re-exporta cn
│   ├── cn.ts                 # cn()  (ruta fijada por la convención styling)
│   └── tokens.css            # bloque @theme  (ruta fijada por la convención styling)
└── test/
    ├── package-manifest.test.ts
    ├── tokens.test.ts
    ├── cn.test.ts
    └── public-api.test.ts
```

Decisiones de estructura (no fijadas por la documentación, se dejan indicadas):

| Decisión | Por qué |
|---|---|
| Archivos planos en `src/` (`cn.ts`, `tokens.css`) | La convención `styling` fija literalmente `packages/ui/src/tokens.css` y `packages/ui/src/cn.ts`. La estructura `modules/`/`lib/` de `_base` es para las apps, no para este paquete. |
| `tokens.css` expuesto por `exports` como `./tokens.css` | La convención `styling` lo importa como `@import '@nerdose/ui/tokens.css';` desde `src/index.css` de las apps. Sin esa entrada en `exports`, la resolución del paquete lo bloquearía. |
| Tests en `test/` y no co-locados en `src/` | El contrato del plan de `workspace` fija `tsconfig.json` con `include: ["src", "test"]`, y `@nerdose/core` ya usa `test/`. Además `tokens.test.ts` necesita `node:fs` y así `src/` queda solo con código que se envía al navegador. `testing-unit` pide co-locación para componentes de las apps; cuando `ui` tenga componentes se puede revisar. |
| Entorno de Vitest `node` (no `jsdom`) | No hay componentes ni DOM en este plan: `cn()` es una función pura y el test de tokens lee un archivo. `jsdom`, Testing Library y `vitest-axe` se agregan con el primer componente. |
| Imports relativos dentro de `ui` (no alias `@/`) | Igual que en `core`: el paquete se consume JIT, y un `@/…` dentro de `packages/ui/src` lo resolvería el alias del consumidor (`apps/web`), no el del paquete. |
| Sin dependencia de `tailwindcss` en `ui` | `tokens.css` es CSS plano con una at-rule `@theme`; lo procesa el Tailwind de cada app. CA-4 se verifica inspeccionando el bloque, como pide la story. Que las clases `bg-bg`, `font-mono` y `text-accent` se generen lo verifica el test de `web` en S-005. |

### Convención `styling` (copiada, partes aplicables)

Styling uses **Tailwind CSS v4** with CSS-first configuration: the visual tokens live in an `@theme` block in `packages/ui`, shared by `web` and `admin`. The look is dark, terminal-like, JetBrains Mono, with `#3DDC84` as the brand accent and one accent per game (NFR-U07).

**Package:**

```
tailwindcss                  # v4
@tailwindcss/vite            # Vite plugin
@fontsource/jetbrains-mono   # self-hosted font (400, 500, 700)
clsx                         # conditional classes
tailwind-merge               # conflict-free class merging
```

(En `@nerdose/ui` solo se instalan `clsx` y `tailwind-merge`; los otros tres son de las apps.)

**Setup en las apps (referencia, se implementa en S-005):**

```css
/* src/index.css */
@import 'tailwindcss';
@import '@nerdose/ui/tokens.css';   /* the @theme block */
@import '@fontsource/jetbrains-mono/400.css';
@import '@fontsource/jetbrains-mono/500.css';
@import '@fontsource/jetbrains-mono/700.css';
```

**Design tokens (verbatim):**

> **Source of truth.** The formal Design System does not exist yet; it will be generated later by `/product-ux-generate` into `docs/design-system/`. **When it exists, its tokens take precedence over the values below**, and `@nerdose/ui/tokens.css` must be updated to match it. Until then, the values below are extracted from the prototype `docs/nerdose.html`, which uses them inline (it declares no CSS variables), so the role names are an interpretation.

```css
/* packages/ui/src/tokens.css */
@theme {
  --font-mono: 'JetBrains Mono', ui-monospace, monospace;

  --color-bg: #0A0C0F;            /* page background */
  --color-surface: #0F1318;       /* cards */
  --color-surface-2: #11151A;     /* raised / inputs */
  --color-surface-3: #141920;
  --color-border: #222A33;
  --color-border-strong: #2A323C;
  --color-border-subtle: #1E252E;

  --color-text: #E6EDF3;          /* primary text */
  --color-text-muted: #9AA6B2;    /* secondary text */
  --color-text-dim: #8D99A6;      /* tertiary text, labels */

  --color-accent: #3DDC84;        /* brand accent, also Devdle */
  --color-on-accent: #06120B;     /* text on accent backgrounds */

  --color-game-devdle: #3DDC84;
  --color-game-bug-hunt: #FFB547;
  --color-game-big-o: #5EB1FF;
  --color-game-timeline: #C39BFF;
  --color-game-grep-grid: #F472B6;
}
```

- Tailwind then exposes them as `bg-bg`, `bg-surface`, `text-text`, `text-text-muted`, `border-border`, `text-accent`, `text-game-bug-hunt`, etc.
- The streak/warning amber is the Bug Hunt accent `#FFB547` in the prototype; it is referenced through the token, not repeated.
- Per-game accent is applied by the game's own `client` via its token, never with a literal hex.

**The `cn()` helper (verbatim):**

```ts
// packages/ui/src/cn.ts
import { clsx, type ClassValue } from 'clsx';
import { twMerge } from 'tailwind-merge';
export const cn = (...inputs: ClassValue[]) => twMerge(clsx(inputs));
```

> Nota: con `verbatimModuleSyntax: true` (en `tsconfig.base.json`), el import inline `type ClassValue` es válido y se borra al compilar. No cambiar a `import { ClassValue }` sin `type`.

**Dark theme only:** The product is dark. There is no light theme and no theme switcher in v1. Tokens are defined once on `:root`; do not add `dark:` variants.

**Rules (aplicables a este plan, verbatim):**
- Use only the tokens above (or later, the Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them.
- Font is JetBrains Mono via `@fontsource/jetbrains-mono`, self-hosted. No Google Fonts or other external font requests.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- No CSS-in-JS and no component CSS files, except the token file and third-party overrides.

### Convenciones de Código (`_base` de `ui`, aplicables)

- TypeScript obligatorio; `tsconfig.json` extiende la base del monorepo (`strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`, `module: ESNext`, `moduleResolution: bundler`, `verbatimModuleSyntax: true`, `skipLibCheck: true`, `noEmit: true`). `jsx: react-jsx` se agrega con el primer `.tsx`.
- Sin `any` salvo en bordes con librerías sin tipos.
- Nombres: archivos `kebab-case` (`cn.ts`, `tokens.css`); funciones `camelCase` (`cn`); tipos `PascalCase` sin `I`; constantes `SCREAMING_SNAKE_CASE`.
- Orden de imports: (1) externos y `@nerdose/*`, (2) `@/`, (3) relativos; grupos separados por una línea en blanco. Imports solo de tipos con `import type`.
- Límites del monorepo: nunca importar `@nerdose/db`, `@nerdose/polyglot` ni `@nerdose/content`; nunca importar de una app. Lo compartido por `web` y `admin` vive en `@nerdose/ui`.
- Comentarios: por defecto ninguno; solo el porqué cuando no es obvio. Sin `// TODO` sin issue.

### Convención `testing-unit` (aplicable)

- Runner Vitest. Tests de comportamiento: el nombre del test describe el comportamiento ("merges … when …"), no la implementación.
- Sin snapshots de árboles grandes; sin reloj real; sin red.
- `jsdom`, Testing Library, `userEvent` y `vitest-axe` aplican a componentes: no hay en este plan.

### ADRs Relevantes

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo con pnpm workspaces y Turborepo; `packages/ui/` contiene "componentes compartidos (header, banners, share, stat cards), tokens, track()".
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los tests MUST usar Vitest; los e2e, Playwright.

### Decisiones de diseño del REQ-001 que aplican (copiadas)

- **Servicios afectados (fila `ui`):** Impacto Bajo; referencia: convention `styling` (web/admin); cambios: `tokens.css` con el bloque `@theme` y el helper `cn()`.
- **Pruebas mínimas (fila `@nerdose/ui`):** `tokens.css` declara `--color-bg: #0A0C0F`, `--color-accent: #3DDC84` y `--font-mono`; `cn()` resuelve conflictos de clases (REQ AC 7).
- **Dependencias:** `web` y `admin` dependen de `@nerdose/ui` (y `@nerdose/core` para tipos, opcional en este grupo).
