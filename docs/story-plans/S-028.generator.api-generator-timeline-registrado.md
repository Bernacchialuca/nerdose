### Decisiones de planificación

1. **Mapa `BANKS` cerrado (decisión 11 de REQ-006).** `LAST_USED_COLUMNS` se reemplaza por un mapa por banco con su tabla, sus campos de `bankItems` y sus columnas `last_used*` permitidas:
   - `terms`: campos `{ id, term, category, definition, summary }`; `lastUsed: { last_used_devdle → terms.lastUsedDevdle, last_used_grep → terms.lastUsedGrep }`.
   - `timeline_facts`: campos `{ id, label, category, event_date, date_precision, note }`; `lastUsed: { last_used → timelineFacts.lastUsed }`.
   Una combinación `(bank, lastUsedField)` fuera del mapa lanza `Error('Unknown last_used field: …')` (mismo mensaje que hoy), tanto en `bankItems` como en `approve`. Si el tipado de Drizzle sobre una unión de tablas complica `.select()`/`.update()`, es válido resolverlo con una función por banco detrás del mapa (lo que importa es que el mapa sea la única fuente de las columnas permitidas y que no haya `if (gameId === …)`).

2. **`ApproveOptions = { bank: BankName | null; lastUsedField: string; itemIds: string[]; date: string }`.** `generateForDate` pasa `bank: spec.bank`. Con `bank: null` o `itemIds: []` solo se aprueba el challenge (preparado para Big O / Bug Hunt, que no usan banco). `BankName` ya existe en `@nerdose/core` (`'terms' | 'timeline_facts'`).

3. **Forma de `bankItems` para `timeline_facts` = `TimelineFact` del paquete.** `{ id, label, category, event_date, date_precision, note, last_used }` con `event_date`/`last_used` como `'YYYY-MM-DD'` (columnas `date` en `mode: 'string'`) y `note` el `jsonb` `{ es, en }` tal cual. Solo filas `status = 'approved'`. `verify` (`facts_in_bank`) compara `label`, `event_date` y `date_precision` con el payload, así que los nombres deben ser exactamente esos (snake_case).

4. **Determinismo con ids de base.** El generador de Timeline ordena por `id` (`sortById`) antes de mezclar con el `rng`; los `id` de `timeline_facts` son UUID aleatorios por `INSERT`. En producción los ids son estables, así que el mismo estado de base da el mismo payload. En tests, los fixtures de hechos usan **ids fijos** (`FACT_ID(nn) = '10000000-0000-4000-8000-0000000000nn'`) para que el test de determinismo compare el payload completo entre dos `t.reset()`.

5. **Registrar Timeline afecta tests que usan el `generatorRegistry` real** (lo mismo que pasó con Grep Grid en S-023):
   - `test/domain/generate-today.test.ts` inserta solo `BANK16`: sin hechos, `generate` de Timeline lanza `RangeError('timeline generate: no category has 5 facts')`, `fillDates` lo atrapa y devuelve `failed: true`. Se agrega `insertFacts(CHRONO5)` al `beforeEach` y las aserciones pasan a 3 juegos.
   - `test/process.test.ts` (dataset real): pasa a esperar 14 fechas para `devdle`, `grep-grid` y `timeline` (`rows.length = 42`).
   - `test/games/registry.test.ts`: `ids()` con los 3 juegos; el caso `not_found` pasa de `'timeline'` a `'big-o'` (id válido, no registrado).
   - `test/scheduler/fill-grep-grid.test.ts` "convive con Devdle…" usa el registry real con el dataset real: con Timeline registrado también genera Timeline; sus aserciones siguen valiendo (Timeline no toca `terms`). No se modifica; la convivencia de los 3 juegos se prueba explícitamente en un archivo nuevo (Task 4).
   - `fill.job.test.ts` y `startup.test.ts` ya usan `devdleOnlyRegistry`: no cambian.

6. **Bancos de test para Timeline.**
   - Un día: `CHRONO5` = 5 hechos `programming_languages` distinguibles, orden correcto `[Python, Java, Go, Docker, Kubernetes]` (el de CA-3): Python `1991-02-20`/day, Java `1995-05-23`/day, Go `2009-11-10`/day, Docker `2013-03-20`/day, Kubernetes `2014-06-07`/day. Con exactamente 5 hechos en una categoría, el conjunto elegido es siempre el mismo.
   - Ambigüedad (CA 26 del REQ): `AMBIGUOUS5` = Python, Java, Go `2009-01-01`/year, Node.js `2009-05-01`/month, Docker → `verify` falla en `distinguishable`.
   - 14 días: dataset real vía `syncBanks({ db: t.svc.db, log })`, igual que `fill-grep-grid.test.ts`.

7. **Seed y secreto (CA-10, parte generator).** El seed ya es `HMAC-SHA256(GENERATOR_SECRET, "timeline:{date}:{attempt}")` por `seedFor`; no hay código nuevo. Se cubre con tests: la fila guarda el seed HMAC esperado y otro secreto da otro `seed` y otro `correct_order` (los `opaque_id` salen del `rng`).

## Contexto Arquitectónico

### Stack Tecnológico

- **Runtime:** Node.js 24 LTS, TypeScript (`strict`, `noUncheckedIndexedAccess`), ESM (`"type": "module"`).
- **Worker:** sin servidor HTTP; croner (UTC), pure-rand (xoroshiro128+) vía `rngFrom` de `@nerdose/core`, `node:crypto` (HMAC).
- **DB:** PostgreSQL 16 vía Drizzle ORM 0.45 + postgres.js; schema y migraciones en `@nerdose/db`; el `generator` conecta como `nerdose_generator`.
- **Validación:** Zod 4 (`payloadSchema` de cada juego valida cada candidato y cada `recentChallenges`).
- **Logs:** Pino (JSON, `service`/`env`, redacción de secretos).
- **Tests:** Vitest + Testcontainers (`postgres:16-alpine` compartido en `globalSetup`, `fileParallelism: false`).
- **Monorepo:** pnpm workspaces + turbo. Dependencias internas con `workspace:*`.

### Arquitectura del Servicio

**Propósito (overview):** worker siempre activo que mantiene aprobados y verificados los desafíos de los próximos 14 días de cada juego (job `fill`, cada hora en UTC), carga los bancos (`terms`, `timeline_facts`) desde `@nerdose/content` al arrancar (`sync_banks`) y es el único proceso que inserta en `challenges`, `terms` y `timeline_facts`. Usa `./generator` (y `./definition` si hace falta) de cada `@nerdose/game-*`. Módulos: `challenge-publishing` (fill, pipeline, seed) y `content-banks` (sync_banks).

**Pipeline actual (`generateForDate`, `src/domain/challenge-publishing/generate.ts`):**
1. `spec = generator.historySpec`; `number = challengeNumber(date, LAUNCH_DATE)` (error si `null`).
2. `history = { bankItems: repo.bankItems(spec), recentChallenges: repo.recentChallenges(gameId, date − spec.recentDays, date − 1, payloadSchema) }` (una vez por fecha).
3. Por `attempt` 0…`GENERATION_MAX_ATTEMPTS − 1`: si `signal.aborted` → `aborted`; `seed = seedFor(GENERATOR_SECRET, gameId, date, attempt)`; `payload = payloadSchema.parse(generator.generate({ date, seed, history }))`; `insertDraft({ gameId, date, number, payload, seed: seedToHex(seed), attempt, generatorVersion: version })`; log `ChallengeGenerated`.
4. `verification = generator.verify(payload, history)`. `ok` → `repo.approve(id, verification, { lastUsedField: spec.lastUsedField, itemIds: generator.usedBankItems(payload), date })` → `approved` (log `ChallengeApproved`) o `duplicate` → `covered` (log `ChallengeRejected` con `reason: 'duplicate_active'`). `!ok` → `repo.reject(id, verification)`, log `ChallengeRejected { reason }`.
5. Agotados: `log.warn({ game_id, date, attempts }, 'ChallengeGenerationFailed')`, `outcome: 'missing'`.

**Único cambio en el pipeline:** el objeto de `approve` suma `bank: spec.bank`.

**Repositorio actual (`challenge-publishing.repository.ts`)**, lo que cambia:
```ts
const LAST_USED_COLUMNS = {
  last_used_devdle: { key: 'lastUsedDevdle', column: terms.lastUsedDevdle },
  last_used_grep: { key: 'lastUsedGrep', column: terms.lastUsedGrep },
} as const;
// bankItems(spec): bank null -> []; bank 'timeline_facts' -> throw Error('timeline_facts bank not available');
//   terms -> select { id, term, category, definition, summary, lastUsed: column } where status = 'approved'
//   y devuelve { ...item, [spec.lastUsedField]: lastUsed }
export type ApproveOptions = { lastUsedField: string; itemIds: string[]; date: string };
// approve(id, log, options): transacción { UPDATE challenges SET status='approved', verification WHERE id AND status='draft';
//   si itemIds: UPDATE terms SET [key] = GREATEST(column, date::date) WHERE id IN itemIds }
//   catch 23505 en uq_challenges_active_game_date -> reject(id, { ok:false, checks, reason:'duplicate_active' }) -> 'duplicate'
```

**`fillDates` (`fill.service.ts`) — no se modifica:** para cada `gameId` de `registry.ids()` (orden de registro: `devdle`, `grep-grid`, `timeline`), `coveredDates(gameId, first, last)` y `generateForDate` por cada fecha no cubierta, ascendente. Un error en un hueco se loguea (`'Gap generation failed'`, `game_id`, `date`) y marca `failed: true` sin frenar los demás. `summary = { generated, approved, rejected, missing }`.

**`fillRange(now, launchDate)`:** `[max(today+1, LAUNCH_DATE), today+14]`. `runGenerateToday` genera solo `[today]`, se niega en `production` y antes de `LAUNCH_DATE`.

**Manejo de errores:** errores inesperados propagan; `runJob` los registra como `failed` en `job_runs` sin rechazar. `AppError('not_found')` para un juego no registrado en `registry.get`.

**Logging:** Pino; eventos `ChallengeGenerated`, `ChallengeApproved`, `ChallengeRejected`, `ChallengeGenerationFailed`, con `game_id`, `date`, `attempt`. `GENERATOR_SECRET` nunca se loguea.

### ADRs Relevantes

**ADR-006: Contrato `GameDefinition`**
- **Decisión:** cada juego es un paquete `packages/games/<game_id>` con entradas `./definition`, `./generator`, `./client`; hay un registry en `api`, `web`/`admin` y `generator` que mapea `game_id` → entrada.
- **Contrato del generador (`@nerdose/core`, `game-generator.ts`):**
  ```ts
  export type BankName = 'terms' | 'timeline_facts';
  export interface HistorySpec { bank: BankName | null; lastUsedField: string; recentDays: number }
  export interface GameGenerator<Payload, BankItem> {
    historySpec: HistorySpec;
    usedBankItems(p: Payload): string[];
    generate(input: { date: string; seed: Uint8Array; history: GeneratorHistory<Payload, BankItem> }): Payload;
    verify(p: Payload, history: GeneratorHistory<Payload, BankItem>): VerificationLog;
  }
  ```
- **Reglas de Implementación (verbatim):**
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
  - La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`). Con `state`, `toPublic` MAY revelar únicamente lo que el jugador ya descubrió en esa Play (Grep Grid: `words[].definition` de los `term_id` presentes en `found_words`); MUST NOT revelar nada de lo no descubierto (REQ-005).
  - `Feedback` MUST ir en el locale del jugador (`ctx.locale`), nunca como `{ es, en }` (ADR-015).
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` (sin estado y con estados intermedios, si el juego usa `state`) y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

**ADR-007: Generator worker y pipeline**
- **Decisión:** worker long-running con croner; `fill` (`10 * * * *` UTC, lock `fill`) para cada juego y cada fecha en `[today+1 … today+14]` sin challenge `approved`/`published`/`voided`; seed `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")` → pure-rand; pipeline draft → `verify()` → `approved` + `last_used_*` o `rejected`.
- **Reglas de Implementación (verbatim):**
  - `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
  - `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
  - Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
  - Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
  - Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
  - El seed MUST ser `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`, con `date` en formato `YYYY-MM-DD`. `GENERATOR_SECRET` MUST existir solo en el entorno del `generator`.
  - `GENERATION_MAX_ATTEMPTS` MUST valer 20 por defecto y ser configurable por variable de entorno.
  - `fill` MUST generar solo para fechas en `[today+1, today+14]`. MUST NOT generar para `today` ni para fechas pasadas.
  - `challenges.number` MUST calcularse con `core` (`date − LAUNCH_DATE + 1`) al insertar.
  - Un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`.
  - El runner MUST usar `execFile` (nunca `exec` con shell), timeout de 10 000 ms, y MUST correr como usuario no root.
  - Los toolchains MUST ser Node 24, Go ≥ 1.25 y JDK 21.
  - El `generator` MUST NOT hacer requests HTTP a servicios externos. Su única salida de red es SMTP (ADR-013).
  - El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.

**ADR-016: Bancos como dataset versionado** (reglas aplicables)
- `api` y `generator` MUST NOT hacer requests a dominios de Wikimedia (`*.wikidata.org`, `*.wikipedia.org`, `*.wiktionary.org`).
- `sync_banks` MUST NOT tocar `last_used_devdle`, `last_used_grep` ni `last_used` (los escribe solo `approve`).
- Mínimo 100 hechos `approved` por categoría v1; ventana de 90 días para Timeline.

**ADR-004: PostgreSQL única base con roles** — el `generator` usa `nerdose_generator` (`GRANT SELECT, INSERT, UPDATE ON timeline_facts`); los fixtures se insertan con el owner y el código bajo test usa el rol del servicio, para que un `GRANT` faltante aparezca en los tests.

**Lint (`eslint.config.js`, raíz):** en `apps/generator/**` está prohibido `@nerdose/game-*/client` y cualquier import de otra app; `./generator` y `./definition` están permitidos.

### Contexto de API

El `generator` no expone red ni cambia contratos HTTP. El contrato que produce y consume la `api` es el `payload` de `challenges`:

**`TimelinePayload` (`payloadSchema` de `@nerdose/game-timeline/definition`):**
```ts
{
  date: 'YYYY-MM-DD',
  category: TimelineCategory,                 // programming_languages | frameworks | companies | operating_systems | video_games ...
  prompt: { es: string, en: string },
  items: [{                                   // × 5, en el orden inicial mezclado (≠ correct_order)
    fact_id: uuid,                            // timeline_facts.id
    opaque_id: string,                        // ^[a-z0-9]{6}$
    label: string,
    event_date: 'YYYY-MM-DD',
    date_precision: 'year' | 'month' | 'day',
    note: { es: string, en: string },
  }],
  correct_order: string[5],                   // opaque_id en orden cronológico
}
```

**`VerificationLog`:** `{ ok: true, checks } | { ok: false, checks, reason }`; `checks = [{ name, ok, detail? }]`. Para timeline los 9 `name`, en orden: `items_count`, `facts_in_bank`, `same_category`, `texts_bilingual`, `distinguishable`, `correct_order_consistent`, `opaque_ids`, `shuffled`, `not_used_90`.

### Contexto de Flujos

**generacion-diaria (`docs/flows/generacion-diaria.md`) — se implementa para timeline.** Pasos relevantes (verbatim):

- **Paso 5 — Cierre del job:** `job_runs` — UPDATE `status = 'success' | 'failed'`, `finished_at`, `summary = { generated, approved, rejected, missing }`.

**Escenario de la story (generación y publicación):**
1. **[generator - fill]** Para cada fecha `D ∈ [max(today+1, LAUNCH_DATE), today+14]` sin desafío vigente: `history = { bankItems: timeline_facts approved con last_used, recentChallenges: timeline en [D−90, D−1] }`.
2. **[generator]** Por `attempt` (0–19): seed HMAC con `GENERATOR_SECRET` → `generate` → `payloadSchema.parse` → insert `draft` → `verify`.
3. **[generator]** `ok` → `approved` + `UPDATE timeline_facts SET last_used = GREATEST(last_used, D)` (una transacción); choque con `uq_challenges_active_game_date` → `rejected` (`duplicate_active`); `!ok` → `rejected` y siguiente intento. Agotados los 20, la fecha queda neutra.
4. **[api - publishing]** (ya implementado, sin cambios) primer request tras las 00:00 UTC → `approved` pasa a `published`.

**cambio-de-dia-y-publicacion:** sin cambios; la `api` publica también los de timeline.

import { challenges, terms, timelineFacts } from '@nerdose/db';

const BANKS = {
  terms: {
    table: terms,
    fields: { id: terms.id, term: terms.term, category: terms.category, definition: terms.definition, summary: terms.summary },
    status: terms.status,
    lastUsed: {
      last_used_devdle: { key: 'lastUsedDevdle', column: terms.lastUsedDevdle },
      last_used_grep: { key: 'lastUsedGrep', column: terms.lastUsedGrep },
    },
  },
  timeline_facts: {
    table: timelineFacts,
    fields: {
      id: timelineFacts.id, label: timelineFacts.label, category: timelineFacts.category,
      event_date: timelineFacts.eventDate, date_precision: timelineFacts.datePrecision, note: timelineFacts.note,
    },
    status: timelineFacts.status,
    lastUsed: { last_used: { key: 'lastUsed', column: timelineFacts.lastUsed } },
  },
} as const;

function lastUsedColumn(bank: BankName, field: string) {
  const entry = (BANKS[bank].lastUsed as Record<string, { key: string; column: AnyColumn }>)[field];
  if (!entry) throw new Error(`Unknown last_used field: ${bank}.${field}`);
  return entry;
}

export type ApproveOptions = { bank: BankName | null; lastUsedField: string; itemIds: string[]; date: string };
