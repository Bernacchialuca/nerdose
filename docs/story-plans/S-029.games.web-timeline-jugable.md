### Arquitectura del servicio (`docs/architectures/games/overview.md`, copiado lo aplicable)

Los cinco paquetes de juego `packages/games/<game_id>` implementan `GameDefinition` de `@nerdose/core` y exponen tres entradas: `./definition` (la usa la `api`), `./client` (React: `Instructions`, `Game`, `Result` y `share()`; la usan `web` y `admin`) y `./generator`. `client` sigue `styling`, `accessibility`, `testing-unit` y `game-clients` (copias de `web`). `game-clients` y `game-registry` describen el lado de la app que consume cada entrada; aquí aplican como contrato que el paquete debe cumplir.

### Convenciones activas (extractos aplicables, verbatim)

#### `game-package`

| Entry | May import | Must not import |
|---|---|---|
| `./client` | `@nerdose/core` (`.`), `zod`, `react`, `@nerdose/ui`, `shared/`, types from `./definition` | `@nerdose/polyglot`, `node:*`, `./generator`, runtime code of `./definition` that carries solutions |

- Game-specific dependencies stay inside the game package (… dnd-kit for `timeline` …).
- `moveSchema` is the single schema used by `web` (before sending) and by `api` (validation); a parse failure is `422 invalid_move`.
- `share(result, number)` never includes the solution and ends with `nerdose.dev`.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk.

> Precedente (Devdle y Grep Grid): el client importa **los schemas** de `../definition/schemas` (Zod, sin solución) para parsear `publicView`, `state` y `result`, y valida la jugada con `moveSchema`. Nunca importa `../definition/index` (el objeto `timeline` con `result()`).

#### `game-clients` (contrato que el paquete cumple)

- `GameClient` is the shape of the `./client` entry: React components `Instructions`, `Game`, `Result` and `share(result, number): string`. The exact props are owned by the game packages; the app passes them through and does not reinterpret them.
- Moves go through the game's `moveSchema` (Zod) before `POST .../move`.
- `share(result, number)` produces the text. The shell calls `navigator.share({ text })` … `track('share:<game_id>')`.
- Shiki (big-o, bug-hunt) and dnd-kit (timeline) are dependencies of the game packages and are loaded in the game's own chunk. The shell never imports them.
- `admin` mounts the same `Game`/`Result` components in **solution mode** … (FG-7, fuera de alcance).
- The `client` never receives the solution before the round ends in `web`.
- Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`.
- Update (REQ-005): `GameProps.feedback: unknown | null` … Clients that do not need it ignore it (Devdle). **Timeline lo ignora** (`feedbackSchema = z.null()`).

#### `styling`

- Use only the tokens (or later, the Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- Focus is always visible: use `focus-visible:` rings with `--color-accent`; never `outline-none` without a replacement.
- State is never conveyed by color alone.
- Respect `prefers-reduced-motion`.
- Values from data or timers: set a CSS variable with `style` (aplica al `transform` de dnd-kit durante el arrastre).
- Touch targets are at least 44 x 44 px.
- REQ-003: no global media queries. Layout uses `flex-wrap` …; only the 320 px adaptations documented in the Design System are allowed. Component `.tsx` files must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).
- Precedente S-024: el escalado a 320 px usa `@container` (container queries de Tailwind v4), no media queries.

#### `accessibility`

- Timeline's drag and drop uses dnd-kit with **both** `TouchSensor` and `KeyboardSensor`, and announces moves through live regions.
- Feedback that uses color (… Timeline correct/wrong, win/loss) is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
- Result, errors and notices appear in `role="status"` (polite) or `role="alert"`.
- No interactive element is built from a `<div>` or `<span>` with a click handler; use a native control.
- Every image or icon is either decorative (`aria-hidden`) or has an accessible name.
- Each of the 5 games can be completed with the keyboard alone (NFR-U03).
- Dynamic updates are announced via live regions; do not move focus unexpectedly.
- axe-core reports zero violations in unit checks.

#### `testing-unit`

- Query by role, label or visible text. `data-testid` only when no accessible query exists.
- Use `userEvent`, not `fireEvent`, for interactions.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- Fixtures use the API's `snake_case` names.
- No snapshot tests of large DOM trees. Tests do not rely on the real date or timers.
- Test names state the behavior.

#### `_base` (Node) — extracto

Archivos y carpetas `kebab-case`; funciones y variables `camelCase`; constantes globales `SCREAMING_SNAKE_CASE`; tipos `PascalCase` sin prefijo `I`; sin `any` salvo en fronteras con librerías sin tipos (comentado).

#### `error-handling` — extracto

El client no lanza `AppError`: un `publicView`/`state`/`result` que no cumple el schema hace fallar el `parse` (Zod) y el host lo trata como error de carga (mismo comportamiento que Devdle y Grep Grid). Los rechazos del servidor llegan como `moveError: { code, message }` (códigos del catálogo cerrado de `@nerdose/core`: `invalid_move` 422, `rate_limited` 429, `validation_error` 422).

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables (reglas aplicables, verbatim)

- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.

- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`.
- `web` y `admin` MUST ser SPAs con React 19 + Vite.
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.
- Decisión: «dnd-kit (`TouchSensor` + `KeyboardSensor`) para Tech Timeline».

#### ADR-003: Monorepo (reglas aplicables, verbatim)

- Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
- `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.

#### ADR-015: Contratos JSON y errores (reglas aplicables, verbatim)

- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` … MUST NOT haber transformaciones a `camelCase` …
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las fechas de día MUST serializarse como `YYYY-MM-DD`.

#### ADR-014: Métricas y analítica (regla aplicable, verbatim)

- `web` MUST llamar solo a `track(event)` de `@nerdose/ui`. MUST NOT referenciar `window.plausible` fuera de ese helper. → el client **no** llama a `track` (lo hace el `ShareButton` de `web`).

### Decisiones de diseño de REQ-006 aplicables (verbatim)

**12. Client: reordenar con dnd-kit (RF 3; CA 10, 11, 36; NFR-U03).** Dependencias nuevas del paquete `timeline` (solo la entrada `./client`, chunk propio de `/timeline`): `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities` (ADR-002). `Game` renderiza la lista como `<ol>` con `SortableContext` vertical:

- **Botones ↑ ↓ por fila** (deshabilitados en los extremos), mismo `reorder()` puro (`arrayMove`) y mismo anuncio por `aria-live="polite"`; el foco sigue al hito.
- Cada fila anuncia su posición ("3 de 5"). `prefers-reduced-motion`: sin transiciones ni animación de soltado.
- El orden en construcción es estado local (`useState` de `opaque_id[]`, inicializado con `public_view.items`), nunca en storage. Al cambiar el idioma, `useGameToday` conserva el `Game` montado (`keepPreviousData`), llegan la nueva `prompt` y la categoría traducida, y el orden local se mantiene porque los `opaque_id` son los mismos (CA 36). Si cambian los `opaque_id` (otro desafío), el orden se reinicia. Al volver a entrar, el orden parte de la mezcla inicial (CA 12).
- "Confirmar" siempre habilitado (salvo `movePending` o `locked`): `moveSchema.parse({ order })` → `onMove`. Un `moveError` `invalid_move` muestra el aviso y deja reordenar y confirmar otra vez.
- A 320 px: lista vertical a ancho completo, fila de `size.row.timeline` (52 px) con asa, label y botones; sin scroll horizontal.

**13. Client: resultado, fechas y share (RF 8, 9; CA 3, 9).** `Result` muestra el veredicto `N/5` (victoria solo con 5/5), "tu orden" con acierto/error por posición (✓ bien / ✗ va en N°, con ícono y borde punteado ámbar para el error, nunca rojo, según `color.md` y `borders.md`), y "orden correcto" como `timeline.rail` con fecha y nota en el idioma activo, el `aside` de rachas y el `footer` del host. Fechas con `Intl.DateTimeFormat(locale, { timeZone: 'UTC', … })` según precisión: `year` → solo el año; `month` → mes y año; `day` → fecha completa (`shared/format-date.ts`; nunca inventa mes ni día). `share(result, number)` = `⏳ Tech Timeline #${number}` / `${squares} ${score}/5` / `nerdose.dev`, con 🟩/🟥 por posición en el orden enviado (CA 3: `🟩🟥🟥🟩🟩 3/5`); sin labels, fechas ni orden. `Instructions`: 5 hitos, del más antiguo al más reciente, un solo intento, tres formas de mover. **Schemas Zod existentes (`src/definition/schemas.ts`, verbatim lo que consume el client):**

```ts
export const ITEMS_COUNT = 5;
const order = z.array(z.string()).length(ITEMS_COUNT);
export const moveSchema = z
  .strictObject({ order })
  .refine((m) => new Set(m.order).size === m.order.length, { path: ['order'], message: 'order must not repeat ids' });
export const stateSchema = z.strictObject({ order: order.optional() });
export const publicViewSchema = z.strictObject({
  category,                                   // z.enum(TIMELINE_CATEGORIES)
  prompt: z.string(),
  items: z.array(z.strictObject({ opaque_id: z.string(), label: z.string() })).length(ITEMS_COUNT),
});
export const feedbackSchema = z.null();
export const resultSchema = z.strictObject({
  win: z.boolean(),
  score: z.number().int().min(0).max(ITEMS_COUNT),
  category,
  correct_order: z.array(z.string()),
  submitted_order: z.array(z.string()),
  items: z.array(z.strictObject({ opaque_id: z.string(), label: z.string(), event_date: day, date_precision: precision, note: z.string() })).length(ITEMS_COUNT),
});
// Tipos: TimelinePublicView, TimelineState, TimelineMove, TimelineResult, TimelineFeedback
```

**Cómo el host (`apps/web`, ya implementado) entrega los errores al client** (`apps/web/src/modules/game-host/game-view.ts`, relevado):
- `moveError` (inline, memoizado por identidad del `ApiError`) solo para `['not_in_word_list', 'rate_limited', 'invalid_move', 'validation_error']`. El client compara por identidad para no repetir el hint.
- `no_session` → el host pinta el banner de cookies + «Reintentar» encima del `Game` (no llega como `moveError`).
- `challenge_voided` en una jugada → el host pasa `locked: true` y su banner `warning` en `notices`.
- `challenge_expired` / `game_finished` → el host recarga y cambia de pantalla (instrucciones o resultado): el `Game` se desmonta.
- Red / 500 → el host pinta un `Alert` con «Reintentar» encima del `Game`; el `Game` sigue montado con su orden local.

#### `jugada-y-cierre-de-partida` (rol del client)

1. **[web - client]** `reorder()` local en cada movimiento; anuncio "Go, posición 3 de 5" (CA 10). `moveSchema.parse({ order: ['a01x2b', 'k3f9x2', …] })` → `POST /api/games/timeline/today/move?lang=es { challenge_number, move: { order } }`.
2. **[api]** valida, cierra la Play (`won`/`lost`) y devuelve `result`.
3. **[web]** `result !== null` → `Result`: `3/5`, tu orden con ✓/✗ por posición, orden correcto con fechas y notas, rachas. "Compartir" → `⏳ Tech Timeline #N` / `🟩🟥🟥🟩🟩 3/5` / `nerdose.dev`.

### Decisiones de este plan (derivadas; `NOT DOCUMENTED - needs verification` donde se indica)

1. **Contrato de props idéntico a Grep Grid** (`types.ts` copiado). `GameProps.feedback` se acepta y se ignora; `gameStats` se acepta y no se muestra en la partida; `ResultProps.publicView` se acepta y no se usa (el `result` ya trae todo).
2. **El client parsea todo con los schemas de la definición** (`parsePublicView`, `parseState`, `parseResult` en `parse.ts`); un dato inválido lanza `ZodError` (el host lo trata como error de carga, como en los otros juegos). `stateSchema` se parsea aunque Timeline no use su contenido mientras juega.
3. **Orden local** = `useState<string[]>` de `opaque_id`, inicializado con `publicView.items.map(i => i.opaque_id)`. Se reinicia **solo** si cambia el **conjunto** de ids (`sameIdSet`, ordenado y comparado); un cambio de `prompt`/idioma con los mismos ids lo conserva (CA-4). Patrón «ajustar estado durante el render» (`prevIdsKey`), sin `useEffect`. Nunca storage (el boundaries test prohíbe `localStorage`/`sessionStorage` en `src/client`).
4. **`reorder(order, from, to)`** puro (= `arrayMove` de `@dnd-kit/sortable`) en `order.ts`; lo usan el arrastre, el teclado y los botones ↑ ↓ (`moveBy(order, id, -1 | +1)`, que devuelve el mismo array si está en el extremo).
5. **Sensores:** `PointerSensor` **restringido a mouse/pen** (subclase `MousePointerSensor` con `activators = [{ eventName: 'onPointerDown', handler: ({ nativeEvent }) => nativeEvent.isPrimary && nativeEvent.button === 0 && nativeEvent.pointerType !== 'touch' }]`, `activationConstraint: { distance: 4 }`), `TouchSensor` (`delay: 150`, `tolerance: 5`) y `KeyboardSensor` (`sortableKeyboardCoordinates`). Así un toque solo lo maneja `TouchSensor` y no compiten (REQ decisión 12 pide `TouchSensor` + `PointerSensor` para mouse). `NOT DOCUMENTED - needs verification`: valores de delay/tolerance/distance.
6. **El arrastre solo arranca desde el asa:** `setActivatorNodeRef` + `listeners` + `attributes` van en el `<button>` del asa; el `<li>` lleva `setNodeRef` y el `style.transform`. Solo el asa tiene `touch-none` (`touch-action: none`).
7. **Sin animación (DS `motion`):** `useSortable({ transition: null })` (sin transición de reacomodo **siempre**, no solo con reduced motion; el DS no tiene transiciones) y sin `DragOverlay` (no hay animación de soltado). El `transform` del arrastre se aplica por `style` (valor de runtime; lo permite `styling`).
8. **Anuncios:** los eventos de arrastre (puntero y teclado) se anuncian con `accessibility.announcements` de `DndContext` (región propia de dnd-kit); los movimientos con ↑ ↓ y los rechazos del servidor, con la región `aria-live="polite"` del hint (patrón `ConsoleHint`). La línea visible del hint repite el último anuncio. Así cada movimiento se anuncia **una** vez.
9. **Fila de partida (`timeline.row` jugando — resuelve el Pendiente):** `<li>` `flex items-center gap-2 rounded-control border border-border-subtle bg-surface px-2 py-1 min-h-13` (52 px); posición `w-4.5 shrink-0 font-mono text-label-comment text-text-dim` (`aria-hidden`); nombre `min-w-0 grow break-words font-mono text-game-item text-text`; asa `buttonClass({ variant: 'icon' })` + `touch-none` con glifo `⠿` `aria-hidden`; grupo ↑ ↓ `flex flex-col gap-1 @xs:flex-row` (apilados cuando el contenedor de la lista mide < 320 px; en línea desde 320 px) con `buttonClass({ variant: 'icon', disabled })`. La lista `<ol>` lleva `@container flex flex-col gap-2`. **Fila tomada:** `border-2 border-game-timeline` con el padding compensado para que el borde no mueva el layout (valores arbitrarios prohibidos: usar utilidades de la escala, p. ej. `px-1.75 py-0.75` en lugar de `px-2 py-1`) y, en el destino, el `<li>` sobre el que está el hito (`over`) se marca `border-dashed border-game-timeline`. **Foco:** el ring `focus-visible` de `buttonClass`. **Bloqueada** (`pending` o `locked`): `useSortable({ disabled: true })`, asa y ↑ ↓ `disabled`. Cálculo a 320 px (256 útiles; panel `p-4` → 224; fila `px-2` → 208): asa 44 + posición 18 + ↑↓ apilados 44 + 3 gaps de 8 = 130 → **78 px para el nombre** (envuelve a 2 líneas con `break-words`; nunca achica los controles de 44 px). `NOT DOCUMENTED - needs verification`: estas medidas resuelven el Pendiente y se documentan en Tarea 7.
10. **Riel (`timeline.rail` — resuelve el Pendiente de la columna de fecha):** la columna fija de 64 px solo entra con años; con `month`/`day` («20 de febrero de 1991», «June 2014») no. **Decisión:** la fecha va **arriba del nombre**, dentro de la columna de texto: ítem `flex gap-3.5` = riel (`w-5 shrink-0`, `aria-hidden`: tramo superior `h-4 w-0.5`, nodo `size-3 rounded-full bg-game-timeline`, tramo inferior `w-0.5 grow`; tramos `bg-game-timeline-rail`, transparentes en el extremo superior del primero e inferior del último) + texto (`flex min-w-0 flex-col gap-1 pt-2.5 pb-4.5`: fecha `font-mono text-numeric-year text-game-timeline`, nombre `font-mono text-game-item text-text break-words`, nota `font-sans text-body-sm text-text-lede`). Funciona igual a 320 y a 1200 sin container queries ni anchos fijos. Fecha con `formatEventDate` (formato **largo** ya implementado y testeado en S-027: `junio de 2014`, `June 8, 1995`; los ejemplos abreviados del screen.md «jun 2014» quedan como nota para limpiar).
