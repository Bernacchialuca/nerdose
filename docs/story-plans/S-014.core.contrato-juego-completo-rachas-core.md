### Convención `game-registry` (aplicable a `core`)

Sección "Update (REQ-004)" (verbatim):

- `applyMove(p, s, m, now, ctx: MoveContext)`: `ctx = { isValidWord(word) }` is built by the `api` from `WordList.has`; games that do not need it ignore it.
- `GameGenerator` declares `historySpec = { bank, lastUsedField, recentDays }` and `usedBankItems(payload)`; the `generator` builds a generic history `{ bankItems, recentChallenges }`, with no per-game logic.

Reglas aplicables (verbatim):

- Routes resolve the game through the registry. No `if (game_id === ...)` or `switch` by game in `apps/api` (ADR-006).
- `moveSchema` of the game validates the move; a failed parse answers `422 invalid_move`. A move invalid for the state also answers `invalid_move`; a Devdle word outside the valid list answers `422 not_in_word_list` and does not consume an attempt.
- Adding a game requires only the package and one line in the registry (the `web`/`admin` and `generator` have their own registries).

Uso previsto en la `api` (de la convención, para que el implementador vea quién arma `ctx`):

```ts
// inside one transaction: applyMove(p, s, m, now, { isValidWord: wordList.has }) -> isFinished -> result/score -> close Play + stats (see platform-day)
```

- "Logic comes from `@nerdose/core` (`today()`, `challengeNumber()`, `nextStreak()`, `liveStreak()`)."
- "`progress.applyResult` calls `nextStreak()` of `@nerdose/core` with `prev_active_day` read from `challenges` with `status IN ('published','voided')`. Reading stats applies `liveStreak()` and never writes."

Reglas aplicables (verbatim):

- The streak function lives in `@nerdose/core` and is the only implementation, used on close, on read and on recompute.

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables (actualizado por REQ-004)

**Decisión:** cada juego es un paquete `packages/games/<game_id>` que implementa el contrato `GameDefinition` de `@nerdose/core`, con tres entradas (`./definition`, `./generator`, `./client`):

```ts
// @nerdose/core — contrato de servidor (entrada ./definition de cada juego)
export interface GameDefinition<Payload, PublicView, State, Move, Feedback, Result, Stats> {
  id: GameId;                       // 'devdle' | 'grep-grid' | 'timeline' | 'big-o' | 'bug-hunt'
  version: number;                  // versión del schema de Payload
  moveSchema: z.ZodType<Move>;

  toPublic(p: Payload, locale: Locale): PublicView;          // sin solución
  initState(p: Payload, now: Date): State;
  applyMove(p: Payload, s: State, m: Move, now: Date, ctx: MoveContext):
    { state: State; feedback: Feedback } | { error: MoveError };   // 'invalid_move' | 'not_in_word_list'
  isFinished(s: State): boolean;
  result(p: Payload, s: State, locale: Locale): Result;      // incluye solución y explicación
  isWin(r: Result): boolean;
  score(r: Result): number;

  initialStats(): Stats;
  reduceStats(prev: Stats, r: Result): Stats;
  historyLabel(r: Result): string;  // "✓ 4/6", "8/8", "3/5", "✓ O(n log n)", "✗ L7"
}

// entrada ./generator
export interface MoveContext { isValidWord(word: string): boolean }   // lo arma la api (WordList.has); los juegos que no lo usan lo ignoran

export interface GameGenerator<Payload> {
  historySpec: { bank: 'terms' | 'timeline_facts' | null; lastUsedField: string; recentDays: number };
  usedBankItems(p: Payload): string[];                       // ids del banco que consume el payload
  generate(input: { date: string; seed: Uint8Array; history: GeneratorHistory }): Payload;
  verify(p: Payload, history: GeneratorHistory): VerificationLog;   // { ok, checks[], reason? }
}
// GeneratorHistory = { bankItems (ítems approved con su last_used_*), recentChallenges (no rejected, [D - recentDays, D - 1]) }
```

**Reglas de Implementación (verbatim):**

- Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
- La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload)`; después, `result(payload, state)`.
- `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
- Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
- `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
- `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

**Aplicación en este plan:** `MoveContext` y el quinto parámetro (Tarea 3); `GameGenerator`, `GeneratorHistory`, `VerificationLog` (Tarea 5). La regla "`generate` MUST ser determinista […] MUST NOT usar `Math.random()`" es la razón de `rngFrom` (Tarea 4).

#### ADR-011: Rachas con días neutros y agregados recalculables

**Decisión** (verbatim):

```
prev_active_day(game_id, D) = max(date) FROM challenges
                              WHERE game_id = :game_id AND date < D
                                AND status IN ('published','voided')
prev_active_day_global(D)   = el mismo max(date), sin filtrar game_id

Al completar una Play del día D:
  game:   current_streak = (last_completed_date >= prev_active_day(game_id, D)) ? current_streak + 1 : 1
          (si last_completed_date == D, no cambia)
  global: global_streak  = (last_active_date >= prev_active_day_global(D)) ? global_streak + 1 : 1
          (si last_active_date == D, no cambia)
  max_* = max(max_*, current)

Al leer: muestra current_streak si last_completed_date == today
         o last_completed_date >= prev_active_day(game_id, today); si no, 0
```

Reglas de dominio del contexto del ADR: completar es ganar, perder o tener la partida anulada; un día sin desafío publicado de un juego es **neutro** para su racha; para la racha global, un día es neutro solo si ningún juego tuvo desafío; la racha se muestra viva solo si el último día completado es hoy o el día activo anterior, si no 0, sin jobs de reseteo; las Play `voided` cuentan para las rachas y `total_completed`.

**Reglas de Implementación (verbatim):**

- La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
- `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
- El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
- Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
- `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
- `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
- La racha leída MUST ser 0 si no está viva, sin escribir en la base.
- Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
- Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.

**Aplicación en este plan:** `nextStreak` implementa la fórmula "Al completar" (sirve igual para la racha de juego y para la global: cambia solo qué `prevActiveDay` pasa el llamador). `liveStreak` implementa "Al leer". `max_*` lo calcula el llamador (`Math.max`), no `nextStreak` (la firma fijada por la convención `testing` devuelve `number`). Las reglas de transacción, de `played`/`wins`/`extra` y de `recomputeStats` son de la `api` (S-020) y de FG-6.

### Decisiones de diseño de REQ-004 aplicables (verbatim)

1. **El contexto de la jugada entra por un parámetro, no por código por juego en la `api`.** `applyMove` no tiene hoy acceso a la lista válida, pero `MoveError` ya incluye `not_in_word_list` (ADR-006). Se agrega un quinto parámetro `ctx: MoveContext = { isValidWord(word: string): boolean }` que la `api` arma con `WordList.has`. Los juegos que no lo usan lo ignoran. Así la `api` no tiene `if (game_id === 'devdle')` (regla de `game-registry`) y la definición sigue pura y testeable. Alternativa descartada: una fábrica `createDevdleDefinition({ wordList })`, porque obliga a construir el registry después de cargar la cache y cambia la forma de la entrada `./definition`.
2. **Historial genérico para generar.** ADR-006 define `generate({ date, seed, history })` sin decir qué es `history`. Cada `GameGenerator` declara `historySpec = { bank: 'terms' | 'timeline_facts' | null, lastUsedField, recentDays }` y `usedBankItems(payload): string[]`. El `generator` arma un historial genérico `{ bankItems, recentChallenges }`: ítems `approved` del banco con su `last_used_*`, y desafíos no `rejected` del juego con `date` en `[D − recentDays, D − 1]`. Para Devdle: `bank: 'terms'`, `lastUsedField: 'last_used_devdle'`, `recentDays: 3`. El `generator` no tiene lógica por juego.

### Decisiones de este plan (no documentadas en la arquitectura)

Estas decisiones completan lo que ADR-006 y la story dejan abierto. Ninguna crea endpoints, tablas ni servicios; son detalles de tipos y de implementación dentro de `core`.

1. **`nextStreak` / `liveStreak` comparten un input `StreakInput = { current: number; lastCompleted: string | null; prevActiveDay: string | null }`** (la firma de `nextStreak` sale literal del ejemplo de la convención `testing`). Ambos devuelven `number`. `lastCompleted` y `prevActiveDay` son `null` cuando la columna es `NULL` (jugador sin partidas previas / ningún día activo anterior).
2. **Casos que el ADR no cubre explícitamente:**
   - `lastCompleted === null` → `nextStreak` devuelve `1`; `liveStreak` devuelve `0`.
   - `prevActiveDay === null` con `lastCompleted !== null` → no hubo ningún día activo anterior que se pudiera perder: `nextStreak` devuelve `current + 1` y `liveStreak` devuelve `current`. (En la práctica no ocurre: si hubo una completada, hubo un día activo; se define para que la función sea total.)
   - La comparación de días es **lexicográfica sobre `YYYY-MM-DD`** (equivale a la cronológica para ese formato). No se parsean fechas.
3. **`MoveContext` vive en `game-definition.ts`** junto a `GameDefinition` (es parte de su firma), aunque ADR-006 lo muestre bajo el comentario "entrada ./generator".
4. **`GameGenerator` es genérico también en el ítem del banco:** `GameGenerator<Payload, BankItem = unknown>` y `GeneratorHistory<Payload = unknown, BankItem = unknown> = { bankItems: readonly BankItem[]; recentChallenges: readonly RecentChallenge<Payload>[] }` con `RecentChallenge<Payload> = { date: string; payload: Payload }`. Motivo: `core` no puede importar los tipos de filas de `@nerdose/db`, y Devdle necesita el término completo (`term`, `category`, `definition`, `summary`, `last_used_devdle`) para generar y las categorías de los `recentChallenges` (de sus payloads). El paquete del juego fija `BankItem` con su propio tipo de fila. El parámetro por defecto mantiene compatible la forma `GameGenerator<Payload>` del ADR.
5. **`VerificationLog = { ok: boolean; checks: VerificationCheck[]; reason?: string }`** (forma del ADR y de `nerdose-db.md`). **`VerificationCheck` = `{ name: string; ok: boolean; detail?: string }`** — `NOT DOCUMENTED - needs verification`: ni ADR-006 ni el schema detallan la forma de cada elemento de `checks[]`; se propone la mínima serializable. Si S-017 necesita otro campo, se extiende ahí sin romper.
6. **`historySpec` se tipa como `HistorySpec = { bank: BankName | null; lastUsedField: string; recentDays: number }` con `BankName = 'terms' | 'timeline_facts'`.** Se exporta `AnyGameGenerator` (equivalente a `AnyGameDefinition`) para el registry del generator. No se agrega `id` a `GameGenerator` (el ADR no lo tiene; el registry del generator mapea por `game_id`).
7. **`rngFrom(seed: Uint8Array): Rng` envuelve pure-rand en una interfaz propia**, para que los paquetes de juego no dependan de `pure-rand` ni de su API (que cambió entre v6, v7 y v8):
   ```ts
   export interface Rng {
     next(): number;                          // int32 crudo de xoroshiro128+, avanza el estado
     int(from: number, to: number): number;   // entero uniforme en [from, to] (pure-rand uniformInt)
     pick<T>(items: readonly T[]): T;         // items[int(0, items.length - 1)]
   }
   ```
8. **Derivación del estado desde el seed (128 bits, todos los bytes cuentan).** El overview del generator delega la derivación exacta en `core`. El ejemplo de la convención del generator (`getInt32(0)` → `xoroshiro128plus(n)`) usa solo 4 de los 32 bytes del HMAC (2³² secuencias posibles y seeds que difieren después del byte 3 darían la misma secuencia). En su lugar:
   - Validar `seed.length >= 16 && seed.length % 4 === 0`; si no, `throw new RangeError('rngFrom: seed must be at least 16 bytes and a multiple of 4')`.
   - Leer el seed en palabras int32 **big-endian** (`new DataView(seed.buffer, seed.byteOffset, seed.byteLength).getInt32(4 * j)`) y plegarlas en 4 carriles: `lanes[j % 4] ^= word[j]`.
   - Si los 4 carriles quedan en 0 (estado degenerado de xoroshiro, que emitiría siempre 0), usar `xoroshiro128plus(0)`; si no, `xoroshiro128plusFromState(lanes)`.
   - Consecuencia: con el seed de 32 bytes del HMAC, cambiar **cualquier** byte cambia la secuencia (salvo colisiones del pliegue XOR, irrelevantes con un HMAC).
   - S-018 debe usar `rngFrom` de `core` y no redefinirlo en `apps/generator/.../seed.ts` (allí queda solo `seedFor` con `node:crypto`). Se anota para S-018; la convención del generator no se toca en esta story.
9. **`Rng.pick([])` lanza `RangeError('Rng.pick: empty list')`**: es un error de programación del generador (debe filtrar antes); `verify` / el pipeline lo capturan como fallo del candidato.
10. **Sin `clock` helper:** `nextStreak` y `liveStreak` reciben el día ya calculado (`string`), igual que `challengeNumber`. No leen `Date` del sistema.

### Tarea 4: PRNG determinista `rngFrom(seed)` sobre pure-rand

**Status:** Completed

#### Description
Crea el módulo `prng` (`src/prng.ts`) con `rngFrom(seed: Uint8Array): Rng`, el PRNG determinista que usarán los `generate` de cada juego (ADR-006: "`generate` MUST ser determinista […] MUST NOT usar `Math.random()`"). Envuelve xoroshiro128+ de pure-rand en una interfaz propia `Rng { next, int, pick }` y deriva el estado de 128 bits a partir de todos los bytes del seed (CA-5).

#### Acceptance Criteria
1. `export interface Rng { next(): number; int(from: number, to: number): number; pick<T>(items: readonly T[]): T }`.
2. `export function rngFrom(seed: Uint8Array): Rng`:
   - Valida `seed.length >= 16 && seed.length % 4 === 0`; si no, `throw new RangeError('rngFrom: seed must be at least 16 bytes and a multiple of 4')` (TS-49).
   - Lee palabras int32 big-endian con `new DataView(seed.buffer, seed.byteOffset, seed.byteLength)` (respeta `byteOffset`, TS-45) y las pliega: `lanes[j % 4] ^= dv.getInt32(4 * j)`.
   - Si `lanes` es `[0, 0, 0, 0]` → `xoroshiro128plus(0)`; si no → `xoroshiro128plusFromState(lanes)` (TS-50).
   - No muta `seed` (TS-44).
3. `next()` devuelve `generator.next()`; `int(from, to)` devuelve `uniformInt(generator, from, to)`; `pick(items)` lanza `RangeError('Rng.pick: empty list')` si `items.length === 0`, y si no devuelve `items[int(0, items.length - 1)]` (con aserción no-null por `noUncheckedIndexedAccess`) (TS-46, TS-47, TS-48).
4. Dos `rngFrom` con el mismo seed producen la misma secuencia; seeds distintos (incluso solo en el byte 31) producen secuencias distintas (TS-41, TS-42).
5. TS-43 fija los 3 primeros `next()` de `rngFrom(SEED_A)` como literales (calculados en la primera corrida).
6. `src/prng.ts` no importa `node:*` (lint de frontera verde).
7. `test/prng.test.ts` cubre TS-41 a TS-50.

#### Technical Details

**Architectural Context References:**

#### Acceptance Criteria
1. Tipos y firmas exactos:
   ```ts
   export interface StreakInput {
     current: number;
     lastCompleted: string | null;   // last_completed_date (juego) o last_active_date (global)
     prevActiveDay: string | null;   // prev_active_day(game_id, D) o prev_active_day_global(D)

   export function liveStreak(input: StreakInput, today: string): number;
   ```
