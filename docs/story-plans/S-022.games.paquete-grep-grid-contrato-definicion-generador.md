### Arquitectura del Servicio

De `docs/architectures/games/manifest.yaml` y `overview.md`: `service: games`, `type: library`, `language: node`; módulos `devdle`, `grep-grid`, `timeline`, `big-o`, `bug-hunt`. Un paquete por juego `packages/games/<game_id>` que implementa el contrato `GameDefinition` de `@nerdose/core` y expone tres entradas separadas: `./definition` (servidor: la usa la `api`), `./client` (React: la usan `web` y `admin`) y `./generator` (`generate` y `verify`: lo usa el `generator`). `definition` y `generator` siguen las convenciones `game-package`, `game-registry`, `validation`, `testing` (y `error-handling`, auto-incluida). Las convenciones `game-clients`, `styling`, `accessibility` y `testing-unit` aplican solo a `./client` (S-024) y no se usan en este plan.

#### Convención `game-package` (extracto verbatim)

```
packages/games/<game_id>/
├── package.json              # name @nerdose/game-<game_id>, exports map below
├── src/
│   ├── definition/           # server contract: GameDefinition implementation
│   │   ├── index.ts          # exports `definition`
│   │   ├── schemas.ts        # Zod: payload, move, public view, result
│   │   └── *.test.ts         # contract tests incl. anti-spoiler
│   ├── client/               # React UI: Instructions, Game, Result, share()
│   ├── generator/            # GameGenerator: generate() and verify()
│   │   ├── index.ts          # exports `generator`
│   │   └── *.test.ts
│   └── shared/               # pure types and helpers used by more than one entry
└── (extra assets of the game, e.g. wordlist/ for devdle)
```

There is no root `.` export: a consumer must pick an entry.

| Entry | Exports | Consumer |
|---|---|---|
| `./definition` | `definition`: object implementing `GameDefinition` (`moveSchema`, `toPublic`, `initState`, `applyMove`, `isFinished`, `result`, `isWin`, `score`, `initialStats`, `reduceStats`, `historyLabel`) | `apps/api`, and `./client`/`./generator` for types |
| `./generator` | `generator`: `GameGenerator` with `generate({ date, seed, history })` and `verify(payload, ctx)` | `apps/generator` |

| Entry | May import | Must not import |
|---|---|---|
| `./definition` | `@nerdose/core` (`.`), `zod`, `shared/` | `@nerdose/polyglot`, `node:*`, React, `./generator`, `./client`, anything that executes code |
| `./generator` | `@nerdose/core` (`.`), `zod`, `@nerdose/polyglot`, `shared/`, `./definition` | `./client`, React |

`shared/` holds only pure, isomorphic code (types, constants, helpers) with no Node or React dependencies.

Rules (las que aplican a este plan):

- One package per game, with `game_id` in `devdle | grep-grid | timeline | big-o | bug-hunt` and package name `@nerdose/game-<game_id>`.
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry.
- `./definition` implements every method of `GameDefinition`; `toPublic` never includes the solution (per-game list in ADR-006).
- Every game has an anti-spoiler contract test: serialize `toPublic(payload)` and every pre-result response and verify none contains a solution value.
- `moveSchema` is the single schema used by `web` (before sending) and by `api` (validation); a parse failure is `422 invalid_move`.
- `generate` is deterministic: same `{ date, seed, history }` gives the same payload. It never uses `Math.random()` or the current time; randomness comes from the PRNG built from the seed.
- Every player-facing text of a `Payload` is `{ es, en }`; `verify` fails if a language is missing.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint).

#### Convención `game-registry` — Update (REQ-005) (verbatim)

- `MoveContext = { isValidWord(word): boolean; locale: Locale }`: the `api` adds the locale it already resolved for `result`. A game uses it to localize `Feedback` (Grep Grid: `feedback.definition`); `Feedback` never carries `{ es, en }` (ADR-015). Devdle ignores it.
- `toPublic(p, locale, state?)`: the `api` passes `play.state` only when the Play is `in_progress` (`game.toPublic(challenge.payload, locale, play?.status === 'in_progress' ? play.state : undefined)`); with no Play or a finished Play it passes nothing. With a state, `toPublic` may reveal only what the player already discovered in that Play (Grep Grid: `words[].definition` for the `term_id`s in `found_words`) and never anything about what is still hidden.
- Both changes are additive: games that do not need them keep compiling and behave the same.
- A move may be valid and leave the state unchanged (Grep Grid: `not_a_word`, `already_found`): `applyMove` returns the same state with a `feedback`, the `api` answers `200` and the idempotent `UPDATE plays SET state` still runs.
- The anti-spoiler contract test of a game that uses `state` covers `toPublic` with no state, with the initial state and with intermediate states.

Reglas previas de `game-registry` que aplican al paquete: `Feedback` returned for a move never contains a solution value that the game has not already revealed by design. Win, score, stats and history label come only from the game definition (`isWin`, `score`, `reduceStats`, `historyLabel`). Every game has an anti-spoiler contract test; the build fails without it.

#### Convención `validation` (extracto)

- Schemas for the moves, payloads, states, results and stats of a game are owned by that game package and imported from it. They are never redefined in `apps/`.
- Types are inferred from schemas (`z.infer`). No hand-written types that duplicate a schema.
- JSON property names in schemas are `snake_case` and match `docs/apis/api.yaml` (ADR-015). No `camelCase` aliases or transforms.
- Day dates are validated as `YYYY-MM-DD` strings.
- Use composition (`.partial()`, `.omit()`, `.pick()`, `.extend()`) instead of duplicating schemas.
- La `api` valida la jugada con `game.moveSchema.safeParse(body.move)`; si falla responde `422 invalid_move`. El `generator` valida cada candidato con `payloadSchema.parse(generator.generate(...))`: **`generate` tiene que devolver siempre un payload que pase `payloadSchema`** (un `parse` fallido corta el job).

#### Convención `error-handling` (extracto)

El catálogo de errores es cerrado y vive en `@nerdose/core`. Un juego **no lanza** `AppError` en `applyMove`: devuelve `{ error: MoveError }` con `MoveError = 'invalid_move' | 'not_in_word_list'`; la `api` lo traduce a `422`. Grep Grid solo usa `'invalid_move'`.

#### Convención `testing` (extracto aplicable)

- Unit tests are for pure functions: no I/O, no containers. Todo lo de este plan es unitario.
- Contract tests for each game: anti-spoiler (ADR-006).
- Code under test receives `now` as a parameter; it never calls `new Date()` in domain logic.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Tests do not touch the network.

#### Convención `_base` (Node) — extracto

`strict` + `noUncheckedIndexedAccess`; archivos y carpetas en `kebab-case`; funciones y variables `camelCase`; constantes globales `SCREAMING_SNAKE_CASE`; tipos `PascalCase` sin prefijo `I`; sin `any` salvo en bordes con librerías sin tipos; sin comentarios salvo el porqué no obvio; sin `// TODO` sin issue. Orden de imports: externos, luego relativos, separados por línea en blanco. (Los paquetes de juego usan imports relativos, sin alias `@/`, igual que Devdle.)

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables (actualizado por REQ-005)

- **Decisión:** cada juego es un paquete `packages/games/<game_id>` que implementa `GameDefinition` de `@nerdose/core` con tres entradas; registries en `api`, `web`/`admin` y `generator`.

```ts
export interface GameDefinition<Payload, PublicView, State, Move, Feedback, Result, Stats> {
  id: GameId;                       // 'devdle' | 'grep-grid' | 'timeline' | 'big-o' | 'bug-hunt'
  version: number;                  // versión del schema de Payload
  moveSchema: z.ZodType<Move>;

  toPublic(p: Payload, locale: Locale, state?: State): PublicView;   // sin solución; state solo con la Play in_progress (REQ-005)
  initState(p: Payload, now: Date): State;
  applyMove(p: Payload, s: State, m: Move, now: Date, ctx: MoveContext):
    { state: State; feedback: Feedback } | { error: MoveError };   // 'invalid_move' | 'not_in_word_list'
  isFinished(s: State): boolean;
  result(p: Payload, s: State, locale: Locale): Result;      // incluye solución y explicación
  isWin(r: Result): boolean;
  score(r: Result): number;

  initialStats(): Stats;
  reduceStats(prev: Stats, r: Result): Stats;
  historyLabel(r: Result): string;  // "✓ 4/6", "8/8", "3/5", "✓ O(n log n)", "✗ L7"
}

export interface MoveContext { isValidWord(word: string): boolean; locale: Locale }

export interface GameGenerator<Payload> {
  historySpec: { bank: 'terms' | 'timeline_facts' | null; lastUsedField: string; recentDays: number };
  usedBankItems(p: Payload): string[];                       // ids del banco que consume el payload
  generate(input: { date: string; seed: Uint8Array; history: GeneratorHistory }): Payload;
  verify(p: Payload, history: GeneratorHistory): VerificationLog;   // { ok, checks[], reason? }
}
// GeneratorHistory = { bankItems (ítems approved con su last_used_*), recentChallenges (no rejected, [D - recentDays, D - 1]) }
```

- **Reglas de Implementación (verbatim):**
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
  - La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`). Con `state`, `toPublic` MAY revelar únicamente lo que el jugador ya descubrió en esa Play (Grep Grid: `words[].definition` de los `term_id` presentes en `found_words`); MUST NOT revelar nada de lo no descubierto (REQ-005).
  - `Feedback` MUST ir en el locale del jugador (`ctx.locale`), nunca como `{ es, en }` (ADR-015).
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` (sin estado y con estados intermedios, si el juego usa `state`) y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015 (extracto aplicable)

JSON en `snake_case`; al jugador nunca se le envían textos `{ es, en }` (se resuelven al locale); catálogo de errores cerrado.

#### ADR-016 / ADR-007 (extracto aplicable)

El banco `terms` es un dataset versionado (`@nerdose/content`); Grep Grid usa una ventana anti-repetición de 30 días sobre `terms.last_used_grep`. El pipeline del `generator` hace hasta 20 intentos por fecha (`attempt` 0–19), cada uno con `seed = HMAC-SHA256(GENERATOR_SECRET, "grep-grid:D:attempt")`.

### Decisiones de diseño de REQ-005 aplicables (verbatim)

1. **Payload del desafío.** `{ date, grid: string[12][12], words: [{ term_id, word, definition: { es, en } }] ×8, placements: [{ term_id, from: Cell, to: Cell, direction }] ×8 }`, con `direction ∈ right | down | down_right | up_right` (→, ↓, ↘, ↗: las 4 direcciones "hacia adelante" del supuesto del request). `from`/`to` son la primera y la última letra; las celdas intermedias se derivan con `lineCells(from, to)` de `shared/geometry.ts`, que usan las tres entradas (la definición para validar y contestar, el generador para ubicar y verificar, el client para pintar). El payload no lleva `summary`: la pantalla solo muestra la definición breve (RF 4, 13). `words` fija el orden de la lista pública. `payloadSchema` se registra en `GeneratorEntry.payloadSchema` y valida cada candidato, como en Devdle.

3. **`toPublic` con el estado de la Play.** […] Grep Grid devuelve `words[i].definition` **únicamente** para los `term_id` presentes en `found_words`; las demás no llevan la propiedad. El test anti-spoiler cubre los tres casos (sin estado, 0 encontradas, k encontradas).

5. **Reglas de `applyMove`.** Orden: (a) estado terminado (`gave_up` o 8 encontradas) → `invalid_move` (defensivo: la `api` ya responde `409 game_finished` antes de llegar); (b) `type: give_up` → `state = { ...s, gave_up: true }`, `feedback: null`; (c) `type: select`: `from ≠ to`, ambas en 0–11 (ya lo garantiza `moveSchema`) y alineadas en una de las 4 direcciones hacia adelante; si no → `invalid_move` (CA 4, 8); (d) coincidencia exacta de `from` y `to` con un `placement` → si el `term_id` ya está en `found_words`: `{ found: false, reason: 'already_found' }` sin cambiar el estado (CA 7); si no: se agrega `{ term_id, cells: lineCells(from, to) }` al final de `found_words` y se responde `{ found: true, term_id, word, definition: words[i].definition[ctx.locale], cells }` (CA 3, 5); (e) línea válida sin coincidencia → `{ found: false, reason: 'not_a_word' }` sin cambiar el estado (CA 6). Ni (d, ya encontrada) ni (e) son errores: la `api` responde `200` y el `UPDATE plays SET state` con el mismo estado es idempotente. Una selección que coincide con un tramo parcial de una palabra es `not_a_word` (CA 6): `from`/`to` deben ser exactamente la primera y la última celda.

6. **Estado, cierre, resultado y stats.** `GrepGridState = { found_words: [{ term_id, cells }], gave_up: boolean }`. `initState → { found_words: [], gave_up: false }`. `isFinished(s) = s.gave_up || s.found_words.length === 8`. `result(p, s, locale) = { win: found === 8, score: found, gave_up: s.gave_up, words: p.words.map(w => ({ term_id, word, definition: w.definition[locale], found, cells })) }` en el orden de la lista (CA 9, 10, 12, 13). `isWin = r.win`, `score = r.score`, `historyLabel = "N/8"` (sin ✓/✗, como fija el PRD). `extra = { words_found: { "0": n, …, "8": n } }`: distribución de palabras encontradas por partida […]; `reduceStats` suma 1 en `String(r.score)`. […] Rendirse con 8/8 es imposible: la octava palabra cierra la Play en esa jugada (CA 13).

7. **Elección de las 8 palabras.** `historySpec = { bank: 'terms', lastUsedField: 'last_used_grep', recentDays: 30 }`; `usedBankItems(p) = p.words.map(w => w.term_id)`. Elegibles: `terms` `approved` con `last_used_grep IS NULL OR last_used_grep <= D − 30`, ordenados por `term`. […] Se eligen 8 con `rngFrom(seed).pick` sobre la lista restante, descartando cualquier candidato que sea subcadena o supercadena de uno ya elegido (CA 30). Sin regla de categorías (supuesto).

8. **Ubicación y relleno.** Determinista a partir del `Rng`: las 8 palabras se ordenan de mayor a menor largo y se ubican una por una probando posiciones y direcciones en un orden barajado con el `rng`; una posición es válida si cada celda está vacía o ya tiene la misma letra (cruces permitidos) y la palabra no queda íntegramente sobre celdas ocupadas (contenida en otra). Si una palabra no entra se retrocede (backtracking acotado); si aun así no hay solución, `generate` devuelve igual un payload que `verify` rechaza y el pipeline reintenta con el seed del intento siguiente (patrón de Devdle: "sin elegibles se elige igual"). Las celdas libres se rellenan con `rng.int(0, 25)` → A–Z; después se comprueba la unicidad y, si alguna palabra aparece dos veces, se vuelven a sortear solo las celdas de relleno hasta 10 veces dentro del mismo `generate` antes de entregar el candidato. Nunca `Math.random()` ni la hora (ADR-006).

9. **`verify`.** Checks con `name` estable para `challenges.verification`, en este orden: `grid_shape` (12×12, solo `^[A-Z]$`), `words_count` (8 `term_id` distintos), `words_in_bank` (cada `term_id` está en `bankItems` con el mismo `term`), `word_shape` (`^[A-Z]{4,12}$`), `texts_bilingual` (`definition.es` y `.en` no vacíos), `no_substrings` (ningún par subcadena/supercadena), `placements_consistent` (cada placement es una línea hacia adelante dentro de la grilla y sus celdas deletrean la palabra), `exactly_once` (cada palabra aparece exactamente 1 vez en toda la grilla contando solo las 4 direcciones permitidas; la reversa no cuenta, supuesto del request), `not_used_30` (`last_used_grep IS NULL OR <= D − 30` y el `term_id` no aparece en `recentChallenges`). El primer check fallido va en `reason`.

### Contexto de Flujos

#### `jugada-y-cierre-de-partida` (extractos verbatim)

- Jugada de grep-grid: `{ "type": "select", "from": { "row", "col" }, "to": { "row", "col" } }` o `{ "type": "give_up" }`.
- Jugada válida sin cambio de estado (solo Grep Grid): una línea válida hacia adelante que no coincide exactamente con una de las 8 palabras (`feedback.reason = 'not_a_word'`) o una palabra ya encontrada (`feedback.reason = 'already_found'`) devuelven el mismo `state`. No son errores: el UPDATE con el mismo `state` es idempotente y la respuesta es `200`, sin penalización.
- Grep Grid, `move.type = 'select'`: si `from` y `to` coinciden exactamente con la primera y la última celda de una palabra no encontrada, se agrega `{ term_id, cells }` al final de `state.found_words` y `feedback.definition` va en `ctx.locale`. `move.type = 'give_up'`: `state.gave_up = true` y `feedback = null`.
- En Grep Grid, `isFinished(state) = state.gave_up || state.found_words.length === 8`: la octava palabra cierra `won` con `score = 8`; `give_up` cierra `lost` con `score = found_words.length` (0–7), cuenta para la racha y `result` trae `gave_up: true` y las 8 `words` con `found` y `cells`. `extra` de grep-grid = `{ words_found: { "0": n, …, "8": n } }`; `reduceStats` suma 1 en `String(score)`.
- `feedback` de grep-grid: `{ found: true, term_id, word, definition, cells: [{ row, col }] }` o `{ found: false, reason: "not_a_word" | "already_found" }`; `null` en `give_up`.
- Inválida para el estado (selección en reversa, no alineada o de una sola celda en Grep Grid) → `422` `{ "error": { "code": "invalid_move", … } }`; nada cambia.

Este plan implementa la parte del paquete: `applyMove`, `isFinished`, `result`, `reduceStats`. La transacción, el `UPDATE plays` y las rachas son de la `api` (S-023).

#### `abrir-y-retomar-juego` (extractos verbatim)

- `public_view` de grep-grid: `{ grid: string[12][12], words: [{ term_id, word, definition? }] ×8 }` — `definition` solo en las palabras ya encontradas (`term_id` presentes en `plays.state.found_words`), en el locale resuelto; nunca en las no encontradas ni sin Play.
- `state` inicial por juego: grep-grid `{ found_words: [], gave_up: false }`.
- En Grep Grid, al retomar o al cambiar de idioma, las definiciones de las palabras encontradas salen de `public_view.words[].definition`; `plays.state.found_words` guarda solo `{ term_id, cells }` (REQ-005).

Este plan implementa `toPublic` e `initState`. Que la `api` pase `play.state` es S-023.

#### `generacion-diaria` (extractos verbatim)

- `history`: challenges no `rejected` del juego en la ventana anti-repetición. En devdle, grep-grid y timeline, además, los ítems `approved` del banco con su `last_used_*`.
- `candidate = games[game_id].generator.generate({ date, seed, history })`.
- grep-grid: checks en este orden, con `name` estable (el primero que falla va en `verification.reason`): `grid_shape` (12×12, solo A–Z), `words_count` (8 `term_id` distintos), `words_in_bank`, `word_shape` (`^[A-Z]{4,12}$`), `texts_bilingual` (`definition.es` y `.en`), `no_substrings` (ninguna palabra es subcadena de otra), `placements_consistent` (cada placement es una línea hacia adelante —`right`, `down`, `down_right`, `up_right`— y sus celdas deletrean la palabra), `exactly_once` (cada palabra exactamente 1 vez contando solo esas 4 direcciones; la reversa no cuenta), `not_used_30` (`terms.last_used_grep IS NULL` o `<= date − 30`, y el `term_id` no aparece en los challenges recientes).
- ok → `terms` — UPDATE `last_used_grep = date` (grep-grid).

### Decisiones de este plan (no documentadas en la arquitectura) — `NOT DOCUMENTED - needs verification`

Detalles que la documentación no fija y que este plan resuelve para que la implementación sea determinista y testeable. Ninguno contradice el REQ; si alguno no convence, se cambia en el REQ.

1. **`exports` sin `./client` en esta story.** La convención `game-package` dice que `exports` tiene exactamente `./definition`, `./client` y `./generator`, pero `./client` es de S-024 y un export que apunta a un archivo inexistente rompe la resolución. En S-022 el `package.json` exporta solo `./definition` y `./generator`; S-024 agrega `./client` (y `react`, `@nerdose/ui`, jsdom).
2. **`shared/geometry.ts` devuelve `null` para una línea inválida.** `lineCells(from, to): Cell[] | null`. También es `null` si alguna coordenada no es un entero en 0–11.
3. **`term_id` como `z.string().min(1)`** (igual que Devdle), no `z.uuid()`: `api.yaml` documenta `format: uuid` pero el molde no lo valida y el test sobre el dataset real usa `wikidata_id` como id.
4. **Orden de `words` en el payload: ordinal por `word`** (`sortByTerm`). El REQ dice que `words` "fija el orden de la lista pública" pero no cuál; el orden alfabético no filtra nada de la ubicación (el orden de ubicación es por largo). `placements` va en el mismo orden que `words`.
5. **La elegibilidad excluye también los `term_id` de `recentChallenges`.** CA-10 define elegible como `last_used_grep IS NULL OR last_used_grep <= D − 30`, pero el check `not_used_30` además rechaza un `term_id` presente en `recentChallenges`, cuya ventana es `[D − 30, D − 1]`. Un término usado exactamente en `D − 30` cumple la regla de fecha y a la vez está en un challenge reciente: si `generate` lo eligiera, `verify` lo rechazaría siempre. `generate` lo excluye para no producir candidatos inválidos a sabiendas.
6. **Menos de 8 elegibles compatibles.** Se completa con términos no elegibles (orden por `term`, mismo `rng.pick`) y, en último caso, con los descartados por subcadena; `verify` rechaza por `not_used_30` o `no_substrings` (patrón Devdle "sin elegibles se elige igual"). Con **menos de 8 ítems en el banco** `generate` lanza `RangeError('grep-grid generate: bank has fewer than 8 terms')` (análogo al `RangeError` de Devdle con banco vacío): no hay forma de devolver un payload que pase `payloadSchema`.
7. **Ubicación fallida.** Si el backtracking agota el presupuesto (`MAX_PLACEMENT_STEPS = 2000` intentos de candidato), las palabras sin ubicar llevan el placement de relleno `{ from: { row: 0, col: 0 }, to: { row: 0, col: len − 1 }, direction: 'right' }` sin escribir sus letras: el payload pasa `payloadSchema` y `verify` falla en `placements_consistent`.
8. **Consumo del `rng`:** una sola instancia `rngFrom(seed)` en este orden: elección de términos → un barajado Fisher–Yates de candidatos por palabra (los 8 barajados se hacen **antes** de empezar el backtracking, para que el consumo no dependa del camino) → relleno (y sus re-sorteos).
9. **`addDays`/`isValidDate` se copian** a `grep-grid/src/generator/dates.ts`: las fronteras prohíben importar entre paquetes de juego y moverlas a `core` está fuera del alcance.
10. **Test de tasa de rechazo sobre el dataset real** en `packages/games/grep-grid/test/` usando `loadDataset()` de `@nerdose/content` como `devDependency` (queda en el grafo de Turbo). Umbral: con 200 seeds, al menos el 95 % de los candidatos pasa `verify`. El umbral no está en el REQ ("mide la tasa de rechazo"); 95 % deja margen sobre los 20 intentos del pipeline.
11. **Checks de `verify` que dependen de uno anterior:** todos los checks se calculan siempre y ninguno lanza; `placements_consistent` y `exactly_once` devuelven `ok: false` con `detail: 'grid_shape failed'` si `grid_shape` falló.

#### Description

#### Acceptance Criteria
