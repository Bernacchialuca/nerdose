# Story Plan: S-006 (core) - Día de la plataforma y tabla players

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-006](../stories/S-006.dia-plataforma-tabla-players.md)
- **Servicio:** core
- **Resumen:** Agrega a `@nerdose/core` (entrada isomorfa `.`) el módulo `platform-day` con cuatro funciones puras que reciben el reloj por parámetro (`today(now)`, `challengeNumber(day, launchDate)` nullable, `nextResetAt(now)`, `secondsToReset(now)`), y los enums compartidos `LOCALES`, `CODE_LANGUAGES` e `isGameId()`. Es la base de la que dependen `api` (S-007, S-008) y `web` (S-009) para día UTC, número de desafío, cuenta regresiva, idioma y lenguaje de código.

> **Alcance de este plan:** solo el servicio `core` (`packages/core`). CA-1 a CA-4 son de `core`. CA-5 (migración de `players`) y CA-6 (permisos por rol) son del servicio `db` y se planifican aparte (`S-006.db.*`).
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a la raíz del paquete, `packages/core/`.
>
> **Fuera de alcance:** `nextStreak()`, `liveStreak()` (rachas, ADR-011), `rngFrom()` (PRNG), la entrada `./notify`, el parseo/validación de `LAUNCH_DATE` desde el env (S-007, en la `api`) y cualquier helper `clock` (la story pide funciones puras con el reloj inyectado; no se crea un `clock` en este plan).

### Convención `platform-day` (aplicable a `core`)

`applies_to: [api, library]`. Lo relevante para `core`:

```ts
import { today, challengeNumber } from '@nerdose/core';

const day = today(clock.now());                         // 'YYYY-MM-DD', UTC
const number = challengeNumber(day, env.LAUNCH_DATE);   // day - LAUNCH_DATE + 1; null if day < LAUNCH_DATE
```

Reglas de la convención que tocan este plan (verbatim):
- `today` is computed on the server with `@nerdose/core` (UTC). A date is never accepted from the client on a player route.
- `number = today - LAUNCH_DATE + 1`; `LAUNCH_DATE` comes from `env`, shared with the `generator`.
- The streak function lives in `@nerdose/core` and is the only implementation, used on close, on read and on recompute. *(fuera de alcance de este plan)*
- `GET /api/today` returns `next_reset_at` (next 00:00 UTC, ISO 8601) and `seconds_to_reset`.

### Convención `testing` (aplicable a `core`)

- **Unit tests** for pure logic (streaks, seeds, day calculation, move reducers): no I/O, no containers.
- Dates, day changes and streaks MUST be tested with a fake clock, never with the real one. Code under test receives `now` as a parameter or from a single `clock` helper of `@nerdose/core`; it never calls `new Date()` in domain logic.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Reset mocks and timers between tests (`vi.clearAllMocks()`, `vi.useRealTimers()`).

Patrón de fake clock (de la convención):

```ts
import { vi, beforeEach, afterEach } from 'vitest';

beforeEach(() => { vi.useFakeTimers({ toFake: ['Date'] }); vi.setSystemTime(new Date('2026-12-01T23:59:58Z')); });
afterEach(() => vi.useRealTimers());
```

En este plan las funciones reciben `now` por parámetro, así que el fake clock se usa solo para probar que **no** leen el reloj del sistema (TS-18).

### Convención `_base` (Node)

- `strict`, `noUncheckedIndexedAccess`; sin `any` salvo en bordes con librerías sin tipos (comentado).
- Archivos `kebab-case`; funciones `camelCase`; constantes globales `SCREAMING_SNAKE_CASE`; tipos `PascalCase` sin prefijo `I`.
- **Dates:** at all system boundaries (HTTP, DB, events, logs) dates are ISO 8601 UTC: `2025-03-15T10:30:00.000Z`. In memory, work with `Date` objects or types from the chosen package. Never strings without a defined format. Never assume the server timezone. Timestamps are always absolute (UTC).
- Comentarios: por defecto ninguno; solo el *por qué* cuando no es obvio.

### Convención `game-registry` (aplicable a `core`)

- A registry entry is validated at startup: unknown or duplicated ids make the process fail to start.
- Routes resolve the game through the registry. No `if (game_id === ...)` or `switch` by game in `apps/api` (ADR-006).

`isGameId()` es el guard que usarán la `api` y el `web` para validar un `game_id` que viene de afuera (URL, query) sin hardcodear la lista.

### ADRs Relevantes

#### ADR-008: Día de la plataforma, publicación perezosa y jugada tardía

- **Decisión:** `today = (now() AT TIME ZONE 'UTC')::date`, calculado en `@nerdose/core`. `number = today − LAUNCH_DATE + 1`. Publicación perezosa single-flight en la `api` (fuera de alcance de `core`).
- **Reglas de Implementación (verbatim):**
  - `today` MUST calcularse siempre en el servidor con la función de `@nerdose/core` (día UTC). MUST NOT aceptarse una fecha del cliente en ninguna ruta de jugador.
  - `number` MUST ser `today − LAUNCH_DATE + 1`, con `LAUNCH_DATE` (`YYYY-MM-DD`) como variable de entorno compartida por `api` y `generator`.
  - La publicación MUST ejecutarse con el primer request del día y al arrancar, protegida con single-flight en memoria: un solo request ejecuta y los concurrentes esperan esa misma promesa.
  - La sentencia de publicación MUST ser exactamente `UPDATE challenges SET status='published' WHERE status='approved' AND date = :today`. MUST NOT publicar fechas pasadas ni futuras.
  - Un `approved` de un día en el que la `api` nunca corrió MUST quedarse `approved`, y ese día es neutro para las rachas.
  - Los bodies de `POST /api/games/{game_id}/today/start`, `/move`, `/report` y `/acknowledge-void` MUST incluir `challenge_number` (entero ≥ 1).
  - Si `challenge_number ≠ number` de hoy, la `api` MUST responder `409` con `{ "error": { "code": "challenge_expired", … } }`.
  - Una Play `in_progress` de un día pasado MUST quedar `in_progress` para siempre y no contar como completada.
  - `GET /api/today` MUST devolver `next_reset_at` (próxima 00:00 UTC, ISO 8601) y `seconds_to_reset`. Al llegar a 0, el front MUST esperar 0–3 s al azar antes de volver a pedir.
- **Modificación de REQ-002 (decisión de diseño 3):** `challengeNumber()` devuelve `null` si `day < LAUNCH_DATE` (no se devuelven números ≤ 0); `Today.number` pasa a `nullable: true`. Alternativa descartada: rechazar el arranque con `LAUNCH_DATE` futura.

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables a `core`, verbatim)

- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
- `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

### Contexto de API

`core` no expone endpoints. Sus funciones alimentan el schema `Today` de `GET /api/today` (`docs/apis/api.yaml` l. 1077), que implementa la `api` en S-008:

```yaml
Today:
  type: object
  required: [date, number, next_reset_at, seconds_to_reset, has_session, global_streak, completed_today, games]
  properties:
    date: { type: string, format: date, description: Día UTC de la plataforma }
```

### Decisiones de este plan (no documentadas en la arquitectura)

> **NO DOCUMENTADO — tipo de retorno de `nextResetAt`:** la story dice "devuelven las 00:00 UTC siguientes" sin fijar el tipo. Se decide **`Date`**, por la convención `_base` ("In memory, work with `Date` objects"); la conversión a ISO 8601 (`toISOString()`) la hace la `api` en el borde HTTP. Si se prefiere un string ISO, cambiar solo la firma y TS-10/11/12.
>
> **NO DOCUMENTADO — redondeo de `secondsToReset`:** el contrato pide entero ≥ 0. Se decide **`Math.ceil`** de los milisegundos restantes / 1000. Con `floor`, a las `23:59:59.500Z` daría `0` y el front (que refetchea al llegar a 0) pediría `GET /api/today` antes del cambio de día y recibiría el día viejo. Con `ceil` el contador llega a 0 recién en la frontera. A las `00:00:00.000Z` exactas el siguiente reset es el del día siguiente, así que devuelve `86400`.
>
> **Validación de entradas:** `challengeNumber` asume `day` y `launchDate` en formato `YYYY-MM-DD` válido. Story, "Manejo de errores": "`launchDate` inválida es responsabilidad de quien parsea el env (S-007)". No se agrega validación ni se lanza error en `core`.

### Tarea 2: Módulo `platform-day`: `today`, `challengeNumber`, `nextResetAt`, `secondsToReset`

**Status:** Completed

#### Descripción

Crea las cuatro funciones puras del día de la plataforma. Reciben el instante (`now: Date`) o las fechas (`'YYYY-MM-DD'`) por parámetro y nunca leen el reloj del sistema, así sirven igual en `api`, `generator` y `web` y se testean sin fake timers. Cubre CA-1, CA-2 y CA-3.

#### Criterios de Aceptación

1. `today(now: Date): string` devuelve la fecha UTC de `now` en formato `YYYY-MM-DD` (con ceros a la izquierda), usando `getUTCFullYear/getUTCMonth/getUTCDate` (o `toISOString().slice(0, 10)`), independiente de la zona horaria del proceso.
2. `challengeNumber(day: string, launchDate: string): number | null` devuelve `diasEntre(launchDate, day) + 1` si `day >= launchDate`, y `null` si `day < launchDate`. Nunca devuelve un número < 1.
3. La diferencia en días se calcula sobre medianoches UTC (`Date.UTC(y, m - 1, d)`), dividiendo por `86_400_000`; el resultado es entero exacto (sin DST porque todo es UTC).
4. `nextResetAt(now: Date): Date` devuelve un `Date` nuevo con las 00:00:00.000 UTC del día siguiente al día UTC de `now` (si `now` es exactamente 00:00 UTC, devuelve las 00:00 del día siguiente).
5. `secondsToReset(now: Date): number` devuelve `Math.ceil((nextResetAt(now).getTime() - now.getTime()) / 1000)`: entero, en el rango `1..86400`.
6. Ninguna función llama `new Date()` sin argumentos, `Date.now()` ni muta el `Date` recibido.
7. `src/platform-day.ts` no importa `node:*` ni `./notify`.

#### Detalles Técnicos

**Referencias al Contexto Arquitectónico:**
- ADR-008: `today` en UTC, `number = today − LAUNCH_DATE + 1`, `next_reset_at` próxima 00:00 UTC, `seconds_to_reset`.

- Convención `_base` → Dates (UTC, `Date` en memoria).
- Convención `testing` → funciones reciben `now` por parámetro.
- Decisiones de este plan: retorno `Date` de `nextResetAt` y `Math.ceil` en `secondsToReset`.
- Contexto de API: mapeo a los campos de `Today`.

**Archivos a Crear/Modificar:**

**Notas de Implementación:**

Con `noUncheckedIndexedAccess`, los elementos de `split` son `string | undefined`: preferir `Date.parse` con sufijo `Z` explícito para evitar ese ruido.
