# Story Plan: S-004 (generator) - Esqueleto del generator con scheduler sin jobs

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-004](../stories/S-004.esqueleto-generator-scheduler.md)
- **Servicio:** generator
- **Resumen:** Crea `apps/generator`, un worker sin puerto que valida su entorno (`@t3-oss/env-core`), crea el logger Pino, se conecta como `nerdose_generator`, verifica el rol (`SELECT current_user`) y arranca un scheduler croner en UTC **sin jobs** que se mantiene vivo con un timer de keep-alive. Ante `SIGTERM`/`SIGINT` cierra ordenadamente con código 0. Si la base no responde al arrancar, sale con código 1.

> **Alcance de este plan:** solo el servicio `generator` (`apps/generator`). No hay cambios de contrato de API ni de base de datos.
>
> **Rutas:** todas las rutas de "Files to Create/Modify" son relativas a `apps/generator/` salvo que se indique `(raíz)`.
>
> **Dependencias:** S-001 y S-002 están `Completed`. No hay dependencias bloqueantes. S-003 (`api`) es independiente; su implementación ya está mergeada en `dev` y sirve de modelo de código (ver "Código Reutilizable").
>
> **Código reutilizable:** no existe `docs/reusable-code/generator/index.md` (la app es nueva). Se reutiliza lo documentado de `@nerdose/core` y `@nerdose/db` y se replican los patrones ya implementados en `apps/api` (no se importan: ADR-003 prohíbe imports entre apps). Al terminar la story conviene correr `/service-update-reusable-code` para `generator`.
>
> **UX / Design System:** la story tiene `affects_ui: false`; no se carga contexto de UX ni de Design System.

## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript con `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`, `module: ESNext`, `moduleResolution: bundler`, `verbatimModuleSyntax: true`, `skipLibCheck: true`, `noEmit: true` (heredado de `tsconfig.base.json` de la raíz).
- **Runtime:** Node.js 24 LTS (`engines.node` `">=24 <25"` en la raíz), pnpm `11.6.0`, Turborepo. Los paquetes internos se consumen como fuente TS (`exports` → `./src/index.ts`, sin build).
- **Scheduler:** `croner` (expresiones cron en UTC, `timezone: 'UTC'`, `protect: true`). Dependencia nueva: versión vigente al instalar, rango `^` (la documentación no fija versión).
- **Base de datos:** PostgreSQL 16 a través de `@nerdose/db` (`createDb(url)` → `{ db, sql }`, Drizzle sobre postgres.js). El `generator` se conecta como `nerdose_generator`.
- **Entorno:** `@t3-oss/env-core` (`^0.13.11`) + `zod` (`^4.6.7`) — mismas versiones que `apps/api` y `@nerdose/db`; `dotenv` (`^18.0.9`) para cargar `.env.local` en desarrollo.
- **Logs:** `pino` (runtime) y `pino-pretty` (solo `NODE_ENV=development`). Mismas versiones que `apps/api` (`pino ^10.4.0`, `pino-pretty ^13.2.0`).
- **Scripts:** `tsx` (`^4.23.15`): `tsx watch src/index.ts` para `dev`; `node --import tsx src/index.ts` en los tests de proceso.
- **Tests:** Vitest `^5.1.0` (raíz) + `@testcontainers/postgresql` (`^12.2.1`). Integración contra PostgreSQL 16 real; nunca se mockea la base en tests de integración.
- **Errores:** `AppError` / `ERROR_CATALOG` / `ErrorCode` de `@nerdose/core`.
- **Fuera de alcance en esta story** (llegan con sus feature groups): `pure-rand`, `nodemailer`/`notify`, `@nerdose/polyglot`, `@nerdose/content`, `GENERATOR_SECRET`, `LAUNCH_DATE`, `GENERATION_MAX_ATTEMPTS`, `SMTP_*`, `ALERT_EMAIL_*`, `runJob`, `job_runs`, advisory locks, `LISTEN generation_requests`.

### Arquitectura del Servicio

- **Tipo:** worker (node). Vive en `apps/generator`. Nombre del paquete: `generator` (filtros: `pnpm --filter generator ...`).
- **Propósito (overview):** worker siempre activo, **sin interfaz de red**, que produce el contenido de nerdose (`fill`, regeneración por cola, `sync_banks`, alertas). Su única salida de red es SMTP. En esta story **no** se implementa ningún job: solo el esqueleto de ejecución sobre el que se registrarán.
- **Módulos de dominio (manifest):** `challenge-publishing`, `content-banks`. Ninguno se implementa en esta story (no se crea `src/domain/` vacío).
- **Convenciones activas usadas en esta story:** `_base`, `scheduler-jobs`, `env-config`, `logging`, `orm`, `testing`, `error-handling`. No aplican todavía: `validation`, `alerts-mail`, `generation-queue`, `challenge-generation`, `code-runner`, `content-sync`.

├── vitest.config.ts

> La convención `scheduler-jobs` prevé además `scheduler/run-job.ts` y `scheduler/jobs/*.job.ts`. Se crean con el primer job (`sync_banks` / `fill`), no en esta story.

**Patrones:**
- Fábricas en lugar de singletons con efectos al importar (`loadEnv`, `createLogger`, `createDatabase`, `startScheduler`, `createShutdownHandler`), para testear con entornos, destinos y dependencias propias. Es la forma ya usada en `apps/api`.
- `startScheduler(deps)` recibe sus dependencias inyectadas (`scheduler-jobs`).
- El tiempo de los jobs vendrá de un `clock` inyectable (`scheduler-jobs`); en esta story no hay jobs, así que no se introduce todavía.

**Manejo de errores (`error-handling`, worker):** no hay HTTP. El mismo modelo `AppError` se usa para fallos esperados (aquí: entorno inválido → `AppError('validation_error')`). Ningún error llega a un cliente: se loguea. Los errores de arranque que impiden funcionar (entorno inválido, base caída) terminan el proceso con código 1; un error de un job (futuro) nunca mata el proceso.

**Logging (`logging`):** un único logger Pino por servicio; primer argumento objeto de contexto, segundo argumento mensaje corto y **estático** en inglés (sin interpolar); nunca se loguean secretos (la `DATABASE_URL` incluye contraseña: **no se loguea**); child logger por job (`{ job }`) cuando existan jobs; en tests `LOG_LEVEL=silent` o un destino de captura.

### ADRs Relevantes

#### ADR-001: Mapa de servicios
- **Decisión:** 4 servicios (`web`, `admin`, `api`, `generator`) y un PostgreSQL compartido, sin bus ni Redis. El `generator` no tiene puerto.
- **Reglas de Implementación (verbatim):**
  - Los servicios MUST ser exactamente `web`, `admin`, `api` y `generator`, en `apps/web`, `apps/admin`, `apps/api` y `apps/generator`.
  - `api` MUST ser la única interfaz HTTP del backend. `generator` MUST NOT abrir ningún puerto ni exponer endpoints.
  - `api` MUST NOT ejecutar código (no `child_process`, `vm`, `eval` ni equivalentes) y MUST NOT llamar a APIs externas, salvo el envío de mail de alertas (ADR-013).
  - `generator` MUST ser el único proceso que hace `INSERT` en `challenges`, `terms` y `timeline_facts`.
  - `web` y `admin` MUST hablar solo con `api` (más Plausible en `web`, si está activo). MUST NOT acceder a la base.
  - MUST NOT agregarse Redis, RabbitMQ, Kafka, BullMQ ni ningún broker en v1.
  - Debe haber una sola instancia de `api` en v1. Las caches y el rate limit en memoria dependen de eso (ADR-012).
- **Aplicación en esta story:** el código de `apps/generator/src` MUST NOT importar `node:http`, `node:https`, `node:net`, `hono` ni `@hono/node-server`, y no tiene variable `PORT` (TS-27).

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)
- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `api` y `generator` MUST correr en Node.js 24 LTS. `engines.node` MUST ser `">=24 <25"`.
- Todo acceso a la base MUST pasar por Drizzle ORM con el driver postgres.js. SQL crudo solo en migraciones, en las vistas `metrics_*` y donde Drizzle no lo soporte (`LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`).
- El PRNG del `generator` MUST ser `pure-rand` (xoroshiro128+). MUST NOT usarse `Math.random()` en la generación de desafíos.
- Los tests MUST usar Vitest; los e2e, Playwright.
- **Aplicación en esta story:** `SELECT current_user` es introspección sin tablas, sin nada que Drizzle modele; se ejecuta con el tagged template `sql` de postgres.js devuelto por `createDb`, con un comentario de una línea (mismo criterio que la `api` en S-003).

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)
- El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
- Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
- `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
- `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.
- **Ya aplicado en la raíz:** `pnpm-workspace.yaml` incluye `apps/*`; `eslint.config.js` ya tiene el bloque `files: ['apps/generator/**']` que prohíbe `@nerdose/game-*/client` e imports desde otras apps; `test/eslint-boundaries.test.ts` ya cubre `apps/generator`; `test/repo-hygiene.test.ts` ya verifica que `apps/generator/.env.test` esté ignorado.
- **Consecuencia:** el código de `apps/api` (logger, `withTimeout`, `verifyDbRole`, helpers de test) se **replica** en `apps/generator`, no se importa. Mover esas piezas a un paquete compartido no está documentado y queda fuera de alcance.

#### ADR-004: PostgreSQL como única base, con propiedad por roles (reglas aplicables, verbatim)
- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
- Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db`, con permisos por columna sobre `challenges`, `terms` y `timeline_facts` exactamente como en la tabla de arriba. (Ya hecho para esta etapa en S-002: `0000_roles_and_grants`.)

#### ADR-007: Generator como worker siempre activo y pipeline de generación
- **Decisión:** el `generator` es un worker long-running con un scheduler interno (croner, expresiones cron en UTC), que también escucha `generation_requests` (ADR-005). Jobs: `fill` (`10 * * * *`) y `sync_banks` (al arrancar).
- **Reglas de Implementación aplicables a esta story (verbatim):**
  - `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
  - El `generator` MUST NOT hacer requests HTTP a servicios externos. Su única salida de red es SMTP (ADR-013).
  - El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.
- **Reglas que aplican cuando se registren jobs (no en esta story, verbatim, para contexto):**
  - `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
  - Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
  - Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
  - Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.

#### ADR-005: Comunicación api-generator por PostgreSQL (regla aplicable, verbatim)
- `api` y `generator` MUST NOT comunicarse por HTTP, sockets ni archivos. Toda coordinación MUST pasar por tablas de `nerdose-db`.
- **Aplicación:** en esta story no hay coordinación. Más adelante, la conexión `LISTEN` de `generation-queue` reemplaza al timer de keep-alive como handle que mantiene vivo el proceso (decisión 9 de REQ-001).

### Convenciones activas (extracto aplicable)

#### `scheduler-jobs` (croner) — configuración de referencia y reglas aplicables

Forma de referencia de la convención (con jobs; en esta story la lista está vacía):

```ts
// apps/generator/src/scheduler/scheduler.ts
import { Cron } from 'croner';

export function startScheduler(deps: Deps) {
  const fill = new Cron('10 * * * *', { timezone: 'UTC', protect: true }, () => runJob('fill', fillJob, deps));
  return { stop: () => fill.stop() };
}
```

Apagado ordenado de referencia:

```ts
process.on('SIGTERM', async () => {
  shutdown.abort();               // the running candidate finishes; no new one starts
  scheduler.stop();
  await queueListener.stop();
  await running;                  // wait for in-flight job; locks are released in `finally`
  await sql.end();
  process.exit(0);
});
```

En esta story no hay `queueListener` ni `running`: el handler queda en `shutdown.abort()` → `scheduler.stop()` → `await sql.end()` → log `Shutdown complete` → `process.exit(0)` (Flujo de la story y Escenario 3 de REQ-001).

Reglas aplicables (verbatim):
- The `generator` runs as a long-running process. It never depends on system cron or an external scheduler.
- Overlapping runs of the same job inside one process are prevented (`protect: true`) in addition to the advisory lock.
- On `SIGTERM` the current candidate finishes, no new work starts and the locks are released.
- The `generator` opens no port and exposes no endpoint. Its only network output is SMTP.
- Time comes from an injectable `clock`; jobs never call `new Date()` directly.
- Use child loggers per job (`{ job }`) and per candidate (`{ game_id, date, attempt }`).

**Decisión 9 de REQ-001 (keep-alive):** si croner no tiene jobs, no hay ningún handle activo y Node terminaría solo. `startScheduler(deps)` registra la lista de jobs (vacía) y mantiene un handle (un timer) hasta `stop()`. Más adelante, la conexión `LISTEN` de `generation-queue` cumple ese papel.

#### `logging` (Pino) — configuración de referencia

Forma ya implementada en `apps/api/src/shared/logger.ts` (replicar; `SERVICE_NAME` por defecto `generator`):

```ts
export function createLogger(
  env: Pick<GeneratorEnv, 'LOG_LEVEL' | 'SERVICE_NAME' | 'NODE_ENV'>,
  destination?: pino.DestinationStream,
) {
  const options: pino.LoggerOptions = {
    level: env.LOG_LEVEL,
    base: { service: env.SERVICE_NAME, env: env.NODE_ENV },
    timestamp: pino.stdTimeFunctions.isoTime,
    formatters: { level: (label) => ({ level: label }) },
    redact: {
      paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token', '*.refreshToken', '*.apiKey', 'password'],
      censor: '[REDACTED]',
    },
    transport:
      env.NODE_ENV === 'development' && !destination
        ? { target: 'pino-pretty', options: { colorize: true } }
        : undefined,
  };
  return destination ? pino(options, destination) : pino(options);
}
```

Reglas: un logger por servicio; mensajes estáticos; errores esperados (`AppError`) en `warn`/`info` sin stack, inesperados en `error` con stack; nunca secretos.

### Contexto de Base de Datos

- **Sin cambios de schema ni migraciones.** No hay tablas de negocio todavía.
- **Estado de la base tras S-002** (`packages/db/migrations/0000_roles_and_grants.sql`):

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'nerdose_api') THEN
    CREATE ROLE nerdose_api LOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'nerdose_generator') THEN
    CREATE ROLE nerdose_generator LOGIN;
  END IF;
END $$;
--> statement-breakpoint
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
--> statement-breakpoint
GRANT USAGE ON SCHEMA public TO nerdose_api, nerdose_generator;
--> statement-breakpoint
DO $$ BEGIN
  EXECUTE format('REVOKE CREATE, TEMPORARY ON DATABASE %I FROM PUBLIC', current_database());
  EXECUTE format('GRANT CONNECT ON DATABASE %I TO nerdose_api, nerdose_generator', current_database());
END $$;
```

- `nerdose_generator` tiene `CONNECT` sobre la base y `USAGE` sobre `public`: alcanza para `SELECT current_user`.
- **Única consulta de esta story:** `SELECT current_user` (verificación del rol al arrancar, decisión 11 de REQ-001), con timeout de 2 s. Comentario de una línea: "Introspección sin tablas: no hay nada que Drizzle modele."
- **Pool:** `createDb(url)` usa `max: 10` por defecto.
- **En local** la contraseña de `nerdose_generator` la fija `pnpm --filter @nerdose/db db:migrate` desde `DATABASE_URL_GENERATOR` (S-002). La `DATABASE_URL` del `generator` debe usar el mismo usuario y contraseña: `postgres://nerdose_generator:<password>@127.0.0.1:5432/nerdose`.

### Contexto de Flujos

Ninguno de `docs/flows/` (la story declara "Flujos Afectados: Ninguno"). Los flujos de arranque y apagado están en REQ-001 (copiados en lo que aplica al `generator`):

**Arranque del `generator`** (REQ-001, Escenario 1, paso 5):
1. `env.ts` valida el entorno; si falta o es inválida una variable, aborta antes de abrir conexiones, con código ≠ 0 y un mensaje que nombra la variable (Escenario 4).
2. `createDb(env.DATABASE_URL)`.
3. `SELECT current_user` y log `{ db_role: 'nerdose_generator' }`. **Si la base no responde, el proceso aborta con código 1 y un mensaje claro: no puede hacer nada sin base** (decisión 11).
4. `startScheduler(deps)` y log `Scheduler started` con `{ jobs: 0 }`. No se ejecuta ningún job.

**Apagado ordenado del `generator`** (REQ-001, Escenario 3) — Trigger: `SIGTERM` (Ctrl+C en `pnpm dev` o `kill`):
1. `shutdown.abort()`;
2. `scheduler.stop()`, que libera el handle de keep-alive;
3. `await sql.end()`;
4. log `Shutdown complete`;
5. `process.exit(0)`.

Manejo de errores:
- Si `sql.end()` falla, se registra el error y el proceso sale igual con 0, porque el cierre fue pedido.
- Un segundo `SIGTERM` durante el apagado no reinicia el apagado (el handler es idempotente).

**Riesgo (story):** `turbo run dev` corta todas las tareas si el `generator` falla por no tener base; el README (S-005) indica el orden de arranque (`docker compose up -d` → `db:migrate` → `pnpm dev`). El `generator` explica por qué abortó (log `fatal`).
