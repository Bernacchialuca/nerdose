### Arquitectura del Servicio (`docs/architectures/web/overview.md`, copiado lo aplicable)

- SPA de los jugadores de nerdose (`nerdose.dev`). Mobile-first desde 320 px, accesible (WCAG 2.1 AA), se juega completa con teclado. Nunca tiene la solución antes de que termine la partida: la `api` es la dueña de la verdad y valida cada jugada.
- **shell** — layout, header, banners, rutas y manejo global de errores. Sin lógica por juego.
- **catalog** — home (`/`): estado de hoy de los 5 juegos, racha global y cuenta regresiva al próximo día.
- **game-host** — `/:game_id`: carga con `React.lazy` el `client` del juego (`packages/games/<game_id>/client`) mediante un registry; instrucciones, partida, resultado y share.
- **session** — sesión anónima (`POST /api/session`, cookie `nd_pid` gestionada por la `api`), preferencias (idioma) y aviso de cookies bloqueadas.
- Cliente HTTP de mismo origen (`/api/*`), JSON en `snake_case` sin transformar y errores por `error.code` (ADR-015).
- Analítica opcional con `track()` de `@nerdose/ui` detrás de `VITE_PLAUSIBLE_DOMAIN`, apagada por defecto (ADR-014).
- Contextos de React a nivel app: solo el de sesión/preferencias (locale) además del `QueryClientProvider`.
- **Contrato de props de los `client`:** ADR-006 solo define que cada `client` exporta `Instructions`, `Game`, `Result` y `share(result, number)`; las props las fija el paquete del juego (ver "Integration Points").
- **Reloj del día:** el cliente no calcula "hoy": usa `number`, `next_reset_at` y `seconds_to_reset` de `GET /api/today` y espera 0–3 s al azar antes de pedir de nuevo al llegar a 0 (ADR-008).
- **Almacenamiento del navegador:** solo conveniencias por visitante (nunca solución, estado de partida ni tokens).

### Convenciones activas (copiadas, partes aplicables)

**`_base`:**
- SPA Vite, sin SSR. Código pesado o por feature se divide con `React.lazy` + `import()` dinámico.
- Estructura: `app/` solo wiring (providers, router, layout), sin lógica de negocio; `modules/{module}/{routes,components,api,index.ts}`; un módulo **nunca** importa internals de otro módulo: usa su `index.ts` o pasa por `lib/` o un paquete compartido; `lib/` sin JSX; `hooks/` hooks genéricos.
- Fronteras: paquetes internos por nombre (`@nerdose/core`, `@nerdose/ui`, `@nerdose/game-<game_id>/client`). De un paquete de juego solo se importa `./client`. Nunca `@nerdose/db`, `@nerdose/polyglot`, `@nerdose/content`.
- Naming: archivos `kebab-case`; componentes `PascalCase`; hooks `use-*.ts` → `useX`; query keys por factory (`todayKeys.all`); tipos `PascalCase`; constantes `SCREAMING_SNAKE_CASE`; campos de API `snake_case` tal cual (`challenge_number`, `seconds_to_reset`).
- Imports: absolutos con `@/*`; orden (1) externas y `@nerdose/*`, (2) `@/`, (3) relativos; `import type` para tipos.
- Variables de entorno: **todo** acceso a `import.meta.env` en `src/lib/env.ts`, validado con Zod al cargar el módulo. Solo `VITE_*`. Conocidas: `VITE_PLAUSIBLE_DOMAIN` y `VITE_PLAUSIBLE_SCRIPT_URL` (la URL es obligatoria solo si hay dominio).
- Fechas: el cliente **nunca decide qué día es hoy**; las cuentas regresivas usan `seconds_to_reset`.
- Async: `async/await`; componentes nunca `async`; una promesa rechazada sin manejar es un bug.
- Comentarios: solo el porqué no obvio; sin `// TODO` sin issue.

**`routing`:**
- Todas las rutas en `src/app/router.tsx`. Toda ruta de componente es lazy (`lazy` o `React.lazy`). El shell y la home son la única UI eager.
- `/:game_id` → `game-host`; `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`; cualquier otro renderiza la 404.
- ```tsx
  const { game_id } = useParams();
  if (!isGameId(game_id)) return <NotFound />;   // isGameId de @nerdose/core
  ```
- El código de un juego se carga solo cuando se abre su ruta; la home nunca importa el `client` de un juego.
- Componentes de ruta finos: componen componentes del módulo y leen params; la lógica vive en hooks del módulo.
- Sin `if`/`switch` por juego en el router ni en el shell; decide el registry.
- Al cambiar de ruta, mover el foco al `<h1>` (o al landmark `main`) y actualizar `document.title`.
- Cambio de día: la URL no cambia; al llegar a 0 el catálogo y el juego abierto re-piden sus queries.

**`data-fetching`:**
- `fetch` solo desde `lib/api-client.ts` (`api<T>(path, { method, json })`). Respuestas sin transformar (`snake_case`). URLs relativas `/api/...`.
- Datos del servidor solo en TanStack Query, nunca copiados a `useState`/context. Una factory de keys por módulo.
- Mutaciones invalidan lo que dejan viejo; **no editan caches a mano salvo que la respuesta traiga el estado nuevo** (`POST …/start` y `POST …/move` lo traen).
- Mutaciones de una partida incluyen `challenge_number`; el cliente nunca manda fechas. Sin `retry` en mutaciones.
- Validar la jugada con el `moveSchema` del juego antes de enviar (lo hace el client: `onMove` ya recibe un `DevdleMove` validado); igual manejar `422 invalid_move`.
- Ramificar por `ApiError.code`, nunca por `message` ni solo por status.
- Ejemplo de la convención (forma de referencia):
  ```ts
  export function useSubmitMove(gameId: GameId) {
    const qc = useQueryClient();
    return useMutation({
      mutationFn: (move: unknown) =>
        api<MoveResponse>(`/api/games/${gameId}/today/move`, { method: 'POST', json: move }),
      onSuccess: (res) => {
        if (res.result !== null) { // the move closed the round
          qc.invalidateQueries({ queryKey: todayKeys.all });
          qc.invalidateQueries({ queryKey: ['me', 'stats'] });
        }
      },
    });
  }
  ```

**`error-handling` (variante `web`):**

| `code` | Recuperación en `web` |
|---|---|
| `challenge_expired` | Invalidar `today` y la query del juego y recargar el desafío; aviso corto de "desafío nuevo" |
| `challenge_voided` | La vista del juego pasa al estado anulado (`acknowledge-void` es FG-6) |
| `game_finished` | Re-pedir el estado de la partida y mostrar el resultado |
| `no_challenge_today` | Estado "sin desafío hoy" |
| `no_session` | Llamar `POST /api/session` una vez y reintentar; si sigue sin sesión, aviso de cookies bloqueadas y juego deshabilitado |
| `not_in_word_list` (Devdle) | Mensaje inline; no consume intento |
| `invalid_move`, `validation_error` | Mensaje inline en el control; sin navegación |
| `rate_limited` | Mensaje con la espera de `Retry-After`; no consume intento |
| `internal_error`, red | Retry inline, o la pantalla de error de ruta si falló toda la vista |

- Cada estado de error tiene salida (reintentar, ir a la home o mensaje explicativo); se anuncian (`role="alert"` o `aria-live`) y no dependen solo del color. Nunca stack traces ni JSON crudo. Sin servicio de error tracking: solo consola.

**`game-clients`:**
- Registry en `src/modules/game-host/registry.ts` (`game_id` → `import()` de la entrada `./client`). Es el **único** lugar que lista juegos. La story pide registry **parcial**: `Partial<Record<GameId, () => Promise<GameClient>>>` (REQ-004 decisión 13).
- El host pide la vista pública y el estado con TanStack Query (`/api/games/{game_id}/today`) y los pasa a los componentes del client; el shell no lee campos propios del juego.
- Share: `share(result, number)` produce el texto; el shell llama `navigator.share({ text })` si existe y si no `navigator.clipboard.writeText`, con confirmación visible; después `track('share:<game_id>')`. **El texto nunca lo arma el shell.**
- Cada juego es su propio chunk (`import()` dinámico). Sumar un juego = paquete + línea en el registry + traducciones.

**`state-management`:** server data en Query; identidad de pantalla en la URL (`/:game_id`); estado efímero en el componente (`useState`): aviso «día nuevo», anulado durante la partida, último error de jugada, «✓ Copiado»; valores derivados se calculan en render; `useEffect` no sincroniza un estado con otro.

**`i18n`:** todo texto de UI por `t()`; mismas claves en `es` y `en`; plurales con `_one`/`_other`; interpolación, nunca concatenación. Los paquetes de juego traen sus textos en un namespace propio (`devdle`) que se registra en la misma instancia de i18next. El contenido (`definition`, `summary`) y los `message` de error llegan resueltos de la `api`.

**`analytics`:** solo `track()` de `@nerdose/ui`; único evento `share:<game_id>` sin propiedades; se dispara **después** de que `navigator.share` o el copiado al portapapeles tengan éxito. Nunca `window.plausible` fuera del helper. Con `VITE_PLAUSIBLE_DOMAIN` vacío: sin script y `track()` no-op. Con valor: script con `defer` y `data-domain` desde `VITE_PLAUSIBLE_SCRIPT_URL`.

**`styling` (+ actualización REQ-003):** solo tokens de `@nerdose/ui` (sin hex, sin `[#…]`, sin valores arbitrarios `/\[(\d|#|rgb)/`, sin `rounded-md|shadow-md|text-2xl|font-semibold`); `cn()` para clases condicionales; mobile-first desde 320 px sin scroll horizontal; targets ≥ 44×44; foco visible `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-accent`; sin media queries globales: `flex-wrap` y `repeat(auto-fit, minmax(min(Npx, 100%), 1fr))`; contenedor `max-w-page` (1240) con gutter 32 (`px-8`); botones y links con `buttonClass(...)` / `linkClass(...)`; respetar `prefers-reduced-motion`.

**`accessibility`:** un `<main>`, landmarks header/nav/footer, un `<h1>` por pantalla; controles nativos; estado no solo por color; resultado, errores y avisos en `role="status"` / `role="alert"`; al navegar, foco al heading y `document.title`; cada juego completable solo con teclado (NFR-U03); axe sin violaciones.

**`testing-unit`:** consultas por rol/label/texto; `userEvent`; axe en cada componente interactivo; red con MSW (`snake_case`, error `{ error: { code, message } }`); sin mockear módulos propios salvo para aislar una unidad; timers falsos para cuenta regresiva y jitter; sin snapshots grandes.

**`testing-e2e`:** Playwright no está instalado en `apps/web` (precedente S-013). Este plan **no** lo agrega: los criterios de 320 px, teclado y axe se cubren con tests unitarios de ruta completa (jsdom), guardas estáticas y verificación manual (ver TS-56).

### ADRs Relevantes

#### ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables
- **Decisión:** cada juego es un paquete con `./definition`, `./client` (`Instructions`, `Game`, `Result`, `share(result, number)`) y `./generator`; las apps los resuelven por registry.
- **Reglas de Implementación (verbatim, aplicables):**
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

#### ADR-008: Día de la plataforma y publicación (reglas aplicables, verbatim)
- Los bodies de `POST /api/games/{game_id}/today/start`, `/move`, `/report` y `/acknowledge-void` MUST incluir `challenge_number` (entero ≥ 1).
- Si `challenge_number ≠ number` de hoy, la `api` MUST responder `409` con `{ "error": { "code": "challenge_expired", … } }`.
- Una Play `in_progress` de un día pasado MUST quedar `in_progress` para siempre y no contar como completada.
- `GET /api/today` MUST devolver `next_reset_at` (próxima 00:00 UTC, ISO 8601) y `seconds_to_reset`. Al llegar a 0, el front MUST esperar 0–3 s al azar antes de volver a pedir.

#### ADR-009: Identidad del jugador anónimo (reglas aplicables, verbatim)
- `POST /api/session` MUST ser idempotente y responder `200 { locale, preferred_code_language, created }`.
- Las rutas de jugador que lo exigen MUST responder `401` con `{ "error": { "code": "no_session", … } }` si falta la cookie o no es válida.
- Toda mutación (`POST`, `PATCH`) MUST rechazar con `415` un `Content-Type` distinto de `application/json`, y con `403 forbidden_origin` un header `Origin` ausente o distinto del permitido […]. (El wrapper `api()` ya manda `Content-Type: application/json` cuando hay `json`; el `Origin` lo pone el navegador.)

#### ADR-014: Métricas y analítica (reglas aplicables, verbatim)
- `web` MUST llamar solo a `track(event)` de `@nerdose/ui`. MUST NOT referenciar `window.plausible` fuera de ese helper.
- Si `VITE_PLAUSIBLE_DOMAIN` está vacío, el build MUST NOT inyectar el script de Plausible y `track()` MUST ser un no-op.
- Si `VITE_PLAUSIBLE_DOMAIN` tiene valor, `VITE_PLAUSIBLE_SCRIPT_URL` MUST ser obligatoria (el build falla si falta), y el script MUST inyectarse con `defer` y `data-domain`.
- El evento de share MUST llamarse exactamente `share:<game_id>` (por ejemplo `share:devdle`) y MUST NOT llevar propiedades personalizadas.

#### ADR-015: Contratos JSON y errores (reglas aplicables, verbatim)
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` […]. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo […].
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.

### API Context

Story: "Cambios de API: Ninguno". Consume (copiado de `docs/apis/api.yaml`):

**`GET /api/today?lang={es|en}`** → `200 Today` (ya implementado en `catalog`):
```yaml
Today: { date: 'YYYY-MM-DD', number: integer|null, next_reset_at: ISO, seconds_to_reset: integer, has_session: boolean,
         global_streak: { current, max }, completed_today: integer,
         games: [ { game_id, challenge_status: published|voided|none, play_status: in_progress|won|lost|voided|null, history_label: string|null, current_streak } ] }
```

**`GET /api/games/{game_id}/today?lang={es|en}`** (cookie opcional) → `200 GameToday`; `404 not_found` (juego sin paquete en la `api`); `429 rate_limited`.
```yaml
GameToday:
  required: [game_id, date, number, challenge_status, public_view, play, result, game_stats]
  game_id: GameId
  date: string (date)
  number: integer >= 1, nullable          # null antes de LAUNCH_DATE (challenge_status none)
  challenge_status: published | voided | none
  public_view: PublicView, nullable       # null si challenge_status es none o voided
  play: PlayView, nullable                # { status: in_progress|won|lost|voided, state, score: integer|null, code_language: js|go|java|null }
  result: Result, nullable                # solo con la Play terminada
  game_stats: GameStatsView, nullable     # solo si la Play terminó
```
- `play == null` → instrucciones; `play.status == in_progress` → retoma con `play.state`; Play terminada → resultado; `challenge_status: none` → "sin desafío hoy"; `voided` → aviso de anulación.
- Ejemplo: `{ game_id: devdle, date: '2026-11-03', number: 128, challenge_status: published, public_view: { length: 5, possible_categories: [programming_languages, git, databases, networking, linux, apis, security, software_engineering] }, play: { status: in_progress, state: { guesses: [ { guess: REACT, marks: [absent, present, absent, absent, absent] } ] }, score: null, code_language: null }, result: null, game_stats: null }`

**`POST /api/games/{game_id}/today/start`** (cookie obligatoria), body `ChallengeNumberBody { challenge_number: integer >= 1 }` (ej. `{ challenge_number: 128 }`) → `200 { play: PlayView }` (ej. `{ play: { status: in_progress, state: { guesses: [] }, score: null, code_language: null } }`). Idempotente. Errores: `401 no_session`, `403 forbidden_origin`, `404 no_challenge_today | not_found`, `409 challenge_expired | challenge_voided | game_finished`, `415`, `422 validation_error`, `429 rate_limited` (30/min por jugador).

**`POST /api/games/{game_id}/today/move?lang={es|en}`** (cookie obligatoria), body `MoveRequest { challenge_number: integer >= 1, move: Move }` (Devdle: `{ challenge_number: 128, move: { guess: REACT } }`) → `200 MoveResponse`:
```yaml
MoveResponse:
  required: [feedback, play, result, streaks, game_stats]
  feedback: Feedback                       # devdle: DevdleGuess { guess, marks[] }
  play: { status, state, score }           # SIN code_language
  result: Result, nullable                 # solo si la jugada cerró la partida
  streaks: { game: { current, max }, global: { current, max } }, nullable   # solo si cerró
  game_stats: GameStatsView, nullable      # solo si cerró
```
- Ejemplo en curso: `{ feedback: { guess: REDIS, marks: [correct, correct, absent, absent, absent] }, play: { status: in_progress, state: { guesses: [ { guess: REDIS, marks: [correct, correct, absent, absent, absent] } ] }, score: null }, result: null, streaks: null, game_stats: null }`
- Errores: `401 no_session`, `403`, `404 no_challenge_today | not_found`, `409 challenge_expired | challenge_voided | game_finished`, `415`, `422 invalid_move | not_in_word_list` (Devdle, **no** consume intento), `429 rate_limited` con header `Retry-After` (60/min por jugador, 300/min por IP).

**Schemas de Devdle (los parsea el client; `web` los trata como `unknown`):**
```yaml

DevdleGuess: { guess: '^[A-Z]{4,12}$', marks: (correct|present|absent)[] }
DevdleState: { guesses: DevdleGuess[] (max 6) }
DevdleResult: { win: boolean, score: integer 1..6, word: string, category: TermCategory, definition: string, summary: string, guesses: DevdleGuess[] }

```

**Respuestas de error (ejemplos exactos de `api.yaml`):**
- `401` → `{ error: { code: no_session, message: 'Activá las cookies para jugar' } }`

**Orden de validación de `start`/`move` en la `api` (REQ-004 decisión 7):** sesión → `challenge_number == número de hoy` (si no, `409 challenge_expired`) → desafío de hoy en cache (si no, `404 no_challenge_today`) → `status != 'voided'` (`409 challenge_voided`) → `moveSchema`. #### User flows relevantes (copiados de `user-flows.md`, filtrados)

**Flujo 1 — Jugar el desafío del día (incluye retomar).** JTBD: resolver un desafío corto igual para todos y sostener el hábito. Trigger: tarjeta en `home`.

**Flujo 2 — Cambio de día con la partida abierta (`challenge_expired`).**
- Happy path: (1) partida `in_progress` del `#N`, pasa la medianoche UTC; (2) jugada con `challenge_number = N` → `challenge_expired`; (3) el front carga el desafío nuevo (`#N+1`) y vuelve a `{juego}-instrucciones` con el nuevo `#número` en el header y el aviso «Empezó el desafío #N+1. - Container `flex-wrap`, gap 16, padding 18 22, radio 14, fondo tintado + borde. Ícono en círculo 40×40 (`success` check, `failure` x, `warning` `!`, `neutral` sin ícono). Título Mono 700 18; subtítulo Inter 14. Acción: button `md` (`flex flex-wrap gap-2.5`).
- Variants: `success` / `failure` (resultado; los usa el client), `neutral` (informativo, título opcional, sin ícono, REQ-004), `warning` (condición persistente: cookies O-03; tintes `#140F07` / `#3A2A12`, subtítulo `#C9A46A`).
- Accesibilidad: `role="status"` en `success`, `failure` y `warning`; `neutral` sin rol vivo por defecto (`announce` lo activa). El contenedor no es focusable; la acción sí. Sin depender del color.
- `warning` (O-03): va bajo el header, dentro del contenedor de página (1240, gutter 32), 24px bajo el header.
- **Don't: no poner más de un banner a la vez** (por eso D3 fusiona veredicto + alerta-anulado del resultado anulado; los avisos `día nuevo` + `sin desafío` coexisten porque el `screen.md` lo pide explícitamente: «Si el día nuevo no tiene desafío, se muestra junto a `alerta-sin-desafio`»).

**`alert` v-actual:** solo errores del sistema; `role="alert"` (se anuncia al aparecer); foco no se mueve; ícono `x` + título con texto; acción `outline-tinted`/`secondary` `md`; va en el lugar del contenido que falló; no más de una Alert a la vez; contenido: qué pasó + qué hacer («No pudimos cargar…» + «Reintentar»), sin códigos técnicos.

**`button` v1.3.0 (aplicable):** `accent` = acción principal dentro del contexto de un juego (relleno con el acento): «Jugar →», **Compartir activo**, Confirmar. **Compartir es `accent` (tamaño `share`: 44px alto, padding 14, gap 8) con ícono `share`: activo al terminar, deshabilitado durante el juego.** `icon` = 44×44 solo-ícono, `aria-label` obligatorio, SVG `aria-hidden`. `secondary` = outline, texto `text.primary`. Deshabilitado = neutro sin hover; el consumidor pone `aria-disabled="true"` y bloquea la acción (el control sigue siendo focusable). Do: `primary` (verde) para avanzar de juego.

**`streak-pill`:** ámbar con ícono de llama; `value` 0 o `null` → píldora gris neutra; sin `render` → `<span>`.

**`language-selector`:** `SegmentedControl` ES/EN (`role="group"`, botones `aria-pressed`, 44×44).

**`site-footer`:** una sola línea (lema + `exit 0`), del shell, igual en todas las pantallas.

### Decisiones de este plan (derivadas, sin inventar contrato)

| # | Decisión | Por qué |
|---|---|---|
| D1 | **Header por `handle` de ruta.** `routes/game.tsx` exporta `handle: ShellHandle = { header: (params) => ReactNode \| null }`. `Shell` lee `useMatches()`; si el último match con `handle.header` devuelve un nodo, lo renderiza en lugar de `AppHeader` y **no** pinta su banner genérico de cookies (la pantalla de juego tiene su `banner-cookies` con «Reintentar»). Para `game_id` inválido el `header` devuelve `null` → `AppHeader` + 404. | El header tiene que quedar fuera de `<main>` (landmark `banner`) y necesita datos del módulo `game-host`; así `app/` no importa nada de `game-host` (TS-50 se mantiene), el shell no tiene lógica por juego y el código de juego sigue en el chunk lazy. |
| D2 | **Un solo texto de loader:** `$ cargando {slug}…` («$ cargando devdle…»). | Mientras carga `GET …/today` no se sabe la fase (instrucciones/partida/resultado). El cambio de idioma no muestra loader (D7). |
| D3 | **Resultado anulado** (desafío `voided` con Play `won`/`lost`, o Play `voided`): `web` pinta **un** `Banner` `warning` con `titleAs="h1"`, título «Desafío anulado» y detalle «Este desafío tenía un error y fue anulado. Tu racha no se ve afectada.», `card-rachas` (si hay `game_stats`) y la fila de salidas. No monta `Result` (el plan `games` lo fija así) → no hay `card-palabra` en este estado. | Fusiona `veredicto` + `alerta-anulado` respetando «no más de un banner a la vez»; el `screen.md` anota que la anulación llega con FG-6 y que en REQ-004 solo se respeta el estado al leer. |
| D4 | **O-02 y `acknowledge-void` quedan para FG-6.** En instrucciones anulado solo se muestra `alerta-anulado` + «Volver a los juegos». | O-02 crea la Play `voided` vía `POST …/acknowledge-void`, que la story no consume ("Consume `GET /api/today`, `GET …/today`, `POST …/start` y `POST …/move`"). |
| D5 | **`btn-compartir` = `buttonClass({ variant: 'accent', game, size: 'share' })`**, no `primary`. | `button.md`: «Compartir es `accent` (tamaño `share`)»; el DS manda sobre el wireframe en estética. Para Devdle el color es el mismo verde. |
| D6 | **Foco al heading con `focusMainHeading()`** (`lib/focus-main-heading.ts`): busca `main h1`, le pone `tabindex="-1"` si no tiene y lo enfoca. Lo usan el `Shell` (cambio de pathname) y `game-host` (cambio de fase, salvo la primera fase tras una carga directa, `location.key === 'default'`). | Los `h1` del client no tienen `tabIndex`: sin esto el foco del shell no ocurre. | D7 | **Cambio de idioma sin loader:** `useGameToday` usa `placeholderData: keepPreviousData`; la key incluye el locale. | Cambiar ES/EN no debe perder ni vaciar el tablero (screen.md). |
| D8 | **`card-rachas`** lee `game_stats.current_streak` / `game_stats.max_streak` (de `GameToday` o del `MoveResponse` de cierre) y `today.global_streak.current` de `useToday()`. | `GameToday` no trae `streaks`; `game_stats` es la "racha viva" y `today` se invalida al cerrar, así que la global queda actualizada (CA-6). |
| D9 | **Sesión `unavailable`** (429 al crear sesión): «Empezar» deshabilitado + `Banner` `warning` con el texto existente `catalog.progress.unavailable` («No pudimos iniciar tu sesión. Recargá en unos minutos para jugar.»), sin «Reintentar». | El texto de cookies sería falso para un 429; la home ya resolvió este estado así (REQ-002 CA 13). |
| D10 | **`no_session` en una mutación:** `withSessionRetry` llama `createSession()` una vez y reintenta; si vuelve `no_session`, la pantalla pasa a `sin sesión`. «Reintentar» hace lo mismo manualmente e invalida `todayKeys.all` para que `useSession().status` se recalcule. | Convención `error-handling` («Call POST /api/session once and retry; if still without session, show the blocked-cookies notice»). |
| D11 | **Registro de i18n del juego al cargar el client:** `loadGameClient` (memoizado) hace `i18n.addResourceBundle(lng, client.i18n.namespace, client.i18n.resources[lng], true, true)` para `es` y `en` antes de resolver. | Contrato del client; un solo lugar, sin lógica por juego. |
| D12 | **Carga del client:** el cuerpo usa `React.lazy` (memoizado por `game_id`) sobre `loadGameClient(gameId)`; el Compartir del header usa `use(loadGameClient(gameId))` dentro de su propio `<Suspense>`. Ambos comparten la misma promesa → un solo chunk. | ADR-002: «Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`». |
| D13 | **Juego válido sin client** (`/timeline`, …): pantalla `sin desafío hoy` armada por `web` (h1 con `games.{id}.name`, `alerta-sin-desafio`, «Volver a los juegos») **sin** llamar a la `api`; header de juego sin «Cómo se juega». | REQ-004 decisión 13 / CA-8. |
| D14 | **Enlaces a `/stats`** (header y `link-stats`) apuntan a `/stats` aunque la ruta llegue en FG-10 (hoy cae en la 404). | Mismo criterio que `GlobalStreakPill` (S-013); no se inventa una pantalla. |

### Tarea 4: Vista derivada de la pantalla de juego (`deriveGameView`) y mapeo de errores

**Status:** Completed
**Categoría:** Logic

#### Descripción

Función pura que decide qué pantalla y qué bloques de `web` se muestran a partir de: si hay client, el estado de la query, el estado de la sesión, el error de la última mutación y el estado efímero de la ruta (aviso «día nuevo», anulado durante la partida). #### Criterios de Aceptación

     hasClient: boolean;
     query: { data: GameToday | undefined; isPending: boolean; isError: boolean; error: unknown };
     sessionStatus: SessionStatus;
     dayChanged: boolean;            // llegó challenge_expired y todavía no se tocó «Empezar»
     voidedDuringPlay: boolean;      // un move respondió challenge_voided
     actionError: unknown;           // error de la última mutación (start o move)
   };
   type Session = 'ok' | 'noSession' | 'unavailable';
   type GameView =
     | { kind: 'noClient' }
     | { kind: 'loading' }
     | { kind: 'loadError' }
     | { kind: 'noChallenge'; number: number | null; dayChanged: boolean }
     | { kind: 'voided'; number: number | null }
     | { kind: 'voidedResult'; number: number | null; gameStats: GameStatsView | null }
     | { kind: 'instructions'; number: number; dayChanged: boolean; session: Session }
     | { kind: 'playing'; number: number; publicView: unknown; state: unknown; locked: boolean; moveError: MoveErrorInfo | null; session: Session; moveFailed: boolean }
