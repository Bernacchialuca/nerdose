# Story Plan: S-030 (core) - Base de reportes y recálculo de agregados en core

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-030](../stories/S-030.base-reportes-recalculo-core.md)
- **Servicio:** core
- **Resumen:** Agrega a `@nerdose/core` (`packages/core`) el recálculo de agregados desde el historial: `replayStreak(completedDays, activeDays)` y `rebuildGameStats(game, plays)` en `streaks.ts`, sin tocar `nextStreak` ni `liveStreak`. También suma el miembro `culprits(p)` al contrato `GameDefinition` (con los tipos `Culprit` y `CulpritKind`) y el código `invalid_culprit` (422) al `ERROR_CATALOG`, con sus mensajes ES/EN en la `api`. Es la base del reporte del jugador (S-031) y de la anulación desde el admin (S-032).

> **Alcance de este plan:** solo el servicio `core` (`packages/core`), más el ajuste mínimo y obligatorio en `apps/api` que provoca el código de error nuevo (ver la decisión 4). La story también afecta a `db` (ya **Completed**, plan `S-030.db.*`) y a `games`, que implementa `culprits(p)` en Devdle, Grep Grid y Timeline y tiene su propio plan. Acá se cubren **CA-3** completo, la parte de contrato de **CA-4** (el tipo y el miembro de `GameDefinition`; las implementaciones por juego son del plan de `games`) y **CA-5** completo.
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a `packages/core/`, salvo que se indique otra cosa.
>
> **Estado de partida (verificado al planificar):**
> - `REPORT_REASONS`, `ReportReason`, `REPORT_STATUSES` y `ReportStatus` **ya existen** en `src/enums.ts` y se exportan desde `src/index.ts`. Los agregó el plan de `db` (commit `c951810`, decisión 1 de ese plan), con test en `test/enums.test.ts` ("lists REPORT_REASONS and REPORT_STATUSES (S-030)"). En este plan solo se suman tests de tipos y se verifica. No se reescriben.
> - `ERROR_CATALOG` tiene 21 códigos y **no** incluye `invalid_culprit`. La convención `error-handling` de `core` (ya actualizada) y `docs/apis/api.yaml` (`Error.code`, l. 1156) sí lo incluyen.
> - `GameDefinition` no tiene `culprits`. `src/streaks.ts` tiene solo `nextStreak`, `liveStreak` y `StreakInput`.

### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **Tipos del culpable en `core`.** REQ-007 (decisión 3) define la firma `culprits(p): Array<{ kind: 'term' | 'timeline_fact'; id: string; label: string }>`, y `api.yaml` (`AdminChallenge.culprits.items`) tiene la misma forma: `kind` enum `[term, timeline_fact]`, `id` uuid y `label` string. Se le pone nombre a esa forma para que `api`, `games` y `admin` no la redeclaren:
   ```ts
   export type CulpritKind = 'term' | 'timeline_fact';
   export interface Culprit { kind: CulpritKind; id: string; label: string }
   ```
   Viven en `src/game-definition.ts`, junto al contrato, y se exportan **solo como tipos**. No se agrega una constante runtime `CULPRIT_KINDS` porque ningún documento la pide. El enum de `VoidRequest.culprit.kind` (`term | timeline_fact | template | none`) es de la `api` (S-032). `BankName` (`'terms' | 'timeline_facts'`) no se reutiliza: son nombres de tabla y no de `kind`.
2. **`culprits` es un miembro obligatorio del contrato.** REQ-007 lo llama "nuevo miembro del contrato" y ADR-006 exige que `./definition` implemente "todos los métodos de la interfaz". Se declara como `culprits(p: Payload): Culprit[]`, igual que los demás métodos.
   - **Consecuencia transitoria:** al cerrar este plan, `tsc` de `@nerdose/game-devdle`, `@nerdose/game-grep-grid` y `@nerdose/game-timeline` falla ("Property 'culprits' is missing") hasta que se aplique el plan de `games` de esta misma story. Los tests de Vitest de esos paquetes siguen pasando porque Vitest no typechequea. Por eso la verificación de este plan se limita a `@nerdose/core` y `@nerdose/api`, y el plan de `games` **debe** implementarse a continuación, antes de mergear la rama. La convención `game-package` dice "Changing the `GameDefinition` interface touches all five packages in the same commit": se cumple a nivel de rama/PR (los dos planes van en la misma rama `feature/S-030_*`). Si se prefiere un solo commit, el implementador de `games` puede hacer squash.
   - Big O y Bug Hunt todavía no existen como paquetes. No hay nada que tocar para ellos.
3. **Firmas exactas de `replayStreak` y `rebuildGameStats`.** REQ-007 (decisión 2) define el comportamiento. Faltaban los tipos de entrada y de salida, que se fijan así:
   ```ts
   export interface ReplayedStreak {
     current: number;
     max: number;
     lastCompleted: string | null;
   }
   export function replayStreak(
     completedDays: readonly string[],
     activeDays: readonly string[],
   ): ReplayedStreak;

   export type CompletedPlayStatus = 'won' | 'lost' | 'voided';
   export interface CompletedPlay<Result> {
     date: string;                 // 'YYYY-MM-DD'
     status: CompletedPlayStatus;
     result: Result | null;        // obligatorio si status ∈ (won, lost); se conserva al anular
   }
   export interface RebuiltGameStats<Stats> {
     played: number;
     wins: number;
     extra: Stats;
   }
   export function rebuildGameStats<Result, Stats>(
     game: { initialStats(): Stats; reduceStats(prev: Stats, r: Result): Stats },
     plays: readonly CompletedPlay<Result>[],
   ): RebuiltGameStats<Stats>;
   ```
   - `game` es estructural (los dos métodos que usa) y no `GameDefinition<…>` completo. Así acepta un `AnyGameDefinition` del registry (que es lo que tiene la `api`) y los fixtures de test, sin `any` nuevo en `core`, y `streaks.ts` no necesita importar `game-definition.ts`.
   - Los nombres de campo siguen a `StreakInput` (`current`, `lastCompleted`, en `camelCase`). La `api` mapea a `current_streak`/`max_streak`/`last_completed_date` y a `global_streak`/`max_global_streak`/`last_active_date`.
   - `replayStreak` sirve para la racha **por juego** (días completados del juego, días activos del juego) y para la **global** (días completados de todos los juegos, días activos de cualquier juego), igual que `nextStreak`.
   - `total_completed` no lo calcula `core`: es la cantidad de Play completadas de todos los juegos (REQ-007, decisión 11), un `count` que hace la `api`.
4. **`invalid_culprit` arrastra un ajuste en `apps/api`.** `apps/api/src/http/error-messages.ts` declara `MESSAGES: Record<Locale, Record<ErrorCode, string>>`. Al sumar un código, la `api` deja de compilar si no tiene su mensaje. CA-5 pide además "mensajes ES/EN". Este plan los agrega (la story no lo asigna a ningún otro plan y REQ-007 l. 460 lo pide junto con el catálogo):
   - `es`: `'El culpable no pertenece al desafío.'`
   - `en`: `'The culprit does not belong to the challenge.'`

   Los textos salen de la descripción de `api.yaml` l. 827 ("el culpable no pertenece al desafío"). No hay otra fuente de microcopy para este código. Los dos tests de la `api` que asertan `toHaveLength(21)` pasan a 22. La `api` **no** usa todavía el código: lo lanza `VoidService` en S-032.
5. **Orden de `invalid_culprit` en el catálogo.** Se inserta entre `invalid_report` y `validation_error`, exactamente como en el bloque de la convención `error-handling` de `core`. El orden importa porque `test/errors.test.ts` compara con `toEqual` el objeto completo.
6. **`rebuildGameStats` con una Play `won`/`lost` sin `result`.** La base lo prohíbe (DBML `plays.result`: "Obligatorio si status ∈ (won, lost)"), así que es una violación de invariante y no un error esperado. Se lanza `new Error('rebuildGameStats: won/lost play without result')`, con el mismo criterio que `createGameRegistry` (que lanza `Error` ante un registry inválido) y no `AppError` (no es un fallo que vea un cliente). No se valida `date` ni el formato de `status` en runtime: el tipo lo restringe y los datos vienen de la base.
7. **Orden de aplicación en `rebuildGameStats`.** Se ordena una **copia** de `plays` por `date` ascendente con un sort estable (`[...plays].sort(...)`; no `toSorted`, que es ES2023 y no está en el `lib` implícito de `target: ES2022`) y se aplica `reduceStats` en ese orden, que es el de la aplicación incremental. Dos Play del mismo juego y del mismo día no pueden existir (`uq_challenges_active_game_date` + `uq_plays_player_challenge`). La entrada nunca se muta.
8. **El oráculo del test de propiedad vive en el test.** `core` no puede importar `apps/api` (`test/core-boundaries.test.ts`), así que el test de propiedad (CA-3) reimplementa `ProgressService.applyResult` **tal como está en `apps/api/src/domain/progress/progress.service.ts`** (copiado en el Contexto de Flujos) usando el `nextStreak` real. Es un oráculo de referencia, no una segunda implementación de producción. La equivalencia contra el `applyResult` real, con base de datos, la cubre el test de integración de S-032 (REQ-007, riesgos: "test de integración con CA 17, 18 y 29").
9. **Hallazgo de documentación (no bloquea).** ADR-006 (bloque `GameDefinition`) todavía no muestra `culprits(p)` y ADR-015 no lista `invalid_culprit`. REQ-007 l. 616 indica actualizarlos. Las fuentes que **sí** están actualizadas son REQ-007 (decisiones 2 y 3), `docs/apis/api.yaml` y la convención `error-handling` de `core`. Este plan no edita ADRs (son de producto). Queda anotado en el resumen para `/product-change-technical-definition`.

```ts
// src/streaks.ts
export interface StreakInput {
  current: number;
  lastCompleted: string | null;
  prevActiveDay: string | null;
}

function continues(s: StreakInput): boolean {
  return (
    s.lastCompleted !== null && (s.prevActiveDay === null || s.lastCompleted >= s.prevActiveDay)
  );
}

/** Streak after completing `day`. `max_*` is computed by the caller with Math.max. */
export function nextStreak(input: StreakInput, day: string): number {
  if (input.lastCompleted === day) return input.current;
  return continues(input) ? input.current + 1 : 1;
}

/** Streak to display on read: 0 when it is no longer alive. Never writes. */
export function liveStreak(input: StreakInput, today: string): number {
  if (input.lastCompleted === null) return 0;
  return input.lastCompleted === today || continues(input) ? input.current : 0;
}
```

### ADRs Relevantes

#### ADR-011: Rachas con días neutros y agregados recalculables

- **Decisión (verbatim):**
  ```
  prev_active_day(game_id, D) = max(date) FROM challenges
                                WHERE game_id = :game_id AND date < D
                                  AND status IN ('published','voided')
  prev_active_day_global(D)   = el mismo max(date), sin filtrar game_id

  Al completar una Play del día D:
    game:   current_streak = (last_completed_date >= prev_active_day(game_id, D)) ? current_streak + 1 : 1
            (si last_completed_date == D, no cambia)
    global: global_streak  = (last_active_date >= prev_active_day_global(D)) ? global_streak + 1 : 1
            (si last_active_date == D, no cambia)
    max_* = max(max_*, current)
  ```
  **Recálculo** (al anular): para cada jugador afectado, se recorren sus `plays` en orden de fecha aplicando la misma función, y se excluyen las `voided` de `played`, `wins` y `extra`.
- **Reglas de Implementación (verbatim):**
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
  - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
  - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.
- **Aplicación en este plan:** `replayStreak` encadena el `nextStreak` existente (única implementación). `recomputeStats` de la `api` (S-032) se arma con `replayStreak` + `rebuildGameStats` (REQ-007 l. 616: "`replayStreak`/`rebuildGameStats` como forma de `recomputeStats`"). El test de propiedad vive acá (Tarea 5).

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)

- La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.
- **Aplicación:** `culprits(p)` entra al contrato para que la anulación valide el culpable por el registry (`game.culprits(payload)`), sin `switch` por juego en la `api` (REQ-007, decisión 3).

#### ADR-015: JSON y catálogo de errores (reglas aplicables, verbatim)

- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- **Aplicación:** `invalid_culprit` (422) entra al catálogo de `core` y a los mensajes ES/EN de la `api`.

#### ADR-003: Monorepo (regla aplicable)

- La entrada `.` de `@nerdose/core` es isomorfa: no importa `node:*`. Nada de lo que agrega este plan usa APIs de Node.

#### `testing` (verbatim, reglas aplicables)

- Unit tests are for pure functions. If it does I/O, write an integration test.
- Streak and day logic is tested with fake clocks, including neutral days, voids and the day change. `recomputeStats` has a property test with random histories against the incremental result.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Reset mocks and timers between tests (`vi.clearAllMocks()`, `vi.useRealTimers()`).
- Code under test receives `now` as a parameter or from a single `clock` helper of `@nerdose/core`; it never calls `new Date()` in domain logic.
