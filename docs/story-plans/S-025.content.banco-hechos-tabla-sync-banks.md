**`dataset-format` (custom de `content`) — reglas verbatim:**

> - Only `import:banks` and `build:wordlist` may request `*.wikidata.org`, `*.wikipedia.org` or `*.wiktionary.org`, and runtime code never imports them. `api` and `generator` never request those domains.
> - Every request sends the `User-Agent` above.
> - JSON files are written ordered by `wikidata_id`, 2-space indentation, one item per block (diff-friendly); package tests verify it.
> - `import:banks` exits with an error if there are fewer than 500 `approved` `terms` in total (not per category; `TermCategory` is the Devdle set) and prints the counts. `timeline_facts` (REQ-006) is required: `loadDataset()` fails if `timeline_facts.json` is missing; the script exits with `InsufficientTimelineFactsError` if any v1 category has fewer than 100 `approved` facts or fewer than 3 v1 categories exist. `min_sitelinks_timeline` is its own parameter. `manifest.json` carries `counts.timeline_facts { approved, rejected, by_category, by_reason }` and `parameters.timeline { min_sitelinks, min_approved_per_category, min_categories, categories_v1, classes }`. The `--bank=terms|timeline|all` flag (default `all`) limits the run. Fact `rejection_reason` codes: `disputed_date`, `imprecise_date`, `missing_article`, `low_sitelinks`, `missing_note`, `note_year_mismatch`, `excluded`, `duplicate`.
> - The exclusion list lives in `packages/content/data/exclusions.txt`.
> - `words.txt` has one word per line, uppercase, A-Z, 4-12 letters, alphabetically sorted, no duplicates.
> - `LICENSE-DATA.md` is always present with the CC BY-SA 4.0 and CC0 attribution.
> - Items are never curated by hand; sorting is by rule. A wrong text is handled by report, void and `rejected`, and `sync_banks` never revives it.
> - The runtime entry `loadDataset()` parses with Zod and throws on invalid input; it makes no network calls.

> `timeline_facts.json` items have exactly: `wikidata_id`, `label`, `category`, `event_date` (`YYYY-MM-DD`), `date_precision`, `note` (`{es,en}`), `sitelinks`, `status`, `rejection_reason`.

> `manifest.json`: `dataset_version` (`YYYY.MM.DD`, plus `-N` when several are generated the same day), `generated_at` (ISO 8601), `min_sitelinks`, counts per bank and category, and the parameters used.

> **Integration with other conventions:** **content-sync** (the `generator` loads the dataset into the database); **testing** (schema, ordering, minimum-count and manifest tests; the script is tested with recorded fixtures, not live requests); **validation** (Zod schemas).

### ADRs Relevantes

**ADR-016: Bancos de contenido como dataset versionado, sin Wikimedia en producción**
- **Decisión:** el contenido de los bancos se importa offline (`import:banks`) y se versiona en `packages/content/data/` (`terms.json`, `timeline_facts.json`, `manifest.json`); el `generator` lo carga con `sync_banks` al arrancar. Ningún servicio desplegado consulta Wikimedia.
- **Reglas de Implementación (verbatim):**
  - `api` y `generator` MUST NOT hacer requests a dominios de Wikimedia (`*.wikidata.org`, `*.wikipedia.org`, `*.wiktionary.org`). Solo los scripts `import:banks` y `build:wordlist` pueden hacerlo, y MUST NOT importarse desde código de runtime.
  - Los scripts MUST mandar `User-Agent: nerdose-content/<dataset_version> (<WIKIMEDIA_CONTACT>)`. `WIKIMEDIA_CONTACT` es una variable de entorno de desarrollo.
  - Cada ítem de `terms.json` MUST tener exactamente: `wikidata_id`, `term`, `category`, `definition` (`{es,en}`), `summary` (`{es,en}`), `sitelinks`, `status` (`approved`|`rejected`), `rejection_reason` (string o `null`).
  - Cada ítem de `timeline_facts.json` MUST tener exactamente: `wikidata_id`, `label`, `category`, `event_date` (`YYYY-MM-DD`), `date_precision`, `note` (`{es,en}`), `sitelinks`, `status`, `rejection_reason`.
  - Los JSON MUST escribirse ordenados por `wikidata_id`, con indentación de 2 espacios y un ítem por bloque, para que los diffs sean legibles.
  - `manifest.json` MUST incluir `dataset_version` con el formato `YYYY.MM.DD` (más `-N` si hay varias el mismo día), `generated_at` (ISO 8601) y `min_sitelinks`.
  - `import:banks` MUST terminar con error si hay menos de 500 `terms` `approved` o menos de 100 `timeline_facts` `approved` en alguna categoría v1 (`programming_languages`, `frameworks`, `companies`, `operating_systems`, `hardware`, `video_games`).
  - `sync_banks` MUST hacer `INSERT … ON CONFLICT (wikidata_id) DO UPDATE` con estas reglas:
    - Si el ítem en la base está `rejected`, MUST NOT cambiarlo (sigue `rejected`).
    - Si en la base está `approved` y en el dataset `rejected`, pasa a `rejected` con su `rejection_reason`.
    - MUST NOT tocar `last_used_devdle`, `last_used_grep` ni `last_used`.
    - MUST NOT borrar ítems que están en la base y no en el dataset.
  - `sync_banks` MUST registrar en `job_runs` (`job = 'sync_banks'`) un `summary` con `dataset_version`, `inserted`, `updated`, `unchanged` y `kept_rejected`.
  - `packages/games/devdle/wordlist/words.txt` MUST tener una palabra por línea, en mayúsculas, A–Z, 4–12 letras, ordenadas alfabéticamente y sin duplicados.
  - `packages/content/` MUST incluir `LICENSE-DATA.md` con la atribución CC BY-SA 4.0 de los textos derivados de Wikipedia y CC0 de Wikidata.

**ADR-003: Monorepo y paquetes compartidos** (aplica por la dirección de dependencias): `content` depende de `core` (ya declarado en `package.json`); `core` nunca depende de `content`. El paquete `timeline` importa los enums de `core` y usa `content` solo como `devDependency`.

### Contexto de Base de Datos

`content` no accede a la base. El dataset tiene que ser cargable en `timeline_facts` (migración `0004`, plan `db`), así que el schema Zod es coherente con estas restricciones:

```dbml
Enum timeline_category { programming_languages frameworks companies operating_systems hardware video_games }
Enum date_precision { year month day }

// rejection_reason: disputed_date, imprecise_date, missing_article, low_sitelinks, missing_note, note_year_mismatch, excluded, duplicate
Table timeline_facts {
  id uuid [pk, default: `gen_random_uuid()`]
  label text [not null]
  category timeline_category [not null]
  event_date date [not null]
  date_precision date_precision [not null]
  note jsonb [not null, note: '{es,en}']
  wikidata_id text [not null, unique]
  sitelinks integer [not null]
  status bank_item_status [not null]
  rejection_reason text [null]
  last_used date [null]
  dataset_version text [not null]
  created_at timestamptz [not null, default: `now()`]
  updated_at timestamptz [not null, default: `now()`]
  indexes { (status, category, last_used) [name: 'idx_timeline_facts_pick'] }
}
```

Invariantes: `status = 'rejected'` ⇒ `rejection_reason IS NOT NULL` (`ck_timeline_facts_rejection_reason`); `note ? 'es' AND note ? 'en'` (`ck_timeline_facts_note_locales`); `wikidata_id` único (clave del UPSERT). `event_date` es tipo `date`: una fecha inexistente (`2014-02-30`) haría fallar el INSERT del `generator`, por eso el schema la rechaza en los `approved`.

### Decisiones de este plan

1. **Constantes de motivos.** `TIMELINE_REJECTION_REASONS = ['disputed_date', 'imprecise_date', 'missing_article', 'low_sitelinks', 'missing_note', 'note_year_mismatch', 'excluded', 'duplicate'] as const` (orden de la decisión 4, que es el orden de aplicación de las reglas) y `type TimelineRejectionReason`. `REJECTION_REASONS` / `RejectionReason` (de `terms`) no cambian.
2. **Re-export sin cambiar la API pública.** `schema.ts` borra su copia local e importa `TIMELINE_CATEGORIES` y `DATE_PRECISIONS` de `@nerdose/core`; `index.ts` los sigue exportando con el mismo nombre (son la misma referencia que en `core`). Se suman de forma aditiva los tipos `TimelineCategory` y `DatePrecision` (re-export de `core`) y `TIMELINE_REJECTION_REASONS` / `TimelineRejectionReason`.
3. **Coherencia fecha–precisión (solo `approved`).** `event_date` mantiene la regex `^\d{4}-\d{2}-\d{2}$` para todos los estados. Para un `approved`: tiene que ser una fecha de calendario real (UTC, verificada con `Date.UTC` ida y vuelta, incluye bisiestos) y además: `year` ⇒ termina en `-01-01`; `month` ⇒ termina en `-01`; `day` ⇒ cualquier fecha real. Un `rejected` no exige coherencia (puede ser justamente `imprecise_date`). El rango 1800–año actual es regla del importador (`imprecise_date`, S-026), no del schema.
4. **Forma de `counts.timeline_facts`.** Igual que `counts.terms`: `{ approved, rejected, by_category: { <TimelineCategory>: { approved, rejected } ×6 }, by_reason: { <TimelineRejectionReason>: count ×8 } }`, todo `strictObject`.
5. **Forma de `parameters.timeline`.** `{ min_sitelinks: count, min_approved_per_category: count, min_categories: count, categories_v1: TimelineCategory[] (sin repetidos), classes: { wikidata_class: string, category: TimelineCategory, date_property: string /^P[1-9]\d*$/ }[] }`. **`classes[].date_property` es NOT DOCUMENTED - needs verification:** la decisión 3 dice "clase de Wikidata → categoría + propiedad de fecha" pero no fija la forma JSON; se elige el nombre `date_property` (`P571`/`P577`). S-026 puede ajustarlo (por ejemplo, para registrar el fallback a `P571`) al implementar `TIMELINE_CLASSES`. Los valores `100` y `3` no se fijan con `z.literal`: se validan en el test del dataset commiteado, como `min_approved_terms: 500`.
6. **Orden de claves.** `counts: { terms, timeline_facts }` y `parameters: { min_sitelinks, min_approved_terms, term_length, languages, classes, timeline }` (lo nuevo al final), en el schema y en los JSON.
7. **Dataset commiteado puente.** `data/timeline_facts.json` = `"[]\n"`; `data/manifest.json` conserva todo lo actual (incluido `dataset_version: "2026.11.10"`, porque el contenido de `terms` no cambia) y suma `counts.timeline_facts` en cero y `parameters.timeline = { min_sitelinks: 10, min_approved_per_category: 100, min_categories: 3, categories_v1: [], classes: [] }`. `10` es `DEFAULT_MIN_SITELINKS` (valor provisorio: S-026 calibra `min_sitelinks_timeline`). Con `categories_v1: []`, el `generator` no tiene hechos que cargar y `sync_banks` sigue funcionando.
8. **Puente mínimo en el script (hasta S-026).** `buildManifest` recibe opcionalmente `timelineFacts` (default `[]`) y `timeline` (default `DEFAULT_TIMELINE_PARAMETERS`); `writeDataset` recibe `timelineFacts` y escribe los **tres** archivos (`.tmp` + `rename`), validando también con `timelineFactsFileSchema`; `runImport` relee el `timeline_facts.json` existente (validado; ausente → `[]`) y el `parameters.timeline` del manifiesto previo (si existe y es válido) y los vuelve a escribir sin cambios. Es exactamente el comportamiento que S-026 llamará `--bank=terms`, sin el flag. Un `timeline_facts.json` existente e inválido hace fallar `runImport` con `DatasetError` (`file: 'timeline_facts.json'`) **antes** de consultar Wikimedia y sin escribir nada.
9. **Fixtures del `generator`.** Se actualizan solo los JSON de `apps/generator/test/fixtures/datasets/{v1,v2,conflict,dup-rejected,invalid}/` (manifiesto ampliado + `timeline_facts.json` = `[]`) para que su suite siga verde; no se toca código del `generator`. Las fixtures con hechos para CA-6/CA-7 son del plan `generator`.

```ts
  const [y, m, d] = value.split('-').map(Number) as [number, number, number];
  const date = new Date(Date.UTC(y, m - 1, d));
  return date.getUTCFullYear() === y && date.getUTCMonth() === m - 1 && date.getUTCDate() === d;
}

function matchesPrecision(value: string, precision: DatePrecision): boolean {
  if (precision === 'year') return value.endsWith('-01-01');
  if (precision === 'month') return value.endsWith('-01');
  return true;
}
```
- Ojo con `Date.UTC` para años 0–99 (los mapea a 1900+): no aplica porque la regex exige 4 dígitos y el importador rechaza años < 1800, pero la verificación ida y vuelta igual lo detecta.
- Mantener `strictObject` (claves exactas de ADR-016).
