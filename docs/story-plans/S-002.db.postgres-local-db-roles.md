### ADRs Relevantes

#### ADR-004: PostgreSQL como única base, con propiedad por roles

- **Decisión:** PostgreSQL 16 como única base (`nerdose-db`). La frontera entre servicios se hace cumplir en la base con tres roles: dueño del schema (DDL, solo corre migraciones), `nerdose_api` y `nerdose_generator` (sin DDL, con `GRANT` explícitos por tabla y columna).
- **Reglas de Implementación (verbatim):**
  - La única base MUST ser PostgreSQL ≥ 16. MUST NOT agregarse otra base (Redis, MongoDB, SQLite) en v1.
  - Los campos que varían por juego (`challenges.payload`, `challenges.verification`, `plays.state`, `plays.result`, `player_game_stats.extra`, `challenge_reports.context`, `job_runs.summary`) MUST ser `jsonb`.
  - Los textos de contenido bilingües MUST guardarse como `jsonb` con la forma `{ "es": string, "en": string }`.
  - Las fechas de día MUST ser `date` (día UTC). Los instantes MUST ser `timestamptz`.
  - Los ids MUST ser `uuid` (`gen_random_uuid()`), salvo las PK compuestas o naturales que define `docs/db-schemas/nerdose-db.md`.
  - La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
  - Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db`, con permisos por columna sobre `challenges`, `terms` y `timeline_facts` exactamente como en la tabla de arriba.
  - La unicidad de un Challenge vigente MUST implementarse como índice único parcial sobre `(game_id, date)` con `WHERE status IN ('approved','published','voided')`.
  - `plays` MUST tener `UNIQUE (player_id, challenge_id)` y `challenge_reports` MUST tener `UNIQUE (player_id, challenge_id)`.
  - Los enums del dominio (`game_id`, `challenge_status`, `play_status`, `code_language`, `locale`, etc.) MUST ser enums de PostgreSQL con los valores exactos del análisis de dominio.
- **Riesgo documentado:** una migración olvida los `GRANT` de una tabla nueva → **mitigación:** test de integración que corre con cada rol las operaciones esperadas sobre una base migrada. El test de permisos de esta story (Tarea 6) es la plantilla para sumar casos por tabla.
- **Aplica en esta story:** solo las reglas de roles (sin DDL para servicios, `GRANT` en migración versionada). No hay tablas todavía.

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo pnpm + Turborepo; `packages/db` contiene schema Drizzle, migraciones, queries compartidas y vistas `metrics_*`.
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

#### ADR-002: Stack tecnológico (reglas aplicables)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `api` y `generator` MUST correr en Node.js 24 LTS. `engines.node` MUST ser `">=24 <25"`.
- Todo acceso a la base MUST pasar por Drizzle ORM con el driver postgres.js. SQL crudo solo en migraciones, en las vistas `metrics_*` y donde Drizzle no lo soporte (`LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`).
- Los tests MUST usar Vitest; los e2e, Playwright.

> `ALTER ROLE ... PASSWORD`, `CREATE ROLE` y las consultas a `pg_roles` / `has_*_privilege` no son expresables con Drizzle: se usan con el `sql` de postgres.js y un comentario de una línea que lo justifica (regla de `orm`).

#### ADR-015: Contratos JSON y errores (aplicado vía `@nerdose/core`)

- El catálogo de errores es cerrado. Este paquete solo usa `validation_error` (status 422) para fallos de configuración. No se agregan códigos.

#### `orm` (Drizzle) — configuración de referencia

```ts
// packages/db/src/client.ts
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

export function createDb(url: string, options: { max?: number } = {}) {
  const sql = postgres(url, { max: options.max ?? 10 });
  const db = drizzle(sql, { schema });
  return { db, sql };
}

export type Db = ReturnType<typeof createDb>['db'];
export type Tx = Parameters<Parameters<Db['transaction']>[0]>[0];
```

```ts
// packages/db/drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  dialect: 'postgresql',
  schema: './src/schema',
  out: './migrations',
  dbCredentials: { url: process.env.DATABASE_URL_OWNER! }, // role nerdose_owner, DDL only
});
```

```bash
pnpm --filter @nerdose/db db:generate --name add_challenge_reports   # generate SQL
pnpm --filter @nerdose/db db:migrate                                  # apply, with DATABASE_URL_OWNER
```

Reglas de `orm` aplicables:
- All DB access goes through Drizzle with postgres.js. No other driver or ORM in `apps/` or `packages/`.
- The Drizzle schema and the migrations live only in `@nerdose/db`. Services MUST NOT declare tables.
- Services connect with their own role: `api` as `nerdose_api`, `generator` as `nerdose_generator`. Neither uses the owner role or has DDL permissions. `DATABASE_URL_OWNER` is used only by `db:migrate`.
- Raw SQL only for what Drizzle cannot express. Document why in a one-line comment.
- Migrations are forward-only, reviewed by hand, and committed together with the schema change. Never edit an applied migration.
- Migrations run before starting `api` and `generator`, with the owner role. Services do not run migrations at startup.
- The first migration, `0000_roles_and_grants` (manual SQL), creates `nerdose_api` and `nerdose_generator` with `LOGIN` and no password (idempotent) and sets the base grants (no DDL for services). Passwords are never versioned: after applying migrations, `db:migrate` optionally runs `ALTER ROLE` from `DATABASE_URL_API` / `DATABASE_URL_GENERATOR`.
- Each service MUST only write the tables and columns its role allows (ADR-004). A test runs the expected operations with each role.

#### `env-config` — reglas aplicables

- Secretos nunca se loguean.

```ts
import type { GlobalSetupContext } from 'vitest/node';
import { migrateAsOwner, createRoles } from '@nerdose/db/testing';

declare module 'vitest' {

export async function setup({ provide }: GlobalSetupContext) {
  container = await new PostgreSqlContainer('postgres:16-alpine').start();
  const urls = await createRoles(container.getConnectionUri());

  provide('ownerUrl', urls.owner);
  provide('apiUrl', urls.api);
  provide('generatorUrl', urls.generator);
}
export async function teardown() { await container?.stop(); }
```

- **Tablas:** ninguna nueva. El schema Drizzle queda vacío (`src/schema/index.ts`); las tablas del DBML de `docs/db-schemas/nerdose-db.md` se crean en los feature groups que las usan, cada una con sus `GRANT`.
- **Roles:**

| Rol | Quién lo crea | Contraseña | Permisos tras `0000_roles_and_grants` |
|---|---|---|---|
| `nerdose_owner` | Local: Docker Compose (`POSTGRES_USER`, superusuario del contenedor). Tests: `createRoles` (sin superusuario, con `CREATEROLE`, dueño de la base y del schema `public`) | Local: `POSTGRES_PASSWORD` de `.env` (raíz). Tests: aleatoria | DDL; corre las migraciones |
| `nerdose_api` | La migración (`IF NOT EXISTS`). En tests ya existe porque la crea `createRoles` | Sin contraseña en la migración; `db:migrate` la fija desde `DATABASE_URL_API` | `CONNECT` a la base, `USAGE` en `public`; sin `CREATE` en `public`, sin `CREATE`/`TEMPORARY` en la base |
| `nerdose_generator` | Igual que `nerdose_api` | Desde `DATABASE_URL_GENERATOR` | Igual que `nerdose_api` |

- **Migración `0000_roles_and_grants` (contenido exacto, de la story):**

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'nerdose_api') THEN
    CREATE ROLE nerdose_api LOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'nerdose_generator') THEN
    CREATE ROLE nerdose_generator LOGIN;
  END IF;
END $$;

REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO nerdose_api, nerdose_generator;

DO $$ BEGIN
  EXECUTE format('REVOKE CREATE, TEMPORARY ON DATABASE %I FROM PUBLIC', current_database());
  EXECUTE format('GRANT CONNECT ON DATABASE %I TO nerdose_api, nerdose_generator', current_database());
END $$;
```

  - No se usa `ALTER DEFAULT PRIVILEGES` (ADR-004 exige `GRANT` explícitos por tabla y columna).
  - Separar cada sentencia con `--> statement-breakpoint` (formato de drizzle-kit): el migrador ejecuta cada fragmento por separado y así no depende de que el driver acepte varias sentencias en una sola llamada.
- **Registro de migraciones:** `drizzle.__drizzle_migrations` (schema `drizzle`, tabla `__drizzle_migrations`, columnas `id`, `hash`, `created_at`), creado por `drizzle-orm/postgres-js/migrator`. Una segunda ejecución no aplica nada (CA-3).
- **Estrategia de migraciones (de `nerdose-db.md`):** drizzle-kit, SQL manual donde Drizzle no alcanza; forward-only; en `packages/db/migrations/`; se aplican con `pnpm --filter @nerdose/db db:migrate` usando `DATABASE_URL_OWNER` antes de levantar `api` y `generator`.

### Task 4: Sincronización de contraseñas `syncRolePasswords`

**Status:** Completed

#### Description

Implementar el paso 3 de `db:migrate`: dadas las URLs opcionales de `nerdose_api` y `nerdose_generator`, validar que el usuario de cada URL sea el rol esperado y que tenga contraseña, y luego ejecutar `ALTER ROLE <rol> PASSWORD <contraseña>`. Es lo que permite conectar con esas URLs sin versionar contraseñas (CA-5).

#### Acceptance Criteria

1. `src/migrations/sync-role-passwords.ts` exporta `SERVICE_ROLES = { api: { role: 'nerdose_api', variable: 'DATABASE_URL_API' }, generator: { role: 'nerdose_generator', variable: 'DATABASE_URL_GENERATOR' } } as const` y `syncRolePasswords(sql: Sql, urls: { api?: string; generator?: string }): Promise<Array<'nerdose_api' | 'nerdose_generator'>>`.
2. Valida **todas** las URLs presentes antes de ejecutar cualquier `ALTER ROLE`:
   - usuario (`decodeURIComponent(new URL(url).username)`) distinto del rol esperado → `AppError('validation_error', '<VARIABLE> debe usar el usuario <rol> (recibido: <usuario>)')`;
   - contraseña vacía → `AppError('validation_error', '<VARIABLE> no tiene contraseña')`;
   - URL no parseable → `AppError('validation_error', '<VARIABLE> no es una URL válida')`.
3. Por cada URL válida, en orden `api` → `generator`: obtiene la sentencia con `` sql`SELECT format('ALTER ROLE %I PASSWORD %L', ${role}::text, ${password}::text) AS stmt` `` y la ejecuta con `sql.unsafe(stmt)`; la contraseña es `decodeURIComponent(new URL(url).password)`.
4. Devuelve los roles sincronizados en ese orden (`[]` si no hay URLs).
5. Ningún mensaje de error contiene la contraseña ni la URL completa.

#### Technical Details

**Architectural Context References:**
- Contexto de Base de Datos → tabla de roles; contraseñas fuera de la migración.
- Convención `env-config` → `DATABASE_URL_API` / `DATABASE_URL_GENERATOR` las lee solo `db:migrate`.
- Convención `error-handling` / Código Reutilizable → `AppError('validation_error', ...)`.
- Convención `orm` → SQL crudo justificado con comentario de una línea.

**Files to Create/Modify:**
- `src/migrations/sync-role-passwords.ts`

**Implementation Notes:**
- `format('%L')` hace el escape del literal en PostgreSQL (soporta `'`, `\` y cualquier carácter); no armar el literal en TypeScript.
- `ALTER ROLE` es repetible: correrlo con la misma contraseña no cambia nada observable (CA-3).
- El tipo `Sql` se importa de `postgres` (`import type { Sql } from 'postgres'`).
- Aceptable: con `log_statement = 'ddl'` o `'all'` PostgreSQL podría registrar la sentencia; es comportamiento estándar de `ALTER ROLE ... PASSWORD` y no afecta al repo.

**Dependencies:**
- `postgres` (tipo `Sql`), `@nerdose/core` (`AppError`).

**Unit Tests:**

**Integration Tests:**
