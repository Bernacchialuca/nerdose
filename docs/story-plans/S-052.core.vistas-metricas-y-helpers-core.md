### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **Firma y semántica de `isStreakAlive`.** La documentación fija los parámetros `(lastCompleted, prevActiveDay, today)` y la regla de ADR-011 ("`last_completed_date == today` o `last_completed_date >= prev_active_day`"). Tipos y valor de retorno elegidos para encajar con `StreakInput`:
   ```ts
   /** ADR-011: alive if completed today or on/after the previous active day. Never writes. */
   export function isStreakAlive(
     lastCompleted: string | null,
     prevActiveDay: string | null,
     today: string,
   ): boolean {
     if (lastCompleted === null) return false;
     return lastCompleted === today || prevActiveDay === null || lastCompleted >= prevActiveDay;
   }
   ```
   Es exactamente la condición actual de `liveStreak` (`lastCompleted === today || continues(input)` con el corte por `null`), extraída y exportada.
2. **`liveStreak` y `nextStreak` sobre el predicado; se elimina `continues`.**
   - `liveStreak(input, today)` → `isStreakAlive(input.lastCompleted, input.prevActiveDay, today) ? input.current : 0`.
   - `nextStreak(input, day)` → `if (input.lastCompleted === day) return input.current;` y luego `isStreakAlive(input.lastCompleted, input.prevActiveDay, day) ? input.current + 1 : 1`. Es equivalente a `continues` porque el caso `lastCompleted === day` ya salió antes. Así queda **una sola** condición de racha en el paquete (ADR-011: "única implementación"). Los tests existentes de `nextStreak`, `liveStreak`, `replayStreak` y el de propiedad no cambian (CA-4).
3. **Firma de `validateMetricsRange` y tipos.** La story dice "devuelve `ok` o el motivo". Se implementa como unión de strings literales, sin objeto:
   ```ts
   export type MetricsRangeReason = 'from_after_to' | 'future' | 'too_long';
   export type MetricsRangeResult = 'ok' | MetricsRangeReason;
   export function validateMetricsRange(from: string, to: string, today: string): MetricsRangeResult;
   ```
   Se exportan los dos tipos (el `admin` mapea `Record<MetricsRangeReason, string>` a sus mensajes y la `api` compara contra `'ok'`). **No** se exporta una constante runtime con los motivos: ningún consumidor documentado la necesita.
4. **Orden de evaluación cuando falla más de una regla:** `from_after_to` → `future` → `too_long`, el orden en que la story, REQ-011 (decisión 5) y la pantalla `metricas` listan los motivos. Ejemplo: `from = '2025-01-01'`, `to = '2026-12-31'`, `today = '2026-12-01'` → `'future'` (no `'too_long'`).
5. **Cálculo de la longitud.** `(Date.parse(\`${to}T00:00:00.000Z\`) - Date.parse(\`${from}T00:00:00.000Z\`)) / MS_PER_DAY > 365` → `'too_long'`, el mismo patrón que `challengeNumber` (UTC, sin `new Date()` del sistema). `from <= to` y `to <= today` se comparan como strings `YYYY-MM-DD` (orden lexicográfico = orden cronológico).
6. **Entradas inválidas.** Precondición, como `challengeNumber`: `from`, `to` y `today` son fechas `YYYY-MM-DD` válidas. El formato lo valida antes cada consumidor: la `api` con Zod (`format: date` de la query) y el `admin` con su chequeo de "vacío" («Elegí las dos fechas del rango.», que **no** es un motivo de core según la pantalla `metricas`). `validateMetricsRange` no valida formato ni lanza.
7. **Ubicación.** `isStreakAlive` en `src/streaks.ts` (junto a `liveStreak`); `validateMetricsRange` y sus tipos en `src/platform-day.ts` (módulo `platform-day` del overview, reutiliza `MS_PER_DAY`). Sin archivos nuevos en `src/`.
8. **API pública: 27 claves runtime.** `Object.keys(core).sort()` suma `'isStreakAlive'` (entre `'isGameId'` y `'liveStreak'`, porque `'G'` < `'S'`) y `'validateMetricsRange'` (al final, después de `'today'`).
9. **Ids de test.** Los `it` nuevos llevan el sufijo `(S-052 TS-n)`. Los tests existentes no se renombran ni se modifican, salvo la lista de claves de `public-api.test.ts` y el bloque de tipos (TS-52), que solo suman entradas.

`src/streaks.ts` actual (extracto que cambia):

```ts
export interface StreakInput {
  current: number;
  lastCompleted: string | null;
  prevActiveDay: string | null;
}

function continues(s: StreakInput): boolean {
  return (
    s.lastCompleted !== null && (s.prevActiveDay === null || s.lastCompleted >= s.prevActiveDay)
  );
}

/** Streak after completing `day`. `max_*` is computed by the caller with Math.max. */
export function nextStreak(input: StreakInput, day: string): number {
  if (input.lastCompleted === day) return input.current;
  return continues(input) ? input.current + 1 : 1;
}

/** Streak to display on read: 0 when it is no longer alive. Never writes. */
export function liveStreak(input: StreakInput, today: string): number {
  if (input.lastCompleted === null) return 0;
  return input.lastCompleted === today || continues(input) ? input.current : 0;
}
```

const MS_PER_DAY = 86_400_000;

/** `day - launchDate + 1`, or `null` before launch. Inputs must be valid `YYYY-MM-DD`. */
export function challengeNumber(day: string, launchDate: string): number | null {
  const diff =
    (Date.parse(`${day}T00:00:00.000Z`) - Date.parse(`${launchDate}T00:00:00.000Z`)) / MS_PER_DAY;
  return diff < 0 ? null : diff + 1;
}

### ADRs Relevantes

#### ADR-011: Rachas con días neutros y agregados recalculables

- **Decisión (verbatim, extracto):**
  ```
  Al completar una Play del día D:
    game:   current_streak = (last_completed_date >= prev_active_day(game_id, D)) ? current_streak + 1 : 1
            (si last_completed_date == D, no cambia)
    global: global_streak  = (last_active_date >= prev_active_day_global(D)) ? global_streak + 1 : 1
            (si last_active_date == D, no cambia)
    max_* = max(max_*, current)

  Al leer: muestra current_streak si last_completed_date == today
           o last_completed_date >= prev_active_day(game_id, today); si no, 0
  ```
- **Reglas de Implementación (verbatim, completas):**
  - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
  - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
  - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
  - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
  - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
  - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
  - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
  - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
  - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.
- **Aplicación en este plan:** `isStreakAlive` es la condición única; `nextStreak` y `liveStreak` la usan (decisión 2) y la `api` (S-053) la usa para mover al tramo `'0'` las filas de `metrics_streak_distribution`. Los tests nuevos usan reloj falso para probar la pureza (TS-9, TS-21).

#### ADR-014: Métricas en la base y analítica web opcional

- **Nota de implementación (REQ-011), verbatim:** "las vistas no dependen de "hoy". `metrics_retention` expone conteos (`d1_players`, `d7_players`) y `metrics_streak_distribution` el tramo de la racha guardada con `last_active_date`; la `api` completa `d1`/`d7` y la racha viva con su reloj y con `isStreakAlive` de core (ADR-011), para no duplicar la regla en SQL y poder probarla con relojes falsos."
- El resto de sus reglas (nombres de vistas, `SELECT` para `nerdose_api`, `track()`, Plausible) no aplican a `core`.

#### ADR-008: Día de la plataforma en UTC calculado por el servidor

- `today` lo calcula el servidor con `today(clock.now())` de core. `validateMetricsRange` **recibe** `today` como parámetro y nunca lee el reloj del sistema: la `api` pasa `clock.today()` y el `admin` pasa el día UTC del navegador (si el servidor rechaza un rango que el navegador aceptó por reloj desfasado, el admin muestra el mensaje del servidor; ver "Contexto de Flujos").

#### ADR-003: Monorepo y paquetes compartidos

- `@nerdose/core` tiene una sola entrada `.`, isomorfa y sin `node:*`. Las dos funciones usan solo `Date.parse` y comparación de strings; no agregan imports (TS-23).

**Mensajes del admin por motivo** (pantalla `metricas`, para que los nombres de los motivos calcen con S-054; verbatim):
- `from` > `to` → «La fecha inicial no puede ser posterior a la final.» (`from_after_to`)
- `to` posterior a hoy (UTC) → «El rango no puede incluir fechas futuras. Hoy es {dd/mm/aaaa} (UTC).» (`future`)
- `to − from` mayor a 365 días → «El rango no puede superar los 366 días.» (`too_long`)
- `from` o `to` vacío → «Elegí las dos fechas del rango.» (lo resuelve el admin, **no** core)

  export function isStreakAlive(

  export type MetricsRangeReason = 'from_after_to' | 'future' | 'too_long';
  export type MetricsRangeResult = 'ok' | MetricsRangeReason;

  /** Admin metrics range: `from <= to`, `to <= today`, at most 366 days inclusive. Inputs must be valid `YYYY-MM-DD`. */
  export function validateMetricsRange(from: string, to: string, today: string): MetricsRangeResult {
