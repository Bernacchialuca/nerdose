### Arquitectura del servicio (`docs/architectures/games/overview.md`, copiado lo aplicable)

> Los cinco paquetes de juego `packages/games/<game_id>`. Cada uno implementa el contrato `GameDefinition` de `@nerdose/core` y expone tres entradas separadas: `./definition` (servidor: la usa la `api`), `./client` (React: `Instructions`, `Game`, `Result` y `share()`; la usan `web` y `admin`) y `./generator` (`generate` y `verify`; lo usa el `generator`). ADR-003 y ADR-006.
> **Convenciones por entrada:** `definition` y `generator` siguen `game-registry`, `validation` y `testing`; `client` sigue `styling`, `accessibility`, `testing-unit` y `game-clients`.

### Convenciones activas (extractos aplicables, verbatim)

#### `game-package`

- `./client` — May import: `@nerdose/core` (`.`), `zod`, `react`, `@nerdose/ui`, `shared/`, types from `./definition`. Must not import: `@nerdose/polyglot`, `node:*`, `./generator`, runtime code of `./definition` that carries solutions.
- `./client` exports: React components `Instructions`, `Game`, `Result`, `Preview({ payload, language })`, `share(result, number)`, `i18n` and `HELP_TARGET_ID`.
- `shared/` holds only pure, isomorphic code (types, constants, helpers) with no Node or React dependencies.
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry.
- `share(result, number)` never includes the solution and ends with `nerdose.dev`. (ADR-006 ya dice `share(result, number, locale)`; esta convención se actualiza en la Tarea 10.)
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk. Game-specific dependencies stay inside the game package (Shiki for `big-o` and `bug-hunt`…).

#### `game-clients` (contrato que el paquete cumple)

- `GameClient` is the shape of the `./client` entry defined by the game contract: React components `Instructions`, `Game`, `Result` and `share(result, number): string`. The exact props of those components are owned by the game packages and `@nerdose/core`; the app passes them through and does not reinterpret them.
- Moves go through the game's `moveSchema` (Zod) before `POST .../move`.
- Shiki (big-o, bug-hunt) and dnd-kit (timeline) are dependencies of the game packages and are loaded in the game's own chunk. The shell never imports them.
- **Admin preview:** Contract: `Preview(props: { payload: unknown; language: Locale })`. It (a) parses `payload` with the game's own `payloadSchema` and lets the error propagate if it is invalid, (b) translates its texts with the package's own `i18n` resources according to `language` (it needs neither react-i18next nor the host's `t`), (c) uses `h3` headings and a root `<div lang={language}>` with no landmark of its own, (d) has no controls or effects (no `fetch`, no storage, no play state).
- `web` never mounts `Preview`. The `client` never receives the solution before the round ends in `web`. Share text is never built by the shell; it always comes from the game's `share()`. Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`.
- **Update (REQ-009):** `ClientBaseProps.codeLanguage: CodeLanguage` … In a game package it is optional with default `'js'`, so a client is assignable to the host's component type whether or not the host already passes it. The `Game` reads it only on mount and when the challenge changes; switching the code tab is local state: no request, no persistence, and the chosen option survives it. Shiki (Big O, Bug Hunt) is loaded only through dynamic `import('shiki/…')` inside the game package (`highlight.ts`, own chunk), with the JS regex engine and the `css-variables` theme. The theme's `--shiki-*` variables are defined with `style` on the code block and point to DS tokens: no hex, no CSS file, no Shiki markup. While loading, or if loading fails, the same code is shown without color and with the same structure (no layout shift). Big O's `Preview` shows the code in plain text (it never loads Shiki, so the admin never pays for it) with local-view language tabs (no effects, no fetch, no storage, no play state).

#### `styling`

- Use only the tokens (DS first). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- Text and interactive-element contrast meets WCAG 2.1 AA against the surface it sits on (4.5:1 text, 3:1 large text and UI components). Verify any new color pair.
- Focus is always visible: use `focus-visible:` rings; never `outline-none` without a replacement.
- State is never conveyed by color alone. Respect `prefers-reduced-motion`.
- **When NOT to use Tailwind classes:** values from data (set a CSS variable with `style`); third-party rendered output (Shiki markup): style through a scoped CSS selector in the owning package.
- Mobile-first from 320 px; no horizontal scroll at 320 px; touch targets ≥ 44 × 44 px.
- **REQ-003:** no global media queries (flex-wrap / auto-fit); static check: component `.tsx` must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).

#### `accessibility`

- Use native elements first; ARIA only when no native element fits. No interactive element built from a `<div>`/`<span>` with a click handler.
- Everything operable with the mouse is operable with the keyboard, logical tab order, no traps, visible focus.
- Feedback that uses color (win/loss) is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
- Result, errors and notices appear in `role="status"` (polite) or `role="alert"` regions. Dynamic updates are announced via live regions; do not move focus unexpectedly.
- Contrast ≥ 4.5:1 text (3:1 large / UI boundaries). Each game can be completed with the keyboard alone (NFR-U03). axe-core reports zero violations in unit checks.

#### `testing-unit`

- Query by role, label or visible text; `data-testid` only when no accessible query exists. Use `userEvent`, not `fireEvent`.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- Fixtures use the API's `snake_case` names. No snapshot tests of large DOM trees. Tests do not rely on the real date or timers.

#### `_base` (Node) — extracto

- Archivos `kebab-case`; sin `any` salvo bordes con librerías sin tipos (comentar el porqué); `async/await`; comentarios solo para el porqué.

#### `error-handling` — extracto

- Los errores esperados del juego no se lanzan desde el client: un `publicView` / `result` / `payload` inválido deja propagar el `ZodError` (mismo criterio que los otros clients); los rechazos del servidor llegan como `moveError` y se muestran en la línea de aviso.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Front: «Shiki (core, motor de regex JS, gramáticas js/go/java), cargado lazy solo en Big O y Bug Hunt.»
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

#### ADR-003: Monorepo (reglas aplicables, verbatim)

- Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
- `apps/web` y `apps/admin` MUST importar solo `./client`.
- `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)

- `client`: «Instructions, Game, Result (componentes React) y share(result, number, locale): string» · «Preview({ payload, language }) — solo lectura, el tablero con la solución, para el admin (REQ-008)».
- MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- `toPublic` MUST NOT incluir: … ni `bug_line`/`bug_type`/`mutation`/`fix`/`failing_test`/`tests`/`template`/`params`/`explanation` de Bug Hunt.
- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `share(result, number, locale)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
- `Preview` MUST ser de solo lectura: valida `payload` con el schema del juego, traduce con los recursos del propio paquete según `language`, y no hace `fetch`, no usa storage ni estado de partida. `web` MUST NOT montarla (necesita el `payload` completo, que solo devuelve `/api/admin/*`). El admin la monta en ES y EN lado a lado; un juego sin `Preview` cae a la vista genérica del payload (REQ-008).
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015: Contratos JSON y errores (reglas aplicables, verbatim)

- Todas las propiedades JSON … MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
- Los enums MUST serializarse con sus valores exactos del dominio (`code_language`: `js | go | java`; `locale`: `es | en`).

#### ADR-014: Métricas y analítica

- `track('share:<game_id>')` lo llama el host (`web`) después de compartir; el client no importa `track`.

### Decisiones de diseño de REQ-010 aplicables (verbatim)

- **Decisión 1:** «El payload guarda **una** `bug_line` y **una** lista `pickable_lines`… Cambiar de pestaña conserva la selección porque es el mismo número de línea (CA 3); `move.language` solo se guarda como `code_language`.»
- **Decisión 3:** «`toPublic(p, locale)` → `{ function_name, spec: p.spec[locale], code: p.code, pickable_lines, visible_tests }`. `function_name` se agrega a la vista pública (no revela nada: está en la línea 1 del código) para que el cliente muestre los tests como llamadas (`maxIndex([3, 7, 2]) → 1`) sin parsear el código.»
- **Decisión 8:** «`BugHuntState = { language?: CodeLanguage; line?: number }`; `initState → {}`; mientras la Play está `in_progress` el estado sigue vacío (la línea seleccionada y el lenguaje visible viven solo en el cliente: al retomar no hay selección, CA 8). `moveSchema = z.strictObject({ language: z.enum(CODE_LANGUAGES), line: z.number().int().min(1) })`.»
- **Decisión 9:** «`result(p, s, locale)` → `{ win, score, chosen_line: s.line, code_language: s.language, bug_line, bug_type, function_name, failing_test, fix: { js: { before, after }, go: …, java: … }, explanation: { steps: string[] } }` con los pasos en `locale`. `fix[lang].before` es la línea `bug_line` de `code[lang]` y `after` es `fix[lang]` del payload: el cliente la muestra como `-`/`+` del lenguaje de la pestaña… **`share` con idioma:** `GameClient.share(result, number, locale)`. Cambio aditivo: los 4 juegos actuales ignoran el tercer argumento (una función con menos parámetros sigue siendo asignable) y el host (`share-button.tsx` l. 83) pasa el `locale` activo. Bug Hunt: `🐛 Bug Hunt #N · <Lenguaje>` / `🟩 bug encontrado` | `🟥 se me escapó` (en: `🟩 bug found` | `🟥 it got away`) / `nerdose.dev`, sin la línea ni el tipo de bug (CA 10).»
- **Decisión 10:** «Partida: especificación arriba; pestañas JS/Go/Java (`tablist`, arranca en `codeLanguage` de `ClientBaseProps`); código con numeración como grupo de selección única operable con teclado: las líneas fuera de `pickable_lines` no son seleccionables ni enfocables; la selección (número de línea) sobrevive al cambio de pestaña y de idioma; "Confirmar" deshabilitado hasta elegir; `moveSchema.parse({ language, line })` antes de `onMove`. Tests visibles como `maxIndex([3, 7, 2]) → 1` y el aviso "1 test oculto falla". Cambiar de pestaña no hace requests (CA 3). Resultado: veredicto con ícono y texto; línea elegida y línea del bug marcadas con ícono y texto, no solo color (CA 5, 23); test que falla (llamada, esperado y obtenido); fix `-`/`+` del lenguaje de la pestaña; explicación numerada; el código sigue con pestañas (vista). Shiki: se copian del paquete de Big O `highlight.ts`, `shiki-vars.ts`, `use-tokenizer.ts` y el helper de `radio` (≈ 100 líneas): los paquetes de juego no se importan entre sí (`game-package`) y Shiki no puede subir a `@nerdose/ui` (ADR-002). Duplicación aceptada; si aparece un tercer juego de código se extrae a un paquete propio. `Preview({ payload, language })` para el admin: especificación, código en los 3 lenguajes con la línea del bug marcada, `bug_type`, mutación (`from` → `to`), tests visibles, test que falla, fix y explicación en `language`; solo lectura (ADR-006). Sin Shiki (como el `Preview` de Big O).»
- **Revisión UX (cierra puntos abiertos):** chip «tipo: …» con la etiqueta de `bug_type` en el idioma activo; el chip «mutación» no se muestra al jugador, sí en el `Preview` del admin. Tests como llamadas con `function_name` y sintaxis neutra, iguales en las 3 pestañas; el test que falla usa el mismo formato. Cada línea elegible es un blanco de 40 px de alto y ancho completo; las no elegibles no son interactivas; el tag «◀ tu elección» se reduce al glifo `◀` fijo al borde visible del bloque y el texto completo lo dan la línea de aviso y el botón «Confirmar línea N →». En el resultado los tags bajan bajo su línea. En mobile los tests van antes del código.

- **D7 — Líneas como `radiogroup` propio.** En modo `select` el cuerpo es `<div role="radiogroup" aria-label="Líneas de {name} en {lenguaje}">`; cada línea de `pickable_lines` es `<button type="button" role="radio" aria-checked aria-label="Línea {n}: {código sin indentación}">` de ancho completo y `min-h-10`; las demás son `<div>` sin rol ni foco. Roving tabindex entre elegibles (tabIndex 0 en la elegida o, sin elección, en la primera elegible; −1 en el resto). Teclado (screen.md: «flechas ↑ ↓ … + Espacio → la elige»): `ArrowDown` / `ArrowUp` (wrap), `Home` / `End` **mueven solo el foco** (y el tab stop); `Espacio` o click **eligen** la enfocada; `Enter` sobre una línea no hace nada; `ArrowLeft` / `ArrowRight` no se interceptan (quedan para el scroll horizontal). Helper `moveLine(index, key, count)` sobre `moveRadio` limitado a esas 4 teclas. En modo `select` el contenedor con scroll no lleva `tabIndex` (los radios son el contenido enfocable: una sola parada de Tab); en `result` y `preview` lleva `tabIndex={0}` y nombre «Código de {name} en {lenguaje}» como Big O.
- **D8 — Números y líneas no elegibles.** Números de línea `aria-hidden`, `w-7.5 flex-none pr-3 text-right font-mono text-meta text-text-dim` (`#8D99A6` ≈ 6,4:1 sobre `#0D1116`): se distinguen del texto de las líneas no elegibles (`text-text-dim`, Mono 15) por tamaño (12 vs 15 px) y posición (columna fija alineada a la derecha), sin depender del color (`NOT DOCUMENTED - needs verification`: interpretación del gap «que el número se distinga»). Líneas no elegibles en `select` y `preview`: `text-text-dim` **sin** colores de Shiki y sin hover. En `result` todas las líneas se resaltan igual (ya no hay elegibles).
- **D9 — Tags responsivos por container query.** El bloque es `@container`. Partida: el tag de la elegida es `<span aria-hidden="true" class="sticky right-0 ml-auto bg-game-bug-hunt-tint pl-3 font-mono text-meta-strong text-game-bug-hunt">◀<span class="hidden @lg:inline"> tu elección</span></span>` (glifo fijo al borde visible del scroll en < 32rem, texto completo desde 32rem); el estado accesible lo dan `aria-checked`, la línea de aviso y el botón. Resultado / preview: tag `basis-full pl-12 @lg:ml-auto @lg:basis-auto @lg:pl-5 @lg:flex-none` (bajo la línea en < 32rem, al margen desde 32rem, como las notas de Big O) con glifo `aria-hidden` y texto visible; la línea tiene `aria-describedby` hacia el tag.
- **D10 — El fix sigue a la pestaña.** `Result` y `Preview` guardan `language` (inicial: `result.code_language` / `'js'`) y lo actualizan con `CodeBlock.onLanguageChange`; `FixDiff` muestra `fix[language]`. Sin `publicView` en el `Result` no hay pestañas: el fix queda en `result.code_language`.
- **D11 — `formatCall` / `formatValue` pasan a `shared/`.** Se mueven a `src/shared/format.ts` (sin depender de `generator/types`: `type TestArg = number | readonly number[]`, `type TestValue = number | boolean | readonly number[]`) y se agrega `formatArgs(input)` (`'[3, 7, 2], 4'`, para el texto accesible). `src/generator/format.ts` queda como `export { formatCall, formatValue } from '../shared/format';` (los imports del generador, `generator/index.ts` y `format.test.ts` no cambian). Así la llamada que ve el jugador es la misma que arma la explicación del generador.
- **D12 — Preview.** Raíz `<div lang>`; especificación (`h3` «qué debería hacer»), `CodeBlock` modo `preview` (`highlight={false}`, no elegibles en `text-text-dim`, línea del bug con fondo `bg-game-bug-hunt-tint`, `shadow-bar-bug-hunt` y tag «🐛 línea del bug»), chips «tipo: …» (accent) y «mutación: {from} → {to}» (`Badge variant="chip"`), tests visibles (`h3` «tests», **sin** la fila del oculto: el test que falla se muestra entero debajo), test que falla (`h3`), fix (`h3`, sigue a la pestaña, D10) y «Por qué falla» (`h3`) con los pasos en `language`. Las 3 pestañas son la única interacción (excepción de Big O, `game-boards` 1.6.0); sin radios, hints ni regiones vivas.
- **D13 — `Result` sin `publicView`.** Si `publicView` es `undefined` o `null`, se omiten pregunta, especificación, pestañas y código; test que falla, fix (en `result.code_language`), pasos y chip se muestran igual (no se lanza error).
- **D14 — Carga de Shiki.** Igual que Big O D11: `loadTokenizer()` memoiza la promesa; si rechaza, limpia la memoria y el bloque queda sin color. Un tokenizer que lanza o devuelve otra cantidad de líneas deja el bloque sin color. Shiki nunca se importa de forma estática: el admin importa `@nerdose/game-bug-hunt/client` completo y, como `Preview` pasa `highlight={false}`, nunca dispara la carga.
- **D15 — Botón confirmar.** Sin línea: texto «Elegí una línea», `aria-disabled="true"` (la etiqueta ya dice el motivo); con línea: «Confirmar línea {n}» + `<span aria-hidden="true">→</span>`; `pending`: «Confirmando…» y `aria-disabled="true"`. Nombre de archivo de las pestañas con `fileNames(function_name)`: `maxIndex` → `max-index.js` / `max_index.go` / `MaxIndex.java`.
- **D16 — Reset por desafío.** `Game` usa `codeKey = js\0go\0java` como Big O: un desafío nuevo reinicia línea, pestaña (a `codeLanguage ?? 'js'`) y aviso; un cambio de `locale` / `t` / `publicView.spec` no reinicia nada. `state = {}` siempre arranca sin selección (CA-5: la selección es estado local del componente; al salir y volver el `Game` se remonta vacío).
