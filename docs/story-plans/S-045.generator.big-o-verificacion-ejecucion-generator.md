#### Convención `challenge-generation` (reglas aplicables, verbatim)

- The seed is `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")` with `date` as `YYYY-MM-DD`, feeding `pure-rand` (xoroshiro128+). `Math.random()` and the current time are never used for generation.
- `GENERATION_MAX_ATTEMPTS` defaults to 20 and is configurable by env; `attempt` goes from 0 to `GENERATION_MAX_ATTEMPTS - 1`.
- `generateForDate` accepts `firstAttempt` and a `regenerate` mode (REQ-008). Regeneration starts at `max(challenges.attempt)` for the (`game_id`, `date`) + 1, tries up to `GENERATION_MAX_ATTEMPTS` candidates (never repeating a seed) and returns the verified candidate as `draft` instead of approving it; the queue worker performs the atomic replacement.
- A candidate is inserted as `draft` first, then `verify()` runs. It becomes `approved` only if `verify()` returns `ok: true`; the full log is stored in `challenges.verification`. Otherwise it becomes `rejected`.
- `challenges.number` is computed with `@nerdose/core` (`date - LAUNCH_DATE + 1`) at insert time. `generator_version` is stored with every challenge.
- Never generate for `today` or past dates. If a day arrives without a challenge the day is neutral.
- If tomorrow's challenge for a game is missing after all attempts: `UPSERT generation_failures` (one row per game and date, with `attempts` and `last_reason`). That row is the alert: the admin shows it in Próximos desafíos; nothing is sent (ADR-017).
- The `generator` imports only `./generator` (and `./definition` if needed) of the game packages, and makes no HTTP requests to external services.

Registro (verbatim): "Grep Grid registers as `{ gameId: 'grep-grid', generator, payloadSchema, version: 'grep-grid@1' }`". Para Big O, la decisión 11 del REQ fija `{ gameId: 'big-o', generator, payloadSchema, version: 'big-o@1' }`.

#### Convención `code-runner` del `generator` (reglas verbatim)

- The runner uses `execFile` (never `exec` with a shell), with timeout 10 000 ms, and runs as a non-root user.
- Arguments are never built from untrusted strings; code goes in files, not in the command line.
- A timeout, a non-zero exit or a compile error is a failed check (candidate `rejected`), not an exception that stops the job: `runInLanguage` returns `ok: false` and never throws for a problem of the snippet.
- Only the `generator` imports `@nerdose/polyglot`. `./definition` and `./client` entries of games never import it, nor `node:child_process`.
- Required toolchains: Node 24, Go >= 1.25, JDK 21. Versions are not silently substituted.
- The runner makes no network calls; network isolation and resource limits are defined with the hosting (deferred).
- **logging**: log language, duration and exit status at `debug`; never the full source at `info`.
- **testing**: tests that run toolchains are integration tests and require them installed; a CI job compiles the emitted code.

Entorno del hijo (verbatim): "Every `execFile` uses `timeout`, `killSignal: 'SIGKILL'`, `maxBuffer: 1_048_576`, `encoding: 'utf8'` and a minimal environment (`PATH`, `HOME`, `GOCACHE`, `GOPATH`, `TMPDIR`, only the defined ones: never `DATABASE_URL` or `GENERATOR_SECRET`)."

`checkToolchains` (verbatim): "`checkToolchains(): Promise<{ js, go, java }>` (each `{ ok, version }`) runs `node --version`, `go version` and `java -version` (read from stderr) and never throws if one is missing."

#### Convención `testing` (reglas aplicables, verbatim)

- One shared container per suite, started in `globalSetup`. Never start a container in `beforeAll` per file or inside an `it`.
- Do not mock the database or `postgres.js` in integration tests. Real PostgreSQL 16 only.
- Every file resets the database in `beforeAll` and owns its fixtures. No test depends on data left by another file.
- Fixtures use the owner role; the code under test uses `nerdose_api` or `nerdose_generator`.
- No wall-clock sleeps to wait for a condition. Await the observable condition or use `Wait.*` strategies.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Keep log output quiet with `LOG_LEVEL=silent`.
- Jobs are exercised through their run function with a real `Db` and fake clock; the croner schedule is not waited on.

#### Convención `logging` (extracto)

- `logger.info({ context }, 'message')`: primer argumento, objeto de contexto; segundo, mensaje corto y **estático**, sin interpolar.
- `warn`: "Something unexpected but recoverable (retry, fallback)".
- Los eventos de dominio del `generator` usan PascalCase (`ChallengeGenerated`, `ChallengeRejected`, `ChallengeGenerationFailed`). Los de operación, una frase (`Database unavailable at startup`, `Gap generation failed`, `Job finished`).

#### Convención `env-config` (extracto)

- Nunca leer `process.env` fuera de `src/config/env.ts`. `test/env-isolation.test.ts` lo verifica sobre todo `src/`.

### ADRs Relevantes

#### ADR-007: Generator como worker y pipeline de generación

Decisión: el `generator` es un proceso long-running con croner que mantiene 14 días aprobados y verificados por adelantado, con seed HMAC e intentos acotados. La verificación de juegos de código ejecuta en JS, Go y Java.

Reglas de Implementación (verbatim, completas):
- `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
- `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
- Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
- Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
- Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
- El seed MUST ser `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`, con `date` en formato `YYYY-MM-DD`. `GENERATOR_SECRET` MUST existir solo en el entorno del `generator`.
- `GENERATION_MAX_ATTEMPTS` MUST valer 20 por defecto y ser configurable por variable de entorno.
- `fill` MUST generar solo para fechas en `[today+1, today+14]`. MUST NOT generar para `today` ni para fechas pasadas.
- `challenges.number` MUST calcularse con `core` (`date − LAUNCH_DATE + 1`) al insertar.
- Un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`.
- El runner MUST usar `execFile` (nunca `exec` con shell), timeout de 10 000 ms, y MUST correr como usuario no root.
- Los toolchains MUST ser Node 24, Go ≥ 1.25 y JDK 21.
- El `generator` MUST NOT hacer requests HTTP a servicios externos. No tiene salida de red fuera de la base (ADR-017).
- El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)

- `generateForDate` MUST hacer `await` de `verify`; los generadores síncronos siguen siendo válidos.
- `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
- `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

#### ADR-017: Alertas registradas en el admin (reglas aplicables, verbatim)

- Las alertas MUST NOT salir del sistema en v1: ningún servicio MUST enviar mails, webhooks ni notificaciones push.
- La falla de generación MUST registrarse con `INSERT … ON CONFLICT (game_id, date) DO UPDATE SET attempts, last_reason, updated_at`. Una corrida posterior para la misma fecha MUST actualizar esa fila, no crear otra.

### Decisiones de diseño de REQ-009 aplicables (verbatim)

- **Decisión 11 (extracto).** "`apps/generator/src/games/registry.ts` (`{ gameId: 'big-o', generator, payloadSchema, version: 'big-o@1' }`)".
- **Decisión 14 (extracto).** "README de arranque: Node 24, Go ≥ 1.25 y JDK 21 en el `PATH` del `generator` (el arranque no los valida: un toolchain faltante se ve como `run_<lang>` fallido con `toolchain_missing`, y el `generator` loguea un `warn` al arrancar si `go version` o `java -version` fallan). Los tests de `polyglot` y de `verify` que ejecutan toolchains son de integración y **fallan** (no se saltean) si falta uno, con un mensaje que lo nombra."
- **Formato de `reason`** (plan `S-045.games`, decisión 2, implementado): `reason` es el `name` del primer check que falla. Si el primero es `run_<lang>`, es `'run_<lang>: <kind>'`: `'run_go: timeout'`, `'run_java: compile_error'`, `'run_js: toolchain_missing'`, `'run_js: invalid_output'`. Los motivos del ajuste van como prefijo del `detail` (`'ambiguous_fit: …'`), y `reason` es el nombre del check (`'fit_unambiguous'`).
- **Orden de los 13 checks** (`VERIFY_CHECKS`, implementado): `texts_bilingual`, `code_shape`, `variety_recipe`, `variety_answer`, `run_js`, `run_go`, `run_java`, `counts_agree`, `counts_in_range`, `example_matches_run`, `fit_quality`, `fit_unambiguous`, `fit_matches_answer`.
- **Escala** (`SCALE`, implementada): `o_1`, `o_log_n`, `o_n` y `o_n_log_n` → 2⁸…2¹⁶ (9 puntos); `o_n2` → 2⁶…2¹²; `o_n3` → 2⁴…2⁹; `o_2n` → 10…20; `o_n_fact` → 4…10.
- **`detail` de los checks** (implementado):
  - `run_<lang>` fallido: `'<kind> (<durationMs> ms): <primera línea informativa de stderr, ≤ 200 caracteres>'`, o sin `': …'` si `stderr` está vacío;
  - `counts_agree` fallido: `'differs at n=<n>: js=<a> go=<b> java=<c>'`;
  - `fit_unambiguous` fallido: `'ambiguous_fit: best=<op> (<cv>) second=<op> (<cv>) min=<umbral>'`;
  - `fit_matches_answer`: `'best=<op> answer=<op>'`.

### Contexto de Base de Datos

Sin migración. Tablas que escribe el pipeline (ref. `docs/db-schemas/nerdose-db.md`):

```dbml
Table challenges {
  id uuid [pk, default: `gen_random_uuid()`]
  game_id game_id [not null]
  date date [not null, note: 'Día UTC en que se juega']
  number integer [not null, note: 'date − LAUNCH_DATE + 1; igual para los 5 juegos ese día']
  payload jsonb [not null, note: 'Contenido completo CON la solución y textos {es,en}. Inmutable desde approved. Nunca sale al jugador antes de terminar']
```

### Contexto de Flujos

**`generacion-diaria`** (`docs/flows/generacion-diaria.md`). Pasos aplicables (verbatim):
- Paso 2: "`challenges` — SELECT (`game_id`, `date`) WHERE `date BETWEEN today+1 AND today+14` AND `status IN ('approved','published','voided')`. Los pares que faltan de (registry × fechas) son los huecos."
- Paso 3: "`seed = HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")` → `pure-rand`. … `candidate = games[game_id].generator.generate({ date, seed, history })`. … **Tabla:** `challenges` — INSERT (`game_id`, `date`, `number = date − LAUNCH_DATE + 1`, `payload`, `status = 'draft'`, `generator_version`, `seed`, `attempt`) … **Operación de BD (ok):** `challenges` — UPDATE `status = 'approved'`, `verification` … **(no ok):** `challenges` — UPDATE `status = 'rejected'`, `verification`."
- Paso 4: "`generation_failures` — INSERT (`game_id`, `date`, `attempts`, `last_reason`) ON CONFLICT (`game_id`, `date`) DO UPDATE `attempts`, `last_reason`; `attempts` = `GENERATION_MAX_ATTEMPTS` de la corrida y `last_reason` = `verification.reason` del último candidato."
- Manejo de errores: "El código emitido no compila o el runner hace timeout (10 s) → `verification.ok = false` → Candidato `rejected`; siguiente `attempt`."

Lo que cambia con esta story, según el REQ (escenario "generar y verificar el desafío del día"):
- `big-o` entra en el registry, así que el paso 2 detecta sus huecos;
- la historia de big-o es `[D - 30, D + 30]` sin `D` (ya implementado);
- `verify` ejecuta los 3 lenguajes en paralelo y corre los 13 checks;
- "Toolchain ausente, timeout o error de compilación → check `run_<lang>` fallido, candidato `rejected`, el job sigue (nunca excepción)".

**`regenerar-desafio`** (`docs/flows/regenerar-desafio.md`). Pasos aplicables (verbatim):
- Paso 3: "igual que `generacion-diaria`, con `attempt` desde `max(attempt) + 1` y hasta `GENERATION_MAX_ATTEMPTS` intentos."
- Paso 4: "1. `challenges` (viejo) — UPDATE `status = 'rejected'`, `verification = verification || '{"reason":"regenerated"}'` 2. `challenges` (nuevo) — UPDATE `status = 'approved'`, `verification` … 4. `generation_requests` — UPDATE `status = 'done'`, `new_challenge_id`, `processed_at = now()`".
- Errores: "Ningún candidato pasa la verificación → `generation_requests.status = 'failed'`, `error` → El viejo sigue `approved`; … no se escribe `generation_failures`".

REQ: "La regeneración tarda segundos más que en los otros juegos (3 subprocesos por candidato); el polling de 5 s ya lo cubre."

### Tarea 2: `warn` al arrancar si falta Go o Java

#### Descripción

**Notas de Implementación:**
```ts
import { checkToolchains, type ToolchainReport } from '@nerdose/polyglot';
import type { Logger } from 'pino';

const REQUIRED = [
  { toolchain: 'go', required: 'Go >= 1.25' },
  { toolchain: 'java', required: 'JDK 21' },
] as const;

/** El arranque no valida los toolchains (REQ-009): avisa y sigue; Big O rechaza con run_<lang>: toolchain_missing. */
export async function warnMissingToolchains(
  log: Logger,
  check: () => Promise<ToolchainReport> = checkToolchains,
): Promise<void> {
  let report: ToolchainReport;
  try {
    report = await check();
  } catch (err) {
    log.warn({ err }, 'Toolchain check failed');
    return;
  }
  for (const { toolchain, required } of REQUIRED) {
    if (!report[toolchain].ok) log.warn({ toolchain, required }, 'Toolchain missing at startup');
  }
}
```

- En `test/startup.test.ts`, el factory `deps()` existente no pasa `checkToolchains` (usa el real; los toolchains están instalados). Los tests nuevos TS-14 y TS-15 lo pasan explícito y detienen `scheduler` y `queue` en un `finally`, igual que los existentes.
- TS-14: para verificar el orden, `lines().findIndex((l) => l.msg === 'Toolchain missing at startup') < lines().findIndex((l) => l.job === 'sync_banks')`.
