### Arquitectura del servicio (`docs/architectures/games/overview.md`, copiado lo aplicable)

> Los cinco paquetes de juego `packages/games/<game_id>` (`@nerdose/game-devdle`, `-grep-grid`, `-timeline`, `-big-o`, `-bug-hunt`). Cada uno implementa el contrato `GameDefinition` de `@nerdose/core` y expone tres entradas separadas: `./definition` (servidor: la usa la `api`), `./client` (React: `Instructions`, `Game`, `Result` y `share()`; la usan `web` y `admin`) y `./generator` (`generate` y `verify`; lo usa el `generator`). ADR-003 y ADR-006.
> **Convenciones por entrada:** `definition` y `generator` siguen `game-registry`, `validation` y `testing` (copias de `api`); `client` sigue `styling`, `accessibility`, `testing-unit` y `game-clients` (copias de `web`).

### Convenciones activas (extractos aplicables, verbatim)

#### `game-package`

- `./client` — May import: `@nerdose/core` (`.`), `zod`, `react`, `@nerdose/ui`, `shared/`, types from `./definition`. Must not import: `@nerdose/polyglot`, `node:*`, `./generator`, runtime code of `./definition` that carries solutions.
- `./client` exports: React components `Instructions`, `Game`, `Result` and `share(result, number)`.
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry.
- `share(result, number)` never includes the solution and ends with `nerdose.dev`.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk.
- Game-specific dependencies stay inside the game package (Shiki for `big-o` and `bug-hunt`…).

#### `game-clients` (contrato que el paquete cumple)

- `GameClient` is the shape of the `./client` entry defined by the game contract: React components `Instructions`, `Game`, `Result` and `share(result, number): string`. The exact props of those components are owned by the game packages and `@nerdose/core`; the app passes them through and does not reinterpret them.
- Moves go through the game's `moveSchema` (Zod) before `POST .../move`.
- Shiki (big-o, bug-hunt) and dnd-kit (timeline) are dependencies of the game packages and are loaded in the game's own chunk. The shell never imports them.
- **Admin preview:** Each `client` also exports `Preview` with props `{ payload, language }` (REQ-008): read-only, shows the board with the solution overlaid, no API calls and no play state. Contract: `Preview(props: { payload: unknown; language: Locale })`. It (a) parses `payload` with the game's own `payloadSchema` and lets the error propagate if it is invalid, (b) translates its texts with the package's own `i18n` resources according to `language` (it needs neither react-i18next nor the host's `t`), (c) uses `h3` headings and a root `<div lang={language}>` with no landmark of its own, (d) has no controls or effects (no `fetch`, no storage, no play state).
- `web` never mounts `Preview`. The `client` never receives the solution before the round ends in `web`.
- Share text is never built by the shell; it always comes from the game's `share()`.
- Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`.
- `GameProps.feedback: unknown | null` (REQ-005): clients that do not need it ignore it.

#### `styling`

- Use only the tokens (DS first). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- Text and interactive-element contrast meets WCAG 2.1 AA against the surface it sits on (4.5:1 text, 3:1 large text and UI components). Verify any new color pair.
- Focus is always visible: use `focus-visible:` rings with `--color-accent`; never `outline-none` without a replacement.
- State is never conveyed by color alone. Respect `prefers-reduced-motion`.
- **When NOT to use Tailwind classes:** values from data (set a CSS variable with `style`); third-party rendered output (Shiki markup): style through a scoped CSS selector in the owning package.
- Mobile-first from 320 px; no horizontal scroll at 320 px; touch targets ≥ 44 × 44 px.
- **REQ-003:** no global media queries (flex-wrap / auto-fit); static check: component `.tsx` must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).

#### `accessibility`

- Use native elements first; ARIA only when no native element fits. No interactive element built from a `<div>`/`<span>` with a click handler.
- Everything operable with the mouse is operable with the keyboard, logical tab order, no traps, visible focus.
- Feedback that uses color (win/loss) is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
- Result, errors and notices appear in `role="status"` (polite) or `role="alert"` regions. Dynamic updates are announced via live regions; do not move focus unexpectedly.
- Contrast ≥ 4.5:1 text (3:1 large / UI boundaries). Each game can be completed with the keyboard alone (NFR-U03). axe-core reports zero violations in unit checks.

#### `testing-unit`

- Query by role, label or visible text; `data-testid` only when no accessible query exists. Use `userEvent`, not `fireEvent`.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- Fixtures use the API's `snake_case` names. No snapshot tests of large DOM trees. Tests do not rely on the real date or timers.

#### `_base` (Node) — extracto

- Archivos `kebab-case`; sin `any` salvo bordes con librerías sin tipos (comentar el porqué); `async/await`; comentarios solo para el porqué.

#### `error-handling` — extracto

- Los errores esperados del juego no se lanzan desde el client: un `publicView` / `result` / `payload` inválido deja propagar el `ZodError` (mismo criterio que los otros clients); los rechazos del servidor llegan como `moveError` y se muestran en la línea de aviso.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Front: «Shiki (core, motor de regex JS, gramáticas js/go/java), cargado lazy solo en Big O y Bug Hunt.»
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

#### ADR-003: Monorepo (reglas aplicables, verbatim)

- Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
- `apps/web` y `apps/admin` MUST importar solo `./client`.
- `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)

- MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- `toPublic` MUST NOT incluir: … `answer` de Big O …
- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
- `Preview` MUST ser de solo lectura: valida `payload` con el schema del juego, traduce con los recursos del propio paquete según `language`, y no hace `fetch`, no usa storage ni estado de partida. `web` MUST NOT montarla (necesita el `payload` completo, que solo devuelve `/api/admin/*`). El admin la monta en ES y EN lado a lado; un juego sin `Preview` cae a la vista genérica del payload (REQ-008).
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015: Contratos JSON y errores (reglas aplicables, verbatim)

- Todas las propiedades JSON … MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
- Los enums MUST serializarse con sus valores exactos del dominio (`code_language`: `js | go | java`; `locale`: `es | en`).

#### ADR-014: Métricas y analítica

- `track('share:<game_id>')` lo llama el host (`web`) después de compartir; el client no importa `track` (regla vigente para los otros clients).

### Decisiones de diseño de REQ-009 aplicables (verbatim)

- **Decisión 5:** `toPublic(p, locale)` → `{ code: p.code, options: BIG_O_OPTIONS }` con las 8 opciones **en orden fijo** (`o_1 … o_n_fact`, nunca dependiente de la respuesta). `result(p, s, locale)` → `{ win, score, answer, chosen_option: s.option, code_language: s.language, recipe_category, trap_option, explanation: { steps: string[], line_notes: [{ line, text }], tip: string | null, example } }` con los textos en `locale`. `line_notes[].line` vale para los 3 lenguajes; `example` es el recuadro "en números" del prototipo (`n`, operaciones exactas de la receta en ese `n` y las que daría la trampa; `trap_ops = null` si no hay trampa).
- **Decisión 6:** `BigOState = { language?, option? }`; mientras la Play está `in_progress` el estado sigue vacío (la opción seleccionada y el lenguaje visible viven solo en el cliente, CA 3 y 8).
- **Decisión 7:** `share(result, number)` = `🧮 Big O #${number}` / `${r.win ? '🟩' : '🟥'} ${LANGUAGE_LABEL[r.code_language]}` / `nerdose.dev`, idéntico en es y en, sin la opción elegida ni la correcta (CA 10). Etiquetas de las opciones en `shared/options.ts` (hoy `shared/labels.ts`), neutrales al idioma.
- **Decisión 12 (web, contrato que el client recibe):** `ClientBaseProps.codeLanguage: CodeLanguage` (genérico, lo usan Big O y Bug Hunt; los demás lo ignoran) = `session.preferred_code_language ?? 'js'`. El `Game` arranca en ese lenguaje; cambiar de pestaña es estado local y no hace requests ni persiste nada (CA 3). La opción seleccionada es estado local que sobrevive al cambio de pestaña y de idioma (`keepPreviousData` ya conserva el `Game` montado) y se pierde al salir (CA 8). El `Result` muestra el código en `result.code_language` (pestañas también disponibles) y recibe `publicView.code` (`ResultProps.publicView` ya existe).
- **Decisión 13:** Código como texto seleccionable con numeración de líneas y resaltado de Shiki (core + motor de regex JS + gramáticas js/go/java, importado de forma dinámica dentro del paquete: chunk propio de `/big-o`, ADR-002). Mientras Shiki carga, o si falla, se muestra el mismo código sin color. El tema de colores sale de los tokens del DS y cumple AA sobre el fondo del bloque. El bloque de código tiene scroll horizontal propio; la página no (CA 21, 320 px). Pestañas de lenguaje con el patrón `tablist` (flechas ← → y foco visible); las 8 opciones como grupo de selección única operable con teclado y botón "Confirmar" deshabilitado hasta elegir; `moveSchema.parse({ language, option })` antes de `onMove`. Resultado: veredicto con ícono y texto, opción elegida y correcta marcadas con ícono y texto, no solo color; pasos numerados; notas por línea junto al código; recuadro "en números" si hay `example`; `tip` si existe. `Preview({ payload, language })` para el admin: código con pestañas, respuesta, `trap_option` y la explicación en `language`; solo lectura, sin `fetch` ni storage.
- **Revisión UX (cierra puntos abiertos):** opciones como `radiogroup`; `Preview` del admin en texto plano, sin resaltado; emoji del share 🧮; recuadro «en números» y consejo solo cuando la receta los trae (`example` / `tip`).

### Flow Context

#### `abrir-y-retomar-juego` (paso 3, extracto)

```
alt challenge_status = none → "sin desafío hoy"          (web; el client no se monta)
else challenge_status = voided → aviso de anulación      (web)
```

### Decisiones de este plan (derivadas; `NOT DOCUMENTED - needs verification` donde se indica)

- **D1 — `codeLanguage` opcional en el client.** `ClientBaseProps.codeLanguage?: CodeLanguage`, default `'js'` (mismo default que `session.preferred_code_language ?? 'js'`). Solo se lee al montar el `Game` (estado inicial) y al cambiar de desafío; si cambia con el `Game` montado (p. ej. el selector de preferencias) la pestaña visible no salta.
- **D2 — Tema de Shiki por variables CSS.** `createCssVariablesTheme` + `codeToTokensBase`; el client renderiza sus propias líneas (número, código, nota) y cada token como `<span style={{ color: token.color }}>` con `color = var(--shiki-…)`. Las variables `--shiki-*` se definen en el `style` del contenedor del bloque (`SHIKI_VARS`) apuntando a tokens del DS: `--shiki-foreground: var(--color-text)`, `--shiki-background: var(--color-surface-sunken)`, `--shiki-token-keyword: var(--color-game-big-o)`, `--shiki-token-function: var(--color-game-big-o-light)`, `--shiki-token-constant: var(--color-game-big-o-muted)`, `--shiki-token-parameter: var(--color-text)`, `--shiki-token-string: var(--color-text-body)`, `--shiki-token-string-expression: var(--color-text-body)`, `--shiki-token-comment: var(--color-text-dim)`, `--shiki-token-punctuation: var(--color-text-muted)`, `--shiki-token-link: var(--color-game-big-o-light)`. Así no hay hex, ni CSS propio, ni estilos de Shiki sobre el DOM: la estructura plana y la resaltada son el mismo árbol (sin salto de layout). Es la forma de cumplir «style through a scoped CSS selector in the owning package» sin archivo CSS (`styling`: «set a CSS variable with `style`»).
- **D3 — Tokens Big O ausentes → tokens existentes.** Pestaña activa `bg-game-big-o-border` (`#1B2E45`; texto `#E6EDF3` ≈ 11,7:1); línea resaltada `bg-game-big-o-tint` (`#0B1522`) + `shadow-[inset_3px_0_0_var(--color-game-big-o)]`; nota de línea `text-game-big-o-light` (`#9ACFFF`, ≈ 11:1 sobre `#0B1522`); número de paso `bg-game-big-o-border` + `text-game-big-o-light` (≈ 8,4:1); números de línea `text-text-dim` (`#8D99A6`, ≈ 6,4:1 sobre `#0D1116`, cumple el ≥ 4,5:1 de la pantalla). Valores verificados por test contra `tokens.css` (TS-18). No se toca `@nerdose/ui` (no es servicio afectado).
- **D4 — Tipografía.** Código `font-mono text-body leading-loose` (15px / lh 2); opción `font-mono text-game-item` con `font-normal` (sin elegir), `font-bold` (elegida) y `font-extrabold` (correcta); pestaña `font-mono text-label-comment` (+ `font-bold` activa); nombre de archivo `font-mono text-meta text-text-dim`; nota `font-mono text-meta`; número de paso `font-mono text-label-comment font-bold`; paso `font-sans text-body text-text-body`; consejo `font-sans text-body-sm text-text-muted`; pregunta/`h1` `font-mono text-title-section lg:text-title-section-lg` (26 → 32 px con tracking negativo; no hay rol de 30 px); título del panel «Paso a paso» `font-mono text-title-panel`. `tab-size: 4` como `style={{ tabSize: 4 }}` en el cuerpo del código (Tailwind v4 no trae utilidad; `NOT DOCUMENTED - needs verification`: si la versión instalada la tiene, usarla).
- **D5 — Layout con DOM en orden mobile.** `Game` y `Result` usan `flex flex-col gap-6 lg:grid lg:grid-cols-12 lg:items-start` (patrón de Grep Grid/Timeline, `lg:` = 1024 px ≈ el breakpoint efectivo de Big O, 1028 px, de `grid.md`), con los bloques **en el DOM en el orden de mobile** y ubicados en desktop con `lg:col-start-*` / `lg:row-start-*`. `Game`: A = tabs+código+opciones+línea de aviso (`lg:col-span-7 lg:row-span-3`), B = «Confirmar respuesta» (`lg:col-span-5 lg:col-start-8 lg:row-start-2`), C = card-reglas (`lg:col-span-5 lg:col-start-8 lg:row-start-1`), D = `aside` del host (`lg:col-span-5 lg:col-start-8 lg:row-start-3`). `Result`: A = pregunta+código+opciones (`lg:col-span-7`), B = panel `aside` «Paso a paso» (`lg:col-span-5 lg:col-start-8 lg:row-start-1 lg:row-span-2`), C = `footer` del host (`lg:col-span-7 lg:col-start-1 lg:row-start-2`), D = `aside` del host (`lg:col-span-5 lg:col-start-8 lg:row-start-3`). Así el orden de foco coincide con el de lectura en mobile (el viewport primario) y en desktop recorre izquierda → derecha por fila.
- **D6 — Opciones como `radiogroup` propio.** `<div role="radiogroup" aria-labelledby>` con 8 `<button type="button" role="radio" aria-checked>`; roving tabindex (tabIndex 0 en la elegida o, sin elección, en la primera; −1 en el resto); ArrowRight/ArrowDown → siguiente con wrap, ArrowLeft/ArrowUp → anterior con wrap, Home/End → primera/última: mueven el foco **y** eligen (patrón APG radio); Espacio/Enter/click eligen la enfocada. Se eligió botón con rol en lugar de `<input type="radio">` para controlar el borde estable y el comportamiento de teclado de forma determinista en tests (mismo criterio de roving tabindex que el tablero de Grep Grid).
- **D7 — Trampa en la preview:** `border-2 border-dashed border-game-big-o-muted` (≈ 7,4:1 sobre `bg-surface`), sin relleno, texto `text-text`, etiqueta «trampa» / «trap» debajo del valor; el patrón punteado + texto cubre NFR-U04.
- **D8 — Pestañas en la preview.** La story (CA-6) y `o-02-detalle-desafio` piden «código en texto plano **con pestañas**»; el contrato `game-clients` (d) y el DS («sin botones, sin roving tabindex») dicen «sin controles». Gana lo específico (story + screen): las 3 pestañas son estado de vista local, sin efectos (sin `fetch`, storage ni estado de partida); no hay radios, hints ni regiones vivas. Se documenta como excepción en `game-boards` (Tarea 10).
- **D9 — Números de «en números».** `n` se muestra tal cual (`String(n)`: es argumento de `f`, «f(1024)»); `ops` y `trap_ops` con `new Intl.NumberFormat(locale)` (es: `10.240`, `1.048.576`; en: `10,240`, `1,048,576`). Los textos de los pasos, notas y consejo se renderizan como texto plano (llegan resueltos del servidor; no se parsea markup).
- **D10 — `Result` sin `publicView`.** Si `publicView` es `undefined` o `null`, se omiten pregunta, pestañas y código; opciones y explicación se muestran igual (no se lanza error).
- **D11 — Carga de Shiki.** `loadTokenizer()` memoiza la promesa a nivel de módulo; si rechaza, limpia la memoria (un montaje posterior reintenta) y el bloque actual queda sin color. Un tokenizer que lanza o que devuelve una cantidad de líneas distinta a la del código deja el bloque sin color. Shiki nunca se importa de forma estática: el admin importa `@nerdose/game-big-o/client` completo y, como `Preview` pasa `highlight={false}`, nunca dispara la carga.
- **D12 — Notas por línea responsivas por container query.** El bloque es `@container`; la nota tiene `basis-full pl-12 @lg:ml-auto @lg:basis-auto @lg:pl-5` y la línea `flex flex-wrap items-center @lg:flex-nowrap`: bajo la línea cuando el bloque mide < 32rem (mobile, 320–400 px) y al margen derecho desde 32rem (desktop 7/12 ≈ 680 px; card del admin 6/12 ≈ 540 px). No hay breakpoint global.
