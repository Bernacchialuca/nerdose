### Convenciones aplicables (extracto)

#### `content-sync` (verbatim, update REQ-006 y reglas)

- `timeline_facts.json` is now required (end of "optional until FG-5"). `sync_banks` loads `terms` and then `timeline_facts` in the **same transaction**, with the same modes (`approved`, `to_rejected`, `insert_rejected`) and `ON CONFLICT (wikidata_id) DO UPDATE ... WHERE status <> 'rejected'`; it never writes `last_used`.
- `summary` keeps the ADR-016 totals (`dataset_version, inserted, updated, unchanged, kept_rejected, skipped`) and adds `by_bank: { terms, timeline_facts }`. The `term` uniqueness rule does not apply to facts. `sameContent` for facts compares `label`, `category`, `event_date`, `date_precision`, `note` and `sitelinks`.

UPSERT rules:

| Case | Result |
|---|---|
| New `wikidata_id` | Inserted with the dataset status |
| In database `rejected` | Unchanged (stays `rejected`) |
| In database `approved`, dataset `rejected` | Becomes `rejected` with its `rejection_reason` |
| In database but not in dataset | Not deleted |
| Any case | `last_used_devdle`, `last_used_grep` and `last_used` are never touched |

Rules:
- `sync_banks` runs at startup (before `fill`) under advisory lock `sync_banks` and records `job_runs` with `summary` `{ dataset_version, inserted, updated, unchanged, kept_rejected }`.
- The load is `INSERT ... ON CONFLICT (wikidata_id) DO UPDATE` with the table above and is idempotent.
- The dataset is validated with Zod on load; an invalid file fails the job, not a partial load.
- `api` and `generator` never request `*.wikidata.org`, `*.wikipedia.org` or `*.wiktionary.org`.
- The `generator` is the only process that writes `terms` and `timeline_facts` (the `api` can only update `status` and `rejection_reason` through its role).
- Bank items rejected by the `api` after a void stay `rejected` across syncs.
- Integration with **testing**: idempotency test (two runs, same state) and `rejected` precedence.

#### `orm` (reglas aplicables, verbatim)

- No direct `db` calls from HTTP handlers, jobs or use-case functions. Always go through a module repository.
- One repository per domain module. Never share a repository across unrelated modules.
- Use types inferred from the schema (`typeof table.$inferSelect`) or from `@nerdose/db`. No hand-written types that duplicate the schema.
- Every `jsonb` column MUST be parsed with the Zod schema of its owner when read or written. The database does not validate it. → `note` se escribe desde un `TimelineFactItem` ya validado por `timelineFactsFileSchema`.
- Day columns are `date` (UTC day) and instants are `timestamptz`. Do not convert them with local timezones. → `timelineFacts.eventDate` y `lastUsed` usan `mode: 'string'` (`'YYYY-MM-DD'`).
- Raw SQL only for what Drizzle cannot express. Document why in a one-line comment.
- Each service MUST only write the tables and columns its role allows (ADR-004).

#### `testing` (reglas aplicables, verbatim)

- Do not mock the database or `postgres.js` in integration tests. Real PostgreSQL 16 only.
- Unit tests are for pure functions. If it does I/O, write an integration test.
- Every file resets the database in `beforeAll` and owns its fixtures. No test depends on data left by another file. (En este servicio `setupTestDb().reset()` se llama en `beforeEach`, como en `sync-banks.test.ts`.)
- Fixtures use the owner role; the code under test uses `nerdose_api` or `nerdose_generator`.
- No wall-clock sleeps to wait for a condition.
- Tests do not touch the network or Wikimedia.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.

### ADRs Relevantes

#### ADR-016: Bancos de contenido como dataset versionado (reglas aplicables, verbatim)

- `api` y `generator` MUST NOT hacer requests a dominios de Wikimedia (`*.wikidata.org`, `*.wikipedia.org`, `*.wiktionary.org`).
- Cada ítem de `timeline_facts.json` MUST tener exactamente: `wikidata_id`, `label`, `category`, `event_date` (`YYYY-MM-DD`), `date_precision`, `note` (`{es,en}`), `sitelinks`, `status`, `rejection_reason`.
- `sync_banks` MUST hacer `INSERT … ON CONFLICT (wikidata_id) DO UPDATE` con estas reglas:
  - Si el ítem en la base está `rejected`, MUST NOT cambiarlo (sigue `rejected`).
  - Si en la base está `approved` y en el dataset `rejected`, pasa a `rejected` con su `rejection_reason`.
  - MUST NOT tocar `last_used_devdle`, `last_used_grep` ni `last_used`.
  - MUST NOT borrar ítems que están en la base y no en el dataset.
- `sync_banks` MUST registrar en `job_runs` (`job = 'sync_banks'`) un `summary` con `dataset_version`, `inserted`, `updated`, `unchanged` y `kept_rejected`.

#### ADR-007: Generator worker y pipeline (reglas aplicables, verbatim)

- `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
- Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
- Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
- Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
- El `generator` MUST NOT hacer requests HTTP a servicios externos.

#### ADR-004: PostgreSQL única base con roles (reglas aplicables, verbatim)

- Los textos de contenido bilingües MUST guardarse como `jsonb` con la forma `{ "es": string, "en": string }`.
- Las fechas de día MUST ser `date` (día UTC). Los instantes MUST ser `timestamptz`.
- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.

Permisos sobre `timeline_facts` (migración `0004`): `nerdose_generator` → `SELECT, INSERT, UPDATE`; `nerdose_api` → `SELECT` y `UPDATE (status, rejection_reason)`. El generator **no** tiene `DELETE` (coherente con "nunca borra").

### Decisión de diseño de REQ-006 aplicable (verbatim, decisión 10)

> **Carga del banco en el generator (C-52; RF 13; CA 23, 24).** `ContentBanksRepository` suma `listTimelineFacts()` y `upsertTimelineFact(item, version, mode)` con los mismos modos que `terms` (`approved`, `to_rejected`, `insert_rejected`) y `ON CONFLICT (wikidata_id) DO UPDATE … WHERE status <> 'rejected'`; nunca escribe `last_used`. `syncBanks` procesa `terms` y después `timeline_facts` en la **misma transacción** (sin la regla de `term` único, que no aplica). `summary` mantiene las claves de ADR-016 como totales (`dataset_version, inserted, updated, unchanged, kept_rejected, skipped`) y suma `by_bank: { terms: {...}, timeline_facts: {...} }`, que el admin de FG-7 podrá leer. `sameContent` de hechos compara `label`, `category`, `event_date`, `date_precision`, `note` y `sitelinks`. Un `rejected` en la base sigue `rejected` (regla de servicio + trigger `bank_items_rejected_terminal`).

CA del REQ:
- **23.** DADO un dataset nuevo desplegado con 40 hechos más, CUANDO arranca el generator, ENTONCES se insertan los 40 hechos, queda registrada la carga con su versión y volver a arrancar no cambia nada.
- **24.** DADO el hecho `Docker`, que en la base está `rejected` y que el dataset trae `approved`, CUANDO arranca el generator, ENTONCES `Docker` sigue `rejected` y el `last_used` de los hechos existentes no se modifica.

### Decisiones de este plan

Tomadas al planificar porque la fuente no las fija. Revisar si no convencen.

1. **Forma de `by_bank`.** Cada banco lleva los mismos 5 contadores que los totales (`inserted, updated, unchanged, kept_rejected, skipped`), sin `dataset_version`. Los totales de primer nivel se calculan al final como suma, así ADR-016 sigue cumpliéndose y el admin de FG-7 lee `by_bank` sin ambigüedad.
2. **`skipped` en hechos.** La regla de `term` único no aplica, pero hay un caso que sí hay que saltear: un hecho `rejected` **nuevo** cuyo `event_date` no es una fecha de calendario (el schema de `content` solo lo exige a los `approved`). Insertarlo haría fallar el `INSERT` en PostgreSQL y, por ser la misma transacción, **revertiría toda la carga, `terms` incluido**. Se cuenta en `by_bank.timeline_facts.skipped`, sin log de warn (igual que los `rejected` no insertables de `terms`). Helper puro `isStorableDate(value)`: `^\d{4}-\d{2}-\d{2}$`, año ≥ 1 y fecha de calendario real.
3. **`to_rejected` con fecha no almacenable.** Si un hecho ya está `approved` en la base y el dataset lo trae `rejected` con un `event_date` no almacenable, la regla `approved → rejected` sigue valiendo. Como en ese modo el `DO UPDATE` solo escribe `status`, `rejection_reason` y `dataset_version`, el servicio pasa al repositorio el ítem con el `event_date` **guardado en la base** (`{ ...item, event_date: row.eventDate }`) para que el `VALUES` del `INSERT` sea válido. Se hace siempre en `to_rejected` (el contenido del `VALUES` es irrelevante en ese modo), no solo cuando la fecha es inválida.
4. **Orden dentro de los hechos.** No hace falta procesar los `approved` primero (no hay unicidad por `label`); se recorren en el orden del archivo (ya ordenado por `wikidata_id`).
5. **Log `ContentItemRejected`.** Se suma el campo `bank` (`'terms'` o `'timeline_facts'`) al log existente: `{ bank, wikidata_id, reason }`. El test actual usa `objectContaining`, así que no se rompe.
6. **Comparación de `note`.** `sameFactContent` compara `note.es` y `note.en` por valor (la columna `jsonb` vuelve como objeto), igual que `definition`/`summary` en `terms`. `event_date` se compara como string `'YYYY-MM-DD'` (`mode: 'string'`).
7. **Atomicidad (CA-8) en test.** Para provocar un fallo real en la fase de hechos sin mockear la base, el test crea con el rol owner un trigger temporal `BEFORE INSERT ON timeline_facts` que lanza una excepción para un `wikidata_id` concreto, y lo elimina en `finally`. Es SQL crudo **solo en el test**, documentado con un comentario de una línea.
