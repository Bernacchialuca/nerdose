# Story Plan: S-056 (ui) - Stats propias en los clients y heatmap anual

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-056](../stories/S-056.stats-propias-clients-y-heatmap.md)
- **Servicio:** ui
- **Resumen:** `@nerdose/ui` suma el componente `Heatmap`: grilla de 365 días (53 semanas × 7 días, lunes a domingo, hoy a la derecha) anclada en el `today` que manda el servidor. Completa los días vacíos, pinta 5 niveles de la rampa verde del DS (4 y 5 comparten tono), marca hoy con borde, muestra etiquetas de mes y leyenda «0 1 2 3 4 5», y da la cantidad de cada día en texto: nombre accesible por celda y línea `detalle-dia` para el día enfocado o tocado. Se navega con flechas desde un único punto de tabulación.

> **Alcance de este plan:** solo el servicio `ui` (`packages/ui`, más `docs/architectures/ui/overview.md` y `docs/reusable-code/ui/`). Queda **fuera**:
> - **`games`** (misma story, plan aparte, ya completado): `StatsSummary` y funciones de resumen de los 5 `./client` (CA-1, CA-2, CA-3).
> - **`web`** (S-057): la pantalla `/stats`, el panel `actividad` que envuelve al `Heatmap`, el título `h2` «Actividad», los textos ES/EN (caption, nombre de celda, detalle, resumen, vacío) vía i18next y el paso de `MyStats.today` / `MyStats.heatmap`.
> - **S-058**: borrar `analytics.ts` y los exports `injectAnalytics` / `track` / `AnalyticsEvent`. Este plan **no** los toca (ver Tarea 4 sobre `test/public-api.test.ts`).
> - **Design System:** en modo auto no se crean ni modifican specs del DS. La variante de 365 días es un gap **aceptado** en REQ-011 (ver «DS Gaps»).
>
> **Rutas:** las de «Archivos a crear/modificar» son relativas a `packages/ui/`, salvo las que empiezan con `docs/` (raíz del repo).

### Stack Tecnológico

- TypeScript estricto (`strict: true`, `noUncheckedIndexedAccess: true`; `tsconfig.json` extiende `../../tsconfig.base.json` con `jsx: react-jsx`), módulos ES.
- React 19 (`peerDependencies: react ^19.3.1`), sin build propio: el paquete exporta su fuente (`exports: { ".": "./src/index.ts", "./tokens.css": "./src/tokens.css" }`).
- Tailwind CSS v4 (`tailwindcss ^4.3.4`) con los tokens en el bloque `@theme` de `src/tokens.css` (`@source "./components";` hace que Tailwind escanee las clases de `src/components`).
- `clsx ^2.1.1` + `tailwind-merge ^3.7.0` vía `cn()` (extendido con `TEXT_ROLES`, `RADIUS_ROLES`, `SHADOW_ROLES` de `src/theme.ts`).
- Tests: Vitest (`vitest.config.ts`: `environment: 'jsdom'`, `setupFiles: ['./test/setup.ts']`, `include: ['test/**/*.test.ts', 'src/**/*.test.{ts,tsx}']`), `@testing-library/react ^16.3.3`, `@testing-library/user-event ^14.6.8`, `@testing-library/jest-dom ^7.0.1`, `vitest-axe ^0.1.0` (matchers registrados en `test/setup.ts`).
- Lint: ESLint flat config de la raíz con `eslint-plugin-jsx-a11y` (`flatConfigs.recommended`) y `react-hooks` sobre `packages/ui/**/*.{ts,tsx}`; `no-restricted-imports` prohíbe `@nerdose/db`.
- `Intl.DateTimeFormat` del runtime (ICU completo en Node 24 y navegadores). Salidas verificadas en Node 24.22 con `timeZone: 'UTC'`:
  - Fecha larga `{ weekday: 'long', day: 'numeric', month: 'long', year: 'numeric' }`: `es` 2026-11-10 → `"martes, 10 de noviembre de 2026"`; `en` → `"Tuesday, November 10, 2026"`; `es` 2026-11-08 → `"domingo, 8 de noviembre de 2026"`.
  - Día abreviado `{ weekday: 'short' }`: `es` → `"mar"`, `"dom"`, `"vie"`; `en` → `"Tue"`, `"Sun"`, `"Fri"`.
  - `{ day: '2-digit', month: '2-digit' }` **no** rellena el día en `es` (2026-11-08 → `"8/11"`; `en` → `"11/08"`). `formatToParts` da `es` `[day "8", literal "/", month "11"]` y `en` `[month "11", literal "/", day "08"]` → hay que rellenar `day`/`month` con `padStart(2, '0')` para obtener `"08/11"` / `"11/08"`.
  - Mes corto `{ month: 'short' }`: `es` → `"dic"`, `"ene"`, …, `"sept"` (septiembre), `"oct"`, `"nov"`; `en` → `"Dec"`, `"Sep"`, `"Oct"`, `"Nov"`.

### Convenciones activas (todas custom, `docs/architectures/ui/conventions/`; partes aplicables, verbatim)

#### `_base` (React + Vite)

- TypeScript is mandatory. `tsconfig.json` extends the monorepo base with `strict: true` and `noUncheckedIndexedAccess: true`.
- No `any` except at boundaries with untyped libraries, and then wrapped in a typed function.
- Naming: Files `kebab-case` (`game-card.tsx`, `format-date.ts`); Components `PascalCase`; Types / interfaces `PascalCase`, no `I` prefix; Constants `SCREAMING_SNAKE_CASE`; API fields `snake_case`, exactly as the API.
- Component files export one main component; tests live next to the file as `*.test.tsx`.
- Imports: Order within a file: (1) external libraries and `@nerdose/*`, (2) `@/` imports, (3) relative imports from the same folder. Separate groups with a blank line. Type-only imports use `import type`.
- Dates: At system boundaries (HTTP, logs) dates are ISO 8601 UTC; day dates are `YYYY-MM-DD`. The client **never decides what "today" is**: the day and challenge number come from the `api`. Format dates for display with `Intl.DateTimeFormat` using the active locale. Never assume the browser timezone equals UTC.
- Comments: Default: no comments. Comment only the why when it is not obvious.

#### `styling` (Tailwind CSS v4)

- Use only the tokens above (or later, the Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- Text and interactive-element contrast meets WCAG 2.1 AA against the surface it sits on (4.5:1 text, 3:1 large text and UI components). Verify any new color pair.
- Focus is always visible: use `focus-visible:` rings with `--color-accent`; never `outline-none` without a replacement.
- State is never conveyed by color alone: pair it with an icon, text or pattern (see `accessibility`).
- Respect `prefers-reduced-motion`: animations are disabled or reduced under it.
- No CSS-in-JS and no component CSS files, except the token file and third-party overrides.
- **Responsive design:** no global media queries. Layout uses `flex-wrap` and `repeat(auto-fit, minmax(min(300px, 100%), 1fr))`; only the 320 px adaptations documented in the Design System are allowed.
- **Tokens grow additively:** per-game tints, status tints, streak amber family, type roles (`--text-*`), radii (`--radius-*`), shadows, `--animate-blink` and the `texture-dots` utility live in `tokens.css`; existing token names are kept.
- **Static check:** component and web `.tsx` files must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`).
- Values from data or timers (progress width, countdown): set a CSS variable with `style={{ '--w': pct + '%' }}` and consume it in a class.

#### `accessibility` (WCAG 2.1 AA)

- Use native elements first: `<button>`, `<a>`, `<input>`, `<label>`, `<table>`. Use ARIA only when no native element fits.
- Everything operable with the mouse is operable with the keyboard, in a logical tab order, with no keyboard traps.
- Provide a visible focus ring on every focusable element (`focus-visible`).
- Feedback that uses color is also expressed with an icon, a pattern or text, and exposed to screen readers as text.
- Touch targets are at least 44 x 44 px. Layout reflows at 320 px without horizontal scroll and supports 200% text zoom.
- Rules: Contrast is at least 4.5:1 for text (3:1 for large text and UI boundaries) against its actual background. No interactive element is built from a `<div>` or `<span>` with a click handler; use a native control. Every image or icon is either decorative (`aria-hidden`) or has an accessible name. Color is never the only carrier of meaning. Focus is never removed (`outline: none`) without a visible replacement. Dynamic updates are announced via live regions; do not move focus unexpectedly. axe-core reports zero violations in unit checks.

#### `testing-unit` (Vitest + Testing Library)

- Query by role, label or visible text. `data-testid` only when no accessible query exists.
- Use `userEvent`, not `fireEvent`, for interactions.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- No snapshot tests of large DOM trees.
- Tests do not rely on the real date or timers; use fake timers.
- Test names state the behavior ("shows ... when ..."), not the implementation.

```tsx
import { axe } from 'vitest-axe';
it('has no axe violations', async () => {
  const { container } = render(<Component … />);
  expect(await axe(container)).toHaveNoViolations();
});
```

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

> Consecuencia para `ui`: el paquete **no** importa `i18next` ni `react-i18next` (lo verifica `components.test.ts` TS-57). Todo texto del `Heatmap` entra por props ya traducido por `web`; el componente solo formatea fechas con `Intl` según el `locale` recibido.

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db`.
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

#### ADR-008: Día de la plataforma (reglas aplicables, verbatim)

- `today` MUST calcularse siempre en el servidor con la función de `@nerdose/core` (día UTC). MUST NOT aceptarse una fecha del cliente en ninguna ruta de jugador.

> Consecuencia: `Heatmap` **nunca** usa `new Date()` ni `Date.now()` para decidir hoy; recibe `today` (`MyStats.today`) y hace toda la aritmética de días en UTC sobre strings `YYYY-MM-DD`.

### Decisiones de diseño de REQ-011 aplicables (verbatim)

- **Supuesto [Heatmap]:** C-34 pide los últimos 365 días → **Supuesto tomado:** cada celda es un día UTC con cantidad de partidas completadas (de 0 a 5; las anuladas cuentan); la intensidad se distingue por niveles con patrón o número accesible, no solo por tono. El día de hoy se incluye aunque todavía no se haya jugado. Los días anteriores a la primera Play del jugador aparecen como vacíos. Se muestra la cantidad también como texto para lectores de pantalla (por semana o por celda enfocable).
- **Supuesto [Zona horaria]:** el día de la plataforma es UTC → **Supuesto tomado:** el heatmap y el historial usan fechas del día de la plataforma, no la zona horaria local del jugador, igual que las rachas, para que coincidan con lo que vio en la home.
- **Decisión 8. `MyStats.today`.** La respuesta agrega el día de la plataforma para anclar la grilla de 365 días: el cliente no calcula "hoy" (overview de `web`, ADR-008) y así el heatmap y la racha usan el mismo día (CA 12). `heatmap` sigue trayendo solo los días con al menos una Play completada; el cliente completa los vacíos.
- **Servicios afectados (`ui`):** `Heatmap` con variante de 365 días y alternativa no cromática por celda; retiro de `analytics.ts` (S-058, fuera de este plan).
- **Revisión UX — Layout de `/stats`:** heatmap de 53 columnas de semana (lunes a domingo) × 7 días, con scroll propio en mobile que abre en hoy y entero en desktop. Usa los 5 niveles del DS (4 y 5 comparten el último tono, porque el DS prohíbe una sexta tonalidad). La alternativa no cromática es la cantidad exacta en texto: `detalle-dia` para el día enfocado o tocado, nombre accesible por celda, leyenda «0–5» y resumen del grupo. El teclado navega con un solo punto de tabulación y flechas.
- **CA 6 (REQ):** DADO un jugador con Play en los últimos 365 días CUANDO ve el heatmap ENTONCES cada día con partidas muestra la cantidad completada (0 a 5), los días sin actividad quedan vacíos, y la información está disponible como texto además del tono de color.
- **CA 12 (REQ):** DADO que el día de la plataforma cambia a las 00:00 UTC CUANDO el jugador abre `estadisticas` a las 00:05 UTC ENTONCES el heatmap incluye el día nuevo como hoy.
- **CA 30 (REQ):** DADO el feedback de cualquier juego, el heatmap, … CUANDO se revisa sin distinguir colores ENTONCES cada estado se entiende por texto, ícono o patrón y no solo por color.

### Database Context

Sin cambios. El dato sale de `plays` (`date`, `count(*)` WHERE `player_id` AND `date >= today − 364` AND `status IN ('won','lost','voided')` GROUP BY `date`), armado por la `api` (S-055).

### Flow Context

#### `estadisticas-del-jugador` (extracto verbatim, lo que toca al heatmap)

- **Paso 3 — Heatmap e historial:** `plays` — heatmap: `date`, `count(*)` WHERE `player_id` AND `date >= today − 364` AND `status IN ('won','lost','voided')` GROUP BY `date`. … El heatmap viene en orden `date` ascendente.
- **Paso 4 — Respuesta:** `"today": "YYYY-MM-DD"`, … `"heatmap": [ { "date": "YYYY-MM-DD", "completed": "integer 0–5" } ]`.
- **Notas:** Las Play `voided` cuentan en el heatmap, el historial, las rachas y `total_completed`, pero no en `played`, `wins` ni `extra` (invariante 23). Las Play `in_progress` (incluidas las de días pasados) no aparecen.

Este plan **no modifica** pasos del flujo: provee el componente que `web` usa para renderizar `heatmap` anclado en `today`.

### Integration Points

#### Contrato `Heatmap` (lo que `web` consumirá en S-057)

export type HeatmapDay = { date: string; completed: number };          // = MyStats.heatmap[i]

  className?: string;

#### `components/heatmap.md` v1.0.0 (spec completo, verbatim)

>

>
> **Cuándo NO usar:** para datos que el jugador tiene que leer celda por celda (no hay valores por celda accesibles).
>
> **Anatomía:** 1. **Caption** — `type.meta` (Mono 12), `text.dim`: "últimas 4 semanas · juegos completados por día" (L215) / "últimas 12 semanas · …" (L319). 2. **Grilla** — `role="img"` con `aria-label` que resume el dato. 3. **Celdas** — color por nivel 0-4 (`data.heatmap.*`). 4. **Leyenda (solo `month`)** — "0" + 5 cuadros 12×12 radio 3 + "4", Mono 11 `text.dim`, gap 6 (L221).

>
> **Spacing & sizing rules:** Caption sobre la grilla con gap 8 (`month`) o 10 (`quarter`).
>
> **Accesibilidad:** **ARIA:** `role="img"` + `aria-label` con el resumen … **Requisito:** el `aria-label` lleva el dato, no solo el título. **WCAG 1.4.11:** niveles 0 y 1 contra el fondo `#0F1318` dan 1,1:1 y 2,1:1. ### Decisiones de este plan (derivadas, sin inventar contrato)

1. **Un solo componente para `heatmap` + `detalle-dia`.** El detalle depende del día enfocado o tocado, que es estado interno del grid; exponerlo como callback obligaría a `web` a duplicar la lógica. `web` solo pasa textos.
2. **Semántica ARIA `grid`.** DOM = 7 filas (`role="row"`, lunes a domingo) × 53 columnas de semana; cada día en rango es un `role="gridcell"` que contiene un `<button type="button">` nativo (regla «usar control nativo para el clic») con `aria-label` = `cellLabel(info)`. Roving tabindex: solo el día activo tiene `tabIndex={0}` (inicial: hoy). Visualmente es la misma grilla (filas = días de la semana, columnas = semanas).
3. **Días fuera de rango** (antes de `today − 364` en la primera columna, después de `today` en la última) se renderizan como `<span aria-hidden="true">` del mismo tamaño, invisibles. Siempre hay 365 celdas en rango y 371 − 365 = 6 huecos.
4. **Teclado:** `ArrowUp`/`ArrowDown` = −1/+1 día; `ArrowLeft`/`ArrowRight` = −7/+7 días; `Home` = `today − 364`; `End` = `today`. Si el destino cae fuera de `[today − 364, today]`, el foco **no se mueve** (sin envolver). Teclas manejadas llaman a `preventDefault()`; el resto se ignora.
5. **Detalle:** día activo = el último enfocado/tocado (`selected`) o `today` si no hubo interacción o si el seleccionado quedó fuera del rango tras un cambio de `today`. Si el total del rango es 0 y no hubo interacción, muestra `emptyDetail`. El `<p>` del detalle **no** es región `aria-live`: el nombre de la celda enfocada ya se anuncia y una región viva lo duplicaría.
6. **Niveles:** `heatmapLevel(completed)` = 0, 1, 2, 3 para 0–3 y 4 para ≥ 4 (4 y 5 comparten tono, DS prohíbe una sexta tonalidad). `completed` se acota a `0..5` (contrato `maximum: 5`).
7. **Hoy:** `aria-current="date"` + anillo `ring-1 ring-border-interactive` (`border.interactive`, 6,8:1 sobre `#0F1318`). Distinto del foco (`outline` 2px `accent` con offset 2).
8. **Etiquetas de mes:** fila `aria-hidden` sobre el grid; una etiqueta (`Intl` `{ month: 'short' }`, UTC) en la columna que contiene el día 1 de cada mes dentro del rango (con `today = 2026-11-15`: 12 etiquetas, de «dic» en la columna 3 a «nov» en la 50). El mes parcial del inicio no lleva etiqueta: evita superposiciones cuando el día 1 cae a 1–2 columnas del borde.
9. **Leyenda:** fila `aria-hidden` con «0 1 2 3 4 5», cada número junto a su cuadro 12×12 (4 y 5 con `bg-heatmap-4`). Es visual: el dato para lectores de pantalla está en cada celda y en el resumen.
10. **Scroll:** wrapper `overflow-x-auto` con padding interno de 4px para que el anillo de foco de las celdas del borde no se recorte; al montar y cuando cambia `today`, `scrollLeft = scrollWidth` (abre mostrando hoy). En desktop (≥ 950px útiles) no hay scroll.
11. **Área táctil:** las celdas miden 14×14 (medida del DS, 53 columnas tienen que entrar en ≈ 954px en desktop). Excepción documentada al mínimo de 44px, con el mismo criterio que el tablero de Grep (S-024): el dato también es accesible por teclado, por nombre de celda y por el total del resumen; tocar es un atajo. Anotarla en el informe de la auditoría (S-059).
12. **Tokens nuevos (aditivos):** `--color-heatmap-0..4` (valores de `data.heatmap.*`) y `--radius-micro: 3px` (`radius.micro`). Se suma `'micro'` a `RADIUS_ROLES`.
13. **Formato de fechas** (en el modelo, puro): `longDate` = `Intl.DateTimeFormat(locale, { weekday: 'long', day: 'numeric', month: 'long', year: 'numeric', timeZone: 'UTC' })`; `shortDate` = `weekday: 'short'` + `' '` + partes `day`/`month` de `{ day: '2-digit', month: '2-digit' }` con `padStart(2, '0')` y los literales del locale (`es` «dom 08/11», `en` «Sun 11/08»). Las fechas se construyen con `Date.UTC(y, m − 1, d)`; nunca con la zona local.
