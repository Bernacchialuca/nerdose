> Root scripts delegate to Turborepo: `dev`, `build`, `lint`, `typecheck`, `test` (`turbo run <task>`).

**Ports in development** (copiado): `api` 3000, `web` 5173, `admin` 5174. `web` proxies `/api/*` to the api and `admin` proxies `/api/admin/*` (same origin emulation, no CORS).

**How to use** (copiado):
- Start-up order (documented in `README.md`): `docker compose up -d` → `pnpm --filter @nerdose/db db:migrate` → `pnpm dev`.
- Copy each `.env.example` to `.env.local` (and the root one to `.env` for Compose) and fill the values. Real values are never committed.
- Add a workspace by creating its folder under `apps/`, `packages/` or `packages/games/`; it must define `lint`, `typecheck` and `test` scripts so Turborepo picks it up.
- Run a single package: `pnpm --filter @nerdose/<name> <script>`.

**Rules** (las que aplican, copiadas):
- pnpm is the only package manager. No `npm`, `yarn` or `bun` lockfiles or commands.
- `engines.node` is `">=24 <25"` and `packageManager` is pinned in the root `package.json`.
- Tasks (`build`, `dev`, `lint`, `typecheck`, `test`) are orchestrated by Turborepo; `dev` is `persistent` and uncached.
- `.gitignore` excludes `.env`, `.env.local`, `.env.test`, `node_modules`, build output and Turborepo cache. Only `.env.example` files are committed, with empty values and a comment per variable.
- `compose.yaml` publishes PostgreSQL only on `127.0.0.1` and keeps data in the named volume `nerdose-pgdata`. Rebuilding from scratch is an explicit `docker compose down -v`.
- No secrets in the repository: `.env.example` files never contain real values.
- Deployment, CI/CD, hosting and production secrets are out of scope until they are defined.

**Integration with other conventions** (copiado):
- **env-config**: each service declares its variables in its own `env.ts` and keeps `.env.example` in sync; the root `.env.example` only holds Compose variables.
- **testing**: the root Vitest config runs each package's tests; integration tests need Docker (Testcontainers) and fail with a clear message without a daemon.
- **orm**: `db:migrate` is the single migration command and reads `DATABASE_URL_OWNER`.

### ADRs Relevantes

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo con pnpm workspaces y Turborepo.
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.
- **Aplica a este plan:** `pnpm dev` se orquesta con Turborepo; el README usa solo comandos `pnpm` (nunca `npm`/`yarn`/`bun`). Los tests nuevos van en el proyecto `workspace` (`test/`).

#### ADR-004: PostgreSQL como única base, con propiedad por roles (regla aplicable, verbatim)

- La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
- **Aplica a este plan:** el README instruye usar `nerdose_api` en `apps/api/.env.local` y `nerdose_generator` en `apps/generator/.env.local`, y la verificación de CA-1 comprueba el `db_role` de cada log.

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- Los tests MUST usar Vitest; los e2e, Playwright.

### Decisiones de diseño del REQ-001 que aplican

- **Decisión 3 (puertos):** `api` en `3000`, `web` en `5173` y `admin` en `5174`.
- **Decisión 4 (variables incrementales):** cada servicio declara solo las variables que usa este grupo; no se exigen secretos que nada usa todavía (`ADMIN_PASSWORD_HASH`, `GENERATOR_SECRET` no existen aún).
- **Decisión 5 (`.env.example` sin valores):** los valores reales van en `.env.local` (y `.env` en la raíz para Compose), que están en `.gitignore`.
- **Escenario 1 – Arranque local (pasos, copiados):**
  1. **[Desarrollador]** `docker compose up -d`. PostgreSQL 16 queda escuchando en `127.0.0.1:5432` con el rol `nerdose_owner` y la base `nerdose`.
  2. **[`@nerdose/db`]** `pnpm --filter @nerdose/db db:migrate`: conecta con `DATABASE_URL_OWNER` y aplica `0000_roles_and_grants`; sincroniza las contraseñas desde `DATABASE_URL_API` y `DATABASE_URL_GENERATOR`; sale con código 0.
  3. **[Desarrollador]** `pnpm dev` ejecuta `turbo run dev`: las 4 tareas son `persistent` y sin cache.
  4. **[`api`]** valida el entorno; `SELECT current_user` y log `{ db_role: 'nerdose_api' }`; `serve(..., port: 3000)`.
  5. **[`generator`]** valida el entorno; log `{ db_role: 'nerdose_generator' }`; `startScheduler(deps)` y log `Scheduler started` con `{ jobs: 0 }`.
  6. **[`web`]** Vite dev server en `:5173`, con proxy `'/api' → 'http://localhost:3000'`.
  7. **[`admin`]** Vite dev server en `:5174`, con proxy `'/api/admin' → 'http://localhost:3000'`.
  - **Outcome:** 4 procesos corriendo; los logs muestran el rol de cada backend y el scheduler activo sin jobs.
  - **Manejo de errores:** `db:migrate` con PostgreSQL apagado sale con código 1; si la base no responde al arrancar el `generator`, sale con código 1; si no responde al arrancar la `api`, deja un log `warn` y arranca igual (el health informa el fallo).
- **Riesgo (copiado):** `turbo run dev` corta todas las tareas si una falla (por ejemplo, el `generator` sin base). **Mitigación:** el README de arranque indica el orden (`docker compose up -d` → `db:migrate` → `pnpm dev`). El `generator` explica por qué abortó.
- **Escenario 2 – Health por el origen de cada SPA:** si la `api` está caída, el proxy de Vite responde `502`/`504` (aceptable en desarrollo). `admin` solo hace proxy de `/api/admin`: `GET :5174/api/health` no llega a la `api` (intencional, replica producción).

## Tareas

### Tarea 1: Test del grafo de `turbo run dev`

**Status:** Completed

#### Descripción

Fijar con un test que `pnpm dev` (`turbo run dev`) ejecuta exactamente `web`, `admin`, `api` y `generator`, como tareas `persistent` y sin cache, con el comando esperado de cada app. La configuración ya existe (S-001 y los planes de cada app); lo que falta es la garantía de que una app nueva sin `dev`, un script renombrado o un cambio en `turbo.json` no rompa CA-1 en silencio. El test usa `turbo run dev --dry=json`, que resuelve el grafo sin ejecutar nada.

#### Criterios de Aceptación

1. Existe `test/helpers/turbo.ts` con `turboDryRun(task: string): TurboDryRun` que ejecuta `node_modules/.bin/turbo run <task> --dry=json` con `cwd: REPO_ROOT` y devuelve el JSON tipado.
2. Si el proceso falla (`result.error` o `status !== 0`), el helper lanza `Error` con el mensaje `turbo run <task> --dry=json failed: <detalle>`.
3. Existe `test/turbo-dev.test.ts` que cubre TS-1, TS-2, TS-3 y TS-4.
4. `pnpm test:workspace`, `pnpm lint:workspace` y `pnpm typecheck:workspace` pasan.

#### Detalles Técnicos

**Referencias al Contexto Arquitectónico:**
- Grafo real de `turbo run dev` (tabla en "Arquitectura del Servicio") — es el output esperado.
- Patrón de `test/helpers/compose.ts` (Código Reutilizable) para el helper.
- Regla de `monorepo-tooling`: "`dev` is `persistent` and uncached".
- ADR-003: tareas orquestadas por Turborepo.

**Archivos a crear/modificar:**
- `test/helpers/turbo.ts` (nuevo)
- `test/turbo-dev.test.ts` (nuevo)

**Notas de implementación:**
- Tipo local mínimo:
  ```ts
  export interface TurboDryRunTask {
    taskId: string;
    command: string;
    resolvedTaskDefinition: { persistent: boolean; cache: boolean };
  }
  export interface TurboDryRun {
    tasks: TurboDryRunTask[];
  }
  ```
- Usar `spawnSync(join(REPO_ROOT, 'node_modules/.bin/turbo'), ['run', task, '--dry=json'], { cwd: REPO_ROOT, encoding: 'utf8' })`. No usar `npx` (añade latencia y puede resolver otra versión).
- **Ejecución anidada:** este test corre dentro de `turbo run test` (tarea `//#test:workspace`). Si el `turbo` anidado se queja por variables `TURBO_*` heredadas o por el lock del daemon, pasar `env` sin las claves que empiecen con `TURBO_` y agregar `--no-daemon`. Verificarlo corriendo tanto `pnpm test:workspace` como `pnpm test`.
- Definir la constante `NONEXISTENT = '<NONEXISTENT>'` en el test (valor literal que emite Turborepo para paquetes sin el script).
- Leer el resultado una vez por `describe` (el dry-run tarda ~1 s). Si hiciera falta, subir el `timeout` del test a `20_000`.
- `stdout` del dry-run puede venir precedido de líneas no-JSON en algunas versiones: si `JSON.parse` falla, recortar desde el primer `{`. Solo implementarlo si se observa el problema.

**Dependencias:**
