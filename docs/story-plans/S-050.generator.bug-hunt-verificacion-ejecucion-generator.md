4. **Runner con guion propio de Bug Hunt (`scriptedBugHuntRunner`).** El `scriptedRunner` de Big O numera las llamadas en rondas de 3, y en Bug Hunt no sirve:

'correct' : 'mutant'`. Si el guion devuelve `undefined`, ejecuta de verdad con `runInLanguage`. Así el intento rechazado es sintético y el siguiente se aprueba con ejecución real (mismo criterio que S-045, decisión 4).

Es la misma forma que el respaldo "equivalente" de `generate` (decisión 14 de S-049).

#### Convención `challenge-generation` (reglas aplicables, verbatim)

- The seed is `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")` with `date` as `YYYY-MM-DD`, feeding `pure-rand` (xoroshiro128+). `Math.random()` and the current time are never used for generation.
- `GENERATION_MAX_ATTEMPTS` defaults to 20 and is configurable by env; `attempt` goes from 0 to `GENERATION_MAX_ATTEMPTS - 1`.
- `generateForDate` accepts `firstAttempt` and a `regenerate` mode (REQ-008). Regeneration starts at `max(challenges.attempt)` for the (`game_id`, `date`) + 1, tries up to `GENERATION_MAX_ATTEMPTS` candidates (never repeating a seed) and returns the verified candidate as `draft` instead of approving it; the queue worker performs the atomic replacement.
- A candidate is inserted as `draft` first, then `verify()` runs. It becomes `approved` only if `verify()` returns `ok: true`; the full log is stored in `challenges.verification`. Otherwise it becomes `rejected`.
- `verify` may return `VerificationLog` or `Promise<VerificationLog>`; `generateForDate` always `await`s it. A failure of the code runner (timeout, compile error, missing toolchain) is a failed check of the candidate, never an exception of the job.
- The history of a date `D` is read once, before the attempts: `recentChallenges` are the challenges of the game with `status IN ('approved','published','voided')` and `date` in `[D - recentDays, D + aheadDays]`, **excluding the row of `D`** (`historyWindow` in `generate.ts`). `aheadDays` is optional (default 0). Excluding `D` keeps the old `approved` challenge of a regeneration from counting against its replacement.
- `challenges.number` is computed with `@nerdose/core` (`date - LAUNCH_DATE + 1`) at insert time. `generator_version` is stored with every challenge.
- Never generate for `today` or past dates. If a day arrives without a challenge the day is neutral.
- If tomorrow's challenge for a game is missing after all attempts: `UPSERT generation_failures` (one row per game and date, with `attempts` and `last_reason`). That row is the alert: the admin shows it in Próximos desafíos; nothing is sent (ADR-017).
- The `generator` imports only `./generator` (and `./definition` if needed) of the game packages, and makes no HTTP requests to external services.

Registro de Big O (verbatim, "Update (REQ-009)"): "Big O registers as `{ gameId: 'big-o', generator, payloadSchema, version: 'big-o@1' }` with `historySpec = { bank: null, lastUsedField: '', recentDays: 30, aheadDays: 30 }` and `usedBankItems = () => []`; `approve` touches no bank." Para Bug Hunt, la decisión 11 del REQ fija `{ gameId: 'bug-hunt', generator, payloadSchema, version: 'bug-hunt@1' }`.

#### Convención `code-runner` del `generator` (reglas verbatim)

- The runner uses `execFile` (never `exec` with a shell), with timeout 10 000 ms, and runs as a non-root user.
- Arguments are never built from untrusted strings; code goes in files, not in the command line.
- A timeout, a non-zero exit or a compile error is a failed check (candidate `rejected`), not an exception that stops the job: `runInLanguage` returns `ok: false` and never throws for a problem of the snippet.
- Only the `generator` imports `@nerdose/polyglot`. `./definition` and `./client` entries of games never import it, nor `node:child_process`.
- Required toolchains: Node 24, Go >= 1.25, JDK 21. Versions are not silently substituted.
- **testing**: tests that run toolchains are integration tests and require them installed; a CI job compiles the emitted code.

Entorno del hijo (verbatim): "Every `execFile` uses `timeout`, `killSignal: 'SIGKILL'`, `maxBuffer: 1_048_576`, `encoding: 'utf8'` and a minimal environment (`PATH`, `HOME`, `GOCACHE`, `GOPATH`, `TMPDIR`, only the defined ones: never `DATABASE_URL` or `GENERATOR_SECRET`)." `startGenerator` (helper de test) ya pasa `HOME` y, si están definidos, `GOCACHE`, `GOPATH` y `TMPDIR` (S-045).

#### Convención `testing` (reglas aplicables, verbatim)

- One shared container per suite, started in `globalSetup`. Never start a container in `beforeAll` per file or inside an `it`.
- Do not mock the database or `postgres.js` in integration tests. Real PostgreSQL 16 only.
- Every file resets the database in `beforeAll` and owns its fixtures. No test depends on data left by another file.
- Fixtures use the owner role; the code under test uses `nerdose_api` or `nerdose_generator`.
- No wall-clock sleeps to wait for a condition. Await the observable condition or use `Wait.*` strategies.
- Test files are co-located or under `test/`, suffixed `.test.ts`; `describe` names the unit and `it` the scenario.
- Keep log output quiet with `LOG_LEVEL=silent`.
- Jobs are exercised through their run function with a real `Db` and fake clock; the croner schedule is not waited on.

#### Convención `logging` (extracto)

- `logger.info({ context }, 'message')`: el primer argumento es el objeto de contexto y el segundo, un mensaje corto y **estático**, sin interpolar.
- Los eventos de dominio del `generator` usan PascalCase: `ChallengeGenerated`, `ChallengeApproved`, `ChallengeRejected` (con `reason`) y `ChallengeGenerationFailed`. Llevan `game_id`, `date` y `attempt` del logger hijo.

#### Convención `env-config` (extracto)

- Nunca leer `process.env` fuera de `src/config/env.ts`. `test/env-isolation.test.ts` lo verifica sobre todo `src/`. Los tests pueden leer `process.env`.

### ADRs Relevantes

#### ADR-007: Generator como worker y pipeline de generación

Decisión: el `generator` es un proceso long-running con croner que mantiene 14 días aprobados y verificados por adelantado, con seed HMAC e intentos acotados. La verificación de los juegos de código ejecuta en JS, Go y Java.

Nota de Bug Hunt (verbatim, ya escrita por el plan `S-050.games`): "**Bug Hunt (REQ-010):** los valores esperados de los tests se calculan en `generate` con el intérprete `evaluate` de `@nerdose/polyglot` (sin procesos) y `verify` los confirma ejecutando la versión correcta y la mutada en los 3 lenguajes (un `main` por variante y lenguaje, 6 ejecuciones por candidato, los lenguajes en paralelo). Si el intérprete y la ejecución real no coinciden, el candidato se rechaza (`correct_agrees` / `mutant_agrees`)."

Reglas de Implementación (verbatim, completas):
- `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
- `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
- Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
- Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
- Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
- El seed MUST ser `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`, con `date` en formato `YYYY-MM-DD`. `GENERATOR_SECRET` MUST existir solo en el entorno del `generator`.
- `GENERATION_MAX_ATTEMPTS` MUST valer 20 por defecto y ser configurable por variable de entorno.
- `fill` MUST generar solo para fechas en `[today+1, today+14]`. MUST NOT generar para `today` ni para fechas pasadas.
- `challenges.number` MUST calcularse con `core` (`date − LAUNCH_DATE + 1`) al insertar.
- Un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`.
- El runner MUST usar `execFile` (nunca `exec` con shell), timeout de 10 000 ms, y MUST correr como usuario no root.
- Los toolchains MUST ser Node 24, Go ≥ 1.25 y JDK 21.
- El `generator` MUST NOT hacer requests HTTP a servicios externos. No tiene salida de red fuera de la base (ADR-017).
- El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)

- `generateForDate` MUST hacer `await` de `verify`; los generadores síncronos siguen siendo válidos.
- `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
- `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

#### ADR-017: Alertas registradas en el admin (reglas aplicables, verbatim)

- Las alertas MUST NOT salir del sistema en v1: ningún servicio MUST enviar mails, webhooks ni notificaciones push.
- La falla de generación MUST registrarse con `INSERT … ON CONFLICT (game_id, date) DO UPDATE SET attempts, last_reason, updated_at`. Una corrida posterior para la misma fecha MUST actualizar esa fila, no crear otra.

### Decisiones de diseño de REQ-010 aplicables (verbatim)

- **Decisión 11 (extracto).** "Cuatro líneas: … `apps/generator/src/games/registry.ts` (`{ gameId: 'bug-hunt', generator, payloadSchema, version: 'bug-hunt@1' }`) … el día del despliegue Bug Hunt sigue neutro y se juega desde el día siguiente (mismo criterio que Big O y Timeline, CA 24). … `bankUsage = null`, `usedBankItems = () => []`."
- **Decisión 6.1 (extracto).** "`historySpec = { bank: null, lastUsedField: '', recentDays: 60, aheadDays: 60 }`, sin la fila de `D` … Cuentan `approved`, `published` y `voided` (`ACTIVE_STATUSES`); un regenerado queda `rejected` y no cuenta."
- **Decisión 6.4 (extracto).** "si tampoco, se devuelve igual el último candidato y `verify` lo rechaza con su motivo, de modo que tras 20 intentos queda la falla registrada (ADR-017, CA 17) sin relajar ninguna regla."
- **Decisión 7.** Esta es la cola de la decisión, sobre el resultado: "El resultado va a `challenges.verification` (`{ ok, checks[], reason? }`, sin cambiar `VerificationLog`); `reason` es el `name` del primer check que falla, salvo en los `run_*`, donde es `run_<variante>_<lang>: <kind>` (p. ej. `run_mutant_go: timeout`). El admin ya lo muestra (CA 19)."

**Implementado en el plan `S-050.games`:**
- **`VERIFY_CHECKS` (13, en orden):** `texts_bilingual`, `code_shape`, `lines_consistent`, `tests_consistent`, `variety_combo`, `run_correct_js`, `run_correct_go`, `run_correct_java`, `run_mutant_js`, `run_mutant_go`, `run_mutant_java`, `correct_agrees`, `mutant_agrees`.
- **Regla de salteo:**
  - los 5 checks en memoria se calculan siempre. Si falla alguno, no se ejecuta nada y los checks 6 a 13 quedan `{ ok: false, detail: 'skipped' }`;
  - dentro de un lenguaje, la correcta y la mutada corren siempre las dos, en ese orden;
  - `correct_agrees` se calcula solo si los 3 `run_correct_*` dieron salida válida, y `mutant_agrees`, solo si la dieron los 3 `run_mutant_*`. Si no, quedan `skipped`. Los dos son independientes entre sí.
- **Formato de `reason`:**
  - `run_<variante>_<lang>: <kind>` (`'run_mutant_go: timeout'`, `'run_correct_java: compile_error'`, `'run_correct_js: toolchain_missing'`);
  - `tests_consistent: equivalent_mutant` y `tests_consistent: not_enough_passing`;
  - en el resto de los casos, el `name` del check.
- **`detail`:**
  - checks 1 a 5 ok: sin `detail`;
  - `run_*` ok: `'<durationMs> ms'`;
  - `run_*` fallido: `'<kind> (<durationMs> ms): <primera línea informativa de stderr, ≤ 200 caracteres>'`, sin `': …'` si `stderr` está vacío;
  - `*_agrees` ok: `'<n> tests'`;
  - `*_agrees` fallido: `'differs at tests[<i>] <llamada>: js=<a> go=<b> java=<c>'`;
  - `tests_consistent`: `'equivalent_mutant: no failing test'` / `'not_enough_passing: <k> passing, <v> visible'`.
- **Ejecución:** 6 por candidato. Los 3 lenguajes van en paralelo y, dentro de cada uno, la correcta y después la mutada. Nunca hay más de 3 subprocesos a la vez.
