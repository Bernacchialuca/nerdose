### Decisiones de planificación (a confirmar en la revisión del plan)

1. **Orden de resolución del idioma.** El CA-10 de la story (y el RF-7 del REQ) dice `locale` del Player → `Accept-Language` → `es`. ADR-015, `docs/apis/api.yaml` (`info.description` y parámetro `Lang`) y las convenciones `player-identity` y `error-handling` fijan **`?lang` → `players.locale` → `Accept-Language` → `es`**. El ADR es la regla vinculante y S-008 necesita `?lang` (decisión 8 del REQ: con cookies bloqueadas el front manda `?lang=`), así que se implementa el orden del ADR. El orden del CA-10 se cumple igual cuando no viene `?lang`. Un `?lang` con un valor fuera de `es|en` **se ignora** y la resolución sigue (no es `422`): el middleware es global y no tiene que romper rutas que no declaran `lang`.
2. **`Accept-Language` con varios idiomas.** El contrato solo dice "si es `es` o `en`, si no `es`". `pickLocale` recorre los tags ordenados por `q` (desc, empate = orden de aparición) y devuelve el primero cuyo subtag primario sea `es` o `en`; si ninguno coincide, `es`. Ej.: `fr-FR,en;q=0.8` → `en`; `pt-BR` → `es`; `en-US` → `en`; header ausente o vacío → `es`.
3. **Mensajes de error en inglés.** ADR-015 exige `message` en el locale resuelto. Hoy `src/http/error-messages.ts` es "español fijo, transitorio hasta la resolución de locale". Esta story lo vuelve bilingüe. Los textos en español actuales **no cambian** (hay tests que dependen de ellos). Los textos en inglés **no están documentados** y se proponen en la Task 2: hay que revisarlos.
4. **Montaje de `originAndContentType`.** La story describe el pipeline de `POST /api/session` como "rate limit por IP → `originAndContentType`". La convención `security` monta `originAndContentType` como middleware global (dos veces: `WEB_ORIGIN` en `/api/*`, `ADMIN_ORIGIN` en `/api/admin/*`), y el rate limit va por ruta. Se sigue la convención: el chequeo de origen y content-type corre **antes** del limiter, así que un pedido rechazado con `403`/`415` no consume cupo. CA-5 y CA-6 se cumplen igual.
5. **El JSON mal formado da `422 validation_error`.** Con un body que no es JSON válido, `@hono/zod-validator` (validator `json` de Hono) lanza `HTTPException(400)`, y el error handler actual lo convertiría en `500 internal_error`. ADR-015 dice que "cualquier otro body inválido" es `422 validation_error`, así que el error handler mapea `HTTPException` con status 400 a `AppError('validation_error')`.
6. **Las URLs de origen se normalizan.** `WEB_ORIGIN` y `ADMIN_ORIGIN` se validan como URL y se guardan como `new URL(v).origin`, así que una barra final configurada por error (`http://localhost:5173/`) no rompe la comparación exacta con el header `Origin`.
7. **IP sin `TRUST_PROXY_HEADER`.** Por la convención `security`, si `TRUST_PROXY_HEADER` no está configurada, la clave del rate limit por IP es `'unknown'` y todos los clientes comparten el balde. En desarrollo local (sin proxy que agregue el header) las 20 sesiones / 10 min se comparten entre todas las pestañas. El front ya maneja el `429` de sesión (sigue sin sesión). Queda documentado en el comentario de `.env.example`.

### ADRs Relevantes

#### ADR-009: Identidad del jugador anónimo (cookie `nd_pid`)

- **Decisión:** el jugador se identifica con la cookie funcional `nd_pid`, cuyo valor es `players.id` (UUID v4). `POST /api/session` es idempotente. La cookie es `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, sin `Domain`, con `Max-Age=34560000` (400 días) y se renueva en cada `POST /api/session`. La protección CSRF es mismo origen + `SameSite=Lax` + `Content-Type: application/json` + chequeo de `Origin`. Sin CORS.
- **Reglas de Implementación (verbatim):**
  - El nombre de la cookie MUST ser `nd_pid` y su valor MUST ser el `players.id` (UUID v4) tal cual.
  - La cookie MUST emitirse con `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=34560000` y MUST NOT llevar atributo `Domain`.
  - `POST /api/session` MUST ser idempotente y responder `200 { locale, preferred_code_language, created }`.
  - Al crear un Player, `locale` MUST salir de `Accept-Language` si es `es` o `en`, y si no, `es`. `preferred_code_language` MUST ser `js`.
  - Un `nd_pid` que no corresponde a un Player existente MUST tratarse como ausente (se crea otro Player y se reemplaza la cookie).
  - Las rutas de jugador que lo exigen MUST responder `401` con `{ "error": { "code": "no_session", … } }` si falta la cookie o no es válida.
  - `GET /api/today` MUST funcionar sin cookie y devolver `has_session: false`.
  - Toda mutación (`POST`, `PATCH`) MUST rechazar con `415` un `Content-Type` distinto de `application/json`, y con `403 forbidden_origin` un header `Origin` ausente o distinto del permitido: `WEB_ORIGIN` para las rutas de jugador y `ADMIN_ORIGIN` para `/api/admin/*`. Ambas variables son **obligatorias** en todos los ambientes (producción: `https://nerdose.dev` y `https://admin.nerdose.dev`; local: los orígenes del dev server de Vite). El chequeo nunca se desactiva por falta de configuración.
  - La `api` MUST NOT emitir headers CORS.
  - MUST NOT guardarse PII del jugador (ni IP, ni email, ni fingerprint) en `players`. El `user_agent` solo se guarda en el `context` de un reporte.

#### ADR-012: Caches y rate limit en memoria de la api (reglas de rate limit)

- **Decisión:** rate limit con `hono-rate-limiter` y store en memoria. `429` con `{ "error": { "code": "rate_limited", "message": "…" } }` y header `Retry-After`.

| Ruta | Clave | Límite |
|---|---|---|
| `POST /api/session` | IP | 20 / 10 min |
| `POST /api/games/{game_id}/today/move` | `player_id` | 60 / min |
| `POST /api/games/{game_id}/today/move` | IP | 300 / min |
| `POST …/start`, `POST …/acknowledge-void`, `PATCH /api/me/preferences` | `player_id` | 30 / min |
| `POST /api/games/{game_id}/today/report` | IP | 10 / hora |
| `GET /api/*` | IP | 600 / min |
| `POST /api/admin/login` | IP | 5 / 15 min |
| `/api/admin/*` con JWT | – | sin límite |

  En esta story aplican solo las filas `POST /api/session` y `PATCH /api/me/preferences`.

- **Reglas de Implementación (verbatim, las de rate limit):**
  - Los límites MUST ser exactamente los de la tabla, configurados con `hono-rate-limiter` y store en memoria.
  - La IP del cliente MUST tomarse del header del proxy de confianza configurado (`TRUST_PROXY_HEADER`, por ejemplo `X-Forwarded-For`), nunca de un header arbitrario sin configurar.
  - Un `429` MUST incluir `Retry-After` en segundos y el body `{ "error": { "code": "rate_limited", "message": … } }`. MUST NOT haber captcha.
  - El límite por `player_id` MUST aplicarse después de resolver la cookie `nd_pid`. Si no hay cookie, aplica solo el límite por IP.

#### ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores

- **Decisión:** JSON en `snake_case` con los nombres del dominio y la DB. Locale de la respuesta: `?lang=` → `players.locale` → `Accept-Language` → `es`. Errores `{ "error": { "code", "message" } }` con catálogo cerrado en `@nerdose/core`. Rutas sin versión.
- **Reglas de Implementación (verbatim):**
  - Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
  - Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
  - `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
  - El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
  - Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
  - Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
  - Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
  - Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; `code_language`: `js | go | java`; `locale`: `es | en`).
  - Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.

#### ADR-004: PostgreSQL única base con roles (aplicable)

- La `api` se conecta con el rol `nerdose_api`. Sobre `players` tiene `SELECT, INSERT, UPDATE` (migración `0001_players`): **no tiene `DELETE`**. Los tests insertan fixtures con el rol owner.

#### `player-identity` — configuración de referencia

```ts
// apps/api/src/domain/identity/session-cookie.ts
import { setCookie } from 'hono/cookie';

export function issuePlayerCookie(c: Context, playerId: string) {
  setCookie(c, 'nd_pid', playerId, {
    httpOnly: true, secure: true, sameSite: 'Lax', path: '/',
    maxAge: 34_560_000,            // 400 days, renewed on every POST /api/session
    // no `domain`: host-only on nerdose.dev
  });
}
```

```ts
// POST /api/session -> 200 { locale, preferred_code_language, created }
const pid = getCookie(c, 'nd_pid');
const existing = pid && isUuid(pid) ? await repo.findById(pid) : null;   // an unknown pid is treated as absent
const player = existing
  ? await repo.touch(existing.id)                                         // last_seen_at = now
  : await repo.create({ locale: pickLocale(c.req.header('accept-language')), preferred_code_language: 'js' });
issuePlayerCookie(c, player.id);
return c.json({ locale: player.locale, preferred_code_language: player.preferred_code_language, created: !existing });
```

```ts
// required: 401 no_session if missing or unknown; optional: used by GET /api/today (has_session: false)
export const playerSession = (mode: 'required' | 'optional') => createMiddleware<AppEnv>(async (c, next) => {
  const pid = getCookie(c, 'nd_pid');
  const player = pid && isUuid(pid) ? await c.var.deps.identity.find(pid) : null;
  if (!player && mode === 'required') throw new AppError('no_session');
  c.set('player', player);
  if (player) c.set('logger', c.var.logger.child({ playerId: player.id }));
  await next();
});
```

Reglas (verbatim):
- The cookie name is `nd_pid` and its value is `players.id` as is.
- Cookie attributes are exactly `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=34560000`, with no `Domain`.
- `POST /api/session` is idempotent: it renews the cookie and `last_seen_at` for an existing player, creates one otherwise, and answers `200 { locale, preferred_code_language, created }`.
- A new player gets `locale` from `Accept-Language` if it is `es` or `en`, else `es`; `preferred_code_language` is `js`.
- A `nd_pid` that does not match an existing player is treated as absent (a new player is created and the cookie replaced).
- Player routes that require identity answer `401 no_session` without a valid cookie. `GET /api/today` works without a cookie and returns `has_session: false`.
- No PII is stored in `players` (no IP, email or fingerprint). The `user_agent` is stored only in the `context` of a report.
- The `api` never trusts a `player_id` from the body, query or headers. The only source is the cookie.
- `players.user_id` is reserved for a future `User` and is never set in v1.
- Admin routes never read or emit `nd_pid`.

Locale (verbatim): "Order: query `?lang=es|en` -> `players.locale` -> `Accept-Language` -> `es`. All `{ es, en }` content is resolved before responding; `message` of errors uses the same locale."

#### `security` — configuración de referencia

```ts
// apps/api/src/http/middleware/security.ts
import { createMiddleware } from 'hono/factory';
import { AppError } from '@nerdose/core';

const MUTATING = new Set(['POST', 'PATCH', 'PUT', 'DELETE']);

// Mounted twice: originAndContentType(env.WEB_ORIGIN) on /api/* (player routes)
// and originAndContentType(env.ADMIN_ORIGIN) on /api/admin/*. Both env vars are required.
export const originAndContentType = (allowedOrigin: string) =>
  createMiddleware(async (c, next) => {
    if (MUTATING.has(c.req.method)) {
      if (c.req.header('origin') !== allowedOrigin) throw new AppError('forbidden_origin');
      if (!c.req.header('content-type')?.toLowerCase().startsWith('application/json')) {
        throw new AppError('unsupported_media_type');
      }
    }
    await next();
  });
```

```ts
// apps/api/src/http/middleware/rate-limit.ts
import { rateLimiter } from 'hono-rate-limiter';
import { AppError } from '@nerdose/core';

export const limit = (opts: { windowMs: number; limit: number; key: (c: Context) => string }) =>
  rateLimiter<AppEnv>({
    windowMs: opts.windowMs,
    limit: opts.limit,
    standardHeaders: 'draft-6',
    keyGenerator: opts.key,
    handler: (c) => {
      c.header('Retry-After', String(Math.ceil(opts.windowMs / 1000)));
      throw new AppError('rate_limited');
    },
  });

export const clientIp = (trustHeader?: string) => (c: Context) =>
  (trustHeader && c.req.header(trustHeader)?.split(',')[0]?.trim()) || 'unknown';
```

```ts
import { secureHeaders } from 'hono/secure-headers';
import { bodyLimit } from 'hono/body-limit';

app.use(secureHeaders());
app.use(bodyLimit({ maxSize: 64 * 1024, onError: () => { throw new AppError('validation_error'); } }));
```

Reglas (verbatim):
- No CORS: the `api` never emits `Access-Control-*` headers and no CORS middleware is installed.
- Every mutation (`POST`, `PATCH`, `PUT`, `DELETE`) requires `Content-Type: application/json`, otherwise `415 unsupported_media_type`.
- Every mutation requires an `Origin` header equal to `WEB_ORIGIN` (player routes) or `ADMIN_ORIGIN` (`/api/admin/*`), otherwise `403 forbidden_origin`. Both variables are required in every environment (ADR-009); the check is never disabled by missing configuration.
- There is no CSRF token. Protection is same origin + `SameSite=Lax` + the two checks above.
- The limits are exactly those of the table, with `hono-rate-limiter` and the in-memory store. No captcha.
- A `429` carries `Retry-After` in seconds and the body `{ "error": { "code": "rate_limited", "message": ... } }`.
- The client IP comes only from the header named by `TRUST_PROXY_HEADER`. Never trust an arbitrary `X-Forwarded-For` that is not configured.
- Per-`player_id` limits apply after the `nd_pid` cookie is resolved.
- Payload size limits are set at the framework level (`bodyLimit`), not in application code.
- Stack traces and internal messages are never exposed (see `error-handling`).
- HTTPS is enforced by the infrastructure (deferred). The `api` does not terminate TLS.
- Moving to more than one `api` instance requires moving the limiter store to Postgres or Redis first (ADR-012).

- Responses have **no generic envelope**: the resource is returned directly. Errors use `{ "error": { "code", "message" } }` per `error-handling`.
- No CORS headers are emitted. Security headers come from `hono/secure-headers`; any relaxation is documented in `overview.md`.
- The `app` is built by `buildApp(deps)` so tests can instantiate it with their own dependencies.

Request context: "Any log inside a handler uses `c.var.logger` (not the global logger) to keep the `requestId`. `player_id` is added to the child logger by `player-session` when the cookie resolves."

#### `orm` — extracto aplicable

```ts
// apps/api/src/domain/identity/identity.repository.ts
import { eq } from 'drizzle-orm';
import { players } from '@nerdose/db';
import type { Db, Tx } from '@nerdose/db';

export class IdentityRepository {
  constructor(private readonly db: Db | Tx) {}

  async findById(id: string) {
    const [row] = await this.db.select().from(players).where(eq(players.id, id));
    return row ?? null;
  }
}
```

Reglas (verbatim, las aplicables):
- No direct `db` calls from HTTP handlers, jobs or use-case functions. Always go through a module repository.
- One repository per domain module. Never share a repository across unrelated modules.
- Use types inferred from the schema (`typeof table.$inferSelect`) or from `@nerdose/db`. No hand-written types that duplicate the schema.
- Day columns are `date` (UTC day) and instants are `timestamptz`. Do not convert them with local timezones.
- Each service MUST only write the tables and columns its role allows (ADR-004). A test runs the expected operations with each role.

#### `error-handling` — extracto aplicable

- `message`: text in the locale resolved for the request (`?lang` → `players.locale` → `Accept-Language` → `es`). No stack traces, SQL or internal details.
- `AppError`: responds with `status` from the catalog, `code` and the localized message; logs at `warn` without stack (`rate_limited` and `no_session` may log at `info`).
- Anything else (including unexpected driver errors): logs at `error` with stack and responds `500 internal_error` with a generic message.
- Never throw a plain `Error` for an expected failure.

#### `logging` — extracto aplicable

- `logger.info({ context }, 'message')`: objeto de contexto primero y mensaje corto y **estático** después.
- Never log: passwords, tokens, API keys, session cookies, request bodies with PII.
- Expected errors (`AppError`): `warn` o `info`, sin stack.
- In tests: silence logs or use a test transport.

#### `testing` — extracto aplicable

- One shared container per suite, started in `globalSetup` (ya existe: `test/global-setup.ts` provee `ownerUrl` y `apiUrl`).
- Every file resets the database in `beforeAll` (`truncateAll` de `@nerdose/db/testing`) and owns its fixtures. Fixtures with owner role; code under test with `nerdose_api`.
- Mutations in tests send `Content-Type: application/json` and a valid `Origin`.
- UNIQUE columns use unique values per test (`randomUUID()`). Assert on content (a specific row exists), not on global counts.
- No wall-clock sleeps.

### Task 4: Repositorio y servicio del módulo `identity`

**Status:** Completed

#### Description
Crea `domain/identity` con el acceso a `players` (repositorio) y la lógica de sesión y preferencias (servicio), sin HTTP. El servicio es idempotente: con un id válido intenta "tocar" el Player (`UPDATE ... SET last_seen_at = now() RETURNING *`) y, si no existe, crea uno. Cubre la persistencia de CA-1, CA-3, CA-4 y CA-7.

#### Acceptance Criteria
1. `IdentityRepository(db: Db | Tx)` expone:
   - `findById(id: string): Promise<Player | null>`
   - `create(input: { locale: Locale; preferredCodeLanguage: CodeLanguage }): Promise<Player>`: `INSERT ... RETURNING *`. No setea `id`, `userId`, `createdAt` ni `lastSeenAt` (defaults de la DB).
   - `touch(id: string): Promise<Player | null>`: `UPDATE players SET last_seen_at = now() WHERE id = $1 RETURNING *`. Devuelve `null` si no hay fila.
   - `updatePreferences(id: string, patch: { locale?: Locale; preferredCodeLanguage?: CodeLanguage }): Promise<Player | null>`: actualiza solo las claves presentes, con `RETURNING *`. Devuelve `null` si no hay fila.
2. `IdentityService` (construido con el repositorio) expone:
   - `startSession({ pid, acceptLanguage }): Promise<{ player: Player; created: boolean }>`. Si `pid` es un UUID válido, hace `touch(pid)`. Si eso da `null` o el `pid` es ausente o inválido, hace `create({ locale: pickLocale(acceptLanguage), preferredCodeLanguage: 'js' })` y devuelve `created: true`.
   - `find(pid: string | undefined): Promise<Player | null>`. Devuelve `null` si `pid` es ausente o no es UUID (no consulta la DB) y, si no, `findById`.
   - `updatePreferences(playerId, patch)`. Si el repositorio devuelve `null` (el Player desapareció en medio), lanza `AppError('no_session')`.
3. La validación de UUID usa `z.uuid()` (Zod 4) o equivalente. Un `pid` inválido nunca llega a PostgreSQL (TS-7).
4. Todo corre con el rol `nerdose_api` sin errores de permisos (TS-57). No hay `DELETE` sobre `players` en ningún lado.
5. `user_id` nunca se escribe.

#### Technical Details

**Architectural Context References:**
