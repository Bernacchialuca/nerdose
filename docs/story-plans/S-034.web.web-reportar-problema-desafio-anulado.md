## Referencia de la Story

- **Story:** [S-034](../stories/S-034.web-reportar-problema-desafio-anulado.md)
- **Servicio:** web
- **Resumen:** Cierra el circuito del jugador de REQ-007 en `apps/web`: el link «Reportar un problema» (con su estado «Ya reportaste este desafío») en la partida, el resultado y el resultado anulado de Devdle, Grep Grid y Tech Timeline; el diálogo O-01 (motivo con `select` nativo, mensaje opcional con contador `0 / 1000`, aviso anti-spoiler desde la partida, confirmación dentro del overlay y todos los errores); y el aviso O-02 de desafío anulado con «Marcar como completado» (`acknowledge-void`), que lleva al resultado anulado mínimo. > **Alcance de este plan:** solo `apps/web`. La fila `ui` de la story («Contenedor de diálogo (`panel` + `button` …; bottom-sheet anclado en mobile)», impacto Bajo) tiene su propio plan y **se implementa después** que este (orden de la tabla de la story). Lo que ese `Dialog` todavía no hace y la UX pide (anclar el panel al borde inferior en mobile, `aria-describedby`, fondo `inert`) queda como **pendiente de `ui`** (D2), sin redeclarar estilos en `web`.
>
> **Rutas:** todas las rutas de «Archivos a crear/modificar» son relativas a `apps/web/`.
>
> **Dependencias:** S-031 (API del jugador: `report`, `acknowledge-void`, `GameToday.reported`, Play `voided` en `getToday`) está **Completed** y mergeada en `dev`. Todos los tests usan MSW; la verificación manual usa la `api` real.
>
> **Catálogo de código reutilizable:** no existe `docs/reusable-code/web/index.md` (se recomienda `/service-update-reusable-code` para `web`). El código reutilizable de abajo se relevó leyendo `apps/web/src` y `packages/ui/src` al planificar.

### Arquitectura del Servicio (`docs/architectures/web/overview.md`, partes aplicables)

- SPA de los jugadores (`nerdose.dev`), mobile-first desde 320 px, WCAG 2.1 AA, jugable completa con teclado. Nunca tiene la solución antes de que termine la partida: la `api` es la dueña de la verdad.
- **Módulos:** `shell`, `catalog` (home), **`game-host`** (`/:game_id`: carga con `React.lazy` el `client` del juego por registry; instrucciones, partida, resultado y share), `stats`, `about`, `session` (sesión anónima por cookie `nd_pid` gestionada por la `api`, preferencias y aviso de cookies bloqueadas).
- Cliente HTTP de mismo origen (`/api/*`), JSON `snake_case` sin transformar y errores por `error.code` (ADR-015).
- Identidad anónima por cookie `nd_pid` `HttpOnly`: el front no la lee ni la escribe; solo llama a `POST /api/session` (ADR-009).
- Contextos de React a nivel app: solo sesión/preferencias (locale) además del `QueryClientProvider`.
- **Contrato de props de los `client`** (ADR-006): cada `client` exporta `Instructions`, `Game`, `Result` y `share(result, number)`; `web` los declara estructuralmente en `GameClient` (`apps/web/src/modules/game-host/types.ts`). `ResultProps` ya tiene los slots `aside?: ReactNode` y `footer?: ReactNode` (los tres `Result` los renderizan); `GameProps` **no** tiene slot lateral (solo `notices`).
- **Deuda de e2e (D3):** Playwright no está instalado: las stories de juego cubren los flujos con tests de ruta en jsdom, axe y verificación manual.
- Almacenamiento del navegador: solo conveniencias por visitante, con `try/catch`. Esta story no usa storage.

### Convenciones activas (todas custom, `docs/architectures/web/conventions/`; partes aplicables copiadas)

**`_base`**
- SPA con Vite, sin SSR. TypeScript estricto; sin `any` salvo en bordes con librerías sin tipos.
- Estructura: `src/modules/{module}/{routes,components,api}/`, `index.ts` como superficie pública; un módulo no importa internals de otro (usa su `index.ts`).
- Naming: archivos `kebab-case`, componentes `PascalCase`, hooks `use-*.ts` → `useX`, query keys por factory de módulo, campos de API en `snake_case` tal cual.
- Imports: `@/*` absolutos; orden (1) externos y `@nerdose/*`, (2) `@/`, (3) relativos; `import type` para tipos.
- Fechas: el cliente nunca decide qué es «hoy»; el día y el número vienen de la `api`.
- Async: `async/await`; los handlers que llaman código async manejan o muestran el error. Comentarios solo para el porqué.

**`data-fetching`** (reglas, verbatim)
- Call `fetch` only from `lib/api-client.ts`. No `axios`, no ad-hoc `fetch` in components.
- Server data lives in TanStack Query. Never copy query results into `useState` or a context.
- Do not convert keys to `camelCase` and do not rename API fields; types use the API names.
- URLs are relative (`/api/...`). No hardcoded hosts, no CORS configuration, no `VITE_API_URL`.
- Mutating requests send `Content-Type: application/json` (the wrapper does it when `json` is given).
- Mutations of a game round include `challenge_number`; the client never sends a date.
- Query keys come from per-module factories, never inline string literals repeated across files.
- Do not set `retry` on mutations; a repeated move is the user's decision.
- Branch on `ApiError.code`, never on `message` text or on the HTTP status alone.
- Never log or persist API responses outside the Query cache.
- Mutations invalidate the queries they make stale; they do not hand-edit caches unless the response carries the new state.

`api<T>(path, { method, json })` lanza `ApiError(status, code, message, retryAfter?)`; una falla de red es un `TypeError` de `fetch` (no `ApiError`). `queryClient`: `staleTime: 30_000`, sin refetch on focus, sin retry de 4xx, `mutations: { retry: false }`.

**`error-handling`** (tabla de recuperación de `web`, filas aplicables, verbatim)

| `code` | Recovery in `web` |
|---|---|
| `challenge_expired` | Invalidate `today` and the game query and reload the challenge; show a short "new challenge" notice |
| `challenge_voided` | Refetch; the game view switches to the voided state and offers `acknowledge-void` |
| `no_session` | Call `POST /api/session` once and retry; if still without session, show the blocked-cookies notice and disable play |
| `invalid_move`, `validation_error`, `invalid_report` | Inline message on the control; no navigation |
| `rate_limited` | Message with the `Retry-After` wait; disable the action until then |
| `already_reported` | Show the "already reported" state |
| `internal_error`, network | Inline retry, or the route error screen if the whole view failed |

Reglas: branch on `ApiError.code`; never show stack traces or raw JSON; every error state has a way forward; error messages are announced (`role="alert"` or `aria-live`) and do not rely only on color; expected errors are handled where they occur; do not swallow errors silently; UI-only messages come from i18n.

**`game-clients`** (reglas, verbatim)
- Import only `@nerdose/game-<game_id>/client`. Never `./definition` or `./generator`, and never `@nerdose/polyglot`.
- The registry is the only place that lists games. No `if (gameId === ...)` or `switch` by game anywhere in `apps/*`.
- The shell renders games only through `Instructions`, `Game`, `Result` and `share`; it does not read game-specific fields.
- The `client` never receives the solution before the round ends in `web`; the app never requests or caches anything beyond the public view and the move responses.

**`styling`**
- Solo tokens de `@nerdose/ui` (sin hex, sin valores arbitrarios `[#…]`/`[12px]`, sin `rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`, `outline-none` en `game-host`); `cn()` para clases condicionales; foco visible con `focus-visible:` (lo dan `buttonClass`/`linkClass`/`FOCUS_RING`); estado nunca solo por color; `prefers-reduced-motion`.
- **Responsive (REQ-003):** sin media queries ni prefijos `sm:/md:/lg:` (en `game-host` lo exige `game-host-styles.test.ts`). Layout con `flex-wrap` + `basis`. Mobile-first desde 320 px, sin scroll horizontal; targets ≥ 44 × 44.
- `buttonClass({ variant, size, game?, fullWidth?, disabled? })` y `linkClass({ tone? })` se aplican a `<button>` y a `<Link>`.

**`state-management`**
- Server data solo en TanStack Query; estado efímero de UI (abierto/cerrado, valor del campo) en `useState`; derivados en render; `useEffect` no sincroniza un estado con otro.

**`i18n`** (reglas, verbatim)
- Every UI string goes through `t()`; no hardcoded user-facing literals in components.
- Every key exists in both `es` and `en`; a missing key fails the unit test that compares both resource trees.
- Never translate or choose a language for content that comes from the `api`; render it as received.
- Never build sentences by concatenating translated fragments; use interpolation.
- Do not translate error codes; branch on codes and show the `api`'s message or a UI key.

**`accessibility`** (reglas, verbatim)
- Contrast is at least 4.5:1 for text (3:1 for large text and UI boundaries) against its actual background.
- No interactive element is built from a `<div>` or `<span>` with a click handler; use a native control.
- Every image or icon is either decorative (`aria-hidden`) or has an accessible name.
- Color is never the only carrier of meaning.
- Focus is never removed (`outline: none`) without a visible replacement.
- Modal and overlay UI traps focus while open, closes with `Escape` and returns focus to the trigger.
- Dynamic updates are announced via live regions; do not move focus unexpectedly.
- axe-core reports zero violations in unit checks and e2e page checks.
- Every input has a visible `<label>` or an `aria-label`; errors are tied with `aria-describedby`.

**`testing-unit`** (reglas, verbatim)
- Query by role, label or visible text. `data-testid` only when no accessible query exists.
- Use `userEvent`, not `fireEvent`, for interactions.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- Fixtures use the API's `snake_case` names; do not write camelCase fixtures.
- Mock the network with MSW, never the app's own modules (api client, hooks) except to isolate a single unit.
- No snapshot tests of large DOM trees.
- Tests do not rely on the real date or timers; use fake timers.
- Test names state the behavior ("shows ... when ..."), not the implementation.
- Tests never hit a real `api`.

**`testing-e2e`**: Playwright no está instalado (deuda D3 del overview). Se cubre con tests de ruta completa en jsdom (router real, MSW) + axe + verificación manual (D9).

**`analytics`**: sin eventos nuevos (el único evento custom es `share:<game_id>`).

### ADRs Relevantes

**ADR-015: Contratos JSON y errores** — Decisión: JSON `snake_case` sin transformar, errores `{ error: { code, message } }` con catálogo cerrado, `message` en el locale resuelto. Reglas de Implementación (verbatim):
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
- Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
- Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; `code_language`: `js | go | java`; `locale`: `es | en`).
- Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.

**ADR-009: Identidad del jugador anónimo** — Decisión: cookie `nd_pid` `HttpOnly` emitida por la `api`; el front solo llama a `POST /api/session`. Reglas aplicables (verbatim):
- `POST /api/session` MUST ser idempotente y responder `200 { locale, preferred_code_language, created }`.
- Las rutas de jugador que lo exigen MUST responder `401` con `{ "error": { "code": "no_session", … } }` si falta la cookie o no es válida.
- Toda mutación (`POST`, `PATCH`) MUST rechazar con `415` un `Content-Type` distinto de `application/json`, y con `403 forbidden_origin` un header `Origin` ausente o distinto del permitido: `WEB_ORIGIN` para las rutas de jugador y `ADMIN_ORIGIN` para `/api/admin/*`. […] El chequeo nunca se desactiva por falta de configuración.
- MUST NOT guardarse PII del jugador (ni IP, ni email, ni fingerprint) en `players`. El `user_agent` solo se guarda en el `context` de un reporte.

**ADR-006: Contrato GameDefinition** — Regla aplicable (verbatim): «Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.» → `ReportLink`, `ReportDialog` y O-02 son genéricos: reciben `gameId` y lo usan solo en la URL y en `t('games.<gameId>.name')`.

**ADR-017: Alertas registradas en el admin** — El umbral y `alerted_at` son del servidor; la web no muestra nada de la alerta (la confirmación es la misma alcance o no el umbral).

### API Context (de `docs/apis/api.yaml`; ningún cambio de API en esta story)

**`GET /api/games/{game_id}/today?lang={locale}` → `200 GameToday`** (campos requeridos: `game_id, date, number, challenge_status, public_view, play, result, game_stats, reported`)
- `challenge_status: 'published' | 'voided' | 'none'`.
- `public_view`: `null` si `challenge_status` es `none` o `voided`.
- `play`: «Con `challenge_status: voided` viene la Play del jugador si existe (`status: voided`)». `PlayView = { status: 'in_progress'|'won'|'lost'|'voided', state, score, code_language }`.
- `result`: `null` salvo Play terminada (con `voided`, `null`).
- `game_stats`: «Si la Play terminó o está `voided`».
- **`reported: boolean`** — «El jugador ya reportó este desafío; false sin sesión».

**`POST /api/games/{game_id}/today/report`** (`reportChallenge`, cookie `nd_pid`, rate limit 10/hora por IP)
- Body `ReportRequest`: `{ challenge_number: integer ≥ 1 (required), reason: ReportReason (required), message?: string maxLength 1000, code_language?: 'js'|'go'|'java' }` («Solo big-o y bug-hunt; si la Play tiene `code_language`, manda la Play»).
- `ReportReason`: `wrong_answer | ambiguous | wrong_explanation | translation | display_bug | other` (`REPORT_REASONS` de `@nerdose/core`, en ese orden).
- Descripción: «Solo sobre un desafío `published` o `voided` de ese juego, de hoy o de un día pasado, identificado por `challenge_number`. `context` lo arma el servidor (`code_language`, `play_status`, `play_state`, `user_agent`) y `locale`. Uno por jugador y desafío.»
- `201 { report_id: uuid }` — ej. `{ report_id: 3f6c1d2e-8a4b-4c1f-9e2a-7b5d0c9e1a23 }`.
- `401 no_session` · `403 forbidden_origin` · `404 not_found` (desafío inexistente, futuro o no reportable) · `409 already_reported` (`{ error: { code: already_reported, message: 'Ya reportaste este desafío' } }`) · `415` · `422 invalid_report` («`reason` inválido o `message` > 1000 caracteres»; la `api` hace `trim` del mensaje) · `429 rate_limited` (header `Retry-After`).

**`POST /api/games/{game_id}/today/acknowledge-void`** (`acknowledgeVoid`, cookie `nd_pid`, rate limit 30/min por `player_id`)
- Body `ChallengeNumberBody`: `{ challenge_number: 128 }`.
- Descripción: «Para un jugador sin Play en el desafío anulado de hoy: crea una Play `voided` (`finished_at = now()`), `ON CONFLICT DO NOTHING`, y actualiza rachas y `total_completed`. Es idempotente: con Play existente devuelve `play: { status: voided }` y las rachas vivas sin volver a sumar.»
- `200 AcknowledgeVoidResponse`: `{ play: { status: 'voided' }, streaks: { game: { current, max }, global: { current, max } } }` — ej. `{ play: { status: voided }, streaks: { game: { current: 4, max: 9 }, global: { current: 6, max: 12 } } }`.
- `401 no_session` · `403` · `404 no_challenge_today` · `409 challenge_expired` / `409 not_voided` (`{ error: { code: not_voided, message: 'Este desafío no está anulado' } }`) · `415` · `422 validation_error` · `429 rate_limited`.

**`POST /api/session`** → `200 { locale, preferred_code_language, created }` (lo usa `withSessionRetry`).

**`GET /api/today?lang={locale}`** → `TodayGame = { game_id, challenge_status, play_status, history_label, current_streak }` por juego (para la tarjeta de la home).

**Mensajes de error reales de la `api`** (`apps/api/src/http/error-messages.ts`): `already_reported` → «Ya reportaste este desafío.» / «You already reported this challenge.»; `invalid_report` → «Reporte inválido.»; `rate_limited` → «Demasiadas solicitudes.». La UI **no** los muestra: usa sus propias claves de i18n (UX O-01), ramificando por `code`.

### Database Context

No aplica: `web` no accede a la base. Los efectos (fila en `challenge_reports`, Play `voided`, rachas) los hace la `api` (S-031).

### Flow Context

**`reporte-de-problema`** (paso 1, el único de `web`; el resto es de la `api`):
- **Request:** `POST /api/games/{game_id}/today/report` con body `{ "challenge_number": integer, "reason": "wrong_answer | ambiguous | wrong_explanation | translation | display_bug | other", "message": "string (opcional, ≤ 1000)", "code_language": "js | go | java (opcional)" }`. Validaciones del servidor: `nd_pid` → desafío `published`/`voided` con `date <= hoy` (REQ-007 decisión 4: reemplaza el par `no_challenge_today`/`challenge_expired` en este endpoint) → body.
- **Response:** `201 { "report_id": "uuid" }`.
- Manejo de errores (lado web, de la UX vigente): `401 no_session` → web recrea la sesión y reintenta una vez; `409 already_reported` → «ya reportaste este desafío»; `422 invalid_report` → web marca el campo; `429` → mensaje genérico; red/5xx → «No pudimos enviar el reporte. Probá de nuevo.» (el flujo menciona `404 no_challenge_today` / `409 challenge_expired`, que S-031 reemplazó por `404 not_found`; ver D7).
- **Este plan:** implementa el paso 1 en `game-host` y la reacción a cada respuesta.

**`anulacion-de-desafio`** (pasos 4 y 5):
- **Paso 4 — Jugador sin Play ve el desafío anulado:** `GET /api/games/{game_id}/today` → `200` con `challenge_status: "voided"`, `public_view: null`, `play: null`. web muestra «Este desafío tenía un error y fue anulado. Tu racha no se ve afectada» con un botón. (Con Play: REQ-007 decisión 5, `play.status: 'voided'` + `game_stats`, `result: null` → resultado anulado mínimo.)

#### Flujos relevantes (`surfaces/web/user-flows.md`)

**Flujo 3 — Desafío anulado y marcar como completado.** Trigger: el jugador entra a `home` o a `{juego}-instrucciones` y el desafío de hoy fue anulado antes de que jugara. Happy path: (1) tarjeta «anulado» en `home`, la toca; (2) se abre O-02 con «Marcar como completado»; (3) la toca: Play `voided` que suma a racha del juego, global y `total_completed`, no a `played`/`wins`/`extra`; (4) se abre `{juego}-resultado` en estado anulado; (5) vuelve a `home`, la tarjeta aparece completada. Alternativos: entrada por URL directa → `{juego}-instrucciones` «Anulado y sin Play»: se muestra O-02 y no se puede empezar; anulación mientras jugaba → siguiente jugada `challenge_voided`, al volver ve el resultado anulado; anulación después de terminar → resultado anulado (aviso + rachas, sin solución ni Compartir) y puede reportar; cerrar O-02 sin marcar → la tarjeta sigue «anulado» y puede marcar después, el mismo día. Errores: doble toque idempotente; `challenge_expired` → la acción se rechaza, las rachas no cambian y la pantalla recarga el desafío de hoy; `not_voided` → O-02 se cierra y la pantalla se refresca; falla de red → «No pudimos marcar el desafío como completado. Probá de nuevo.» y deja reintentar; sin sesión → O-03. Estado final: resultado anulado y tarjeta completada.

**Flujo 4 — Reportar un problema del desafío.** Happy path: (1) toca «Reportar un problema» (si ya reportó: «Ya reportaste este desafío», deshabilitado); (2) O-01, motivo de los 6 y mensaje opcional ≤ 1000 con contador; desde partida, el aviso; (3) «Enviar reporte»; (4) «Gracias, recibimos tu reporte.», «Cerrar», el enlace pasa a «Ya reportaste este desafío»; sigue donde estaba. Alternativos: desde la partida (al cerrar sigue en el mismo estado); tras ver el resultado (sin el aviso); cancelar (no se guarda nada); sobre un desafío anulado (permitido desde el resultado anulado). Errores: `already_reported` → «Ya reportaste este desafío. Lo vamos a revisar.»; límite por IP → «Se enviaron muchos reportes desde esta conexión. Probá de nuevo más tarde.», conserva lo escrito; `invalid_report` → se marca el campo; **cambio de día con O-01 abierto → «El reporte se guarda contra el desafío que el jugador estaba viendo (lleva `challenge_number`; la API acepta desafíos pasados `published` o `voided`)»**; `no_session` → se recrea y se reintenta una vez; red → «No pudimos enviar el reporte. Probá de nuevo.», conserva motivo y mensaje.

#### Cross-surface (`cross-surface-flows.md`, flujo 1, parte web)

El responsable anula en el admin (C-41) → la `api` recarga la cache de hoy tras el COMMIT → el jugador ve `challenge_status: voided` en `GET /api/games/{id}/today` (sin Play: O-02; con Play: resultado anulado). Sincronización por pedido (sin tiempo real): la web lo ve al próximo `GET` (apertura del juego, invalidación o `challenge_voided` en una jugada).

- **Versión fijada:** DS `web` v1.7.0 (frontmatter de `docs/design-system/web/README.md`; la revisión UX de REQ-007 se verificó contra v1.8.0 del CHANGELOG). Accent de la superficie: `color.brand.primary` = `#3DDC84` (`accent`), ya resuelto por `buttonClass`/`linkClass`.

- **Componentes usados:**
  - **banner** (v1.4.0): `warning` (adaptación: fondo `#140F07` / borde `#3A2A12`, ícono `!` en círculo `status.warning`, subtítulo `#C9A46A`), `success` (fondo `#0C1A12` / borde `#1E4A30`, `check` sobre `#3DDC84`, subtítulo `#A9C9B5`); container `flex-wrap`, padding 18 22, `radius.panel`, gap 16; título `type.title.banner` (Mono 700 18) y subtítulo `type.body.sm.tight` (Inter 14); `role="status"` para `success`/`failure`/`warning`; «No poner más de un banner a la vez»; API `variant, title, children, action, titleAs, announce`.
  - **alert** (v1.0.0): solo error de sistema; `role="alert"`; tinte `#1C0F0E` / `#4A2220`; ícono `x`; título + detalle; «Qué pasó + qué hacer, en lenguaje llano»; «No mostrar más de una Alert a la vez».
  - **button** (`buttonClass`): `primary` verde (avanzar), `secondary` outline, `md` (min-h-11), `disabled` neutro con `aria-disabled`.
  - **link** (v1.3.0): Mono sin subrayado; `subtle` en `type.label.comment` (13) `text.body` → hover `text.primary`, `min-height: 44px`; `<a>`/botón nativo; foco ≥ 3:1. **No define estado deshabilitado** (gap aceptado, abajo).
  - **panel** + **button** como contenedor de diálogo, según el pattern de O-04 (`grep-grid.surrender-dialog`), implementado hoy por `Dialog` de `@nerdose/ui`.
- **Accesibilidad (`guidelines/accessibility.md`, placeholder v0.1.0, áreas clave):** contraste texto ≥ 4.5:1, componentes ≥ 3:1; no comunicar estado solo con color; todo interactivo por teclado con foco visible; ESC cierra modales; sin keyboard traps; iconos decorativos `aria-hidden`; live regions para feedback dinámico; cada input con `<label>`; errores con `aria-invalid` + `aria-describedby`; required con `aria-required`; targets ≥ 44 × 44 con ≥ 8 px entre targets; `prefers-reduced-motion`.

### Decisiones de este plan (derivadas, sin inventar contrato)

- **D1 — `ReportDialog` fuera del `switch`, con snapshot.** `GameRoute` guarda `reportTarget: { number: number; from: 'game' | 'result' } | null` y monta `<ReportDialog>` **después** del contenido de cualquier `view.kind` mientras `reportTarget !== null`. El número se fija al abrir. Así, si el día cambia con O-01 abierto (la cuenta regresiva de `ResultExits` invalida `today` y `game-today` a las 00:00 UTC y la vista pasa a instrucciones del nuevo día), el diálogo **no se desmonta** y el reporte sale con el `challenge_number` visto (CA-4, flujo 4). `ReportLink` solo llama a `onOpen()`.
- **D2 — `Dialog` de `@nerdose/ui` tal cual (pendiente de `ui`).** O-01 y O-02 usan `Dialog variant="modal"` (O-02 con `role="alertdialog"`). Hoy el panel queda centrado también en mobile (ancho casi completo por `px-4`), sin `aria-describedby` al aviso y sin `inert` en el fondo (el foco igual queda atrapado y `aria-modal="true"` oculta el resto a los lectores). Esas tres piezas son del plan `ui` de S-034; si ese plan agrega una variante o prop nueva (p. ej. un `variant` de sheet o `describedById`), **ese plan** actualiza los dos consumidores de `web` (cambio de una línea). Los tests de `web` no dependen de CSS (`css: false`). Mitigación del `aria-describedby`: el aviso de spoilers es el **primer** contenido del panel, antes del formulario, así que se lee antes («El aviso de spoilers se lee antes del formulario»).
- **D3 — Orden de las acciones sin breakpoints.** `game-host` no admite `sm:`/`lg:`. Las acciones van en `div.flex flex-row-reverse flex-wrap gap-3` con **DOM [primaria, secundaria]** y cada botón `grow basis-50` (precedente O-04): en una fila (desktop, panel `max-w-xl`) queda secundaria a la izquierda y primaria a la derecha; al envolver (mobile, contenido < 412 px) la primaria queda arriba. El orden de foco es primaria → secundaria: coincide con O-02 (texto → btn-marcar → btn-cerrar) y con O-01 mobile; en O-01 desktop difiere de «btn-cancelar → btn-enviar» (aceptado: no hay forma de tener los dos órdenes con un solo DOM sin media queries).
- **D4 — `link-reportar` como `<button>`.** Abre un overlay (acción, no navegación): `<button type="button" className={linkClass({ tone: 'subtle' })}>`. Estado `ya reportado`: el mismo botón con `aria-disabled="true"`, `cn(linkClass({ tone: 'subtle' }), 'text-text-disabled hover:text-text-disabled cursor-not-allowed')`, `<span aria-hidden="true">✓</span>` + «Ya reportaste este desafío», y el `onClick` no abre nada. Sigue siendo focusable (para devolverle el foco al cerrar O-01).
- **D5 — Posición del link.** Partida: el host lo renderiza **debajo** de `<client.Game>` (la story: «montados por el host debajo de `Game` … sin cambios en los `client`»; `GameProps` no tiene slot lateral). Coincide con el orden mobile de los tres `*-partida` (último bloque); en desktop queda debajo de la fila del juego en vez de al final de la col 5/12 (desvío aceptado por la story). Resultado: en el slot **`aside`** de `<client.Result>`: Devdle y Grep Grid lo dibujan al final de la columna lateral (= screen.md); Timeline lo dibuja en la col 4/12 debajo de «tu orden» (el screen.md lo pone en la col 8/12 bajo la barra de salida; desvío menor, sin cambiar el `client`). Resultado anulado (`VoidedResultView`, de `web`): después de `ResultExits`.
- **D6 — Íconos.** `@nerdose/ui` no exporta un ícono `warning` ni `info` (solo `HelpIcon`, `ChartIcon`, `ShareIcon`). El link en estado normal va **sin ícono** (el texto lo explica) y `btn-aviso-anulado` también; `ya reportado`, `btn-enviar` y `btn-marcar` usan `✓` Unicode `aria-hidden` (inventario de iconografía). Si el plan `ui` de S-034 agrega `WarningIcon`/`InfoIcon`, se pueden sumar sin cambiar tests.
- **D7 — Errores de `report` no listados en la UX.** `404 not_found` (desafío no reportable) → misma `alerta-sistema` («No pudimos enviar el reporte. Probá de nuevo.»). `no_session` que persiste tras el reintento único → `alerta-sistema`. `422 invalid_report` → error del campo **mensaje** («El mensaje puede tener hasta 1000 caracteres.»), porque el `reason` siempre sale del enum. `rate_limited` → texto «límite de reportes» (no se usa `Retry-After`: la UX define un mensaje genérico sin espera). El texto de error de la `api` no se muestra (se ramifica por `code`).
- **D8 — Errores de `acknowledge-void`.** `challenge_expired` → cierra O-02 y aplica `onActionError` (`setDayChanged(true)` + `invalidateDay()`): la vista pasa a instrucciones del desafío nuevo con el aviso «Empezó el desafío #N…». `not_voided` y `no_challenge_today` → cierra O-02 e `invalidateDay()`. Red, 5xx, `rate_limited`, `no_session` persistente y cualquier otro → `alerta-sistema` dentro de O-02 («No pudimos marcar el desafío como completado. Probá de nuevo.»), botón habilitado para reintentar. En `200`, el `onSuccess` **devuelve** la promesa de invalidar `today` y `game-today`, así la mutación sigue `pending` («Marcando…») hasta que llega `GameToday` con la Play `voided` y la vista pasa sola a `voidedResult` (O-02 se desmonta con `VoidedView`). No se edita la cache a mano (la respuesta no trae `game_stats`).
- **D9 — Sin Playwright (precedente S-013/S-021/S-024/S-029/S-033).** Los flujos se cubren con tests de ruta completa en jsdom (router real, MSW) + axe por overlay + verificación manual contra la `api` real (TS-46).
- **D10 — Tarjeta anulada de la home.** La story no lista `catalog`, pero CA-5/CA-7 («cuando abre el juego») y el flujo 3 entran por la tarjeta, que hoy no tiene CTA (`cta: null`). Se aplica lo que ya define la UX (`home.md` `btn-aviso-anulado`, product-map «Anulado»): sin Play `voided` → `cta: { kind: 'link', to: '/<game_id>', label: 'voided', tone: 'secondary' }` («Ver aviso de anulación», que abre la ruta del juego, donde O-02 se abre solo); con `play_status === 'voided'` → se ve **completada** (`status: 'completed'`, `label: history_label`, CTA «Ver resultado» `secondary`). Sin sesión activa, el CTA queda `disabled` como los demás.
- **D11 — Reapertura de O-02.** O-02 se abre solo al entrar al estado `voided` (UX). Para poder «marcar después, el mismo día» sin recargar, el `Banner warning` de `VoidedView` suma la acción `secondary` «Ver aviso de anulación» (mismo texto que `btn-aviso-anulado`), que lo reabre. Al cerrar O-02, el foco va a esa acción (equivale a «lo devuelve a `alerta-anulado`»).
- **D12 — Textos derivados (no definidos en la UX):** opción vacía del select «Sin elegir» / «Not selected»; `aria-label` del ícono de cierre «Cerrar» / «Close»; subtítulo del diálogo `{{game}} #{{number}}` (ej. «Devdle #128»); **todos los textos en inglés** (la UX solo da ES) — ver la tabla de i18n de la Tarea 1.
- **D13 — Mensaje y contador.** Se envía `message` solo si `message.trim() !== ''` (si no, la clave no va en el body). `code_language` no se envía (solo aplica a big-o/bug-hunt, que no tienen client; enviarlo requeriría lógica por juego). El `textarea` tiene `maxLength={1000}`; el contador `{{used}} / {{max}}` va como `hint` del campo (ligado por `aria-describedby`) dentro de un `<span aria-live={used > 900 ? 'polite' : 'off'}>`. El error «El mensaje puede tener hasta 1000 caracteres.» se muestra **solo** ante `422 invalid_report` (a 1000 justos el mensaje es válido).
- **D14 — Foco en O-01.** Foco inicial en el select (`initialFocusRef` → `selectRef`). Error de validación → foco al select. Al pasar a `success`/`ya reportado` (los campos y el botón enfocado desaparecen) → foco al botón «Cerrar» (efecto sobre el cambio de fase). Al cerrar, `Dialog` devuelve el foco al disparador (el link, ahora «Ya reportaste este desafío»).
