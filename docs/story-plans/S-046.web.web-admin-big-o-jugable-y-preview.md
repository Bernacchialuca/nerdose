### Convenciones activas (extractos aplicables, verbatim)

#### `game-clients`
- The registry is the only place that lists games. No `if (gameId === ...)` or `switch` by game anywhere in `apps/*`.
- Each game is loaded with a dynamic `import()` so it is its own chunk.
- The shell renders games only through `Instructions`, `Game`, `Result` and `share`; it does not read game-specific fields.
- The `client` never receives the solution before the round ends in `web`; the app never requests or caches anything beyond the public view and the move responses.
- Share text is never built by the shell; it always comes from the game's `share()`.
- Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`.
- Adding a game must require only a new package, a registry line and its translations.
- Shiki (big-o, bug-hunt) and dnd-kit (timeline) are dependencies of the game packages and are loaded in the game's own chunk. The shell never imports them.
- `admin` mounts … `Preview` … (`web` never mounts `Preview`, ADR-006).
- **Update (REQ-005):** `GameProps.feedback: unknown | null`: the host passes the last `MoveResponse.feedback` … The host does not interpret it.

#### `data-fetching`
- Server data lives in TanStack Query. Never copy query results into `useState` or a context.
- Mutations invalidate the queries they make stale; they do not hand-edit caches unless the response carries the new state.
- Do not convert keys to `camelCase` and do not rename API fields; types use the API names.
- Mutations of a game round include `challenge_number`; the client never sends a date.
- Branch on `ApiError.code`, never on `message` text or on the HTTP status alone.

#### `state-management`
- In-progress game interaction that the game owns (selection, drag order) → State inside the game's `client`.
- App-wide, rarely changing and needed far from its source (locale, session status) → A React context, in `app/`.
- Contexts hold stable, low-frequency values only … Expose a hook (`useX`) that throws a clear error when used outside its provider.
- Never store the solution, game state of an unfinished round, or tokens in `localStorage`. `useEffect` is not used to sync one piece of state into another.

#### `_base`
- A module never imports from another module's internals; it uses that module's `index.ts` or goes through `lib/` or a shared package.
- From a game package, only the `./client` entry may be imported. Never `./definition` or `./generator`. Never import `@nerdose/db`, `@nerdose/polyglot` or `@nerdose/content`.
- Naming: archivos `kebab-case`, hooks `use-*`, constantes `SCREAMING_SNAKE_CASE`, campos de API en `snake_case` exactos. `import type` para tipos. Sin comentarios salvo el porqué.

#### `routing`
- A game's code is loaded only when its route (or its preview of instructions) is opened; the home never imports a game's `client` entry.
- No per-game `if`/`switch` in the router or the shell; the registry decides. Each route sets a meaningful `document.title` and moves focus on navigation.

#### `i18n`
- Never translate or choose a language for content that comes from the `api`; render it as received. Game packages ship their own UI strings through the same i18n instance (a namespace per game).
- Changing language updates `<html lang>` and refetches content queries.

#### `error-handling` (tabla de recuperación, filas aplicables)
| `code` | Recovery in `web` |
|---|---|
| `challenge_expired` | Invalidate `today` and the game query and reload the challenge; show a short "new challenge" notice |
| `challenge_voided` | Refetch; the game view switches to the voided state and offers `acknowledge-void` |
| `game_finished` | Refetch the play state and show the result |
| `no_session` | Call `POST /api/session` once and retry; if still without session, show the blocked-cookies notice and disable play |
| `invalid_move`, `validation_error`, `invalid_report` | Inline message on the control; no navigation |
| `rate_limited` | Message with the `Retry-After` wait; disable the action until then |

#### `accessibility`
- Each of the 5 games can be completed with the keyboard alone (NFR-U03). Color is never the only carrier of meaning. Dynamic updates are announced via live regions. axe-core reports zero violations in unit checks and e2e page checks. Touch targets ≥ 44 × 44 px; layout reflows at 320 px without horizontal scroll.

#### `testing-unit`
- Query by role, label or visible text. Use `userEvent`, not `fireEvent`. Each interactive component has an axe check. Fixtures use the API's `snake_case` names. Mock the network with MSW, never the app's own modules. Tests do not rely on the real date or timers. No snapshot tests of large DOM trees.

#### `styling`
- Use only the tokens. No literal hex colors, no arbitrary `[#abc]` color values in components. Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them. Mobile-first from 320 px. (Guarda del módulo `game-host`, TS-54 vigente: sin hex, arbitrarios, utilidades genéricas ni prefijos responsive `sm:|md:|lg:|xl:` en sus `.tsx`.)

#### `analytics`
- The only custom event is `share:<game_id>`, with no custom properties. Share events are fired by the share button after `navigator.share` or the clipboard copy succeeds.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.
- Decisión: «Shiki (core, motor de regex JS, gramáticas js/go/java), cargado lazy solo en Big O y Bug Hunt.»

#### ADR-003: Monorepo (reglas aplicables)
- `apps/web` y `apps/admin` MUST importar solo `./client`.
- `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)
- La `api` MUST guardar `plays.code_language = codeLanguage(state)` al cerrar la Play y, si no es `null`, actualizar `players.preferred_code_language` en la misma transacción, sin ramificar por `game_id` (REQ-009).
- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
- `Preview` MUST ser de solo lectura … `web` MUST NOT montarla (necesita el `payload` completo, que solo devuelve `/api/admin/*`).
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015: Contratos JSON y errores (reglas aplicables)
- Todas las propiedades JSON MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Los enums MUST serializarse con sus valores exactos del dominio (`code_language`: `js | go | java`; `locale`: `es | en`).

#### ADR-014: Métricas y analítica
- `track('share:<game_id>')` lo llama el host (`web`) después de compartir; el client no importa `track`.

### Decisiones de diseño de REQ-009 aplicables (verbatim)

- **Decisión 6:** `BigOState = { language?, option? }`; mientras la Play está `in_progress` el estado sigue vacío (la opción seleccionada y el lenguaje visible viven solo en el cliente, CA 3 y 8).
- **Decisión 7:** `share(result, number)` = `🧮 Big O #${number}` / `${r.win ? '🟩' : '🟥'} ${LANGUAGE_LABEL[r.code_language]}` / `nerdose.dev`, idéntico en es y en, sin la opción elegida ni la correcta (CA 10).
- **Decisión 12 (web, contrato que el client recibe):** `ClientBaseProps.codeLanguage: CodeLanguage` (genérico, lo usan Big O y Bug Hunt; los demás lo ignoran) = `session.preferred_code_language ?? 'js'`. El `Game` arranca en ese lenguaje; cambiar de pestaña es estado local y no hace requests ni persiste nada (CA 3). La opción seleccionada es estado local que sobrevive al cambio de pestaña y de idioma (`keepPreviousData` ya conserva el `Game` montado) y se pierde al salir (CA 8). El `Result` muestra el código en `result.code_language` (pestañas también disponibles) y recibe `publicView.code` (`ResultProps.publicView` ya existe).
- **Decisión 15 (alcance):** sin cambios en rutas, rachas, publicación, anulación, reportes (el link aparece por el host) ni pantallas del admin (solo la línea del registry de `Preview`).

### Flow Context

#### `abrir-y-retomar-juego` (paso 3, extracto)

```
alt challenge_status = none → "sin desafío hoy"          (web; el client no se monta)
else challenge_status = voided → aviso de anulación      (web)
else play = null → instrucciones → POST …/start           (client: Instructions → onStart)
else play.status = in_progress → retoma con play.state    (client: Game con state = {})
else play terminada → pantalla de resultado con result    (client: Result)
```

> **Acción:** en Big O y Bug Hunt, `public_view.code` trae `js`, `go` y `java`. Cambiar de lenguaje no hace ningún request ni altera la Play (invariante 17). El lenguaje inicial es `players.preferred_code_language`.

Story, Flujo de Interacción (pasos que hace `web`):
1. **[web - GameRoute]** `GET .../today` → instrucciones → `start`.
2. **[web - Game]** código en `session.preferred_code_language ?? 'js'`; pestañas y selección son estado local.
3. **[web - useSubmitMove]** `POST .../move` → copia `play.code_language` a la cache y actualiza la preferencia de sesión; muestra `Result`.

#### `jugada-y-cierre-de-partida` (extracto aplicable)

- big-o: move `{ "language": "js" | "go" | "java", "option": big_o_option }`; la jugada cierra (`feedback = null`).
- `plays`: `status = win ? 'won' : 'lost'`, `result`, `score`, `code_language` (= `move.language` en big-o / bug-hunt; si no, null), `finished_at = now()`.
- `players` — UPDATE `preferred_code_language = codeLanguage(state)` (solo cuando no es null: big-o y bug-hunt).
- Estado final: Play `won` o `lost` con `result`, `score`, `finished_at` y `code_language`; Player `preferred_code_language` actualizado.

#### `preferencias-y-share` (extracto aplicable)

- Paso 3 (solo cliente): `text = share(result, number)` del `client` del juego. ### Decisiones de este plan

- **D1 — `codeLanguage` se resuelve en `GameScreens`.** `GameScreens` llama a `useSession()` y calcula `const codeLanguage = preferred_code_language ?? DEFAULT_CODE_LANGUAGE` con `DEFAULT_CODE_LANGUAGE: CodeLanguage = 'js'` (constante del módulo `game-host`, junto a `GameScreens`). Lo pasa a `Instructions`, `Game` y `Result` (prop genérica de `ClientBaseProps`: Big O y Bug Hunt la usan, los demás la ignoran; no es lógica por juego). En `types.ts` la prop es **requerida** (`codeLanguage: CodeLanguage`): el host siempre la manda, y los clients que la declaran opcional o no la declaran siguen siendo asignables. `GameScreensProps` no cambia (GameRoute no se toca para esto).
- **D2 — La preferencia en cache se escribe desde el módulo `session`.** `SessionContextValue` suma `rememberCodeLanguage: (language: CodeLanguage) => void`, implementado en `SessionProvider` con `useCallback` sobre `queryClient.setQueryData<SessionResponse>(sessionKeys.all, (old) => old && { ...old, preferred_code_language: language })`. Así `game-host` no importa internals de `session` (`sessionKeys` sigue privado) y la cache de sesión sigue siendo la única fuente (`preferred_code_language` del contexto se deriva de ella). **Sin `PATCH /api/me/preferences`:** la `api` ya guardó la preferencia en la transacción del cierre (ADR-006). Si no hay datos de sesión (`old` undefined), es un no-op.
- **D3 — `MoveResponse.play` es `PlayView`.** `game-today.ts`: `MoveResponse.play: PlayView` (con `code_language`), y `PlayView.code_language: CodeLanguage | null` (tipo de `@nerdose/core` en lugar del literal). `useSubmitMove.onSuccess` escribe `play: res.play` en la cache de `GameToday` (ya no conserva `old.play?.code_language`) y, si `res.play.code_language !== null`, llama a `rememberCodeLanguage(res.play.code_language)`. Se escribe en la cache del locale activo (`gameTodayKeys.detail(gameId, locale)`), como hoy. Los fixtures `MoveResponse` existentes suman `code_language: null` a `play` (los de Devdle, Grep Grid y Timeline cierran con `null`).
- **D4 — Shiki no se menciona en `web`, ni siquiera en tests.** Como dnd-kit (TS-2 de `game-host-boundaries`): ningún archivo de `src/` contiene `'shiki'`. Los tests de ruta no lo mockean: el texto del `tabpanel` es el mismo con o sin resaltado, así que las aserciones de código usan `toHaveTextContent` sobre el `tabpanel` (nunca `getByText` de una línea, que con tokens queda partida en `<span>`s). La carga perezosa se prueba por build (TS-37).
- **D5 — Big O deja de ser el «juego sin client» de los tests.** Los tests de juego sin client pasan a `bug-hunt` (registry, `loadGameClient`, `routes/game.test.tsx` TS-30 y TS-53). El texto esperado pasa a «Hoy no hay desafío de Bug Hunt. Es un día neutro: no suma ni corta tu racha.» y el crumb a `bug-hunt`.
- **D6 — El reporte no manda `code_language`.** `ReportRequest.code_language` es opcional y la `api` lo ignora (toma `play?.codeLanguage`); `web` no conoce la pestaña visible (estado del client) y la story no lo pide (decisión 15: reportes sin cambios). Queda como observación O1.
- **D7 — 320 px, contraste y layout real no se verifican en jsdom.** jsdom no calcula layout ni `color-contrast` (precedente: TS-53/TS-42 de Devdle y Timeline). Se cubren con: guardas estáticas existentes (TS-54 del módulo `game-host`), guarda de build de CSS (TS-36), los tests del paquete (`client-styles.test.ts`, `contrast.test.ts`, Completed) y **verificación manual** a 320 px y 1200 px (TS-38). Playwright sigue siendo deuda D3.
- **D8 — Una sola build de Vite para las guardas.** `src/styles.test.ts` ya hace `vite.build({ build: { write: false } })` (60 s de timeout). Las guardas de CSS de Big O y de chunks de Shiki reutilizan **esa misma salida** (extraer `buildWeb()` memoizado a `src/test/vite-build.ts`, o un `beforeAll` compartido en `styles.test.ts`), para no duplicar el tiempo de la suite.
