# Story Plan: S-054 (admin) - Admin: sección Métricas

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-054](../stories/S-054.admin-seccion-metricas.md)
- **Servicio:** admin
- **Resumen:** Implementa el módulo `metrics` del admin (`/metrics`, P-05): rango de fechas en la URL (por defecto los últimos 30 días UTC), validación con `validateMetricsRange` de `@nerdose/core` antes de consultar, `GET /api/admin/metrics` con TanStack Query, cuatro cifras resumen y cuatro tablas HTML con `dataTableClass` de `@nerdose/ui` (jugadores diarios con días vacíos en 0, retención por cohorte, distribución de rachas vivas con su nota, calidad por desafío ordenable con `aria-sort`), estados de carga, vacío, error de validación, 422 del servidor, error de sistema con «Reintentar» y 401; suma el ítem «Métricas» al shell y deja una guarda estática de que el admin no importa analítica.

> **Alcance de este plan:** solo `apps/admin` (más `docs/reusable-code/admin/`). Queda **fuera**:
> - **`api`** (S-053, **Completed**): `GET /api/admin/metrics` ya existe con la respuesta `Metrics` (`summary`, 5 tramos fijos, `status` published|voided) y valida el rango con su reloj (422 `validation_error`).

> - **`db`** (S-052, **Completed**): vistas `metrics_*`. El admin no toca la base.
> - **Auditoría axe con Playwright** (S-059): fuera de esta story. Acá solo `vitest-axe` en jsdom.
> - **DS `admin`**: sin cambios (catálogo vacío; gaps aceptados, ver DS Context).
>
> **Rutas:** las de «Archivos a crear/modificar» son relativas a `apps/admin/`, salvo las que empiezan con `docs/` o se marcan `(raíz)`.
>
> **Dependencias:** S-053 (prerequisito) está **Completed** (commit `9a175a9`, merge `42d3926`). Todos los tests usan MSW; la verificación manual usa la `api` real.

### Convenciones activas (todas custom, `docs/architectures/admin/conventions/`; partes aplicables, verbatim)

**`_base`:**
- Estructura: `src/modules/{module}/` con `routes/` («route components (lazy-loaded entry points)»), `components/` («components used only by this module»), `api/` («query/mutation hooks + query keys of the module») e `index.ts` («public surface of the module»). `src/components/`: «app-wide reusable components (not in @nerdose/ui)». `src/lib/`: «no JSX. Clients, validated env, pure helpers».
- «A module never imports from another module's internals; it uses that module's `index.ts` or goes through `lib/` or a shared package.»
- «API payload types come from the shared packages (`@nerdose/core`, `@nerdose/game-<game_id>`); do not redeclare them locally.» (Para `Metrics` no hay tipo compartido: se declara en `api/` espejando `api.yaml`, como permite `data-fetching`.)
- Naming: archivos `kebab-case`; componentes `PascalCase`; hooks `use-*` → `useX`; «Query keys | factory per module»; constantes `SCREAMING_SNAKE_CASE`; «API fields | `snake_case`, exactly as the API».
- Imports: «Absolute imports via `@/*`. No `../../../`.» Orden: externos y `@nerdose/*`, luego `@/`, luego relativos; `import type` para tipos.
- Fechas: «At system boundaries (HTTP, logs) dates are ISO 8601 UTC; day dates are `YYYY-MM-DD`.» · «The client **never decides what "today" is**: the day and challenge number come from the `api`.» → **Excepción decidida en REQ-011** (escenario «el Responsable consulta Métricas»): «por defecto `to` = hoy UTC del navegador y `from` = `to − 29`»; la `api` revalida con su reloj y responde 422 si el navegador va adelantado (riesgo documentado).
- «Format dates for display with `Intl.DateTimeFormat` using the active locale. Never assume the browser timezone equals UTC.»
- «Default: no comments. […] Comment only the why when it is not obvious.»

**`routing`:**
- Tabla de rutas: «`/metrics` | `metrics` | protected | Metrics as HTML tables».
- Configuración: «`{ path: 'metrics', lazy: () => import('@/modules/metrics/routes/metrics') },`».
- «`metrics`, `reports` and `content` do not import any game code.»
- «Use `<Link>` / `useNavigate`. On route change, move focus to the page `<h1>` and update `document.title`.»
- Reglas: «All routes are declared in `src/app/router.tsx`.» · «Every route except `/login` sits under `RequireAuth`; never rely on hiding links.» · «The nav links and labels are in Spanish» · «Route components are thin; logic lives in module hooks.» · «Each route sets a meaningful `document.title` and moves focus on navigation.»

**`auth`:**

- «Logout and expiry both leave no admin data in the Query cache.»

Never copy query results into `useState` or a context.» · «Do not convert keys to `camelCase` and do not rename API fields; types use the API names.» · «URLs are relative (`/api/...`).» · «Query keys come from per-module factories, never inline string literals repeated across files.» · «Branch on `ApiError.code`, never on `message` text or on the HTTP status alone.»

### ADRs Relevantes

**ADR-014 — Métricas y analítica.** Decisión: «Métricas de producto desde PostgreSQL: cuatro vistas […] que se leen con `GET /api/admin/metrics?from&to` y se muestran en la sección Métricas del admin como tablas HTML» · «Sin analítica web en v1: ni `web` ni `admin` cargan scripts de analítica de terceros ni registran eventos de uso.» Reglas de implementación (verbatim):
- Las vistas MUST llamarse exactamente `metrics_daily_players`, `metrics_retention`, `metrics_streak_distribution` y `metrics_challenge_quality`, y MUST definirse en migraciones de `@nerdose/db`.
- El rol `nerdose_api` MUST tener solo `SELECT` sobre las vistas `metrics_*`.
- En `metrics_challenge_quality`, `completion_rate = finished / started` y `win_rate = won / finished`. Ambas MUST ser `null` si el divisor es 0.
- Las Play `voided` MUST NOT contar en `finished` ni en `win_rate`.
- El admin MUST mostrar las métricas como tablas HTML. MUST NOT agregarse librería de gráficos en v1.
- `web` y `admin` MUST NOT cargar scripts de analítica ni de tracking de terceros, ni enviar eventos de uso. Sumar analítica requiere un ADR nuevo.
- **Nota de implementación (REQ-011):** las vistas no dependen de "hoy". `metrics_retention` expone conteos (`d1_players`, `d7_players`) y `metrics_streak_distribution` el tramo de la racha guardada con `last_active_date`; la `api` completa `d1`/`d7` y la racha viva con su reloj y con `isStreakAlive` de core (ADR-011), para no duplicar la regla en SQL y poder probarla con relojes falsos.

**ADR-010 — Autenticación del admin** (reglas aplicables, verbatim):
- Todas las rutas `/api/admin/*`, salvo `POST /api/admin/login` y `GET /api/admin/health`, MUST exigir `Authorization: Bearer <jwt>` válido. Si falta, es inválido o venció, MUST responder `401` con `{ "error": { "code": "unauthorized", … } }`.
- El admin MUST guardar el token en `sessionStorage` (nunca en `localStorage` ni en una cookie) y, ante un `401`, MUST borrarlo y volver al login.
- Las rutas `/api/admin/*` MUST NOT leer ni emitir la cookie `nd_pid`.

**ADR-015 — Contratos JSON y errores** (reglas aplicables, verbatim):
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
- Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; […]).

**ADR-002 — Stack tecnológico** (reglas aplicables, verbatim): «`web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.» · «Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.» · «Los tests MUST usar Vitest; los e2e, Playwright.» (e2e no adoptado: deuda D3.) La regla de i18next no aplica al admin (UI solo en español, overview).

**ADR-008 — Día de la plataforma** (aplicable): «`today` MUST calcularse siempre en el servidor con la función de `@nerdose/core` (día UTC). MUST NOT aceptarse una fecha del cliente en ninguna ruta de jugador.» → Métricas es ruta de admin; el rango sí es del cliente y la `api` lo valida con su reloj.

### Decisiones de diseño de REQ-011 aplicables (verbatim)

- **Decisión 3:** «`metrics_challenge_quality` lista desafíos `published` o `voided` […]. El admin muestra «publicado» / «anulado».»
- **Decisión 4:** «Cifras resumen de Métricas = nuevo objeto `summary` en la respuesta. […] D1/D7 del resumen = promedio ponderado por `cohort_size` de las cohortes con valor no nulo (`null` si no hay ninguna).»
- **Decisión 5:** «Validación de rango compartida en core. `validateMetricsRange(from, to, today)` (isomorfa) devuelve `ok` o el motivo (`from_after_to`, `future`, `too_long`): `from <= to`, `to <= today`, `to − from <= 365` días (366 días inclusive). La `api` la usa en el schema Zod de la query (422 `validation_error`) y el `admin` la usa antes de consultar (CA 20: no se muestran datos). Una sola regla, sin duplicar.»
- **Escenario «el Responsable consulta Métricas» — admin:** «`RequireAuth` (sin token → `/login`, CA 21). Rango en la URL (`/metrics?from=YYYY-MM-DD&to=YYYY-MM-DD`); por defecto `to` = hoy UTC del navegador y `from` = `to − 29`. `validateMetricsRange(from, to, todayUtc)` de core: si falla, muestra la alerta de rango y **no** consulta (CA 20). `GET /api/admin/metrics?from&to` con `Authorization: Bearer <JWT>`.» · «Cuatro cifras resumen y tablas HTML (`dataTableClass` de `@nerdose/ui`): jugadores diarios (fecha × total + 5 juegos), retención por cohorte, distribución de rachas (con nota "racha viva a hoy, no depende del rango"), calidad por desafío (ordenable por columna con `<button>` en `<th>` y `aria-sort`, estado local). Porcentajes con un decimal (`Intl.NumberFormat('es', { style: 'percent', maximumFractionDigits: 1, minimumFractionDigits: 1 })`), `—` si `null`. Estado del desafío con texto («publicado», «anulado»).» · «Rango sin filas → «sin datos en el rango» en cada tabla vacía (CA 19).»
- **Manejo de errores (verbatim):** «`401` → se borra el token y vuelve al login (convención `auth`).» · «`422 validation_error` (rango que pasó la validación del navegador, por ejemplo por reloj desfasado) → alerta de rango con el `message` del servidor.» · «5xx/red → alerta de sistema con «Reintentar» (P-05: `alerta-sistema`, `btn-reintentar`).»
- **Riesgo:** «el reloj del navegador del admin va adelantado y el rango por defecto incluye "mañana". **Mitigación:** la `api` valida con su reloj y responde 422; el admin muestra el `message`.»
- **Revisión UX — P-05:** «la tabla de jugadores diarios muestra los días sin partidas en 0 (el cliente completa el rango). Si todo el rango está vacío, muestra «Sin datos en el rango.».»
- **Seguridad:** «Las métricas son agregadas: ninguna columna expone `player_id`».

### API Context (de `docs/apis/api.yaml`; sin cambios de API en esta story)

**`GET /api/admin/metrics`** (`operationId: getMetrics`, `security: adminBearer`). Descripción (verbatim): «F11, C-46, ADR-014. Lee las vistas `metrics_*` en el rango `[from, to]`. Devuelve 422 `validation_error` si `from > to`, `to` es posterior a hoy (día UTC de la plataforma) o `to − from > 365` días. `d1`/`d7` y los tramos de `streak_distribution` se calculan en la api con su reloj y con core (REQ-011).»

- Query (ambos `required: true`): `from` (`string`, `format: date`), `to` (`string`, `format: date`).
- `200` → `Metrics`; `401` → `Unauthorized`; `422` → `ValidationError`.
- Auth: `adminBearer` — «JWT HS256 de 8 h obtenido en `POST /api/admin/login` (ADR-010). Claims `{ sub: "admin", iat, exp }`.» Lo agrega `registerApiHooks` (`Authorization: Bearer <token>`).

**Schema `Metrics`** (verbatim):

```yaml
Metrics:
  type: object
  required: [summary, daily_players, retention, streak_distribution, challenge_quality]
  properties:
    summary:

        d7: { type: number, nullable: true }
    daily_players:
      type: array
      description: metrics_daily_players
      items:
        type: object
        required: [date, game_id, players]
        properties:
          date: { type: string, format: date }
          game_id:
            allOf: [ { $ref: '#/components/schemas/GameId' } ]
            nullable: true
            description: null = total
          players: { type: integer }
    retention:
      type: array
      description: metrics_retention
      items:
        type: object

    streak_distribution:
      type: array
      description: 'metrics_streak_distribution; siempre los 5 tramos, en ese orden, aunque tengan 0; cuenta la racha viva a hoy'
      items:
        type: object
        required: [bucket, players]

    challenge_quality:

```

- `GameId`: `enum: [devdle, bug-hunt, big-o, timeline, grep-grid]` (en `@nerdose/core`: `GAME_IDS = ['devdle', 'grep-grid', 'timeline', 'big-o', 'bug-hunt'] as const`, orden del catálogo).
- `ChallengeStatus`: `enum: [draft, approved, published, rejected, voided]` (en la práctica, `published | voided`, Decisión 3).
- Orden de las listas que devuelve la `api` (S-053): `daily_players` `ORDER BY date, game_id NULLS FIRST`; `retention` `ORDER BY cohort_date`; `streak_distribution` siempre los 5 tramos en orden `'0','1','2-6','7-29','30+'`; `challenge_quality` `ORDER BY date DESC, game_id`. **El admin no depende de ese orden**: ordena él (D5).

**Errores** (shape `{ error: { code, message } }`):
- `401` `Unauthorized`: `example: { error: { code: unauthorized, message: 'Sesión vencida' } }`.
- `422` `ValidationError`: `example: { error: { code: validation_error, message: 'Datos inválidos' } }`.

```ts
/** UTC calendar day of `now` as `YYYY-MM-DD`. */
export function today(now: Date): string {
  return now.toISOString().slice(0, 10);
}

export type MetricsRangeReason = 'from_after_to' | 'future' | 'too_long';
export type MetricsRangeResult = 'ok' | MetricsRangeReason;

/** Admin metrics range: `from <= to`, `to <= today`, at most 366 days inclusive. Inputs must be valid `YYYY-MM-DD`. */
export function validateMetricsRange(from: string, to: string, today: string): MetricsRangeResult {
  if (from > to) return 'from_after_to';
  if (to > today) return 'future';
  const days =
    (Date.parse(`${to}T00:00:00.000Z`) - Date.parse(`${from}T00:00:00.000Z`)) / MS_PER_DAY;
  return days > 365 ? 'too_long' : 'ok';
}
```

### Decisiones de este plan (derivadas, sin inventar contrato)

- **D1 — Rango: URL como fuente de verdad, borrador local en el formulario.** `useSearchParams()` da el rango consultado (`from`, `to`). `readRange(params, now)`: sin `from` **ni** `to` → `defaultRange(now)` (`to = today(now)`, `from = to − 29 días`, ambos UTC con `today` de core) **sin escribir la URL**; con al menos uno, cada parámetro que no sea un `YYYY-MM-DD` válido (regex `^\d{4}-\d{2}-\d{2}$` y fecha real) se lee como `''`. El formulario (`RangeForm`) guarda el borrador (`useState`) inicializado desde la URL y se remonta con `key={`${from}|${to}`}` cuando la URL cambia (volver atrás) — así no hay `useEffect` de sincronización. «Consultar» con borrador válido hace `setSearchParams({ from, to })` (entrada nueva en el historial); con el mismo rango que la URL, llama `refetch()` («todas las cifras y tablas se actualizan juntas»).
- **D2 — Validación: `validateMetricsRange` de core, más el caso «vacío» antes de llamarla.** `rangeCheck(from, to, todayUtc)` → `null` o `{ message, invalid: ('from' | 'to')[] }`: vacío → «Elegí las dos fechas del rango.» con `invalid` = los campos vacíos; `from_after_to` → «La fecha inicial no puede ser posterior a la final.», `['from', 'to']`; `future` → «El rango no puede incluir fechas futuras. Hoy es {dd/mm/aaaa} (UTC).», `['to']`; `too_long` → «El rango no puede superar los 366 días.», `['from']` (es el campo que se movió para extender; el screen.md solo fija «los dos si `from` > `to`»). `todayUtc = today(new Date())` en cada render. El rango no se revalida con otra regla propia (Decisión 5: una sola regla).
- **D3 — `TableRegion` pasa a `src/components/table-region.tsx`.** Se mueve sin cambios y `content-stock` (`bank-panel.tsx`, `bank-rejections-panel.tsx`, `top-rejected-panel.tsx`) la importa desde `@/components/table-region`. Evita que `metrics` importe internos de `content-stock`.
- **D4 — Estados y precedencia (un solo bloque `avisos`).** En orden: (1) **borrador inválido** (incluye URL inválida, porque el borrador nace de la URL) → `alerta-rango` con el motivo, campos con `error`, «Consultar» `aria-disabled`, **sin** cifras ni tablas, y la query deshabilitada (`enabled: false`) si el rango de la URL es inválido; (2) **query pendiente** → `<p role="status">Consultando métricas…</p>`, «Consultando…» `aria-disabled`, sin cifras ni tablas; (3) **error `validation_error`** → `Alert` (`alerta-rango`) con `ApiError.message` del servidor, sin «Reintentar», sin cifras; (4) **otro error** (5xx, red, `internal_error`) → `Alert title="No pudimos cargar las métricas. Probá de nuevo."` con `<button>` «Reintentar» (`refetch()`), sin cifras viejas; (5) **datos** → cifras + 4 tablas (con «Sin datos en el rango.» donde corresponda). `401 unauthorized` lo maneja el hook global (borra sesión y caché; `RequireAuth` redirige a `/login`); el módulo no lo distingue. Con borrador válido pero distinto de la URL se siguen mostrando los datos de la URL hasta «Consultar».
- **D5 — Modelo puro en `metrics-model.ts`** (sin JSX):
  - `formatPercent(v: number | null): string` → `Intl.NumberFormat('es', { style: 'percent', minimumFractionDigits: 1, maximumFractionDigits: 1 })`; `null` → `'—'`. Salida real de Node/jsdom: `0.9666…` → `'96,7 %'` (espacio duro U+00A0 antes de `%`).
  - `dailyRows(daily, from, to)` → `[]` si `daily.length === 0`; si no, una fila por día de `[from, to]` en orden descendente: `{ date, total, games: Record<GameId, number> }`, con 0 donde no hay fila (`game_id: null` → `total`). Columnas de juego en `GAME_IDS`.
  - `retentionRows(retention)` → copia ordenada por `cohort_date` descendente.
  - `STREAK_LABELS = { '0': '0', '1': '1', '2-6': '2–6', '7-29': '7–29', '30+': '30+' }` (raya «–» U+2013 como en el screen.md); `streakRows(dist)` → `{ label, players, share }` en el orden de la respuesta, con `share = formatPercent(players / suma)` y `'—'` si la suma es 0.
  - `QUALITY_COLUMNS` (8, en orden: `challenge` «Desafío», `game` «Juego», `started` «Iniciadas», `finished` «Terminadas», `completion_rate` «Completado», `win_rate` «Victorias», `reports` «Reportes», `status` «Estado»); `type QualitySort = { key: QualityKey; dir: 'ascending' | 'descending' }`; `DEFAULT_QUALITY_SORT = { key: 'challenge', dir: 'descending' }`; `nextSort(current, key)` → misma columna invierte el sentido; columna nueva arranca `ascending`; `sortQuality(rows, sort)`: `challenge` compara `date` (y luego `number`), `game` compara `GAME_LABELS` con `localeCompare('es')`, `status` compara la etiqueta, el resto numérico; **`null` siempre al final** en ambos sentidos; desempate estable por `date` desc y luego orden de `GAME_IDS`. No muta el array de la query.
  - `challengeCell(row)` → `` `#${number} · ${formatDayShort(date)}` `` (ej. `'#8 · 03/12'`).
