## Status

## Referencia de la Story

- **Story:** [S-051](../stories/S-051.web-admin-bug-hunt-jugable-y-preview.md)
- **Servicio:** web
- **Resumen:** Monta el client de Bug Hunt (`@nerdose/game-bug-hunt/client`, ya implementado por el plan `games` de esta story) en `apps/web`: suma la dependencia de workspace y la línea `'bug-hunt'` al `clientRegistry` (con eso los 5 juegos tienen client), cambia el contrato estructural del host a `GameClient.share(result, number, locale)` y hace que el botón de compartir del header pase el idioma activo de la sesión (el share de Bug Hunt es el único con texto: «bug encontrado» / «se me escapó», «bug found» / «it got away»). Bug Hunt deja de ser el «juego sin client» de los tests. Cubre con tests de ruta jsdom (instrucciones → partida → resultado, cambio de lenguaje sin requests conservando la línea, líneas no elegibles, ES/EN, confirmación y caches, retomar sin selección, share en el idioma activo, errores, teclado y axe) y extiende las guardas de build (CSS del client y Shiki/chunk de Bug Hunt fuera del chunk de entrada).

> **Alcance de este plan:** solo el servicio `web` (`apps/web/`, más los docs de `docs/reusable-code/web/`, `docs/architectures/web/`, el ítem de `web` en la entrada 1.11.0 de `docs/design-system/web/CHANGELOG.md` y el paso 3 de `docs/flows/preferencias-y-share.md`). Queda **fuera**:
> - **`games`**: la entrada `./client` de Bug Hunt (`Instructions`, `Game`, `Result`, `share(result, number, locale)`, `Preview`, `i18n`, `HELP_TARGET_ID`, Shiki con fallback). Ya está **Completed** (`docs/story-plans/S-051.games.web-admin-bug-hunt-jugable-y-preview.md`). Si un test de ruta revela un defecto del client, se reporta; `web` no lo parchea.
> - **`admin`**: la línea de `bug-hunt` en el registry de `Preview` (CA-7) y `docs/architectures/admin/conventions/game-clients.md`. Tiene su propio plan.
> - **`api`**: sin cambios. `GET …/today`, `POST …/start` y `POST …/move` de Bug Hunt ya funcionan (S-048, registry de la `api` con `bugHunt`).
> - **Sin cambios de lógica de sesión/caches:** `useSubmitMove` ya copia `res.play` completo (con `code_language`) a la cache de `GameToday` y llama a `rememberCodeLanguage` cuando no es `null` (genérico desde S-046). `GameScreens` ya resuelve `codeLanguage = preferred_code_language ?? 'js'`.
>
> **Rutas:** las de «Archivos a crear/modificar» son relativas a `apps/web/`, salvo las que empiezan con `docs/` (raíz del repo).

### Convenciones activas (extractos aplicables, verbatim)

#### `game-clients`
- `GameClient` is the shape of the `./client` entry defined by the game contract: React components `Instructions`, `Game`, `Result` and `share(result, number): string`. *(este plan lo pasa a `share(result, number, locale)`)*
- `share(result, number)` produces the text. The shell calls `navigator.share({ text })` when available and falls back to `navigator.clipboard.writeText`, with a visible confirmation message. After sharing it calls `track('share:<game_id>')` (see `analytics`).
- The registry is the only place that lists games. No `if (gameId === ...)` or `switch` by game anywhere in `apps/*`.
- Each game is loaded with a dynamic `import()` so it is its own chunk.
- The shell renders games only through `Instructions`, `Game`, `Result` and `share`; it does not read game-specific fields.
- The `client` never receives the solution before the round ends in `web`; the app never requests or caches anything beyond the public view and the move responses.
- Share text is never built by the shell; it always comes from the game's `share()`.
- Validate every move with the game's `moveSchema` before sending, and still handle `422 invalid_move` from the `api`.
- Adding a game must require only a new package, a registry line and its translations.
- Shiki (big-o, bug-hunt) and dnd-kit (timeline) are dependencies of the game packages and are loaded in the game's own chunk. The shell never imports them.
- **Update (REQ-009):** `ClientBaseProps.codeLanguage: CodeLanguage` is generic (no per-game branch): the host resolves it as `session.preferred_code_language ?? 'js'` and the client reads it when it mounts (Big O, Bug Hunt); the other clients ignore it. `web` writes `MoveResponse.play.code_language` into the `GameToday` cache and, when not null, into the session cache through `rememberCodeLanguage` (no `PATCH`). Shiki never appears in `apps/web` (not even in tests); a build guard checks it stays out of the entry chunk.

#### `data-fetching`
- Server data lives in TanStack Query. Never copy query results into `useState` or a context.
- Do not convert keys to `camelCase` and do not rename API fields; types use the API names.
- Mutations of a game round include `challenge_number`; the client never sends a date.
- Branch on `ApiError.code`, never on `message` text or on the HTTP status alone.

#### `state-management`
- In-progress game interaction that the game owns (selection, drag order) → State inside the game's `client`.
- App-wide, rarely changing and needed far from its source (locale, session status) → A React context, in `app/`.
- Never store the solution, game state of an unfinished round, or tokens in `localStorage`. `useEffect` is not used to sync one piece of state into another.

#### `_base`
- A module never imports from another module's internals; it uses that module's `index.ts` or goes through `lib/` or a shared package.
- From a game package, only the `./client` entry may be imported. Never `./definition` or `./generator`. Never import `@nerdose/db`, `@nerdose/polyglot` or `@nerdose/content`.
- Naming: archivos `kebab-case`, hooks `use-*`, constantes `SCREAMING_SNAKE_CASE`, campos de API en `snake_case` exactos. `import type` para tipos. Sin comentarios salvo el porqué.

#### `routing`
- A game's code is loaded only when its route (or its preview of instructions) is opened; the home never imports a game's `client` entry.
- No per-game `if`/`switch` in the router or the shell; the registry decides. Each route sets a meaningful `document.title` and moves focus on navigation.

#### `i18n`
- Never translate or choose a language for content that comes from the `api`; render it as received. Game packages ship their own UI strings through the same i18n instance (a namespace per game).
- Changing language updates `<html lang>` and refetches content queries.

#### `error-handling` (tabla de recuperación, filas aplicables)
| `code` | Recovery in `web` |
|---|---|
| `challenge_expired` | Invalidate `today` and the game query and reload the challenge; show a short "new challenge" notice |
| `challenge_voided` | Refetch; the game view switches to the voided state and offers `acknowledge-void` |
| `game_finished` | Refetch the play state and show the result |
| `no_session` | Call `POST /api/session` once and retry; if still without session, show the blocked-cookies notice and disable play |
| `invalid_move`, `validation_error`, `invalid_report` | Inline message on the control; no navigation |
| `rate_limited` | Message with the `Retry-After` wait; disable the action until then |

#### `accessibility`
- Each of the 5 games can be completed with the keyboard alone (NFR-U03). Color is never the only carrier of meaning. Dynamic updates are announced via live regions. axe-core reports zero violations in unit checks and e2e page checks. Touch targets ≥ 44 × 44 px; layout reflows at 320 px without horizontal scroll.

#### `testing-unit`
- Query by role, label or visible text. Use `userEvent`, not `fireEvent`. Each interactive component has an axe check. Fixtures use the API's `snake_case` names. Mock the network with MSW, never the app's own modules. Tests do not rely on the real date or timers. No snapshot tests of large DOM trees.

#### `styling`
- Use only the tokens. No literal hex colors, no arbitrary `[#abc]` color values in components. Tokens live only in `packages/ui`; `web` and `admin` must not redeclare them. Mobile-first from 320 px. (Guarda del módulo `game-host`, TS-54 vigente: sin hex, arbitrarios, utilidades genéricas ni prefijos responsive en sus `.tsx`.)

#### `analytics`
- The only custom event is `share:<game_id>`, with no custom properties. Share events are fired by the share button after `navigator.share` or the clipboard copy succeeds.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

#### ADR-003: Monorepo (reglas aplicables)
- `apps/web` y `apps/admin` MUST importar solo `./client`.
- `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.

#### ADR-006: Contrato `GameDefinition` (reglas aplicables, verbatim)
- Bloque `// entrada ./client`: «Instructions, Game, Result (componentes React) y share(result, number, locale): string».
- `share(result, number, locale)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
- Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
- `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
- `Preview` MUST ser de solo lectura … `web` MUST NOT montarla.
- Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.

#### ADR-015: Contratos JSON y errores (reglas aplicables)
- Todas las propiedades JSON MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Los enums MUST serializarse con sus valores exactos del dominio (`code_language`: `js | go | java`; `locale`: `es | en`).

#### ADR-014: Métricas y analítica
- `track('share:<game_id>')` lo llama el host (`web`) después de compartir; el client no importa `track`.

### Flow Context

#### `abrir-y-retomar-juego` (paso 3, extracto)

```
alt challenge_status = none → "sin desafío hoy"          (web; el client no se monta)
else challenge_status = voided → aviso de anulación      (web)
else play = null → instrucciones → POST …/start           (client: Instructions → onStart)
else play.status = in_progress → retoma con play.state    (client: Game con state = {})
else play terminada → pantalla de resultado con result    (client: Result)
```

> «En Big O y Bug Hunt, `public_view.code` trae `js`, `go` y `java`. El shell le pasa al client del juego `codeLanguage = session.preferred_code_language ?? 'js'` (prop genérica de `ClientBaseProps`; los juegos sin código la ignoran) y el `Game` arranca en ese lenguaje. Cambiar de pestaña es estado local: no hace ningún request, no altera la Play ni persiste la preferencia (invariante 17).»
> «En Bug Hunt la línea seleccionada tampoco se guarda en el servidor: `plays.state` sigue `{}` hasta confirmar; al retomar no hay selección.»
> Vista pública bug-hunt (l. 99): «`{ function_name, spec, code: { js, go, java }, pickable_lines: int[], visible_tests: [{ input, expected }] ×2–3 }` — `spec` va en el locale resuelto; `pickable_lines` va en orden ascendente; `input` es la lista de argumentos de la llamada; `toPublic` ignora `state`. Nunca incluye `bug_line`, `bug_type`, `mutation`, `fix`, `failing_test`, `tests`, `template`, `params` ni `explanation`.»

Story, Flujo de Interacción (pasos que hace `web`):
1. **[web - GameRoute]** `GET .../today` → instrucciones → `start`.
2. **[web - Game]** código en `preferred_code_language`; pestañas y selección son estado local; `moveSchema.parse` antes de `onMove`.
3. **[web - useSubmitMove]** `POST .../move` → muestra `Result` y actualiza la preferencia en cache.

#### `jugada-y-cierre-de-partida` (extracto aplicable)

- bug-hunt: move `{ "language": "js" | "go" | "java", "line": int }`; `line ∉ pickable_lines` → `invalid_move` (`ROLLBACK`, la Play sigue `in_progress`); la jugada válida cierra (`feedback = null`).
- `plays.code_language` = `move.language`; `players.preferred_code_language` actualizado en la misma transacción.
- Play terminada → `409 game_finished`; la web vuelve a pedir `GET …/today` y muestra el resultado. Desafío anulado → `409 challenge_voided`.

#### `preferencias-y-share` (paso 3, extracto; hoy dice `share(result, number)`, ver Tarea 5)

1. `text = share(result, number)` del `client` del juego. Nunca incluye la solución y termina en `nerdose.dev`. *(REQ-010: `share(result, number, locale)`; Bug Hunt `🐛 Bug Hunt #N · <Lenguaje>` / `🟩 bug encontrado` | `🟥 se me escapó` / `nerdose.dev` en el idioma activo)*

3. `track('share:<game_id>')` de `@nerdose/ui`. Es un no-op si `VITE_PLAUSIBLE_DOMAIN` está vacío.

### Decisiones de este plan

- **D1 — `GameClient.share(result, number, locale)` con `locale` requerido en el host.** `types.ts`: `share: (result: unknown, number: number, locale: Locale) => string`. Los 4 clients actuales declaran `share(result, number)` y Bug Hunt `share(result, number, locale = 'es')`: todos siguen siendo asignables (una función con menos parámetros, o con el tercero opcional, es asignable a una que recibe tres). El host siempre lo pasa. El comentario de cabecera de `types.ts` nombra los 5 juegos.
- **D2 — El idioma del share sale de la sesión, en el header.** `ClientShareButton` suma la prop `locale: Locale` y arma `getText={() => client.share(result, number, locale)}`. `GameHostHeader` toma `locale` de `useSession()` (ya llama a `useSession()` para `status`) y lo pasa. El texto se arma al hacer click (`getText`), así que cambiar ES|EN en el resultado y volver a compartir produce el texto en el idioma nuevo sin otra lógica (CA-6). El shell sigue sin componer texto (`game-clients`).
- **D3 — Registry completo, tipo parcial.** Se suma `'bug-hunt': () => import('@nerdose/game-bug-hunt/client')` (orden alfabético como hoy: `big-o`, `bug-hunt`, `devdle`, …). Con esto los 5 `GAME_IDS` tienen client. El tipo sigue `Partial<Record<…>>` y `hasGameClient` / `NoChallengeView` / `deriveGameView({ hasClient: false })` se mantienen (la story pide «una línea en `clientRegistry`», no un refactor; un juego futuro puede registrarse antes que su client). JSDoc: «Los 5 juegos tienen client. Sigue parcial a propósito: un juego nuevo se suma con su paquete (una línea acá + traducciones) y mientras tanto la ruta muestra «sin desafío hoy»».
- **D4 — Ya no hay «juego válido sin client» para los tests de ruta.** Se eliminan: TS-30 de `routes/game.test.tsx`, la primera mitad (`view('/bug-hunt')` + axe) de «TS-53: juego sin client y partida anulada» (queda solo la parte de la partida anulada, renombrada «TS-53: partida anulada»), y `describe('Bug Hunt sin client')` (TS-34) de `routes/big-o.test.tsx`. La rama `noClient` sigue cubierta por `game-view.test.ts` (`hasClient: false → { kind: 'noClient' }`), y la rama de rechazo de `loadGameClient` por un id fuera del registry construido en el test (`'unknown-game' as GameId`, sin `any`). `registry.test.ts` pasa a asertar que **todos** los `GAME_IDS` tienen client.
- **D5 — Shiki no se menciona en `web`, ni siquiera en tests** (vigente desde S-046, TS-3 de `game-host-boundaries`). Los tests de ruta no mockean el resaltador: las aserciones de código usan el `tabpanel` (`toHaveTextContent`) o los nombres accesibles de los radios («Línea 4: …», que el client arma con el texto plano de la línea), nunca `getByText` de una línea elegible resaltada (queda partida en `<span>`s). Las líneas no elegibles en modo `select` se pintan sin Shiki, así que `within(panel).getByText('function maxIndex(nums) {')` es estable para localizar la firma.
- **D6 — Lógica por juego prohibida también para Bug Hunt.** Nuevo test de fronteras: fuera de `test/` y de los `*.test.ts(x)`, `'bug-hunt'` solo aparece en `modules/game-host/registry.ts`, `modules/catalog/games.ts`, `modules/catalog/components/how-it-works.tsx`, `i18n/es.ts`, `i18n/en.ts`; ningún archivo no-test matchea `/chosen_line|bug_line|bug_type|failing_test|pickable_lines|visible_tests|function_name/` (campos de Bug Hunt que el shell no debe leer).
- **D7 — 320 px, contraste y layout real no se verifican en jsdom** (precedente D7 de S-046). Se cubren con: guardas estáticas existentes (TS-54 del módulo `game-host`), guarda de build de CSS (TS-35), los tests del paquete (`client-styles.test.ts`, `contrast.test.ts`, Completed) y **verificación manual** a 320 px y 1200 px (TS-37). Playwright sigue siendo deuda D3.
- **D8 — Fixtures con el desafío de `api.yaml`.** `bug-hunt-today.ts` usa el ejemplo `bug_hunt_en_curso` / `bug_hunt_cierre` (número **128**, fecha `2026-11-03`, `maxIndex`, `bug_line: 4`, `pickable_lines: [2, 3, 4, 5, 8]`) y los textos EN de `packages/games/bug-hunt/src/client/test-fixtures.ts` (copiados, no importados).
