# Story Plan: S-033 (admin) - Admin, login y sección Reportes

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-033](../stories/S-033.admin-login-seccion-reportes.md)
- **Servicio:** admin
- **Resumen:** Convierte el shell vacío de `apps/admin` en el admin operativo del Responsable: login con contraseña única (JWT en `sessionStorage`, bloqueo por `429` con `Retry-After`, `401` global que cierra la sesión), y la sección Reportes (`/reports`) con la cola de grupos por desafío (alertados primero, filtro por estado en la URL, contador en el encabezado), el drawer de detalle (`PayloadView` ES/EN, log de verificación, reportes con Resolver/Descartar) y el modal de anulación con culpable elegido de `culprits` y resumen de consecuencias.

> **Alcance de este plan:** solo `apps/admin`. La fila `ui` de la story («piezas reutilizables derivadas de `@nerdose/ui`…», impacto Bajo) tiene su propio plan si se planifica; este plan **no depende** de él: consume solo lo que `@nerdose/ui` ya exporta hoy y construye las piezas que faltan (diálogo modal/drawer, campos de formulario, pestañas) como componentes **propios de admin** en `src/components/` (ver D4). Si al implementar ya existe un equivalente exportado por `@nerdose/ui` (por el plan `ui` de S-033), se usa ese en lugar del local, sin cambiar los test scenarios.
>
> **Rutas:** todas las rutas de "Archivos a crear/modificar" son relativas a `apps/admin/` salvo que se indique `(raíz)`.
>
> **Dependencias:** S-032 (API del admin: login, reportes, anulación) está **Completed** y mergeada en `dev` (commit `919a0c8`). Todos los tests usan MSW; la verificación manual usa la `api` real.

### Arquitectura del Servicio (`docs/architectures/admin/overview.md`, partes aplicables)

- SPA del responsable de nerdose (`admin.nerdose.dev`). Herramienta interna de un solo usuario, **solo en español** y sin analítica.
- **Módulos (manifest):** `auth`, `reports`, `upcoming`, `content-stock`, `metrics`. Esta story implementa **`auth`** y **`reports`**. `upcoming`, `content-stock` y `metrics` no se tocan (FG-7, FG-10).
- Cliente HTTP de mismo origen (`/api/admin/*`), JSON en `snake_case` sin transformar y errores por `error.code` (ADR-015). En desarrollo el proxy de Vite emula el mismo origen (`/api/admin` → api `:3000`).
- Autenticación: JWT HS256 de 8 h en `sessionStorage`, enviado como `Authorization: Bearer`; ante un `401` se borra el token y se vuelve al login; sin refresh ni multiusuario (ADR-010). Nunca usa la cookie `nd_pid`.
- Contextos de React a nivel app: solo `AuthProvider` además del `QueryClientProvider`.
- **UI solo en español, sin i18n propio.** Los textos del admin se escriben directamente en español. El código de la app no usa `t()`. *(Desvío consciente de ADR-002 «textos por i18next», ya documentado en el overview.)*
- **Preview en modo solución:** pertenece a FG-7. En esta story se reemplaza por `PayloadView` (decisión 12 de REQ-007); **no** se importa ningún `@nerdose/game-*/client` ni se crea el registry de `game-clients`.
- Sin Dockerfile, CI ni despliegue (diferido).

**`auth`**
```ts
// src/modules/auth/token-store.ts
const KEY = 'nerdose_admin_session';
type Session = { token: string; expires_at: string };
export function readSession(): Session | null {
  try {
    const raw = sessionStorage.getItem(KEY);
    const s = raw ? (JSON.parse(raw) as Session) : null;
    return s && new Date(s.expires_at) > new Date() ? s : null;
  } catch { return null; }
}
export const writeSession = (s: Session) => { try { sessionStorage.setItem(KEY, JSON.stringify(s)); } catch {} };
export const clearSession = () => { try { sessionStorage.removeItem(KEY); } catch {} };
```
```ts
configureApi({
  getHeaders: () => { const s = readSession(); return s ? { Authorization: `Bearer ${s.token}` } : {}; },
  onError: (err) => {
    if (err.status === 401 && err.code === 'unauthorized') { clearSession(); queryClient.clear(); router.navigate('/login', { replace: true }); }
  },
});
```
```ts
export function useLogin() {
  return useMutation({
    mutationFn: (password: string) =>
      api<{ token: string; expires_at: string }>('/api/admin/login', { method: 'POST', json: { password } }),
    onSuccess: (s) => writeSession(s),
  });
}
```
- Reglas: token solo en `sessionStorage` (nunca `localStorage`, cookies, store persistido ni URL); solo lo pone `getHeaders`; todo `401 unauthorized` borra token + cache de Query y va a `/login` sin reintentar; `401 invalid_credentials` del login es error de formulario; `rate_limited` muestra la espera de `Retry-After` y deshabilita el envío; sin refresh/«recordarme»/multiusuario; nunca loguear ni mostrar token ni contraseña; `type="password"` + `autocomplete="current-password"`; nunca `nd_pid`; **textos de jugadores como texto plano (nunca `dangerouslySetInnerHTML`)**; logout y vencimiento no dejan datos en la cache.

### ADRs Relevantes

**ADR-010: Autenticación del admin** — Reglas de Implementación (verbatim):
- `ADMIN_PASSWORD_HASH` MUST tener el formato `scrypt$<N>$<r>$<p>$<salt_base64>$<hash_base64>`. La verificación MUST usar `crypto.scrypt` y `crypto.timingSafeEqual`. MUST NOT existir una variable con la contraseña en texto plano.
- El repo MUST incluir un script (`pnpm --filter api admin:hash`) que genere `ADMIN_PASSWORD_HASH` a partir de una contraseña ingresada por stdin.
- El JWT MUST firmarse con `hono/jwt`, algoritmo `HS256` y `ADMIN_JWT_SECRET` (≥ 32 bytes aleatorios). Claims: exactamente `sub: "admin"`, `iat` y `exp = iat + 28800`.
- `POST /api/admin/login` MUST responder `200 { token, expires_at }` (`expires_at` en ISO 8601 UTC) o `401` con `{ "error": { "code": "invalid_credentials", … } }`.
- `POST /api/admin/login` MUST limitarse a 5 intentos cada 15 minutos por IP (`429 rate_limited`).
- Todas las rutas `/api/admin/*`, salvo `POST /api/admin/login` y `GET /api/admin/health`, MUST exigir `Authorization: Bearer <jwt>` válido. Si falta, es inválido o venció, MUST responder `401` con `{ "error": { "code": "unauthorized", … } }`.
- El admin MUST guardar el token en `sessionStorage` (nunca en `localStorage` ni en una cookie) y, ante un `401`, MUST borrarlo y volver al login.
- Las rutas `/api/admin/*` MUST NOT leer ni emitir la cookie `nd_pid`.
- MUST NOT haber refresh tokens ni usuarios múltiples.

**ADR-015: Contratos JSON y errores** — Reglas de Implementación (verbatim):
- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- `message` MUST estar en el locale resuelto de la request. MUST NOT incluir stack traces ni detalles internos.
- El locale MUST resolverse en este orden: query `lang` (`es`|`en`) → `players.locale` → `Accept-Language` → `es`.
- Las respuestas de jugador MUST NOT incluir objetos `{ es, en }`: todo texto de contenido llega ya resuelto como string.
- Las respuestas de `/api/admin/*` que incluyen `payload` MUST devolverlo completo, con los dos idiomas.
- Las fechas de día MUST serializarse como `YYYY-MM-DD` y los instantes como ISO 8601 UTC con `Z`.
- Los enums MUST serializarse con sus valores exactos del dominio (`game_id`: `devdle | bug-hunt | big-o | timeline | grep-grid`; `code_language`: `js | go | java`; `locale`: `es | en`).
- Los errores no previstos MUST loguearse con pino (nivel `error`, con stack) y responder `500 internal_error`.

**ADR-017: Alertas registradas en el admin** — Reglas aplicables (verbatim):
- Las alertas MUST NOT salir del sistema en v1: ningún servicio MUST enviar mails, webhooks ni notificaciones push.
- `GET /api/admin/reports` MUST incluir `alerted_at` por grupo y ordenar primero los grupos con `alerted_at` no nulo.
- Las alertas MUST NOT anular ni despublicar nada.
→ En admin: el contador del encabezado y la etiqueta «alertado» son **el único aviso**; el cliente respeta el orden del servidor (no reordena).

**ADR-002: Stack tecnológico** — Reglas aplicables (verbatim):
- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`. *(Excepción documentada para `admin` en su overview: UI solo en español, sin `t()`.)*
- Los tests MUST usar Vitest; los e2e, Playwright. *(Desvío D3.)*

**ADR-006 (anti-spoiler):** el jugador nunca recibe `payload`; el admin sí, autenticado. El admin muestra la solución completa solo detrás del login.

### API Context (de `docs/apis/api.yaml`; ningún cambio de API en esta story)

**Autenticación:** `adminBearer` — `Authorization: Bearer <JWT>` (HS256, 8 h, claims `{ sub: "admin", iat, exp }`). Todas las rutas `/api/admin/*` salvo `POST /api/admin/login` y `GET /api/admin/health`. Mutaciones `/api/admin/*` exigen `Origin = ADMIN_ORIGIN` (en dev `http://localhost:5174`; el proxy de Vite conserva el `Origin`).

**`POST /api/admin/login`** (`security: []`)
- Body: `{ "password": string (minLength 1) }`
- `200` `AdminLoginResponse` `{ "token": string, "expires_at": string (date-time) }` — ej. `{ token: "eyJhbGciOiJIUzI1NiJ9...", expires_at: "2026-11-03T20:00:00Z" }`
- `401` `{ "error": { "code": "invalid_credentials", "message": "Contraseña incorrecta" } }`
- `415` `unsupported_media_type`, `422` `validation_error`
- `429` `RateLimited`: header `Retry-After` (segundos; la `api` envía `Math.ceil(windowMs / 1000)` = `900`), body `{ "error": { "code": "rate_limited", "message": "Demasiadas solicitudes. Probá de nuevo en un rato" } }`

**`GET /api/admin/reports?status=open|resolved|dismissed`** (default `open`)
- `200` `{ "groups": ReportGroup[] }`; `401 unauthorized`; `422 validation_error`.
```yaml
ReportGroup:   # orden: alerted_at no nulo primero, report_count desc, challenge.date desc; report_count y reasons cuentan solo los del estado filtrado
  required: [challenge, alerted_at, report_count, reasons, reports]
  challenge: AdminChallenge
  alerted_at: string (date-time) | null
  report_count: integer (min 1)
  reasons: { <ReportReason>: integer }       # ej. { wrong_answer: 3, translation: 1 }
  reports: AdminReport[]
AdminChallenge:
  required: [id, game_id, date, number, status, payload, verification, void_reason, voided_at, culprits]
  id: uuid
  game_id: devdle | bug-hunt | big-o | timeline | grep-grid
  date: YYYY-MM-DD
  number: integer (min 1)
  status: draft | approved | published | rejected | voided
  payload: object          # challenges.payload completo: solución y textos { es, en }
  verification: object     # challenges.verification (log de verificación)
  void_reason: string | null
  voided_at: date-time | null
  culprits: [{ kind: term | timeline_fact, id: uuid, label: string }]
AdminReport:
  required: [id, reason, message, locale, context, status, created_at, player_ref]
  id: uuid
  reason: wrong_answer | ambiguous | wrong_explanation | translation | display_bug | other
  message: string | null
  locale: es | en
  context: object          # code_language, play_status, play_state, user_agent

  created_at: date-time
  player_ref: string ^[0-9a-f]{8}$   # primeros 8 hex de sha256(player_id); nunca el id
```
- `verification` real (tipo `VerificationLog` de `@nerdose/core`): `{ ok: boolean, checks: { name: string, ok: boolean, detail?: string }[], reason?: string }`.

**`PATCH /api/admin/reports/{report_id}`** — body `{ "status": "resolved" | "dismissed" }`
- `200` `AdminReport`; `401 unauthorized`; `404` `{ "error": { "code": "not_found", "message": "No encontrado" } }`; `409` `{ "error": { "code": "report_not_open", "message": "El reporte ya fue procesado" } }`; `422 validation_error`.

**`POST /api/admin/challenges/{challenge_id}/void`** — body `VoidRequest`:
```yaml
VoidRequest:
  required: [void_reason, culprit]
  void_reason: string, minLength 1, maxLength 500 (se aplica trim)
  culprit:
    required: [kind]
    kind: term | timeline_fact | template | none
    id: uuid   # obligatorio si kind es term o timeline_fact, prohibido si no; debe estar en AdminChallenge.culprits
```
- Ej.: `{ void_reason: "La respuesta correcta era O(n), no O(n log n)", culprit: { kind: template } }`
- `200` `{ "challenge_id": uuid, "affected_plays": integer ≥ 0 }` — ej. `{ challenge_id: "6a1b2c3d-4e5f-4a6b-8c7d-9e0f1a2b3c4d", affected_plays: 214 }`
- `401 unauthorized`; `404 not_found`; `409` `{ "error": { "code": "not_voidable", "message": "Solo se puede anular un desafío publicado" } }`; `422` `validation_error` (body inválido) o `invalid_culprit` (el culpable no pertenece al desafío).

**`Error`**: `{ "error": { "code", "message" } }`; códigos relevantes: `unauthorized`, `invalid_credentials`, `forbidden_origin`, `not_found`, `not_voidable`, `report_not_open`, `unsupported_media_type`, `invalid_culprit`, `validation_error`, `rate_limited`, `internal_error`. `Unauthorized` ejemplo: `{ error: { code: unauthorized, message: 'Sesión vencida' } }`.

### Flow Context

**`admin-login-y-consultas`** (pasos que esta story implementa del lado `admin`):
1. **Login** — `POST /api/admin/login { "password": "string" }` → `200 { "token", "expires_at" }`. **Acción de admin:** guarda `token` en `sessionStorage` y lo manda como `Authorization: Bearer <token>` en todas las rutas `/api/admin/*`.
2. **Reportes agrupados** — `GET /api/admin/reports?status=open` → `200 { "groups": [ { "challenge": { id, game_id, date, number, status, payload (completo, con solución y {es,en}), verification, void_reason, voided_at, culprits }, "alerted_at", "report_count", "reasons": { "<reason>": int }, "reports": [ { id, reason, message, locale, context, status, created_at, player_ref } ] } ] }`.
3. **Resolver o descartar** — `PATCH /api/admin/reports/{report_id} { "status": "resolved | dismissed" }` → `200 AdminReport`. Sin fila `open` → `409 report_not_open`.
4–5. Stock y métricas: **fuera de esta story** (FG-7 / FG-10).

| Paso | Error | Código | Comportamiento en admin |
|---|---|---|---|
| 1 | Contraseña incorrecta | 401 `invalid_credentials` | muestra el error |
| 1 | 5 intentos en 15 min por IP | 429 `rate_limited` + `Retry-After` | bloquea el formulario hasta `Retry-After` |
| 2–3 | JWT ausente, inválido o vencido (8 h) | 401 `unauthorized` | borra el token y vuelve al login |
| 3 | `report_id` inexistente | 404 `not_found` | refresca la lista |
| 3 | Reporte ya procesado | 409 `report_not_open` | refresca la lista |
| 2, 3 | Query o body inválido | 422 `validation_error` | marca el campo |

**`anulacion-de-desafio`** (paso 1, iniciado por `admin`):
- `POST /api/admin/challenges/{challenge_id}/void` con `Authorization: Bearer <jwt>` y `{ "void_reason": "string — obligatorio", "culprit": { "kind": "term | timeline_fact | template | none", "id": "uuid — obligatorio si kind es term o timeline_fact" } }`. Validaciones: JWT válido → el challenge existe → `status == 'published'` (si no, `409 not_voidable`).
- La `api` anula en una transacción (desafío `voided`, Play `voided`, reportes `open` → `resolved`, ítem culpable → `rejected`, recálculo de agregados) y responde `200 { "challenge_id": "uuid", "affected_plays": "integer" }`.

| 1 | JWT ausente o vencido | 401 | vuelve al login |

**Accesibilidad:** foco campo-motivo → campo-culpable → btn-cancelar → btn-anular; `role="dialog"` + `aria-modal="true"`; el resumen está referenciado por `aria-describedby` del botón destructivo; atrapa el foco; Esc cierra (salvo en loading) y devuelve el foco al disparador; **foco inicial en el motivo**.

**Decisiones:** botón destructivo variante `error` con el resumen justo encima; culpable de una lista (sin `campo-id`); resumen nombra el ítem y avisa de los desafíos ya generados; avisos propios para `not_voidable` e `invalid_culprit`. Descartado: casilla «Entiendo que es irreversible», campo de id.

#### Flujos relevantes (`surfaces/admin/user-flows.md`, flujos 1–3, resumidos sin perder casos)

- **Flujo 1 — Iniciar sesión y retomar tras sesión vencida.** Happy: ruta sin token → P-01 → contraseña → token (8 h) en `sessionStorage` → P-02. Alternativos: `401` durante el uso → borra token, limpia datos, P-01 con «La sesión venció, ingresá de nuevo», luego P-02; Cerrar sesión → borra token en el navegador → P-01; link directo a ruta interna sin token → P-01 → P-02. Errores: contraseña incorrecta (mensaje sin detalle); bloqueo «Demasiados intentos. Probá de nuevo en N minutos.» (no se evalúa la contraseña); vencimiento con O-01 abierto (se pierde el motivo; verificar el estado en P-02 antes de repetir); error de red distinguido de contraseña incorrecta. Final: P-02 con encabezado y token vigente, o P-01 sin token.
- **Flujo 2 — Revisar reportes y anular.** P-02 (alertados primero, filtro `open`) → O-02 (ES/EN, datos, log, reportes con `player_ref`) → «Anular» → O-01 (motivo ≤ 500, culpable de la lista) → resumen → confirmar → P-02 con «Devdle #8 anulado · N partidas afectadas», grupo fuera de abiertos, contador baja. Alternativos: anular desde la fila sin abrir el detalle; culpable `none`/`template`; no anular (flujo 3); revisar resueltos/descartados (sin anular si no está `published`). Errores: no `published` → acción deshabilitada con motivo; `not_voidable` con O-01 abierto → aviso propio; `invalid_culprit` → pedir otro; faltan campos → bloquear y marcar; respuesta fallida (red, 5xx) → informar, **no reenviar solo**; sesión vencida → flujo 1. Criterio: no ejecutar la anulación dos veces por un error de red.
- **Flujo 3 — Resolver o descartar.** En O-02, por reporte: «Descartar» o «Resolver» → `dismissed`/`resolved` sin tocar desafío ni partidas; el drawer sigue abierto; sin reportes abiertos el grupo sale de la cola y el contador baja. Sin acción en bloque. Errores: `report_not_open` → «Este reporte ya estaba cerrado. Actualizamos la lista.» y refresca; falla de red → la fila conserva su estado y se informa el error; sesión vencida → flujo 1.

#### Cross-surface (`cross-surface-flows.md`, flujo 1, partes de admin)

2. **[admin]** El reporte aparece en `/reports`, agrupado por desafío: alertados primero, luego por cantidad y luego por fecha. Si se alcanza el umbral, el grupo queda alertado. No hay mail: la alerta solo existe en el admin, con el contador del encabezado. 3. **[admin]** El responsable abre el detalle (ES y EN, log, motivos, mensajes), confirma el error y anula con motivo y culpable de la lista. Sincronización: manual/bajo demanda; el admin ve el reporte `open` hasta resolverlo, descartarlo o anular; al anular, los abiertos pasan a `resolved`.

### Decisiones de este plan (derivadas, sin inventar contrato)

- **D1 — Sesión como store externo.** `token-store.ts` suma un mini-store (`subscribe(listener)`, `getSessionSnapshot()`, `getEndReason()`), y `AuthProvider` lo lee con `useSyncExternalStore`. `writeSession` y `clearSession(reason?: 'expired' | 'logout')` notifican. Así el `onError` global del cliente HTTP (fuera de React) termina la sesión y `RequireAuth` redirige a `/login` sin acoplar el cliente al router (equivalente al `router.navigate('/login')` de la convención, pero testeable con el router en memoria). El snapshot es el **string crudo** de `sessionStorage` (estable para `useSyncExternalStore`) y `isAuthenticated = readSession() !== null`.
- **D2 — Registro de hooks HTTP fuera del árbol.** `src/app/api-hooks.ts` exporta `registerApiHooks(queryClient)`; se llama a nivel de módulo en `app.tsx` con el `queryClient` global y en `renderWithProviders` con el del test. No se registra en un `useEffect` (los efectos de los hijos corren antes que los del padre y la primera request saldría sin `Bearer`).
- **D3 — Sin Playwright (precedente S-013/S-021/S-024/S-029).** `testing-e2e` y ADR-002 piden Playwright, pero no está instalado en el repo y sumarlo requiere `api` + base sembradas. Los flujos de login, 401, resolver y anular se cubren con **tests de ruta completa en jsdom** (router real, MSW en el borde `fetch`) + axe por pantalla/overlay + verificación manual documentada contra la `api` real (TS-58). Se suma S-033 a la deuda D3 ya registrada.

**`PayloadView` (modelo puro `payload-view-model.ts`):** `flattenPayload(payload)` recorre el objeto en orden de claves y devuelve `{ bilingual: { path, es, en }[]; common: { path, value }[] }`:
- un objeto cuyas claves son exactamente `es` y `en` → fila bilingüe con `path` (ej. `definition`, `items.0.label`);
- otro objeto → recursión con `path` unido por `.`; un array de objetos → recursión con el índice (`items.0`); un array de primitivos → fila común con los valores unidos por `", "`;
- primitivo → fila común (`string` tal cual; `number`/`boolean` con `String()`; `null` → `'null'`).
- Valores `es`/`en` que no son string se formatean con la misma regla (array de primitivos unido; objeto → `JSON.stringify`).
`PayloadView` renderiza dos `<dl>` (ES y EN) con las filas bilingües en el mismo orden (`<dt>` = path, `<dd>` = valor), y un `<dl>` común con `path · value` más la entrada «Culpables posibles» (`Término · REDIS`, uno por `culprit`, o «—» si no hay). Todo como texto (`{value}` en JSX, nunca HTML).

### Tarea 2: Módulo `auth` — token-store, AuthProvider, hooks HTTP y errores tipados

**Status:** Completed
**Categoría:** Logic

#### Descripción
Implementa la sesión del admin según ADR-010 y la convención `auth`: token en `sessionStorage`, `Bearer` en cada request, `401 unauthorized` global que termina la sesión y limpia la cache, y `AuthProvider`/`useAuth` como único contexto de la app. Cubre la base de CA-1 y CA-3.

#### Criterios de Aceptación
1. `src/modules/auth/token-store.ts`: `readSession`, `writeSession`, `clearSession(reason: 'expired' | 'logout' = 'logout')` con la clave `'nerdose_admin_session'` y `try/catch` en todo acceso; `subscribe(listener): () => void`, `getSessionSnapshot(): string | null` (string crudo), `getEndReason(): 'expired' | 'logout' | null` (D1). `writeSession` pone el motivo en `null`. (TS-3, TS-4)
2. `src/modules/auth/auth-context.tsx`: `AuthProvider` usa `useSyncExternalStore(subscribe, getSessionSnapshot)` y expone `useAuth(): { isAuthenticated: boolean; endReason: 'expired' | 'logout' | null; signIn(session): void; signOut(): void }`; `signOut` = `clearSession('logout')` + `queryClient.clear()` (con `useQueryClient`). `useAuth` fuera del provider lanza `Error('useAuth must be used within AuthProvider')`.
