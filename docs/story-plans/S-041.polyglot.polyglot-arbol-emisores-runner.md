### Decisiones de planificación

1. **Go se ejecuta como `go build` + binario, no con `go run` (hallazgo verificado al planificar).** `go run main.go` compila y después lanza el binario como **proceso hijo propio**. Cuando el timeout de `execFile` mata `go run` con `SIGKILL`, el binario sigue vivo, huérfano y consumiendo CPU. Se comprobó en este entorno con un `for {}`: el proceso `…/go-build…/exe/main` sobrevivió al kill. Matar el grupo de procesos (`detached: true` + `process.kill(-pid)`) tampoco sirve acá: el sandbox no crea un grupo nuevo y `kill(-pid)` devuelve `ESRCH`. Por eso el runner de Go hace dos `execFile` sobre el mismo directorio temporal:
   - `go build -o main main.go` es la fase de compilación. Su exit ≠ 0 se clasifica como `compile_error`.
   - Después ejecuta el binario `<dir>/main`. Es hijo directo, así que el timeout lo mata.

   El presupuesto de tiempo es uno solo, `timeoutMs`, compartido entre las dos fases. La fase de ejecución recibe lo que queda (`deadline - now`, mínimo 1 ms). Funcionalmente es lo mismo que hace `go run` (compilar y ejecutar). El diseño del REQ (decisión 3) y las convenciones dicen `go run main.go`; la Task 8 actualiza las convenciones con este cambio.
2. **API pública del paquete** (se exporta desde `src/index.ts`; todo lo demás es interno):
   - Árbol: `createTreeBuilder()` y los tipos `FuncNode`, `Stmt`, `Expr`, `TreeNode`, `NodeId`, `BinOp`, `CompoundOp`.
   - Lenguajes: `LANGUAGES = ['js', 'go', 'java'] as const` y `type Language`. Los valores son los mismos que `CODE_LANGUAGES` de `@nerdose/core`, pero `polyglot` no depende de `core`, para seguir sin dependencias.
   - Emisión: `emit(func, lang): EmitResult`, `emitProgram(func, lang, { calls })` y `wrapFunction(code, lang, { entry, calls })`.
   - Runner: `runInLanguage(lang, source, options?)`, los tipos `RunOutcome`, `RunFailureKind` y `RunOptions`, y las constantes `RUN_TIMEOUT_MS = 10_000` y `RUN_MAX_BUFFER_BYTES = 1_048_576`.
   - Toolchains: `checkToolchains()` → `ToolchainReport`. Lo usa el helper de los tests de integración, y S-045 lo puede reusar para el `warn` de arranque del `generator` (decisión 14 del REQ) sin duplicar el parseo de versiones.
3. **`lineOf: Record<NodeId, number>`, 1-based, con una entrada por cada nodo del árbol.** La decisión 3 del REQ fija `Record`; la convención vieja decía `Map`. Mapeo:
   - `func` → línea 1.
   - Cada sentencia → la línea donde empieza.
   - Cada expresión → la línea de la sentencia que la contiene. Las expresiones del `init`, `cond` y `step` de un `for` caen en la línea de su encabezado.

   Bug Hunt va a apuntar a expresiones (`bugNodeId`) y a traducirlas a línea, por eso el mapeo las incluye. Las llaves de cierre no tienen nodo, así que no aparecen en `lineOf`.
4. **Ids deterministas por instancia de builder.** `createTreeBuilder()` crea un contador propio que arranca en 1. Cada constructor asigna el próximo id al crear el nodo, en el orden real de construcción. Como en JS los argumentos se evalúan antes que la llamada, los hijos reciben ids menores que el padre (ver TS-3). No hay contador global, así que dos builders que arman el mismo árbol producen nodos idénticos. `emit` rechaza un árbol con ids repetidos, por ejemplo uno que mezcla nodos de dos builders.
5. **Validaciones de los builders.** Son errores de programación, así que lanzan; no hay errores de usuario en juego.
   - Identificadores (`func`, parámetros, `let`, `assign`, `inc`, `compound`, `var`, `call`): tienen que cumplir `^[a-z][a-zA-Z0-9]*$` y no estar en `RESERVED_IDENTIFIERS`. Si no, `Error('invalid_identifier: <name>')`.
   - `RESERVED_IDENTIFIERS` es la unión de las palabras reservadas de JS, Go y Java, más los nombres que usa el `main` generado: `main`, `fmt`, `args`, `console`, `Math`, `System`, `String`, `Main`.
   - `num(value)`: tiene que ser entero en `[0, 2³¹ − 1]`. Si no, `RangeError('invalid_number: <value>')`. Los negativos se escriben con `bin('-', …)`. Así se respeta el subconjunto portable: enteros chicos, sin overflow y sin literales negativos que cambien la precedencia.
6. **`==` en JS se emite como `===`.** Para enteros la semántica es la misma; Go y Java emiten `==`.
7. **Precedencia y paréntesis.** Es un único algoritmo para los 3 lenguajes:
   - `prec('*') = 3`, `prec('+') = prec('-') = 2`, comparaciones = 1.
   - `half(x)` vale 3 en Go y Java (es `x / 2`). En JS es atómico (`Math.trunc(...)`).
   - El hijo izquierdo de un `bin` lleva paréntesis si `prec(hijo) < prec(padre)`. El derecho los lleva si `prec(hijo) <= prec(padre)`.
   - El operando de `half` lleva paréntesis en Go y Java si es un `bin` o un `half`.

   Así `x * half(n)` se emite `x * (n / 2)` en Go y Java, y no `x * n / 2`, que da otro resultado con división entera.
8. **Forma del programa.** `wrapFunction` copia la función emitida tal cual (sin reindentar) y agrega un `main` con **una línea de impresión por llamada**, en el orden de `calls`:
   - `calls` tiene que tener al menos una lista. Si no, Go no compila por el `import "fmt"` sin usar.
   - Cada argumento tiene que ser entero en `[-2³¹, 2³¹ − 1]`, porque Java usa `int`. Si no, `RangeError`.
   - `emitProgram` además valida que cada lista tenga tantos argumentos como `func.params`.
   - Los nombres de archivo los decide el runner según el lenguaje: `main.js`, `main.go`, `Main.java`.
9. **Usuario no root (CA-5, decisión 3 del REQ).** `resolveRunAs({ uid: process.getuid?.(), env: process.env })` devuelve una de tres cosas:
   - `{ kind: 'current' }` si el proceso no es root, o si `getuid` no existe.
   - `{ kind: 'as', uid, gid }` si es root y `RUNNER_UID`/`RUNNER_GID` son enteros > 0.
   - `{ kind: 'refuse' }` si es root y alguna de las dos falta, no es un entero o vale 0. Correr como uid 0 anularía la regla.

   La lectura y el parseo de las dos variables viven en `src/config/env.ts` (`readRunnerEnv(env)`), que es el único lugar del paquete que toca variables de entorno (convención `_base`). Se leen **en cada llamada**, no al importar el módulo, para que los tests puedan cambiarlas.
10. **Entorno mínimo.** El hijo recibe solo `PATH`, `HOME`, `GOCACHE`, `GOPATH` y `TMPDIR`, copiados de `process.env` cuando están definidos (`buildChildEnv(env)`). Nunca recibe `DATABASE_URL`, `GENERATOR_SECRET` ni ninguna otra variable del `generator`. `execFile` busca el ejecutable con el `PATH` de ese entorno, y eso permite simular un toolchain ausente con `PATH` vacío (TS-37).
11. **Clasificación de fallas** (`classifyFailure(lang, phase, error, stderr)`). Se evalúa en este orden:
    1. `error.code === 'ENOENT'` → `toolchain_missing`.
    2. `error.code === 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'` → `output_too_large`.
    3. `error.killed && error.signal === 'SIGKILL'` → `timeout`.
    4. Compilación:
       - Go: cualquier exit ≠ 0 de la fase `build`.
       - Java: `stderr` contiene `error: compilation failed`.
       - JS: `stderr` cumple `/^SyntaxError: /m`.

       Cualquiera de los tres → `compile_error`.
    5. Cualquier otro exit ≠ 0 → `runtime_error`.

    Las salidas se comprobaron con los toolchains locales (Node 24.22.2, Go 1.26.0, OpenJDK 21.0.10):
    - Go: `# command-line-arguments` / `./main.go:3:2: declared and not used: x`, exit 1.
    - Java: `Main.java:3: error: ';' expected` … `error: compilation failed`, exit 1.
    - JS: `SyntaxError: Unexpected token ';'`.
    - Un panic de Go sale con exit 2. Una excepción de Java muestra `Exception in thread "main"`.
12. **`RunOutcome`:**
    - `ok: true`: `stdout` es la salida estándar completa (en Go, solo la del binario, no la del build). `durationMs` es un entero que mide el tiempo total (`Math.round(performance.now() - start)`).
    - `ok: false`: `stderr` es el error estándar capturado. En `toolchain_missing` es el mensaje del error (`spawn go ENOENT`). En el rechazo por root vale exactamente `runner_requires_non_root`, con `durationMs: 0`.
    - **Nunca lanza** por timeout, compilación, ejecución, toolchain ausente o salida excesiva. Los errores de infraestructura propios (`mkdtemp` o `writeFile` que fallan) sí se propagan, porque no son un problema del snippet.
13. **Toolchains en los tests de integración (CA-6).** `test/integration/toolchains.ts` exporta `requireToolchains(check = checkToolchains)`. Se llama en el `beforeAll` de cada archivo de integración y lanza un error que nombra el toolchain faltante, por ejemplo `Missing toolchain: go (Go >= 1.25 required, see README "Requisitos")`. Las versiones exigidas no se sustituyen en silencio (convención `code-runner`):
    - Node con major 24.
    - Go ≥ 1.25.
    - JDK con major 21.

    No hay `skip`: si falta un toolchain, el test falla.

### NOT DOCUMENTED - needs verification

Un hijo con `uid = RUNNER_UID` no podría leer `main.go` ni escribir el binario. El plan agrega `chown(dir, uid, gid)` y `chown(archivo, uid, gid)` antes de ejecutar, solo cuando `resolveRunAs` devuelve `kind: 'as'`. Ni el REQ ni las convenciones lo mencionan. **Propósito (overview):** el paquete `@nerdose/polyglot` (`packages/polyglot`) tiene lo común de los juegos de código autogenerados (Big O y Bug Hunt, ADR-007). Contiene el árbol de código neutral al lenguaje, los emisores a JavaScript, Go y Java (una sentencia por línea) y el runner, que ejecuta el código con `child_process.execFile`, timeout de 10 s y usuario no root. Toolchains: Node 24, Go ≥ 1.25 y JDK 21. El aislamiento de red y los límites de recursos se definen con el hosting (diferido).

**Patrones:**
- Funciones puras para el árbol, los emisores, `wrapFunction`, la clasificación, el entorno y `resolveRunAs`. El único módulo con efectos es `run.ts` (más `toolchains.ts`, que ejecuta `--version`).
- El lenguaje se resuelve con un **dialecto** por lenguaje (sintaxis de cada construcción) sobre un **printer común**, que decide la estructura de líneas. Que los 3 lenguajes tengan la misma cantidad de líneas sale de la construcción, y un test lo comprueba igual.
- Errores: los errores de programación (árbol inválido, `calls` inválidos) lanzan `Error`/`RangeError`. Los problemas del snippet al ejecutar se devuelven como valor (`ok: false`), nunca como excepción (convención `code-runner`).
- Logging: `polyglot` no loguea; no tiene logger. Devuelve `durationMs` y `kind` para que lo loguee quien llama (el `generator`, a nivel `debug` y sin el código fuente completo a nivel `info`, en S-045).
- Testing: unitarios sin toolchains (árbol, emisores, programa, clasificación, entorno, usuario y runner con mocks) y de integración con los toolchains reales, que fallan si falta uno.

### ADRs Relevantes

**ADR-007: Generator como worker siempre activo y pipeline de generación**
- **Decisión (runner):** `child_process.execFile` con timeout de 10 s, usuario no root y un `main` por variante y lenguaje que corre todos los inputs. Java en modo source-file (`java Main.java`).
- **Reglas de Implementación (completas, textuales):**
  - `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
  - `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
  - Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
  - Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
  - Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
  - El seed MUST ser `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`, con `date` en formato `YYYY-MM-DD`. `GENERATOR_SECRET` MUST existir solo en el entorno del `generator`.
  - `GENERATION_MAX_ATTEMPTS` MUST valer 20 por defecto y ser configurable por variable de entorno.
  - `fill` MUST generar solo para fechas en `[today+1, today+14]`. MUST NOT generar para `today` ni para fechas pasadas.
  - `challenges.number` MUST calcularse con `core` (`date − LAUNCH_DATE + 1`) al insertar.
  - Un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`.
  - El runner MUST usar `execFile` (nunca `exec` con shell), timeout de 10 000 ms, y MUST correr como usuario no root.
  - Los toolchains MUST ser Node 24, Go ≥ 1.25 y JDK 21.
  - El `generator` MUST NOT hacer requests HTTP a servicios externos. No tiene salida de red fuera de la base (ADR-017).
  - El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.
- **Aplica a esta story:** las reglas del runner (`execFile`, 10 000 ms, no root) y de los toolchains. El resto es del `generator` y aparece solo como contexto. Riesgo registrado en el ADR: "un snippet generado cuelga o consume recursos → timeout de 10 s y usuario no root". La Decisión 1 de este plan (Go sin `go run`) cumple el timeout de verdad: sin ella, el timeout dejaría procesos colgados.

**ADR-003: Monorepo y paquetes compartidos**
- **Decisión:** monorepo con pnpm workspaces y Turborepo. `packages/polyglot/` contiene el árbol de código, los emisores JS/Go/Java y el runner multi-lenguaje.
- **Reglas de Implementación (completas, textuales):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db`.
  - `@nerdose/core` MUST exponer una sola entrada `.`, isomorfa (corre en Node y en el navegador, sin dependencias de Node): MUST NOT importar `node:*`. (Hasta el ADR-017 existía una entrada `./notify`; se eliminó.)
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

**ADR-002: Stack tecnológico**
- **Decisión (worker):** Node.js 24 LTS (TS). Toolchains Go ≥ 1.25 y JDK 21 LTS. Java corre en modo *source-file* (`java Main.java`). Testing: Vitest.
- **Reglas de Implementación (completas, textuales):**
  - Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
  - `api` y `generator` MUST correr en Node.js 24 LTS. `engines.node` MUST ser `">=24 <25"`.
  - El framework HTTP de la `api` MUST ser Hono. MUST NOT usarse Express, Fastify ni NestJS.
  - Todo acceso a la base MUST pasar por Drizzle ORM con el driver postgres.js. SQL crudo solo en migraciones, en las vistas `metrics_*` y donde Drizzle no lo soporte (`LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`).
  - Toda entrada HTTP (body, query, params) MUST validarse con Zod vía `@hono/zod-validator`. Los schemas de jugada MUST importarse del paquete del juego, nunca redefinirse.
  - `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
  - Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
  - Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
  - Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
  - El PRNG del `generator` MUST ser `pure-rand` (xoroshiro128+). MUST NOT usarse `Math.random()` en la generación de desafíos.
  - Los tests MUST usar Vitest; los e2e, Playwright.

  - Funciones y variables: `camelCase`.

**`code-tree` (custom). Reglas vigentes, ajustadas por la decisión 3 del REQ:**
- El árbol es neutral al lenguaje: no se filtran a él nodos propios de un emisor.
- Los emisores respetan una sentencia por línea, y un test comprueba que cada nodo cae en la misma línea en los 3 lenguajes.
- En el árbol solo se permite el subconjunto portable: nada de semántica de división entera (salvo `half` de no negativos), overflow ni módulo de negativos.
- Los emisores son puros y deterministas: el mismo árbol produce el mismo código. Nunca leen el reloj, el azar ni el entorno.
- El código emitido se compila con los compiladores reales en los tests de integración (y en un job de CI, diferido).
- El árbol y los emisores nunca ejecutan código. La ejecución vive solo en el runner, y solo el `generator` puede llamarlo.
- Cada nodo tiene un `id` estable, para que los juegos puedan referirse a nodos (por ejemplo `bugNodeId`) y traducir líneas con `lineOf`.
- Java se emite para modo source-file (`java Main.java`) y Go para compilarse como `main.go` (ver la Decisión 1 sobre `go run`).

**Árbol (decisión 3 del REQ, textual):** nodos con `id` estable (`n1`, `n2`…, asignados por los builders en orden de construcción, deterministas):
- Sentencias: `func(name, params, body)`, `let(name, expr)`, `assign(name, expr)`, `inc(name)` (`x++`), `compound(name, op, expr)` (`+=`, `*=`), `for(init, cond, step, body)`, `while(cond, body)`, `if(cond, then)`, `return(expr)`.
- Expresiones: `num`, `var`, `bin` (`+ - * < <= > >= ==`), `half(expr)` (división entera por 2 de un no negativo: `Math.trunc(x / 2)` en JS, `x / 2` en Go y Java) y `call(name, args)`.
- Tipos: solo enteros (`int` en Go y Java, `number` en JS) y el parámetro `n`.
- Ninguna construcción con costo dependiente de datos: sin arrays, maps, strings ni `break`. Esto reemplaza el "`len` / `length` builtin" y los "arrays de enteros" de la convención vieja.

**Emisores (decisión 3 del REQ, textual):** `emit(func, lang) -> { code, lineOf }`.
- Firma en una línea: `function f(n) {` / `func f(n int) int {` / `static int f(int n) {`.
- Una sentencia por línea y llaves de cierre en su propia línea.
- Indentación de 2 espacios en JS, tab en Go y 4 espacios en Java, como el prototipo.
- `lineOf: Record<nodeId, number>`, 1-based.
- Puros y deterministas.
- Test: para un conjunto de árboles, el mismo nodo cae en la misma línea en los 3 lenguajes y los 3 códigos tienen la misma cantidad de líneas.

**Programa (decisión 3 del REQ, textual):** `emitProgram(func, lang, { calls: number[][] })` genera la fuente completa: `main.js`, `main.go` con `package main` o `Main.java` con `public class Main`. Contiene la función emitida tal cual y un `main` que la llama una vez por cada lista de argumentos e imprime un entero por línea. Es la única pieza que se ejecuta y no agrega instrumentación dentro de la función. `wrapFunction(code, lang, { entry: 'f', calls })` envuelve la función ya emitida en el `main` de su lenguaje, con la misma lógica que `emitProgram`. Lo usa S-045, porque el payload guarda código y no el árbol (decisión 10 del REQ).

**`code-runner` (custom). Reglas vigentes:**
- El runner usa `execFile` (nunca `exec` con shell), con timeout de 10 000 ms, y corre como usuario no root.
- Los argumentos nunca se arman con strings no confiables: el código va en archivos, no en la línea de comandos.
- Un timeout, un exit distinto de cero o un error de compilación son un check fallido (candidato `rejected`), no una excepción que detiene el job.
- Solo el `generator` importa `@nerdose/polyglot`. Las entradas `./definition` y `./client` de los juegos nunca lo importan, ni tampoco `node:child_process`.
- Toolchains requeridos: Node 24, Go ≥ 1.25 y JDK 21. Las versiones no se sustituyen en silencio.
- El runner no hace llamadas de red. El aislamiento de red y los límites de recursos se definen con el hosting (diferido).
- Los directorios temporales son únicos por corrida y se limpian en un `finally`.
- El tamaño de la salida está acotado (`maxBuffer`).
- Integración: el logging (lenguaje, duración y exit a nivel `debug`) lo hace quien llama. Los tests que corren toolchains son de integración y los necesitan instalados.

**Runner (decisión 3 del REQ, textual):** `runInLanguage(lang, source, { timeoutMs = 10_000 }): Promise<RunOutcome>`, con:

```ts
type RunOutcome =
  | { ok: true; stdout: string; durationMs: number }
  | { ok: false; kind: 'timeout' | 'compile_error' | 'runtime_error' | 'toolchain_missing' | 'output_too_large'; stderr: string; durationMs: number };
```

- Escribe la fuente en un directorio temporal único (`mkdtemp`) que se borra en `finally`.
- Corre `node main.js`, `go run main.go` o `java Main.java` con `execFile` (sin shell), `timeout`, `killSignal: 'SIGKILL'`, `maxBuffer` de 1 MiB y un entorno mínimo (`PATH`, `HOME`, `GOCACHE`, `GOPATH`, `TMPDIR`). Para Go, ver la Decisión 1.
- Nunca lanza por un problema del snippet: lo devuelve como `ok: false`.
- `ENOENT` del ejecutable → `toolchain_missing`. Una salida de `go run`/`java` con error de compilación (exit ≠ 0 y salida del compilador en `stderr`) → `compile_error`.
- **Usuario no root:** si el proceso corre como root (`process.getuid() === 0`), el runner exige `RUNNER_UID`/`RUNNER_GID` (variables de entorno del `generator`) y los pasa a `execFile`. Si faltan, devuelve `ok: false` con `kind: 'runtime_error'` y `stderr = 'runner_requires_non_root'`, sin ejecutar. Si el proceso ya no es root (desarrollo local), corre con el usuario actual.

- Pseudoflujo:

  ```ts
  export async function runInLanguage(lang: Language, source: string, options: RunOptions = {}): Promise<RunOutcome> {
    const runAs = resolveRunAs({ uid: process.getuid?.(), env: process.env });
    if (runAs.kind === 'refuse') return { ok: false, kind: 'runtime_error', stderr: 'runner_requires_non_root', durationMs: 0 };
    const timeoutMs = options.timeoutMs ?? RUN_TIMEOUT_MS;
    const start = performance.now();
    const dir = await mkdtemp(join(tmpdir(), 'polyglot-'));
    try {
      const file = join(dir, FILE_NAME[lang]);          // main.js | main.go | Main.java
      await writeFile(file, source, 'utf8');
      if (runAs.kind === 'as') { await chown(dir, runAs.uid, runAs.gid); await chown(file, runAs.uid, runAs.gid); }
      // js: node main.js · java: java Main.java · go: go build -o main main.go → <dir>/main
      // cada execFile con { cwd: dir, timeout, killSignal: 'SIGKILL', maxBuffer, env, encoding: 'utf8', uid?, gid? }
      // en error: return { ok: false, kind: classifyFailure(lang, phase, err, err.stderr ?? ''), stderr, durationMs }
      return { ok: true, stdout, durationMs: Math.round(performance.now() - start) };
    } finally {
      await rm(dir, { recursive: true, force: true });
    }
  }
  ```
