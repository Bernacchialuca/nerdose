# Story Plan: S-038 (games) - Preview en modo solución de los juegos

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-038](../stories/S-038.preview-modo-solucion-juegos.md)
- **Servicio:** games
- **Resumen:** Cada `./client` de Devdle, Grep Grid y Tech Timeline exporta un componente nuevo `Preview` con props `{ payload, language }`: solo lectura, dibuja el tablero del juego con la solución superpuesta y elige los textos `{ es, en }` del `payload` según `language`. No llama a la API, no guarda estado de partida y no depende de `Play`. Lo va a montar el admin (S-039) en el drawer O-02, en dos paneles ES/EN lado a lado.

> **Alcance de este plan:** solo el servicio `games` (`packages/games/devdle`, `packages/games/grep-grid`, `packages/games/timeline`) y la documentación del contrato en la convención `game-clients` de `games`. La story también afecta a `ui` (plan `S-038.ui.*`, aparte). **Este plan no depende de componentes nuevos de `@nerdose/ui`:** usa `cn`, los tokens existentes (`text-game-*`, `bg-surface-*`, …) y las piezas propias de cada paquete (`Board`, `WordCard`, `WordList`, `Rail`, `SectionPanel`). Si el plan de `ui` agrega algo, no es prerequisito.
>
> **Big O y Bug Hunt:** sus paquetes **no existen** en el repo. Implementan `Preview` en sus FG; el admin cae a `PayloadView` si falta (Riesgos de la story). No se crean stubs.
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a la raíz de cada paquete (`packages/games/<game_id>/`), salvo las de `docs/`, que son relativas a la raíz del monorepo.
>
> **Estado actual del código (verificado al planificar):**
> - Línea base verde: `pnpm turbo run test --filter=@nerdose/game-devdle --filter=@nerdose/game-grep-grid --filter=@nerdose/game-timeline` → devdle 24 archivos / 138 tests, grep-grid 24 / 199, timeline 25 / 190.
> - Los tres `src/client/index.ts` exportan `Instructions`, `Game`, `Result`, `share`, `i18n`, `HELP_TARGET_ID` y tipos. **Ninguno exporta `Preview`.**
> - Los componentes de los `client` **no usan react-i18next**: reciben `t: Translate` por props desde el host (`web`). El traductor que hoy existe fuera de `web` es `makeT` en `src/client/test-utils.ts`, **solo para tests** (tira error si falta una clave).
> - `SectionPanel` (copiado en los tres paquetes) siempre renderiza su título como `h2`.
> - `test/boundaries.test.ts` de Grep Grid **prohíbe** que un archivo de `src/client/` contenga los textos `lineCells` o `directionOf` (NFR-S02: en la partida decide el servidor), y permite importar de `src/shared/geometry` y exactamente `src/definition/schemas`.
> - `test/boundaries.test.ts` de Timeline permite al client importar solo de `src/client`, `src/definition/schemas` y `src/shared/format-date` (no `src/shared/prompts`).
> - `test/boundaries.test.ts` de Devdle prohíbe en todo `src/` los textos `fetch(`, `Date.now(`, `new Date()`, `Math.random(`, `node:`.
> - `apps/web/src/modules/game-host/types.ts` tiene una **copia estructural** de `GameClient` (sin `Preview`); como el registry de `web` usa `satisfies` sobre un `import()`, agregar una exportación al módulo no rompe el typecheck de `web`.

### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **`Preview` se traduce solo, con sus propios recursos.** El contrato es `{ payload, language }` (sin `t`), y los `client` no dependen de react-i18next. Cada paquete agrega `src/client/translate.ts` con `translatorFor(language: Locale): Translate`, que resuelve claves con puntos sobre `i18n.resources[language]` e interpola `{{var}}` (misma lógica que `makeT`), pero **devuelve la clave tal cual si no existe** en lugar de tirar (no rompe la UI del admin; el test de árbol de claves ES/EN cubre la completitud, CA-6). `makeT` sigue igual para los tests. Consecuencia para S-039: el `I18nextProvider` de la convención `game-clients` del admin no hace falta para `Preview` (hallazgo, ver 8).
2. **Encabezados de la preview en `h3`.** `Preview` va embebido debajo del título del drawer O-02 (`h2`) y de las cards «ES»/«EN». Para no romper el orden de encabezados del admin (axe `heading-order`), sus secciones usan `h3`. `SectionPanel` de cada paquete gana la prop opcional `headingLevel?: 2 | 3` (default `2`, así `Game`/`Result` no cambian). `Preview` nunca renderiza `h1` ni `h2`.
3. **Payload inválido = error, no fallback silencioso.** `Preview` hace `payloadSchema.parse(payload)` (de `src/definition/schemas`, ya permitido al client) y deja propagar el `ZodError`, igual que `Game`/`Result` con sus datos. En Timeline, un id de `correct_order` que no está en `items` tira `Error('correct_order references unknown opaque_id: <id>')`. El admin (S-039) decide el error boundary. Un `payload` `approved` siempre pasa (lo valida `verify`).
4. **Raíz con `lang`.** La raíz de `Preview` es un `<div lang={language}>` (sin rol ni landmark propio: el admin ya envuelve cada panel en una `section` con `aria-label`). Así un lector de pantalla pronuncia bien el panel EN aunque el admin esté en español.
5. **Devdle reutiliza `Board` y `WordCard`.** El tablero es **una fila** con la palabra y todas sus celdas `correct` (el mismo `Board` de la partida, acento `game-devdle`, glifo `✓`), y debajo la card «// palabra del día» con categoría, definición y resumen en el idioma del panel. `WordCard` pasa a aceptar `result: Pick<DevdleResult, 'word' | 'category' | 'definition' | 'summary'>` y `headingLevel?` (compatible con la llamada actual de `Result`).
6. **Grep Grid: estado de celda y de fila `solution`, sin `lineCells`.** Las celdas de las 8 palabras se calculan desde `placements` con `DIRECTION_STEPS[direction]` desde `from`, `word.length` pasos (`word` buscado por `term_id` en `payload.words`; si falta, `Error`). No se usa `lineCells`/`directionOf` para no tocar la regla de fronteras (NFR-S02) ni debilitarla. Visualmente `solution` es **idéntico a `found`** (fondo `game-grep-grid`, glifo `✓`, peso 800), pero su `aria-label` dice «parte de la solución» (no «encontrada»: nadie jugó). En la lista, la fila `solution` tiene el estilo de la fila encontrada **sin tachado**, la etiqueta «{n} letras» y la definición. Título «// palabras del desafío» (no «de hoy»: la fecha es futura) con el dato «8 palabras». El tablero usa el modo `result` de `Board` (tabla de solo lectura, sin botones ni roving tabindex).
7. **Timeline reutiliza `Rail`.** Consigna como línea `// consigna: {payload.prompt[language]}` y la card «// orden correcto» (`h3`) con el `Rail` del resultado: los 5 hechos en el orden de `correct_order`, con fecha formateada por precisión (`formatEventDate`), nombre, categoría y `note[language]`. El orden lo manda `correct_order`, no el orden de `items`.
8. **Hallazgos de documentación (no bloquean).**
   - La convención `game-clients` del **admin** muestra un `I18nextProvider` por panel "para los textos de UI de los clients"; con la decisión 1, `Preview` no lo necesita (sigue sirviendo si S-039 monta `Game`/`Result`). Se deja anotado para S-039; este plan no edita docs del admin.
   - `docs/design-system/web/README.md` dice `version: 1.7.0` en el frontmatter y `1.4.1` en "Estado actual". Se toma 1.7.0 (coincide con `tokens.css`, "DS 1.7.0").
   - ADR-006 (bloque `// entrada ./client`) lista `Instructions, Game, Result y share`; no menciona `Preview`. La convención `game-clients` de `games` sí (sección "Admin preview"). Queda para `/product-change-technical-definition`.

### Arquitectura del Servicio

**games** — Library node (TypeScript estricto); la entrada `./client` es React. Un paquete por juego `@nerdose/game-<game_id>` con tres entradas: `./definition` (servidor, la usa la `api`), `./client` (React: `Instructions`, `Game`, `Result`, `share()`; la usan `web` y `admin`) y `./generator` (la usa el `generator`). ADR-003 y ADR-006.

**Convenciones activas que aplican a esta story** (entrada `./client`): `game-package`, `game-clients`, `styling`, `accessibility`, `testing-unit` (más `_base`). `game-registry`, `validation`, `testing` y `error-handling` aplican a `definition`/`generator`, que no se tocan.

#### Estructura de un paquete (convención `game-package`)

```
packages/games/<game_id>/
├── package.json              # name @nerdose/game-<game_id>, exports map below
├── src/
│   ├── definition/           # server contract: GameDefinition implementation
│   │   ├── index.ts          # exports `definition`
│   │   ├── schemas.ts        # Zod: payload, move, public view, result
│   │   └── *.test.ts         # contract tests incl. anti-spoiler
│   ├── client/               # React UI: Instructions, Game, Result, share()
│   │   ├── index.ts
│   │   └── *.test.tsx
│   ├── generator/            # GameGenerator: generate() and verify()
│   │   ├── index.ts          # exports `generator`
│   │   └── *.test.ts
│   └── shared/               # pure types and helpers used by more than one entry
└── (extra assets of the game, e.g. wordlist/ for devdle)
```

**What each entry may import** (convención `game-package`, verbatim):

| Entry | May import | Must not import |
|---|---|---|
| `./definition` | `@nerdose/core` (`.`), `zod`, `shared/` | `@nerdose/polyglot`, `node:*`, React, `./generator`, `./client`, anything that executes code |
| `./client` | `@nerdose/core` (`.`), `zod`, `react`, `@nerdose/ui`, `shared/`, types from `./definition` | `@nerdose/polyglot`, `node:*`, `./generator`, runtime code of `./definition` that carries solutions |
| `./generator` | `@nerdose/core` (`.`), `zod`, `@nerdose/polyglot`, `shared/`, `./definition` | `./client`, React |

Interpretación vigente (planes S-020/S-024/S-029): `src/definition/schemas.ts` no lleva solución (schemas Zod y constantes), así que el client **puede** importarlo en runtime; **no** importa `src/definition/index.ts` ni ningún `test-fixtures.ts`.

**Reglas de `game-package` relevantes (verbatim):**
- `exports` contains exactly `./definition`, `./client` and `./generator` (code entries). No default entry.
- `./definition` and `./client` never import `@nerdose/polyglot`, `node:child_process` or anything that executes code (enforced by ESLint, see `monorepo-tooling`).
- Heavy dependencies (Shiki, dnd-kit) belong to the game package and load in the game's own chunk.

#### Convención `game-clients` (games) — sección "Admin preview" (verbatim, estado actual)

- Each `client` also exports `Preview` with props `{ payload, language }` (REQ-008): read-only, shows the board with the solution overlaid, no API calls and no play state. `payload` is the full `{es,en}` payload and `language` picks the text. Games without `Preview` fall back to `PayloadView` in the admin.
- `admin` mounts `Preview` (and previously the same `Game`/`Result` components in **solution mode**) with the full `payload` returned by `/api/admin/*`, in Spanish and in English side by side. The admin renders the preview inside a container that makes it read-only (no moves are sent).

Reglas (verbatim): Import only `@nerdose/game-<game_id>/client`. · The registry is the only place that lists games. · Each game is loaded with a dynamic `import()` so it is its own chunk. · Heavy dependencies (Shiki, dnd-kit) are dependencies of the game packages and are loaded in the game's own chunk.

#### Convención `game-clients` (admin) — cómo lo va a montar S-039 (verbatim, extracto)

`GameClient` is the `./client` entry shape defined by the game contract (`Instructions`, `Game`, `Result`, `share`, and `Preview` with props `{ payload, language }`, read-only, REQ-008). The admin mounts `Preview` in two panels (`es`, `en`) with the fixed i18next instances; a game without `Preview` falls back to `PayloadView`. Props are owned by the game packages and `@nerdose/core`; the admin passes the payload through without reinterpreting it.

Reglas del admin que la preview debe permitir: Previews always show Spanish and English together · Previews never send requests to player endpoints (`/api/games/*`, `/api/session`); they render from the admin payload · The preview must meet the same accessibility rules as the player UI · each panel declares its `lang` and a label.

#### Estilos (convención `styling`, reglas verbatim)

- Use only the tokens above (or later, the Design System's). No literal hex colors, no arbitrary `[#abc]` color values in components.
- Merge conditional classes with `cn()`; never concatenate class strings by hand.
- Text and interactive-element contrast meets WCAG 2.1 AA against the surface it sits on (4.5:1 text, 3:1 large text and UI components).
- State is never conveyed by color alone: pair it with an icon, text or pattern (see `accessibility`).
- No CSS-in-JS and no component CSS files, except the token file and third-party overrides.
- Per-game accent is applied by the game's own `client` via its token, never with a literal hex.
- **Static check:** component and web `.tsx` files must not contain arbitrary values (`/\[(\d|#|rgb)/`) nor generic utilities (`rounded-md`, `shadow-md`, `text-2xl`, `font-semibold`). (Cada paquete lo verifica en `src/client/client-styles.test.ts`: tampoco `outline-none` ni hex.)

#### Accesibilidad (convención `accessibility`, reglas verbatim)

- Contrast is at least 4.5:1 for text (3:1 for large text and UI boundaries) against its actual background.
- No interactive element is built from a `<div>` or `<span>` with a click handler; use a native control.
- Every image or icon is either decorative (`aria-hidden`) or has an accessible name.
- Color is never the only carrier of meaning.
- Dynamic updates are announced via live regions; do not move focus unexpectedly.
- axe-core reports zero violations in unit checks and e2e page checks.
- Language is declared (`<html lang>`) and updated when the locale changes.

#### Tests unitarios (convención `testing-unit`, reglas verbatim)

- Query by role, label or visible text. `data-testid` only when no accessible query exists.
- Use `userEvent`, not `fireEvent`, for interactions.
- Each interactive component has an axe check; fix violations instead of disabling rules.
- No snapshot tests of large DOM trees.
- Tests do not rely on the real date or timers; use fake timers.
- Test names state the behavior ("shows ... when ..."), not the implementation.

Patrón vigente en los paquetes: `// @vitest-environment jsdom` en la primera línea, `render` de Testing Library, `axe` de `vitest-axe`, fixtures locales del client en `src/client/test-fixtures.ts`.

### ADRs Relevantes

- **ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables**
  - Decisión: cada juego es un paquete `packages/games/<game_id>` con `./definition`, `./client` y `./generator`; registry en `api`, `web`/`admin` y `generator`. Consecuencia positiva: "El admin reutiliza los componentes `client` para la preview con la solución."
  - Reglas de Implementación (verbatim, las que aplican al client):
    - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
    - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
    - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
    - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
    - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
    - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.
  - Para esta story: `Preview` recibe el `payload` **completo** (solo llega por `/api/admin/*`); nunca lo pide ni lo cachea. La entrada `./client` sigue sin exportar `payloadSchema` ni el objeto `definition`.

- **ADR-003: Monorepo y paquetes compartidos**
  - Reglas de Implementación (verbatim, las que aplican):
    - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
    - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
    - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
    - `@nerdose/core` MUST exponer una sola entrada `.`, isomorfa (corre en Node y en el navegador, sin dependencias de Node): MUST NOT importar `node:*`.

### Contexto de API

Sin cambios de API. `Preview` **no** llama a ningún endpoint. El `payload` que recibe es el campo `challenge.payload` de `GET /api/admin/challenges/upcoming` (`docs/apis/api.yaml`, `UpcomingDay`):

```yaml
challenge:
  required: [id, status, payload, verification, generator_version, attempt, rejected_items]
  properties:
    id: { type: string, format: uuid }
    status: { $ref: '#/components/schemas/ChallengeStatus' }
    payload: { type: object, additionalProperties: true }
    verification: { type: object, additionalProperties: true }
    generator_version: { type: string }
    attempt: { type: integer, minimum: 0, description: El seed derivado nunca se devuelve }
```

Es decir, `payload` llega como objeto opaco (`unknown` para `Preview`) y cada juego lo valida con su `payloadSchema`.

#### Payloads por juego (`src/definition/schemas.ts`, verbatim)

**Devdle**
```ts
export const WORD_PATTERN = /^[A-Z]{4,12}$/;
const localizedSchema = z.object({ es: z.string(), en: z.string() });
export const payloadSchema = z.object({
  term_id: z.string().min(1),
  word: z.string().regex(WORD_PATTERN),
  category: z.enum(TERM_CATEGORIES),
  definition: localizedSchema,
  summary: localizedSchema,
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
});
```

**Grep Grid**
```ts
export const WORD_PATTERN = /^[A-Z]{4,12}$/;
export const WORDS_COUNT = 8;
const last = GRID_SIZE - 1;   // GRID_SIZE = 12
const idSchema = z.string().min(1);
const localizedSchema = z.object({ es: z.string(), en: z.string() });
export const cellSchema = z.object({
  row: z.number().int().min(0).max(last),
  col: z.number().int().min(0).max(last),
});
const gridSchema = z.array(z.array(z.string().regex(/^[A-Z]$/)).length(GRID_SIZE)).length(GRID_SIZE);
export const payloadSchema = z.object({
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  grid: gridSchema,
  words: z.array(z.object({
    term_id: idSchema,
    word: z.string().regex(WORD_PATTERN),
    definition: localizedSchema,
  })).length(WORDS_COUNT),
  placements: z.array(z.object({
    term_id: idSchema,
    from: cellSchema,
    to: cellSchema,
    direction: z.enum(DIRECTIONS),   // 'right' | 'down' | 'down_right' | 'up_right'
  })).length(WORDS_COUNT),
});
```

**Tech Timeline**
```ts
export const ITEMS_COUNT = 5;
export const OPAQUE_ID_PATTERN = /^[a-z0-9]{6}$/;
const day = z.string().regex(/^\d{4}-\d{2}-\d{2}$/);
const localized = z.object({ es: z.string(), en: z.string() });
const payloadItemSchema = z.object({
  fact_id: z.string().min(1),
  opaque_id: z.string().regex(OPAQUE_ID_PATTERN),
  label: z.string().min(1),
  category,                    // z.enum(TIMELINE_CATEGORIES)
  event_date: day,
  date_precision: precision,   // z.enum(DATE_PRECISIONS): 'year' | 'month' | 'day'
  note: localized,
});
export const payloadSchema = z.object({
  date: day,
  prompt: localized,
  items: z.array(payloadItemSchema).length(ITEMS_COUNT),
  correct_order: z.array(z.string()).length(ITEMS_COUNT),   // opaque_id del más antiguo al más reciente
});
```

`label` de Timeline **no** es `{ es, en }` (nombre propio del hito: "Python", "Docker"); solo `prompt` y `note` lo son.

### Puntos de Integración

- **Consumidor:** `apps/admin` (S-039) vía `() => import('@nerdose/game-<id>/client')` → `Preview`. Contrato: `Preview(props: { payload: unknown; language: Locale })`, `Locale = 'es' | 'en'` (`@nerdose/core`).

    for (const placement of p.placements) {
      const word = p.words.find((w) => w.term_id === placement.term_id);
      if (!word) throw new Error(`placement references unknown term_id: ${placement.term_id}`);
      const { dRow, dCol } = DIRECTION_STEPS[placement.direction];
      for (let i = 0; i < word.word.length; i++) {
        keys.add(cellKey({ row: placement.from.row + dRow * i, col: placement.from.col + dCol * i }));
      }
    }
    return keys;
  }
