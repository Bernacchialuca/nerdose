### Configuración de referencia (convención `monorepo-tooling`, copiada)

```yaml
# compose.yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: nerdose
      POSTGRES_USER: nerdose_owner
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - '127.0.0.1:5432:5432'
    volumes:
      - nerdose-pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U nerdose_owner -d nerdose']
      interval: 5s
      retries: 10
volumes:
  nerdose-pgdata:
```

> The image is the same one Testcontainers uses in tests.

**How to use** (convención, copiado):
- Start-up order (documented in `README.md`): `docker compose up -d` → `pnpm --filter @nerdose/db db:migrate` → `pnpm dev`.
- Copy each `.env.example` to `.env.local` (and the root one to `.env` for Compose) and fill the values. Real values are never committed.

**Rules** (convención, las que aplican a este plan, copiadas):
- `.gitignore` excludes `.env`, `.env.local`, `.env.test`, `node_modules`, build output and Turborepo cache. Only `.env.example` files are committed, with empty values and a comment per variable.
- `compose.yaml` publishes PostgreSQL only on `127.0.0.1` and keeps data in the named volume `nerdose-pgdata`. Rebuilding from scratch is an explicit `docker compose down -v`.
- No secrets in the repository: `.env.example` files never contain real values.
- Deployment, CI/CD, hosting and production secrets are out of scope until they are defined.

**Integration with other conventions** (copiado):
- **env-config**: each service declares its variables in its own `env.ts` and keeps `.env.example` in sync; the root `.env.example` only holds Compose variables.
- **testing**: the root Vitest config runs each package's tests; integration tests need Docker (Testcontainers) and fail with a clear message without a daemon.
- **orm**: `db:migrate` is the single migration command and reads `DATABASE_URL_OWNER`.

### Forma normalizada de `compose.yaml` (verificada con `docker compose config --format json`)

Los tests de la Tarea 1 leen la configuración ya normalizada por Compose, no el YAML crudo (no hay parser YAML en las dependencias y no se agrega uno). Con `POSTGRES_PASSWORD=compose-test` en el entorno, la salida esperada del servicio es:

```json
{
  "name": "nerdose",
  "services": {
    "postgres": {
      "environment": {
        "POSTGRES_DB": "nerdose",
        "POSTGRES_PASSWORD": "compose-test",
        "POSTGRES_USER": "nerdose_owner"
      },
      "healthcheck": {
        "test": ["CMD-SHELL", "pg_isready -U nerdose_owner -d nerdose"],
        "interval": "5s",
        "retries": 10
      },
      "image": "postgres:16-alpine",
      "ports": [
        { "mode": "ingress", "host_ip": "127.0.0.1", "target": 5432, "published": "5432", "protocol": "tcp" }
      ],
      "volumes": [
        { "type": "volume", "source": "nerdose-pgdata", "target": "/var/lib/postgresql/data", "volume": {} }
      ]
    }
  },
  "volumes": { "nerdose-pgdata": { "name": "nerdose_nerdose-pgdata" } }
}
```

Con `--no-interpolate`, `services.postgres.environment.POSTGRES_PASSWORD` es literalmente `"${POSTGRES_PASSWORD}"`. Sin la variable definida, Compose emite el warning `The "POSTGRES_PASSWORD" variable is not set. Defaulting to a blank string.` y sale con 0.

**Precedencia de variables en Compose:** el entorno del proceso tiene prioridad sobre el `.env` del directorio del proyecto. Los tests pasan `POSTGRES_PASSWORD=compose-test` explícitamente para no depender del `.env` local del desarrollador.

### ADRs Relevantes

#### ADR-004: PostgreSQL como única base, con propiedad por roles

- **Decisión:** PostgreSQL 16 como única base de datos (`nerdose-db`), con la frontera entre servicios aplicada en la base mediante tres roles (dueño del schema, `nerdose_api`, `nerdose_generator`).
- **Reglas de Implementación (verbatim):**
  - La única base MUST ser PostgreSQL ≥ 16. MUST NOT agregarse otra base (Redis, MongoDB, SQLite) en v1.
  - Los campos que varían por juego (`challenges.payload`, `challenges.verification`, `plays.state`, `plays.result`, `player_game_stats.extra`, `challenge_reports.context`, `job_runs.summary`) MUST ser `jsonb`.
  - Los textos de contenido bilingües MUST guardarse como `jsonb` con la forma `{ "es": string, "en": string }`.
  - Las fechas de día MUST ser `date` (día UTC). Los instantes MUST ser `timestamptz`.
  - Los ids MUST ser `uuid` (`gen_random_uuid()`), salvo las PK compuestas o naturales que define `docs/db-schemas/nerdose-db.md`.
  - La `api` MUST conectarse con el rol `nerdose_api` y el `generator` con `nerdose_generator`. Ninguno de los dos MUST tener permisos de DDL.
  - Los `GRANT` de cada rol MUST estar en una migración versionada en `packages/db`, con permisos por columna sobre `challenges`, `terms` y `timeline_facts` exactamente como en la tabla de arriba.
  - La unicidad de un Challenge vigente MUST implementarse como índice único parcial sobre `(game_id, date)` con `WHERE status IN ('approved','published','voided')`.
  - `plays` MUST tener `UNIQUE (player_id, challenge_id)` y `challenge_reports` MUST tener `UNIQUE (player_id, challenge_id)`.
  - Los enums del dominio (`game_id`, `challenge_status`, `play_status`, `code_language`, `locale`, etc.) MUST ser enums de PostgreSQL con los valores exactos del análisis de dominio.
- **Aplica a este plan:** la imagen es PostgreSQL 16 (≥ 16) y es la única base; el rol creado por Compose (`POSTGRES_USER=nerdose_owner`) es el **dueño del schema**, que solo usa `db:migrate`. Los roles de servicio y sus `GRANT` los crea la migración (plan `S-002.db`), **no** un script de init de Compose (alternativa descartada en REQ-001, decisión 6).

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo con pnpm workspaces y Turborepo.
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.
- **Aplica a este plan:** los tests nuevos van en el proyecto `workspace` (`test/`) y corren por la tarea Turborepo existente `//#test:workspace`. No se agrega ninguna migración ni SQL a la raíz.

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- Los tests MUST usar Vitest; los e2e, Playwright.

### Decisiones de diseño del REQ-001 que aplican

- **Decisión 4 (variables incrementales):** Raíz (Docker Compose): `POSTGRES_PASSWORD` del rol dueño local. Es la **única** variable del `.env.example` de la raíz.
- **Decisión 5 (`.env.example` sin valores):** cada variable queda vacía y lleva un comentario. Para desarrollo local, el comentario puede mostrar un valor de ejemplo no secreto. Los valores reales van en `.env` de la raíz para Compose (en `.gitignore`).
- **Decisión 6 (roles en la migración):** `nerdose_owner` ya existe antes de migrar: en local lo crea Docker Compose (`POSTGRES_USER`). Alternativa descartada: crear los roles con contraseña en un script de init de Compose.
- **Docker Compose (diseño técnico del REQ):** imagen `postgres:16-alpine`; `POSTGRES_DB=nerdose`, `POSTGRES_USER=nerdose_owner` y `POSTGRES_PASSWORD` leída de `.env` de la raíz (gitignored); puerto solo en loopback `127.0.0.1:5432:5432`; volumen con nombre `nerdose-pgdata` (persistencia entre reinicios; reconstruir desde cero es `docker compose down -v` explícito); `healthcheck` con `pg_isready`.
- **Riesgo documentado:** en local, `nerdose_owner` es superusuario del contenedor (lo crea `POSTGRES_USER`); en Testcontainers no. Mitigación: las pruebas de permisos (CA-4) corren contra los roles de servicio.
- **Seguridad:** PostgreSQL publicado solo en `127.0.0.1`. `DATABASE_URL_OWNER` solo lo lee el script de migración.

### Tarea 1: `compose.yaml` con PostgreSQL 16 y tests de configuración

**Status:** Completed

#### Descripción

Crear `compose.yaml` en la raíz exactamente como lo define la convención `monorepo-tooling`, y los tests que validan su configuración normalizada por Docker Compose. Cubre CA-1 (PostgreSQL 16 en `127.0.0.1:5432`) y la parte de CA-5 que toca a Compose (sin contraseña literal en el repo).
