**`dataset-format` (custom de `content`), reglas (verbatim):**
- Only `import:banks` and `build:wordlist` may request `*.wikidata.org`, `*.wikipedia.org` or `*.wiktionary.org`, and runtime code never imports them. `api` and `generator` never request those domains.
- Every request sends the `User-Agent` above (`nerdose-content/<dataset_version> (<WIKIMEDIA_CONTACT>)`).
- JSON files are written ordered by `wikidata_id`, 2-space indentation, one item per block (diff-friendly); package tests verify it.
- `import:banks` exits with an error if there are fewer than 500 `approved` `terms` in total (not per category; `TermCategory` is the Devdle set) and prints the counts. `timeline_facts` (REQ-006) is required: `loadDataset()` fails if `timeline_facts.json` is missing; the script exits with `InsufficientTimelineFactsError` if any v1 category has fewer than 100 `approved` facts or fewer than 3 v1 categories exist. `min_sitelinks_timeline` is its own parameter. `manifest.json` carries `counts.timeline_facts { approved, rejected, by_category, by_reason }` and `parameters.timeline { min_sitelinks, min_approved_per_category, min_categories, categories_v1, classes }`. The `--bank=terms|timeline|all` flag (default `all`) limits the run. Fact `rejection_reason` codes: `disputed_date`, `imprecise_date`, `missing_article`, `low_sitelinks`, `missing_note`, `note_year_mismatch`, `excluded`, `duplicate`.
- The exclusion list lives in `packages/content/data/exclusions.txt`.
- `LICENSE-DATA.md` is always present with the CC BY-SA 4.0 and CC0 attribution.
- Items are never curated by hand; sorting is by rule. A wrong text is handled by report, void and `rejected`, and `sync_banks` never revives it.
- The runtime entry `loadDataset()` parses with Zod and throws on invalid input; it makes no network calls.
- Integración con `testing`: schema, ordering, minimum-count and manifest tests; **the script is tested with recorded fixtures, not live requests**.

Formatos de ítem (verbatim): `timeline_facts.json` items have exactly: `wikidata_id`, `label`, `category`, `event_date` (`YYYY-MM-DD`), `date_precision`, `note` (`{es,en}`), `sitelinks`, `status`, `rejection_reason`. `manifest.json`: `dataset_version` (`YYYY.MM.DD`, plus `-N` when several are generated the same day), `generated_at` (ISO 8601), `min_sitelinks`, counts per bank and category, and the parameters used.

**`content-sync` (custom), lo que toca a esta story:** `api` y `generator` nunca consultan Wikimedia; el dataset se valida con Zod al cargar (un archivo inválido hace fallar `sync_banks`); los archivos quedan ordenados por `wikidata_id` con 2 espacios. Desplegar un dataset nuevo = commit + deploy.

### ADRs Relevantes

**ADR-016: Bancos de contenido como dataset versionado, sin Wikimedia en producción**
- **Decisión:** el contenido de los bancos se importa offline con `import:banks` (Wikidata SPARQL según el mapeo clase → categoría, primer párrafo de Wikipedia por `page/summary` en es y en, reglas de aceptación C-50/C-51), se versiona en `packages/content/data/` y el `generator` lo carga con `sync_banks`.
- **Reglas de Implementación (verbatim):**
  - `api` y `generator` MUST NOT hacer requests a dominios de Wikimedia (`*.wikidata.org`, `*.wikipedia.org`, `*.wiktionary.org`). Solo los scripts `import:banks` y `build:wordlist` pueden hacerlo, y MUST NOT importarse desde código de runtime.
  - Los scripts MUST mandar `User-Agent: nerdose-content/<dataset_version> (<WIKIMEDIA_CONTACT>)`. `WIKIMEDIA_CONTACT` es una variable de entorno de desarrollo.
  - Cada ítem de `terms.json` MUST tener exactamente: `wikidata_id`, `term`, `category`, `definition` (`{es,en}`), `summary` (`{es,en}`), `sitelinks`, `status` (`approved`|`rejected`), `rejection_reason` (string o `null`).
  - Cada ítem de `timeline_facts.json` MUST tener exactamente: `wikidata_id`, `label`, `category`, `event_date` (`YYYY-MM-DD`), `date_precision`, `note` (`{es,en}`), `sitelinks`, `status`, `rejection_reason`.
  - Los JSON MUST escribirse ordenados por `wikidata_id`, con indentación de 2 espacios y un ítem por bloque, para que los diffs sean legibles.
  - `manifest.json` MUST incluir `dataset_version` con el formato `YYYY.MM.DD` (más `-N` si hay varias el mismo día), `generated_at` (ISO 8601) y `min_sitelinks`.
  - `import:banks` MUST terminar con error si hay menos de 500 `terms` `approved` o menos de 100 `timeline_facts` `approved` en alguna categoría v1 (`programming_languages`, `frameworks`, `companies`, `operating_systems`, `hardware`, `video_games`).
  - `sync_banks` MUST hacer `INSERT … ON CONFLICT (wikidata_id) DO UPDATE` con estas reglas: si el ítem en la base está `rejected`, MUST NOT cambiarlo; si en la base está `approved` y en el dataset `rejected`, pasa a `rejected` con su `rejection_reason`; MUST NOT tocar `last_used_devdle`, `last_used_grep` ni `last_used`; MUST NOT borrar ítems que están en la base y no en el dataset.
  - `sync_banks` MUST registrar en `job_runs` (`job = 'sync_banks'`) un `summary` con `dataset_version`, `inserted`, `updated`, `unchanged` y `kept_rejected`.
  - `packages/games/devdle/wordlist/words.txt` MUST tener una palabra por línea, en mayúsculas, A–Z, 4–12 letras, ordenadas alfabéticamente y sin duplicados.
  - `packages/content/` MUST incluir `LICENSE-DATA.md` con la atribución CC BY-SA 4.0 de los textos derivados de Wikipedia y CC0 de Wikidata.
- **Riesgo registrado:** "el dataset inicial no llega a los mínimos por poca cobertura en español. Mitigación: el script falla y muestra los conteos. Se ajustan el mínimo de `sitelinks` o el mapeo de clases antes del lanzamiento (pregunta abierta del PRD)."

**ADR-003 (monorepo):** `content` depende de `core`, nunca al revés. `scripts/` nunca se importa desde otros paquetes.

### Decisiones de diseño de REQ-006 aplicables (verbatim)

**3. Categorías v1 = categorías con clases mapeadas.** La lista v1 vive en el mapeo `TIMELINE_CLASSES` del script (clase de Wikidata → categoría + propiedad de fecha) y queda registrada en `manifest.parameters.timeline.categories_v1`. Una categoría diferida se quita del mapeo, no aparece en el dataset y, por lo tanto, nunca tiene hechos `approved` en la base: ni el generador ni la `api` necesitan conocer la lista v1. El script exige ≥ 100 `approved` por categoría v1 y ≥ 3 categorías v1 (supuesto del request); si una categoría no llega, el error lo dice y la decisión de diferirla (quitarla del mapeo y documentarla en `dataset-format` y en el PRD, como `internet` y `general_history`) es parte de la story del importador.

**4. Reglas del importador de hechos (C-51; CA 19–22).** Propiedad de fecha por clase: `P571` (inception) para lenguajes, frameworks, empresas y sistemas operativos; `P577` (publication date) para videojuegos y hardware, con fallback a `P571` si el mapeo lo declara. La consulta SPARQL trae cada valor con `wikibase:timeValue`, `wikibase:timePrecision` y `wikibase:rank` (más `label_en`/`mul`, `sitelinks` y artículos ES/EN, reutilizando `ITEM_FIELDS`). Reglas, en orden, con `rejection_reason` como código estable:
- `disputed_date` ("fecha discutida"): sin valor `preferred` y más de un valor `normal` distinto a la precisión común, o valores con rango de incertidumbre (`before`/`after` ≠ 0). Un único valor `preferred` gana sobre los `normal`; los `deprecated` se ignoran.
- `imprecise_date`: precisión menor que año (`timePrecision < 9`) o año fuera de 1800–año actual.
- `missing_article`: sin artículo de Wikipedia en ES o EN.
- `low_sitelinks`: `sitelinks < min_sitelinks_timeline`.
- `missing_note` / `note_year_mismatch`: la nota es la primera oración del summary de Wikipedia (≤ 240 caracteres) en cada idioma; si menciona un año (`\b(1[89]\d{2}|20\d{2})\b`) distinto del de `event_date`, se usa la descripción corta de Wikidata en ese idioma; si tampoco existe o también contradice, se rechaza (`missing_note` si falta, `note_year_mismatch` si contradice).
- `excluded`, `duplicate`: misma semántica que en `terms` (lista de exclusión compartida y `wikidata_id` repetido entre clases; gana la primera categoría del mapeo).
- `event_date` se normaliza según la precisión: `year` → `YYYY-01-01`, `month` → `YYYY-MM-01`, `day` → fecha completa (C-51: nunca se inventa mes o día; la precisión dice qué mostrar). `label` = etiqueta en inglés (o `mul`), sin traducir.
- `min_sitelinks_timeline` es un parámetro propio (no se comparte con `terms`): flag `--min-sitelinks-timeline`, se calibra en la primera corrida y queda en el manifiesto; el script imprime, como ya hace con `terms`, el valor más alto que mantiene ≥ 100 por categoría.

**5. Dataset, manifiesto y escritura (parte de esta story).** […] `writeDataset` escribe los tres archivos con el mismo patrón `.tmp` + `rename`, y solo después de validar los mínimos: si una categoría v1 queda con 80, falla con `InsufficientTimelineFactsError` (categoría y cantidad) y no escribe nada (CA 22). Flag `--bank=terms|timeline|all` (default `all`): con `timeline`, `terms.json` se relee y revalida sin consultar Wikimedia y sus conteos se copian al manifiesto, para no tocar el banco de términos al calibrar los hechos.

**Supuesto [Categorías v1] del REQ:** v1 usa las categorías que, tras la primera corrida, alcancen el mínimo de 100 hechos `approved`. Las que no lo alcancen se difieren (se documentan y se quitan de la lista de v1, como ya pasa con `internet` y `general_history`) en lugar de bajar el umbral o forzar contenido débil. Se exige un mínimo de 3 categorías en v1; con menos, el request se considera bloqueado y se escala.

**Riesgos del REQ:** cobertura insuficiente (mitigación: calibrar `min_sitelinks_timeline` con el valor sugerido y sumar clases adicionales por categoría al mapeo); reglas de fecha laxas (mitigación: `disputed_date` estricto, precisión guardada tal cual, tests con fixtures grabados de casos reales).

### Puntos de Integración

**Wikidata SPARQL (WDQS)** — solo desde el script.
- Endpoint: `GET https://query.wikidata.org/sparql?query=<urlencoded>&format=json`, header `Accept: application/sparql-results+json` (ya lo hace `fetchClassCandidates`).
- Respuesta: `{ head: { vars: [...] }, results: { bindings: [ { var: { type, value, datatype?, "xml:lang"? } } ] } }`.
- Fechas con rango y precisión: patrón de statements completos (no `wdt:`, que solo devuelve el mejor rango):
  ```sparql
  ?item p:P571 ?st .
  ?st psv:P571 ?v ; wikibase:rank ?rank .
  ?v wikibase:timeValue ?time ; wikibase:timePrecision ?precision .
  ```
  - `?time`: `xsd:dateTime`, p. ej. `"2014-06-01T00:00:00Z"`; años BCE con signo `-`.
  - `?precision`: entero; `9` = año, `10` = mes, `11` = día (`< 9` = década o menos; `> 11` = hora o más fino).
  - `?rank`: URI `http://wikiba.se/ontology#PreferredRank` | `#NormalRank` | `#DeprecatedRank`.
- **Hallazgo — `before`/`after` (NOT DOCUMENTED - needs verification):** la decisión 4 define la incertidumbre como "`before`/`after` ≠ 0", pero el formato RDF de WDQS para valores de tiempo expone `timeValue`, `timePrecision`, `timeTimezone` y `timeCalendarModel`; `before`/`after` **no** se exponen en SPARQL. Este plan lo resuelve (ver "Decisiones de este plan", 3) con los calificadores que Wikidata usa para la incertidumbre: `pq:P1319` (earliest date), `pq:P1326` (latest date) y `pq:P1480` (sourcing circumstances) = `wd:Q5727902` (circa). El implementador **verifica** en la Tarea 2, con una consulta real, que esos calificadores existan con ese significado y que `before`/`after` efectivamente no estén disponibles; si alguno estuviera, se usa además.
- Límites: el cliente existente pausa 250 ms entre requests no cacheados y reintenta 429/5xx/red hasta 5 veces (`Retry-After` o 1 s × 2^n); `WikimediaRequestError` al agotar.

**Wikipedia REST `page/summary`** — solo desde el script.
- `GET https://{es|en}.wikipedia.org/api/rest_v1/page/summary/{title}` (título con `_` y `encodeURIComponent`, ya en `summaryUrl`).
- Respuesta usada: `{ type, title, extract }`. `fetchSummary` devuelve `null` en 404 (cacheable), `type === 'disambiguation'` o `extract` vacío.

**Licencias:** textos de Wikipedia CC BY-SA 4.0 (la `note` sale del `extract` o, en fallback, de la descripción de Wikidata, CC0); `label`, `event_date`, `date_precision`, `sitelinks` de Wikidata (CC0).

**Consumidores internos del dataset** (no se modifican, solo regresión): `apps/generator` (`loadDataset()` en `sync_banks`, tests con el dataset por defecto en `process.test.ts`) y `packages/games/grep-grid` (tests con el dataset por defecto, solo `terms`).

### Decisiones de este plan

Puntos que la story y el REQ dejan abiertos o que choquen con el código; se fijan acá para que el implementador no improvise.

1. **Dónde vive cada cosa (archivos de la story).** `TIMELINE_CLASSES` y el tipo `TimelineClass` en `classes.ts` / `wikidata.ts`; consulta y parseo de hechos en `wikidata.ts`; reglas de fecha, de nota y `evaluateFacts` en `rules.ts`; parámetros, mínimos y `InsufficientTimelineFactsError` en `manifest.ts`; orquestación en `run.ts`; `write.ts` no cambia (ya escribe los tres archivos con `.tmp` + `rename` y valida con Zod).
2. **Consulta por clase con todas las fechas del ítem.** Una fila por (ítem, statement de fecha). La consulta exige al menos un statement de la propiedad (o de la de fallback): un ítem sin fecha no es candidato ni aparece en el dataset (no hay código de rechazo para "sin fecha" y la decisión 4 no lo pide). El parser agrupa filas por ítem (`dates: DateStatement[]`).
3. **Incertidumbre (`disputed_date`).** Un statement no `deprecated` es incierto si tiene calificador `P1319` o `P1326`, o `P1480 = Q5727902` (circa). Ver hallazgo en Puntos de Integración. Cualquier statement incierto entre los considerados → `disputed_date`.
4. **"Distinto a la precisión común".** Se comparan los valores **de a pares** a la menor de sus dos precisiones (año si ≤ 9, año-mes si 10, fecha completa si ≥ 11). Si algún par difiere → `disputed_date`. Si ninguno difiere, gana el valor más preciso (todos son compatibles con él; no se inventa nada porque ese valor está en Wikidata). Ej.: `2009` (año) + `2009-11-10` (día) → `2009-11-10`; `2009-11` + `2009-12` → `disputed_date`. Se aplica igual entre varios `preferred` (si hay más de uno) que entre los `normal` cuando no hay `preferred`.
5. **Fallback de propiedad.** Si la clase declara `fallbackProperty`, se usan los statements de `dateProperty` cuando haya al menos uno no `deprecated`; si no, los de `fallbackProperty`. Nunca se mezclan las dos propiedades.
6. **Sin fecha utilizable** (todos `deprecated`, o `time` no parseable, o año BCE) → `imprecise_date`.
7. **Precisión > 11** (hora, minuto…) se trata como `day` (se toma `YYYY-MM-DD`). Precisión 10 con mes `00` → `imprecise_date`; precisión 11 con día `00` → se degrada a `month` (y si además el mes es `00`, a `year`). Nunca se inventa mes ni día.
8. **Primera oración y 240 caracteres.** `firstSentence(text)`: hasta el primer `.`, `!` o `?` seguido de espacio y mayúscula (o fin de texto), `trim`. Si supera 240 caracteres se corta en el último espacio antes del carácter 240 y se agrega `…` (largo total ≤ 240). Un `extract` vacío → nota no disponible (se intenta la descripción).
9. **Precedencia entre idiomas para la nota.** Se resuelve cada idioma por separado (`summary` → `description`). Si en algún idioma la nota "falta" (summary inutilizable y sin descripción) → `missing_note`; si no, pero en algún idioma "contradice" (summary y descripción mencionan otro año) → `note_year_mismatch`.
10. **`missing_article`.** Sin `article_es` o `article_en` (sitelink) **o** `fetchSummary` devolvió `null` en algún idioma (404, desambiguación o `extract` vacío) — igual que en `terms`.
11. **`duplicate` para hechos.** El `wikidata_id` repetido entre clases se fusiona antes de evaluar (gana la primera clase del mapeo, como en `terms`; no genera ítem extra porque `timeline_facts.json` exige `wikidata_id` único). `duplicate` se aplica, como en `terms`, a ítems distintos con el mismo `label` (comparado con `normalizeTerm`) entre los que sobreviven a todas las reglas anteriores: gana el de más `sitelinks` y, a igualdad, el Qid numérico menor. Dos hechos con el mismo nombre en un desafío serían ambiguos.
12. **Ítems `rejected`: fecha y nota.** Todo ítem del archivo necesita `event_date` (`YYYY-MM-DD`) y `date_precision` válidos por schema. Un rechazado lleva la mejor fecha disponible normalizada (el valor más preciso entre los considerados, con precisión `< 9` llevada a `year`); si no hay ninguna utilizable, `event_date: '0000-01-01'`, `date_precision: 'year'`. `note` lleva lo calculado hasta la regla que lo rechazó, `''` si no se llegó a calcular.
13. **Summaries solo para candidatos que pasan las reglas baratas** (`disputed_date`, `imprecise_date`, artículos presentes), sin filtrar por sitelinks, para que la calibración (`highestMinSitelinksTimeline`) pueda evaluar con `minSitelinks: 0` (mismo patrón que `precheck` de `terms`).
14. **`--bank=timeline`** relee y valida `terms.json` (`termsFileSchema`; inválido → `DatasetError('terms.json')` antes de cualquier request), recalcula `counts.terms` desde ese archivo y copia de `previous.parameters` los parámetros de `terms` (`min_sitelinks`, `min_approved_terms`, `classes`) y `previous.min_sitelinks`. Sin `manifest.json` previo válido → `DatasetError('manifest.json', …)` (no hay de dónde copiar los parámetros de `terms`). No se valida el mínimo de 500 `terms` (no se importan).
15. **`--bank=terms`** mantiene el comportamiento actual (puente de S-025): re-lee hechos y `parameters.timeline` y no valida mínimos de hechos. **`--bank=all`** (default) importa los dos bancos y valida los dos mínimos **antes** de escribir nada.
16. **Mínimos parametrizables solo para tests.** `runImport` acepta `minApprovedPerCategory` (default 100) y `minCategories` (default 3), igual que hoy acepta `minApproved` para `terms`; el CLI nunca los expone. El manifiesto registra los valores usados.
17. **`categories_v1`** = categorías presentes en `TIMELINE_CLASSES`, en el orden de `TIMELINE_CATEGORIES`. `parameters.timeline.classes` = `TIMELINE_CLASSES` mapeado a `{ wikidata_class, category, date_property }` (`date_property` = la propiedad principal; el schema no admite fallback).
18. **`min_sitelinks_timeline` por defecto** = `previous.parameters.timeline.min_sitelinks` si existe; si no, `DEFAULT_TIMELINE_PARAMETERS.min_sitelinks` (10). El flag gana.
19. **QIDs del mapeo (NOT DOCUMENTED - needs verification).** La documentación no fija qué clases de Wikidata usar por categoría. El implementador elige y **verifica contra Wikidata** cada QID (etiqueta y que la clase traiga candidatos con la propiedad de fecha), dejando el comentario `// QIDs verificados contra Wikidata …` como en `TERM_CLASSES`. Punto de partida a verificar (no asumir): lenguajes de programación `Q9143` (P571); frameworks de software / frameworks web (P571); empresas de tecnología / de software / de hardware (P571); sistemas operativos (P571); consolas de videojuegos, computadoras personales/domésticas, microprocesadores (P577 con fallback P571); videojuegos (P577 con fallback P571). Para `video_games`, la clase es enorme: el piso de sitelinks de la consulta (`QUERY_SITELINKS_FLOOR`) y `QUERY_LIMIT` acotan el volumen; si la consulta da timeout en WDQS, se sube el piso solo para esa clase (campo opcional `queryFloor` en `TimelineClass`), dejándolo registrado.
20. **Categorías diferidas.** Se deciden con la primera corrida real (Tarea 7): una categoría que no llega a 100 `approved` con el mejor `min_sitelinks_timeline` posible y tras probar clases adicionales se quita de `TIMELINE_CLASSES` y se documenta. Con menos de 3 categorías v1 el trabajo **se detiene y se escala** (no se commitea un dataset que no pasa los mínimos).
