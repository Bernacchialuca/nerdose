## Referencia de la Story

- **Story:** [S-005](../stories/S-005.shells-web-admin-proxy-dev.md)
- **Servicio:** web
- **Resumen:** Crea `apps/web`, la SPA de jugadores (React 19 + Vite) que arranca en `:5173` con `pnpm dev`, reenvía `/api` a la `api` en `http://localhost:3000` (mismo origen, sin CORS) y muestra un shell vacío con los tokens de `@nerdose/ui` (fondo `#0A0C0F`, JetBrains Mono self-hosted, acento `#3DDC84`). >
> Este plan cubre la parte de `web` de CA-1 (que `pnpm dev` levante `web` en `:5173`), CA-2, CA-5 y la mitad de `web` de CA-7.
>
> **Rutas:** todas las rutas de "Files to Create/Modify" son relativas a `apps/web/` salvo que se indique `(raíz)`.
>
> **Dependencias:** S-001, S-002 y S-004 están `Completed`. S-003 figura con `status: Ready` en su frontmatter, pero su implementación ya está mergeada en `dev` (commits `0c0bea6` y `cf6af5a` "mark as completed"): `GET /api/health` y `GET /api/admin/health` responden en `:3000`. [Auto] Se continúa.
>
> **Código reutilizable:** no existe `docs/reusable-code/web/index.md` (la app es nueva). Se reutiliza lo documentado de `@nerdose/ui` (`tokens.css`, `cn()`). Al terminar la story conviene correr `/service-update-reusable-code` para `web`.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
- Los tests MUST usar Vitest; los e2e, Playwright.

> Nota: los archivos de configuración (`vite.config.ts`, `vitest.config.ts`) son TS. No crear `.js` en `apps/web` (lo verifica `test/repo-hygiene.test.ts` de la raíz con `findJsSourceFiles`).

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
- Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
- Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
- `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

> Estos límites ya los hace cumplir `eslint.config.js` de la raíz para `apps/web/**` (`no-restricted-imports` con `noDb`, `noNotify`, `frontendsOnlyClient`, `crossApp('web')`), junto con `eslint-plugin-jsx-a11y` y `eslint-plugin-react-hooks` sobre `apps/web/**/*.{ts,tsx}`. No hay que tocar la config de ESLint.

#### ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores (reglas aplicables, verbatim)

- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`, con `code` del catálogo de arriba (exportado como enum desde `@nerdose/core`).
- **Rutas sin versión:** `/api/*` y `/api/admin/*`.

```ts
// src/lib/api-client.ts
export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,       // error.code from the catalog in @nerdose/core
    message: string,             // error.message, already in the response locale
    readonly retryAfter?: number,
  ) { super(message); }
}

// Optional app-level hooks, registered once at startup (see error-handling and, in admin, auth).
type Hooks = { getHeaders?: () => Record<string, string>; onError?: (err: ApiError) => void };
let hooks: Hooks = {};
export const configureApi = (h: Hooks) => { hooks = h; };

export async function api<T>(path: string, init: RequestInit & { json?: unknown } = {}): Promise<T> {
  const { json, headers, ...rest } = init;
  const res = await fetch(path, {
    ...rest,
    headers: {
      Accept: 'application/json',
      ...(json !== undefined && { 'Content-Type': 'application/json' }),
      ...hooks.getHeaders?.(),
      ...headers,
    },
    body: json !== undefined ? JSON.stringify(json) : rest.body,
  });
  if (res.ok) return (res.status === 204 ? undefined : await res.json()) as T;
  const body = await res.json().catch(() => null);
  const err = new ApiError(
    res.status,
    body?.error?.code ?? 'internal_error',
    body?.error?.message ?? res.statusText,
    Number(res.headers.get('Retry-After')) || undefined,
  );
  hooks.onError?.(err);
  throw err;
}
```

```ts
// src/app/query-client.ts
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      refetchOnWindowFocus: false,
      retry: (count, err) => !(err instanceof ApiError && err.status < 500) && count < 2,
    },
    mutations: { retry: false },
  },
});
```

- URLs relativas (`/api/...`): sin hosts hardcodeados, sin CORS, sin `VITE_API_URL`. No se setea `credentials`.
- `fetch` solo desde `lib/api-client.ts`. Respuestas con claves intactas (`snake_case`).
- Datos de servidor solo en TanStack Query; nunca copiados a `useState` ni a un contexto.
- Branch por `ApiError.code`, nunca por `message` ni solo por status.
- `body?.error?.code` sobre un `unknown`: tipar el `body` parseado como `{ error?: { code?: string; message?: string } } | null` para no usar `any` (TS estricto).

### Contexto de Flujos

La story no referencia flujos ("Ninguno. Los 12 flujos de `docs/flows/` describen funcionalidad de negocio que este request no implementa"). El escenario relevante es el **Escenario 2 de REQ-001** (Health por el origen de cada SPA), copiado:

1. **[Vite dev server de `web`]** El proxy reenvía la request sin cambios a `http://localhost:3000` con el mismo path.
2. **[`api`]** `GET /api/health`, sin autenticación. `deps.health.check()` ejecuta `SELECT 1` con un timeout de 2 s. Si responde: `200 { "status": "ok", "db": "ok" }`. Si falla o vence: `503 { "status": "degraded", "db": "error" }`.
3. **[Vite proxy]** Devuelve la respuesta al navegador o al cliente HTTP en el mismo origen.

**Outcome:** `web` llega a la `api` en su propio origen, sin CORS. Esto valida el enrutamiento de mismo origen del que depende la cookie `nd_pid`.

Y del **Escenario 1** (arranque local), el paso de `web`: "Vite dev server en `:5173`, con proxy `'/api' → 'http://localhost:3000'`". Puertos fijos de la story: `api` 3000, `web` 5173, `admin` 5174.

### Task 4: Test de integración del proxy de mismo origen

**Status:** Completed

#### Description
Probar de forma automática, sin depender de la `api` real ni del puerto 3000, que la regla `/api` de `vite.config.ts` reenvía las requests con el path intacto y devuelve la respuesta tal cual (incluido el `503` del health degradado). Es la evidencia automatizada de CA-2; la verificación contra la `api` real queda en Task 5.

#### Acceptance Criteria
1. `test/vite-proxy.test.ts` (entorno `node`) levanta `STUB` (`node:http` en `127.0.0.1:0`) y un dev server de Vite (`createServer` de `vite`) en `port: 0` con la regla real de `viteConfig.server.proxy['/api']`, reemplazando **solo** el `target` por la URL de `STUB` (ver valores de referencia de Test Scenarios).
2. Cubre TS-4, TS-5, TS-6 y TS-7.
3. Cierra Vite (`server.close()`) y `STUB` en `afterAll`/`afterEach`; no deja handles abiertos (el test termina sin colgarse).
4. El test usa la `root` de `apps/web` para que `GET /` sirva el `index.html` real (TS-7).

#### Technical Details

**Architectural Context References:**
- `data-fetching` → "Same origin and dev proxy".
- Contexto de Flujos → Escenario 2 de REQ-001 (el proxy reenvía sin cambios, mismo path).
- Contexto de API → schema `Health` (`200` / `503`).

**Files to Create/Modify:**
- `test/vite-proxy.test.ts`
- `vitest.config.ts` (solo si hace falta: `include` ya cubre `test/**/*.test.ts` desde Task 1; subir `testTimeout`/`hookTimeout` del archivo si el arranque de Vite tarda)

**Implementation Notes:**
- Marcar el archivo con `// @vitest-environment node`: en jsdom, `createServer` y `node:http` no se comportan como en Node.
- `configFile: false` + `plugins: []`: el test prueba el proxy, no React/Tailwind; así arranca rápido y no procesa CSS. La regla de proxy se toma del `vite.config.ts` real importado, por eso un cambio de path o un `rewrite` en la config real rompe el test.
- Obtener la URL con `server.resolvedUrls?.local[0]` o `server.httpServer?.address()` tras `await server.listen()`.
- `fetch` de Node 24 es global; no hace falta librería.
