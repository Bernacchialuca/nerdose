## Referencia de la Story

- **Story:** [S-001](../stories/S-001.monorepo-base-core-ui.md)

## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript con `strict: true` (ADR-002). Node.js 24 LTS, `engines.node` `">=24 <25"`.
- **Gestor de paquetes:** pnpm (único permitido), versión fijada en `packageManager` del `package.json` raíz.
- **Orquestador de tareas:** Turborepo (`turbo.json`).
- **Lint:** ESLint con flat config (`eslint.config.js`) + `typescript-eslint`; `eslint-plugin-react-hooks` y `eslint-plugin-jsx-a11y` para el código React.
- **Tests:** Vitest (configuración raíz con `projects`).
- **Versiones:** la documentación no fija versiones de `turbo`, `typescript`, `eslint`, `typescript-eslint`, `vitest` ni de los plugins. **NO DOCUMENTADO:** usar la versión estable vigente al implementar y dejarla fijada por `pnpm-lock.yaml`.

> **Precondición del entorno (verificar antes de implementar):** en la máquina de desarrollo actual `node --version` da `v22.14.0` y `pnpm --version` da `11.6.0`. La story requiere Node 24 (`engines.node` `">=24 <25"`). Con Node 22, pnpm avisa (o falla, según la configuración de `engine-strict`) al instalar. Instalar Node 24 antes de empezar, o el CA-1 no se puede validar en las condiciones de la story.

### Arquitectura del Servicio

Del `overview.md` de `workspace`:

- **Propósito:** raíz del monorepo de nerdose. Reúne todo lo que no pertenece a una app ni a un paquete en particular: `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`, la configuración de ESLint (flat config) con los límites de importación de ADR-003, la configuración raíz de Vitest, `compose.yaml` (PostgreSQL 16 local), los `.env.example` de la raíz, `.gitignore` y el README de arranque.
- **Tipo:** library en node, no desplegable. Es la estructura sobre la que se construyen `api`, `generator`, `web`, `admin` y los paquetes compartidos.
- **Módulos:**
  - **tooling** (este plan): workspaces, tareas de Turborepo (`dev`, `build`, `lint`, `typecheck`, `test`), base de TypeScript, ESLint con `no-restricted-imports` y Vitest raíz.
  - **local-env**: `compose.yaml` con PostgreSQL 16, `.env.example`, `.gitignore` y README de arranque. En este plan solo entra `.gitignore`.
- **Paquetes internos sin build (JIT):** exportan su TypeScript fuente. El build para producción queda diferido con el hosting.
- **Fuera de alcance:** despliegue, CI/CD, hosting, DNS/TLS y secretos de producción.

**Estructura objetivo de la raíz** (convención `monorepo-tooling`):

> "Exact globs adapt to the final folder layout; the **set of boundaries** is the contract." (convención `monorepo-tooling`)

**Puertos en desarrollo** (referencia para S-005, no se implementa acá): `api` 3000, `web` 5173, `admin` 5174.

**Cómo se usa** (convención):
- Agregar un workspace creando su carpeta bajo `apps/`, `packages/` o `packages/games/`; tiene que definir los scripts `lint`, `typecheck` y `test` para que Turborepo lo tome.
- Correr un solo paquete: `pnpm --filter @nerdose/<name> <script>`.
- Copiar cada `.env.example` a `.env.local` (y el de la raíz a `.env` para Compose). Los valores reales nunca se versionan.

**Reglas de la convención `monorepo-tooling` (verbatim):**

- pnpm is the only package manager. No `npm`, `yarn` or `bun` lockfiles or commands.
- `engines.node` is `">=24 <25"` and `packageManager` is pinned in the root `package.json`.
- Tasks (`build`, `dev`, `lint`, `typecheck`, `test`) are orchestrated by Turborepo; `dev` is `persistent` and uncached.
- Internal packages are named `@nerdose/<name>` (`@nerdose/game-<game_id>` for games) and use `workspace:*` for internal dependencies.
- The ADR-003 import boundaries are enforced by ESLint (`no-restricted-imports`) and a violation fails `pnpm lint`: apps never import from other apps; `web` and `admin` never import `@nerdose/db` or `@nerdose/core/notify`; `api` imports only `./definition` of games, frontends only `./client`, `generator` only `./generator` (and `./definition`); `./definition` and `./client` never import `@nerdose/polyglot` or `node:child_process`; `@nerdose/core` entry `.` never imports `node:*` or `./notify`.
- No `.js` source files in `apps/` or `packages/` except tool configuration.
- `.gitignore` excludes `.env`, `.env.local`, `.env.test`, `node_modules`, build output and Turborepo cache. Only `.env.example` files are committed, with empty values and a comment per variable.
- `compose.yaml` publishes PostgreSQL only on `127.0.0.1` and keeps data in the named volume `nerdose-pgdata`. Rebuilding from scratch is an explicit `docker compose down -v`.
- No secrets in the repository: `.env.example` files never contain real values.
- Deployment, CI/CD, hosting and production secrets are out of scope until they are defined.

**Integración con otras convenciones** (verbatim):
- **env-config**: each service declares its variables in its own `env.ts` and keeps `.env.example` in sync; the root `.env.example` only holds Compose variables.
- **testing**: the root Vitest config runs each package's tests; integration tests need Docker (Testcontainers) and fail with a clear message without a daemon.
- **orm**: `db:migrate` is the single migration command and reads `DATABASE_URL_OWNER`.
- **accessibility** (web/admin): `eslint-plugin-jsx-a11y` is wired here.
- **game-package**: the three entries of each game are protected by the boundaries above.

### Convenciones de Código (`_base` de node, catálogo)

- TypeScript obligatorio; `strict: true` y `noUncheckedIndexedAccess: true`; `target: ES2022` o superior. Sin `any` salvo en límites con librerías sin tipos (comentando el motivo).
- **Nombres:** archivos y carpetas en `kebab-case`; clases y tipos en `PascalCase` (sin prefijo `I`); funciones y variables en `camelCase`; constantes globales en `SCREAMING_SNAKE_CASE`.
- **Imports:** orden 1) librerías externas (`node:*`, npm), 2) imports absolutos del proyecto, 3) relativos del mismo módulo; grupos separados por una línea en blanco.
- **Async:** `async/await`; ninguna promesa sin manejar.
- **Comentarios:** por defecto ninguno; solo el *por qué* cuando no es obvio. Sin `// TODO` sin issue asociado.

### ADRs Relevantes

#### ADR-003: Monorepo y paquetes compartidos

- **Decisión:** monorepo con pnpm workspaces y Turborepo; `apps/{web,admin,api,generator}` y `packages/{core,db,ui,polyglot,content,games/*}`. Cada paquete de juego expone tres entradas: `definition` (la usa la `api`), `client` (`web` y `admin`) y `generator` (el `generator`).
- **Reglas de Implementación (verbatim):**
  - El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
  - Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
  - Los paquetes internos MUST llamarse `@nerdose/<nombre>` (`@nerdose/core`, `@nerdose/db`, `@nerdose/ui`, `@nerdose/polyglot`, `@nerdose/content`, `@nerdose/game-<game_id>`).
  - Cada paquete de juego MUST exponer por `exports` tres entradas: `./definition`, `./client` y `./generator`.
  - `apps/api` MUST importar solo `./definition` de cada juego. `apps/web` y `apps/admin` MUST importar solo `./client`. `apps/generator` MUST importar solo `./generator` (y `./definition` si lo necesita para validar).
  - `./definition` y `./client` MUST NOT importar `polyglot`, `node:child_process` ni nada que ejecute código.
  - `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
  - `@nerdose/core` MUST exponer dos entradas por `exports`: `.` (isomorfa: corre en Node y en el navegador, sin dependencias de Node) y `./notify` (solo Node, con nodemailer). La entrada `.` MUST NOT importar `./notify` ni `node:*`.
  - `@nerdose/db` MUST ser el único lugar con el schema Drizzle y las migraciones.
  - MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.
- **Riesgo documentado:** un `client` importa por error la solución o el `generator`, y el bundle filtra lógica o datos sensibles. **Mitigación:** las entradas `exports` separadas, las reglas de importación de arriba y los tests de contrato anti-spoiler.

#### ADR-002: Stack tecnológico

- **Decisión:** TypeScript en todo, con Node.js 24 LTS en el backend; testing con Vitest (unit y contrato) y Playwright (e2e).
- **Reglas de Implementación (verbatim):**
  - Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
  - `api` y `generator` MUST correr en Node.js 24 LTS. `engines.node` MUST ser `">=24 <25"`.
  - El framework HTTP de la `api` MUST ser Hono. MUST NOT usarse Express, Fastify ni NestJS.
  - Todo acceso a la base MUST pasar por Drizzle ORM con el driver postgres.js. SQL crudo solo en migraciones, en las vistas `metrics_*` y donde Drizzle no lo soporte (`LISTEN`, `pg_notify`, `pg_try_advisory_lock`, `FOR UPDATE SKIP LOCKED`).
  - Toda entrada HTTP (body, query, params) MUST validarse con Zod vía `@hono/zod-validator`. Los schemas de jugada MUST importarse del paquete del juego, nunca redefinirse.
  - `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
  - Cada juego MUST cargarse en `web` con `React.lazy` en la ruta `/:game_id`. Shiki MUST cargarse solo en las rutas `big-o` y `bug-hunt`.
  - Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
  - Los textos de UI MUST pasar por i18next con claves en `es` y `en`. Los textos de contenido MUST venir resueltos desde la `api`.
  - El PRNG del `generator` MUST ser `pure-rand` (xoroshiro128+). MUST NOT usarse `Math.random()` en la generación de desafíos.
  - Los tests MUST usar Vitest; los e2e, Playwright.
- **Aplican a este plan:** TypeScript `strict`, sin `.js` de código fuente en `apps/`/`packages/`, `engines.node` `">=24 <25"`, Vitest.

### Decisiones de diseño del REQ-001 que aplican

- **Paquetes internos sin build (just-in-time).** `core`, `db` y `ui` exportan su TypeScript fuente por `exports` (`"."` → `./src/index.ts`). `typecheck` es `tsc --noEmit` en cada paquete.
- **Lint con ESLint (flat config) + typescript-eslint.** Se suma `eslint-plugin-react-hooks` en las SPAs y reglas `no-restricted-imports` que hacen cumplir los límites de ADR-003: `apps/web` y `apps/admin` no importan `@nerdose/db` ni `@nerdose/core/notify`, y ninguna app importa de otra.
- **Seguridad:** `.env.example` lleva valores vacíos; `.env`, `.env.local` y `.env.test` están en `.gitignore`.
- **Riesgo (REQ):** `pnpm test` depende de Docker (Testcontainers) en los paquetes con tests de integración (S-002 en adelante). No afecta los tests de este plan, que no usan base.

### Contrato que este plan ofrece a los demás paquetes

Lo que `core`, `ui` (y luego `db`, apps y juegos) tienen que cumplir para engancharse en la raíz. Se implementa en sus propios planes; acá queda escrito porque lo define la raíz:

| Elemento | Valor |
|---|---|
| `name` | `@nerdose/<nombre>` (`@nerdose/game-<game_id>` para juegos) |
| Dependencias internas | `workspace:*` |
| Script `lint` | `eslint .` (toma el `eslint.config.js` de la raíz) |
| Script `typecheck` | `tsc --noEmit` |
| Script `test` | `vitest run` |
| `tsconfig.json` | `{ "extends": "../../tsconfig.base.json", "include": ["src", "test"] }` (en `packages/games/*`: `../../../tsconfig.base.json`) |
| `vitest.config.ts` | propio de cada paquete; el `vitest.config.ts` raíz lo descubre por glob |

Las herramientas (`eslint`, `typescript`, `vitest`, plugins) se instalan una sola vez como devDependencies de la raíz: la resolución de módulos de Node sube hasta `node_modules` de la raíz, y pnpm expone los binarios de la raíz a los scripts de los paquetes. Si en la práctica un paquete no encuentra un binario, declararlo también en sus devDependencies con el mismo rango.

## Test Scenarios

Convenciones de los escenarios:
- Los escenarios de ESLint (TS-10 a TS-27) se implementan en `test/eslint-boundaries.test.ts` con la API de Node de ESLint: `const eslint = new ESLint({ cwd: REPO_ROOT }); const [result] = await eslint.lintText(code, { filePath });`. `filePath` es una ruta relativa a la raíz que **no necesita existir**: solo decide qué bloques de configuración aplican.
- "Error de límite" significa: `result.messages` contiene un mensaje con `ruleId: 'no-restricted-imports'`, `severity: 2` y `message` que incluye el texto indicado.
- "Sin error de límite" significa: ningún mensaje de `result.messages` tiene `ruleId: 'no-restricted-imports'`.
- `REPO_ROOT` = `fileURLToPath(new URL('..', import.meta.url))` desde `test/`.

- **Trampa de flat config, crítica para TS-20:** cuando dos bloques que aplican al mismo archivo configuran `no-restricted-imports`, el bloque posterior **reemplaza** las opciones del anterior; no se combinan. Si se pone un bloque genérico "entre apps" para `apps/**` y otro específico para `apps/web/**`, uno de los dos límites desaparece en silencio. Armar **un único** `no-restricted-imports` por app (o por grupo `web`+`admin`), componiendo arrays de patrones:
  ```js
  const crossApp = (self) => ({
    group: APPS.filter((app) => app !== self).flatMap((app) => [`**/${app}/src/**`, `**/apps/${app}/**`]),
    message: 'Apps never import from other apps.',
  });
  // apps/web: patterns: [noDb, noNotify, frontendsOnlyClient, crossApp('web')]
  ```
  con `const APPS = ['web', 'admin', 'api', 'generator'];`. Como `web` y `admin` tienen apps "otras" distintas, van en bloques separados que comparten los tres primeros patrones.
- **Por qué no los globs relativos del extracto** (`'../../api/*'`): dependen de la profundidad del archivo y dan falsos positivos con las carpetas `api/` de los módulos de `web` (`src/modules/{module}/api/`, convención `_base` de web), por ejemplo `'../../api/today'` (TS-19). Los patrones `**/<app>/src/**` solo coinciden cuando el import entra al `src/` de otra app. La convención permite adaptar los globs ("the **set of boundaries** is the contract").
