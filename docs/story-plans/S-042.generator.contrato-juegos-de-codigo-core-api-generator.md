## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-042](../stories/S-042.contrato-juegos-de-codigo-core-api-generator.md)
- **Servicio:** generator
- **Resumen:** `generateForDate` hace `await` de `generator.verify(...)`, así un juego de código como Big O puede verificar ejecutando subprocesos. Los generadores síncronos siguen funcionando. Además arma la historia con la ventana `[D - recentDays, D + (aheadDays ?? 0)]` sin la fila de `D`, para que una regeneración o un hueco intermedio vean los desafíos ya aprobados para días posteriores. Todo es genérico sobre el registry, sin ramificar por `game_id` (ADR-006).

> **Alcance de este plan:** solo el servicio `generator` (`apps/generator`). La story también afecta a `core` (`Completed`: `GameGenerator.verify` devuelve `VerificationLog | Promise<VerificationLog>`, `HistorySpec.aheadDays?: number`, `codeLanguage`, `BIG_O_OPTIONS`, `RECIPE_CATEGORIES`), a `games` (`Completed`: Devdle, Grep Grid y Timeline con `codeLanguage: () => null` y tests de `verify` con `await`) y a `api` (`Completed`: `plays.code_language`, preferencia y `MoveResponse.play.code_language`). Este plan cubre:
> - **CA-4** completo.
> - **CA-5** completo.
> - **CA-1** (parte `generator`): los tests del `generator` con Devdle, Grep Grid y Timeline siguen en verde.
> - **CA-2, CA-3 y CA-6:** no aplican al `generator`.
>
> **Rutas:** las rutas de "Archivos a crear/modificar" son relativas a `apps/generator/`, salvo las que dicen `(raíz)`.
>
> **Estado actual del código (verificado al planificar, rama `feature/S-042_*` en `12d9844`):**
> - `pnpm --filter generator typecheck` **falla hoy**: `src/domain/challenge-publishing/generate.ts(103..130)` da `TS2322`/`TS2339`/`TS2345`, porque `const verification = generator.verify(payload, history)` (l. 95) ahora es `VerificationLog | Promise<VerificationLog>` y el código lee `.ok` y `.reason` sin `await`. Es la "consecuencia transitoria" que anotó el plan de `core` (decisión 3). Vitest sigue pasando porque no typechequea, y en runtime los tres `verify` son síncronos.
> - `generate.ts` l. 55-63: `recentChallenges(gameId, addDays(date, -spec.recentDays), addDays(date, -1), payloadSchema)`. Solo mira hacia atrás y no lee `spec.aheadDays`.
> - `challenge-publishing.repository.ts` l. 253-271: `recentChallenges(gameId, from, to, payloadSchema)` filtra `between(date, from, to)` y `status IN ('approved','published','voided')` (`ACTIVE_STATUSES`), ordena por `date` ascendente y parsea cada `payload` con el schema. No tiene forma de excluir una fecha.
> - `@nerdose/core` (`packages/core/src/game-generator.ts`) ya declara `HistorySpec.aheadDays?: number` ("Days after D also read as history (default 0); the row of D is excluded (REQ-009)") y `verify(...): VerificationLog | Promise<VerificationLog>`. `core` no exporta un helper de ventana: el cálculo es del `generator` (plan `core`, decisión 4).

El plan `games` fija esa ausencia con un test.

> - Los tests que fuerzan `verify` (`test/domain/grep-grid-pipeline.test.ts` l. 131, `test/domain/timeline-pipeline.test.ts` l. 128) devuelven un valor síncrono o delegan en el `verify` real. Siguen valiendo con el `await`.

### Decisiones tomadas al planificar (no documentadas en la fuente, a revisar si no convencen)

1. **La ventana la calcula una función pura exportada, `historyWindow(date, spec)`, en `generate.ts`.** Devuelve `{ from: addDays(date, -spec.recentDays), to: addDays(date, spec.aheadDays ?? 0), exclude: date }`. Hay un único camino de código: sin `aheadDays` la ventana es `[D - recentDays, D]` sin `D`, que da exactamente las mismas filas que hoy (`[D - recentDays, D - 1]`). Así "con `aheadDays` ausente el comportamiento es el actual" (CA-5) sale por construcción, sin un `if`. Que sea pura permite tests unitarios sin base, incluido el cruce de año. El default 0 lo aplica el consumidor (plan `core`, decisión 4).
2. **La exclusión de `D` se hace en SQL, con un parámetro opcional `excludeDate` en `recentChallenges`.** La firma pasa a `recentChallenges(gameId, from, to, payloadSchema, excludeDate?: string)`. Con `excludeDate` se agrega `ne(challenges.date, excludeDate)` al `and(...)`. Sin él, el comportamiento es el de hoy. Es compatible con los llamadores y wrappers existentes. Se elige SQL y no un `filter` en `generateForDate` por dos motivos: el repositorio devuelve exactamente la ventana que pide la story ("`recentChallenges` pide `[D - 30, D + 30]` sin la fila de `D`"), y no se parsea el `payload` de la fila vieja de `D` en una regeneración. `generateForDate` **siempre** pasa `exclude` (= `date`).
3. **Estados de la ventana sin cambios:** `approved`, `published` y `voided` (`ACTIVE_STATUSES`, REQ-009 decisión 2). `draft` y `rejected` no cuentan. Un regenerado queda `rejected` y no cuenta. Un `voided` sí cuenta.
4. **`verify` se espera con `await generator.verify(payload, history)` y nada más.** No se agrega timeout, `try/catch` ni conversión de errores en `generateForDate`. El timeout de 10 s es del runner (`code-runner`, ADR-007), y "no compila / timeout → `verification.ok = false`" es responsabilidad del `verify` del juego (flujo `generacion-diaria`, Manejo de Errores). Si la promesa de `verify` rechaza, el error se propaga igual que hoy un `throw` síncrono: `generateForDate` rechaza, el candidato queda `draft` y `runFill` lo loguea y marca la corrida `failed` (flujo, fila "Error de BD en un candidato", mismo manejo genérico de `fillDates`). Hay un test que fija ese comportamiento (TS-15), para que no quede una promesa sin manejar.
5. **Los intentos siguen siendo secuenciales.** El `await` dentro del `for` garantiza que el intento `n + 1` (seed, `insertDraft`) arranca después de que resolvió el `verify` del intento `n`. No se paralelizan candidatos: rompería el orden de `attempt` y la regla de "el primero que pasa" (ADR-007).
6. **Helper de test `withGenerator(entry, overrides)`** en `test/helpers/registry.ts`: devuelve `{ ...entry, generator: { ...entry.generator, ...overrides } }`. Es el patrón que ya usan inline `grep-grid-pipeline.test.ts` y `timeline-pipeline.test.ts` (`{ ...entry, generator: { ...entry.generator, verify } } as typeof entry`), extraído para los tests nuevos de `verify` asíncrono y de `historySpec` con `aheadDays`. Los tests existentes no se reescriben.
7. **Helper de test `devdlePayload(date, category = 'git')`** en `test/helpers/challenges.ts` (nuevo): un payload de Devdle válido para `payloadSchema` (misma forma que el fixture inline de `generate.test.ts` l. 141-148), para sembrar challenges con `makeChallenge` en las pruebas de ventana. `recentChallenges` parsea cada `payload`, así que el `payload: {}` por defecto de `makeChallenge` no sirve.
8. **El "juego de prueba" con `aheadDays` es la entrada de Devdle con `historySpec` reemplazado** (`withGenerator(devdle, { historySpec: { ...spec, recentDays: 30, aheadDays: 30 }, verify: spy })`). No se crea un paquete ni se registra nada en `src/games/registry.ts`. Big O real llega con S-043/S-045.
9. **Ids de test.** Los `it` nuevos llevan el sufijo `(S-042 TS-n)`, como en los planes `core`, `games` y `api` de esta story, para no chocar con los `TS-n` de stories anteriores que ya usan los archivos de test del `generator`.
10. **Hallazgos de documentación de producto (no bloquean, este plan no los edita):**
    - `docs/architectures/generator/conventions/challenge-generation.md` no tiene la sección "Update (REQ-009)" que REQ-009 ("Cambios a documentación técnica") pedía aplicar: `await verify` y ventana `[D - recentDays, D + aheadDays]` sin `D`. El snippet "Pipeline per candidate" sigue mostrando `const log = gen.verify(payload, verifyContext)` sin `await`. (La parte "Big O registrado (`big-o@1`)" es de S-045.)
    - `docs/flows/generacion-diaria.md` paso 3 sigue diciendo "`history`: challenges no `rejected` del juego en la ventana anti-repetición", sin `aheadDays` ni la exclusión de `D`, y no dice que `verify` puede ser asíncrono. Ya lo anotaron los planes `core` (decisión 8) y `games` (decisión 6).

    Quedan anotados para `/product-change-technical-definition`. El catálogo de código reutilizable del `generator` (documentación del servicio) **sí** se actualiza, en la Tarea 3.

## Contexto Arquitectónico

### Stack Tecnológico

- **Lenguaje:** TypeScript con `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`, `module: ESNext`, `moduleResolution: bundler` y `verbatimModuleSyntax: true` (`tsconfig.base.json`, raíz). **Sin** `exactOptionalPropertyTypes`. Alias `@/` → `apps/generator/src/`.
- **Runtime:** Node.js 24 LTS. Worker sin puerto HTTP. Scheduler `croner` `^11.0.0`.
- **Validación:** Zod `^4.6.7`. Variables de entorno con `@t3-oss/env-core` `^0.13.11`.
- **Base de datos:** PostgreSQL 16, Drizzle ORM `^0.45.4` sobre postgres.js. Schema y migraciones en `@nerdose/db`. El `generator` se conecta con el rol `nerdose_generator`.
- **Logs:** Pino `^10.4.0`.
- **Tests:** Vitest con un único contenedor PostgreSQL 16 de Testcontainers (`@testcontainers/postgresql` `^12.2.1`) en `globalSetup`, `fileParallelism: false` y reset por test (`t.reset()` en `beforeEach`).
- **Paquetes del monorepo:** `@nerdose/core`, `@nerdose/db`, `@nerdose/content`, `@nerdose/game-devdle`, `@nerdose/game-grep-grid` y `@nerdose/game-timeline` (`./generator` y `./definition`).
- **Scripts:** `pnpm --filter generator lint | typecheck | test`.

### Arquitectura del Servicio

`generator` (manifest: `type: worker`, `language: node`; módulos `challenge-publishing` y `content-banks`). Worker siempre activo, sin interfaz de red. Mantiene aprobados y verificados los desafíos de los próximos 14 días de cada juego (job `fill`, cada hora en UTC). Atiende los pedidos de regeneración de la `api` (`LISTEN generation_requests` + `FOR UPDATE SKIP LOCKED`). Es el único proceso que inserta en `challenges`, `terms` y `timeline_facts`.

Convenciones activas: `_base`, `logging` (catálogo); `orm`, `validation`, `error-handling`, `env-config`, `testing`, `scheduler-jobs`, `generation-queue`, `challenge-generation`, `code-runner`, `content-sync` (custom).

**Patrones:**
- **Repositorio por módulo** que recibe `Db | Tx` por constructor (`ChallengePublishingRepository`).
- **`generateForDate` recibe dependencias explícitas** (`GenerateDeps = { repo: Pick<...>, env, log, signal }`) y la `entry` del registry. Los tests inyectan entradas con el `generator` modificado.
- **Pipeline por candidato** (`challenge-generation`): seed HMAC → `generate` → `payloadSchema.parse` → `insertDraft` → `verify` → `approve` (con `last_used_*` en la misma transacción) o `reject`. En modo `'regenerate'` el candidato verificado queda `draft` y se devuelve como `candidate`.
- **Eventos de dominio en logs:** `ChallengeGenerated`, `ChallengeApproved`, `ChallengeRejected`, `ChallengeGenerationFailed`. Esta story no cambia los logs.

**Manejo de errores** (convención `error-handling`, extracto que aplica): los repositorios dejan propagar los errores del driver. En `fill`, un error en un hueco se loguea y marca la corrida `failed` sin frenar los demás huecos. `processNextRequest` nunca lanza. Esta story **no agrega códigos de error ni manejo nuevo** (decisión 4).

**Testing** (convención `testing`, reglas que aplican):
- Un solo contenedor compartido, levantado en `globalSetup`. Nunca levantar contenedores por archivo.
- No mockear la base en tests de integración. Solo PostgreSQL 16 real.
- Los tests unitarios son para funciones puras (`historyWindow`, como `fillRange` en `test/domain/fill-range.test.ts` y `addDays` en `test/shared/dates.test.ts`). Si hay I/O, test de integración.
- Las fixtures se insertan con el rol **owner** (`t.owner.db`). El código bajo test usa el rol **`nerdose_generator`** (`t.svc.db`).
- Se afirma sobre contenido (filas concretas, fechas concretas), no sobre conteos globales.
- `describe` nombra la unidad e `it` el escenario. Archivos `*.test.ts` bajo `test/`.
- Sin sleeps de reloj para esperar una condición. (El `setTimeout` corto dentro de un `verify` de prueba simula trabajo asíncrono. No espera ninguna condición.)

### ADRs Relevantes

**ADR-006: Contrato `GameDefinition` y juegos como paquetes enchufables**
- **Decisión:** cada juego es un paquete `packages/games/<game_id>` con tres entradas. Hay un registry en `api`, `web`/`admin` y `generator`. Contrato de la entrada `./generator` (extracto verbatim):
  ```ts
  export interface GameGenerator<Payload> {
    historySpec: { bank: 'terms' | 'timeline_facts' | null; lastUsedField: string; recentDays: number; aheadDays?: number };   // aheadDays default 0 (REQ-009)
    usedBankItems(p: Payload): string[];                       // ids del banco que consume el payload
    generate(input: { date: string; seed: Uint8Array; history: GeneratorHistory }): Payload;
    verify(p: Payload, history: GeneratorHistory): VerificationLog | Promise<VerificationLog>;   // { ok, checks[], reason? }
  }
  // GeneratorHistory = { bankItems (ítems approved con su last_used_*), recentChallenges (no rejected, [D - recentDays, D + aheadDays] sin la fila de D) }
  ```
- **Reglas de Implementación (verbatim):**
  - La `api` MUST guardar `plays.code_language = codeLanguage(state)` al cerrar la Play y, si no es `null`, actualizar `players.preferred_code_language` en la misma transacción, sin ramificar por `game_id` (REQ-009).
  - `generateForDate` MUST hacer `await` de `verify`; los generadores síncronos siguen siendo válidos.
  - Cada juego MUST vivir en `packages/games/<game_id>`, con `game_id` ∈ `devdle | grep-grid | timeline | big-o | bug-hunt`.
  - La entrada `./definition` MUST exportar un objeto que implemente `GameDefinition` de `@nerdose/core`, con todos los métodos de la interfaz.
  - Las rutas de juego de la `api` MUST resolver el juego por el registry. MUST NOT haber `if (game_id === '…')` ni `switch` por juego en `apps/api` ni en el shell de `apps/web`.
  - La `api` MUST NOT serializar `challenges.payload` en ninguna respuesta de jugador. Antes de terminar la Play solo puede responder `toPublic(payload, locale, state?)`; después, `result(payload, state)`.
  - La `api` MUST pasar `state` a `toPublic` solo si la Play está `in_progress` (sin Play o con la Play terminada, `undefined`). Con `state`, `toPublic` MAY revelar únicamente lo que el jugador ya descubrió en esa Play (Grep Grid: `words[].definition` de los `term_id` presentes en `found_words`); MUST NOT revelar nada de lo no descubierto (REQ-005).
  - `Feedback` MUST ir en el locale del jugador (`ctx.locale`), nunca como `{ es, en }` (ADR-015).
  - `toPublic` MUST NOT incluir: la palabra de Devdle, `placements` de Grep Grid, `correct_order`/`event_date`/`fact_id` de Timeline, `answer` de Big O, ni `bug_node_id`/`failing_test`/`fix`/`line_of`/`mutation` de Bug Hunt.
  - Cada juego MUST tener un test de contrato anti-spoiler: se serializa `toPublic(payload)` (sin estado y con estados intermedios, si el juego usa `state`) y toda respuesta pre-resultado, y se verifica que no contienen ningún valor de la solución.
  - `moveSchema` MUST usarse tanto en `web` (antes de enviar) como en la `api` (`@hono/zod-validator`). Si el parse falla, la respuesta es `422 invalid_move`.
  - `share(result, number)` MUST NOT incluir la solución y MUST terminar en `nerdose.dev`.
  - `bankUsage` MUST coincidir con `historySpec` del generator del mismo juego (banco y campo `last_used_*`); un test del paquete lo verifica. Los juegos sin banco declaran `null` (REQ-008).
  - `culprits(p)` MUST devolver solo ítems de banco presentes en el payload; un juego sin banco devuelve `[]` (REQ-007).
  - `Preview` MUST ser de solo lectura: valida `payload` con el schema del juego, traduce con los recursos del propio paquete según `language`, y no hace `fetch`, no usa storage ni estado de partida. `web` MUST NOT montarla (necesita el `payload` completo, que solo devuelve `/api/admin/*`). El admin la monta en ES y EN lado a lado; un juego sin `Preview` cae a la vista genérica del payload (REQ-008).
  - `generate` MUST ser determinista: el mismo `{ date, seed, history }` da el mismo `Payload`. MUST NOT usar `Math.random()` ni la hora actual.
  - `Payload` MUST incluir todos los textos que lee el jugador como `{ es, en }`. `verify` MUST fallar si falta algún idioma.
  - Sumar un juego MUST requerir solo crear su paquete y registrarlo en los tres registries, sin cambiar rutas, tablas ni lógica de rachas.
- **Aplica a esta story:** la regla de `await` de `verify` (CA-4), el contrato `historySpec.aheadDays` con la ventana `[D - recentDays, D + aheadDays]` sin `D` (CA-5), y "sin `if (game_id === …)`": `generateForDate` sigue siendo genérico sobre la `entry`.

**ADR-007: Generator como worker siempre activo y pipeline de generación**
- **Decisión:** worker long-running con croner. `fill` cada hora (`10 * * * *` UTC) para `[today+1 … today+14]`. Seed `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`. Pipeline por candidato: `INSERT challenges (status='draft', ...)` → `verify()` → `approved` + `last_used_*` o `rejected` con la `verification`.
- **Reglas de Implementación (verbatim):**
  - `generator` MUST correr como proceso long-running. MUST NOT depender de cron del sistema ni de un scheduler externo.
  - `fill` MUST definirse con croner y la expresión UTC `"10 * * * *"`. `sync_banks` MUST correr una vez al arrancar, antes de la primera corrida de `fill`. `fill` MUST correr también una vez al arrancar, después de `sync_banks`.
  - Cada job MUST tomar `pg_try_advisory_lock` con su clave (`fill`, `sync_banks`). Si no lo obtiene, MUST salir sin hacer nada.
  - Cada corrida MUST registrarse en `job_runs` (`job`, `status`, `started_at`, `finished_at`, `summary`).
  - Los jobs MUST ser idempotentes: correrlos dos veces seguidas no cambia el resultado.
  - El seed MUST ser `HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}")`, con `date` en formato `YYYY-MM-DD`. `GENERATOR_SECRET` MUST existir solo en el entorno del `generator`.
  - `GENERATION_MAX_ATTEMPTS` MUST valer 20 por defecto y ser configurable por variable de entorno.
  - `fill` MUST generar solo para fechas en `[today+1, today+14]`. MUST NOT generar para `today` ni para fechas pasadas.
  - `challenges.number` MUST calcularse con `core` (`date − LAUNCH_DATE + 1`) al insertar.
  - Un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`.
  - El runner MUST usar `execFile` (nunca `exec` con shell), timeout de 10 000 ms, y MUST correr como usuario no root.
  - Los toolchains MUST ser Node 24, Go ≥ 1.25 y JDK 21.
  - El `generator` MUST NOT hacer requests HTTP a servicios externos. No tiene salida de red fuera de la base (ADR-017).
  - El `generator` MUST cerrar ordenadamente con `SIGTERM`: termina el candidato en curso y libera los locks.
- **Aplica a esta story:** "un candidato MUST pasar a `approved` solo si `verify()` devuelve `ok: true`. El log completo MUST guardarse en `challenges.verification`". Con `verify` asíncrono, lo que se guarda es el **log resuelto**, nunca la `Promise` (que serializada a jsonb daría `{}`). "Termina el candidato en curso" con `SIGTERM`: el chequeo de `signal.aborted` sigue al principio de cada intento, así que un `verify` asíncrono en curso termina antes de cortar.

**ADR-005 (extracto que aplica):** la `api` y el `generator` se comunican solo por PostgreSQL (`generation_requests` + `LISTEN/NOTIFY`). La regeneración usa el mismo `generateForDate` en modo `'regenerate'`, así que hereda el `await` y la ventana. En una regeneración, la fila `approved` vieja de `D` **no** cuenta contra su reemplazo (REQ-009 decisión 2): eso es lo que garantiza la exclusión de `D`.

### Contexto de API

No aplica: el `generator` no expone HTTP ni cambia contratos de la `api`. El contrato que consume es el de `@nerdose/core` (ver ADR-006 arriba y Puntos de Integración).

### Contexto de Base de Datos

Sin cambios de schema ni de GRANTs. Tabla leída por la ventana (`docs/db-schemas/nerdose-db.md`, extracto verbatim):

```dbml
Table challenges {
  id uuid [pk, default: `gen_random_uuid()`]
  game_id game_id [not null]
  date date [not null, note: 'Día UTC en que se juega']
  number integer [not null, note: 'date − LAUNCH_DATE + 1; igual para los 5 juegos ese día']
  payload jsonb [not null, note: 'Contenido completo CON la solución y textos {es,en}. Inmutable desde approved. Nunca sale al jugador antes de terminar']
  status challenge_status [not null, default: 'draft']
  generator_version text [not null]
  seed text [not null, note: 'HMAC-SHA256(GENERATOR_SECRET, "{game_id}:{date}:{attempt}") en hex']
  attempt integer [not null, note: 'Intento con el que se derivó el seed (0..GENERATION_MAX_ATTEMPTS-1, y siguientes en regeneración)']
  verification jsonb [not null, default: `'{}'::jsonb`, note: 'Log de la verificación: { ok, checks[], reason? }']
  void_reason text [null]
  voided_at timestamptz [null]
  alerted_at timestamptz [null, note: 'Alcanzó el umbral de reportes (una sola vez, nunca vuelve a NULL). Es la alerta: el admin lo muestra en Reportes (ADR-017)']
  created_at timestamptz [not null, default: `now()`]

  indexes {
    (game_id, date) [unique, name: 'uq_challenges_active_game_date', note: "Parcial: WHERE status IN ('approved','published','voided')"]
    (game_id, date, status) [name: 'idx_challenges_game_date_status']
    (date, status) [name: 'idx_challenges_date_status']
  }

  Note: 'Desafío de un juego para un día. Lo crea solo el generator'
}
```

- `challenge_status`: `draft | approved | published | voided | rejected`. La ventana cuenta `approved`, `published` y `voided` (`ACTIVE_STATUSES` en el repositorio).
- `uq_challenges_active_game_date` garantiza como máximo una fila activa por (`game_id`, `date`). En una regeneración, esa fila de `D` es la `approved` vieja, y es la que la exclusión deja afuera.
- La consulta de la ventana usa el índice `idx_challenges_game_date_status`. REQ-009: "`recentChallenges` de Big O lee ≤ 60 filas por fecha".
- Consulta resultante (REQ-009, Flujo de Interacción, paso 2, verbatim): `history.recentChallenges = SELECT date, payload FROM challenges WHERE game_id = 'big-o' AND date BETWEEN D-30 AND D+30 AND status IN ('approved','published','voided')`, sin la fila de `D`; `bankItems = []`.

### Tarea 1: `await` de `verify` en `generateForDate` y helper `withGenerator`

**Status:** Completed

#### Descripción

`generateForDate` pasa a hacer `const verification = await generator.verify(payload, history)`. Así un juego de código (Big O, S-045) puede verificar ejecutando subprocesos, y los generadores síncronos (Devdle, Grep Grid, Timeline) siguen funcionando: `await` de un valor síncrono devuelve el mismo valor. #### Descripción

`generateForDate` arma `history.recentChallenges` con la ventana `[D - recentDays, D + (aheadDays ?? 0)]`, sin la fila de `D`, para que un juego sin banco (Big O) vea los desafíos ya aprobados para días posteriores en una regeneración o al llenar un hueco intermedio, y para que en una regeneración el `approved` viejo de `D` no cuente contra su reemplazo. Se agrega la función pura `historyWindow` y el parámetro opcional `excludeDate` en `recentChallenges`. Para los tres juegos registrados (sin `aheadDays`) las filas de la historia son las mismas que hoy. Cubre CA-5 (TS-1 a TS-10).

#### Criterios de Aceptación

1. `generate.ts` exporta `historyWindow(date: string, spec: HistorySpec): { from: string; to: string; exclude: string }` con `from = addDays(date, -spec.recentDays)`, `to = addDays(date, spec.aheadDays ?? 0)` y `exclude = date` (decisión 1).
2. `ChallengePublishingRepository.recentChallenges(gameId, from, to, payloadSchema, excludeDate?: string)`: con `excludeDate` agrega `ne(challenges.date, excludeDate)`. Sin él, la consulta es idéntica a la actual. Se mantienen `status IN ('approved','published','voided')` y el orden por `date` ascendente (decisiones 2 y 3).
3. `generateForDate` llama `repo.recentChallenges(gameId, window.from, window.to, payloadSchema, window.exclude)` con `window = historyWindow(date, spec)`. La misma `history` se pasa a `generate` y a `verify`.
4. Con `aheadDays` ausente o `0`, la historia de Devdle, Grep Grid y Timeline tiene exactamente las mismas filas que antes (`[D - recentDays, D - 1]`).
5. No hay `if (game_id === …)`. El cálculo depende solo de `entry.generator.historySpec`.
6. Tests: `test/domain/history-window.test.ts` (TS-1 a TS-4), `test/domain/challenge-publishing.repository.test.ts` (TS-5, TS-6) y `test/domain/generate.test.ts` (TS-7 a TS-10), con sufijo `(S-042 TS-n)`.

  ```ts
  import type { GeneratorHistory, HistorySpec } from '@nerdose/core';

  /**
   * Ventana de historia del juego para la fecha D: [D - recentDays, D + aheadDays] sin la fila de D.
   * Sin aheadDays equivale a [D - recentDays, D - 1]. En una regeneración, el approved viejo de D
   * no cuenta contra su reemplazo (REQ-009).
   */
  export function historyWindow(date: string, spec: HistorySpec) {
    return {
      from: addDays(date, -spec.recentDays),
      to: addDays(date, spec.aheadDays ?? 0),
      exclude: date,
    };
  }

  // en generateForDate:
  const window = historyWindow(date, spec);
  const history: GeneratorHistory = {

    recentChallenges: await repo.recentChallenges(gameId, window.from, window.to, payloadSchema, window.exclude),
  };
  ```
