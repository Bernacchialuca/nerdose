# Story Plan: S-005 (admin) - Shells de web y admin con proxy de mismo origen y pnpm dev

## Status

**Status:** Completed

## Referencia de la Story

- **Story:** [S-005](../stories/S-005.shells-web-admin-proxy-dev.md)
- **Servicio:** admin
- **Resumen:** Crea `apps/admin`, la SPA del responsable (React 19 + Vite) que arranca en `:5174` con `pnpm dev`, reenvía **solo** `/api/admin` a la `api` en `http://localhost:3000` (mismo origen, sin CORS; `/api/health` no llega a la `api`, igual que en producción) y muestra una pantalla vacía de Admin con los tokens de `@nerdose/ui`, sin login ni funcionalidad. Monta `QueryClientProvider`, un router mínimo con `errorElement` y tests de render + `vitest-axe`.

> **Alcance de este plan:** solo el servicio `admin` (`apps/admin`). Los otros servicios de la story tienen su propio plan:
> - `web` → `S-005.web.shells-web-admin-proxy-dev.md` (ya implementado, commit `2593f18`).
> - `workspace` → `S-005.workspace.*` (tarea `dev` de Turborepo para las 4 apps y README de arranque; CA-1 de punta a punta).
>
> Este plan cubre la parte de `admin` de CA-1 (que `pnpm dev` levante `admin` en `:5174`), CA-3, CA-4, CA-6 y la mitad de `admin` de CA-7.
>
> **Rutas:** todas las rutas de "Files to Create/Modify" son relativas a `apps/admin/` salvo que se indique `(raíz)`.
>
> **Dependencias:** S-001, S-002, S-003 y S-004 están implementadas y mergeadas en `dev` (`GET /api/health` y `GET /api/admin/health` responden en `:3000`; `apps/api/src/http/routes/index.ts` monta `app.get('/api/admin/health', ...)`). La parte `web` de esta misma story ya está hecha y es la **referencia directa** de este plan: la estructura de `apps/admin` replica la de `apps/web` con las diferencias de la tabla "Diferencias con `web`".
>
> **Código reutilizable:** no existe `docs/reusable-code/admin/index.md` (la app es nueva). Se reutiliza lo documentado de `@nerdose/ui` (`tokens.css`, `cn()`). `apps/web` está documentado en `docs/reusable-code/web/`, pero ADR-003 prohíbe importar de otra app: sus piezas se **replican** (la convención `data-fetching` define `api-client.ts` por app). Al terminar la story conviene correr `/service-update-reusable-code` para `admin`.
>
> **UX / Design System:** la story tiene `affects_ui: true`, pero la Revisión UX de REQ-001 resolvió **sin impacto UX**: la pantalla vacía de `admin` es andamiaje, no una pantalla del producto, y no tiene `screen.md`. Se cargó el Design System de `admin` (v0.1.1, `placeholder`): sin gaps. Mandan los tokens de la convención `styling`, que coinciden con `foundations/color.md`.

### ADRs Relevantes

#### ADR-002: Stack tecnológico (reglas aplicables, verbatim)

- Todo el código propio MUST ser TypeScript con `strict: true`. MUST NOT haber archivos `.js` de código fuente en `apps/` ni en `packages/` (salvo configuración de herramientas).
- `web` y `admin` MUST ser SPAs con React 19 + Vite. MUST NOT usarse SSR ni Next.js/Remix.
- Los estilos MUST ser Tailwind CSS v4, con los tokens en `@theme`. MUST NOT cargarse fuentes ni CSS de CDNs de terceros.
- Los tests MUST usar Vitest; los e2e, Playwright.

> Nota: la regla de ADR-002 "Los textos de UI MUST pasar por i18next con claves en `es` y `en`" aplica a `web`; el overview de `admin` fija "UI solo en español, sin i18n propio" (i18next solo se inicializará para los `client` de juegos de la preview, Feature Group 7). No crear `.js` en `apps/admin` (lo verifica `test/repo-hygiene.test.ts` de la raíz con `findJsSourceFiles`).

#### ADR-003: Monorepo y paquetes compartidos (reglas aplicables, verbatim)

- El gestor de paquetes MUST ser pnpm, con workspaces declarados en `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `packages/games/*`). MUST NOT usarse npm, yarn ni bun.
- Las tareas (`build`, `lint`, `typecheck`, `test`) MUST orquestarse con Turborepo desde `turbo.json`.
- Los paquetes internos MUST llamarse `@nerdose/<nombre>`.
- `apps/web` y `apps/admin` MUST importar solo `./client`.
- `apps/web` y `apps/admin` MUST NOT importar `@nerdose/db` ni `@nerdose/core/notify`.
- MUST NOT haber dependencias entre apps (`apps/*` no importa de otro `apps/*`). Lo compartido va en `packages/`.

> `eslint.config.js` de la raíz ya cubre `apps/admin/**` (`no-restricted-imports` con `noDb`, `noNotify`, `frontendsOnlyClient`, `crossApp('admin')`, más `jsx-a11y` y `react-hooks` sobre `apps/admin/**/*.{ts,tsx}`), y `test/eslint-boundaries.test.ts` ya lo prueba. **No tocar la config de ESLint.** Consecuencia práctica: **no copiar imports de `apps/web`**; replicar el código.

#### ADR-015: Contratos JSON en `snake_case`, i18n de respuestas y formato de errores (reglas aplicables, verbatim)

- Todas las propiedades JSON de requests y responses MUST estar en `snake_case` y coincidir con los nombres de `docs/apis/api.yaml` y `docs/db-schemas/nerdose-db.md`. MUST NOT haber transformaciones a `camelCase` en la `api` ni en los clientes HTTP de `web` y `admin`.
- Toda respuesta de error MUST tener exactamente la forma `{ "error": { "code": string, "message": string } }`.
- **Rutas sin versión:** `/api/*` y `/api/admin/*`.

```ts
// src/lib/api-client.ts
export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,       // error.code from the catalog in @nerdose/core
    message: string,             // error.message, already in the response locale
    readonly retryAfter?: number,
  ) { super(message); }
}

type Hooks = { getHeaders?: () => Record<string, string>; onError?: (err: ApiError) => void };
let hooks: Hooks = {};
export const configureApi = (h: Hooks) => { hooks = h; };

export async function api<T>(path: string, init: RequestInit & { json?: unknown } = {}): Promise<T> {
  const { json, headers, ...rest } = init;
  const res = await fetch(path, {
    ...rest,
    headers: {
      Accept: 'application/json',
      ...(json !== undefined && { 'Content-Type': 'application/json' }),
      ...hooks.getHeaders?.(),
      ...headers,
    },
    body: json !== undefined ? JSON.stringify(json) : rest.body,
  });
  if (res.ok) return (res.status === 204 ? undefined : await res.json()) as T;
  const body = await res.json().catch(() => null);
  const err = new ApiError(
    res.status,
    body?.error?.code ?? 'internal_error',
    body?.error?.message ?? res.statusText,
    Number(res.headers.get('Retry-After')) || undefined,
  );
  hooks.onError?.(err);
  throw err;
}
```

### Contexto de API

La story no cambia la API. `admin` consume, **a través del proxy de Vite**, el endpoint implementado en S-003 (`docs/apis/api.yaml`, sin cambios):

```yaml
/api/admin/health:
  get:
    tags: [Health]
    summary: Salud de la api (ruta de admin)
    description: Mismo chequeo que `/api/health`, accesible desde `admin.nerdose.dev`. No exige JWT.
    operationId: getAdminHealth
    security: []
    responses:
      '200':
        description: La api está viva y llega a la base
        content:
          application/json:
            schema: { $ref: '#/components/schemas/Health' }
      '503':
        description: La api no llega a la base
        content:
          application/json:
            schema: { $ref: '#/components/schemas/Health' }

Health:
  type: object
  required: [status, db]
  properties:
    status: { type: string, enum: [ok, degraded] }
    db: { type: string, enum: [ok, error] }
```

- Sin autenticación. Ruta inexistente en la `api` → `404 { "error": { "code": "not_found", "message": "…" } }`.
- La UI de la pantalla vacía **no** llama al health: se verifica por el origen de `admin` (`http://localhost:5174/api/admin/health`) con un cliente HTTP (CA-3). Si hace falta tipar `Health` en un test, declararlo en el test (`{ status: 'ok' | 'degraded'; db: 'ok' | 'error' }`).
- `GET http://localhost:5174/api/health` **no llega a la `api`** (CA-4): el proxy no tiene regla para ese path, así que lo atiende el propio dev server de Vite (con `Accept: */*` el fallback SPA de Vite responde el `index.html` con `200 text/html`). Lo que se verifica es que la `api` no recibe la request y que la respuesta no es el JSON de `Health`.
- Si la `api` está caída, el proxy responde `502`/`504` (aceptable en desarrollo).

### Contexto de Flujos

La story no referencia flujos. El escenario relevante es el **Escenario 2 de REQ-001** (Health por el origen de cada SPA), copiado:

**Trigger:** `GET http://localhost:5173/api/health` (origen de `web`) o `GET http://localhost:5174/api/admin/health` (origen de `admin`).

1. **[Vite dev server de `web` / `admin`]** El proxy reenvía la request sin cambios a `http://localhost:3000` con el mismo path.
2. **[`api`]** Endpoint `GET /api/health` o `GET /api/admin/health`, sin autenticación. `deps.health.check()` ejecuta `SELECT 1` con un timeout de 2 s. Si responde: `200 { "status": "ok", "db": "ok" }`. Si falla o vence: `503 { "status": "degraded", "db": "error" }`.
3. **[Vite proxy]** Devuelve la respuesta al navegador o al cliente HTTP en el mismo origen.

**Outcome:** cada SPA llega a la `api` en su propio origen, sin CORS. Esto valida el enrutamiento de mismo origen del que dependen la cookie y el JWT.

**Notas:** `admin` solo hace proxy de `/api/admin`: `GET :5174/api/health` no llega a la `api`. Es intencional y replica producción (`admin.nerdose.dev` solo enruta `/api/admin/*`).

Del **Escenario 1** (arranque local), el paso de `admin`: "**[`admin`]** Vite dev server en `:5174`, con proxy `'/api/admin' → 'http://localhost:3000'`." Puertos fijos de la story: `api` 3000, `web` 5173, `admin` 5174.
