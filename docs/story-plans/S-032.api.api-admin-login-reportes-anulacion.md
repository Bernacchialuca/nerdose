### Decisiones de planificación

1. **Ubicación de las rutas.** El módulo `admin` (`src/domain/admin/`) tiene login, middleware JWT, listado y `PATCH` de reportes (story, "Servicios Afectados"). La anulación vive en `quality` (`src/domain/quality/void.service.ts`) y su ruta en `src/domain/quality/quality-admin.routes.ts`, montada en `/api/admin` (overview: "`admin` agrupa las rutas `/api/admin/*` que no son de `quality` ni `publishing`").
2. **El middleware JWT se monta en `registerRoutes` antes de cualquier ruta de admin**, sobre `/api/admin/*`, y deja pasar exactamente `POST /api/admin/login` y `GET /api/admin/health`. Una ruta de admin inexistente sin token responde `401 unauthorized` (CA-3: "cualquier endpoint de `/api/admin/*`").
3. **Traducción del 401 de `hono/jwt`.** `error-handler.ts` traduce `HTTPException` con `status === 401` a `AppError('unauthorized')` (además del 400 → `validation_error` que ya existe). El middleware propio lanza `AppError('unauthorized')` si `sub !== 'admin'` o si `exp` falta.
4. **El rate limit del login cuenta todos los intentos** (correctos e incorrectos), con `limit({ windowMs: 900_000, limit: 5, key: clientIp(TRUST_PROXY_HEADER) })` antes del validador y de `verifyPassword`. ADR-010/ADR-012: "5 intentos cada 15 minutos por IP". `Retry-After: 900`.
5. **Parámetros de scrypt del hash generado:** `N = 16384`, `r = 8`, `p = 1`, salt de 16 bytes aleatorios, hash de 64 bytes, codificados en base64 (`scrypt$16384$8$1$<salt_base64>$<hash_base64>`). Ningún documento fija los valores; son los defaults de `node:crypto` y entran en el `maxmem` por defecto. `verifyPassword` lee N/r/p/longitud del string guardado, así que cambiarlos no rompe hashes existentes.
6. **`ADMIN_PASSWORD_HASH` se valida con el formato completo** (`/^scrypt\$\d+\$\d+\$\d+\$[A-Za-z0-9+/]+={0,2}\$[A-Za-z0-9+/]+={0,2}$/`), más estricto que el `startsWith('scrypt$')` del ejemplo de `env-config`: un hash truncado hace fallar el arranque y no cada login. `ADMIN_JWT_SECRET`: `z.string().min(32)`. Ambas obligatorias en todos los ambientes.
7. **`AdminService.login` recibe el reloj** (`Clock`) para `iat`: `signAdminToken(secret, Math.floor(clock.now().getTime() / 1000))`. Los tests de vencimiento firman con un `now` 8 h 1 min en el pasado (no hace falta reloj falso en `hono/jwt`).
8. **Listado de reportes:** dos consultas (reportes del estado + challenges con `id IN (…)`), agrupado y ordenado en memoria: `alerted_at IS NOT NULL` primero, `report_count` desc, `challenge.date` desc; dentro del grupo, `reports` por `created_at` desc (la story no fija el orden interno; se usa el del índice `idx_reports_status_created_at`). `reasons` solo incluye claves con conteo > 0. Sin paginación (REQ-007 decisión 9).
9. **`culprits` de un desafío cuyo `game_id` no está en el registry** (big-o, bug-hunt, sin paquete todavía): `[]`, sin lanzar. En la anulación, un juego sin definición solo admite `template`/`none`; `term`/`timeline_fact` → `422 invalid_culprit`. Para el recálculo se exige la definición (`games.get`); hoy el `generator` solo crea desafíos de los tres juegos registrados.
10. **Recarga de cache tras anular:** si `challenge.date === today(clock.now())`, `TodayCache.reload(hoy)` después del COMMIT. Si la recarga falla, se loguea `error` y la respuesta sigue siendo `200` (la anulación ya está persistida; `memory-cache`: "failures on reload keep the previous content and log at error"). La carrera la cubre el `FOR SHARE` de S-031.
11. **Recálculo:** `ProgressService.recompute(repo, { playerIds, game })` deduplica y ordena `playerIds` ascendente; por jugador bloquea `lockGameStats(player, game)` → `lockPlayerStats(player)` (mismo orden que `applyResult`); después hace **una** consulta de días activos y **una** de Play completadas de todos los afectados, y escribe 2 `UPDATE` por jugador. `max_streak`/`max_global_streak` salen del replay (`replayStreak().max`), no del valor previo, para que el resultado sea idéntico a recalcular desde cero (CA-7, ADR-011).
12. **Lectura de `jsonb` en el recálculo:** `plays.result` se pasa a `rebuildGameStats(game, …)` tal como viene de la base, igual que hoy `applyResult` pasa el `result` del juego a `reduceStats` (el `GameDefinition` no expone un `resultSchema` que permita parsearlo en la `api`). Una Play `won`/`lost` sin `result` hace lanzar a `rebuildGameStats` → `ROLLBACK` → `500`.
13. **Body de la anulación con `kind` y `id`:** `culprit.id` obligatorio (uuid) con `term`/`timeline_fact` y **prohibido** con `template`/`none` (`.strict()` + `superRefine`) → `422 validation_error`. `void_reason` con `trim`, 1–500.
14. **Fallas inyectables en tests.** `VoidService` recibe `runInTx: VoidTx` (como `MoveTx` de S-031) con repos `{ quality, progress }` ligados a la transacción; los tests de CA-9 envuelven `progress.saveGameStats` para que lance en la mitad del lote.

### ADRs Relevantes

- **ADR-010: Autenticación del admin**
  - Decisión: login `POST /api/admin/login { password }` comparado contra `ADMIN_PASSWORD_HASH` (scrypt de `node:crypto`) con `timingSafeEqual`; JWT HS256 con `ADMIN_JWT_SECRET`, claims `{ sub: "admin", iat, exp }`, 8 h, sin refresh; `sessionStorage` + `Authorization: Bearer`; rotar el secreto invalida todas las sesiones.
  - Reglas de Implementación (verbatim):
    - `ADMIN_PASSWORD_HASH` MUST tener el formato `scrypt$<N>$<r>$<p>$<salt_base64>$<hash_base64>`. La verificación MUST usar `crypto.scrypt` y `crypto.timingSafeEqual`. MUST NOT existir una variable con la contraseña en texto plano.
    - El repo MUST incluir un script (`pnpm --filter api admin:hash`) que genere `ADMIN_PASSWORD_HASH` a partir de una contraseña ingresada por stdin.
    - El JWT MUST firmarse con `hono/jwt`, algoritmo `HS256` y `ADMIN_JWT_SECRET` (≥ 32 bytes aleatorios). Claims: exactamente `sub: "admin"`, `iat` y `exp = iat + 28800`.
    - `POST /api/admin/login` MUST responder `200 { token, expires_at }` (`expires_at` en ISO 8601 UTC) o `401` con `{ "error": { "code": "invalid_credentials", … } }`.
    - `POST /api/admin/login` MUST limitarse a 5 intentos cada 15 minutos por IP (`429 rate_limited`).
    - Todas las rutas `/api/admin/*`, salvo `POST /api/admin/login` y `GET /api/admin/health`, MUST exigir `Authorization: Bearer <jwt>` válido. Si falta, es inválido o venció, MUST responder `401` con `{ "error": { "code": "unauthorized", … } }`.
    - El admin MUST guardar el token en `sessionStorage` (nunca en `localStorage` ni en una cookie) y, ante un `401`, MUST borrarlo y volver al login.
    - Las rutas `/api/admin/*` MUST NOT leer ni emitir la cookie `nd_pid`.
    - MUST NOT haber refresh tokens ni usuarios múltiples.

- **ADR-011: Rachas con días neutros**
  - Decisión:
    ```
    prev_active_day(game_id, D) = max(date) FROM challenges
                                  WHERE game_id = :game_id AND date < D
                                    AND status IN ('published','voided')
    prev_active_day_global(D)   = el mismo max(date), sin filtrar game_id

    Al completar una Play del día D:
      game:   current_streak = (last_completed_date >= prev_active_day(game_id, D)) ? current_streak + 1 : 1
              (si last_completed_date == D, no cambia)
      global: global_streak  = (last_active_date >= prev_active_day_global(D)) ? global_streak + 1 : 1
              (si last_active_date == D, no cambia)
      max_* = max(max_*, current)
    ```
    **Recálculo** (al anular): para cada jugador afectado, se recorren sus `plays` en orden de fecha aplicando la misma función, y se excluyen las `voided` de `played`, `wins` y `extra`.
  - Reglas de Implementación (verbatim):
    - La función de rachas MUST vivir en `@nerdose/core` y ser la única implementación. La `api` MUST usarla en el cierre, en la lectura y en el recálculo.
    - `prev_active_day` MUST considerar solo challenges con `status IN ('published','voided')`. MUST NOT haber jobs que reseteen rachas ni que marquen días neutros.
    - El cierre de una Play (`won`/`lost`) y la actualización de `player_game_stats` y `player_stats` MUST ocurrir en la misma transacción. Si falla una, se revierte todo.
    - Una Play cuenta como completada si `status IN ('won','lost','voided')`. Una `in_progress` nunca cuenta.
    - `played`, `wins` y `extra` MUST excluir las Play `voided`. `total_completed` y las rachas MUST incluirlas.
    - `extra` MUST calcularse solo con `reduceStats` del `GameDefinition` del juego.
    - La racha leída MUST ser 0 si no está viva, sin escribir en la base.
    - Debe existir una función `recomputeStats(player_id, game_id?)` que reconstruya `player_game_stats` y `player_stats` desde `plays`. MUST dar el mismo resultado que la aplicación incremental (test de propiedad con historias aleatorias).
    - Los tests de rachas MUST usar relojes falsos e incluir días neutros, anulaciones y cambio de día.

- **ADR-012: Caches y rate limit en memoria**
  - Decisión (extracto): cache "Desafíos de hoy" `Map<game_id, challenge>` (`published` o `voided` de `today`), recargada al cambiar el día, al arrancar y al anular. Rate limit `POST /api/admin/login` por IP: 5 / 15 min; `/api/admin/*` con JWT: sin límite.
  - Reglas de Implementación (aplicables, verbatim):
    - La cache de desafíos MUST invalidarse al cambiar el día (ADR-008), al arrancar y al terminar `POST /api/admin/challenges/{challenge_id}/void`.
    - Los límites MUST ser exactamente los de la tabla, configurados con `hono-rate-limiter` y store en memoria.
    - La IP del cliente MUST tomarse del header del proxy de confianza configurado (`TRUST_PROXY_HEADER`, por ejemplo `X-Forwarded-For`), nunca de un header arbitrario sin configurar.
    - Un `429` MUST incluir `Retry-After` en segundos y el body `{ "error": { "code": "rate_limited", "message": … } }`. MUST NOT haber captcha.

- **ADR-004: PostgreSQL única base con roles** (aplicable)
  - `nerdose_api`: lectura y escritura de `plays`, `player_game_stats`, `player_stats`, `challenge_reports`; sobre `challenges`: `SELECT` y `UPDATE` **solo** de `status`, `void_reason`, `voided_at` y `alerted_at`; sobre `terms` y `timeline_facts`: `SELECT` y `UPDATE (status, rejection_reason)`.
  - Regla: "La `api` MUST conectarse con el rol `nerdose_api` […]. Ninguno de los dos MUST tener permisos de DDL." → todo `UPDATE` de este plan toca solo esas columnas (`FOR UPDATE` de `challenges` es válido porque el rol tiene `UPDATE` de columna).

- **ADR-015 (vía convención `error-handling`)**: JSON `snake_case`; errores `{ "error": { "code", "message" } }` con catálogo cerrado; `invalid_culprit` (422) ya existe en `ERROR_CATALOG` y en `error-messages.ts` ("El culpable no pertenece al desafío." / "The culprit does not belong to the challenge.").

- **ADR-016 (vía story y REQ-007)**: los rechazos por anulación viven solo en la base; `sync_banks` nunca revive un `rejected` (trigger `bank_items_rejected_terminal`).

### Convenciones activas (extracto aplicable)

- **auth-jwt** (custom): estructura `scripts/admin-hash.ts` + `src/domain/admin/{admin-auth.ts, admin-auth.middleware.ts, admin.routes.ts}`. Ejemplo de referencia:
  ```ts
  // ADMIN_PASSWORD_HASH = scrypt$<N>$<r>$<p>$<salt_base64>$<hash_base64>
  export async function verifyPassword(password: string, stored: string): Promise<boolean> {
    const [, N, r, p, salt, hash] = stored.split('$');
    const expected = Buffer.from(hash!, 'base64');
    const actual = await scryptAsync(password, Buffer.from(salt!, 'base64'), expected.length,
      { N: Number(N), r: Number(r), p: Number(p) });
    return actual.length === expected.length && timingSafeEqual(actual, expected);
  }

  export async function signAdminToken(secret: string, now = Math.floor(Date.now() / 1000)) {
    const exp = now + 28800; // 8 h
    const token = await sign({ sub: 'admin', iat: now, exp }, secret, 'HS256');
    return { token, expires_at: new Date(exp * 1000).toISOString() };
  }
  ```
  Reglas: comparación con `crypto.scrypt` + `crypto.timingSafeEqual`; claims exactamente `sub`, `iat`, `exp = iat + 28800`; nunca `jsonwebtoken`/`jose`; `alg` fijo `HS256` al verificar; `401 invalid_credentials` / `401 unauthorized`; `/api/admin/*` nunca lee ni emite `nd_pid`; secretos solo de `env`, nunca logueados; en tests usar un secreto de test y un hash generado por `hashPassword`, sin saltear la verificación.
- **security** (custom): no CORS; toda mutación exige `Content-Type: application/json` (`415 unsupported_media_type`) y `Origin` igual a `ADMIN_ORIGIN` en `/api/admin/*` (`403 forbidden_origin`) — ya montado en `buildApp`; `POST /api/admin/login` 5 / 15 min por IP; `/api/admin/*` con JWT válido sin límite; IP solo del header `TRUST_PROXY_HEADER`.
- **env-config** (custom): todo en `src/config/env.ts`, validado al arrancar; `ADMIN_PASSWORD_HASH` y `ADMIN_JWT_SECRET` solo en el entorno de la `api`; `.env.example` lista cada variable sin valor y con comentario (hay un test que lo verifica); nadie fuera de `config/env.ts` lee `process.env` (test `env-isolation`).
- **memory-cache** (custom): `TodayCache` se recarga "after `POST /api/admin/challenges/{challenge_id}/void`"; una falla de recarga conserva el contenido previo y loguea `error`; solo los servicios de publicación y anulación disparan recargas.
- **platform-day** (custom): "Voiding a challenge (`published` only) sets `status`, `void_reason`, `voided_at`, reloads the today cache and calls `recomputeStats(player_id, game_id)` for each affected player using the same core function."; `today` siempre de `@nerdose/core` con el reloj inyectado.
- **orm** (custom): repositorio por módulo, `Db | Tx` por constructor; SQL crudo solo donde Drizzle no llega (no hace falta aquí: `.for('update')`, `inArray`, `sql\`now()\``); tipos inferidos del schema.
- **validation** (custom): toda ruta con input usa `zValidator(..., validationHook)`; falla → `422 validation_error`; JSON `snake_case`.
- **error-handling** (custom): ver Manejo de errores arriba; "Unique-constraint violations are translated by the service layer"; "Never throw a plain `Error` for an expected failure".
- **testing** (custom): un contenedor compartido; fixtures con owner; reloj falso; sin sleeps; un test por rol para grants.
- **logging**: mensajes estáticos, contexto en el objeto; nunca contraseñas ni tokens.

### Contexto de Flujos

**admin-login-y-consultas** (`docs/flows/admin-login-y-consultas.md`) — pasos que implementa este plan (con las precisiones de REQ-007):
1. **Login:** `POST /api/admin/login { "password": "string" }` → `crypto.scrypt` con los parámetros de `ADMIN_PASSWORD_HASH` y `timingSafeEqual`; si coincide, JWT HS256 con `ADMIN_JWT_SECRET` y `{ sub: "admin", iat, exp = iat + 28800 }` → `200 { "token", "expires_at" }`; incorrecta → `401 invalid_credentials`; 5 intentos/15 min por IP → `429 rate_limited` + `Retry-After`.
2. **Reportes agrupados:** `GET /api/admin/reports?status=open` → `challenge_reports` SELECT `id`, `challenge_id`, `reason`, `message`, `locale`, `context`, `status`, `created_at` WHERE `status = :status`; `challenges` SELECT `id`, `game_id`, `date`, `number`, `status`, `payload`, `verification` (+ `void_reason`, `voided_at`, `alerted_at`) de los reportados → `200 { groups[] }`. **MODIFICADO por REQ-007:** orden alertados → `report_count` desc → `date` desc; `culprits`, `void_reason`, `voided_at`, `player_ref`, `alerted_at`.
3. **Resolver o descartar:** `PATCH /api/admin/reports/{report_id} { "status": "resolved | dismissed" }` → `UPDATE challenge_reports SET status WHERE id AND status = 'open' RETURNING`; sin filas y reporte existente → `409 report_not_open`; inexistente → `404 not_found`. Eventos `ReportResolved`/`ReportDismissed` solo en logs. `200 AdminReport`.
- Errores: JWT ausente, inválido o vencido → `401 unauthorized` en pasos 2–5; query/body inválido → `422 validation_error`.
- Pasos 4 (stock) y 5 (métricas): **no** se implementan (FG-7/FG-10).

**anulacion-de-desafio** (`docs/flows/anulacion-de-desafio.md`) — pasos 1–3 (los 4–5 son de S-031):
1. **Pedido:** `POST /api/admin/challenges/{challenge_id}/void { "void_reason", "culprit": { "kind": "term | timeline_fact | template | none", "id" } }` con `Authorization: Bearer <jwt>`. Validaciones: JWT → existe → `published` (si no, `409 not_voidable`). **MODIFICADO:** `422 invalid_culprit` si el culpable no está en `game.culprits(payload)`; `SELECT … FOR UPDATE`.
2. **Anular (transacción):** (1) `UPDATE challenges SET status = 'voided', void_reason, voided_at = now()`; (2) `UPDATE plays SET status = 'voided', finished_at = coalesce(finished_at, now()) WHERE challenge_id` (conservan `result`) devolviendo `player_id`; (3) `UPDATE challenge_reports SET status = 'resolved' WHERE challenge_id AND status = 'open'`; (4) `term` → `UPDATE terms SET status = 'rejected', rejection_reason = void_reason WHERE id = culprit.id` (**MODIFICADO:** `AND status = 'approved'`); `timeline_fact` → igual sobre `timeline_facts`; `template`/`none` → sin cambios. Eventos `ChallengeVoided`, `ContentItemRejected`, `ReportResolved` solo en logs.
3. **Recalcular (misma transacción):** por jugador afectado recorre sus `plays` por `date` con la función de rachas y `reduceStats`; `voided` cuentan para rachas y `total_completed`, no para `played`/`wins`/`extra`. UPDATE `player_game_stats` (`current_streak`, `max_streak`, `played`, `wins`, `last_completed_date`, `extra`) y `player_stats` (`global_streak`, `max_global_streak`, `last_active_date`, `total_completed`). Evento `StreaksUpdated`. **MODIFICADO:** por lote, orden de bloqueo `player_game_stats` → `player_stats` por `player_id` asc, `replayStreak`/`rebuildGameStats`. Response `200 { "challenge_id", "affected_plays" }`. Después del COMMIT invalida la cache de hoy (**MODIFICADO:** solo si es de hoy).
- Errores: `401 unauthorized`, `404 not_found`, `409 not_voidable`, `422 validation_error`, error de BD en 2–3 → `500 internal_error` con ROLLBACK ("nada queda anulado a medias").

**estadisticas-del-jugador** (`docs/flows/estadisticas-del-jugador.md`): sin cambios de pasos; `GET /api/me/stats` lee los agregados recalculados. La racha se muestra viva si `last_completed_date >= prev_active_day`; `win_rate = wins / played`.

### Task 6: `VoidService` y `POST /api/admin/challenges/{challenge_id}/void`

**Status:** Completed

#### Description

Implementa la anulación transaccional en `quality`: validación del body, `FOR UPDATE` del challenge, validación del culpable con `game.culprits`, updates de challenge, plays, reportes y banco, recálculo por lote, recarga de `TodayCache` tras el COMMIT y eventos en logs (CA-6, CA-7, CA-8, CA-9).

#### Acceptance Criteria

1. Ruta `POST /api/admin/challenges/:challenge_id/void` en `quality-admin.routes.ts` montada en `/api/admin` (protegida por el middleware de la task 3): `zValidator('param', { challenge_id: z.uuid() })`, `zValidator('json', voidRequestSchema)` con `validationHook` → `deps.voids.void(challengeId, body, log)` → `200 { challenge_id, affected_plays }`.
2. `voidRequestSchema` = `{ void_reason: z.string().trim().min(1).max(500), culprit: { kind: enum, id?: uuid } }` estricto, con `id` obligatorio para `term`/`timeline_fact` y prohibido para `template`/`none` (TS-29, TS-30).
3. En una sola transacción (`runInTx`), en este orden:
   1. `lockChallengeForUpdate(id)`: `SELECT id, game_id, date, status, payload FROM challenges WHERE id FOR UPDATE` → sin fila `404 not_found`; `status !== 'published'` → `409 not_voidable` (TS-32, TS-33, TS-35).
   2. Culpable: `term`/`timeline_fact` deben estar en `game.culprits(payload)` como `{ kind, id }` (juego sin definición → `invalid_culprit`) → si no, `422 invalid_culprit` antes de escribir (TS-31).
   3. `UPDATE challenges SET status = 'voided', void_reason = $reason, voided_at = now() WHERE id`.
   4. `UPDATE plays SET status = 'voided', finished_at = COALESCE(finished_at, now()) WHERE challenge_id RETURNING player_id` (sin tocar `result` ni `score`).
   5. `UPDATE challenge_reports SET status = 'resolved' WHERE challenge_id AND status = 'open' RETURNING id` (conteo).
   6. `term` → `UPDATE terms SET status = 'rejected', rejection_reason = $reason WHERE id AND status = 'approved'`; `timeline_fact` → igual en `timeline_facts`; `template`/`none` → nada (TS-25, TS-28).
   7. `progress.recompute(repos.progress, { playerIds, game })` (task 5).
4. Cualquier error → ROLLBACK → `500 internal_error`; el desafío sigue `published` y nada cambió (TS-34).
5. Después del COMMIT: si `challenge.date === today(clock.now())` → `TodayCache.reload(hoy)`; si falla, log `error` `'Today cache reload failed'` y la respuesta sigue `200` (decisión 10) (TS-23).
6. Eventos post-COMMIT (`info`): `ChallengeVoided { challenge_id, game_id, culprit_kind, affected_plays }`, `ContentItemRejected { kind, id }` (solo si una fila cambió), `ReportResolved { challenge_id, count }`, `StreaksUpdated { challenge_id, players }` (TS-38).
