# S-004: Esqueleto del generator con scheduler sin jobs

**Status:** Ready
**Created:** 2026-11-03
**Source:** REQ-001

## Historia de Usuario

**Como** desarrollador de Nerdose,
**quiero** un worker `generator` que arranque su scheduler sin jobs y cierre ordenadamente,
**para** tener la base de ejecución sobre la que se registran los jobs de generación.

## Criterios de Aceptación

### CA-1: Scheduler activo sin jobs

**DADO** el `generator` en ejecución con la base migrada
**CUANDO** se observa su salida
**ENTONCES** indica que el scheduler está activo (`Scheduler started`, `{ jobs: 0 }`) y no ejecuta ningún job (REQ AC 9)

### CA-2: Apagado ordenado

**DADO** el `generator` en ejecución
**CUANDO** recibe `SIGTERM`
**ENTONCES** cierra ordenadamente (libera keep-alive, `sql.end()`, log `Shutdown complete`) y termina con código 0 (REQ AC 10)

### CA-3: SIGTERM repetido

**DADO** el `generator` ya apagándose
**CUANDO** recibe un segundo `SIGTERM`
**ENTONCES** no reinicia el apagado (handler idempotente)

### CA-4: Variable de entorno faltante

**DADO** falta `DATABASE_URL` u otra variable requerida
**CUANDO** se arranca el `generator`
**ENTONCES** aborta al inicio con un mensaje que nombra la variable (REQ AC 14)

### CA-5: Rol observable y base caída

**DADO** la base migrada / la base no responde
**CUANDO** arranca el `generator`
**ENTONCES** registra `{ db_role: 'nerdose_generator' }`; si la base no responde, sale con código 1 y mensaje claro (REQ AC 4, parte `generator`)

### Flujo de Interacción y Consideraciones Técnicas

- Sin puerto; croner en UTC. Con 0 jobs no hay handle activo y Node terminaría: `startScheduler(deps)` registra la lista vacía y mantiene un timer de keep-alive hasta `stop()`.
- Handler de `SIGTERM` (ref: `scheduler-jobs`): `shutdown.abort()`, `scheduler.stop()`, `await sql.end()`, log `Shutdown complete`, `process.exit(0)`. Si `sql.end()` falla, se loguea y sale igual con 0.
- Variables: `NODE_ENV`, `LOG_LEVEL`, `SERVICE_NAME`, `DATABASE_URL` (rol `nerdose_generator`).
- **Pruebas:** `startScheduler` con 0 jobs y `stop()` libera el handle; con `child_process.spawn` sobre la URL de Testcontainers, registra el scheduler activo y sale con 0 ante `SIGTERM`; entorno sin `DATABASE_URL` aborta nombrando la variable.
- **Riesgo:** `turbo run dev` corta todas las tareas si el `generator` falla por no tener base; el README (S-005) indica el orden de arranque.
