# S-035: Tablas de cola y fallas, y consumo de bancos en el contrato

**Status:** Ready
**Created:** 2026-11-13
**Source:** REQ-008

## Historia de Usuario

**Como** Responsable del producto,
**quiero** que existan las tablas de pedidos de regeneración y de fallas de generación, y que cada juego declare qué banco consume,
**para** que `generator` y `api` compartan una base y un contrato comunes para regenerar desafíos y calcular el stock.

## Criterios de Aceptación

### CA-1: Migración 0007

**DADO** una base con las migraciones hasta `0006`
**CUANDO** se aplica `0007_generation_queue_and_failures`
**ENTONCES** existen el enum `generation_request_status` (`pending|done|failed|cancelled`), `generation_requests` y `generation_failures` con sus índices, checks y trigger `set_updated_at`, sin tocar tablas existentes (REQ DB)

### CA-2: Un solo pedido pendiente

**DADO** un pedido `pending` para un Challenge
**CUANDO** se intenta insertar otro `pending` para el mismo Challenge
**ENTONCES** `uq_generation_requests_pending` lo impide (REQ RF 3, CA 4)

### CA-3: Checks de consistencia

**DADO** un pedido
**CUANDO** `status = 'done'` sin `new_challenge_id`, o `status <> 'pending'` sin `processed_at`
**ENTONCES** la base rechaza la fila

### CA-4: Grants por rol

**DADO** los roles `nerdose_api` y `nerdose_generator`
**CUANDO** se aplican los grants
**ENTONCES** `nerdose_api` tiene `SELECT, INSERT` en `generation_requests` y `SELECT` en `generation_failures`; `nerdose_generator` tiene `SELECT, INSERT, UPDATE` en ambas; nadie tiene `DELETE` (ADR-004, ADR-017)

### CA-5: Schema Drizzle

**DADO** `packages/db`
**CUANDO** se importa el schema
**ENTONCES** `generation.ts` exporta las tablas y el tipo `GenerationRequestStatus` en `@nerdose/core`

### CA-6: bankUsage en el contrato

**DADO** `GameDefinition`
**CUANDO** se consulta `bankUsage` de cada juego
**ENTONCES** Devdle es `terms/last_used_devdle/365/1`, Grep Grid `terms/last_used_grep/30/8`, Timeline `timeline_facts/last_used/90/5`; Big O y Bug Hunt `null`; un test de paquete verifica que coincide con `historySpec` (REQ Decisión 11)

### Cambios de API

Ninguno (el contrato HTTP lo cubre S-037).

### Cambios de Base de Datos

Migración `0007_generation_queue_and_failures` (solo crea objetos nuevos; sin datos ni downtime).

- Enum `generation_request_status`: `pending | done | failed | cancelled` (enmienda ADR-005, ver Decisión 1 del request).
- `generation_requests`: `id uuid PK`, `challenge_id uuid NOT NULL → challenges(id) ON DELETE RESTRICT`, `status` default `pending`, `new_challenge_id uuid NULL → challenges(id)`, `error text NULL`, `requested_at`, `processed_at`. Índice único parcial `uq_generation_requests_pending (challenge_id) WHERE status='pending'` (SQL manual), `idx_generation_requests_status (status, requested_at)`, `idx_generation_requests_challenge (challenge_id, requested_at)`. Checks: `done ⇒ new_challenge_id`, `status<>'pending' ⇒ processed_at`.
- `generation_failures`: PK (`game_id`,`date`), `attempts >= 1`, `last_reason`, `created_at`, `updated_at` con trigger `set_updated_at`.
- Grants según el criterio CA-4.

### Flujo de Interacción

1. **[db]** Se aplica `0007` antes de cualquier cambio en `api` o `generator`.
2. **[core/games]** `bankUsage` queda disponible por el registry; la `api` lo importa solo desde `./definition`.

### Consideraciones Técnicas

El test de `bankUsage` vs `historySpec` evita que el stock muestre ventanas distintas de las reales. Convención `game-registry`: sin constantes por juego en `apps/api`.
