# S-037: API admin, próximos desafíos, regeneración, fallas y stock

**Status:** Ready
**Created:** 2026-11-13
**Source:** REQ-008

## Historia de Usuario

**Como** Responsable del producto,
**quiero** consultar por API los próximos 14 días, pedir la regeneración de un desafío, ver las fallas activas y el stock de contenido,
**para** operar el contenido automático desde el admin sin exponer soluciones a los jugadores.

## Criterios de Aceptación

### CA-1: Próximos 14 días

**DADO** hoy 2026-12-01 y desafíos `approved` hasta el 12-15
**CUANDO** se pide `GET /api/admin/challenges/upcoming`
**ENTONCES** devuelve `{ days, active_failures }` de `today+1` a `today+14` (nunca hoy), un item por juego del registry, con `challenge` (`payload`, `verification`, `attempt`, `rejected_items`, sin seed), `regeneration` (solo `pending`/`failed`) y `failure` solo si no hay challenge (REQ CA 1, 2, 8-10)

### CA-2: Parámetro days

**DADO** `days` fuera de 1-14
**CUANDO** se pide
**ENTONCES** `422 validation_error`

### CA-3: Regenerar

**DADO** un Challenge `approved` con fecha futura
**CUANDO** se hace `POST .../regenerate`
**ENTONCES** responde `202 { request_id, status: pending, requested_at }`, inserta el pedido y hace `pg_notify` en la misma transacción, sin ejecutar el generador (REQ CA 3)

### CA-4: Idempotencia

**DADO** un pedido pendiente
**CUANDO** se repite
**ENTONCES** `INSERT ... ON CONFLICT DO NOTHING` y se devuelve el pendiente existente (REQ CA 4)

### CA-5: No regenerable

**DADO** un Challenge `published`, `voided`, `rejected`, `draft` o con fecha de hoy o pasada
**CUANDO** se intenta regenerar
**ENTONCES** `409 not_regenerable` sin crear pedido; `404 not_found` si no existe (REQ CA 5)

### CA-6: Fallas activas

**DADO** fallas registradas
**CUANDO** se pide `GET /api/admin/generation-failures`
**ENTONCES** devuelve solo las activas (fecha en la ventana y sin Challenge vigente), ordenadas por fecha y juego, sin `payload`

### CA-7: Stock

**DADO** los bancos del registry
**CUANDO** se pide `GET /api/admin/content/stock`
**ENTONCES** devuelve por banco `approved_available`, `approved_total`, `rejected_total`, `days_of_stock`, `cycle_ok`, `consumers` (Devdle y Grep Grid para `terms`), `rejections` (máx. 200 con motivo), `last_sync` (última corrida `success`, `null` si no hay) y `top_rejected_guesses` (50, por jugadores distintos) (REQ CA 11-14)

### CA-8: Auth y anti-spoiler

**DADO** cualquier endpoint nuevo sin sesión, vencida o con token inválido
**CUANDO** se pide
**ENTONCES** `401`; y los endpoints de jugador (`today`, `start`, `move`) nunca incluyen solución, `payload` ni `verification` de desafíos futuros (test de regresión, REQ CA 15, 16, NFR-S01)

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| api | Alto | Módulo `admin`: `upcoming`, `generation-failures`, `stock`; módulo `publishing`: `regenerate` idempotente con `pg_notify`; cálculo de `rejected_items` con `definition.culprits`; stock desde `bankUsage`; test anti-spoiler | Pending |

### Cambios de API

- `GET /api/admin/challenges/upcoming`: `pending_request` se reemplaza por `regeneration`; `challenge` suma `attempt` y `rejected_items`; raíz suma `active_failures`.
- `POST /api/admin/challenges/{id}/regenerate`: 202 `{ request_id, status, requested_at }`.
- `GET /api/admin/content/stock`: `BankStock.consumers`; nuevas definiciones de `approved_available`, `days_of_stock` (mínimo) y `cycle_ok` (todos); `cycle_ok` por consumidor = `approved_total >= itemsPerChallenge × windowDays`.
- Nuevo `GET /api/admin/generation-failures` (`{ failures: [{ game_id, date, attempts, last_reason, updated_at }] }`).
Ver `docs/apis/api.yaml` (actualizado en esta creación de stories).

### Cambios de Base de Datos

Sin cambios de esquema; usa las tablas de S-035 (`SELECT, INSERT` en `generation_requests`, `SELECT` en `generation_failures`). Las lecturas van siempre a la base, sin `TodayCache`.

### Flujo de Interacción

1. **[admin → api]** `GET upcoming?days=14` → 4 consultas indexadas + una por banco para `rejected_items`.
2. **[admin → api]** `POST regenerate` → valida (404/409) → INSERT idempotente → `pg_notify` → 202.
3. **[admin → api]** `GET generation-failures` para el contador del shell; `GET content/stock` para la sección Stock.

### Flujos Afectados

- **regenerar-desafio** (ref: docs/flows/regenerar-desafio.md)
- **admin-login-y-consultas** (ref: docs/flows/admin-login-y-consultas.md)

### Consideraciones Técnicas

La `api` no importa constantes por juego (convención `game-registry`). `seed` nunca se serializa. Se puede probar con filas sembradas, en paralelo con S-036. Payloads grandes en `upcoming`: aceptable para un solo usuario.
