# S-042: Contrato de juegos de código en core, api y generator

**Status:** Ready
**Created:** 2026-11-14
**Source:** REQ-009

## Historia de Usuario

**Como** equipo de desarrollo,
**quiero** que el contrato `GameDefinition`/`GameGenerator` exprese el lenguaje de código de la Play, la verificación asíncrona y la ventana de historia hacia adelante,
**para** que juegos de código como Big O funcionen en la `api` y el `generator` sin ramificar por `game_id`.

## Criterios de Aceptación

### CA-1: codeLanguage en el contrato

**DADO** los juegos Devdle, Grep Grid y Timeline
**CUANDO** implementan `codeLanguage`
**ENTONCES** devuelven `null` y sus tests siguen en verde (REQ decisión 1)

### CA-2: Cierre guarda lenguaje y preferencia

**DADO** un juego de prueba cuyo `codeLanguage(state)` devuelve `go`
**CUANDO** la jugada cierra la Play
**ENTONCES** la `api` guarda `plays.code_language = go` y `players.preferred_code_language = go` en la misma transacción; si devuelve `null` no toca la preferencia (REQ CA 4, 5)

### CA-3: Respuesta con code_language

**DADO** una jugada que cierra la Play
**CUANDO** la `api` responde
**ENTONCES** `MoveResponse.play.code_language` trae el lenguaje confirmado (o `null`) (REQ decisión 12)

### CA-4: verify asíncrono

**DADO** un generador cuyo `verify` devuelve `Promise`
**CUANDO** `generateForDate` lo ejecuta
**ENTONCES** hace `await` y los generadores síncronos siguen funcionando (REQ decisión 2)

### CA-5: Ventana hacia adelante

**DADO** un juego con `historySpec.aheadDays = 30` y `recentDays = 30`
**CUANDO** se arma la historia para la fecha D
**ENTONCES** `recentChallenges` pide `[D - 30, D + 30]` sin la fila de `D`; con `aheadDays` ausente el comportamiento es el actual (REQ decisión 2)

### CA-6: Enums del dominio

**DADO** los enums del núcleo
**CUANDO** se consultan
**ENTONCES** existen `BIG_O_OPTIONS` (8 opciones en orden fijo) y `RECIPE_CATEGORIES` (5) (REQ decisión 5)

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| core | Medio | `GameDefinition.codeLanguage`, `GameGenerator.verify` puede devolver `Promise`, `HistorySpec.aheadDays`, enums `BIG_O_OPTIONS` y `RECIPE_CATEGORIES` | Pending |
| games (devdle, grep-grid, timeline) | Bajo | `codeLanguage: () => null` | Pending |
| api | Medio | Al cerrar guarda `plays.code_language` y `players.preferred_code_language` desde `codeLanguage(state)`; `MoveResponse.play.code_language` | Pending |
| generator | Medio | `await generator.verify(...)`; ventana `[D - recentDays, D + aheadDays]` sin `D` | Pending |

### Cambios de API

`MoveResponse.play` suma `code_language` (requerido, nullable). La descripción de `POST .../move` se precisa. Ver sección de documentación técnica actualizada en `docs/apis/api.yaml`.

### Cambios de Base de Datos

Ninguno de schema. Primera vez que la `api` escribe `plays.code_language` y actualiza `players.preferred_code_language` (GRANT `UPDATE` ya existe).

### Flujo de Interacción

1. **[api - GameplayService.move]** aplica la jugada y, al cerrar, `code_language = game.codeLanguage(state)`.
2. **[api]** `UPDATE plays … code_language`; si no es null, `UPDATE players SET preferred_code_language` en la misma transacción.
3. **[generator - generate.ts]** `history = recentChallenges(gameId, D - recentDays, D + aheadDays)` sin `D`; `await generator.verify(...)`.

### Flujos Afectados

- **jugada-y-cierre-de-partida** (ref: docs/flows/jugada-y-cierre-de-partida.md) — pasos 3 y 4
- **generacion-diaria** (ref: docs/flows/generacion-diaria.md) — paso 3

### Consideraciones Técnicas

Cambios aditivos: los juegos existentes no cambian de comportamiento. Sin `if (game_id === …)` (ADR-006). Estados de la ventana: `approved`, `published`, `voided`. Incluir test de integración de cierre con un juego de prueba.
