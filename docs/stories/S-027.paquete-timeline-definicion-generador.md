# S-027: Paquete Tech Timeline, definición y generador

**Status:** Completed
**Created:** 2026-11-10
**Source:** REQ-006

## Historia de Usuario

**Como** desarrollador de Nerdose,
**quiero** el paquete `@nerdose/game-timeline` con la lógica pura del juego (definición y generador),
**para** que la API y el generator registren Tech Timeline sin código específico, con desafíos verificables, no predecibles y sin filtrar la solución.

## Criterios de Aceptación

### CA-1: Vista pública anti-spoiler

**DADO** `toPublic(p, locale)` y un payload de 5 hechos
**CUANDO** se serializa
**ENTONCES** devuelve `{ category, prompt: p.prompt[locale], items: [{ opaque_id, label }] }` en el orden mezclado, sin fechas, notas, `fact_id` ni `correct_order`; un test de contrato lo verifica (REQ CA 1; NFR-S01, NFR-S04)

### CA-2: Estado y validación de la jugada

**DADO** `TimelineState = { order?: string[] }` con `initState → {}` e `isFinished(s) = s.order !== undefined`
**CUANDO** `moveSchema` o `applyMove` reciben solo 4 ids, un id repetido, un id desconocido o una confirmación con el estado ya terminado
**ENTONCES** devuelven `invalid_move` y el estado no cambia; con una permutación exacta de los 5 ids devuelven `{ state: { order }, feedback: null }` (REQ CA 6, 7; decisión 6)

### CA-3: Puntaje y resultado

**DADO** el orden correcto [Python, Java, Go, Docker, Kubernetes]
**CUANDO** `result` recibe [Python, Go, Java, Docker, Kubernetes], el orden exacto o el inverso
**ENTONCES** `score` es 3, 5 y 0; `win` solo con 5; `result` trae `category`, `correct_order`, `submitted_order` e `items` cronológicos con `note[locale]`; `historyLabel` es `N/5` (REQ CA 3, 4, 5, 9)

### CA-4: Stats propias

**DADO** una Play que cierra con `score` k en la categoría c
**CUANDO** se llama `reduceStats`
**ENTONCES** suma 1 a `extra.by_category[c].played` y k a `extra.by_category[c].correct` (decisión 7)

### CA-5: Distinguibilidad

**DADO** `shared/dates.ts`
**CUANDO** se comparan hechos como Go (2009, precisión año) y Node.js (2009-05), o 2009-05 y 2009-09
**ENTONCES** el primer par no se distingue y el segundo sí; una fecha idéntica nunca se distingue; el desafío con el primer par se descarta y se reintenta con el seed siguiente (REQ CA 26, 27)

### CA-6: Elección de hechos y ventana de 90 días

**DADO** `generate({ date, seed, history })` con `historySpec = { bank: 'timeline_facts', lastUsedField: 'last_used', recentDays: 90 }`
**CUANDO** se arma el desafío del 2026-12-10 y `Java` se usó el 2026-11-20
**ENTONCES** `Java` no se elige; para el 2027-02-20 sí puede elegirse; la categoría se elige entre las que tienen al menos 5 elegibles y los 5 hechos son de una misma categoría y distinguibles (REQ CA 28, 29)

### CA-7: `opaque_id` y mezcla desde el seed

**DADO** un desafío generado
**CUANDO** se revisan sus 5 `opaque_id` y el orden inicial
**ENTONCES** son únicos de 6 caracteres `[a-z0-9]` sorteados con el `rng`, su orden alfabético no coincide con `correct_order`, el orden inicial tampoco, el mismo hecho en dos desafíos tiene ids distintos, y no se usa `Math.random()` ni la hora (REQ CA 29, 30; ADR-006)

### CA-8: Verificación

**DADO** `verify`
**CUANDO** se evalúa un desafío
**ENTONCES** ejecuta en orden los checks `items_count`, `facts_in_bank`, `same_category`, `texts_bilingual`, `distinguishable`, `correct_order_consistent`, `opaque_ids`, `shuffled` y `not_used_90`, y el primer fallido va en `reason`

### CA-9: Determinismo y localización

**DADO** el mismo `seed` y `history`
**CUANDO** se genera dos veces
**ENTONCES** el payload es idéntico; consigna, categoría y notas cambian entre `es` y `en` sin alterar ids ni orden; las fechas se formatean según precisión con `Intl.DateTimeFormat` en UTC (año, mes y año, o fecha completa)

### Flujo de Interacción

#### Escenario: generar y verificar un desafío

1. **[games/timeline - generate]** Con `rng = rngFrom(seed)`: elegibles = `approved` con `last_used IS NULL OR <= D − 90` y fuera de `recentChallenges`; categoría = `rng.pick` entre las ordenadas por nombre con ≥ 5 elegibles; hechos barajados (Fisher–Yates) y agregados si son distinguibles de los ya elegidos, hasta 5.
2. **[games/timeline]** Sortea `opaque_id` y la mezcla inicial, re-sorteando hasta 10 veces si coinciden con el orden correcto; arma `{ date, category, prompt, items, correct_order }` con `items` en orden mezclado.
3. **[games/timeline - verify]** Corre los 9 checks y devuelve `{ ok, checks, reason }`.

### Flujos Afectados

- **generacion-diaria** (ref: docs/flows/generacion-diaria.md) — paso 3 con los checks de Timeline.
- **jugada-y-cierre-de-partida** (ref: docs/flows/jugada-y-cierre-de-partida.md) — `state = { order }` al cerrar, `score` y `extra.by_category`.

### Consideraciones Técnicas

**Riesgos:** pocas combinaciones distinguibles tras la ventana de 90 días. Con ≥ 100 hechos por categoría sobra; si `verify` rechaza, el pipeline reintenta con otro seed.

**Seguridad:** `toPublic` solo copia `opaque_id` y `label`; ninguna parte del generador usa fuentes no deterministas.

**Performance:** filtrado de ≤ 600 hechos y selección voraz de 5; microsegundos.
