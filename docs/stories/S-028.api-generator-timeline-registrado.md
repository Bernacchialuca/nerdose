# S-028: API y generator, Tech Timeline registrado de punta a punta

**Status:** Ready
**Created:** 2026-11-10
**Source:** REQ-006

## Historia de Usuario

**Como** jugador de Nerdose,
**quiero** que Tech Timeline se genere, se publique y se juegue por la API con las mismas reglas que los otros juegos,
**para** poder empezar, confirmar mi orden una sola vez y ver mi resultado y mis rachas.

## Criterios de Aceptación

### CA-1: Registro sin endpoints nuevos

**DADO** `timeline` agregado a los registries de `api` y `generator`
**CUANDO** se levantan los servicios
**ENTONCES** las rutas genéricas sirven Timeline sin endpoints nuevos ni cambios en `GameplayService`, y Devdle y Grep Grid se comportan igual (REQ RF 20; CA 35)

### CA-2: Abrir y empezar

**DADO** un jugador con sesión y un desafío `published` para hoy
**CUANDO** abre el juego y toca "Empezar" (también repetido)
**ENTONCES** la vista pública trae categoría, consigna y 5 hitos mezclados sin fechas, notas, `fact_id` ni `correct_order`, y se crea una sola Play `in_progress` con `state = {}` (REQ CA 1, 2)

### CA-3: Confirmaciones válidas

**DADO** el orden correcto [Python, Java, Go, Docker, Kubernetes]
**CUANDO** el jugador confirma un orden con 3 aciertos, el correcto o el inverso
**ENTONCES** la Play pasa a `lost` (3/5 y 0/5) o `won` (5/5) con `score` 0–5, el `state` guarda el orden enviado y se actualizan en la misma operación la racha de Timeline, la racha global y `extra.by_category` (REQ CA 3, 4, 5)

### CA-4: Confirmaciones inválidas

**DADO** una Play en curso
**CUANDO** se envían 4 ids, uno repetido o uno ajeno al desafío
**ENTONCES** responde `422 invalid_move`, la Play sigue `in_progress` y se puede confirmar un orden válido después (REQ CA 6, 7)

### CA-5: Partida terminada, retomar y concurrencia

**DADO** una partida terminada, o dos pestañas que confirman a la vez
**CUANDO** el jugador reabre el juego o envía otra jugada
**ENTONCES** ve el resultado con el orden correcto y su puntaje, la jugada nueva recibe `game_finished`, la Play se cierra una sola vez y las rachas se actualizan una sola vez; sin confirmar, retoma con el orden inicial (REQ CA 8, 12, 18)

### CA-6: Reglas comunes

**DADO** un `challenge_number` distinto al de hoy, un desafío `voided`, un día sin desafío, un navegador sin sesión o más de 60 jugadas por minuto
**CUANDO** el jugador abre o confirma
**ENTONCES** recibe respectivamente `challenge_expired`, `challenge_voided`, "sin desafío hoy" (día neutro), `no_session` o HTTP 429 (REQ CA 13–17)

### CA-7: Contrato anti-spoiler en la API

**DADO** toda respuesta previa al cierre
**CUANDO** se serializa y se busca cualquier `event_date`, `note`, `fact_id` o `correct_order`
**ENTONCES** no aparece ninguno (test de integración; NFR-S01, NFR-S04)

### CA-8: Home con estado real

**DADO** la home con Timeline `published`
**CUANDO** el jugador no empezó, tiene la partida en curso o la completó con 3/5
**ENTONCES** `GET /api/today` devuelve "sin jugar", "en curso" o "completado" con `history_label: "3/5"`, y Bug Hunt y Big O siguen "sin desafío hoy" (REQ CA 34)

### CA-9: Generación a 14 días y uso del banco

**DADO** que hoy es 2026-12-01 y Timeline tiene desafíos aprobados hasta el 2026-12-14
**CUANDO** corre la generación
**ENTONCES** se genera, verifica y aprueba el del 2026-12-15 con `generator_version = 'timeline@1'`, nunca el de hoy; los 5 hechos quedan con `last_used = GREATEST(last_used, D)` en `timeline_facts` y `terms` no cambia (REQ CA 25, 31)

### CA-10: Publicación y secreto del seed

**DADO** el Challenge `approved` de Timeline del 2026-12-02
**CUANDO** llega el primer request después de las 00:00 UTC
**ENTONCES** pasa a `published` junto con los de los otros juegos, y el desafío no se puede predecir desde el repositorio público sin `GENERATOR_SECRET` (REQ CA 32, 33)

### CA-11: Racha global compartida

**DADO** un jugador con partidas de Devdle y Grep Grid
**CUANDO** juega los tres juegos el mismo día
**ENTONCES** cada juego mantiene su Play y su racha, y la racha global cuenta el día una sola vez (REQ CA 35)

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| api | Bajo | `createGameRegistry([devdle, grepGrid, timeline])` en `apps/api/src/games/registry.ts`; tests de integración del ciclo y de contrato anti-spoiler | Done |
| generator | Medio | Entrada `{ gameId: 'timeline', generator, payloadSchema, version: 'timeline@1' }` en `generatorRegistry`; `ChallengePublishingRepository` multi-banco: mapa `BANKS` (`terms`, `timeline_facts`) en lugar de `LAST_USED_COLUMNS`, `bankItems(spec)` por banco y `approve` con `ApproveOptions.bank` | Pending |

### Cambios de API

#### Endpoints Existentes a Modificar

No cambian rutas, métodos ni códigos de error. Se implementan los schemas ya contratados de Timeline y se ajusta uno (ref: `docs/apis/api.yaml`):

- **`PlayState`**: nueva rama `TimelineState` (`order`: array de 5 strings, vacío mientras la Play está `in_progress`) y descripción de `EmptyState` acotada a Big O y Bug Hunt. Justificación: `result(payload, state, locale)` necesita el orden enviado al cerrar, al reabrir el juego terminado y en la etiqueta de la home.
- **`GameStatsView.extra`**: forma de timeline `{ by_category: { <category>: { played, correct } } }`.
- Ejemplos de Timeline en `GET …/today`, `POST …/move` (`200` con 3/5 y `422 invalid_move`) y `GET /api/today` (`history_label: "3/5"`).

#### Nuevos Endpoints

Ninguno.

### Cambios de Base de Datos

Ninguno de schema (la tabla viene de S-025). Se usan filas de `challenges` (`game_id = 'timeline'`), `plays` (`state = TimelineState`, `score` 0–5) y `player_game_stats` (`extra.by_category`).

### Flujo de Interacción

#### Escenario: abrir, empezar y confirmar

1. **[api - gameplay]** `GET /api/games/timeline/today` → desafío de hoy en `TodayCache` → `toPublic` → `200 GameToday`.
2. **[api]** `POST …/start { challenge_number }` → `INSERT plays … ON CONFLICT DO NOTHING` con `state = {}`.
3. **[api]** `POST …/move { challenge_number, move: { order } }` → `BEGIN; SELECT plays … FOR UPDATE` → `applyMove`; `invalid_move` → `ROLLBACK` → `422`.
4. **[api]** Cierre inmediato (`isFinished`): `result` → `UPDATE plays SET status, result, score, finished_at` → `progress.applyResult` (`extra.by_category`) → `COMMIT` → `200 { feedback: null, play, result, streaks, game_stats }`.

#### Escenario: generación y publicación

1. **[generator - fill]** Para cada fecha `D ∈ [max(today+1, LAUNCH_DATE), today+14]` sin desafío vigente: `history = { bankItems: timeline_facts approved con last_used, recentChallenges: timeline en [D−90, D−1] }`.
2. **[generator]** Por `attempt` (0–19): seed HMAC con `GENERATOR_SECRET` → `generate` → `payloadSchema.parse` → insert `draft` → `verify`.
3. **[generator]** `ok` → `approved` + `UPDATE timeline_facts SET last_used = GREATEST(last_used, D)`; `!ok` → `rejected` y siguiente intento. Agotados los 20, la fecha queda neutra.
4. **[api - publishing]** Primer request tras las 00:00 UTC → `approved` pasa a `published`.

**Manejo de errores:** `429`, `409 game_finished` / `challenge_expired` / `challenge_voided`, `401 no_session`, `404 no_challenge_today`, `500` con `ROLLBACK` completo.

### Flujos Afectados

- **generacion-diaria** (ref: docs/flows/generacion-diaria.md) — se implementa para Timeline.
- **abrir-y-retomar-juego** (ref: docs/flows/abrir-y-retomar-juego.md) — sin cambios de forma.
- **jugada-y-cierre-de-partida** (ref: docs/flows/jugada-y-cierre-de-partida.md) — cierre de Timeline.
- **cambio-de-dia-y-publicacion** (ref: docs/flows/cambio-de-dia-y-publicacion.md) — sin cambios; publica también Timeline.

### Consideraciones Técnicas

**Seguridad:** la `api` nunca serializa `challenges.payload` al jugador; el cliente nunca decide el resultado (NFR-S02); `GENERATOR_SECRET` solo en el `generator` (NFR-S03).

**Performance:** `bankItems` usa `idx_timeline_facts_pick`; `public_view` ≈ 300 B y `result` ≈ 2 KB.

**Despliegue:** el día del despliegue Timeline sigue neutro y se juega desde el día siguiente.
